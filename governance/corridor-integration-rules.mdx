# Corridor Integration Rules

Cross-corridor integration is a core CrownThrive advantage, but integration must be governed. A platform should not send users, data, content, money, or rights into another corridor merely because the systems can connect.

## Required checks

Before a cross-corridor handoff, establish:

1. **Purpose** — what customer or institutional need does the handoff solve?
2. **Identity** — which actor and role is moving?
3. **Consent** — what communications, data sharing, or enrollment permissions exist?
4. **Rights** — is the content, product, brand, data, or license permitted to move?
5. **Cultural alignment** — does CIE approve the context and representation?
6. **Eligibility** — does the receiving corridor allow this actor or asset?
7. **Data minimization** — what is the minimum information required?
8. **Economics** — what commission, fee, reward, split, or attribution applies?
9. **Support ownership** — who handles failure, questions, refund, dispute, or correction?
10. **Measurement** — what event proves the handoff occurred and whether it created value?

## Routing pattern

```text
Source corridor
→ Identity / role
→ CIE + CHLOM + policy checks
→ Approval if required
→ IO/MCP adapter
→ Receiving corridor
→ DAIL event
→ CrownLytics measurement
```

## Anti-silo / anti-sprawl rule

If two platforms solve the same public customer problem, integration design should first determine whether one is a backend engine, feature, channel, imprint, or successor rather than maintaining overlapping public promises.

## Phase 3 implication

The Orchestrator should evaluate corridor-routing rules as policy, not rely on prompt text or an agent's judgment alone.
