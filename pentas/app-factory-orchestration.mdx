# App Factory Orchestration Contract

Penta is the governed orchestrator for CrownThrive App Factory. It coordinates providers but does not inherit unlimited authority over them.

## Assignment

The App Factory program is operated through the Penta build, certification, release, routing, security, observability, continuity, governance, documentation, and economic families.

Primary responsibilities:

- PentaRoute resolves the canonical property, domain, provider, and repository topology.
- PentaGitHub governs source import, branches, CI, release lineage, and workflow dispatch.
- PentaDeploy coordinates Vercel and cPanel deployment actions.
- PentaData coordinates MySQL migration, backup, outbox, and ThriveBase projection.
- PentaBuilder supervises ephemeral Android build execution.
- PentaSecurity verifies signatures, nonces, scopes, secrets custody, and signing references.
- PentaGreen resolves economic activation where pricing, Crown Credits, Stripe, or paid entitlements are implicated.
- PentaDocs preserves architecture, runbooks, changes, and evidence boundaries.
- PentaObserve monitors health, drift, queues, outbox, artifacts, and publication freshness.
- PentaSELF and continuity families may perform bounded repair and rollback within approved scopes.
- PentaCertify independently evaluates the exact deployed state.

## Required rollout packet

Before provider mutation, Penta creates or resolves a rollout packet containing:

- property ID;
- display brand and machine slug;
- canonical hostname and aliases;
- desired GitHub repository and source ref;
- source provenance and release digest;
- runtime topology;
- database authority;
- Vercel project binding;
- cPanel account and document root;
- DNS authority;
- Vault aliases;
- CHLOM and CIE profiles;
- economic activation state;
- health and readback methods;
- rollback targets;
- certification gates.

## Authority resolution

A command is executable only after resolving:

1. caller identity and Penta assignment;
2. tenant and property scope;
3. current lifecycle state;
4. CHLOM rights and entitlement authority;
5. CIE brand and cultural constraints;
6. PentaGreen economic state when applicable;
7. Vault credential alias availability;
8. provider adapter capability;
9. idempotency and retry safety;
10. evidence and rollback requirements.

## Source-import responsibility

The current next dependency is source import into `crownthrive1/CrownThrive-App-Factory`.

Penta must distinguish:

- full 1,603-file release custody artifact;
- 992-file canonical runtime-source derivative;
- generated frontend output;
- Composer production dependencies;
- Android build artifacts;
- institutional evidence.

The source import must verify the governed runtime archive SHA-256 and expected source tree before provider-specific follow-on changes are introduced.

## Build dispatch

Penta does not provide a permanent Android build server. It authorizes a single GitHub Actions job for a single App Factory build.

Required dispatch evidence:

- application and build ID;
- GitHub repository, workflow, and ref;
- source commit;
- dispatch attempt number;
- idempotency key;
- requested build type;
- active signing reference;
- expected timeout;
- Vercel dispatch receipt.

## Build claim and callback

The runner must atomically claim the build before compilation. The callback is accepted only when:

- build ownership matches;
- per-build scope is active and unexpired;
- state transition is permitted;
- artifact metadata is valid;
- independently calculated digest matches;
- callback is idempotent.

## Provider-readback rule

A provider HTTP success or dashboard state is not sufficient. Penta performs the strongest available readback:

- GitHub commit/tree and CI status;
- Vercel deployment/project/domain state;
- cPanel release path and HTTPS health;
- MySQL schema and transactional state;
- public DNS resolver state;
- Android artifact bytes and SHA-256;
- ThriveBase event and receipt;
- ThriveApps allowed and prohibited catalog responses.

## Repair doctrine

When a dependency fails, Penta repairs the smallest affected component and continues.

Examples:

- If source identity fails, stop provider deployment and reconcile source.
- If GitHub runner startup fails before steps execute, classify provider-runner availability rather than code failure.
- If frontend output is missing, build and verify generated assets rather than committing stale output.
- If outbox delivery fails, preserve the MySQL transaction and retry the idempotent event delivery.
- If an artifact digest fails, reject the artifact and request a new build.
- If a production release fails health, retain or restore the previous release.

## Evidence preservation

Every completed dependency writes a receipt containing:

- command and subject;
- authority decision;
- provider identifiers;
- source or artifact digests;
- execution and readback timestamps;
- result and reason codes;
- rollback state;
- material exceptions;
- next dependency.

PentaDocs records operational truth suitable for readers. ThriveBase preserves machine-operable institutional state. GitHub preserves source lineage. Drive preserves governed release and evidence packages.

## Completion rule

The App Factory program is not complete when the website loads. Completion requires a real governed transaction:

`application definition → signed build request → ephemeral compilation → verified artifact → ThriveBase receipt → authorized publication → ThriveApps projection → rollback proof`.
