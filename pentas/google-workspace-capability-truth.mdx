## Sheets ownership model

The governed living-mirror model is:

`user-owned native Sheet -> governed Drive folder -> inherited service-identity writer -> ThriveBase population -> independent readback`

This avoids the service identity's direct Drive ownership quota while retaining machine write/readback capability.

A production canary created a user-owned Sheet for `penta_discovery.automation_bindings_v1`, bound table UUID `00785438-657d-4fc9-ae32-7dfe60307d88`, and service-account OAuth successfully wrote the `DATA` header. Independent connector readback observed the exact written header. The provider capability is therefore verified separately from the larger mirror orchestrator.

## API-key inspection and rotation

Both governed service identities currently have **zero** `apikeys.keys.*` IAM permissions. `keys.list` returns provider `PERMISSION_DENIED` even though `apikeys.googleapis.com` is enabled.

Current dispositions:

- API-key inspection: `HOLD_IAM`
- API-key rotation: `HOLD_IAM_D3`

Rotation must not begin by deleting the existing key. When IAM and a fresh CHLOM D3 invocation are present, the required sequence is:

1. create the replacement key;
2. apply exact API/application restrictions;
3. bind all governed consumers;
4. perform provider and runtime readback;
5. supersede the old key in PentaCredentials/CHLOM/DAIL;
6. retire the old key only after the overlap/readback window passes.

Raw key strings, OAuth tokens and service-account private keys are prohibited from PentaDocs, GitHub, DAIL payloads and ordinary logs.
