## PentaDocs

> **Canonical registry member.** Documentation is a projection of governed state, not a maturity or authority promotion.

PentaDocs maintains CrownThrive's human-readable and machine-readable institutional knowledge across Drive, repository source, structured ledgers, DAIL evidence, public documentation, support surfaces, product guides, and historical archives.

Its operating purpose is to make the CrownThrive Convergent Ecosystem understandable, recoverable, auditable, and reusable without allowing prose to silently replace runtime truth or institutional authority.

## Mission and responsibilities

PentaDocs is responsible for:

- discovering and binding exact sources;
- preserving provenance, stable identity, version, and supersession lineage;
- reconciling conflicts against an explicit source hierarchy;
- producing audience-specific human guidance and machine-readable knowledge;
- maintaining architecture, runbook, standard, changelog, help-center, developer, operator, owner, and auditor views;
- projecting current state to Drive, repository source, public documentation, and required product/support destinations;
- recording review, merge, deployment, and provider-readback state separately;
- updating documentation, delta, and reconciliation ledgers;
- preserving historical versions rather than silently rewriting institutional memory;
- publishing corrections and continuity instructions when a source or public claim changes.

PentaDocs does not create legal, rights, licensing, payment, credential, provider-write, production, or D3 authority.

PentaDocs must not become a second DAIL ledger. Documentation records reference canonical event IDs, hashes, receipts, source versions, or structured ledgers.

## Current DAIL documentation profile

The current DAIL architecture is the **Cursor-Controlled Capacity Mesh**:

```text
One canonical CHLOM DAIL chain
→ Machine / Human / Hybrid / Cursor projections
→ Cursor coordination
→ 500K Continuity Lock
→ Head / Continuity / Archive routing
→ PentaBalancer admission
→ PentaGas capacity accounting
→ MeshAssist and approved capacity donors
→ one canonical writer and terminal readback
```

The governing architecture preserves:

- one canonical chain and writer;
- Four-Part Cursor projections rather than four ledgers;
- deterministic 500K lock activation and 450K release hysteresis;
- 70% Head / 30% Continuity / 0% Archive while locked;
- explicit separation between continuity route allocation and donor compute allocation;
- PentaBalancer as admission control, not authority;
- PentaGas as capacity accounting, not authority;
- bounded MeshAssist and donor contribution;
- retired predecessor drain clocks as preserved lineage, not active schedulers;
- append-only correction and terminal readback.

See [DAIL Cursor-Controlled Capacity Mesh](/chlom/dail-cursor-controlled-capacity-mesh).

## Cross-surface state model

PentaDocs uses explicit states instead of one ambiguous "done" flag:

```text
DISCOVERED
→ SOURCE_PRESENT
→ EXTRACTED
→ RECONCILED
→ DOCUMENTED
→ REVIEWED
→ MERGED
→ DEPLOYED
→ PROVIDER_READBACK
→ PUBLIC_CURRENT
```

`CONFLICT`, `SUPERSEDED`, `RETIRED`, and named `HOLD_*` states may occur at any appropriate boundary.

A repository branch can be `DOCUMENTED` while public deployment is `HOLD_MERGE_OR_DEPLOYMENT`. A public page can be `PUBLIC_CURRENT` while the underlying runtime remains `HOLD_PRODUCTION_CERTIFICATION`. These states must not be collapsed.

## Source authority hierarchy

Unless a system-specific contract says otherwise, resolve mutable claims in this order:

1. Current provider or runtime readback.
2. Canonical DAIL event and terminal receipt.
3. Governed database ledger or registry.
4. Accepted repository source and exact commit.
5. Governed Drive source and institutional phase records.
6. Public PentaDocs or help-center projection after provider readback.
7. Historical documents as lineage unless explicitly reaffirmed.

A lower source does not silently override a higher current source. Conflicts are preserved in a contradiction or adjudication record.

## Documentation release workflow

1. Resolve the exact subject identity and sources.
2. Read current mutable runtime/provider state where applicable.
3. Preserve the predecessor document, revision, repository source, or ledger row.
4. Reconcile contradictions and authority boundaries.
5. Build human and machine projections.
6. Validate frontmatter, links, routes, stable IDs, schemas, access boundaries, and evidence references.
7. Update PentaDocs change, delta, and reconciliation ledgers.
8. Update CHLOM, DAIL phase/release, master IP/asset, product, or support records where applicable.
9. Commit repository source and record the branch/commit/PR.
10. Merge and deploy through the governed documentation release path.
11. Read back the public provider route and expected content.
12. Append terminal release evidence and next-review triggers.

See [PentaDocs Cross-Surface Documentation Contract](/standards/pentadocs-cross-surface-documentation-contract).

## Inputs, outputs, events, and state

- **Inputs:** exact source records, provider/runtime readback, DAIL receipts, accepted repository source, Drive records, structured ledgers, and accountable-owner adjudications.
- **Outputs:** human pages, machine manifests, standards, changelogs, runbooks, source maps, ledgers, publication packets, and correction records.
- **Events:** material documentation changes, conflicts, reconciliations, reviews, merges, deployments, readbacks, corrections, supersessions, and retirements.
- **State:** documentation, runtime, provider, authority, rights, release, and public state remain separately typed.
- **Retention:** preserve predecessor source and correction lineage according to the source system, CHLOM, DAIL, privacy, and rights contract.

## Authority and non-authorities

Execution eligibility remains `false` in the current namespace projection. PentaDocs may prepare, validate, reconcile, and route documentation under its operating contract; material provider writes require a separately authorized release path.

PentaDocs must never:

- manufacture PASS, maturity, production, deployment, provider readback, or public-current state;
- manufacture legal, licensing, ownership, payment, fiduciary, security, credential, or D3 authority;
- expose plaintext secrets or protected evidence;
- treat documentation confidence as runtime evidence;
- erase historical contradictions or failed releases;
- bypass CHLOM, PentaHybrid, PentaAssure, PentaStatus, or required human/professional review;
- infer that a page exists publicly merely because repository source exists.

## Reliability and failure recovery

Treat these as explicit states:

- stale source or observation boundary;
- missing Drive or repository source;
- repository merge pending;
- documentation provider deployment pending;
- broken navigation or link;
- public route mismatch;
- conflicting current and historical claims;
- missing authority or accountable owner;
- restricted data exposure;
- machine/human projection mismatch;
- incomplete master-ledger propagation.

On failure:

1. preserve the first failed boundary;
2. stop any unsupported parity claim;
3. repair the smallest source or projection;
4. validate and read back again;
5. append a correction or supersession record;
6. update the next-review trigger.

## Testing and certification

PentaDocs certification should cover:

- source identity and authority;
- contradiction reconciliation;
- human/machine semantic parity;
- frontmatter and schema validation;
- navigation and link validation;
- restricted/public information boundaries;
- stable IDs and supersession;
- repository review and exact commit;
- deployment and provider readback;
- ledger and DAIL evidence projection;
- rollback/correction behavior;
- failure-state honesty.

`DOCUMENTED ≠ TESTED ≠ CERTIFIED ≠ AUTHORIZED ≠ DEPLOYED ≠ PUBLIC_CURRENT`.
