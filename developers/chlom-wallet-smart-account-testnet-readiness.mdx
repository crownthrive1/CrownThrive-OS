# CHLOM Wallet smart-account testnet readiness

**State:** `SPECIFIED_NOT_DEPLOYED`  
**Target chain:** Sepolia / `eip155:11155111`  
**Broadcast:** disabled  
**Production signer:** none  
**Money movement:** none

The next CHLOM Wallet blockchain step is not “launch a token.” It is to prove that a governed CrownThrive wallet identity can safely bind to a modular smart account on a public test network while preserving passkey security, provider portability, rights separation and rollback evidence.

## Current account-abstraction baseline

Upstream `eth-infinitism/account-abstraction` now identifies **v0.9.0** as its latest ERC-4337 release. The release states a v0.9 EntryPoint candidate at:

```text
0x433709009B8330FDa32311DF1C2AFA402eD8D009
```

Current Sepolia explorer evidence shows contract activity at that address. This makes v0.9 the appropriate **research baseline** for new CHLOM testnet work rather than silently freezing the older v0.8 planning record.

That is a feature of the evidence model: a plausible or even likely address is not enough for a privileged singleton that validates smart-account operations.

## Candidate stack

```text
CHLOM stable wallet ID
```

The account implementation and factory remain deliberately unselected. Selecting them before completing the security/recovery criteria would create artificial momentum instead of evidence.

## WebAuthn registration gate

The source-controlled registration verifier now supports a narrow controlled-test profile:

- `webauthn.create` client-data validation;
- expected challenge binding;
- HTTPS origin and RP-ID binding;
- CBOR attestation-object parsing;
- RP-ID hash validation;
- user-presence and user-verification flags;
- attested credential data extraction;
- ES256 / P-256 COSE public-key validation;
- deterministic credential commitment;
- `none` attestation profile only.

The `none` attestation profile intentionally makes **no authenticator trust/attestation claim**. Production attestation policy remains a separate security/privacy/product decision.

The existing assertion verifier separately performs ES256/P-256 signature validation. Registration and assertion therefore now have independent controlled-test contracts rather than one vague “passkey supported” claim.

## Why factory/account selection is still open

Before CHLOM picks an account implementation or factory, the candidate must support the actual CrownThrive requirements:

- WebAuthn/passkey validation without exporting signing secrets;
- recoverable credential rotation;
- explicit module allowlisting and removal;
- deterministic deployment or equally strong identity binding;
- ERC-1271-compatible signature validation where required;
- compatible ERC-4337 version/EntryPoint;
- no hidden paymaster dependency;
- no mandatory vendor-hosted custody;
- exportable state and provider exit;
- independent audit evidence appropriate to the implementation;
- clear failure and recovery behavior.

ERC-7579 interface compatibility alone is insufficient evidence that a module or account implementation is safe.

## Non-broadcast manifest

The machine-readable readiness manifest explicitly contains:

```yaml
account_implementation_selected: false
factory_selected: false
user_operation_built: false
simulation_completed: false
broadcast_enabled: false
transaction_hash: null
money_movement: false
```

This keeps construction moving while making it impossible to confuse research with a deployed wallet.

## Next smart-account gates

1. Reconcile the EntryPoint v0.9 source-artifact mismatch with direct runtime-code evidence.
2. Select a minimal account implementation candidate and record exact source/version/license/audit evidence.
3. Select a factory or deterministic deployment pattern.
4. Bind the selected account to the WebAuthn registration/assertion/recovery profile.
5. Generate a complete unsigned UserOperation candidate.
6. Simulate it against Sepolia without broadcasting.
7. Run recovery/module-abuse/adversarial tests.
8. Obtain independent security disposition.
9. Create a separate signer/testnet-broadcast authority receipt.
10. Only then submit the first governed testnet transaction.

No public testnet or mainnet transaction is authorized by this page.
