# CHLOM Wallet Continuity Factory & Automation v1

This controlled-test layer turns continuity from architectural intent into an institutional runtime contract.

It binds the CrownThrive proprietary factory, CHLOM Wallet execution envelopes, Policy Assurance, identity pins, DAIL lineage, recovery controls, modules, plugins, API/MCP contracts and read-only oracle observations into one fail-closed continuity graph.

## Factory projection

The source catalog defines **24 continuity blueprints** projected across the **25 active proprietary-factory domains**, producing **600 deterministic candidate assets**. Projection is intentionally separate from factory generation advancement: the continuity suite remains bound to generation 48 and may not claim generation 49 merely because continuity projections exist.

Asset classes include pallets, modules, plugins, API contracts, MCP toolsets, code libraries, script runners, metaprotocol IP, prompt packs, agent contracts, ML feature pipelines, ML advisory models, oracle connectors, truth snapshots, heartbeat rules, identity pins, dependency graphs, schedulers, recovery plans, rollback scripts, observability probes, chaos scenarios, CI gates and documentation artifacts.

In addition to those 600 domain projections, ThriveBase records **48 exact-head direct implementation components** covering the actual pallets, modules, plugins, MCP contracts, API contract, metaprotocol candidates, prompts, source code, test/chaos scripts, runtime SQL and ML advisory model. Direct components and projected assets are versioned by exact source head rather than overwritten in place.

## Continuity fleet

The suite binds four existing Gen6 factory continuity/recovery identities by exact stable agent ID, DID and SHA-256 fingerprint:

- Assurance lane
- Culture lane

- Platform lane

A heartbeat label is not accepted as proof of freshness. Freshness is derived from the recorded heartbeat timestamp and deadline. An expired heartbeat automatically degrades continuity to HOLD; the continuity layer never manufactures a replacement heartbeat.

## Interfaces

The controlled-test package adds four Wallet continuity pallets, six modules, four internal plugin candidates, eight MCP contracts and one OpenAPI contract. It also binds the pre-existing `ct.chlom.backup-recovery` module and `ct.plugin.google-drive-continuity` provider-portability surface.

The MCP and HTTP API contracts are source-complete but **not represented as live servers**. ThriveBase registers them fail-closed as `HOLD_UNBOUND_MCP_SERVER` and `CONTRACT_ONLY_HOLD_UNBOUND_SERVER`. The internal continuity runtime operates through governed private SQL functions and automation until an independently verified server binding exists.

## Continuity algorithms

The source-controlled runtime implements:

- canonical hashing and deterministic asset generation;
- exact CrownThrive request-budget semantics (`-1` unlimited local ceiling, `0` zero requests, positive integers exact ceilings, `null` unresolved/fail closed);
- evidence-expiry evaluation;
- heartbeat freshness derivation;
- read-only oracle validation;
- strictest-wins ECAC/HOLD/DENY composition;
- deterministic continuity dependency evaluation;
- reversible recovery planning;
- a fixed-weight ML-compatible risk advisory pipeline.

The ML score is advisory only. It cannot issue a final ECAC/HOLD/DENY decision or upgrade a deterministic HOLD/DENY.

## Automation

ThriveBase registers ten private cadence-aware continuity jobs. One hourly `pg_cron` scheduler evaluates which jobs are due and performs internal, fail-closed reconciliation only. The scheduler may downgrade stale current-state heartbeat labels and append continuity receipts; it may not create independent review, refresh a heartbeat without evidence, make a provider write or activate production.

Continuity lanes cover heartbeat invalidation, exact-head reconciliation, evidence expiry, oracle reconciliation, dependency drift, truth snapshots, recovery drills, cultural continuity, deterministic factory projection and documentation synchronization.

## Oracle and truth closure

Six oracle contracts cover GitHub exact source head, ThriveBase runtime evidence, DAIL evidence lineage, CHLOM identity pins, Mintlify documentation projection and read-only chain observation. GitHub/ThriveBase/DAIL/identity are registered as controlled-test evidence sources. Mintlify direct-runtime and chain-readback bindings remain HOLD until real adapter evidence exists.

Provider success is evidence, not institutional truth. A continuity truth snapshot closes only across the registered source head, private ThriveBase state, DAIL/evidence lineage, exact agent identity, heartbeat freshness, dependency state and oracle evidence. Missing or stale evidence results in HOLD; forbidden authority boundaries result in DENY.

## Security boundary

The private runtime uses RLS + FORCE RLS, no anon/authenticated table access, service-role-only reads and append-only version/evidence records. Recovery is non-destructive by default and all live economic, Rights, provider and chain authority remains outside this tranche.
