## Authentication

The specification declares two `apiKey` header schemes:

```text
X-Public-ID: <public API identifier>
X-Secret-Key: <server-side secret>
```

Both headers are required by the documented secured operations.

<ParamField header="X-Public-ID" type="string" required>
  Public API identifier from the Collab Portal Secure API account. It is paired with the server-side secret and does not authorize an operation by itself.
</ParamField>

<ParamField header="X-Secret-Key" type="string" required>
  Server-side Secure API secret. Use a placeholder in examples and a governed secret reference at runtime; never expose the value in public source, browser code, screenshots, logs, messages, or evidence payloads.
</ParamField>

<RequestExample>

```bash Read project metadata after authorization
curl --request GET \
  --url "https://portal.crownthrive.com/secure-api/project/meta" \
  --header "X-Public-ID: <public-id>" \
  --header "X-Secret-Key: <server-side-secret>"
```

</RequestExample>

The request above shows the verified method, URL, and header names only. It is not permission to use a production credential and no response example is supplied because this page does not reproduce an exact current account-specific response body.

Production credentials must remain server-side. They must not be committed to this public repository, Mintlify, browser JavaScript, screenshots, Gmail, GitHub comments, logs or DAIL payload bodies.

## Project-manager integration design

Because the verified API can **read and update existing projects but cannot create projects**, the initial safe pattern is:

<Steps>
  <Step title="Use a pre-created institutional project">
    Select an existing, approved CrownThrive project; do not invent or assume a project UID.
  </Step>
  <Step title="Discover account-specific fields">
    Read `GET /project/meta` and pin the actual project and custom-field identities.
  </Step>
  <Step title="Resolve and preserve current state">
    Prefer `GET /project/uid/{uid}` after bootstrap. Read the existing object and preserve fields outside the bounded update.
  </Step>
  <Step title="Validate the proposed diff">
    Allow only the approved status/information/custom-field values and exclude billing, legal, financial, rights, sensitive IP, and client/staff authority mutations.
  </Step>
  <Step title="Write and read back once">
    Use `PUT /project/uid/{uid}`, then immediately retrieve the project and compare the expected values.
  </Step>
  <Step title="Record or fail closed">
    Record the non-sensitive request/response evidence reference. On `401`, `404`, `422`, `429`, unknown outcome, or semantic mismatch, do not retry blindly; open a governed delta and use the documented fallback.
  </Step>
</Steps>

## Project schema constraints

The public OpenAPI model exposes project fields including:

- `uid`;
- `name`;
- `status`;
- `start_date`;
- `end_date`;
- `due_time`;
- `info_description` for staff-visible project information;
- `info_title_client` and `info_description_client` for client-visible information;
- `business_sector`;
- `estimated_value` and currency;
- time-spend requirement;
- `project_custom_fields`;
- client, secondary clients, teammates, team and leader on read views.

The update model reuses project list/view components. Until a live test proves partial-update behavior, the adapter must not assume PUT is PATCH-like. The safe implementation is schema discovery \+ current-object read \+ validated update payload \+ read-after-write verification.

## Project lookup types

`GET/PUT /project/{type}/{identifier}` supports:

- `uid` — exact project UID;
- `name` — exact project name;
- `contains_the_following` — project-name substring;
- `most_recent` — identifier must be `true`.

Production automation should prefer stable UID after initial discovery. Name/substring lookup is a bootstrap/recovery method, not the durable identity layer.

## API rate and failure behavior

The contract documents HTTP `429` for request-limit exhaustion and instructs users to inspect monthly usage in **Integrations → Secure API**. The portal UI snapshot separately showed a 20,000-request monthly account limit at the time of inspection. Treat the UI limit as a dated account-state observation, not a permanent provider guarantee.

The OpenAPI example inside the generic `Error-429` schema still mentions a 200-request monthly maximum. That conflicts with the current account UI. The account UI is newer account-specific evidence; the generic example should not be used as CrownThrive's current limit.

The adapter must maintain:

- request budget and monthly usage awareness;
- bounded exponential backoff for safe idempotent reads only;
- no automatic mutation replay after unknown outcome;
- read-after-write verification;
- dead-letter/delta record for failed writes;
- secret-safe logging;
- request correlation IDs in CrownThrive's own adapter layer when implemented.

| Failure or ambiguity | Documented handling |
| --- | --- |
| `401` during screenshot-transcribed credential test | Classify as transcription authentication failure; do not label the provider credential invalid or brute-force variants |
| `429` | Respect request-budget limits; safe idempotent reads may use bounded backoff |
| `404` or `422` | Preserve the response evidence, open a delta, and do not retry a mutation blindly |
| Unknown write outcome | Read back before any further decision; never assume failure or success |
| Account UI vs OpenAPI quota conflict | Keep both dated sources; do not hard-code either as a permanent guarantee |

## OpenAPI security-definition anomaly

The contract correctly defines `Public-ID` and `Secret-Key` as `apiKey` header schemes. Several operations nevertheless place scope-like strings such as `read:contacts`, `write:contacts`, `read:project` or `write:project` inside the security requirement arrays.

For OpenAPI `apiKey` schemes those arrays are not OAuth scope grants. They should be treated as provider documentation hints, not as a verified authorization model. Some labels are also inconsistent—for example certain company/project reads reference contact/write labels.

Therefore:

- do not derive least-privilege policy solely from those strings;
- verify actual key permissions through the portal/admin configuration and live safe tests;
- record observed behavior separately from the OpenAPI annotation;
- never elevate a key because a Swagger label says `write:*`.

Dummy mode can validate selected read-contract behavior without touching production data. It cannot prove CrownThrive production credential validity, project existence, account-specific custom fields or write capability.

## Initial automation authority

### Automatically permitted after credential binding and testing

- `GET /project/meta`;
- `GET /projects`;
- `GET /project/uid/{uid}`;
- read-after-write verification;
- bounded read-only health/contract checks.

### Conditionally permitted D1/D2 project update

`PUT /project/uid/{uid}` may update **only** approved project-management status fields after:

- project UID is pinned;
- `/project/meta` field identities are pinned;
- current project object is read;
- proposed diff contains no billing, client authority, legal, financial, rights or sensitive-IP mutation;
- validation passes;
- read-after-write verification succeeds.

A failed or ambiguous write opens `docs_delta_opened` / project-integration incident state and falls back to GitHub \+ Gmail.

### Not part of the default PM loop

- CRM contact/company creation or mutation;
- marketing subscription changes;
- Worlds assignment;
- project economics changes;
- client/staff assignment changes;
- any operation whose effect cannot be verified from the contract/current object.

## Secure adapter runtime

A server-side runtime exists in the connected CrownThrive Supabase project as Edge Function `collab-portal-pm` **version 2**. Version 2 adds a Supabase Vault bridge so credentials can be bound server-side without entering public source or depending on an unavailable environment-secret setter.

```yaml
runtime_provider: Supabase Edge Functions
function: collab-portal-pm
runtime_version: 2
runtime_state: active_vault_capable_read_certification_blocked_on_exact_credential_copy
caller_authentication: Supabase JWT required
collab_portal_credentials_in_source: false
secret_sources:
  - environment_when_managed_out_of_band
  - supabase_vault_service_role_bridge
vault_function: public.get_runtime_secret
vault_function_public_execute: revoked
write_gate_default: closed
allowed_read_actions:
  - health
  - project_meta
  - list_projects
  - find_project
conditional_write_action:
  - update_project_status
conditionally_allowed_fields:
  - status
  - info_description
  - project_custom_fields
read_before_write: required
read_after_write: required
unknown_outcome_blind_retry: prohibited
```

The runtime resolves `COLLAB_PORTAL_PUBLIC_ID`, `COLLAB_PORTAL_SECRET_KEY` and `COLLAB_PORTAL_ALLOW_WRITE` from server-side configuration. If environment values are absent it can read named Supabase Vault secrets through a service-role-only bridge. Raw values are not returned by health state, written to Git/Mintlify or placed in project-manager logs.

A separate internal read-certifier reaches the SuitePro API using Vault values without exposing them to the caller. The first `GET /project/meta` certification attempt reached the provider and returned `401`. Because the source values were manually transcribed from a low-resolution screenshot, this result is classified as `screenshot_transcription_auth_failed`, not `provider_credential_invalid`. The exact copied Public ID and Default key must replace the screenshot transcription before the certification can advance.

`COLLAB_PORTAL_ALLOW_WRITE` remains false. No production PUT has been attempted. A temporary bootstrap certification function created during runtime testing was immediately retired to a JWT-protected `410 disabled` endpoint after the internal certifier became available.
