# CHLOM WalletKit API & MCP Contract

CHLOM WalletKit is the developer-facing capability family for integrating CrownThrive platforms and approved partner systems with CHLOM Wallet OS.

**Current status:** `CANDIDATE / CONTROLLED_TEST`  
**Mutation authority:** disabled unless separately approved  
**Live money movement:** not authorized by this contract

## Design goals

- one stable CrownThrive contract over replaceable providers;
- Stripe-specific fields stay inside the Stripe adapter;
- chain-specific fields stay inside chain adapters;
- every mutation is idempotent and correlation-bound;
- payment, entitlement, fulfillment, allocation and settlement are distinct states;
- APIs expose only the least data required by the caller;
- provider/chain outage does not corrupt institutional truth;
- MCP tools mirror the same authority classes as HTTP APIs.

## Required headers

Consequential requests should carry:

```http
Authorization: Bearer <approved-token>
Idempotency-Key: <caller-generated-stable-key>
X-CrownThrive-Correlation-ID: <stable-correlation-id>
X-CrownThrive-Contract-Version: 1
```

Secrets, provider signing material and raw wallet keys are never accepted in ordinary payload fields.

## Provider event envelope

```json
{
  "provider": "stripe",
  "provider_event_id": "provider-native-event-id",
  "event_type": "payment.succeeded",
  "occurred_at": "2026-08-21T00:00:00Z",
  "environment": "test-or-live",
  "signature_state": "verified",
  "payload_digest": "sha256-hex",
  "correlation_id": "ct-correlation-id"
}
```

The envelope proves that CHLOM received provider evidence. It does not state what rights or fulfillment should result.

## CHLOM value event

```json
{
  "wallet_id": "ct-wallet-id",
  "event_type": "payment.provider_succeeded",
  "asset_code": "USD",
  "amount_minor": 10000,
  "provider": "stripe",
  "provider_ref": "provider-reference",
  "schedule_ref": "ct.econ.example.v3",
  "entitlement_ref": null,
  "correlation_id": "ct-correlation-id",
  "idempotency_key": "merchant-or-system-stable-key",
  "occurred_at": "2026-08-21T00:00:00Z",
  "metadata": {}
}
```

CHLOM adds its own sequence, payload digest and chain hash when the event is accepted.

## Allocation preview

Allocation preview is a pure calculation. It cannot initiate a transfer.

Request:

```json
{
  "gross_minor": 10001,
  "rules": [
    {"leg_code": "operating", "bps": 7000},
    {"leg_code": "rights", "bps": 2000},
    {"leg_code": "thrivefund", "bps": 1000}
  ]
}
```

Invariant:

```text
sum(bps) = 10,000
sum(amount_minor) = gross_minor
```

If the schedule does not total `10,000` basis points, the function fails closed. Rounding remainder is deterministic and must not disappear from the gross amount.

## Entitlement decision

An entitlement response should make the distinction between payment and rights explicit:

```json
{
  "decision": "allow | deny | hold | require_review",
  "wallet_id": "ct-wallet-id",
  "asset_ref": "ct.asset.example",
  "license_ref": "ct.license.example.v2",
  "valid_until": null,
  "evidence_level": "E4_transactional",
  "policy_version": "ct.policy.entitlement.v4",
  "correlation_id": "ct-correlation-id"
}
```

A `payment.succeeded` provider event can be one input. It is never the entire decision.

## Unified Value Receipt

The CHLOM Unified Value Receipt is the human/machine explanation object that lets one wallet view show Money, Rights, Rewards and Impact while keeping the underlying records separate.

```json
{
  "value_receipt_id": "ct.uvr.example",
  "wallet_id": "ct-wallet-id",
  "source_event_ref": "ct-event-id",
  "money": {"asset": "USD", "amount_minor": 4900, "state": "reconciled"},
  "rights": {"entitlement_ref": "ct.entitlement.example", "state": "active"},
  "rewards": {"reward_ref": "ct.reward.example", "state": "earned"},
  "impact": {"obligation_ref": "ct.impact.example", "state": "calculated"},
  "policy_version": "ct.policy.uvr.v1",
  "receipt_digest": "64-hex",
  "anchor_state": "not_anchored"
}
```

A Unified Value Receipt is not a substitute for the Stripe/provider financial receipt, governing license, reward ledger or ThriveFund settlement evidence. Corrections append lineage rather than rewriting a prior receipt.

## Proof receipt

```json
{
  "proof_id": "ct.proof.01...",
  "subject_ref": "ct.record.example",
  "algorithm": "sha256",
  "digest": "64-hex",
  "anchor": {
    "state": "not_anchored | candidate | confirmed_test | confirmed_production",
    "network_id": null,
    "transaction_ref": null
  }
}
```

Raw private evidence should not be included in a public proof receipt.

## Stripe boundary

The first Stripe commercialization architecture is for CrownThrive to charge its own CHLOM software customers. Marketplace seller payouts, platform application fees, custody and cross-border transfers are separate future gates.

A future Stripe webhook integration must:

1. verify the provider signature before processing;
2. store an immutable receipt/digest;
3. deduplicate by provider event ID;
4. use a stable correlation ID and idempotency key;
5. translate provider state to a CHLOM event;
6. evaluate entitlement and economic policy independently;
7. make fulfillment idempotent;
8. reconcile refunds/disputes/credit notes/reversals;
9. preserve the provider's native reference for audit;
10. fail closed when policy, rights or schedule authority is missing.

## Chain-adapter boundary

Chain adapters normalize:

- network ID;
- account ID;
- transaction reference;
- block/finality state;
- contract/interface version;
- event/log reference;
- proof digest;
- gas/fee observation;
- failure/reorg state.

The adapter may not redefine CHLOM ownership or license meaning merely because a contract or token exists on-chain.

## Certification suite

Before a mutation-capable WalletKit release, the integration suite must prove at least:

- duplicate/reordered webhook handling;
- provider timeout and retry behavior;
- amount/currency mismatch HOLD;
- refund/dispute reversal lineage;
- payment succeeded but rights missing HOLD;
- entitlement issuance and fulfillment replay safety;
- Unified Value Receipt correction/reversal lineage;
- economic schedule version mismatch HOLD;
- 10,000-bps conservation;
- provider outage/degraded mode;
- database restore and replay;
- chain reorg/finality behavior where applicable;
- invalid signature rejection;
- privilege-escalation rejection;
- no secrets in logs or public artifacts.

Only exact-version evidence can promote the corresponding release.
