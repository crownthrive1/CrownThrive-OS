## Program purpose

Recovered CHLOM research called for an open-source pallet library, a Developer DAO and bounty program. Those are historical target ideas, not present production claims. The current institutional need is a **controlled builder program** that can evolve toward broader participation without giving contributors unsafe authority.

## Builder pathways

- internal CrownThrive developer;
- approved contractor;
- ecosystem platform developer;
- integration partner;
- open-source contributor;
- security researcher;
- documentation contributor;
- SDK maintainer;
- certified implementation partner.

## Contributor lifecycle

<Steps>
  <Step title="Apply and establish identity">
    Record the contributor and, when applicable, the represented organization. Do not infer authority from an email address, community profile, or prior relationship.
  </Step>
  <Step title="Complete applicable terms">
    Resolve confidentiality, IP assignment or contribution-license terms, disclosure rules, and the public/private boundary for the exact work package.
  </Step>
  <Step title="Receive bounded access">
    Assign the minimum repository, tool, role, and sandbox scopes. Production credentials are excluded by default.
  </Step>
  <Step title="Accept a specification">
    Pin the issue or work package, expected output, acceptance tests, evidence requirements, review owner, and stop conditions.
  </Step>
  <Step title="Implement and test">
    Work through a branch and review path using synthetic data, secret scanning, dependency/security checks, and the required tests or evals.
  </Step>
  <Step title="Complete review and record the outcome">
    Security, rights, code, and documentation review remain separate where applicable. Acceptance, release evidence, and the contribution record must identify the exact revision and scope.
  </Step>
</Steps>

## Required controls

- contributor identity and organization record;
- NDA/confidentiality where needed;
- IP assignment or contribution license appropriate to the work;
- no production credentials by default;
- least-privilege repository/tool access;
- synthetic test data;
- branch/PR review requirements;
- secret scanning;
- dependency/security checks;
- test/eval evidence;
- DAIL contribution/release events once available.

## Access and environment boundary

| Surface | Default posture | Promotion requirement |
| --- | --- | --- |
| Public documentation/source | Only rights-cleared, public-safe material | Normal branch, validation, and review gates |
| Private source or evidence | No access by implication | Explicit role, purpose, confidentiality, and least-privilege record |
| Sandbox/test | Synthetic data and bounded test identities | Approved work package and environment-specific credentials |
| Production read | Not granted by contributor status | Exact operation, data class, owner, and read-certification evidence |
| Production write | Closed by default | Separate operation-specific authority, rollback/readback, and independent review |
| Security testing | No implicit permission | Approved scope and disclosure rules |

## Bounty model

A future bounty program can cover bugs, missing adapters, SDKs, docs, tests, accessibility, security findings, pallet prototypes and integration fixtures. Each bounty should define scope, acceptance tests, rights/IP terms, reward type, review owner, disclosure rules and whether work may be public.

No historical CHM/token reward model is assumed current. Early rewards can use ordinary contracted compensation, approved cash bounties, credits, CrownRewards, affiliate economics or other legally reviewed methods.

## Developer progression

Builders can progress through verified capability tiers such as:

1. Sandbox Developer
2. Verified Contributor
3. Platform Integrator
4. CHLOM Implementation Developer
5. Certified Partner / Maintainer

Tier names and privileges remain version-controlled.

<Info>
  A tier label is a capability record, not a credential, employment classification, professional license, production role, payment promise, or sovereign authority. The applicable access record controls.
</Info>

## CrownThriveU relationship

CrownThriveU can host developer onboarding, API tutorials, security training, CHLOM architecture education and certifications. Completion can become a prerequisite for higher-risk scopes.

## Phase 3 priority

Sprint 0 should create the contributor/authority schema and repository access rules. Phase 3 services can then produce real developer work packages instead of relying on informal access and chat instructions.

## Testing, acceptance, and support

A work package is ready for acceptance only when the specified tests/evals pass at the exact revision, the public/private boundary is intact, secrets and dependencies have been checked, review findings are resolved or held, and the acceptance owner records the result. A green test cannot award a contributor tier, deploy a provider change, or certify unrelated production behavior.

If identity, scope, terms, acceptance criteria, compensation, disclosure handling, or the review owner is missing, stop before implementation and use the [support request workflow](/workflows/support-request). Technical contributions must also follow the [API integration standards](/technology/api-integration-standards) and [documentation authoring playbook](/standards/pentadocs-authoring-and-review-playbook).
