</Warning>

## Source boundary

The founder-supplied developer documentation establishes:

- the exact API host and six endpoint URLs;
- use of the `Authorization` header with the API key;
- JSON request content type for Delete and Get Single Image;
- form/data request content type for Upload;
- request parameter names and example value shapes;
- response object shapes;
- a displayed `v4.0.0` product version.

The supplied material **does not explicitly show HTTP verbs**. The institutional contract therefore records each verb as `pending_source_verification`; agents may not infer a verb merely from endpoint naming or request-body shape.

## Runtime and secret architecture

```text
caller with valid CrownThrive/Supabase JWT
        ↓
thrivetools-opt-api-control
        ↓
server-side get_runtime_secret
        ↓
Supabase Vault primary credential
        ↓
ThriveTools OPT API
```

A matching recovery alias is stored separately in Vault for credential continuity. The adapter reports only whether configuration exists; it never returns the credential value.

## Current adapter behavior

`thrivetools-opt-api-control` v1 is intentionally fail-closed:

- `health` reports adapter/configuration state without exposing the key;
- `capabilities` returns the documented endpoint catalog and risk classes;
- all provider read dispatch returns `provider_dispatch_not_certified` until HTTP methods and authenticated read behavior are certified;
- all upload/delete mutation dispatch remains disabled.

## Certification sequence

1. verify exact HTTP verb for each endpoint from authoritative provider/application evidence;
2. execute `check-status` as the first bounded authenticated D0 read;
3. validate status code, JSON content type and response schema;
4. certify `get-images`, `get-media` and `get-single-image` with bounded schemas;
5. register read operations in the central API/MCP control plane only after exact contract validation;
6. leave upload/delete disabled unless separately authorized;
7. if upload is later enabled, certify file-size/type/compression/media-upload semantics and read-after-write evidence;
8. if delete is later enabled, test reversible/non-permanent behavior first and govern permanent deletion separately;
9. record request hashes/latency/status without logging provider payloads containing restricted data;
10. preserve export/provider-exit and object-custody behavior for GATE-007 continuity.

## Phase wiring

- **Phase 2.99:** document contract, bind credentials server-side, resolve child identity, keep dispatch fail-closed, reconcile stale API/engine/domain records.
- **Phase 3:** the Institutional Core may register certified D0 OPT tools after method/read proof; this does not make OPT the first Phase 3 pilot or bypass the A → B → C sequence.
- **Phase 4:** OPT may become a shared media/image adapter used by approved platform cohorts after data/rights/storage boundaries are accepted.
- **Phase 5\+:** commerce/publication workflows may use OPT only when their source-asset rights, output custody, costs/quotas and recovery paths are governed.
- **Phase 10/20 continuity:** provider exit, credential recovery, source/original preservation and image-object portability must be reproducible.
