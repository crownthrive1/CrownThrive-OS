# CHLOM MCP, Public Identity and Modular Integration

CHLOM's developer surface follows the metaprotocol rule: integrations depend on stable CHLOM contracts, not on one storage provider or blockchain implementation.

<Info>
  Current implementation state: **controlled test**. Public resolver readback is verified. The authenticated CHLOM control-plane/MCP service is deployed; independent end-to-end authenticated MCP client certification remains open.
</Info>

## Public identity resolver

CHLOM uses opaque public IDs with a DID projection:

```text
ctid_<opaque identifier>
  -> did:chlom:ctid_<opaque identifier>
```

A resolver response may contain:

```json
{
  "public_id": "ctid_...",
  "did": "did:chlom:ctid_...",
  "state": "active",
  "public_keys": [
    {
      "algorithm": "Ed25519",
      "purpose": "authentication",
      "public_jwk": {}
    }
  ]
}
```

Private signing material is not part of this contract.

Public IDs are designed for stable public verification. They do not encode an SSN, email address, password, government identifier or private key.

## Dedicated MCP server contract

Canonical server identity:

```yaml
server_id: ct.mcp.chlom-core
stage: controlled_test
protocol_version: "2026-07-28"
auth: governed authenticated service/user context
```

The dedicated server keeps CHLOM capability evolution independent from unrelated CrownThrive provider adapters.

The registry also reserves names for capabilities that remain disabled until their runtime and approval gates exist:


Registering the contract does not activate the operation.

D3 rights, binding-license, money, treasury, production-token and irreversible remedy actions remain human-reserved under CrownThrive's approval constitution.

## Module discovery

Clients should discover capabilities rather than hard-code assumptions about the whole CHLOM estate.

A module record includes:

```yaml
module_id: ct.chlom.dail
canonical_name: Decentralized Autonomous Information Ledger
version: 0.1.0
state: prototype
authority_ceiling: D2
self_healing_class: rollback_capable
mcp_enabled: true
api_enabled: true
```

A capability record adds:

```yaml
capability_id: ct.cap.chlom.dail.public-verify
module_id: ct.chlom.dail
kind: api
risk_class: D0
state: test
public_safe: true
hot_swappable: true
```

This structure lets CHLOM evolve without requiring every consumer to upgrade simultaneously.

## DAIL developer contract

DAIL is append-only from the application perspective.

Applications should submit or receive events with:

```yaml
event_type:
entity_type:
entity_id:
entity_version:
correlation_id:
causation_id:
authority_basis:
visibility_class:
payload:
```

The server generates and verifies integrity metadata such as payload hashes, previous-event references and event hashes.

Consumers must not treat a database UPDATE as a correction mechanism. Corrections are new DAIL events.

## Fingerprint contract

The first controlled-test fingerprint primitive is SHA-256 over canonical input.

Fingerprinting establishes byte/text integrity; it does not by itself prove ownership, authorship or legal rights.

Future media fingerprints may add acoustic, image/perceptual or semantic similarity methods, but those results remain evidence signals rather than automatic ownership judgments.

## Agent registry

Agent introspection is machine-readable. Consumers can inspect:

- stable agent ID;
- parent/orchestrator;
- class;
- autonomy level;
- D0–D3 ceiling;
- lifecycle state;
- module scope;
- schedule profile;
- voting eligibility;
- self-healing permission;
- heartbeat/health state.

The registry does not reveal private prompts, secrets or protected reasoning.

## Algorithm registry

The developer surface can expose public-safe algorithm contracts and evaluation state while keeping restricted implementation details sealed.

Examples include:

- fingerprint/hash integrity;
- DAIL chain verification;
- rights-conflict detection;
- oracle aggregation/outlier detection;
- anomaly ensembles;
- graph-risk analysis;
- Sybil-risk research;
- model drift;
- self-healing root-cause classification;
- tokenomics simulation;
- policy resolution;
- DLA conflict checking;
- ZK scheme selection.

A registry entry marked `disabled` or `specified` must not be treated as callable production functionality.

## Platform adapter rule

Virality Music and KJV/Sermon Toolkit currently have controlled-test bindings to CHLOM identity/evidence continuity. Their DLA/LEX commerce bindings remain staged as specifications until rights and transaction gates close.

Every future CrownThrive platform can implement the same adapter contract:

```text
platform
  -> stable platform ID
  -> CHLOM actor/service identity
  -> capability discovery
  -> scoped API/MCP credentials
  -> DAIL events
  -> platform-specific feature flags
```

This is how CHLOM becomes reusable across the ecosystem without forcing every platform into one application.

## Security requirements

Never place in browser code, public docs or client-side MCP configuration:

- Vault passwords;
- private signing keys;
- unrestricted service-role credentials;
- protected algorithm thresholds;
- sealed rights evidence;
- treasury keys;
- production blockchain custody secrets.

Public keys and opaque public IDs are intentionally public. Private keys are not.
