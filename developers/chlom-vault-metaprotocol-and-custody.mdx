# CHLOM Vault Metaprotocol & Custody

**State:** CONTROLLED_TEST / PUBLIC-CONTRACT-ONLY / GOVERNED_HOLD FOR CANONICAL ACCEPTANCE  
**CHLOM:** Compliance Hybrid Licensing and Ownership Model.  
**Ledger:** DAIL — Decentralized Autonomous Information Ledger.  
**Phase effect:** none. This contract does not advance Phase 3.

This contract defines how CrownThrive agents, APIs, MCP tools and skills may use protected institutional assets without making the protected body a public or client-returnable object.

## Vault-first protected-asset rule

A materially novel CrownThrive algorithm, calibration, private policy, canon, doctrine, operating method, prompt grammar, signing material, provider credential, proprietary script, defensive rule, private evidence topology or comparable moat is classified before distribution.

Protected bodies classified as `TRADE_SECRET`, `TRADE_SECRET_CANDIDATE`, `RESTRICTED_INSTITUTIONAL`, or `PUBLIC_CONTRACT_RESTRICTED_IMPLEMENTATION` are held in an approved encrypted secret/custody plane. Public repositories and documentation may expose only an approved public contract: stable identifier, version, digest, permitted input/output classes, lifecycle, high-level invariants and reason-code classes.

A public contract never implies that a protected implementation body is public, downloadable or directly callable by an unauthenticated client.

## Current algorithm custody projection

The current controlled-test registry contains **20 versioned algorithms** across CHLOM, Generation 6 and CIE. Every registered algorithm has an individual restricted custody capsule. Where a protected implementation bundle is actually materialized, custody is additionally bound to that versioned implementation bundle. Where an implementation is not yet materialized or enabled, the algorithm remains `HOLD`/`disabled` rather than being inferred from its interface.

The public projection intentionally does **not** publish Vault aliases, secret identifiers, private implementation source, exact calibration, weights, private feature vectors, defensive thresholds, private evaluation corpora or credential topology.

## Non-exportable capability gateway

Protected assets are consumed through purpose-bound server-side capabilities rather than raw-secret retrieval.

```text
caller identity + authority + purpose + task scope
  -> capability contract
  -> classification / lifecycle / policy check
  -> optional oracle / independent-verifier check
  -> server-side secret injection or protected implementation invocation
  -> sanitized result envelope
  -> DAIL / invocation receipt
```

The gateway has no supported raw-secret export operation. Passwords, provider tokens, private keys, algorithm bodies and protected scripts are never legitimate client results.

Current logical operations include:

- sanitized capability description;
- protected algorithm invocation;
- restricted hybrid-identity resolution receipt;
- encrypted-archive metadata;
- novel-asset intake/classification candidate;
- provider proxy candidate; and
- allowlisted restricted-script execution candidate.

Provider proxy and restricted-script execution remain fail-closed until an exact provider adapter or sandboxed allowlisted handler is independently certified. Arbitrary dynamic code execution is not part of this contract.

## Hybrid identity and fingerprint privacy

CHLOM separates public continuity from private institutional identity.

For an eligible person/actor:

1. a stable public SHA-256 fingerprint is assigned under the stable identity profile;
2. a separate random private subject identifier is created;
3. the private identifier is **not derived** from the public fingerprint;
4. the mapping is immutable, forced-RLS and non-public;
5. public knowledge of the fingerprint does not provide a computational route to the private identifier.

Authorized server-side CHLOM/oracle workflows may resolve the mapping only with a declared purpose and authority basis. Every successful resolution produces a restricted audit event and DAIL receipt. Public/client responses may expose the public fingerprint plus a mapping digest/receipt state, but not the private subject identifier itself.

A fingerprint establishes version/identity-reference integrity within its defined profile. It does not by itself prove ownership, legal rights, authorship, accreditation, DID/VC control or cryptographic nonrepudiation.

## DAIL before blockchain

DAIL is the current canonical logical event ledger. It preserves version, evidence, approval, correction, access-resolution and archive history while the later blockchain/anchor layer remains separately gated.

Future decentralized anchoring may consume DAIL event hashes and approved CHLOM identity/capability proofs. It must not require re-exposing the protected source material. The present design is therefore intentionally portable: protected data stays private while approved digests, events and public references can later be anchored to another verification substrate.

## Encrypted monthly archive

CrownThrive maintains one **logical monthly archive stream**, with immutable revisions inside the month when material custody changes.

Each revision contains encrypted protected-asset/custody state and a small machine-readable manifest/checksum set. The archive encryption key remains in the protected server-side custody plane and is not copied into GitHub, public documentation, client code or the archive itself.

Archive lifecycle is additive:

`prepared -> encrypted -> uploaded -> verified -> superseded`

`superseded` means historical, not deleted. A newer monthly revision points back to the prior one. Historical archive bytes and DAIL events remain recoverable.

## Novel-asset Foundry

Agents may identify a repeated or materially novel CrownThrive method and open a protected-asset intake candidate. Candidate examples include algorithms, operating methods, orchestration designs, canons, doctrines, security methods and reusable private capability packs.

Novelty detection does not establish patentability, ownership or commercial readiness. It creates a classified candidate that can be:

`captured -> independently reviewed -> vaulted -> fingerprinted -> capability-bound -> public-contract-only -> licensed/packaged candidate`

Public commercialization may describe the capability and its permitted outcome without transferring the CrownThrive trade-secret implementation unless a separately accepted license explicitly says otherwise.

## Authority and speed

Routine D0/D1 evidence append, fingerprint assignment, telemetry, reconciliation, archive sealing, safe candidate creation and deterministic custody operations do not require a new sovereign vote merely because they occurred.

D2 material actions follow their applicable independent-verification/authority policy. D3 remains human-reserved. A Vault row, hash, CI pass, agent output or oracle recommendation cannot manufacture authority.

## Preservation doctrine

Nothing is silently deleted to make current state look cleaner.

Retired logic, old algorithm versions, prior fingerprints, superseded archives, denied attempts, failed migrations and conflicting evidence remain historical records. Active execution may move to a successor version, but the predecessor is represented explicitly as superseded, revoked, archived or held.

## Public/private invariant

The public CrownThrive Support/Mintlify plane MUST remain capable of explaining:

- what a protected capability does;
- what version is referenced;
- its public contract digest;
- its lifecycle and authority ceiling;
- what evidence class is required; and
- why an invocation was accepted, held or denied.

It MUST NOT reveal the protected body needed to reproduce CrownThrive's private implementation, credentials, secret topology, or restricted identity mapping.
