CHLOM Wallet is an institutional wallet/economic-evidence control plane. It records governed provider receipts, settlement provenance, value class, reversals, and chain-hashed ledger events. Production activation does **not** convert CHLOM Wallet into a custodian of customer cryptocurrency.

## Stripe adapters

Two Stripe funding classes are distinguished:

- Fiat payment processing: `ct.adapter.stripe.wallet.v1`
- Stablecoin payments: `ct.adapter.stripe.stablecoin-payments.v1`

The stablecoin adapter is deployed in production and fails closed at the provider-enablement boundary.

### Stablecoin tender model

The adapter is modeled for Stripe-supported stablecoin payments including USDC, USDP, and USDG on provider-supported networks. Stripe handles customer-wallet interaction and provider settlement. CHLOM Wallet records the payment as evidence and does not claim custody of the customer token.

When a verified Crown Credits top-up settles, the Crown Credits ledger automatically projects a secret-free settlement event into the CHLOM Wallet append-only evidence ledger. If the Stripe payment method is crypto, the event is tagged with the stablecoin adapter and stablecoin tender provenance.

The projection never creates an entitlement, rights grant, public claim, or on-chain custody by inference.

## Production settlement authority

Production Stripe reconciliation is readback-authoritative. A provider callback or success status is evidence, not final economic truth.

The system independently reads Stripe provider objects before recording a verified settlement. A live webhook may accelerate processing when a provider destination is available, but loss or absence of a dedicated destination does not weaken the readback verification rule.

## Provider capability state

The adapter may be `production` while the provider state is `provider_enablement_pending`. This distinction is mandatory.

Current Stripe platform configuration is machine-read before use. If Stripe reports crypto unavailable, no Checkout flow may pretend crypto is enabled.

## Wallet continuity control plane (Phase 3)

CHLOM Wallet continuity is a separate, production-available **private** control plane over the shared `chlom_wallet` continuity substrate. It observes continuity health, evaluates evidence freshness, records read-only oracle observations, and produces plan-only recovery output. It never moves money, writes providers, grants rights, broadcasts chain actions, or executes destructive recovery.

Use it for server-to-server operational tooling that needs continuity status, evidence freshness checks, or reversible recovery planning. Do not use it from browsers, public clients, or any integration that cannot hold server-side credentials.

### Access model

The provider binding is the Supabase Edge Function `chlom-wallet-continuity` (`ACTIVE`, `verify_jwt=true`). The function additionally requires equality with the runtime service-role credential. Requests without the service-role credential receive `403` with `forbidden_service_role_required`.

The function exposes three surfaces:

- `GET /health` — bounded service and boundary state.
- `POST /mcp` — JSON-RPC MCP endpoint (protocol version `2026-07-28`).
- `/api/*` — HTTP routes mapped one-to-one onto the MCP tools.

### Continuity MCP tools

Eight service-role-only operations are bound for server-to-server use:

| Tool | Purpose | Risk class |
| --- | --- | --- |
| `chlom_wallet_continuity_status_v1` | Read exact-head continuity status | D0 |
| `chlom_wallet_continuity_assets_v1` | List sanitized continuity factory projections | D0 |
| `chlom_wallet_continuity_dependencies_v1` | Read the continuity dependency graph | D0 |
| `chlom_wallet_continuity_expiry_evaluate_v1` | Evaluate evidence freshness; stale evidence downgrades to HOLD | D1 |
| `chlom_wallet_continuity_oracle_observe_v1` | Record a sanitized read-only oracle observation | D1 |
| `chlom_wallet_continuity_recovery_plan_v1` | Create a reversible, non-destructive recovery plan | D2 |
| `chlom_wallet_continuity_truth_snapshot_v1` | Run the fail-closed continuity tick and append a truth snapshot | D1 |
| `chlom_wallet_continuity_factory_projection_v1` | Read the deterministic factory projection summary | D1 |

Fresh evidence resolves to `ECAC`. Stale or invalid evidence resolves to `HOLD`. Explicit forbidden boundaries resolve to `DENY`. Recovery output is plan eligibility only; `execution_authorized` and `automatic_destructive_action` remain `false`.

Example server-to-server call:

```bash
curl -X POST "https://<project-ref>.supabase.co/functions/v1/chlom-wallet-continuity/mcp" \
  -H "Authorization: Bearer $SUPABASE_SERVICE_ROLE_KEY" \
  -H "Content-Type: application/json" \
  -H "MCP-Protocol-Version: 2026-07-28" \
  -H "Mcp-Method: tools/call" \
  -H "Mcp-Name: chlom_wallet_continuity_status_v1" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"chlom_wallet_continuity_status_v1","arguments":{}}}'
```

The service-role credential is server-side infrastructure. Never embed it in browser code, return it in responses, or expose it through MCP content.

## Hard boundaries

- No secret material in responses.
- No provider success → entitlement inference.
- No provider success → rights grant.
- No provider success → public performance claim.
- No stablecoin tender → CHLOM custody inference.
- No Crown Credits → crypto-asset inference.
- No deletion of governed ledger history.
- Provider reversals append compensating evidence; history is not silently rewritten.
