## Start an adapter record

<Steps>
  <Step title="Resolve the platform identity">
    Use the stable platform ID and current lifecycle record. Do not derive identity from a hostname, vendor account, or UI label alone.
  </Step>
  <Step title="Classify the available interface">
    Identify whether the bounded capability is public, partner, private, vendor-adapted, MCP, event/webhook, batch, or not yet available.
  </Step>
  <Step title="Pin the contract and environment">
    Record the current base URI by environment, version, auth, scopes, schemas, side effects, data classes, events, limits, and deprecation policy from authoritative evidence.
  </Step>
  <Step title="Map institutional ownership">
    Separate the provider/platform record from CrownThrive identity, rights, order, entitlement, approval, evidence, and claim authority.
  </Step>
  <Step title="Test and promote by scope">
    Advance documentation, authentication, sandbox, integration, production-read, production-write, and monitoring states separately.
  </Step>
</Steps>

## Federation outcome

CrownThrive should operate a **federated API architecture**. Platforms remain modular, while CrownThrive IO provides consistent identity, governance, routing, metering, documentation and observability.

## Platform API registry

Each platform record should carry:

| Field | Purpose |
| --- | --- |
| `platform_id` | Stable CrownThrive identity |
| `api_status` | none / research / vendor / adapter / private / partner / public |
| `api_owner` | Responsible engineering owner |
| `provider` | First-party or vendor dependency |
| `base_uri` | Environment-specific endpoint reference |
| `api_version` | Current contract version |
| `auth_method` | OIDC/OAuth, API key, signed request, service credential, etc. |
| `scopes` | Least-privilege capabilities |
| `events` | Canonical emitted/consumed events |
| `webhooks` | Supported callback contracts |
| `rate_policy` | Quotas and throttles |
| `data_classes` | Data handled by the interface |
| `chlom_touchpoints` | Rights/rules/approval/evidence requirements |
| `sandbox` | Safe test capability |
| `deprecation` | Sunset and migration policy |

## Interface classes

<Tabs>
  <Tab title="Direct APIs">
    **Public API** is approved external developer access. **Partner API** is an authenticated ecosystem or enterprise integration. **Private API** is limited to controlled CrownThrive service-to-service or platform-to-platform calls.
  </Tab>
  <Tab title="Adapters">
    A **vendor adapter** normalizes a third-party contract without making the provider authoritative for every institutional record. A **batch connector** governs import/export where a supported real-time interface does not exist.
  </Tab>
  <Tab title="Tools and events">
    An **MCP tool** exposes one bounded agent-facing operation with explicit permissions. An **event/webhook adapter** handles a versioned and authenticated event contract. Neither class creates authority beyond the underlying operation.
  </Tab>
</Tabs>

## Canonical API domains for Phase 3

The institutional API should grow around stable capability namespaces rather than brand-specific database tables:

- `/identity`
- `/organizations`
- `/roles`
- `/assets`
- `/rights`
- `/licenses`
- `/policies`
- `/approvals`
- `/events`
- `/evidence`
- `/cases`
- `/revenue-rules`
- `/entitlements`
- `/products`
- `/campaigns`
- `/affiliates`
- `/impact`
- `/platforms`

Platform-specific APIs can extend these without changing their core meaning.

<Info>
  Names such as `/identity` and `/assets` are semantic namespace candidates. Builders must not concatenate them with a guessed hostname or treat them as callable until a versioned interface record supplies an exact base URI and contract.
</Info>

## Contract standards

- semantic/versioned contracts;
- OpenAPI for REST interfaces where practical;
- GraphQL only where its query flexibility is materially useful;
- idempotency for consequential writes;
- signed webhooks;
- typed errors;
- correlation/request IDs;
- explicit pagination;
- least-privilege scopes;
- audit emission for consequential operations;
- documented retry and rate-limit behavior;
- backward-compatible deprecation windows.

## Platform onboarding

As each CrownThrive platform is added, the developer team performs inventory, provider/API inspection, data mapping, identity mapping, rights mapping, event mapping, adapter contracting, sandbox work, testing, approval, production promotion, and version monitoring in that order.

The registry therefore scales incrementally with the portfolio instead of delaying the entire ecosystem until every platform has a perfect API.

## Authentication, failures, and support

Authentication is recorded per interface; there is no federation-wide credential in this page. A registry row must distinguish human session, service identity, OAuth/OIDC, API key, signed request, provider token, and unauthenticated public access where applicable, along with its scope and tenant boundary.

No common error envelope, retry schedule, pagination contract, or idempotency key is defined here. An adapter must preserve the provider's exact failure semantics while exposing a stable CrownThrive-facing contract only after those semantics are tested. Unknown mutation outcomes must not be replayed blindly.

Use [API endpoint discovery](/developers/api-endpoint-discovery-and-adapter-registry) to establish a missing contract, [SDKs and sandbox](/developers/sdk-sandbox-webhooks) for safe test design, and the [support request workflow](/workflows/support-request) for ownership, credential, or production-state conflicts.
