# CHLOM Wallet Passkey & Smart-Account Adapter

**State:** `SPECIFIED / CONTROLLED_TEST`  
**Production passkey wallet:** not claimed  
**Cryptographic WebAuthn assertion verifier:** not yet certified  
**Smart-account deployment:** not authorized  
**Chain broadcast:** disabled

The CHLOM Wallet user-experience target is passkey-friendly: normal customers should not need to learn seed phrases, bundlers, EntryPoints, chain IDs or module standards merely to use CrownThrive services. The backend still preserves explicit authority, recovery, replay protection and chain identity.

## Standards profile

The design references public interoperability standards rather than inventing custom cryptography:

- **WebAuthn Level 3** for public-key credential ceremonies and relying-party/origin binding;
- **CAIP-2** for chain identifiers;
- **CAIP-10** for chain-qualified account identifiers;
- **ERC-4337** as the primary Ethereum account-abstraction interoperability model;
- **ERC-7579** as a modular smart-account interface candidate.

Adoption of a standard does not itself authorize chain deployment.

## Controlled-test challenge service

The restricted wallet runtime now has a server-side challenge-control layer for registration/authentication/recovery-step-up experiments.

The service:

- generates a random 32-byte challenge;
- returns the challenge only to the controlled caller;
- persists the **SHA-256 challenge digest**, not the raw challenge;
- binds the challenge to a stable CHLOM wallet;
- binds relying-party ID and HTTPS origin;
- enforces a bounded expiration window;
- consumes a challenge once;
- rejects origin/RP mismatch;
- rejects exact replay.

A canary passed:

```yaml
wrong_origin_state: rp_or_origin_mismatch
valid_consume_state: CONSUMED_TEST
replay_state: challenge_already_consumed
raw_challenge_persisted: false
credential_verified: false
smart_account_deployed: false
money_movement: false
result: PASS_PASSKEY_CHALLENGE_CANARY
```

`credential_verified:false` is intentional. This canary proves challenge/origin/replay control, **not** full authenticator-data/client-data/signature verification.

```json
  "recovery_policy": "separate_governed_record_required",
  "broadcast": false,
  "deploy": false,

```

The intent is a governance/evidence artifact, not a `UserOperation` and not a transaction.

## WebAuthn boundary

The adapter records only what is required to bind a controlled wallet-registration intent:

- credential identifier commitment;
- RP ID;
- HTTPS origin;
- COSE algorithm identifier;
- resident-key/user-verification policy indicators;
- declared transports;
- exact policy/version references.

The public reference code does not generate or export signing material. The raw credential identifier is committed to a deterministic digest before it is used as a CHLOM cross-system evidence key.

Origin/RP mismatch fails closed. HTTP origins fail closed for this production-target profile.

### Still required for a real WebAuthn verifier

The production path must still verify the complete ceremony, including the exact challenge, `clientDataJSON`, authenticator data, RP ID hash, origin/type, user-presence/user-verification policy, credential public key/algorithm, signature, replay/counter behavior where meaningful, registration attestation policy if adopted, and credential lifecycle/revocation state.

The current controlled-test challenge service must not be represented as that full verifier.

## Chain and account identity

CAIP-2 identifies the chain independently of the provider. CAIP-10 composes that chain ID with an account address. CHLOM keeps its stable wallet ID above both:

```text
ct.wallet.*
   ↓
CAIP-2 chain ID
   ↓
CAIP-10 account ID
```

This lets a CrownThrive wallet survive chain/provider migration without making the blockchain address the sole institutional identity.

Wildcard/multichain proposals are not assumed stable merely because draft standards exist. Production-target records require an explicit chain ID.

## ERC-4337 boundary

ERC-4337 defines `UserOperation`, `EntryPoint`, bundler and account-validation concepts. CHLOM Wallet does not currently create or submit a production `UserOperation`.

A later adapter must bind, at minimum:

- explicit chain ID;
- supported EntryPoint version/address;
- account factory version;
- nonce/replay policy;
- signer/passkey validation module;
- paymaster policy if any;
- gas/fee limits;
- simulation result;
- exact deployment/runtime code digest;
- independent security review.

## ERC-7579 boundary

ERC-7579 is considered for modular account interoperability. A module cannot be silently enabled merely because it conforms to an interface. CHLOM still requires an allowlisted module record, code identity, authority scope, revocation path and security evidence.

High-risk module examples include session keys, delegated execution, recovery modules and spending controls. Their convenience does not waive authorization.

## Recovery model

Recovery is a separate governed state machine. A future production design must define:

- passkey loss/replacement;
- additional credential enrollment;
- device theft;
- guardian/multisig recovery where used;
- delay/step-up requirements for material changes;
- account-module replacement;
- founder/institutional succession for treasury wallets;
- compromised-credential quarantine;
- audit and correction evidence.

No recovery secret is represented in public documentation.

## Reference tests

The controlled public reference suite proves:

- CAIP-2 validation;
- CAIP-10 composition;
- HTTPS origin requirement;
- RP/origin binding;
- deterministic credential commitment;
- duplicate-transport normalization;
- smart-account intent remains `broadcast:false` and `deploy:false`;
- external account binding remains `candidate_unverified` until deployment evidence exists.

## Promotion gates

Production passkey/smart-account activation requires complete WebAuthn cryptographic verification, credential lifecycle/recovery drills, exact account/factory/module implementation, EVM/testnet execution evidence, independent security review/audit appropriate to risk, chain/provider exit proof, privacy review and a current Phase gate. Until then, this remains a controlled interoperability construction lane.
