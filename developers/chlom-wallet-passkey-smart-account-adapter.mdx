# CHLOM Wallet Passkey & Smart-Account Adapter

**State:** `CONTROLLED_TEST_ACTIVE / SPECIFIED_NOT_DEPLOYED`  
**Production credential activation:** disabled  
**Smart-account deployment:** not authorized  
**Chain broadcast:** disabled  
**Money movement:** disabled

CHLOM Wallet is designed to present one simple CrownThrive identity and wallet experience while preserving strict separation among authentication, rights, money, rewards, impact, proof and blockchain adapters. Passkeys remove seed-phrase ceremony from the customer experience; they do not erase authority, recovery, replay, counter, custody or chain-governance requirements underneath.

## Standards and implementation profile

The current lane uses public interoperability standards and a patched verification library rather than custom cryptography:

- **WebAuthn Level 3** for public-key credential ceremonies, relying-party binding and authenticator data;
- **ES256 / P-256** as the bounded controlled-test credential algorithm;
- **CAIP-2** for chain identifiers;
- **CAIP-10** for chain-qualified account identifiers;
- **ERC-4337 v0.9** as the account-abstraction hashing and transaction-intent profile;
- **ERC-7579** as a modular-account interface candidate;
- **`@simplewebauthn/server@13.3.2`** for deployed controlled-test registration and assertion verification.

Adopting or testing a standard does not authorize production credentials, an account deployment, a signer, a bundler, a paymaster or a blockchain transaction.

## Challenge and credential data plane

The private `chlom_wallet` runtime now enforces the following model:

1. A 32-byte challenge is generated for registration, authentication or recovery step-up.
2. Only the SHA-256 challenge digest is persisted.
3. The challenge is bound to the authenticated subject, stable CHLOM wallet, RP ID, exact HTTPS origin, purpose and expiration.
4. A challenge is consumed once; exact replay fails closed.
5. Failed verification attempts append HOLD receipts and cancel the challenge after the bounded threshold.
6. Registration persists only the credential public key, public-key digest, nonreversible credential lookup/commitment digests, counter, transports, device/backup state and policy evidence.
7. Assertion verification binds the stored public key, challenge digest, RP ID, origin, user presence, user verification, signature and counter policy.
8. Every accepted controlled-test ceremony appends a CHLOM ledger event and an immutable verification receipt.

Raw challenges, raw credential identifiers and private key material are not persisted by the governed wallet tables.

## Stable wallet and chain identity

CHLOM keeps its institutional wallet identifier above providers and chains:

```text
ct.wallet.*
  ├── WebAuthn credential binding
  ├── provider/payment aliases
  ├── CAIP-2 chain identity
  └── CAIP-10 account identity
```

A blockchain address is an adapter binding, not the sole institutional identity. This preserves provider and chain portability and prevents account-address churn from erasing wallet history.

## ERC-4337 v0.9 unsigned intent

The public-safe reference implementation now builds the exact **unsigned** ERC-4337 v0.9 `PackedUserOperation` intent and EIP-712 hash envelope for the candidate Sepolia EntryPoint.

The builder:

- implements Keccak-256 and validates known vectors;
- uses the upstream v0.9 `PackedUserOperation` type string;
- packs verification/call gas and priority/max fee into the required 128-bit pairs;
- hashes `initCode`, `callData` and empty `paymasterAndData` according to the controlled profile;
- constructs the `ERC4337` / `1` EIP-712 domain;
- produces deterministic struct, domain and final UserOperation hashes;
- rejects signatures, paymasters and nonempty factory/init code;
- marks opaque call data HOLD;
- never submits the intent to a bundler or RPC endpoint.

The deterministic test vector is:


A Solidity harness independently recomputes the struct hash, domain separator and final UserOperation hash on an isolated in-memory EVM. This is a hash-construction cross-check, not a live EntryPoint simulation.

## Promotion gates

Production or public-testnet activation still requires:

- authenticated browser registration and assertion canary against the deployed runtime;
- production authenticator-attestation policy decision;
- credential replacement, compromise and recovery drills;
- target EntryPoint runtime-code-hash verification;
- reviewed smart-account implementation and factory;
- reviewed account call-data and factory-init-code encoders;
- local and public-testnet EntryPoint simulation;
- independent security review appropriate to value at risk;
- governed signer and recovery authority receipts;
- explicit governed testnet broadcast authorization;
- customer-facing wallet deployment, privacy review and current phase approval.

Until those gates pass, CHLOM Wallet remains a controlled identity, evidence and transaction-intent system—not a deployed blockchain wallet.
