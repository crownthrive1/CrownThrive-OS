### Website-root installation

For a website using this exact ThrivePush website identity, deploy the file as `/thrivepusher.js` at the website origin root so the service worker receives the intended scope. Do not substitute another website ID/pixel key or rename the file without generating a site-specific governed artifact.

The current CrownThrive control plane has no authorized cPanel/Verpex file-manager connector, so the repository/Supabase/Drive copies do **not** prove that the file has been deployed to the live website root. That deployment remains an explicit verification item.

## Credential state

The founder supplied a current API key, but the connected secure-write layer rejected direct Vault insertion. The attempted write did not persist the value. The intended aliases are:

```text
thrivepush_api_key
thrivepush_api_key_recovery
```

No agent may work around the secret-write control by encoding, obfuscating, committing, emailing or logging the key. Until an approved secret-write path binds both aliases, authenticated provider dispatch remains fail-closed.

## Certification sequence

1. bind primary and recovery Vault aliases through an approved secret-write path;
2. extract exact paths, methods and schemas for the documented families;
3. certify bounded D0 reads first;
4. add output-schema validation, timeouts, request audit and purpose/data-class rules;
5. register only certified D0 MCP tools;
6. separately govern campaign/personal-notification/automation mutations, consent/suppression behavior and rollback before any provider write is enabled;
7. verify the root service-worker deployment and update the platform registry.

## Security and privacy boundaries

Subscriber identifiers, browser/device data, consent/suppression state, campaign audiences, notification history and team/account data may be personal or operational data. Public docs expose interface structure only, not customer records or credential material.
