# CrownThrive Services Stack Developer Contract

**Stack ID:** `ct.stack.crownthrive-services-stack`  
**Plugin:** `ct.plugin.crownthrive-services-stack`  
**MCP server:** `ct.mcp.crownthrive-services-stack`  
**State:** controlled test

## Integration principle

Applications integrate with a stable CSS lane contract. Provider-specific behavior is isolated behind an adapter and provider binding.

Every material route records:

- lane ID;
- contract ID and exact version;
- source and destination identity;
- provider binding;
- required capability and authority;
- data classes;
- least-data policy;
- idempotency strategy;
- retry and rate policy;
- rollback or compensation;
- readback;
- evidence and verifier.

Read tools expose sanitized contracts and lifecycle state. Plan tools create bounded institutional records only; they do not directly mutate a provider. Certification requires the exact bound verifier and current evidence.

## Public/private contract

Public-safe outputs may expose stable IDs, names, versions, purposes, authority classes, lifecycle states, evidence classes, reason codes, provider-binding state and cryptographic digests.

Restricted implementation includes credentials, private identity mappings, protected routing logic, algorithm weights, provider topology, account-specific billing evidence, customer data, confidential control evidence and protected adapters.

## Request-budget semantics

- `-1` means no CrownThrive-local monthly ceiling;
- `0` means disabled;
- a positive integer means an explicit CrownThrive-local monthly ceiling;
- `NULL` means unresolved and fail closed.

Provider throttles, quotas, billing, included capacity, contracts and abuse controls remain authoritative.

## Activation gates

A lane is not `shared_service_active` until its exact contract, provider binding, authentication/capability, CaaS control map, negative tests, continuity, rollback/readback and independent certification are current.

Provider capability alone is insufficient.
