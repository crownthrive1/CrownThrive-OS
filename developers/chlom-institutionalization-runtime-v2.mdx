# CHLOM Institutionalization Runtime v2

**State:** `ACTIVE_REAL_PACKAGE_INGESTED`  
**Phase:** 2.99  
**Service:** `ct.service.chlom-wallet-institutionalize-v2`  
**Originating specialist:** `ct.agent.chlom-wallet-settlement`  
**Release authority:** none

The Institutionalization Runtime closes the gap between source-controlled engineering evidence and THIVEBASE institutional memory. It accepts only a deterministic package that is bound to the CrownThrive Support repository, the expected workflow, the frozen source snapshot, the committed manifest, and a GitHub-signed OIDC identity.

## Trust path

```text
GitHub-hosted workflow
  -> short-lived GitHub OIDC JWT
  -> RS256/JWKS signature verification
  -> issuer, audience, repository, repository-ID and owner-ID checks
  -> exact workflow, actor, branch and PR checks
  -> current PR/branch readback from GitHub
  -> frozen-source ancestry proof
  -> committed-manifest readback
  -> canonical manifest and package-digest verification
  -> append-only THIVEBASE package and ingest receipts
```

The function does not accept a Supabase user JWT as its trust root. `verify_jwt` is disabled at the platform middleware so the function can apply its own exact GitHub OIDC verification. A missing or invalid GitHub bearer token fails closed.

## RDLF deployment-lineage fence

The incident is now protected by a dedicated deterministic algorithm:

```yaml
algorithm_id: ct.algorithm.chlom.runtime-deployment-lineage-fence.v1
short_name: RDLF
semantic_version: 1.0.0
state: CONTROLLED_TEST
```

RDLF binds five layers before a runtime can be represented as healthy:

1. exact function/service identity and deployment version;
2. exact deployed EZBR digest and custom OIDC authentication mode;
3. exact source blob plus required module exports;
4. deployed unauthenticated `401 github_oidc_bearer_required` liveness;
5. real package and GitHub OIDC ingest continuity with every live/authority field false.

The historical version-3 deployment is retained as a negative observation and must evaluate to HOLD. The corrected version-4 deployment must evaluate to PASS.

## Immutable GitHub subject support

The runtime supports both the earlier repository subject format and GitHub's immutable repository/owner-ID subject format. Both remain pinned to:

```yaml
repository: crownthrive1/CrownThrive-Support
repository_id: '1336348391'
repository_owner: crownthrive1
repository_owner_id: '315660018'
```

Wrong owner IDs, repository IDs, branches, audiences, workflow identity, actors, signatures, and expired tokens are rejected.

## THIVEBASE data plane

The runtime records:

- package identity and digest;
- artifact hashes, classifications, owners, sizes, and public-projection state;
- algorithm IDs, source paths, invariants, dependencies, and authority boundaries;
- documentation impact;
- deterministic gap analysis;
- GitHub repository, branch, workflow, run, actor, and OIDC claim digests;
- token fingerprint rather than the token value;
- request and claims digests;
- exact source ancestry and manifest readback evidence;
- deployment lineage and failed/corrected runtime observations.

It does not persist raw OIDC tokens or raw artifact bodies.

## Deterministic runtime advisor

`ct.algorithm.chlom.institutionalization-runtime-advisor.v1` evaluates edge-function state, package/ingest canaries, OIDC subject compatibility, CI state, package registration, review readiness, commercialization boundaries, and runtime-lineage evidence. It emits P0-P3 advisory records with bounded agent handoffs.

It has no network access, credentials, write authority, decision authority, or automatic release authority. A future model-based extension requires a prompt/model/version receipt and independent review.

## Recovery contract

Failures remain fail closed. Recovery requires:

1. classify the failure without logging tokens;
2. preserve append-only evidence;
3. compare deployed module linkage against source-controlled exports;
4. evaluate RDLF and require a HOLD for the failed observation;
5. redeploy only exact known-good source;
6. run the module-linkage and RDLF regression contracts;
7. rerun package, ingest, OIDC-subject, unit, and deployed-liveness canaries;
8. verify the exact committed manifest and source ancestry;
9. confirm the non-canary package/receipt readback;
10. obtain independent security and release review before production use.

Automatic resume is prohibited.
