## Phase 2.98 Pass C2 — Documentation Autonomy & Phase Gates

## Checkpoint

- **Baseline:** merged Pass C1 `28d7f40661a641834b0de9ab06142738eb1db68e`
- **Phase:** 2.98
- **Next-phase rule:** Phase 2.99 remains hard-gated
- **Primary purpose:** make documentation change-control and agent governance inherited requirements for every remaining extraction and future implementation

## Adopted institutional rule

CrownThrive Support now explicitly treats the versioned institutional record as the sole governed source of truth for approved institutional meaning while preserving runtime/source systems as authoritative evidence for the facts they originate.

A new **Documentation Source-of-Truth & Autonomous Governance Standard** defines:

- material docs-impact outcomes: `docs_updated`, `docs_no_change`, `docs_delta_opened`;
- page/article stable IDs and version/correction fields;
- Phase 2.98 → 2.99 → 3 articleization sequence;
- D0–D3 documentation change classes;
- Documentation Sentinel, Documentation Steward, Platform Registry, Catalog/Rights Metadata, Release/Website, Legal/Rights, Security/Privacy, Economic/Commerce and Phase Gate agent roles;
- subordinate approval/quorum limits;
- self-checking requirements;
- controlled self-healing and fail-safe rules;
- cost-aware grassroots automation;
- continuous reconciliation of Phase 2.99 and Phases 3–5 after material continuations;
- target hosts `docs.crownthrive.io`, `api.crownthrive.io`, `mcp.crownthrive.io`, `holdings.crownthrive.com` without falsely claiming undeployed services are live.

## Articleization decision

Actual articles are already being created in Phase 2.98. Phase 2.99 is now explicitly the formal **Help Center Articleization & Documentation Projection seed** in addition to its private-core work.

The 795-title recovered inventory must become machine-addressable. P0/P1 customer, operator, developer, legal, rights/licensing, commerce and support categories need substantive source-grounded bodies or explicit unresolved-source records before Phase 3 engineering is accepted.

## Mintlify service state

Mintlify is now registered as `ct.service.documentation.mintlify`, a replaceable third-party documentation infrastructure service under CrownThrive Support.

Current state:

- deployment plan: Hobby;
- Git source: `crownthrive1/CrownThrive-OS` / `main`;
- `docs.crownthrive.io` added as the canonical target custom hostname;
- custom hostname remains pending DNS ownership and certificate validation;
- current source-code repos beyond the Support repository are not exposed to Mintlify workflows and are recorded `not_connected`, not nonexistent;
- link-rot checking is now `blocking` with anchors/snippets enabled;
- brand-sensitive spellcheck remains `warning`;
- one weekly Monday link-integrity workflow is active with low-risk auto-merge boundaries.

Fresh custom-hostname verification currently requires the ownership and ACME records stored in the Mintlify service registry. Values must be re-read before DNS changes because certificate-validation tokens can rotate.

## Phase-gate updates

### Phase 2.99

Added Workstream 0 for article/category/version/navigation/redirect manifests, documentation impact contracts, source-repository mappings, changelog/drift queues and documentation host state.

### Phase 3 readiness

P0/P1 extraction now requires versioned article coverage and docs-impact mapping. Phase 2.99 must seed documentation manifests and connected-repository mappings. A material release with no synchronized docs, approved no-impact decision or permitted governed delta is a no-go condition.

### Phases 3–5 charter

All later phases now inherit documentation impact, article versioning, bounded agent approvals and continuous gate reconciliation. Phase 4 explicitly requires event/PR-driven docs/changelog propagation for connected repositories and drift detection for non-connected/third-party systems.

## Source-code automation blocker

The current Mintlify organization exposes only the Support repository to workflow automation. Automatic documentation updates from Virality, KJV/Sermon Toolkit, AdLuxe and other application source changes cannot be represented as connected source-code automation until those repositories are connected or otherwise registered as authorized sources.

Until then, current public behavior, authorized source artifacts, Drive/File Library records and documented site release evidence remain valid verification inputs.
