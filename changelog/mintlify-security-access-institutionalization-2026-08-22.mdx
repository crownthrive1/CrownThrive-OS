## Mintlify Security & Access Institutionalization — 2026-08-22

## Decision

Founder-supplied current Mintlify security/access evidence is now institutionalized under the CrownThrive secret-management and service-governance model. **No raw credential value is published in this record or elsewhere in the public CrownThrive-OS/Mintlify projection.**

## Credential estate

The dated provider inventory contains:

| Class | Active records |
| --- | --: |
| Project identifier | 1 |
| Admin API keys | 2 |
| Assistant API keys | 2 |
| Mintlify Index API keys | 2 |
| MCP machine client | 1 client ID \+ 1 client secret |

The MCP workload identity is registered by provider name as `thrivebase_mintly`. The client identifier and client secret remain restricted.

## Implemented custody controls

- Nine provider values were placed into encrypted ThriveBase Supabase Vault custody: one project identifier, six API keys, one MCP client identifier and one MCP client secret.
- Nine corresponding private credential-registry records were materialized under stable `ct.cred.mintlify.*` identities.
- The private registry records credential class, ordinal where applicable, intended use, provider date, custodian, verification state, Vault reference and SHA-256 fingerprint.
- Public, anonymous and ordinary authenticated database roles are not granted access to the private credential-registry schema/table.
- Public documentation receives metadata only; Vault identifiers, secret values and private fingerprints are not projected here.

## Purpose boundaries

- **Admin API keys:** server-side updates, previews, automations, agent jobs and analytics export.
- **Assistant API keys:** trusted-backend proxy use for assistant messages, search and page content; never browser/client embedding.
- **Index API keys:** Mintlify Index workloads only.
- **MCP client credential:** machine-to-machine access for the named workload identity; not an end-user credential and not a universal agent secret.

## Verification state

Current state: `founder_attested_not_runtime_tested`.

The inventory and custody are verified as institutional records, but this change does not claim successful live authentication with every credential or independently certify provider-enforced scopes/rate limits. Bounded read/canary tests must produce separate evidence before a credential is marked `runtime_verified`.

## Rotation and exposure policy

No credential was rotated or revoked as part of this institutionalization. Rotation/revocation is required on suspected disclosure, scope/role change, confirmed misuse, provider compromise, workload retirement/offboarding, or the governed rotation schedule. Rotation must update the private fingerprint and runtime binding without changing the durable institutional identity.
