# 2026-08-22 — ThriveBase Capacity Recovery & Status Resilience

## Decision

Institutionalize the August 22 ThriveBase capacity interruption as a governed continuity event and convert the validated recovery pattern into a standing status/incident contract for the full CrownThrive agent estate.

## Current outcome

- ThriveBase/Supabase recovered after the capacity-plan change and restart;
- fresh native readiness and heartbeat evidence passed;
- service status returned to `OPERATIONAL`;
- the incident lifecycle was resolved with append-only recovery evidence;
- the authorized-application UUID was correctly classified as an OAuth application identifier rather than an API secret;
- no secret vault write was performed from that identifier;
- the current registered agent estate was bound to the incident-status continuity contract;
- the lesson was promoted to a validated factory/productization candidate under commercial `HOLD`.

## Current-state correction — August 23, 2026

The original August 22 recovery event remains valid historical evidence. A later founder-authorized capacity change now supersedes its prior capacity baseline for current-state purposes:

- current plan: Supabase Pro;
- current compute: **Small**;
- current Postgres database disk: **8 GB**, intentionally provisioned under Founder authority;
- current diagnostic: `GREEN`;
- current direct Postgres connection ceiling: 90;
- current Small recommended database-size reference: 50 GB;
- current ThriveBase local request budget: `-1` using the canonical `-1 = unlimited / 0 = zero / positive = literal / null = fail-closed` contract.

The prior Micro/2 GB projection is preserved as historical evidence and must not be treated as current capacity. See [ThriveBase Institutional Registry](/platforms/thrivebase-institutional-registry) and the [August 23 capacity reconciliation](/changelog/2026-08-23-thrivebase-small-8gb-capacity-reconciliation).

## Documentation changes

A new **Status & Resilience** section now governs:

- ecosystem service state;
- incident lifecycle and evidence;
- all-agent acknowledgements and impact notation;
- post-restart recovery readback;
- credential/vault separation;
- public/private status projection;

## Governance boundary

Private provider billing, account identifiers, credential values, operational thresholds and security-sensitive evidence remain outside public Mintlify. Only sanitized incident patterns and reusable interfaces may progress toward external packaging.

## Phase effect

This is a Phase 2 continuity and institutional-learning improvement. It does not constitute Phase 3 activation.

The corresponding [Ecosystem Status & Resilience Control](/technology/ecosystem-status-resilience) is now documented as the canonical public-safe service-status and incident-continuity contract. The incident remains a dated Phase 2 evidence record; the status-control page governs future reuse.
