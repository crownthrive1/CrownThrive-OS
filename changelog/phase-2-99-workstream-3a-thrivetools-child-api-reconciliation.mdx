## Decision

Direct CrownThrive application/API evidence resolves **ThriveTools SEO** and **ThriveTools OPT** as distinct child applications inside the `ct.platform.thrivetools` family:

```text
ct.platform.thrivetools
├── ct.platform.thrivetools-seo
└── ct.platform.thrivetools-opt
```

Child identities do not merge into the root platform, and child credentials, engines, API contracts, quotas, deployment state and runtime evidence do not promote to the root by inheritance.

## ThriveTools OPT evidence

Founder-supplied developer documentation establishes:

- product identity **ThriveTools OPT**;
- displayed version `v4.0.0`;
- API base `https://optimize.thrivetools.io/api`;
- authentication through the `Authorization` header;
- six documented endpoint URLs;
- source-visible request parameter and response shapes;
- source-visible optimization/storage status example.

Documented paths:

- `/get-images`;
- `/get-media`;
- `/upload`;
- `/delete`;
- `/get-single-image`;
- `/check-status`.

The supplied material does **not explicitly state HTTP verbs**. No verb is inferred from route names or content type.

## Credential handling

The founder-supplied API credential is **restricted runtime-only**. It is stored server-side in Supabase Vault under primary and recovery aliases. Both aliases are present and their fingerprints match without exposing the value.

The raw credential is prohibited from GitHub, Mintlify, source examples, logs, screenshots, CI output, email and client-side code.

## Runtime scaffold

Supabase Edge Function `thrivetools-opt-api-control` v1 is deployed with JWT verification enabled. It is deliberately fail-closed:

- health/configuration reporting may confirm configuration without exposing the credential;
- capabilities may expose only the governed operation catalog;
- provider read dispatch is disabled until exact HTTP methods and authenticated D0 behavior are certified;
- provider upload/delete dispatch is disabled.

## Machine tool contracts

- `opt.media.list`;
- `opt.image.get`.

D2 mutation targets:

- `opt.images.upload` — disabled and human approval required;
- `opt.images.delete` — disabled and human approval required.

## Security and destructive-action controls

Upload and Delete are not activated by possession of a credential. Future upload certification must cover exact method, bounded file references/types/sizes, compression limits, rights/provenance, privacy classification, output validation, audit evidence and recovery/provider-exit behavior. Future deletion certification requires exact target validation, retention/recovery policy and explicit scoped authority. `permanent_delete=true` remains a high-scrutiny destructive operation.
