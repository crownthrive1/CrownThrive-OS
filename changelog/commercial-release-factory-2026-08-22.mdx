# Commercial Release Factory — August 22, 2026

CrownThrive established a bounded **Commercial Release Factory** for CrownThrive Launch, CrownThrive Ready and CrownThrive Procure.

## Exact initial cohort

The factory binds the existing 30 packaged `1.0.0-candidate.4` digital products: ten products per platform. Existing deterministic package rebuild and independent integrity evidence is preserved; the release factory does not reclassify package QA as commercial acceptance.

THIVEBASE now contains exactly:

- 30 governed product catalog records with public visibility disabled;
- 30 exact-version release package records; and
- 270 hard-gate rows: nine release dimensions for every product.

All 270 gate rows remain `HOLD`. No missing or contradictory evidence is converted into PASS merely to advance the cohort.

## Agent and machine contract

The existing non-voting `ct.agent.commercial-release-packager` is the canonical release-package orchestrator. The runtime now carries 18 separately bound release skills/workers: the established packaging, rights, pricing/tax, fulfillment, credit-checkout, entitlement, accessibility, DNS/TLS, governance and Sites-publisher workers plus dedicated source-normalization, remedy/rollback, Sites-readback, evidence-hashchain, credential-alias, provider-capability, drift-reconciliation and safe-replication workers.

Every worker remains non-voting and no-self-approval. Replication increases bounded throughput only; it creates no vote, D3 authority, payment authority, final rights authority, credential-disclosure authority or direct-main authority.

## Protected implementation

Eight Commercial Release Factory algorithms are registered as `TRADE_SECRET`, Vault-bound, non-public and invocation-disabled:

- Product Release Fitness Index;
- Gate Evidence Completeness Analyzer;
- Credit Rail Outcome Mapper;
- Provider Feed Reconciliation Graph;
- Domain and TLS Readiness Scorer;
- Accessibility Conformance Risk Triage;
- Independent Review Handoff Graph; and
- Rollback and Remedy Consistency Guard.

Only public-contract digests may cross the public boundary. The new protected implementation package is in Vault custody and is **pending a new encrypted Drive recovery export/readback**. It is not falsely marked as present in an older archive.

## Commerce decision

Launch, Ready and Procure product checkout is standardized as **Crown Credits-only**. Per-SKU Stripe Product/Price creation is prohibited for these three surfaces. A separately governed Stripe funding rail may fund Crown Credits where authorized, but funding evidence does not independently grant a product license or entitlement.

The required sequence remains:

```text
credit redemption evidence
→ license / entitlement policy decision
→ entitlement
→ protected fulfillment
→ append-only remedy / reversal if needed
```

No product price, tax conclusion, offer, checkout, credit debit, entitlement or Stripe object was created by this institutionalization pass.

## Automated package dimensions

For each product the factory prepares independent packets for:

1. rights and provenance;
2. pricing and tax;
3. private fulfillment;
4. Crown Credits checkout and event/replay handling;
5. entitlement and license;
6. refund, dispute and rollback;
7. accessibility and device evidence;
8. DNS, TLS and canonical routing;
9. governed acceptance and publication.

Unknown, stale, contradictory or originator-only hard-gate evidence resolves to HOLD.

## Sites publication architecture

The default Sites publication path is a **governed dynamic feed** followed by provider readback rather than unrestricted direct editing by the release originator. Automatic publication is possible only where the accepted release policy, certified destination adapter, route, read-after-write proof and rollback controls all permit it.

The three public-safe feed endpoints were read on August 22. Launch, Ready and Procure each returned HTTP `200`, schema `1.0.0`, the exact expected surface/platform identity and an empty `items` array. The empty array is correct because no product has a governed release PASS.

A dedicated synthetic auto-publish canary was invoked through its internal-auth contract. It returned HTTP `409` / `blocked` before any write because an accepted authoritative canary release was absent. The active policy requires four authoritative yes-votes, includes mandatory Agent D, requires authority receipts and explicitly treats synthetic votes as non-authoritative. No vote was fabricated to make the canary write.
