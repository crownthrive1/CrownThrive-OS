## Purpose

Close the documentation and machine-state drift created when `S102` verified the Collab Portal webhook configuration UI after the earlier `S101` Secure API adapter had already encoded `webhook_contract: not_recovered` language.

The correction preserves both facts:

1. `S101` still proves that the recovered Secure API OpenAPI 3.0.3 specification does **not** expose webhook registration or webhook event endpoints.
2. `S102` separately proves that the current first-party Collab Portal UI supports configurable webhook endpoints and distinct Project Created, Project Updated and Project Deleted event selection.

These are not contradictory when their evidence scopes are kept separate.

## Scope

This packet synchronizes the current public-safe Collab Portal architecture, API seed, validation queue, machine manifest and CI invariants so future agents cannot regress to either of these false conclusions:

- `Collab Portal webhooks are completely unknown`; or
- `because the UI has webhooks, a production-authenticated event receiver is certified`.

## Non-goals

This packet does not:

- bind or expose production Collab Portal credentials;
- execute `GET /project/meta` against the CrownThrive account;
- identify or pin the institutional project UID;
- enable the project-status write gate;
- execute any `PUT` mutation;
- claim project creation, task, comment, milestone, file or signature APIs;
- infer a webhook signing secret/header;
- invent retry, replay, timeout or dead-letter behavior;
- activate an inbound webhook receiver;
- advance Phase 3.

## Evidence baseline

### S101 — Secure API

S101 remains authoritative for the recovered HTTP API specification:

- OpenAPI 3.0.3;
- base URL `https://portal.crownthrive.com/secure-api/`;
- paired `X-Public-ID` and `X-Secret-Key` headers;
- project meta/list/find/update operations;
- no project-create/task/comment/milestone/file/signature/webhook registration or event endpoints in that specification.

### S102 — Webhook UI

S102 remains authoritative for the current UI evidence:

- configurable webhook endpoint surface;
- separate Project Created, Project Updated and Project Deleted toggles;
- selectable project payload fields;
- representative Project Created preview payload;
- preview UUID remains sample/unverified because the associated project name and other fields were null.

S102 does **not** prove sender authentication, signature verification, delivery-attempt identity, retry schedule/limits, replay mechanics, timeout policy, dead-letter behavior or receiver certification.

### Runtime evidence

The connected CrownThrive Supabase project has a deployed `collab-portal-pm` Edge Function in `active_fail_closed_unconfigured` state. The runtime requires caller JWT authentication, contains no Collab Portal credential values in source, reads credentials only from server-side environment secrets, defaults writes closed and bounds the eventual write surface to project-management status/information/custom fields with read-before-write and read-after-write verification.
