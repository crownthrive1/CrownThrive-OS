## Why this pass exists

CrownThrive already has automated institutional validation, but **validation and enforcement are not the same control**.

```text
monitoring
"Policy violation detected. FAIL."

versus

enforcement
"Policy violation detected. FAIL. GitHub blocks merge into main."
```

The institutional target is the second model.

## Why post-merge validation remains valuable

Even after merge enforcement is enabled, the push-to-`main` workflow remains mandatory defense-in-depth. It detects:

- bypass or emergency-merge defects;
- ruleset drift;
- changes introduced by a merge mechanism rather than the PR head;
- workflow/configuration inconsistencies;
- canonical-branch corruption or later direct-write exposure.

Pre-merge enforcement prevents known noncompliance from entering `main`; post-merge validation independently verifies the canonical branch after the transition.

## Executable policy direction

The current S100/S103 source/identity/domain/provider work is increasingly suitable for policy-as-code transitions such as:

```text
source authority
→ canonical identity
→ ownership/authority
→ domain
→ provider
→ deployment
→ entitlement
→ rights
→ economic state
→ publication eligibility
```

Agents may propose transitions, but the governance layer should reject unsupported state promotion. Examples that must fail closed include:

- `historical → current` without effective source/authority evidence;
- `unverified → production_verified` without runtime evidence;
- `provider_capability → CrownThrive_deployed` without account/deployment evidence;
- `payment → entitlement` without fulfillment proof;
- `product_listing → rights_granted` without a valid license/rights path;
- `source Active domain label → current secure canonical host` without registrar/DNS/TLS/runtime evidence.
