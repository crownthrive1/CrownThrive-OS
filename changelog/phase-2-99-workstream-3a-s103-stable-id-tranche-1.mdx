## Purpose

Resolve a bounded set of previously `unresolved` S103 rows where the institutional record already establishes the asset identity strongly enough to assign or reuse a stable machine ID, while keeping provider, deployment, API, domain-runtime and commercial capability separately gated.

## Scope

This tranche resolves exactly six current-role identities:

- `S103-PF-009` ThriveTools → `ct.platform.thrivetools`;
- `S103-PF-010` ThriveRelay → `ct.platform.thriverelay`;
- `S103-PF-022` The Mane Experience → `ct.platform.the-mane-experience`;
- `S103-PF-024` Backroad FM → `ct.platform.backroad-fm`;
- `S103-PF-054` The Sermon Toolkit → `ct.platform.kjv-sermon-toolkit`;
- `S103-PF-069` ThriveMaps → `ct.platform.thrivemaps`.

## Non-goals

This packet does not certify any vendor/account/installed version, deploy a service, activate an API, change rights or pricing, bind credentials, create a legal entity, or convert a source `Active`/`Live` label into current production proof. It also does not adjudicate the CrownApps/ThriveApps branding family or the unresolved Melanated media graph.

## Evidence baseline

- **ThriveTools:** S100 platform/tool-family row, `thrivetools.io` source row, S100 engine assignment and current legal/taxonomy coverage.
- **ThriveRelay:** dedicated institutional registry explicitly preserves a distinct relay/automation asset and separates institutional service identity from vendor implementation.
- **The Mane Experience:** S100 P0 `Active / GTM` row, media-federation canonical role, source domain and engine assignment.
- **Backroad FM:** dedicated institutional registry already publishes `ct.platform.backroad-fm` and the media federation preserves a distinct radio/programming role.
- **The Sermon Toolkit:** current developer adapter matrix already uses `ct.platform.kjv-sermon-toolkit` for the KJV Visualized / Sermon Toolkit family.
- **ThriveMaps:** dedicated institutional registry verifies a current public feedback/roadmap/changelog platform while keeping backend/API capability separately unverified.

## Authority and safety class

Classification: **D1 identity normalization from governed evidence**. No consequential D2/D3 legal, rights, money, privacy, security or source-history authority is exercised. Stable IDs identify assets; they do not imply capability or authorization.

- no selected row requires founder/counsel/provider adjudication to establish the identity itself;

## Rollback and correction

If stronger later evidence proves an identity merge, split or naming error, append a correction/supersession relationship. Do not recycle a stable ID for a different asset and do not erase the historical S103 row or its prior mapping state.

## Downstream impact

- **Phase 3:** the six IDs may seed platform identity records, but provider/API/deployment activation remains separately gated.
- **Phase 4:** future federation can reference these stable IDs instead of historical labels after adapter certification.
- **Phase 5:** identity resolution alone does not establish an active offer or revenue lane.
- **Phase 6:** licensing/developer exposure still requires rights/API authority beyond identity.
- **Phase 8:** S100/S103 reporting can link these identities without forcing count equality.
- **Phase 10:** continuity exports preserve these stable IDs across provider or brand changes.
