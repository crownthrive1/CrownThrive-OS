# Institutional Changelog Index

This is the front door to CrownThrive's change history. Historical changelog pages are preserved at their existing routes; this index groups them by subject so people and machines can find the **major release**, then drill into the **subject-specific patches** that explain how that state was reached.

## Changelog rule

A material CrownThrive change should have two linked views when appropriate:

1. **Major/main changelog record** — executive description of what materially changed, why it matters, current phase/gate impact and where the detailed history lives.
2. **Subject changelog/patch record** — implementation-specific evidence, migration, source reconciliation, tests, rollback and supersession lineage.

Mechanical corrections do not need a new major release entry unless they change institutional meaning. Historical pages are not rewritten out of existence; they remain linked as predecessors/superseded evidence.

## Subject-first patching rule

When a new patch is created, put its durable documentation with the subject it changes first: agents under Automation Team, pallets under CHLOM, APIs under Developer Platform/Technology, domains/engines under Portfolio/Platform Intelligence, rights/legal under Governance/Support, and phase acceptance under Changelog and Decisions. The changelog page should link back to the durable subject page rather than duplicating the entire operating contract.

## Machine continuity

Each major/subject changelog should converge on stable fields for machine ingestion:

```yaml
change_id:
subject_ids: []
phase:
observed_or_effective_at:
predecessor_changes: []
what_changed: []
why_changed:
evidence_refs: []
gate_impact: []
downstream_phase_impact: []
docs_impact:
rollback_or_restore_target:
current_status: current | superseded | historical | blocked
```

This keeps the changelog useful as an institutional event graph rather than a chronological pile of prose.
