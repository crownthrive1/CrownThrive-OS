## Phase 2.99 — Collab Portal Webhooks & Runtime

## What changed

Current first-party Collab Portal UI evidence verifies a configurable outbound webhook surface and distinct **Project Created**, **Project Updated** and **Project Deleted** event toggles. The webhook template builder exposes selectable payload data, and a Project Created preview confirms project, assignment and project-custom-field payload families.

The preview contains a UUID-like `project_uid`, but `project_name` and several other values are null. That value is therefore a **preview/sample identity**, not the CrownThrive Institutional Build project UID, until authenticated project lookup establishes the relationship.

## Secure runtime established

The connected CrownThrive Supabase project was restored to healthy service and a server-side Edge Function named `collab-portal-pm` version 1 was deployed.

The runtime is deliberately **fail closed**:

```yaml
provider: Supabase Edge Functions
function: collab-portal-pm
status: active
caller_authentication: Supabase JWT required
collab_portal_secret_in_source: false
credential_binding: pending
write_gate_default: closed
reads:
  - health
  - project_meta
  - find_project
conditional_write:
  - update_project_status
allowed_write_fields:
  - status
  - info_description
  - project_custom_fields
read_before_write: required
read_after_write: required
blind_mutation_retry: prohibited
```

The function reads Collab Portal credentials only from server-side environment variables and contains no production credential values. Because the current Supabase connector can deploy functions but does not expose project-secret management, credential binding remains a real deployment dependency outside the public documentation workflow.

## Why this design

The objective is not maximum portal authority. It is a narrow, auditable project-status projection that can eventually participate in the hourly CrownThrive PM loop without making Collab Portal the institutional source of truth.

The adapter is built so that:

- no credential can be committed in public source;
- writes cannot occur until explicitly enabled server-side;
- the real project is resolved by authenticated lookup rather than screenshot inference;
- only PM status/information/custom-field state can be changed initially;
- each write is preceded by a read and followed by a read-back comparison;
- ambiguous outcomes are not automatically replayed;
- GitHub/PentaDocs and Gmail remain the fallback continuity path.

## Webhook gate

The webhook capability is now `ui_contract_verified`, not `unknown`, but it is not production-certified.

Still required:

- sender authentication/signature or another fail-closed integrity mechanism;
- delivery-attempt identity;
- retry timing/limits;
- replay behavior;
- receiver idempotency/deduplication;
- observability and incident handling;
- polling/read fallback.

Until those are known and tested, the receiver is not activated as an authoritative event source.

## Downstream phase propagation

- **Phase 3:** external-adapter pilot now includes both bounded outbound API projection and inbound project-event receiver certification.
- **Phase 4:** event-driven Collab Portal synchronization becomes eligible after sender-integrity, idempotency and replay tests pass.
- **Phase 5:** CRM/marketing writes remain separately purpose/consent gated; PM authority does not imply marketing authority.
- **Phase 8:** project-state evidence may feed portfolio reporting only after semantics, account boundaries and reconciliation are certified.
- **Phase 10:** preserve adapter configuration, webhook event/export mapping and a polling/read fallback so continuity does not depend on SuitePro delivery.
