## CrownThrive Sites™ release and Penta workflow

## Scope

This workflow governs changes to CrownThrive Sites™ source, public deployment claims, public API/MCP contracts, ecosystem bindings, documentation, verification, and release state. It supplements the general Website Patch Workflow and Penta provider lifecycle; the stricter applicable control wins.

## Phase 3 release sequence

1. **Discover** — identify the affected route, source, provider, capability, contract, claim, data class, and existing evidence.
2. **Govern** — resolve the current directive/policy/contract/task-order authority, decision class, required reviewers, and prohibited effects.
3. **Build** — PentaBuild™ or the assigned bounded executor constructs the exact source/integration artifact without self-certifying it.
4. **Bind** — PentaCredentials™ resolves the required provider credential references without exposing secret material.
5. **Certify** — PentaCertify™ validates source identity, contract shape, security boundaries, and the required live readback for the exact provider/interface operation.
6. **Execute** — only an operation that has current authority and required certification may perform the approved bounded effect.
7. **Verify** — independent readback confirms the expected effect, source/deployment relationship, failure behavior, and rollback/recovery state.
8. **Preserve** — PentaDocs™ reconciles current state, records supersession/history, and preserves exact evidence/rollback references.
9. **Nurture** — PentaNurture™ monitors certified live scope for drift, degradation, expiration, credential health, and remediation needs.

## Organizational responsibility

| Penta role/system | Required output | May not do |
| --- | --- | --- |
| PentaManagers™ | bounded contract/task order with scope, TTL, evidence and acceptance criteria | manufacture provider, budget, rights, or D3 authority |
| PentaBuild™ / assigned executor | exact source/integration artifact and build receipt | self-certify consequential output |
| PentaCredentials™ | current credential-binding/readiness evidence | expose secret values or convert credentials into authority |
| PentaCertify™ | independent exact-scope certification/readback receipt | infer unrelated write authority from a read test |
| PentaDocs™ | current-state documentation, changelog, archive/supersession record | publish an unverified operational claim as fact |
| PentaNurture™ | live health/drift observation and remediation route | waive a failed or expired gate |
| Independent verifier / rollback owner | result readback, mismatch detection, recovery evidence | reuse stale exact-head evidence as current approval |

## Deployment claims

A source artifact and a provider deployment are separate records.

When current external deployment cannot be independently resolved, the documentation state must be `readback_required`, `unverified`, or `HOLD`. Historical route evidence remains preserved but cannot be promoted into a current deployment claim by documentation alone.

## Automation boundary

Automation may prepare, test, reconcile, certify allowed read-only operations, perform specifically authorized reversible actions, and report evidence. It may not autonomously:

- activate payments or checkout;
- broaden customer-data access;
- grant rights or licenses;
- expose credentials;
- turn a candidate product into a live commercial offer;
- widen provider-write scope beyond the exact authorized operation;
- self-approve a material release;
- perform D3 reserved-human decisions.

## Current-main and PR rule

A stale or divergent PR is not promoted simply because its historical checks passed. PentaVergence/PentaCloser should classify the packet:

- **represented** → close the obsolete transport while preserving history;
- **valuable missing delta** → selectively restack only the useful source on current main;
- **genuine HOLD** → preserve the packet until the missing authority/evidence is available;
- **current ready work** → rerun exact-head checks and merge only on the governed current-base path.

No force overwrite is required for normal convergence.

## Definition of done

A Sites release is complete only when the applicable chain contains:

- current source identity;
- authority/contract binding;
- build evidence;
- credential binding where required;
- exact-scope certification;
- execution evidence for any side effect;
- independent readback;
- PentaDocs reconciliation;
- rollback/recovery state;
- current nurture/health evidence when the scope remains live.

A green build, successful preview, provider capability, or historical production snapshot alone does not satisfy this definition.
