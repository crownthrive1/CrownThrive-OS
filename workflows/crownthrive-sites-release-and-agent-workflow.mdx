# CrownThrive Sites™ release and agent workflow

## Scope

This workflow governs changes to the CrownThrive Sites™ public deployment, its public API routes, documentation records, and future MCP contract. It supplements the [Website Patch Workflow](/workflows/website-patch); the stricter control applies.

## Release sequence

1. **Detect and classify** — Documentation Sentinel or an operator records the affected route, capability, claim, data class, and release risk.
2. **Prepare** — the implementation packet declares stable IDs, changed files, expected public effect, tests, documentation impact, and rollback target.
3. **Build** — the Website and Release executor implements a bounded change in the service source.
4. **Validate** — automated tests confirm the public route and public API contract. New APIs require schema and non-capability checks.
5. **Reconcile** — Documentation Steward updates the platform registry, developer contract, workflow, and changelog where material.
6. **Independent review** — Evidence Auditor verifies claims and Agent S checks security, secrets, dependencies, auth, data, and supply-chain effects.
7. **Publish** — a verified production deployment is created only after the applicable gate passes.
8. **Readback** — the deployed route and API status are checked against the released source and the record is updated with outcome and rollback reference.

## Agent responsibilities

| Role | Required output | May not do |
| --- | --- | --- |
| Documentation Sentinel | Drift and documentation-impact packet | Publish, approve, or promote an unverified claim |
| Website and Release executor | Scoped source change and test result | Self-approve material release |
| Documentation Steward | Public-safe registry and developer-contract reconciliation | Invent a production integration |
| Evidence Auditor | Independent claim and source verification | Treat a plan as operational evidence |
| Agent D | Gate outcome and exact handoff | Waive hard gates |
| Agent S | Security and resilience assessment | Approve risky self-authored work |

## Automation boundary

After every accepted service change, the release flow must:

- update the governed Mintlify documentation record or explicitly record a reviewed no-change determination;
- create and verify a production publication;
- preserve the exact source, release, and rollback references in the applicable change record;
- surface unresolved evidence, rights, privacy, security, commerce, and accessibility gates as blocked or deferred.

Automation may prepare, validate, and report. It may not autonomously activate payments, process customer data, widen access, grant rights, deploy a write-capable MCP tool, or make reserved founder/legal/security decisions.

## Definitions of done

A Sites release is complete only when source validation, production verification, documentation reconciliation, claim review, and rollback readiness all exist. A successful build alone is not release completion.
