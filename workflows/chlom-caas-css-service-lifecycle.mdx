# CHLOM CaaS and CSS Service Lifecycle

The lifecycle prevents shared-service architecture from becoming a paper diagram or a collection of unverified provider aliases.

## Service lifecycle

`specified -> candidate -> controlled_test -> verified -> active -> superseded -> retired`

`hold` and `blocked` are valid fail-closed states. A service is not `verified` merely because a provider exists or a contract page was written.

## Contract lifecycle

`candidate -> controlled_test -> verified -> active -> superseded -> retired`

A mutation contract cannot advance without:

- exact input and output schemas;
- bounded authority at D0–D2;
- least privilege and purpose;
- idempotency;
- rollback or compensating action;
- read-after-write;
- negative tests;
- different independent verification.

## Provider-binding lifecycle

`unresolved -> candidate -> configured -> read_verified -> write_verified`

Provider states never replace canonical CSS identity. Missing providers remain unresolved. Blocked credentials remain blocked. A read canary does not prove mutation safety.

## Platform-adoption lifecycle

`candidate -> planned -> controlled_test -> connected -> verified`

A migration must preserve local history and use versioned supersession. Existing platform-specific presentation, workflows, cultural corridors, and customer experiences may remain. Institutional truth moves to the CSS service only after reconciliation and readback.

## CHLOM CaaS lifecycle

`control candidate -> control binding -> evidence candidate -> observed -> independently verified -> current assurance -> drift/expiration -> remediation or supersession`

CaaS outputs may include readiness, evidence freshness, blocker classes, remediation sequencing, exception state, and specialist-review triggers.

CaaS does not automatically declare legal compliance, cybersecurity certification, accessibility conformance, audit passage, tax correctness, accounting correctness, licensing authority, or regulatory approval.

## Route lifecycle

`candidate -> controlled_test -> read_verified -> bounded write canary -> write_verified`

Every route requires exact service and contract identities, minimum-necessary fields, authentication or capability evidence, idempotency, retry policy, rollback, readback, DAIL receipt, and independent verification.

## Asset lifecycle

`specified -> generated_candidate -> controlled_test -> verifying -> certified -> approved_not_live -> live -> superseded -> retired`

A package record is not a deployment, installation, operative license, customer entitlement, or live offer.

## CaaS package lifecycle

`research -> candidate -> rights_review -> pricing_review -> fulfillment_review -> approved_not_live -> live`

No package becomes live until exact pricing, rights, license acceptance, tax/accounting treatment, fulfillment, support, privacy, security, refund/revocation behavior, and governance are accepted.

## Hourly control loop

The internal CSS subroute runs at minute `:41` without consuming another external scheduler slot. It:

1. refreshes provider-binding evidence;
2. compares exact contracts and dependencies;
3. measures service readiness;
4. measures CaaS control assurance;
5. preserves HOLD/BLOCKED states;
6. updates seven agent heartbeats and run receipts;
7. creates no external provider write, checkout, entitlement, D3 decision, or sovereign vote.

## Reserved authority

A/B/C/D/S remain the sovereign voter pool. D3 remains human or qualified-professional reserved. CSS agents cannot approve their own work, merge directly to `main`, expose secrets or private identity mappings, or convert a provider success into institutional truth.
