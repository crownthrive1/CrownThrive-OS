## Institutional role

The CrownThrive Public API Marketplace packages public-safe API and intelligence profiles as developer products without exposing CrownThrive's internal databases or private provider credentials.

It separates:

- external catalog and plan reads;
- customer developer keys;
- subscription activation;
- usage and quota accounting;
- provider/source materialization;
- HOT/WARM/COLD data routes;
- internal and external planes;
- MCP discovery and consumption.

## Commerce

The marketplace has four plans and a live Stripe base-subscription product. Checkout-session readback is the activation evidence.

Current boundaries:

- base subscription: live;
- enterprise: quote/contract mode;
- overage settlement: not live;
- dedicated Stripe webhook lane: registered but capacity-blocked;
- 15-minute Stripe reconciliation job: active;
- provider billing, quotas and throttles remain separate from CrownThrive's local policy.

## Security topology

Customer API keys are stored as SHA-256 hashes. Customers do not receive internal database access.

Current topology:

- runtime role: `ct_api_marketplace_runtime`;
- external schema: `api_marketplace_public`;
- HOT: product registry;
- WARM: response cache;
- COLD: snapshot items;
- direct cross-plane database access: prohibited;
- customer reverse transport: prohibited;
- provider write: prohibited;
- target public ThriveBase plane: approved but pending separate provider project creation.

The current runtime still resides on the private project with logical isolation. Physical public-project separation remains an explicit pending topology step.

## Request-budget hold

The local monthly request-budget policy is unresolved and therefore fail-closed. This does not negate the read canaries, catalog or commerce activation; it prevents the system from inventing a local request ceiling.

Provider throttles, billing limits and quotas continue to apply even when CrownThrive later sets an unlimited local ceiling.
