## Recovered institutional evidence

Recovered CHLOM institutional compendium material places ThriveRelay inside the `Operations & Institutional Memory` corridor alongside Collab Portal, ThriveSupport, Mintlify, Ops Oasis and ThriveTools.

That evidence is sufficient to preserve ThriveRelay as an institutional concept/asset requiring disposition. It is **not** sufficient to declare a current software implementation, vendor, API or production host.

## Current vendor-association caution

Historical project context has associated the name ThriveRelay with third-party tooling at different points in CrownThrive's build history. Phase 2.98 does not automatically preserve those vendor mappings as current truth.

Current public `spryn.io` evidence identifies Spryn as a Froiden-built sprint planning/execution product with self-hosted and cloud options. That current vendor identity does not by itself prove that Spryn is presently ThriveRelay, was contractually renamed by CrownThrive, or remains the intended implementation.

Canonical rule:

```text
ThriveRelay institutional service ID
        ≠
any particular vendor/product
unless an effective implementation/adoption record links them
```

This protects CrownThrive from vendor lock-in and from historical mapping drift.

## Service contract to preserve

Until the current implementation is adjudicated, ThriveRelay should preserve a narrow semantic role rather than duplicate OpsOasis or ThrivePush.

Candidate institutional responsibility:

- relay governed events between operational systems;
- workflow handoff/queue routing;
- retry and delivery continuity;
- scheduled/recurring automation triggers;
- integration state synchronization;
- execution acknowledgements;
- dead-letter/failure routing;
- machine-to-machine operational notifications;
- audit/evidence linkage.

These functions may be implemented together initially, but their stable institutional IDs and responsibilities should remain distinct.

## Reliability requirements

Any implementation selected for ThriveRelay should support:

- idempotent delivery;
- retry/backoff;
- dead-letter handling;
- replay with authority checks;
- schema/version validation;
- observability;
- rate limiting;
- tenant isolation;
- secret isolation;
- delivery evidence;
- export/backup;
- vendor replacement.

## Automation safety

A relay is transport, not authority. ThriveRelay must not independently decide that a user is entitled, a license is valid, money should move or content should publish. It carries authorized events or invokes already-authorized workflows.

Consequential relay deliveries require the originating authority/evidence reference and may require destination-side reauthorization.

## API/MCP role

ThriveRelay itself may expose operational tools such as:

- `get_delivery_status`
- `replay_delivery`
- `list_failed_deliveries`
- `pause_route`
- `resume_route`
- `get_route_health`

Route mutation/replay tools are operator-level capabilities and require incident/audit controls.

## Implementation decision matrix

Phase 2.98/2.99 must compare candidate implementations against:

- self-host/cloud portability;
- queue/event capabilities;
- webhook support;
- schedulers;
- retries/dead letters;
- observability;
- API/webhook integrations;
- auth/secrets;
- source availability/license;
- exportability;
- operating cost;
- agent integration;
- infrastructure burden;
- recovery characteristics.

A sprint/project-management product should not be selected merely because it was historically used if it does not satisfy the relay contract.
