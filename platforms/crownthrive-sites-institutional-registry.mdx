## Purpose

CrownThrive Sites™ is CrownThrive's productized website-system and managed implementation lane. It sits between self-service digital products and bespoke platform engineering, packaging reusable site systems, bounded implementation, lifecycle support, and governed ecosystem integration.

The platform may participate in commerce, beauty/wellness/phygital, faith/ministry, media/culture, education/community, advertising/distribution, professional-services, and other corridors without inheriting the authority of those domains.

## Current-state rule

Earlier source records proved a hosted public surface and read-only API routes. Those proofs remain historical evidence. They are not converted into a perpetual claim that the same provider version, route set, deployment, DNS, TLS, source revision, or runtime health remains current.

Current external-state claims require fresh readback through the applicable Penta provider path.

## Operating-system relationships

- **PentaDocs™** — current public-safe documentation, current-state corrections, release records, archive lineage, and machine-readable knowledge projection.
- **GitHub** — source-control and CI evidence transport. GitHub state does not manufacture institutional authority.
- **CHLOM** — policy, rights, evidence, authority, compliance, and bounded-execution rules.
- **PentaFabric™ / PentaMesh™** — governed interoperability and transport across certified interfaces.
- **PentaCredentials™** — credential references/readiness without exposing secret material.
- **PentaBuild™** — adapter, plugin, provider-binding, and integration asset construction.
- **PentaCertify™** — exact interface/provider/operation certification using evidence and live readback where required.
- **PentaNurture™** — health, drift, maintenance, and remediation routing.

Other ecosystem systems may connect only through explicit contracts and current certification. A planned ecosystem connection is not represented as a live customer connection.

## Lifecycle states

CrownThrive Sites records should distinguish at least:

- `candidate` — proposed product/system/configuration;
- `built` — source artifact exists;
- `controlled_test` — bounded test evidence exists;
- `readback_required` — source/deployment claim lacks current provider proof;
- `certified` — the exact declared scope has passed certification;
- `production_monitored` — certified live scope has current nurture/health evidence;
- `hold` — a required gate is unresolved;
- `superseded` — a newer version/state governs while history is retained.

No state transition is implied merely by elapsed time, a passing preview, or source presence.

## Public API and MCP

The Phase-2.99 predecessor packet described a narrow read-only API and a proposed MCP contract. That contract lineage is retained at [CrownThrive Sites API and MCP Boundary](/developers/crownthrive-sites-api-and-mcp-boundary).

Current rule: any public API/MCP route must be represented according to **current** source identity, provider readback, data class, authority class, and certification state. Side-effecting tools require exact-operation authorization and independent verification.

## Commercial and customer boundary

This registry does not activate:

- customer accounts;
- submissions or CRM writes;
- checkout or recurring billing;
- product prices;
- protected digital delivery;
- customer entitlements;
- rights grants;
- provider-wide deployment writes;
- D3 actions.

Those are separately governed through their applicable commerce, rights, privacy/security, provider, and authority controls.

## Release and rollback

Material Sites changes use a versioned, reviewable release packet containing source identity, changed scope, expected effect, tests, documentation impact, provider/runtime readback where applicable, and rollback or recovery state.

A build PASS alone is not release completion. A release becomes a current production claim only when the applicable source, governance, provider, documentation, verification, and recovery evidence agree.
