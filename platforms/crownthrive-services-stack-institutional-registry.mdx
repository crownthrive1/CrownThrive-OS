# CrownThrive Services Stack Institutional Registry

**Framework ID:** `ct.framework.crownthrive-services-stack`  
**Plugin ID:** `ct.plugin.crownthrive-services-stack`  
**MCP server:** `ct.mcp.crownthrive-services-stack`  
**CaaS authority:** CHLOM™ PLATFORM  
**State:** controlled test / governed HOLD  
**Authority ceiling:** D2  
**Sovereign-vote effect:** none

CrownThrive Services Stack, or CSS, is CrownThrive's canonical shared-service architecture. Its role is to prevent each platform from recreating identity, authentication, authorization, billing, licensing, analytics, notifications, CRM, ticketing, search, commerce, routing, rewards, and documentation as disconnected institutional truths.

## Institutional invariants

1. A CrownThrive service identity is stable and provider-independent.
2. A provider account is an execution binding, not the CSS service identity.
3. A contract candidate is not a verified deployment.
4. A target adoption row is not proof that a platform is connected.
5. A successful provider call does not manufacture billing, economic, entitlement, compliance, or governance truth.
6. Mutations require exact-operation authority, idempotency, rollback, readback, and independent verification.
7. CHLOM CaaS provides control evidence and readiness—not automatic legal or professional compliance conclusions.
8. History is append, correction, version, or supersession. Nothing is silently deleted.

## Registry layers

The restricted THIVEBASE registry separates:

- canonical service identities;
- service dependencies;
- versioned public contracts;
- provider bindings and provider-limit evidence;
- CHLOM control catalog and service-control bindings;
- control evidence and expiration;
- whole-ecosystem platform adoption targets;
- service routes and certification states;
- readiness observations;
- CSS/CaaS package assets;
- dependency graphs;
- append-only receipts and runs.

This separation is mandatory. It prevents an API key, provider record, route plan, commercial package, and institutional service from being treated as the same object.

## Provider bindings

Provider bindings progress through:

`unresolved -> candidate -> configured -> read_verified -> write_verified`

They may also enter `hold`, `blocked`, `revoked`, or `superseded`.

Every binding records the provider identity, role, exact contract version, credential state, provider-limit policy, evidence references, owner, different verifier, and public digest.

Request-budget semantics remain:

- `-1` — no CrownThrive-local monthly ceiling;
- `0` — disabled;
- positive integer — explicit CrownThrive-local ceiling;
- `NULL` — unresolved and fail closed.

Provider throttles, billing, quotas, included capacity, abuse controls, and contractual restrictions remain independently authoritative.

## Platform adoption

Every registered ecosystem platform receives a target CSS adoption matrix. The default states are candidates until exact connection evidence exists.

The migration pattern is:

`inventory local duplicate -> resolve CSS contract -> bind provider/adapter -> read canary -> reconcile data and identity -> bounded cutover -> readback -> supersede local duplicate`

A platform may retain specialized domain workflows and user experience. It must not silently fork the institutional truth owned by a shared CSS service.

## Asset estate

CSS includes 672 deterministic package candidates:

`14 services × 12 asset types × 4 deployment profiles`

The 12 asset types are plugin, kernel, contract, adapter, schema, event, workflow, skill, script, test suite, runbook, and policy.

The four deployment profiles are internal controlled, service runtime, edge/serverless, and customer-private.

These are derived package candidates under the existing proprietary estate. The authoritative source-asset count delta is zero.

## CaaS packages

Five non-operative product candidates are registered:

- CHLOM CaaS Foundation;
- CHLOM CaaS Growth Operations;
- CHLOM CaaS Commerce Assurance;
- CHLOM CaaS Enterprise Service Fabric;
- CHLOM Managed CaaS Assurance.

They remain research, candidate, or HOLD. Operative licenses, checkout, entitlements, payment movement, seller payouts, legal compliance claims, and exact prices are not active.
