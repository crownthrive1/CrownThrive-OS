# CrownThrive Services Stack

**Stable ID:** `ct.stack.crownthrive-services-stack`  
**Framework:** `ct.framework.crownthrive-services-stack`  
**CHLOM platform:** `ct.platform.chlom-caas`  
**Short name:** CSS  
**State:** controlled test / governed HOLD

CrownThrive Services Stack is the ecosystem's shared service architecture. It prevents every CrownThrive platform from rebuilding identity, authentication, authorization, billing, licensing, analytics, notifications, CRM, ticketing, search, commerce, routing, rewards, and documentation as isolated infrastructure.

CSS is connective tissue, not a monolith. Every lane has a stable CrownThrive contract while providers remain replaceable execution systems.

## Contract-first rule

A platform integrates with the CSS contract, not directly with an arbitrary provider account. Provider bindings remain explicit, versioned, replaceable and independently evidenced.

`provider capability ≠ CrownThrive deployment`

`provider success ≠ institutional truth`

`shared service contract ≠ unrestricted provider write`

## CHLOM CaaS boundary

CHLOM Compliance-as-a-Service supplies control mapping, evidence requirements, authority boundaries, lifecycle state, gap detection, certification receipts, rollback/readback requirements and audit-ready continuity.

It does not automatically declare a platform legally compliant, cybersecurity certified, accessibility conformant, tax-correct, audit-passed, regulator-approved or professionally certified.

## Lifecycle

`inventory -> contract candidate -> adapter candidate -> controlled test -> read verified -> bounded write canary -> write verified -> shared service active`

HOLD, BLOCKED, SUPERSEDED and RETIRED remain explicit lifecycle states. Failed evidence is preserved.

## Provider portability

Each lane may have a primary provider candidate and one or more fallbacks. Selection considers exact contract support, credential state, evidence freshness, data minimization, continuity, provider limits, cost, reversibility and operational risk.

A fallback plan never silently reroutes economic, identity or protected data. Material failover requires exact scope, evidence, rollback and readback.

## Asset binding

CSS projects 672 derived package candidates:

`14 lanes × 12 asset types × 4 deployment profiles`

These bind to the existing Asset Fabric and Proprietary Asset Factory. Their authoritative source-asset count delta is zero. They do not manufacture 672 independent IP claims merely because package projections exist.

## Governance

- A2/D2 automated ceiling;
- no sovereign vote;
- no D3 automation;
- no originator self-certification;
- no direct-main merge;
- no raw secret or private-identity export;
- no public protected implementation;
- no inherited provider-write authority;
- no live checkout or entitlement from a contract record;
- append, version or supersede—never silently delete.
