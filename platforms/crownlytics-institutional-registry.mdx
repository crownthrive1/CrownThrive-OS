## Current API evidence

Current first-party documentation identifies REST/JSON responses, Bearer API-key authentication, UTC behavior and API families for User, Websites, Pageviews, Visitors, Goals, Goal conversions, Annotations, Website statistics, Custom domains, Account payments and Account logs.

Documentation proves the contract family. It does not by itself prove that the live CrownThrive account accepts the credential or that any mutation is authorized.

## Credential custody

The existing CrownLytics provider credential completed the founder-authorized encrypted-envelope binding protocol. Primary and continuity-recovery references are present and server-side equality is verified.

The recovery reference contains the same provider credential. It is a dual continuity reference, not independently issued recovery. An opaque immutable version archive, active binding, protected custody records and restricted DAIL receipt preserve continuity.

No credential value, private fingerprint, Vault mapping or immutable archive mapping may appear in public documentation, logs, examples, generated artifacts or customer outputs.

## Runtime boundary

The JWT/admin-protected CrownLytics control adapter remains fail-closed for provider dispatch until one bounded authenticated read passes. The read must prove the expected account/tenant context, exact endpoint, response schema, timeout behavior and least-data projection.

Credential custody is not runtime authentication. Runtime authentication is not provider-write authority.

## Sensitive analytics data

CrownLytics data can include visitor/session identifiers, pageview data, goal/conversion evidence, replay or interaction metadata, account logs and other potentially sensitive operational records. General API/MCP projection must remain purpose-bound and least-data.

Do not return raw IP history, raw visitor/session identifiers, unrestricted replay bodies, account credentials or raw provider responses through general tools.

## Write authority

General provider writes remain closed. Any future write requires:

- exact operation and purpose;
- tenant and data-class bound;
- bounded payload;
- idempotency;
- authorization class;
- rollback;
- read-after-write;
- sanitized audit evidence.

A successful bounded write canary applies only to that operation and does not create arbitrary mutation authority.
