# ThriveSupport Institutional Registry

## Record identity

- Record class: `platform-intelligence`
- Platform/framework family: `ThriveSupport / Help Center Knowledge Architecture / CrownThrive Support`
- Program phase: `2.98`
- Inherited institutional release: `2.7.9.1`
- Extraction pass: `A — institutional core and public control plane`
- Evidence state: `multi-era / partially verified-current`
- Primary function: institutional memory, support knowledge, public policy/rule projection, operational documentation, recovery and machine-readable knowledge publication

## Canonical role

Current CrownThrive public material describes ThriveSupport as the institution's written memory and source-of-truth structure. It is explicitly framed as more than a FAQ system: a place for platform rules, governance posture, corridor/integration rules, technical runbooks, operating procedures, security/incident posture, versioned frameworks and public documentation.

Public source evidence also ties ThriveSupport to Collab Portal, Governance Stack, CHLOM, InfoSec and the corridor system.

This role is consistent with the merged `2.7.9.1` institutional architecture, but the implementation must remain layered. A public documentation deployment is not itself the complete private institutional authority.

## Lineage model

### Layer 1 — historical Help Center

Observed host: `help.crownthrive.com`

Current reachability evidence shows a large legacy Help Center corpus with categories including Legal and Compliance and General Policies. Recovered article families include privacy, CCPA, data deletion, breach preparedness, payment policy, affiliate terms, intellectual property, accessibility, sustainability, dispute resolution, platform-specific terms and other support/legal content.

State: `legacy-reachable / source-recovery corpus`

Rules:

- preserve it as historical source evidence while extraction continues;
- do not automatically treat every article as current policy;
- retain article title, URL, category, source date where available, recovery state and successor mapping;
- distinguish educational legal/compliance articles from binding current agreements;
- do not destroy it until dependency, redirect and archival coverage are proven.

### Layer 3 — crownthrivesupport.com branded knowledge entry point

Current CrownThrive portfolio material names `https://crownthrivesupport.com` as the primary hub for Help Center Knowledge Architecture / ThriveSupport.

The merged `2.7.9.1` release records the custom CrownThrive Support subdomain as intentionally deferred during the phased build. Therefore:

- the domain is an intended branded route, not proof of a completed current deployment;
- no `production` state is assigned until DNS/TLS/application routing and content behavior are verified;
- future authenticated/private areas require real server-side/application authorization, not hidden navigation or robots rules;
- the branded domain should consume the same governed knowledge authority rather than become a competing source of truth.

State: `target-branded-entry / deployment-unverified`

## Knowledge authority model

The institutional authority is not defined as “whatever page is most recent.” It is:

```text
authoritative structured registries
+ approved source evidence
+ effective-dated policies
+ version/correction history
+ role/authority decisions
        ↓
audience-specific projections
        ├── public Mintlify / CrownThrive Support
        ├── future crownthrivesupport.com public support
        ├── authenticated member/operator knowledge
        ├── restricted evidence views
        └── machine APIs/MCP resources
```

## Public/private boundary

### Public-safe

- platform explanations;
- public claims with evidence/as-of state;
- published policies;
- support articles;
- public runbooks where disclosure is safe;
- public developer/API contracts;
- current framework summaries;
- release notes and correction history;
- public status and lifecycle notices.

### Authenticated/relationship-scoped

- member-specific procedures;
- customer/partner/developer guidance;
- organization/team operating instructions;
- entitlement-dependent documentation;
- approved internal-but-nonsecret procedures.

### Restricted/strategic/machine-only

- private contracts;
- raw rights evidence;
- customer/identity/payment records;
- credentials and secret references;
- security-sensitive runbooks;
- investigations;
- private economics;
- unpublished works/source files;
- confidential CHLOM methods;
- policy-engine internals;
- raw authorization state;
- private evaluation artifacts.

No public repository or public documentation host may become the storage authority for those classes.

## Search and retrieval control

ThriveSupport search must become identity- and classification-aware.

Required order:

1. identify caller and assurance level;
2. determine role, relationship, tenant/platform and purpose;
3. apply resource/data classification policy;
4. select permitted search/index partitions;
5. retrieve only authorized material;
6. record access/evidence event where required;
7. generate answer/projection within the same authorization boundary.

Retrieving restricted material first and attempting to redact it after model generation is not an acceptable primary control.

## Automated publication model

```text
source / registry / policy change
→ stable-ID resolution
→ source-authority and version check
→ audience/data classification
→ secrets/PII/restricted-content scan
→ transformation to projection
→ legal/rights/cultural/claim rules
→ link/schema/accessibility/SEO tests
→ approval gate where required
→ publish
→ search/sitemap/index refresh
→ DAIL/change event
→ drift monitor
→ rollback path
```

Goal: routine knowledge publication should become highly automated while consequential legal, rights, cultural, security and authority decisions remain gated.

## Legal Depot interaction

Legacy Help Center Legal and Compliance content may contain useful historical policy evidence but must not override a newer effective-dated agreement merely because it remains searchable.

Legal policy precedence requires:

- stable policy ID;
- policy family;
- version;
- effective date;
- actor/platform/geography/transaction applicability;
- acceptance mechanism;
- supersedes/superseded-by relationship;
- counsel-review state;
- source evidence;
- public projection.

## Support routing model

Target routing should separate:

- `support case` — account, billing, technical, access or customer problem;
- `knowledge` — how-to, rules, explanations and self-service;
- `legal/policy` — effective agreements and compliance notices;
- `status/incident` — outages and operational status;
- `roadmap/feedback` — ThriveMaps/product-direction lane;
- `execution/collaboration` — Collab Portal;
- `developer` — API/MCP/SDK contracts;
- `restricted institutional` — authorized private control plane.

This prevents ThriveSupport from becoming an undifferentiated catch-all.
