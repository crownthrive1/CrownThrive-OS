# ThriveKiosks & TapStations Institutional Registry

## Institutional identity

CrownThrive's phygital strategy separates **interactive software/service endpoints** from **configured physical hardware and field operations**.

| Surface | Stable ID | Current institutional role |
| --- | --- | --- |
| ThriveKiosks | `ct.platform.thrivekiosks` | interactive phygital endpoint for identity/check-in, loyalty, ordering, profiles, media, ticketing, local discovery and approved commerce |
| TapStations | `ct.platform.tapstations` | configured hardware/device, installation, maintenance and field-deployment layer |
| AdLuxe Places | `ct.platform.adluxe-places` | place-based advertising inventory, schedules, campaigns, screens and proof-of-play |

**Phase:** 2.98 Pass D4<br />**Current source status:** Holdings strategy and recovered institutional platform/legal records establish role and target architecture; current device fleet, provider stack, source repository, hardware inventory, installed software, production APIs and live locations remain verification-gated.

<Warning>
  A domain, mockup, installed browser, device purchase, kiosk shell or signage provider does not prove a production ThriveKiosks deployment. Each live endpoint requires a registered device/location, software/version, owner, permissions, privacy/accessibility controls, health evidence and rollback/recovery path.
</Warning>

## Source-defined use cases

The current Holdings strategy defines ThriveKiosks/TapStations as potential endpoints for:

- check-in;
- identity/account linking;
- loyalty/rewards;
- digital media;
- ticketing and scanning;
- ordering/commerce;
- professional profiles;
- advertising;
- local discovery.

Initial deployments should be partner-funded, leased, sponsored or attached to proven locations where feasible to reduce capital risk. This is strategic guidance, not proof of an active deployment fleet.

## Role separation

ThriveKiosks provides the interaction/runtime experience. TapStations governs configured hardware and field service. AdLuxe Places governs place-based advertising. CrownThrive ID governs identity/account context. CrownRewards governs reward rules/ledger. ThriveTickets governs tickets/events. CrownLytics normalizes measurements. CHLOM governs applicable permissions, rights, agreements and evidence.

No subsystem should silently become the source of truth for another subsystem's records.

## Interaction flows

### Check-in

```text
user or guest arrives
→ notices/consent displayed
→ optional CrownThrive ID/account resolution
→ event/location eligibility
→ check-in event
→ optional ticket validation
→ optional reward event
→ confirmation
→ audit/analytics event
```

### Commerce/order

```text
product/service discovered
→ current price/availability retrieved
→ checkout provider handoff
→ payment authoritative at processor
→ CrownThrive order record
→ receipt/entitlement/fulfillment route
→ kiosk confirmation
```

Kiosk UI must never treat a payment attempt as a successful order.

### Ticketing

```text
ticket presented
→ ThriveTickets verification
→ event/venue/time/status check
→ scan/check-in event
→ duplicate/invalid state handled
→ attendance evidence
→ optional CrownRewards/CrownLytics event
```

### Advertising

```text
placement registered
→ AdLuxe Places campaign eligibility
→ approved creative/version
→ schedule
→ playback/impression evidence
→ local interaction/conversion where supportable
→ normalized report
```

## Privacy and safety

Kiosks are public/shared-device environments. Default controls include:

- minimum necessary data display;
- no persistent authentication session after completion;
- clear logout/session timeout;
- masked personal/account information;
- no raw payment credentials stored locally;
- restricted camera/microphone/sensor use;
- signage/notice for any recording or analytics;
- child/minor-safe modes where applicable;
- accessible interaction paths;
- remote wipe/disable capability where technically supported;
- physical tamper and maintenance procedures;
- incident escalation.

Precise location, health, private spiritual, family or other sensitive data must not be reused for advertising without explicit authority.

## Accessibility baseline

Every public endpoint should document:

- reachable placement and physical controls;
- screen height/angle considerations;
- keyboard/switch compatibility where applicable;
- high-contrast/readable presentation;
- text resizing;
- captions/transcripts for media;
- timeout extension or alternatives;
- screen-reader/audio alternative where supported;
- staff/remote assistance path;
- accessible ticket/check-in alternative.

A hardware provider's accessibility marketing does not certify CrownThrive's configured deployment.

## Device security baseline

Minimum controls:

- unique device identity;
- least-privilege runtime account;
- signed or verified deployments where supported;
- automatic security updates under controlled policy;
- restricted local admin access;
- full-disk/device encryption where supported;
- remote health monitoring;
- kiosk-mode/browser lockdown;
- no plaintext secrets;
- key/token rotation;
- network segmentation where feasible;
- audit events for configuration changes;
- recovery image or documented rebuild path.

## Economic models

Potential commercial models include partner-funded install, lease, rental, sponsorship, managed service, advertising share, installation fee and maintenance fee. None is active by default.

Every economic schedule must identify effective date, device/location scope, installation cost, recurring fees, connectivity, maintenance, ownership, replacement, ad share, payment processing, taxes, insurance, damage/loss and termination/sell-off behavior.

## Agent boundaries

| Agent | Autonomous work | Prohibited authority |
| --- | --- | --- |
| Endpoint Health Agent | poll health, detect offline/stale devices, open incidents, retry safe telemetry | cannot remotely wipe/reimage without approved incident policy |
| Deployment QA Agent | verify configuration, routes, accessibility checklist, links and version | cannot promote a device to production without release authority |
| Commerce/Ticket QA Agent | sandbox test scans/checkouts and reconciliation | cannot issue refunds, tickets or paid entitlements without authority |
| AdLuxe Placement Agent | verify placement mapping, schedule and reporting | cannot change campaign economics or restricted targeting |
| Documentation Agent | update device/location/API/help/changelog records from approved evidence | cannot expose private site/network credentials |

## Controlled self-healing

Permitted: retry telemetry, restart bounded user interface processes under approved policy, refresh non-secret configuration, re-fetch signed content, reopen stale incidents, regenerate documentation indexes and rerun tests.

Prohibited silent actions: factory reset, device wipe, payment configuration change, price change, ad-policy override, credential exposure, account impersonation or new location activation.
