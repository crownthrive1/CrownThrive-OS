## Verified current public capability

Current CrownPulse public material exposes one-line pixel installation, campaigns, configurable widgets/popups, social-proof notifications, visitor-activity presentation, campaign notifications, notification handlers, custom domains, team/plan capabilities, analytics/statistics retention claims, API access and white-label/custom-branding options.

Current public notification-handler integrations include email, webhook, Slack, Discord, Telegram, Microsoft Teams, SMS, phone call, WhatsApp, X/Twitter, Google Chat and internal notifications.

## Current provider and custody snapshot — 2026-08-21

Founder-supplied administrator evidence identifies the current CrownPulse implementation as **66socialproof / AltumCode**, with installed version `v57.0.0`, an available `v61.0.0` update and expired vendor support. This is a dated operational snapshot, not permission to upgrade or mutate the provider account.

Current public technical routes are:

- API documentation: `https://crownpulse.com/api-documentation`;
- account API surface: `https://crownpulse.com/account-api`.

A founder-supplied privileged API credential is now held only in the restricted CHLOM/ThriveBase credential-control path with primary and recovery custody verified. The raw value, fingerprint and recovery material are prohibited from public documentation, examples, GitHub, logs and screenshots. Credential custody does **not** certify endpoint behavior: no authenticated production request or write canary was executed as part of this documentation pass, and provider writes remain closed.

The same administrator snapshot contained account-level activity counters and several unconfirmed/suspicious-looking signup records. Raw dashboard user counts therefore remain restricted operational evidence and must not be represented as verified active customers, unique humans or qualified community reach without a defined population/methodology.

## Public proof and engagement claims

The site displays dynamic counters for notifications created, notifications displayed and users. These are `public_dynamic_counter` records and require retrieval timestamps before reuse.

CrownPulse social proof must never fabricate events. Displayed signals must be tied to an authorized source, an explicitly identified synthetic/demo context, or manually authored messaging that is not falsely represented as observed customer behavior.

## Consent and suppression controls

CrownPulse can present or transmit engagement through multiple channels. The institutional control plane must distinguish website social proof, transactional notifications, operational alerts, marketing messages, lifecycle re-engagement and administrator/internal alerts.

Required controls include consent/source record, channel eligibility, opt-out/suppression, frequency caps, quiet hours where applicable, campaign owner, template version, destination verification, retries/idempotency, abuse protection and delivery/evidence logs.

## Public compliance claims

The current site states GDPR, CCPA and PECR compliance. Classification: `public-claimed` pending policy, implementation and legal verification. CrownPulse does not receive blanket ecosystem compliance certification from marketing copy.

## Data classes

Potential classes include account/user profile, tracked website/domain, campaign configuration, widget/style configuration, visitor/activity events, conversion/social-proof events, IP/device/browser/geographic statistics, notification destination identifiers, webhook URLs, chat/workspace integration configuration, phone/SMS/WhatsApp destinations, custom domains, teams, API key references, account-payment metadata and delivery/statistics records.

Credentials, tokens and webhook secrets belong in restricted secret storage.

## Relationship to CrownLytics and ThrivePush

```text
CrownLytics
measurement / analytics / conversion evidence
       ↓ governed event
CrownPulse
social proof / engagement display / selected notification routing
       ↓ lifecycle qualification
ThrivePush

```

A single event may flow through all three, but each service receives only fields necessary for its role.

## MCP candidate tools

Read-oriented candidates:

- `list_campaigns`
- `get_campaign`
- `list_campaign_notifications`
- `list_notification_handlers`
- `list_custom_domains`

Higher-risk mutations include campaign changes, widget publishing, notification-handler creation, external-channel sending, custom-domain mutation and account/team/payment changes. External message sending is a consequential side effect and must be explicitly scoped, rate-limited and audited.

## Plan and quota governance

Public plan copy exposes campaign, notification, impression, domain, team, retention, branding and API limits. Canonical values must come from an effective-dated plan/entitlement registry. Enterprise `unlimited` language still requires operational limits, fair-use/abuse rules and backend configuration.

## Security priorities

- API-key isolation and rotation;
- webhook destination validation and SSRF protection;
- template injection/XSS prevention;
- custom-domain verification;
- tenant isolation;
- channel-provider credential isolation;
- opt-out/suppression enforcement;
- anti-spam and anti-fraud controls;
- false-social-proof prevention;
- signed or traceable source-event linkage.
