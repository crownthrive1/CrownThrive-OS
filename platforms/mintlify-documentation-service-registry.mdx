# Mintlify Documentation Service Registry

## Current identity

- **Service ID:** `ct.service.documentation.mintlify`
- **Institutional platform:** `ct.platform.crownthrive-support`
- **Source repository:** `crownthrive1/CrownThrive-Support`
- **Deploy branch:** `main`
- **Active deployment endpoint:** [crown-thrive.mintlify.io](https://crown-thrive.mintlify.io/)
- **Current access observation:** the deployment endpoint resolves and hands off to Mintlify authentication
- **Custom-domain target:** `docs.crownthrive.io`
- **Custom-domain disposition:** governed Phase 20 deferral; not current production authority

Mintlify renders a governed documentation projection. It does not own CrownThrive institutional knowledge, decide source authority or convert a draft GitHub packet into accepted policy.

## Superseded custom-domain evidence

Earlier DNS and certificate-validation values are historical provider evidence and must not be reused. The custom hostname currently fails public readback and is not represented as active. Any future activation requires a fresh provider read, current DNS/TLS values, explicit authority, independent HTTPS readback, redirect/canonical verification and a rollback record.

## GitHub-to-Mintlify workflow

The connected documentation source is the public CrownThrive Support repository. Documentation changes must:

1. identify their public-safe source and authority;
2. update `docs.json` navigation or record an explicit governed-unlisted disposition;
3. pass documentation and packet-specific validation;
4. preserve private evidence, credentials and runtime topology outside public prose;
5. remain draft/HOLD when specialist, legal, rights, security or phase gates are incomplete;
6. merge through the governed GitHub path before Mintlify publication.

The Sites production-bootstrap packet is navigated in the documentation estate but remains a Phase 2.99 HOLD until its machine manifest reaches the required terminal state.

## Help Center boundary

The 795-record Help Center machine manifest is canonical source structure after its governed merge. That closes machine materialization only. Original bodies remain unrecovered unless separately proven, every record still requires terminal disposition and owner/risk/exposure/source mapping, and Phase 3 remains blocked.

## Automation posture

Automation may detect broken internal links, unlisted pages, stale verification dates and deterministic schema drift. It may prepare bounded documentation fixes. It may not invent missing article bodies, publish secrets, mark candidate DIDs as signed credentials, alter current legal or commerce policy, or merge its own consequential packet.

## Recovery standard

CrownThrive must retain:

- Git history and governed release references;
- machine-readable navigation and article manifests;
- source registers and checksums;
- redirect/canonical maps;
- workflow definitions;
- custom-domain history without reusable stale validation tokens;
- off-provider exports and rebuild instructions;
- the last known good documentation deployment reference.

The documentation estate must remain reconstructable if Mintlify becomes unavailable.
