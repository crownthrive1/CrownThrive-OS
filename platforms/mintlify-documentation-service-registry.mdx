## Security and access credential inventory — 2026-08-22

Founder-supplied current provider-dashboard evidence establishes a bounded Mintlify credential estate for this deployment. The raw credential material is **restricted runtime-only** and is not stored in this repository, Mintlify page content, examples, screenshots, tickets, or public changelogs.

| Credential class | Current count | Intended use | Public documentation rule |
| --- | --: | --- | --- |
| Project identifier | 1 | deployment/project targeting and governed server-side administration | existence/state only; value restricted |
| Admin API key | 2 | server-side updates, previews, automations, agent jobs and analytics export | count/scope/state only; values restricted |
| Assistant API key | 2 | assistant messages, search and page-content access through a trusted backend proxy | never embed client-side; count/scope/state only |
| Mintlify Index API key | 2 | indexing workloads | count/scope/state only; values restricted |
| MCP `client_credentials` grant | 1 | machine-to-machine Mintlify MCP access for the governed `thrivebase_mintly` client | client name/state only; client ID and secret restricted |

Custody is now split correctly:

- secret values are encrypted in the ThriveBase Supabase Vault;
- a private `thivebase_private` credential registry records stable institutional IDs, Vault references, credential class, intended use, provider date, state and SHA-256 fingerprints;
- the private schema is not exposed to `public`, `anon` or ordinary `authenticated` roles;
- the public Mintlify/GitHub projection records only non-secret inventory, purpose, governance state and rotation/verification posture;
- no credential value may be copied into generated examples, CI output, browser bundles, agent prompts, public logs or knowledge articles.

<Note>
  **Canonical naming:** `ThriveBase` is the institutional system name. The physical schema identifier `thivebase_private` is preserved here because it is an exact deployed legacy database identifier; it must not be treated as the canonical product/platform spelling. Any schema rename requires a separately governed migration and readback.
</Note>

Stable credential families are registered under `ct.cred.mintlify.*`. Full secret-store references and cryptographic fingerprints remain private operational evidence rather than public documentation payloads.

Current verification state is `founder_attested_not_runtime_tested`. This is sufficient to establish custody and inventory, but it does **not** certify each key's effective API scope, rate limits, revocation behavior or live endpoint success. Read-only/canary certification must be recorded separately before a key is promoted to `runtime_verified`.

### Rotation and incident rule

Do not rotate merely because the credentials were institutionalized. Rotate or revoke on suspected exposure, role/scope change, provider compromise, offboarding, confirmed misuse, or the governed rotation schedule. Any rotation must preserve the stable credential record, replace the Vault secret atomically where feasible, update the private fingerprint, invalidate superseded runtime bindings, and create an evidence/change event without publishing either the old or new value.

## Required automation posture

The current founder-authorized GitHub scope is intentionally limited to **`crownthrive1/CrownThrive-OS`**. Do not connect additional GitHub repositories to this documentation workflow unless a later explicit founder decision changes that boundary.

Within CrownThrive-OS, automation should register and maintain:

- repository and branch;
- platform/service IDs represented by documentation;
- documentation impact mapping;
- code/document owners and approval class;
- public-safe API/schema/event documentation sources;
- changelog policy;
- secrets boundary;
- documentation-agent permissions;
- rollback path.

Application/platform state outside the repository is imported as governed evidence through authorized public inspection, source/release artifacts, Drive/File Library records, provider exports and other registered sources. Those external sources remain `not_connected_to_mintlify_workflows` rather than candidates for automatic Git attachment under the current directive.

Documentation agents should run from CrownThrive-OS PR/change events and bounded scheduled evidence/drift checks rather than frequent uncontrolled polling.

## Publication boundary

PentaDocs may publish approved public-safe or authenticated institutional projections. The Mintlify provider layer must not receive unrestricted production secrets, raw customer/payment payloads, privileged communications, confidential rights evidence or protected trade-secret implementation merely because the provider can store and render text.

## Recovery standard

CrownThrive must retain:

- Git repository and release history;
- machine-readable navigation/article manifest;
- off-provider content export;
- source register and checksums;
- redirect/canonical map;
- custom-domain/DNS record;
- workflow definitions;
- rebuild instructions;
- last known good deployment reference.

The institution must be able to rebuild documentation if Mintlify becomes unavailable.

## Service-product status

Mintlify is registered as a **third-party documentation infrastructure service/product** in the CrownThrive operating spine. It is not a CrownThrive-owned SaaS product and should not be marketed as such.
