## Collab Portal Institutional Registry


Collab Portal is CrownThrive's controlled relationship/workspace surface for partners, collaborators, clients, vendors, licensees and selected operators. It is not the institutional source of truth and does not replace GitHub/PentaDocs, CHLOM, CrownThrive ID, OpsOasis, ThriveMaps or the private institutional core. Mintlify remains the current PentaDocs rendering/hosting provider.

## Project-management role

The initial CrownThrive PM integration should be intentionally narrow.

The Secure API can:

- retrieve project metadata/custom-field definitions;
- list projects;
- find an existing project by UID, exact name, name substring or most-recent;
- update an existing project.

The contract does **not** currently expose project creation. Therefore an institutional project such as `CrownThrive Institutional Build` must exist before automation can bind to it.

After the project UID is recovered, the UID becomes the stable external mapping. The project name remains a display/bootstrap identifier.

## Source-of-truth boundary

```text
runtime/evidence systems
        ↓
CrownThrive institutional records
        ↓
GitHub / Mintlify governed state
        ↓
Collab Portal project projection
        ↓
Gmail / human notification
```

A Collab Portal field is not allowed to silently override a governed institutional record. If the portal and repository disagree, reconcile from source authority and open a correction/delta.

## CRM boundary

The API can read/create/update contacts and companies. Those surfaces are **not enabled by default for the hourly institutional PM loop**.

CRM writes require their own purpose, consent, ownership, duplicate-resolution, welcome-email, community/Worlds, marketing and data-retention rules. A project-status agent does not inherit CRM marketing authority.

## Marketing boundary

`POST /marketing/subscribe` subscribes contacts to marketing audiences. It is excluded from the project-management automation by default.

Any future use requires:

- consent/source evidence;
- audience ID governance;
- suppression/unsubscribe compatibility;
- purpose limitation;
- ThrivePush/marketing responsibility reconciliation;
- error/partial-failure handling.

## Worlds boundary

`GET /worlds` is documented as available only with a Worlds Power-up. The current power-up entitlement is not verified from the OpenAPI alone.

World assignment capabilities also appear in contact/company schemas, but no PM agent may use them merely because the schema exposes the fields.

## OpenAI provider configuration

The portal exposes an OpenAI provider configuration UI with an API-key field and model selector. This proves a provider-configuration capability; it does not make the portal the CrownThrive-wide AI secret authority.

Rules:

- use a newly generated OpenAI project key, never a key exposed in chat/screenshot;
- keep the key server-side and portal-side only where required;
- never commit it to CrownThrive-OS;
- keep OpenAI key rotation independent from Collab Portal Secure API secret rotation;
- apply model/provider budgets, evals and authority limits outside the provider dropdown;
- do not make institutional behavior depend permanently on one provider UI model label.

## Webhook boundary

The user confirms the broader SuitePro/Collab Portal system has webhook capability. The supplied Secure API OpenAPI does not include webhook registration or event schemas.

Webhook integration remains `source_not_recovered` for:

- event names;
- payloads;
- endpoint registration;
- signature scheme;
- retry schedule;
- delivery logs;
- idempotency/replay;
- secret rotation.

Do not build event-driven automation from assumptions. Recover the webhook contract separately.

## API quality findings

The specification uses API-key security schemes correctly for header names but also includes scope-like strings in security requirement arrays. Those are not OAuth scopes, and several operation labels are inconsistent. Actual access rights must be tested and recorded from observed account behavior.

The generic `Error-429` example mentions 200 monthly requests, while the current account UI displays 20,000. Keep both evidence records; use the newer account UI for the dated CrownThrive account snapshot and do not rewrite the older generic schema example.

## Reliability and mutation rules

For the PM adapter:

1. discover project meta;
2. resolve/pin project UID;
3. read current project;
4. calculate a minimal allowed diff;
5. PUT once;
6. read back;
7. compare expected/actual;
8. record evidence;
9. on ambiguity, stop mutation and open an incident/delta;
10. fall back to GitHub \+ Gmail.

Never blind-retry a mutation whose outcome is unknown.

## Data classification

Potential portal data includes:

- client/contact PII;
- company information;
- projects and internal descriptions;
- partner/collaborator records;
- files and potentially sensitive IP;
- CRM notes and custom fields;
- team/staff assignment;
- business/economic project fields.

Project-status automation should use the minimum fields needed and avoid copying restricted evidence into general project descriptions.

## Signature and sensitive-file role

Institutional doctrine still assigns Collab Portal a role for agreements, signatures, controlled partner files and sensitive collaboration. Those capabilities are visible at the product level but are not exposed in `S101` Secure API operations.

They remain separate integration lanes requiring their own evidence, acceptance/version tracking and API/export contract if automation is desired.

## Continuity / vendor exit

Collab Portal is an execution projection, so CrownThrive must survive its loss.

Required continuity assets:

- project UID mapping;
- field mapping;
- API contract snapshot/hash;
- credential owner and rotation record;
- export procedure;
- current project-state mirror in institutional records;
- critical file/approval/signature evidence references outside a single vendor where law/contract permits;
- fallback GitHub \+ Gmail PM workflow;
- vendor replacement adapter plan.
