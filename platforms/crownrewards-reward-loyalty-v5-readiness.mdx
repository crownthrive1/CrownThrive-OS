# CrownRewards — Reward Loyalty v5 Readiness

## Identity boundary

CrownRewards and its public alias **My CrownRewards** are CrownThrive loyalty/retention assets. Their current underlying self-hosted engine is **Reward Loyalty**.

This relationship is intentionally separate from the other infrastructure relationships:

| CrownThrive asset | Underlying provider/engine | Institutional job |
| --- | --- | --- |
| Crown Affiliates | Partnero | affiliate/referral attribution, partners, customers, commissions and transactions |
| AdLuxe Network | Adserver.Online | advertising delivery, inventory/campaign reporting and ad-serving capability |
| CrownRewards / My CrownRewards | Reward Loyalty | closed-loop loyalty, points, stamps, rewards, vouchers, passes and partner/member operations |

Cross-platform events may interoperate through CrownThrive ID, IO/MCP, CHLOM, THIVEBASE and CrownLytics, but the providers and institutional identities do **not** collapse into one system.

## v5 API architecture

Reward Loyalty v5 separates two API models.

### Session-token REST API

The REST API is designed for signed-in custom frontends, mobile apps and third-party integrations.

```text
https://mycrownrewards.com/api/{locale}/v1
```

Authentication is session/Bearer-token based and follows the signed-in actor.

Source: `https://rewardloyalty.co/docs/5.x/api-reference/overview`

### Agent API

The Agent API is the stronger CrownThrive machine-to-machine target for POS systems, automations and approved AI agents.

```text
https://mycrownrewards.com/api/agent/v1
```

The provider documents:

- `X-Agent-Key` authentication;
- separate partner, member and admin key classes;
- granular scopes;
- request audit logging;
- rate limits;
- stateless JSON requests;
- health discovery;
- OpenAPI 3.0;
- runtime tool discovery;
- OpenAI, Anthropic, MCP and generic tool-definition formats.

Provider sources:

- `https://rewardloyalty.co/docs/5.x/agent-api`
- `https://rewardloyalty.co/docs/5.x/agent-api/overview`
- `https://rewardloyalty.co/docs/5.x/agent-api/authentication`
- `https://rewardloyalty.co/docs/5.x/agent-api/scopes`
- `https://rewardloyalty.co/docs/5.x/agent-api/tool-discovery`

## Upgrade gate

The v4 production install must not be overwritten merely because v5 is available.

Required sequence:

1. preserve current v4 production and license evidence;
2. obtain the v5 entitlement/package through the provider's supported path;
3. back up the production database, uploaded files, configuration, environment and current application package;
4. create a staging clone;
5. validate server/runtime requirements and required PHP extensions;
6. apply the v5 upgrade in staging using the provider-supported method;
7. reconcile partners, members, cards, balances, transactions, rewards, stamps, vouchers, passes, plans, staff, branding and settings;
8. test public, member, partner, staff and admin flows;
9. verify email, queues/jobs, QR/wallet behavior, privacy/security and activity logs;
10. enable Agent API only after feature/plan permission and least-privilege scope design;
11. create separate keys by environment and integration surface;
12. certify read-only health, OpenAPI and tool discovery before any write scope;
13. run missing-scope, wrong-tenant, malformed-input, duplicate/idempotency, rate-limit, retry, timeout and reconciliation tests;
14. document rollback and cutover;
15. obtain the appropriate governance approval before production migration.

Provider update guidance explicitly recommends testing updates in a test environment and backing up the database before production deployment.

Source: `https://rewardloyalty.co/docs/5.x/installation-and-updates/updating`

## Security model

Agent API keys must remain server-side and follow least privilege. A general-purpose admin key is not the default integration model.

CrownThrive rules:

- no Agent API key in browser JavaScript or mobile bundles;
- no single production key reused across development/staging/production;
- separate integrations receive separate keys where practical;
- start with read-only health/discovery;
- grant write scopes only for a proven workflow;
- provider permissions never override CrownThrive organization/role/CHLOM checks;
- all material writes require idempotency/reconciliation evidence;
- keys must have a tested rotation/revocation procedure;
- raw member/partner data is not projected into public Mintlify documentation.
