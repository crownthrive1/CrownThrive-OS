# PENTA Dictionary & Institutional Glossary

This is the living human-and-machine terminology reference for CrownThrive's PENTA architecture. It defines canonical names, intended meanings, boundaries, and relationships. New terms may be added as the ecosystem expands, but existing meanings should not be silently changed without versioning and preserved historical context.

## Foundational doctrine

### PENTA

**Discover → Govern → Execute → Verify → Preserve.** The five-stage institutional execution doctrine. PENTA is both a naming family and an operating contract. A PENTA participant should be human-legible, machine-addressable, governed, observable, verifiable, and preservable.

### Discover

The evidence-first process of identifying providers, assets, routes, endpoints, schemas, contracts, dependencies, versions, state, capabilities, and participants. Discovery does not imply authority.

### Govern

The authority and policy stage. Governance determines whether an action is permitted, under which capability, risk class, evidence threshold, credential boundary, and continuity rule.

### Execute

Performance of a governed operation through a runtime, provider adapter, queue, workflow, compiler, service, or other certified execution surface.

### Verify

Independent or provider-backed evidence that an operation produced the intended result. Includes read-after-write, receipts, hashes, canaries, tests, heartbeats, status readback, signatures, and reconciliation.

### Preserve

Retention of the institutional truth required for auditability, continuity, reproducibility, succession, provenance, future automation, and long-term stewardship.

## PENTA institutional systems

### PentaMedia

CrownThrive's PENTA media-operations layer. Manages media asset bindings, maintenance cycles, receipts, status, and ongoing continuity across governed media properties.

### PentaBooks

Governed book-production and literary continuity system. Covers books, sources, canon facts, editions, assets, standards, bindings, QA runs, events, system state, and public catalog projection.

### PentaGeneration

Seven-generation continuity system. Responsible for horizons, intergenerational handoff, stewardship evidence, lineage-aware continuity, proofs, assets, events, bindings, and system state.

### PentaStudios

Studio and production-operations system. Covers production assets, provider bindings, routes, control surfaces, and MCP interoperability.

### Penta Federation

Federation layer for cross-system identity, bindings, events, proofs, and federation state. It prevents each PENTA system from becoming an isolated island.

### PentaFramework Factory

Governed software/framework production participant. Produces or extends reusable framework assets through the broader CrownThrive Software Factory and Phase 3 certification architecture.

### Penta Control

Control-plane runtime for PENTA systems. Provides a consolidated administrative/execution control surface without replacing CHLOM authority.

### Penta MCP

Machine/tool interoperability layer for PENTA participants. Provides MCP-addressable capability surfaces while remaining subordinate to governance and certification rules.

### PentaDocs

Canonical CrownThrive institutional documentation and knowledge layer. Human explanation, machine context, doctrine, runbooks, governance records, architecture, glossary, version history, and institutional memory live here. The underlying documentation vendor may vary; PentaDocs is the CrownThrive system identity.

## PentaRoute execution family

### PentaRoute

Canonical routing orchestrator. Resolves a requested operation to a registered route, runtime, or provider adapter and checks governance/certification before dispatch.

### PentaTun

Runtime execution participant. Routes governed work into registered internal execution surfaces and runtime corridors.

### PentaBeata

Heartbeat and liveness participant. Continuously checks whether registered runtime/control surfaces remain operational and records observable state.

### PentaFetch

Bounded fetch participant for governed retrieval. Used for controlled retrieval rather than arbitrary unregistered network access.

### PentaGet

HTTP GET primitive for certified/registered read routes.

### PentaHead

HTTP HEAD primitive for metadata and transport inspection.

### PentaOptions

HTTP OPTIONS primitive for allowed-method and capability inspection where supported.

### PentaPost

HTTP POST primitive. It is an execution mechanism, not an authority grant; exact operation certification remains required for mutations.

### PentaPut

HTTP PUT primitive for certified replacement/update operations.

### PentaPatch

HTTP PATCH primitive for certified partial updates.

### PentaDelete

HTTP DELETE primitive for exact certified deletions. **It never means universal delete authority.**

## Discovery, query, and reading

### PentaDiscover

Self-discovery participant for providers, endpoints, assets, contracts, services, dependencies, capabilities, and missing integrations.

### PentaSearch

Search participant for governed indexes, registries, documentation, catalogs, and search-capable providers.

### PentaQuery

Structured query participant for governed data sources.

### PentaRead

Generic governed read abstraction for resources that are not necessarily HTTP GET operations.

### PentaList

Enumerates governed resources, records, services, assets, or entries from registered sources.

### PentaResolve

Resolves canonical identities, references, bindings, routes, aliases, or target addresses.

### PentaObserve

Non-mutating observation participant for health, provider state, configuration state, and runtime evidence.

### PentaParse

Parses and normalizes supported payloads into canonical representations.

### PentaTransform

Performs governed data/content transformations without silently changing source provenance.

### PentaValidate

Validates payloads, schemas, contracts, packages, states, or evidence against defined rules.

## State, cache, and movement

### PentaCache

Governed cache read/write/invalidation participant. Cache operations remain scoped and observable.

### PentaSync

Synchronizes authorized state between registered systems while retaining source-of-truth and reconciliation rules.

### PentaIngest

Ingests governed content, records, evidence, provider data, or institutional packages.

### PentaImport

Imports governed artifacts/configuration packages into an approved target.

### PentaExport

Exports governed artifacts, evidence packages, reports, or portable institutional state.

### PentaSnapshot

Captures a point-in-time state/evidence snapshot for verification, continuity, comparison, or audit.

## CRUD abstractions

### PentaCreate

Creates a new governed resource only through a certified create contract.

### PentaUpdate

Updates an existing governed resource through a certified update operation.

### PentaUpsert

Creates or updates according to a certified idempotent upsert contract.

## Queues, scheduling, and reliability

### PentaQueue

Queue participant for enqueue, claim/dequeue, acknowledgement, completion, retry, and queue evidence.

### PentaRetry

Bounded retry participant using controlled backoff and retry eligibility rules. It must not endlessly repeat irreversible work.

### PentaDispatch

Dispatches governed work to a certified runtime, worker, provider adapter, or queue.

### PentaSchedule

Creates and reconciles governed internal schedules. External duplicate clocks should not be manufactured merely because scheduling exists.

### PentaLock

Applies bounded logical locks to work items or resources to prevent unsafe concurrent execution.

### PentaReconcile

Compares desired and observed state and produces convergence actions or evidence.

### PentaRollback

Executes a certified rollback or compensating operation when reversal is part of the certified contract.

## Integration, events, and streams

### PentaBind

Creates or refreshes governed bindings among providers, credentials, runtimes, assets, systems, and routes.

### PentaHook

Webhook participant for registration, verification, delivery, receipt handling, and lifecycle management.

### PentaEvent

Emits, receives, records, and reconciles governed events.

### PentaStream

Handles governed streaming or continuous event/data flows where a certified stream contract exists.

## Security and authority

### PentaVault

Credential and secret-custody participant. PentaVault references or brokers secrets through approved vault mechanisms; it should not expose secrets in public evidence surfaces.

### PentaAuth

Authentication and authorization orchestration participant. Authentication proves identity; authorization determines permitted action. They are related but not interchangeable.

### PentaSign

Signature participant for governed signatures, request signing, evidence signing, package signing, or identity-bound attestations.

### PentaCertify

Promotes an operation or capability only when required evidence and certification rules have passed. It does not certify by naming convention.

### PentaAudit

Records and verifies operational evidence, receipts, decision context, versions, and relevant provenance.

## Testing and assurance

### PentaTest

Runs governed tests, canaries, contract checks, and verification suites.

### PentaBeata

See heartbeat definition above. PentaBeata is a continuous assurance participant, not merely a ping utility.

### PentaRollback

See rollback definition above. Rollback capability is part of bounded-write certification when a provider supports safe reversal.

### Read-after-write

Verification pattern in which a mutation is followed by an independent read of the same resource/state to confirm the intended result.

### Canary

A bounded test execution designed to prove a runtime/provider contract with minimal blast radius. Good canaries are synthetic, reversible where possible, idempotent, and evidence-producing.

### Receipt

Machine-readable evidence of an execution, including relevant identifiers, timestamps, hashes, status, target, method, version, and result.

### Evidence hash

Cryptographic digest used to detect evidence/content drift and support reproducibility and audit integrity.

### PentaRelease

## CrownThrive institutional architecture

### CrownThrive

The institutional and ecosystem umbrella. PENTA systems operate inside CrownThrive rather than replacing it.

### CrownThrive OS

The operating-system/control-plane architecture that coordinates governed automation across CrownThrive services and properties.

### Phase 3

Current convergence era centered on autonomous self-discovery, bounded-write certification, provider-adapter completion, runtime proof, hardwired institutional execution, and progressive closure of remaining capability gaps.

### CHLOM

CrownThrive governance, capability, rights, policy, evidence, vault, continuity, and certification authority. CHLOM determines whether an operation is authorized; PENTA execution components do not manufacture authority.

### ThriveBase

CrownThrive's primary execution, state, automation, database, evidence, and runtime control plane built on Supabase infrastructure.

### Integration Mesh

Machine-readable set of registered provider/integration contracts, capabilities, endpoints, vault references, health state, quotas, and certification metadata.

### Federation

A design pattern that shares canonical identity/contracts across repositories and systems while avoiding divergent copies of authority definitions.

### Repository Federation Bus

Runtime that propagates or coordinates repository-level federation state and events.

### Runtime certification

Process of proving that a registered runtime/provider is reachable and, where applicable, authenticated and capable of the exact certified operation.

### Bounded-write certification

Certification model in which **specific operations** become write-verified rather than granting provider-wide write authority.

### Operation-level authority

Authority attached to one exact operation/path/verb/contract instead of the entire provider.

### D0 / D1 / D2 / D3

CrownThrive risk/governance classes. Lower classes may be eligible for more autonomous execution; D3 represents high-impact or irreversible authority that remains subject to stronger human/founder governance.

## Documentation and knowledge terms

### Canonical

The authoritative current identity, definition, registry, or source used to resolve conflicts among copies.

### Historical version

A preserved superseded version retained for provenance, reproducibility, governance history, or continuity.

### Current truth

The best verified representation of the system's present production state. Current truth should be distinguished from plans, targets, drafts, and historical snapshots.

### Institutionalize

To convert an idea, configuration, workflow, asset, or runtime into a governed, named, documented, registered, versioned, observable, and continuity-aware institutional capability.

### Hardwired

Within CrownThrive documentation, hardwired should mean a persistent registered binding with health/availability monitoring, explicit capability contracts, vault-bound credentials where applicable, retry/reconnect behavior, and institutional evidence. It does **not** mean bypassing provider controls or exposing secrets publicly.

### Vault-bound

A credential/secret relationship in which the institutional record stores a vault reference or brokered capability rather than plaintext secret material.

### Machine-readable

Structured in a way software can reliably identify identity, role, state, version, capability, dependencies, evidence, or policy without interpreting prose alone.

### Human-readable

Explained in language sufficient for operators, developers, auditors, partners, and future stewards to understand purpose and boundaries.

### Self-discovery

Continuous autonomous inspection of the operating environment to identify missing adapters, endpoints, provider capabilities, dependencies, stale bindings, or certification gaps.

### Self-heal

Governed repair of known-safe conditions through bounded remediation logic. Self-heal does not authorize arbitrary infrastructure mutation.

### Fail-closed

When required proof, authority, contract, credential, or target binding is missing, the system refuses the operation rather than assuming permission.

### Fail-open

A policy that continues execution when proof or control is unavailable. Fail-open is generally inappropriate for sensitive CrownThrive mutations unless explicitly designed and approved.

### Idempotency

Property that permits a repeated operation without causing unintended duplicate effects. Important for retries, queue processing, payments, webhooks, deployments, and reconciliation.

### Compensating action

A safe counter-operation used when a true rollback is unavailable. The compensating action must itself be governed and certified.

### Provider-native adapter

Implementation that uses a provider's supported APIs, contracts, authentication, and lifecycle rather than pretending all providers behave identically.

### Hosted tool adapter

A tool capability available through the ChatGPT/connected-tool environment that is cataloged by CrownThrive but cannot be assumed callable directly from an independent deployed runtime without a separate provider credential/contract.

## Extension rules for future PENTA names

A new PENTA name should be created only when all of the following are true:

1. It describes a distinct institutional responsibility.
2. Its meaning is not already covered cleanly by another PENTA participant.
3. It can be defined in terms of Discover, Govern, Execute, Verify, Preserve.
4. It has a machine key and human name.
5. Its authority boundary is explicit.
6. Its relationship to PentaRoute, Phase 3, CHLOM, ThriveBase, Penta Federation, or another certified corridor is documented.
7. Its lifecycle and versioning model are defined.
8. It is added to this dictionary and the relevant machine registry.

### Reserved naming pattern

Use **Penta \+ concise role noun/verb** where the name communicates the system responsibility clearly. Avoid names that are merely decorative or duplicate an existing component.

### Future participants

Future external developers, licensed operators, acquired systems, community institutions, providers, and new CrownThrive corridors may participate in PENTA through certified adapters and federation contracts without giving up their own brand identities.
