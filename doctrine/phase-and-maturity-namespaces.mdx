# Phase and Maturity Namespaces

CrownThrive has used the word **phase** in several valid but different systems. Every reference must carry a namespace. A phase label is never evidence of production, legal or commercial status.

## 1. Institutional-build program

Canonical namespace: `institutional_build_phase`.

| Phase / release | Meaning |
| --- | --- |
| Phase 1 | CrownThrive Operating System map and initial standards |
| Phase 2 | CHLOM and Help Center recovery |
| Phase 2.5 | institutional consolidation |
| Phase 2.7 | exhaustiveness and forgotten-IP recovery |
| Phase 2.8 | contradiction hunting and adjudication |
| Phase 2.9 | adversarial continuity |
| Phase 2.95 | IP/developer/API/pallet/paper completeness |
| Phase 2.97 / `2.7.9.0` | initial governance, standards and protection baseline |
| `2.7.9.1` | deep governance re-audit patch to Phase 2.97 |
| Phase 2.98 | platform-by-platform extraction and verification |
| Phase 2.99 | private core, automation topology and machine seed package |
| Phase 3 | executable institutional core and developer substrate |
| Phase 4 | federated ecosystem activation and Thrive Flywheel |
| Phase 5 | institutional scale, licensing and sovereign expansion |

The four-part machine release `EPOCH.PROGRAM.AUDIT.PATCH` is separate from the human-readable phase label.

## 2. CHLOM product-delivery program

Canonical namespace: `chlom_product_delivery_phase`.

The 2026 CHLOM High-Level Technical Build Pack uses a product-specific delivery roadmap:

- **CHLOM Product Phase 0 — Foundation:** charter, terms, registry reconciliation, pilot selection, DLA contract, threat model, provider decisions, backlog and architecture records;
- **CHLOM Product Phase 1 — MVP Build:** identity, asset/evidence, rights graph, DLA, LEX, agreements, entitlements, policy, audit, disputes and core integrations;
- **CHLOM Product Phase 1B — Pilot & Hardening:** selected CrownThrive capability pallets, finance reconciliation, security, accessibility, support, runbooks, SLOs and analytics;
- **CHLOM Product Phase 2 — Partner Scale:** SSO, developer portal, advanced policy, jurisdiction configuration, partner onboarding and reporting;
- **CHLOM Product Phase 3 — Optional Protocol:** verifiable credentials, public anchors, advanced privacy, governance automation and optional DAO/token work only after validation.

These labels describe the CHLOM product roadmap and do not replace CrownThrive's institutional Phase 3–5 charter. The current program crosswalk places CHLOM Foundation/MVP work inside institutional Phase 3, pilots/integration across institutional Phases 3–4, and optional protocol work across Phase 3E/Phase 5.

## 3. Historical CHLOM protocol-adoption phases

Canonical namespace: `chlom_historical_protocol_phase`.

Historical Goldpaper/MTD sources described:

- development/testing;
- XENthrive transfer of docs/IP;
- builder onboarding;
- validator and AI co-training;
- CrownThrive ecosystem rollout;
- full decentralization.

These phases are preserved as historical target architecture. They do not prove current transfer, builder network, validator environment, token economics or decentralization.

## 4. Ecosystem rollout phase

Canonical namespace: `ecosystem_rollout_phase`.

Public CrownThrive material has used **Phase 0** to describe integration, internal testing and staged ecosystem activation. This does not mean no CrownThrive platform is live. Public wording should state what the label measures and give capability-specific status.

## 5. Founder/incubator progression

Canonical namespace: `incubator_progression_stage`.

Historical handbook and incubator sources use Phase 0–4 or other staged development language for people, ventures and programs. Preserve the original source meaning and map to current portfolio/product states without treating the numbers as identical.

## 6. Asset/platform lifecycle

Canonical namespace: `asset_lifecycle_state`.

`concept → validate → build → pilot → beta → active → growth → license → reserve → merge → sunset → archive`

A platform may be `active` publicly while a specific API, SSO, commerce or admin capability is `uninspected`, `build` or `degraded`.

## 7. Implementation maturity

Canonical namespace: `implementation_state`.

`uninspected → recovered → reconciled → decomposed → specified → prototype → test → controlled_pilot → production → maintained → degraded → superseded`

Each CHLOM component, platform capability, adapter and room/product can progress independently.

## 8. Legal activation

Canonical namespace: `legal_state`.

`not_reviewed → research_only → legal_review_required → draft → counsel_review → jurisdiction_ready → authorized → active → suspended → expired → terminated`

MM Suites franchise/regional licensing, patents/trademarks, investment/equity/token models and external CHLOM offerings require this separate state.

## 9. Product/release state

Canonical namespace: `release_state`.

Products, books, music, licenses, services and policies use their own release/approval states. They do not inherit a platform or institutional phase number.

## 10. Technical program and migration

Use named `sprint`, `release`, `migration_stage`, `cohort`, `pilot` or ADR-defined program IDs. Avoid unqualified “Phase N” for an API migration or deployment.

## Wording rule

Never write “CrownThrive is in Phase 3” without the namespace.

Correct:

- “The CrownThrive institutional-build program is preparing Phase 3.0.”
- “The CHLOM product-delivery roadmap is entering its MVP build.”
- “Virality Music is publicly active; its SSO adapter is still specified.”
- “MM Suites is foundational IP and build-stage phygital architecture; legal franchise activation is gated.”

<Warning>
  Phase numbers are planning and control labels. They do not establish ownership, filing, availability, production readiness, legal status, integration completeness, customer proof or commercial authorization.
</Warning>
