# Framework and Engine Registry

CrownThrive's institutional IP includes frameworks and engines that are neither ordinary brands nor standalone software platforms. Phase 2.95 keeps those concepts explicit so later engineering can implement them as policies, schemas, workflows, services or reusable operating patterns without forcing each into a public app.

## Phase 2.99 Workstream 3A macro reconciliation

The [Macro Source & Claim Seed](/knowledge/phase-2-99-workstream-3a-macro-source-claim-seed) assigns stable machine identities and resolves the recovered linear framework string into typed relationships.

Canonical macro IDs now include:

- `ct.framework.convergent-ecosystem` — umbrella institutional operating field;
- `ct.framework.cultural-imprint-engine` — cultural/narrative/canon governance;
- `ct.framework.thrive-flywheel` — value circulation and growth;
- `ct.framework.chlom` — rights/rules/roles/revenue/records/remedies governance;
- `ct.framework.hybrid-incubator` — shared development/activation operating model;
- `ct.framework.mm-suites` — specific Melanin Magic Suites phygital proving-ground architecture;
- `ct.framework.corridor-architecture` — organizational lane and governed-handoff model;
- `ct.framework.one-seat-multiple-industries` — target cross-platform experience doctrine.

The source shorthand `Convergent Ecosystem > CIE > Thrive Flywheel > CHLOM > MM Suites > Corridors > Platforms` is treated as an **ordered governance/application stack**, not a strict legal ownership or database-containment hierarchy (`CT-CON-033`).

`MM Suites` is not the generic machine name for every ecosystem capability bundle. Generic reusable bundles use `pallet`, `capability pallet`, `suite` or another separately governed identity; **MM Suites / Melanin Magic Suites** remains the specific beauty/wellness phygital, Suite Pro, location and franchise/regional-license readiness architecture (`CT-CON-032`).

## Phase 2.99 Workstream 3A engine/service source overlay

The [Holdings 85-Row Engine & Service Seed](/knowledge/phase-2-99-workstream-3a-holdings-85-engine-service-source-seed) now binds `CT-COUNT-003` to the exact `S100-ENG-001` through `S100-ENG-085` management rows.

These source rows are not all the same object class. They include vendor products, self-hostable scripts, plugins/add-ons, hosted services, platform engines, replacement candidates, retired/reserve implementations and planned acquisitions. Source status/license/support fields remain dated management evidence rather than current deployment certification.

`CT-CON-037` prevents source `Active/Core/Live/Build` labels from becoming current operational proof. `CT-CON-038` separates license/entitlement, support/renewal, provider availability, installed version and deployment state.

The 85-row registry is also **not exhaustive current-provider truth**. Providers recovered after the S100 plan remain separate current evidence and must not be forced into the historical count.

## Registry fields

Each framework should carry stable ID, canonical name, aliases, owner, source family, version, current status, IP class, purpose, inputs, outputs, affected corridors, implementation components, policy relationships, evidence, public claim wording and successor/predecessor links.

Each engine/service record should additionally carry source-row ID, provider/product identity, source assignment, platform/capability relationships, license/entitlement evidence, support state, provider availability, installed version, repository/deployment, API/webhook/export state, data classes, security/support risk, replacement/vendor-exit path and last verification.

## Current machine rule

Platforms **perform** work. Corridors **organize** work. Frameworks **govern or shape** work. Engines/services **execute reusable capability**. Phase 2.99 machine seeds and any later engineering schemas must preserve those distinctions. Phase 3 remains blocked until the applicable seed/reference/provider gates are satisfied.
