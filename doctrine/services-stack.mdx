## CrownThrive Services Stack (CSS)

The **CrownThrive Services Stack (CSS)** is CrownThrive's shared service architecture: the connective tissue that lets many platforms reuse institutional capabilities without rebuilding the same infrastructure independently.

CSS is not a single public app and it is not a replacement for the brands or corridors it serves. It is the reusable service layer beneath them.

## Canonical service domains

The current canonical CSS service domains are:

1. Identity
2. Authentication
3. Authorization
4. Billing
5. Licensing
6. Analytics
7. Notifications
8. CRM
9. Ticketing
10. Search
11. Commerce
12. Routing
13. Rewards
14. Documentation

Additional capabilities may be admitted only through governed framework/service registration; they do not silently become CSS merely because multiple platforms use them.

## Why CSS exists

Without CSS, each CrownThrive platform would repeatedly rebuild login, permissions, billing, licensing, analytics, messaging, CRM, ticketing, search, commerce, routing, rewards and documentation. That creates incompatible policy, duplicated cost, fragmented data and inconsistent member experiences.

CSS establishes a shared-capability contract:

```text
Platform / Corridor
→ governed CSS service request
→ identity + authority + policy checks
→ reusable capability execution
→ evidence / event / receipt
→ platform-specific experience
```

A platform keeps its own identity, experience and business logic while relying on shared institutional rails where appropriate.

## CIE, CHLOM and CSS boundaries

CSS is an execution layer, not an authority factory.

| Layer | Governs |
| --- | --- |
| Cultural Imprint Engine (CIE) | cultural alignment, narrative, representation, canon, aesthetics and responsible reuse |
| CHLOM | rights, permissions, licensing, roles, records, evidence, remedies and compliance state |
| CSS | reusable institutional service execution under already-resolved authority |
| PentaGreen | economic activation, SKU/commerce authority and ECAC/HOLD/DENY for governed economic state |
| Thrive Flywheel | how value, attention, participation, proof and retention circulate across the ecosystem |

A CIE pass cannot create a license. A CHLOM license cannot bypass a CIE cultural block. A CSS service cannot manufacture caller authority. A successful provider call cannot manufacture CrownThrive economic truth.

## Service contract

Every CSS service should resolve to a machine-readable contract containing at minimum:

- stable service ID and canonical name;
- purpose and owning institutional capability;
- supported callers/platforms;
- input and output schema;
- authentication and authorization requirements;
- CHLOM/CIE/PentaGreen policy hooks where applicable;
- data classification and retention requirements;
- idempotency and event semantics;
- error and HOLD states;
- evidence and observability requirements;
- rollback/compensation behavior;
- support/SLA expectations;
- version and deprecation policy.

## Platform integration rule

Platforms integrate to CSS by **capability**, not by copying provider-specific assumptions into each product.

For example:

```text
Locticians / ThriveSeat / CrownThriveU / Media / Commerce surface
                 ↓
          CSS capability contract
                 ↓
     replaceable provider / internal engine
```

The provider may change while the institutional service contract remains stable.

## Relationship to CIE

CIE is a first-class policy input wherever a CSS request affects cultural expression, public narrative, imprint reuse, audience classification or representation.

Examples include:

- routing a Kulture House project into media channels;
- publishing or syndicating a Bonged Out! cultural asset;
- reusing a universe, character, image or campaign across corridors;
- generating public-facing descriptions or creative derivatives;
- adapting a culturally specific experience into a new market or format.

CSS may execute the approved routing, notification, documentation or analytics capability. It does not decide cultural legitimacy on its own.

## Anti-fragmentation rule

A new service requirement should first ask whether CSS already provides the capability. A new public platform should not be created merely to expose a reusable internal service.

A new provider also does not create a new institutional service identity. Provider implementations remain replaceable behind the governed CSS contract.

## Operational maturity

CSS service records should progress through explicit lifecycle states such as:

```text
PROPOSED → CONTRACTED → CONTROLLED_TEST → VERIFIED → ACTIVE
                                      ↘ HOLD / RETIRED / SUPERSEDED
```

Technical success is not enough for promotion. Required rights, security, data, operational and governance evidence must pass independently.

## Institutional result

CSS reduces duplication while increasing interoperability. It makes the Convergent Ecosystem easier to scale because platforms can remain culturally and commercially distinct while sharing controlled institutional infrastructure.
