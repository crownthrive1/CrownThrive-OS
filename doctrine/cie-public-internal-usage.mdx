# CIE Public & Internal Usage

CrownThrive has **one Cultural Imprint Engine**.

```yaml
framework_id: ct.framework.cultural-imprint-engine
canonical_name: Cultural Imprint Engine
canonical_acronym: CIE
canonical_name_only: true
public_profile: ct.cie.profile.public.v1
internal_profile: ct.cie.profile.internal.v1
```

`CIE` is shorthand for **Cultural Imprint Engine**. `Cultural Impact Engine` is stale projection drift and is rejected for new records, schemas, contracts, API/MCP surfaces, agents and documentation. It is not an alternate engine identity.

Public and internal usage are profiles of the same engine. They do not create separate engines, separate doctrine or separate authority.

## Public-safe profile

The public-safe profile supports:

- public doctrine and institutional explanation;
- public-safe status and decision-state projection;
- deterministic validation and conformance;
- sanitized CIE → CHLOM handoff envelopes;
- public developer contracts and integration guidance;
- public-safe source and canon references.

Public-safe fields may include stable IDs, CIE state, condition codes, audience class, canon state, public source references, contract version and public digests.

The public profile must not expose:

- raw private evidence;
- private evidence references;
- credentials or secrets;
- protected calibration or weights;
- private evaluation corpora;
- defensive rules;
- private reasoning.

## Internal-governed profile

The internal-governed profile supports approved CrownThrive operations under RBAC and institutional identity controls.

It may support:

- internal governance and conformance;
- opaque private-evidence references;
- CIE ↔ CHLOM reconciliation;
- drift and correction workflows;
- separately authorized protected-runtime invocation;
- internal agent/human evidence preparation.

Internal use does **not** authorize raw-secret echo, uncontrolled evidence publication, private-reasoning export, D3 automation, sovereign votes, provider writes, economic state changes or licenses.

## Same authority ceiling

Changing profile changes visibility and data handling. It does not change CIE's authority.

Both profiles retain:

- the same Cultural Imprint Engine identity;
- the same ten CIE governance domains;
- the same decision vocabulary;
- the same CHLOM boundary;
- the same D2 ceiling;
- the same non-voting state;
- the same human-reserved D3 boundary.

## Projection rule

Internal-governed records may be projected publicly only after restricted fields are removed or replaced with approved public-safe references.

Public-safe records do not become internal evidence truth merely because they are published.

```text
internal governed state
→ disclosure / rights / evidence check
→ sanitize restricted fields
→ public-safe projection
```

The reverse direction requires independent evidence resolution rather than trust-by-publication.

## CHLOM relationship

Both profiles can interoperate with CHLOM through the same typed contract. Profile choice changes which evidence references may travel; it never changes CHLOM's ownership, licensing, permission, evidence or remedies authority.

See [CIE ↔ CHLOM Interoperability](/doctrine/cie-chlom-interoperability).

## Fail-closed conditions

Return HOLD when any material requirement is unresolved, including:

- engine identity;
- usage profile;
- RBAC for internal use;
- evidence visibility;
- contract version;
- digest;
- object/use identity;
- audience or canon state;
- receiving-system authority.

## Machine projection

The CIE child package carries the public-safe machine projection in:

- `registry/cie-usage-profiles.v1.json`;
- `framework/manifest.json`;
- `api/api-contract.v2.json`;
- `mcp/mcp-tools.v2.json`;
- `scripts/validate_wave2_interoperability.py`.

A declared API/MCP contract is not proof that a public network endpoint has been deployed. Network activation remains a separate governed state.
