# CrownThrive Institutional Archive

**Status:** Active archive policy under the PENTA Phase Model  
**Current institutional phase:** Phase 3 — Execute  
**Canonical lifecycle:** Discover → Govern → Execute → Verify → Preserve

## Purpose

The archive preserves superseded, stale, historical, prior-version, pre-entry, retired, and transitional CrownThrive records without allowing those records to silently operate as current instruction.

CrownThrive does not clean history by rewriting old evidence to match today's architecture. The institution preserves the historical record, identifies its disposition, and links forward to the current canonical successor.

> **Preserve the evidence. Retire the obsolete instruction. Link to the successor.**

## PENTA phase-history consolidation

The institutional roadmap is now the five-phase PENTA model: Phase 1 Discover, Phase 2 Govern, Phase 3 Execute, Phase 4 Verify, Phase 5 Preserve.

Historical decimal institutional phases are retired as current roadmap taxonomy. Phase 2.5, 2.7, 2.8, 2.9, 2.95, 2.97, 2.98, 2.99, pre-entry convergence, and similar institutional transition labels are preserved as historical aliases of the broader **Phase 2 — Govern** generation.

Their documents, releases, branches, filenames, migration identifiers, articles, and receipts are not deleted simply because the naming model changed. They remain evidence of what CrownThrive knew, planned, attempted, certified, or operated at that point in time. What is retired is their authority to function as the current institution-wide roadmap.

No new decimal institutional phases should be created. Precision belongs in component versions, maturity states, certification states, release numbers, waves, milestones, or temporary delivery cohorts.

See [`../phase-model/PENTA_PHASE_MODEL.md`](../phase-model/PENTA_PHASE_MODEL.md), [`PENTA_PHASE_RETIREMENT_MANIFEST.json`](PENTA_PHASE_RETIREMENT_MANIFEST.json), and the additive [`RELEASE_SUPERSESSION_LEDGER.v1.json`](RELEASE_SUPERSESSION_LEDGER.v1.json).

## Archive rule

A record belongs in the historical/archive layer when it describes an earlier institutional phase, uses a retired phase label as current roadmap language, has a newer canonical successor, carries stale provider/runtime/version claims, represents a prior roadmap or deprecated workflow, has been renamed/merged/sunset, or remains useful as evidence but should not be used as present implementation instruction.

## Required historical labeling

Where practical, archived material should identify its original title/path, effective period, archival disposition, reason, successor record, relevant evidence references, and whether any requirement was explicitly inherited by a current system.

If preserving the original body verbatim matters, add metadata or an archive wrapper rather than changing historical prose to sound current.

## Archive states

- `HISTORICAL` — evidence of a valid prior state.
- `SUPERSEDED` — prospectively replaced by an identified successor.
- `DEPRECATED` — retained but no longer recommended/current.
- `RETIRED` — intentionally removed from active operational use.
- `RETIRED_TIMELINE_ALIAS` — former institutional phase/timeline label retained solely for historical mapping.
- `UNRESOLVED_HISTORY` — preserved source whose current successor or disposition is not yet proven.

## Current-vs-history precedence

When current and historical material conflict, CrownThrive OS current effective records control institution-wide state. OS-bound verified evidence, current governance, active component records, and certified provider readbacks control within their exact scope.

PentaDocs, websites, storefronts, media surfaces, and other public properties are downstream projections. Publication lag creates a reconciliation task; it does not redefine the current OS.

## Machine and search behavior

Historical pages should generally be marked `Historical`, `deprecated: true`, and `noindex: true` where search visibility would likely cause current-state confusion. Public institutional-history pages may remain discoverable when their historical status is unmistakable.

Machine consumers should treat retired timeline aliases as non-authoritative planning metadata. A historical label can be used to locate evidence but must resolve through the canonical PENTA phase model before being interpreted as current institutional state.

## Retire the instruction, not the evidence

Archive processing must never fabricate missing bodies, erase provenance, remove correction history, rewrite historical evidence to match modern terminology, convert an old capability claim into current proof, expose restricted evidence, remove a still-required compatibility contract, or destroy institutional custody merely to simplify navigation.

Retirement should remove obsolete behavior from the active operating surface. It should not destroy the ability to understand why that behavior existed.

## Priority archive cohorts

1. Phase 1 / Phase 2 / Phase 2.x / pre-entry status and roadmap pages whose current function is replaced by the PENTA model.
2. Superseded CHLOM/CIE/runtime/API/MCP generations.
3. Historical roadmap generations replaced by the canonical PENTA lifecycle.
4. Renamed or legacy brand/imprint records.
5. Recovered Help Center titles with substantive current successors.
6. Old release notes, manifests, provider-state snapshots, test artifacts, migration notes, and implementation receipts retained for audit history.
7. Duplicate or abandoned architecture paths that have a proven current successor.

## Relationship to releases and compatibility

Git tags, GitHub releases, changelogs, migration names, schemas, archived docs, and compatibility identifiers are historical records. They do not need to be renamed simply because the institution adopted the PENTA model.

An old `v1` or `v2` API may remain the correct current component contract. Institutional Phase 3 does not force every component to version 3. Likewise, a historical Phase 2.99 file can remain named Phase 2.99 while being classified as `RETIRED_TIMELINE_ALIAS` and linked to Phase 2 — Govern history.

## Current canon

For current institutional orientation use the PENTA Phase Model, Phase 3 Current State, PENTA Doctrine, the root README, and current version/governance/provider/evidence registries.

**Historical records explain how CrownThrive got here. Current records determine where CrownThrive is now and what it may do next.**
