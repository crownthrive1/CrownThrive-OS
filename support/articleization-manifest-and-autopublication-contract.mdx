## Articleization Manifest and Autopublication Contract

## Decision

This contract originated in the historical Phase 2.98/2.99 documentation-recovery program. Those labels below describe lineage, not current institutional authority.

**Phase 2.99 Workstream 0** converts that growing body into a complete machine-addressable Help Center projection: category manifests, article IDs, versions, routes, redirects, source mappings, docs-impact contracts, changelogs, drift queues and publication controls.

**Current Phase 3 — Execute** generates and maintains contract-driven API, MCP, schema, event and service documentation from executable institutional systems, subject to independent subsystem evidence.

```text
Phase 2.98
source-grounded platform, policy, workflow and registry articles
        ↓
Phase 2.99 Workstream 0
complete article/category/version/navigation/source manifest
        ↓
Phase 3
contract-generated technical documentation and synchronized change events
        ↓
PENTA Phase 4 — Verify / Phase 5 — Preserve
evidence revalidation, portfolio-wide drift control and durable continuity
```

CrownThrive did not wait until Phase 3 to write articles. During current Phase 3 execution, undocumented P0/P1 gaps remain explicit holds rather than being treated as completed by phase promotion.

## Scope

The recovered Help Center inventory currently targets **795 article titles** across public support, operator knowledge, platform guides, policies, legal/depot coverage, developer documentation, CHLOM, products, rights/licensing, governance, workflows, SOPs, recovery and institutional doctrine.

The number is a recovered-title estate, not proof that 795 current substantive bodies are already complete. Every title must resolve to one of these states:

- `substantive_current`;
- `substantive_historical`;
- `redirected_to_successor`;
- `merged_into_canonical`;
- `restricted_projection_only`;
- `source_recovery_pending`;
- `owner_validation_pending`;
- `legal_or_specialist_review_pending`;
- `retired_history_preserved`;
- `rejected_duplicate_or_unsupported`.

A placeholder title without a source/status record does not count as completed articleization.

## Source-of-truth rule

The versioned CrownThrive institutional record is the governed source of truth for approved institutional meaning, terminology, relationships, policies, lifecycle and public-safe representation.

Runtime/source systems remain authoritative evidence for the facts they originate, including:

- processor payment objects;
- source-code revisions and tests;
- provider delivery logs;
- product/catalog records;
- customer account state;
- deployment and uptime evidence;
- signed agreements;
- rights/source files;
- current public routes;
- analytics counters;
- domain/DNS state.

Documentation must cite/map those sources rather than replace them with unsupported prose. When runtime evidence and approved institutional meaning disagree, open a governed conflict/delta. Do not silently make one imitate the other.

## Article versioning

Use semantic intent rather than cosmetic churn:

- **patch** — typo, broken link, formatting, nonmaterial clarification or evidence-reference repair that does not change obligations/meaning;
- **minor** — new steps, capability, route, example, role, product state, compatibility detail or expanded explanation without reversing the governing rule;
- **major** — changed policy, legal/economic obligation, rights scope, canon, privacy/security control, API contract, eligibility, lifecycle, source authority or platform relationship.

Corrections never erase the prior record. A correction event records what changed, why, source, approver, effective time, affected platforms/products/API clients and public-notice requirement.

## Documentation impact contract

Every material change in a connected or inspected system must resolve exactly one outcome:

```yaml
docs_impact_id:
change_id:
source_repository_or_system_id:
source_revision_or_event_id:
change_type:
materiality:
affected_platform_ids: []
affected_article_ids: []
affected_policy_ids: []
affected_api_contract_ids: []
affected_changelog_ids: []
outcome: docs_updated|docs_no_change|docs_delta_opened
reason:
validation_results: []
approvals: []
published_revision:
completed_at:
```

### `docs_updated`

Required articles/changelogs/manifests changed in the same governed release or an explicitly linked documentation PR.

### `docs_no_change`

A responsible agent/human records why the change has no documentation impact. This is not a bypass phrase; it requires an inspectable basis.

### `docs_delta_opened`

The documentation cannot safely update yet because evidence, owner validation, specialist review, source access or implementation completion is missing. A delta record, owner, severity and deadline are created. Material public releases may be blocked depending on risk.

A material change with no one of these outcomes fails the release gate.

## Risk classes

### D0 — mechanical

Examples: link repair, formatting, generated index, spelling allowlist, nonmaterial metadata normalization.

May be automatically prepared, validated, approved and merged by bounded agents when all checks pass.

### D1 — operationally low risk

Examples: current route inventory, additive support steps, nonbinding API examples, dated metrics snapshot, explicit unresolved-source record.

May use subordinate approval under a defined quorum when no legal, rights, privacy, security, canon, economic or contractual materiality exists.

### D2 — material

Examples: product/plan/price/license/API behavior, user-facing workflow, eligibility, public claim, content/canon relationship, data handling, provider state or release-readiness conclusion.

Requires responsible domain-agent review and authorized human/owner approval where the adopted authority matrix requires it.

### D3 — high consequence

Examples: legal terms, binding license, exclusive/adaptation rights, securities/franchise/equity claims, privacy/security incident, Scripture/canon authority, paid entitlements, source-history recovery, public allegations, regulated categories or irreversible production action.

No subordinate agent quorum may final-approve D3. Qualified human authority and any required legal/security/rights review must be recorded.

## Subordinate approval rules

A subordinate approval may be accepted only when:

- the change is D0 or an explicitly permitted D1 class;
- the agent is authorized for the article/platform/data class;
- the source and diff are inspectable;
- no conflict, unresolved evidence or policy exception exists;
- automated validation passes;
- the approving agent did not author the entire material change without independent check where separation is required;
- rollback is available;
- DAIL records the decision.

A subordinate may return:

- `approve`;
- `approve_after_mechanical_fixes`;
- `deny_with_required_changes`;
- `escalate_for_domain_review`;
- `escalate_for_human_authority`;
- `block_due_to_missing_evidence`.

Lower-level approval never overrides a higher-level denial or hard gate.

## Self-checking contract

Before publication, agents verify:

1. source hierarchy and freshness;
2. stable IDs and aliases;
3. current versus historical/research/deployed state;
4. version/effective date;
5. cross-page terminology and counts;
6. public/private/restricted boundary;
7. links, anchors, navigation and redirects;
8. claims, metrics and evidence period;
9. API/schema/code examples against contracts;
10. legal/rights/privacy/security/economic materiality;
11. affected platform and master changelogs;
12. phase-gate impact;
13. rollback/correction path;
14. no false completion or invented source.

Material articles require an independent verification path: separate agent, test, authoritative export or responsible human review.

## Controlled self-healing

Permitted self-healing includes:

- retrying idempotent read-only source checks;
- recreating generated navigation/search/index manifests;
- repairing broken internal links and anchors;
- refreshing dated snapshots from authorized sources;
- regenerating nonbinding API examples from a versioned schema;
- reopening a failed docs-impact task;
- rebasing a documentation branch when no semantic conflict exists;
- rerunning validation;
- rolling back a failed documentation-only release;
- suppressing an obviously unsafe autopublish and escalating.

Agents must not silently:

- change legal terms or license scope;
- alter price, fee, split, royalty or payout;
- grant/revoke paid entitlements;
- resolve ownership, canon, Scripture, privacy or security disputes;
- rotate/expose credentials outside approved secret systems;
- rewrite Git history;
- force-push reconstructed build artifacts as source;
- mark unverified provider capability as deployed;
- delete prior corrections or evidence;
- publish restricted/private material;
- waive a phase gate.

## Lean automation architecture

CrownThrive is grassroots and cost-sensitive. The default implementation order is:

1. Git and GitHub as version/control evidence;
2. existing Mintlify projection for public docs;
3. Python/Node validation scripts in the repository;
4. GitHub Actions for event/scheduled checks within free/low-cost limits;
5. JSON/YAML/CSV manifests before a new database is justified;
6. open standards: OpenAPI, JSON Schema, AsyncAPI where applicable, OAuth/OIDC, webhooks and MCP;
7. serverless/scheduled jobs only for work that cannot be performed reliably in CI;
8. provider-neutral adapters and exports;
9. paid services only when they reduce total operating risk/cost or unlock revenue;
10. budget, rate-limit and token controls for every agent.

Scrappy means remove waste and manual duplication. It does not mean remove evidence, access control, rollback or review.

## Validation pipeline

Minimum CI checks:

- MDX/build validation;
- duplicate article ID and canonical-route detection;
- broken internal/external links and anchors;
- orphan and unlisted article detection;
- frontmatter/record-schema validation;
- prohibited public secrets/PII patterns;
- unresolved merge markers;
- historical/current state labeling;

- OpenAPI/schema/example validation;

## Publication workflow

```text
source change/event discovered
→ affected platform/article/API/policy map
→ risk/materiality classification
→ source/evidence retrieval
→ draft or generated update
→ self-check
→ independent/domain validation
→ approve / deny-with-changes / escalate
→ CI and preview
→ merge/publish
→ production smoke check
→ changelog + DAIL event
→ drift monitor
→ correction/rollback if needed
```

Publication never means the source event itself is automatically approved. Documentation automation follows approved state and may also expose that a release is pending, blocked, partially verified or corrected.

## Article completion definition

An article is complete for its current state only when:

- stable ID and canonical route exist;
- audience/exposure and owner are known;
- substantive source-grounded body or explicit unresolved-source body exists;
- current/historical/research status is clear;
- sources/evidence and last verification are recorded;
- legal/rights/privacy/security/economic dependencies are handled;
- related platforms/products/policies/API contracts are linked;
- version/effective date/correction path exist;
- search/navigation/redirects pass;
- release/changelog evidence exists;
- no known material contradiction is silently hidden.
