## Identity, role, and data boundary

1. Sites dispatch verifies the signed-in ChatGPT viewer.
2. The server normalizes the viewer email and converts it to a one-way SIWC identity fingerprint.
3. Only that fingerprint, a fixed action, and a strictly allowlisted payload cross the server-to-server gateway.
4. Supabase resolves the active role on every protected request and remains authoritative for wallet, balance, purchases, entitlements, releases, roles, and audit events.
5. A customer is implicit. Admin and superadmin require an active private principal record.
6. Superadmin can add, change, reactivate, or revoke operators. Self-revocation and removal of the final active superadmin are blocked transactionally.
7. Raw email, marketplace passwords, wallet fingerprints, provider object IDs, secrets, and storage paths must never appear in public markup or catalog feeds.

A redirect, checkout identifier, email field, browser state, or client-visible link is never accepted as payment, identity authorization, entitlement, license, or delivery evidence.

## Stripe and webhook topology

The runtime maintains separate default, test, and live signed-event receiver paths. All remain unarmed. The handlers reject Connect events, read provider objects back before settlement, lease idempotent receipts, and accept only the allowlisted checkout, asynchronous-payment, refund, and dispute event families.

Stripe funds Crown Credits only. A verified top-up appends credits to the CrownThrive ledger; a later, separate atomic redemption creates the product order, exact-version entitlement, and license grant. A redirect, Stripe object, or wallet balance never creates product access by itself.

No existing Stripe endpoint is safe to reuse. The connected tool cannot create a least-privilege account key and atomically transfer the one-time endpoint signing secret into private runtime custody. Endpoint registration therefore remains held and no secret was exposed.

## Funding activation runbook

Complete these steps in order:

1. Rotate any historically exposed Stripe secret.
2. In Stripe Dashboard, create a least-privilege **test** restricted key.
3. Transfer it directly into Supabase secret custody as the test restricted key; never expose it to chat, source, GitHub, Mintlify, Drive, or logged SQL arguments.
4. Create the dedicated test webhook endpoint with the seven allowlisted events, `connect=false`, and API version `2026-06-24.dahlia`.
5. Transfer its one-time signing secret directly into test webhook secret custody.
6. Complete taxability, active registration, customer-jurisdiction, rights, accessibility, operative-terms, exact-release, competitive-pricing, malware, protected-delivery, refund, dispute, reversal, and rollback evidence.
7. Approve an exact offer-release binding only after independently authenticated reviewer evidence passes.
8. Run test-mode duplicate, asynchronous, expiration, refund, dispute, reversal, and reconciliation canaries.
9. Create separate live credentials and endpoint only after test certification.
10. Run one bounded live canary, activate one exact offer, observe it, and expand in controlled tranches.

The existing Stripe payout record is outside this dashboard release. It is not treated as evidence that funding works and it is not used to bypass provider readiness.
