# MetaMask Embedded Wallets funding and dual-wallet execution

CrownThrive uses MetaMask Embedded Wallets as the user-facing embedded-wallet, funding, identity-verification, and WalletConnect corridor while retaining a separately governed Trust Wallet Agent Kit wallet path for bounded autonomous execution.

Provider configuration is never treated as economic authority. Wallet or funding success remains subject to CHLOM policy and ThriveEvergreen's exact `ECAC | HOLD | DENY` decision.

## Dual wallet execution model

CrownThrive has selected both wallet trust models rather than forcing one model onto every transaction.

### Mode A — user-approved WalletConnect

Stable ID:

```text
ct.wallet-mode.walletconnect.user-approved.v1
```

Rules:

- user self-custody;
- explicit modal confirmation required;
- no autonomous execution;
- unattended value ceiling = `0`;
- authority ceiling D2;
- appropriate for customer/founder transactions where wallet sovereignty must remain with the human signer.

The production control plane is active, but the actual request tool remains disabled until the MetaMask production origin is allowlisted and the VM frontend binding passes native Sites readback.

### Mode B — dedicated CHLOM Agent Wallet

Stable ID:

```text
ct.wallet-mode.agent-wallet.autonomous.v1
```

Rules:

- Trust Wallet Agent Kit CLI on a persistent trusted runner;
- dedicated encrypted institutional Agent Wallet;
- no key material in a transient Edge Function;
- exact CHLOM/ThriveEvergreen policy evaluation before execution;
- default unattended-value ceiling = `0` until a separately certified limit is established;
- D3 remains human-reserved;
- wallet creation and runner binding are not inferred from configuration.

Current state:

```text
runtime contract: PRODUCTION
activation: CONFIGURED_PENDING_RUNNER
wallet created: false
persistent runner bound: false
autonomous money movement: DENY until exact execution gate passes
```

### Mode C — MetaMask embedded user wallet

Stable ID:

```text
ct.wallet-mode.metamask.embedded.user-wallet.v1
```

This is the embedded MPC/user-wallet experience for authenticated site users. It is human-controlled and is not the autonomous CHLOM Agent Wallet.

## Server-side identity verification

CrownThrive's MetaMask control endpoint verifies wallet identity server-side using ES256 and provider JWKS.

The verifier checks:

1. token signature;
2. expected issuer;
3. JWT `aud` equals the ThriveBase MetaMask project Client ID;
4. wallet public-key/address ownership claim for the requested authentication mode.

Current provider JWKS canaries:

```text
social JWKS: PASS HTTP 200
external-wallet JWKS: PASS HTTP 200
invalid-token negative canary: PASS — HTTP 401
wrong-origin negative canary: PASS — HTTP 403
```

The endpoint exposes no raw secrets.

## Security invariants

- MetaMask Client Secret remains server-side only.
- Key export is disabled in the production Wallet Services contract.
- WalletConnect transactions require human confirmation.
- Agent Wallet autonomy is a separate policy lane and defaults to zero unattended value.
- No provider wallet event creates Crown Credits directly.
- No on-chain confirmation creates a license or entitlement directly.
- CHLOM Wallet preserves evidence and policy lineage; it does not silently become custodial.
- ThriveEvergreen remains the economic activation authority.
- Provider plan limits and provider eligibility always supersede CrownThrive-local request ceilings.

## Completion gates

### MetaMask user-wallet lane

1. Add `https://vm.crownthrive.com` to the MetaMask Mainnet project's allowlist.
2. Complete the provider Going Live Checklist.
3. Confirm the production Wallet Services plan entitlement required for funding.
4. Inject the frontend SDK into the Virality site through a certified Sites write/readback/rollback cycle.
5. Run a real authenticated wallet identity canary without moving value.
6. Run a funding-display canary without purchasing.
7. Promote the site-mesh binding only after readback.

### Agent Wallet lane

1. Bind a persistent trusted TWAK runner.
2. Create the dedicated Agent Wallet locally on that runner.
3. Register only public addresses/account IDs in CHLOM Wallet.
4. Run holdings and transaction-build canaries.
5. Prove unauthorized signing is denied.
6. Certify asset/address allowlists, value ceilings, compensation/rollback, and exact ECAC policy.
7. Promote signing/broadcast tools only after the full execution gate passes.
