# Governed release auto-publish

CrownThrive treats publication as the terminal effect of a governed release decision, not as a side effect of building a file, creating a price or registering a provider project.

The governed auto-publish policy is fail-closed.

## Core invariant

A digital release may publish automatically only when all applicable conditions are simultaneously true:

1. the subject and destination have stable registered identities;
2. the release is bound to an exact version and SHA-256 content digest;
3. every required certification dimension is `pass` or explicitly `not_applicable`;
4. four of the five currently accepted sovereign voters (A/B/C/D/S) have independently approved the exact release, including mandatory Agent D;
5. there are no disqualifying negative votes;
6. any D3 release has the required human approval;
7. the destination route is active;
8. the destination adapter is certified for its exact operation;
9. rollback and read-after-write requirements are satisfied; and
10. the destination surface has passed its own bootstrap/capability evidence.

If any applicable state is `HOLD`, `UNKNOWN`, pending, failed, stale, superseded or mismatched to the exact release snapshot, publication remains quarantined.

## Release and vote model

The machine record keeps release identity, specialist certifications, eligible votes, human approval, destination routing, provider-adapter certification and publication evidence as separate dimensions.

Synthetic, test-only and non-sovereign vote rows never count toward operative quorum. Test fixtures must use identities that cannot be confused with A/B/C/D/S, and every authoritative vote must prove its repository, agent and OIDC execution binding. Several rows created by one execution context are not independent votes.

The originating agent cannot vote on its own release. A rebuild, new asset hash, material catalog digest, changed license/economic snapshot or changed destination creates a different authorization snapshot. Prior votes are not silently inherited by a changed artifact.

## Product factory

Eligible product and asset records automatically project into governed release candidates. Public publication payloads contain public-safe catalog data only; credentials, storage paths, restricted evidence and protected economic calibration remain in private governed custody.

When all required certification dimensions become PASS, the release factory routes vote requests to eligible relay agents. The database does not impersonate independent voters or manufacture quorum.

## Publication modes

### Governed catalog projection

Routine digital products use a surface-scoped governed catalog projection. This lets a verified storefront consume accepted releases without requiring a new page-code mutation for every product.

Once a storefront has a verified consumer bootstrap, the logical path is:

`release PASS → governed publication → registered storefront`

### Provider mutation

Page, layout, code or one-time site-bootstrap changes use a separate provider-mutation adapter. Certification of the catalog projection does not certify a website provider's source-write capability.

Each provider-backed site is certified against its own project and rollback evidence before source mutation can become autonomous.

## Current production boundary

The Developer Marketplace, KJV Visualized / Sermon Toolkit and Virality Music have governed destination records and bootstrap plans. Their provider-source mutation paths remain unproven, so production auto-publication remains off until the one-time storefront consumer bootstrap is independently verified.

Virality continues to treat SoundCloud API use as `REMOVED_BY_FOUNDER_OVERRIDE`; the release system does not reintroduce that dependency.

## Adapter certification

The governed catalog adapter has passed a committed write/readback/rollback canary. An earlier invalid same-transaction proof was rejected rather than being promoted to PASS; provider-visible evidence must represent committed state.

Provider-source adapters remain separate certifications.

## Automatic rollback

Authorization is continuously re-evaluated. If a published release loses required certification or quorum, the system withdraws the current projection, preserves rollback evidence and quarantines the release. Restoring PASS does not erase prior publication or rollback history.

A newer accepted exact release supersedes the prior release instead of rewriting its evidence lineage.

## Scheduled operation

Publication dispatch, vote-request routing, adapter health proof and storefront-bootstrap verification run as persistent THIVEBASE automation. Public documentation intentionally omits private execution cadence, internal queue identifiers and endpoint topology.

## Provider loss and degraded mode

If a certified adapter loses certification, affected automatic-publication paths disable themselves and queued work returns to quarantine. If a previously verified storefront consumer can no longer be verified, the surface returns to a non-autonomous state.

No provider-health failure may silently convert into a PASS.

## Relationship to Store Credits

Publication and commerce activation remain separate certification dimensions. A storefront listing must not grant entitlement from payment-provider metadata. CHLOM/THIVEBASE remains the license and entitlement authority.

Store Credits remain separately gated until the applicable legal, tax and live-rail requirements pass. A technically deliverable package is not sufficient to publish a purchasable offer.

## Absolute no-go rules

- Never publish `HOLD`, `UNKNOWN`, pending or failed releases.
- Never count a non-voting specialist as an independent vote.
- Never let an originating agent self-approve its release.
- Never carry votes across a changed exact version/hash.
- Never equate catalog-projection certification with provider source-write certification.
- Never enable a production surface before its consumer bootstrap is verified.
- Never remove rollback or read-after-write evidence to increase automation throughput.
- Never grant a CrownThrive license from payment-provider metadata.
- Never reintroduce a retired provider/API dependency through publication automation.

The intended steady state is highly automated, but automation remains downstream of evidence and authority.
