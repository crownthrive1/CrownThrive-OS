# CrownThrive Services Stack

**Framework ID:** `ct.framework.crownthrive-services-stack`  
**Version:** `1.0.0`  
**State:** controlled test / governed HOLD  
**CHLOM decision contract:** `ALLOW | HOLD | DENY`

CrownThrive Services Stack, or **CSS**, is the shared-service connective tissue for the CrownThrive ecosystem. It prevents each platform from rebuilding identity, authentication, authorization, billing, licensing, analytics, notifications, CRM, ticketing, search, commerce, routing, rewards, and documentation independently.

CSS separates three things that must never be collapsed:

1. the stable CrownThrive service identity;
2. the versioned CrownThrive service contract;
3. the replaceable provider or internal execution system.

A provider capability does not prove a CrownThrive deployment. A successful API call does not automatically create billing truth, license rights, entitlement, settlement, professional compliance, or public certification.

## CHLOM CaaS enforcement

CHLOM evaluates a CSS request against:

- exact service and contract version;
- platform identity and service profile;
- authentication, authorization, tenant, and purpose context;
- requested data class and minimum-necessary fields;
- provider binding and evidence freshness;
- provider-exit and continuity evidence;
- observability and documentation state;
- reserved professional, payment, rights, or D3 authority.

The result is:

- `ALLOW` — a bounded operational request is inside current controlled authority;
- `HOLD` — the request may be valid, but required evidence, review, or service readiness is incomplete;
- `DENY` — the request crosses a prohibited authority, identity, tenant, data, provider, or lifecycle boundary.

An `ALLOW` result is not legal compliance, professional certification, a rights grant, payment movement, or sovereign approval.

## Provider replaceability

CSS providers are aliases and execution systems. CrownThrive retains the service identity, contract, evidence, continuity, and licensing layer.

Every provider binding requires an exit-plan candidate covering:

- export and data portability;
- fallback provider or manual continuity;
- migration and rollback;
- contract/version drift;
- retention, deletion, and evidence preservation;
- provider-specific billing, quotas, throttles, and terms.

## Reusable service profiles

CSS currently defines:

- Base Platform Profile;
- Commerce Platform Profile;
- Community Platform Profile;
- Media Platform Profile;
- CHLOM CaaS Managed Profile.

Platform/profile bindings are candidates until identity, contract, provider, tenant, security, accessibility, continuity, and independent verification evidence prove the exact deployment.
