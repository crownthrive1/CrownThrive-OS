# Incident Status Continuity Skill

**Skill ID:** `ct.skill.ops.incident-status-continuity.v1`<br />**Version:** `1.0.0`<br />**Runtime state:** `test`<br />**Commercial state:** `hold`

This skill standardizes how CrownThrive agents respond to outages, degradations, maintenance, recovery and capacity events without allowing narrative confidence to become operational truth.

## Purpose

The skill converts a material service event into a governed evidence chain:

```text
signal
→ incident
→ affected services
→ agent acknowledgements
→ impact / no-impact observations
→ diagnosis / action / escalation
→ recovery readback
→ documentation impact
→ lesson
→ factory candidate
```

## Required behavior

Every registered agent must be capable of receiving an institutional incident notice. The acknowledgement record proves the contract was applied; it does not claim that the agent independently diagnosed the event.

When relevant, agents must append one or more allowed observation types:

| Observation | Meaning |
| --- | --- |
| `ack` | institutional notice received |
| `impact` | the agent or its lane was affected |
| `no_impact` | verified no material impact |
| `diagnosis` | evidence-backed technical or operational diagnosis |
| `action` | bounded mitigation or corrective action |
| `recovery_readback` | independent or assigned recovery verification |
| `lesson` | reusable post-incident finding |
| `escalation` | authority, human, legal, security or provider escalation required |

## Fail-closed rules

The skill may **never**:

- expose or return raw secret values;
- treat an OAuth app ID, client ID, project ID or publishable key as secret API material;
- manufacture provider or human authority;
- mark a service healthy without fresh evidence;
- silently change billing, plan, spend-cap, security or provider settings;
- self-approve D3 actions;
- publish private provider/account evidence into public documentation;
- convert a postmortem lesson directly into a commercial product without certification.

## Credential continuity handoff

When an outage affects credential-dependent integrations, the incident skill hands off to the governed credential-continuity lane.

```text
service recovery evidence
→ secret classification
→ secure runtime entry
→ vault custody
→ version receipt
→ non-secret readback
```

If the required secret is not actually present, the correct state is **HOLD\_MISSING\_SECRET\_MATERIAL**, even if the service itself is operational.

## Documentation impact contract

Every material incident must produce one of the standard documentation outcomes:

- `docs_updated`;
- `docs_no_change`;
- `docs_delta_opened`.

Incident lessons that affect policies, runbooks, service descriptions, status vocabulary, capacity thresholds, recovery logic, credential custody or provider boundaries must update the institutional knowledge projection.

## Factory handoff

Validated lessons may be forwarded to the following reusable factory lanes:

- continuity;
- observability and drift;
- infrastructure capacity;
- support/runbook generation;
- skill compilation;
- productization;
- portfolio monetization.

The public body may expose only a sanitized pattern. Protected algorithms, private thresholds, account evidence, credentials, internal evidence and CrownThrive-specific operational intelligence remain vaulted.

## Commercialization gate

This skill is **not currently for sale**. Commercial activation requires:

1. independent validation;
2. IP/rights review;
3. security and privacy review;
4. sanitized public package generation;
5. documentation and version receipt;
6. approved pricing/SKU authority;
7. entitlement and checkout certification;
8. release receipt.

Until those gates pass, `commercial_state=hold`, `checkout_enabled=false`, and `entitlement_active=false` remain mandatory.
