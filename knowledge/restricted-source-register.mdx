# Restricted Source Register

Phase 2.7 distinguishes **knowledge that must be remembered** from **content that may be publicly exposed**.

## Restricted source families

Examples may include:

- confidential founder handbooks or activation packages
- private CHLOM technical compendia and implementation details
- contracts, assignments, licenses, NDAs, and signed agreements
- patent drafts and invention disclosures
- private investor, valuation, franchise, or prospectus materials
- customer and partner records
- unpublished media masters and source assets
- private product masters
- credentials, API keys, signing material, recovery codes, and secrets
- security architecture that would materially increase attack risk
- restricted MM Suites economics and partner material
- internal legal case records
- private analytics and financial records

## Public-safe index fields

The public knowledge base may preserve only safe metadata such as:

- stable source ID
- generic title or source family
- owner/control class
- confidentiality level
- authoritative storage class
- retention requirement
- access authority
- whether a public-safe summary exists
- whether it may be used by agents
- legal hold status where disclosure is appropriate

## Storage boundary

Mintlify is an institutional **projection**, not the vault. Restricted source bodies belong in approved private repositories, secure document storage, evidence stores, databases, or secret managers according to data class.

## Agent rule

An agent may know that a restricted source exists without receiving its body. Access should be scoped to the minimum material necessary for the task and recorded in the audit trail.

## Continuity rule

Every restricted source should have an authoritative location and backup/retention policy so institutional memory does not disappear when a vendor, employee, contractor, or account becomes unavailable.
