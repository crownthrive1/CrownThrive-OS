# Institutional Contradiction Ledger

Phase 2.8 does not erase conflicting records. It classifies them, determines whether the conflict is temporal, semantic, operational, legal, numerical, or architectural, and assigns a resolution path.

## Resolution classes

- **Temporal evolution** — both statements were valid in different periods.
- **Scope mismatch** — numbers or labels describe different populations or asset classes.
- **Successor / rename** — one record supersedes another but lineage must remain.
- **Target vs current** — one source describes intended architecture, another describes production reality.
- **Legal-status uncertainty** — language implies a legal structure not yet evidenced as implemented.
- **Public-claim conflict** — external pages make materially different claims that must be reconciled.
- **Owner decision required** — the available sources cannot safely resolve the conflict.

## Counting rule

The institution should never publish one undifferentiated number for "platforms" unless the underlying registry defines what is included. At minimum track:

- legal entities;
- operating brands;
- software platforms;
- frameworks;
- media properties;
- imprints;
- active domains;
- products/services;
- portfolio assets;
- archived/superseded assets.

A dated `ecosystem_total` may be computed only from a versioned inclusion rule.

## Conflict handling rule

A conflict is not resolved by deleting the older source. Resolution must create:

1. a canonical current value or explicit unresolved state;
2. effective date;
3. source authority;
4. prior value and lineage;
5. reason for change;
6. affected public pages, registries and agents;
7. validation owner;
8. evidence reference.

<Warning>
  Phase 3 must not ingest unresolved conflicts as if they were ordinary facts. Any conflict marked owner-decision, legal-status, or evidence-required must be machine-readable as unresolved and block autonomous consequential action where relevant.
</Warning>
