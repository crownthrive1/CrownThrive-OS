# Historical Context Boundary

CrownThrive preserves its history without allowing history to impersonate present authority.

<Warning>
  **Historical, latent, recovered, legacy, archived, superseded, retrospective, source-era, and research-only material is context-only. It has zero implementation authority.**
</Warning>

## The rule

A historical or latent source may be used to understand lineage, terminology, prior assumptions, abandoned designs, unresolved ideas, architectural intent, cultural context, or why a current system exists.

It may **not** by itself authorize, trigger, or justify:

- production implementation or deployment;
- provider writes or configuration changes;
- money movement, billing, settlement, or payouts;
- token minting, transfer, issuance, staking, bridging, or launch;
- governance votes, appointments, removals, or delegated authority;
- license or rights grants, revocations, assignments, or transfers;
- public claims that a capability is currently live;
- security-policy changes or credential handling;
- current legal conclusions; or
- promotion of an archived design into a current contract, registry, workflow, or runtime.

## Context can inform; context cannot command

Historical material can surface a **latent candidate**. A latent candidate is an idea worth preserving or reconsidering. It remains non-executable until a new current-state record is created and approved through the authority, evidence, legal, security, and production gates that apply to that subject.

```text
historical / latent source
        ↓
context extraction
        ↓
current-state comparison
        ↓
explicit new proposal or current record
        ↓
required evidence + owner + approval + tests
        ↓
only then: eligible for implementation
```

There is no automatic promotion path from archive to runtime.

## Required historical source state

Historical source records should resolve to the following institutional posture:

```yaml
context_mode: historical_only
latent_content: may_be_considered
implementation_authority: none
execution_authority: none
production_proof: false
current_state_proof: false
agent_auto_promotion: prohibited
restricted_body_publication: prohibited
```

## Confidentiality survives archival classification

Calling a document historical does not make a confidential document public. NDAs, agreements, investor materials, private founder packages, private financial models, personal records, restricted technical material, and other protected sources remain subject to their applicable access and retention controls.

Likewise, classifying a contract or legal instrument as a historical source record does **not** amend, terminate, waive, or reinterpret its legal effect. Contractual effect must be determined from the governing agreement, later amendments, authoritative company records, and legal review where required.

## Historical source classes

| Class | What it is | Public treatment | Runtime authority |
| --- | --- | --- | --- |
| `HISTORICAL_CONTEXT` | Prior doctrine, architecture, policy, roadmap, or documentation | Public-safe summary may be published | None |
| `LATENT_CONTEXT` | Unimplemented or dormant concept worth preserving | Describe concept and lineage only | None |
| `RESTRICTED_HISTORICAL` | Confidential legal, commercial, founder, financial, security, or partner material | Metadata/public-safe summary only | None |
| `SUPERSEDED` | Explicitly replaced current-era material | Preserve correction/successor links | None |
| `PRIVATE_CONTEXT` | Personal or non-institutional source retained for context | Do not publish body | None |
| `UNKNOWN_HOLD` | Source whose status cannot yet be resolved | Hold; do not promote | None |

## Historical-context agent boundary

The Historical Context Guardian may:

- inventory and fingerprint historical records;
- classify source family, confidentiality, lineage, and supersession;
- extract public-safe summaries;
- identify latent concepts for later human/current-state review;
- compare historical claims against current records;
- detect collisions, contradictions, and terminology drift;
- generate archive indexes and migration receipts; and
- verify that historical content is not being used as production authority.

It may never implement the historical source, deploy it, execute transactions, change governance, grant rights, perform provider writes, assert a live state from historical evidence, or promote itself into an implementation lane.

## Current-source requirement

Any future reuse of a historical idea requires a **new current source**. At minimum that record must identify:

1. the historical source being considered;
2. the specific idea being reused;
3. the current owner and accountable lane;
4. current legal/security/commercial implications;
5. current evidence and provider state where relevant;
6. implementation and rollback requirements;
7. required approval class; and
8. an explicit statement that the new record—not the historical source—is the authority for the proposed work.

## Why this exists

CrownThrive has a large historical corpus whose value is institutional memory. Preserving it prevents repeated mistakes, lost inventions, naming drift, undocumented assumptions, and false origin stories. The same corpus becomes dangerous if an old roadmap, token design, prospectus, founder handbook, launch guide, or architecture paper is treated as proof of what is live today.

PentaDocs therefore keeps the history visible while enforcing a one-way boundary between **remembering** and **implementing**.
