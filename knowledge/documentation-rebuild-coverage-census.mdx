# Documentation Rebuild Coverage Census

This census answers a question that raw page counts cannot: **what institutional knowledge is actually missing, what has already been reconstructed, and what must happen before the recovered Help Center estate can be considered rebuilt?**

It is governed by the [Documentation Reconciliation & Continuity Framework](/standards/documentation-reconciliation-continuity-framework), [Articleization Manifest and Autopublication Contract](/support/articleization-manifest-and-autopublication-contract), and [795-Article Disposition Seed](/support/help-center-795-article-disposition-seed).

## Two different universes

CrownThrive currently has two documentation count universes that must never be subtracted from one another as though they were one-to-one.

| Universe | Meaning | Current rule |
| --- | --- | --- |
| **795 recovered legacy Help Center titles** | forensic title/hierarchy estate recovered from source `S11` | every title requires a governed terminal disposition |
| **Current Mintlify MDX corpus** | live/current institutional pages, registries, standards, runbooks, changelogs and technical records | counted independently from repository/navigation validation |

Many current pages did not exist in the old Help Center. Conversely, many legacy titles should merge into stronger canonical pages, become redirects, move to restricted knowledge, remain historical, or stay unresolved until source recovery. Therefore:

```yaml
naive_missing_count: prohibited
formula_795_minus_current_pages: invalid
required_method: exact_title_to_current_disposition_crosswalk
```

## Terminal disposition model

Every recovered title ultimately resolves to one of six canonical outcomes:

1. `canonical_article`
2. `merged_successor`
3. `permanent_redirect`
4. `restricted_record`
5. `superseded_history`
6. `unresolved_source`

The detailed workflow state may remain more specific, but every title needs exactly one terminal class so machines and future operators can determine what happened to it.

## Rebuild sequence

Every legacy record follows the same lossless sequence:

```text
recover title / source body or fragment
→ verify source authority and completeness
→ resolve stable platform/framework/policy identity
→ classify current vs historical vs target state
→ map to current canonical page or create explicit new target
→ reconstruct substantive body from current approved evidence when original body is missing
→ add continuity links
→ classify audience / public-private boundary / D0-D3 risk
→ validate claims, rights, legal, API and security dependencies
→ publish / merge / redirect / restrict / preserve history / hold unresolved
→ emit changelog + machine-seed delta + DAIL evidence
```

A reconstructed current article must never be represented as the verbatim historical original when the original body was not recovered.

## Definition of rebuilt

The legacy estate is rebuilt only when every recovered title has a stable disposition, source/exposure/risk/owner classification, canonical route or explicit nonpublic state, continuity links, correction/version history, and a machine-readable relationship to the current institutional graph.

Candidate mapping satisfies the discovery/crosswalk layer of that standard. Substantive reconstruction, terminal review and governed publication still have to close.

That is the standard that turns recovery into institutional memory rather than a folder of old titles.
