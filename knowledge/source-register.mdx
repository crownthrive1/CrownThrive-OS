# Institutional Source Register

The knowledge base should distinguish source families rather than treating every document as equally authoritative.

## Current major source families

### CHLOM institutional recovery master

The current recovery corpus includes:

- **CHLOM Institutional Master Compendium v1.0** — consolidated institutional reconstruction.
- interim DOCX and Markdown masters preserved in Google Drive.
- recovery package and Mintlify rebuild materials.

Use: current Phase 2 reconstruction, terminology normalization, Help Center recovery, architecture reconciliation.

### Legacy Help Center structure

- **Help Center Structure**
- **Help Center Spine/Structure**

Use: recovered platform taxonomy, CHLOM module taxonomy, legacy knowledge corridors, article inventory and navigation reconstruction.

These sources establish that a topic or article existed. They do not automatically prove that the feature described remains active today.

### CHLOM architecture and protocol sources

Retained source families include:

- CHLOM Master materials
- White Paper
- BlackPaper
- Internal Gold Paper
- Genesis Volume
- Technical White Paper
- Extended Technical Appendices
- LEX concept materials
- token / launch / testbed materials
- formal-model and TLA\+ research artifacts

Use: historical architecture, target specifications, formal invariants, future decentralized modules.

These are generally subordinate to current Phase 2/2.5 registries for present-state claims.

### CrownThrive corporate and portfolio sources

Major source families include:

- CrownThrive Founders Handbook / Playbook / Activation Package
- CrownThrive Foundational Volume
- Holdings business-plan and portfolio working registries
- domain inventory
- engine/service inventory
- platform and brand inventories
- project prospectuses such as MM Suites

Use: portfolio lineage, operating corridors, asset registry, governance, HoldCo planning, strategic planning.

### Production and operating evidence

Examples include:

- live platform state
- release records
- Stripe/webhook evidence
- product registries
- production routes
- current GitHub main branches
- test and CI results
- current public policy pages

Use: strongest evidence for what is actually operational now.

## Source classification

Every source should eventually have:

- source ID
- title
- owner/custodian
- source family
- date
- classification
- authority tier
- claims supported
- conflicts
- superseded-by reference
- current review state

## Restricted material

The public knowledge base must not reproduce:

- credentials or secrets
- private contracts
- raw customer or licensee records
- protected personal data
- privileged communications
- unreleased confidential assets
- proprietary Fingerprint implementation
- confidential policy DSL
- private economic calibration
- confidential partner pricing

A public source register may record that restricted evidence exists without publishing the evidence itself.
