# Phase 2.0–2.9 Retroactive Reconciliation Program

## Purpose

The institutional build does not treat an earlier pass as permanently closed when stronger evidence later appears. Phase 2.0 through 2.9 remain historically accepted milestones, but their **effective conclusions are continuously reconcilable** until the Phase 2.99 hard exit gate is satisfied.

This is not phase-resetting. It is controlled correction.

## Governing rule

```yaml
historical_passes_preserved: true
new_evidence_may_supersede_effective_state: true
silent_rewrite: prohibited
phase_3_entry_until_reconciled: blocked
reconciliation_direction: macro_to_micro_and_micro_to_macro
```

## Why this lane exists

Newly recovered files, refreshed source indexes, revived domains, restored applications, current provider documentation, current account evidence and founder adjudications can reveal that an earlier conclusion was incomplete, too broad, stale or based on a weaker source.

Examples include:

- historical CHLOM materials describing a detailed Substrate/DAO/token/ZKP target architecture while current implementation evidence remains hybrid and cloud-first;
- old public or prospectus language that presents planned legal/economic structures more strongly than current evidence allows;
- revived websites that convert a prior `unreachable` or `unknown` state into a current reachable snapshot without proving the underlying repository/provider/API;
- multiple source variants containing different economic percentages;
- restored or newly discovered source masters that close a recovery gap without rewriting the original dated gap count.

## Reconciliation hierarchy

Every new source is evaluated in this order.

### Layer 1 — Institutional macro doctrine

Questions:

- Does this change CrownThrive's legal/operating identity?
- Does it alter the five-phase institutional program?
- Does it change CHLOM, CIE, Thrive Flywheel, MM Suites or Holdings relationship doctrine?
- Does it change public/private authority boundaries?
- Does it change current-vs-target architecture?

### Layer 2 — Portfolio and corridor architecture

Questions:

- Does a platform/brand/framework move between canonical, alias, predecessor, reserve, sunset or research states?
- Does its corridor or system-of-record role change?
- Does a source reveal a missing platform, engine, domain or dependency?

### Layer 3 — Platform and capability state

Questions:

- Is the platform reachable?
- Which capabilities are actually verified?
- What provider/account/API/repository/deployment state is known?
- What claims, products, roles, portals and legal surfaces changed?

### Layer 4 — Object and record detail

Questions:

- Which universe, room, work, product, SKU, price, policy, license, entitlement, API endpoint, event or role record changes?
- What effective date and source supports the change?

### Layer 5 — Documentation and automation projection

Questions:

- Which article, changelog, registry, policy page, API doc, SEO route or machine seed changes?
- Does the change require `docs_updated`, `docs_no_change` or `docs_delta_opened`?
- Which automated workflow or evaluation must be regenerated?

Duplicate files may corroborate a source family without creating false independent authority.

## Website and revived-source scan contract

A site scan records separate evidence for:

- DNS/host reachability;
- HTTP status and soft-404 behavior;
- page identity and canonical;
- robots and sitemap;
- visible product/feature/legal claims;
- authenticated account/admin evidence if authorized;
- provider/engine evidence;
- API/docs evidence;
- repository/source evidence;
- last verified timestamp.

`reachable` is not equivalent to `fully operational`, and `revived` is not equivalent to `recovered editable source`.

## Reconciliation action classes

- `confirm` — new evidence supports the current effective state.
- `refine` — state remains broadly correct but needs narrower scope or detail.
- `supersede` — a stronger current source changes effective state.
- `reopen` — a previously resolved question becomes uncertain.
- `close_gap` — authoritative evidence resolves a known missing record.
- `new_gap` — new evidence creates an unresolved dependency or contradiction.
- `historical_only` — source is preserved but does not alter current state.

## Macro-to-micro closure rule

A reconciliation pass is not complete merely because the source register is updated. The correction must propagate to all affected:

- doctrine/architecture pages;
- portfolio/platform registries;
- contradiction/adjudication queues;
- source authority records;
- legal/rights/economic schedules;
- developer/API/MCP manifests;
- articles and changelogs;
- machine seeds and tests.

## Phase 2.99 hard-exit relationship

Phase 2.99 cannot exit while a material newly recovered source has been ingested but its impacts remain unclassified.

Before Phase 3.0 entry:

1. all known newly recovered source families have source IDs or duplicate relationships;
2. material claims have been extracted and classified;
3. contradictions are resolved or explicitly blocking/allowed-unresolved;
4. macro architecture remains coherent;
5. platform/object-level corrections have propagated;
6. documentation and machine seeds reflect the same effective state;
7. validation proves no forbidden silent promotion occurred.
