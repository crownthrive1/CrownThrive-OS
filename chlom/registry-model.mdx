## CHLOM Registry Model

Phase 2.5 treats documentation as a projection of governed records rather than the only place institutional truth exists.

<Warning>
  **Conceptual registry model.** The families, YAML examples, and event names below establish modeling intent. They do not publish a current database schema, API endpoint, storage location, identifier allocator, authentication method, event-bus topic, production record, or authority to mutate institutional state.
</Warning>

## Model a governed record

<Steps>
  <Step title="Choose the stable institutional identity">
    Create or resolve the canonical record independently from public name, domain, vendor, implementation, corridor, or lifecycle state.
  </Step>
  <Step title="Attach aliases and source evidence">
    Preserve provider IDs, historical names, source claims, effective periods, and conflicts rather than overwriting lineage.
  </Step>
  <Step title="Separate state dimensions">
    Record lifecycle, implementation, deployment, evidence, rights, authority, economic, and documentation states independently where applicable.
  </Step>
  <Step title="Change state through a governed contract">
    Validate actor/service identity, authority, version precondition, evidence, side effects, and documentation impact before mutation.
  </Step>
  <Step title="Emit a normalized event and correction path">
    Record the state transition with correlation, version, authority, evidence, and remedy/supersession references; do not silently update dependent records.
  </Step>
</Steps>

<Tabs>
  <Tab title="Identity registries">
    Brands, platforms, assets, domains, services, agents, product families, and roadmap items need stable IDs and alias/lineage handling.
  </Tab>
  <Tab title="Authority registries">
    Rights, rules/policies, roles, permissions, licenses/DLAs, evidence, and remedies/cases control bounded meaning and action.
  </Tab>
  <Tab title="Execution registries">
    Workflows, events, metrics, revenue obligations, use cases, and integrations describe versioned behavior without replacing their governing authority records.
  </Tab>
</Tabs>

## Core registry families

The CHLOM operating model should be representable through machine-readable registries such as:

- brands
- platforms
- assets
- domains
- engines/services
- sources
- rights
- rules/policies
- roles
- revenue obligations
- evidence references
- licenses / DLAs
- remedies / cases
- agents
- permissions
- workflows
- events
- metrics
- use cases
- product families
- roadmap items

## Stable identifiers

A registry ID should not change merely because:

- the public name changes
- the domain changes
- the vendor changes
- the implementation is replaced
- the asset moves corridors
- the priority changes
- the product enters reserve or sunset

Stable IDs preserve institutional continuity.

## Example asset record

```yaml
id: CT-ASSET-024
name: Virality Music
owner: CrownThrive LLC
corridor: Media & Culture
status: active
priority: P0
rights_governance: chlom
public_route: https://vm.crownthrive.com
```

Illustrative only: current production registry controls actual values.

## Example license record

```yaml
id: DLA-...
asset_id: CT-ASSET-...
licensor: ...
licensee: ...
rights: [...]
rules: [...]
status: review
approvals: [...]
revenue_rules: [...]
evidence_refs: [...]
remedy_state: none
```

This license shape is also illustrative. Ellipses and empty arrays are unresolved placeholders, not values to send to a live service.

## Event model

State-changing systems should emit normalized events rather than silently modifying unrelated records.

Examples:

```text
asset.registered
asset.status_changed
rights.reviewed
license.proposed
license.approved
license.activated
payment.confirmed
entitlement.created
evidence.added
correction.issued
remedy.hold_created
license.suspended
license.revoked
appeal.filed
remedy.restored
```

Event names are normalized examples. Their payloads, versions, producer/consumer authority, transport, signing, retention, retry, replay, and production topics require an exact event contract.

## Documentation projection

PentaDocs should publish approved public-safe meaning from these records through its current Mintlify rendering provider. Internal dashboards may expose deeper state. Restricted evidence remains behind controlled access.

The long-term goal is that people, agents, Codex, APIs, websites, and support documentation all reference the same institutional IDs and governed state.

## API, errors, and support boundary

This page defines no base URL, authentication/authorization flow, request/response fields, error envelope, pagination, concurrency mechanism, or service-level behavior. Builders should use the [service contract](/chlom/phase-3-service-contract) for the required mutation/evidence envelope and the [API endpoint discovery workflow](/developers/api-endpoint-discovery-and-adapter-registry) to pin an executable interface.

When identity, alias, source authority, current value, owner, or correction lineage conflicts, preserve all claims and use the [support request workflow](/workflows/support-request). Do not choose a value by similarity or recency alone.
