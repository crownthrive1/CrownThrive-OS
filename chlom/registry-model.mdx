# CHLOM Registry Model

Phase 2.5 treats documentation as a projection of governed records rather than the only place institutional truth exists.

This page is the current public-safe registry successor for recovered CHLOM registry, identity, evidence, and machine-contract material. It defines stable object semantics and continuity boundaries; it does not claim that every registry family is production-complete or that the existence of a registry row independently grants execution authority.

## Core registry families

The CHLOM operating model should be representable through machine-readable registries such as:

- brands
- platforms
- assets
- domains
- engines/services
- sources
- rights
- rules/policies
- roles
- revenue obligations
- evidence references
- licenses / DLAs
- remedies / cases
- agents
- permissions
- workflows
- events
- metrics
- use cases
- product families
- roadmap items

The registry model works with [CrownThrive ID](/technology/crownthrive-id) for stable actor identity, [Source Reconciliation and Authority](/chlom/source-reconciliation) for contradiction resolution, and the [Rights Ledger and Evidence Model](/chlom/rights-ledger-and-evidence) for provenance and evidence references.

## Stable identifiers

A registry ID should not change merely because:

- the public name changes
- the domain changes
- the vendor changes
- the implementation is replaced
- the asset moves corridors
- the priority changes
- the product enters reserve or sunset

Stable IDs preserve institutional continuity. Provider IDs, repository slugs, URLs, usernames, payment IDs, CRM IDs, or other external identifiers should be treated as aliases or evidence references unless the governing registry explicitly defines otherwise.

## State and authority are separate axes

A registry may record that an object exists, is planned, is in controlled test, is active, or is retired. That lifecycle state is not the same as authority to execute a sensitive action.

For example:

```text
actor exists ≠ actor may approve
product exists ≠ product may be sold
license record exists ≠ license is active
provider account exists ≠ provider writes are authorized
payment object exists ≠ institutional settlement is final
agent exists ≠ agent has D3 authority
```

Consumers must resolve the applicable role, policy, evidence, approval, lifecycle, and phase controls before execution.

## Example asset record

```yaml
id: CT-ASSET-024
name: Virality Music
owner: CrownThrive LLC
corridor: Media & Culture
status: active
priority: P0
rights_governance: chlom
public_route: https://vm.crownthrive.com
```

Illustrative only: current production registry controls actual values.

## Example license record

```yaml
id: DLA-...
asset_id: CT-ASSET-...
licensor: ...
licensee: ...
rights: [...]
rules: [...]
status: review
approvals: [...]
revenue_rules: [...]
evidence_refs: [...]
remedy_state: none
```

The example intentionally uses `review` rather than implying activation. A machine consumer must not infer an effective license, entitlement, payout, or settlement from record shape alone.

## Evidence and source lineage

Every material registry claim should be traceable to an authority basis or evidence reference appropriate to that claim. Where the source is restricted, public-safe records can expose a stable reference and review state without exposing the underlying artifact.

Corrections should preserve lineage: old value, correction event, new value, reason/source, affected dependencies, and remediation status. This lets registries support historical audit as well as current state.

## Actor and role linkage

Registry objects that refer to people, organizations, service accounts, agents, or reviewers should use stable actor references rather than relying solely on mutable email addresses or provider-native usernames. The identity record and the authorization record remain separate so a merged account, renamed user, or provider migration does not rewrite historical authority.

## Event model

State-changing systems should emit normalized events rather than silently modifying unrelated records.

Examples:

```text
asset.registered
asset.status_changed
rights.reviewed
license.proposed
license.approved
license.activated
payment.confirmed
entitlement.created
evidence.added
correction.issued
remedy.hold_created
license.suspended
license.revoked
appeal.filed
remedy.restored
```

An event name describes an observed institutional transition; it does not authorize the transition. Authorization must be resolved before the event is accepted as a valid governed state change.

## Machine-contract boundary

Registries are the stable object substrate for APIs, agents, documentation, and future services. Machine contracts should reference stable IDs, explicit lifecycle states, versioned schemas, authority requirements, evidence references, and failure/hold semantics instead of scraping human-facing prose for implied permission.

The [Institutional Registry Architecture](/technology/institutional-registry-architecture) describes the broader cross-system implementation pattern, while [MCP Topology & Tool Boundaries](/technology/mcp-topology-and-tool-boundaries) defines how tool-facing execution must preserve scope and side-effect boundaries.

## Documentation projection

Mintlify should render approved public-safe meaning from these records. Internal dashboards may expose deeper state. Restricted evidence remains behind controlled access.

The documentation projection must not become a second competing registry. If documentation and runtime evidence conflict, open a reconciliation delta under the source-authority contract rather than silently changing one to imitate the other.

## Phase and activation boundary

The long-term goal is that people, agents, APIs, websites, and support documentation all reference the same institutional IDs and governed state. Reaching substantive documentation maturity does not itself activate production behavior.

The [Phase 3 Readiness Gate](/technology/phase-3-readiness-gate) independently governs broader machine execution. Until its hard exit passes, the registry model may support controlled-test qualification and reconstruction while provider writes, money movement, rights/license activation, high-risk authority, and terminal documentation disposition remain fail-closed.
