## Source boundary

The recovered CHLOM component atlas explicitly lists **LEX integration/deployment runbooks**. The exact historical runbook body has not been located. This article therefore institutionalizes the named IP asset and defines a conservative current runbook using already recovered LEX, DLA, API, provider-adapter, governance and release-certification requirements.

It must not be quoted as the original historical deployment procedure.

## Runbook objective

Integrate a CrownThrive or partner surface with LEX without creating direct provider dependencies, bypassing source-right/DLA truth, exposing protected assets or enabling payment/storefront state to manufacture licensing authority.

## Deployment stages

```text
0. SOURCE / CONTRACT READINESS
1. TENANT / CLIENT REGISTRATION
2. READ-ONLY DISCOVERY
3. LISTING CANDIDATE CANARY
4. TRANSACTION CANDIDATE CANARY
5. AGREEMENT / ENTITLEMENT CANARY
6. PAYMENT / SETTLEMENT CANARY
7. REMEDY / REVERSAL TEST
8. CERTIFICATION PACKET
9. STAGED ACTIVATION
10. POST-ACTIVATION RECONCILIATION
```

No stage automatically authorizes the next one; required evidence/gates must pass.

## Stage 0 — Contract readiness

Confirm stable IDs and supported versions for:

- tenant/platform;
- asset/rights registry;
- DLA schema/lifecycle;
- LEX API/interface contract;
- Compliance Packs;
- agreement/entitlement layer;
- economic schedule;
- DAIL/evidence;
- provider adapters;
- rollback/compensation path.

Unresolved canonical terms or missing source-right mapping = HOLD.

## Stage 1 — Client and scope registration

Register the integration client/application, environment, authentication method, exact scopes, owner, rate/usage budget, callback/webhook endpoints and secret references. Never place credentials in the documentation repo.

## Stage 2 — Read-only discovery

Enable safe listing/search reads first. Validate tenant isolation, public/private projections, stale-index behavior, rate limits, schema compatibility and provider-neutral IDs.

No write scopes are required for this stage.

## Stage 3 — Listing candidate canary

Use synthetic or controlled-test rights-bearing assets. Submit a listing candidate; verify:

```text
asset resolves
source rights resolve
DLA version resolves
licensor authority resolves
scope <= DLA rights
policy checks run
listing remains candidate until gate passes
DAIL receipt exists
```

Reject a deliberately invalid rights case as a negative control.

## Stage 4 — Transaction candidate canary

Exercise an eligible and ineligible buyer/licensee scenario. Verify the transaction cannot jump from candidate to fulfilled because a provider/UI action succeeded.

## Stage 5 — Agreement and entitlement canary

Record acceptance of an exact terms version. Verify an entitlement is created only when agreement, DLA, eligibility, policy and required economic conditions permit it. Verify revocation propagates to current entitlement usability.

## Stage 6 — Payment / settlement canary

With a controlled provider/test event:

- authenticate/normalize provider event;
- apply semantic idempotency;
- compare expected obligation to provider evidence;
- verify duplicate delivery does not duplicate entitlement/allocation;
- verify mismatch creates HOLD rather than rewriting expected values;
- verify refund/reversal path.

## Stage 7 — Remedy / rollback exercise

Before broad activation, test:

- listing hold/takedown;
- transaction cancellation where allowed;
- DLA suspension/revocation effect;
- provider refund/reversal;
- entitlement suspension;
- adapter rollback/provider disable;
- correction and DAIL lineage.

Rollback must restore a safe institutional state, not merely turn off the UI.

## Stage 8 — Certification packet

Bind exact integration release/client version and head SHA to:

```yaml
schema_conformance:
rights_negative_tests:
tenant_isolation:
security_review:
secret_scan:
idempotency_tests:
provider_adapter_tests:
rollback_test:
body/documentation_integrity:
required_approvals:
```

`CERTIFIABLE_PACKET` is not deployment authority.

## Stage 9 — Staged activation

Activate the smallest approved population first: exact tenant, offer/listing cohort, geography/channel or controlled test set. Monitor holds, provider errors, rights conflicts, settlement mismatches and support cases before expansion.

## Stage 10 — Reconciliation and observation

Post-activation checks:

- canonical listing/DLA readback;
- entitlement/provider access readback;
- payment/settlement reconciliation;
- webhook/event health;
- audit/DAIL evidence;
- rate/usage state;
- customer/operator support path;
- provider replacement/exit readiness.

## Provider replacement rule

A provider migration should not change stable asset, DLA, listing, transaction, agreement or entitlement IDs. Export/readback old provider state, bind aliases, test the replacement adapter, reconcile outstanding events, then retire the old adapter with continuity evidence.

## Failure / stop conditions

Stop/HOLD deployment for:

- rights or authority mismatch;
- secret exposure;
- cross-tenant data access;
- inability to reverse/compensate a canary;
- duplicate economic/entitlement effect;
- stale/incorrect current state;
- missing required evidence/approvals;
- unresolved provider/schema mismatch;
- inability to reproduce DAIL/canonical readback.

## Tests

Test the entire runbook with a deliberately revoked DLA, duplicate payment event, provider outage, schema downgrade, invalid buyer, cross-tenant request, rollback and provider replacement.

## Versioning

The runbook evolves separately from the LEX API and provider adapters. Each deployment packet records the exact runbook/version it followed.
