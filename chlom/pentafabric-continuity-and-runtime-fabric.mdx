# Pentafabric Continuity & Runtime Fabric

CrownThrive Pentafabric™ is operated as a governed program rather than a static architecture diagram. Its continuity/runtime model combines three institutional commitments:

1. a **seven-generation continuity charter** preserving mission, provenance, rights, stewardship and recoverability across succession;
2. a **governed lifecycle and maintenance model** that permits bounded automation without manufacturing authority; and
3. a **continuous CHLOM runtime fabric** that executes bounded agent lanes and emits DAIL evidence for each cycle.

PentaGeneration is the named CrownThrive continuity subsystem responsible for seven-generation stewardship, institutional memory, succession and handoff logic, archive/version inheritance and long-horizon preservation. It operates within the same evidence and authority boundaries described here; its existence does not autonomously transfer ownership or reserved authority.

See [CrownThrive Pentafabric](/chlom/pentafabric) for the layer model and [Continuous Build & Commercialization](/chlom/continuous-build-commercialization) for the build-to-commercialization loop.

## Seven-generation continuity charter

The seven-generation horizon is a planning and stewardship commitment, not an irrevocable transfer of legal ownership. Each generation inherits an evidence-backed institutional state, operating constraints, rights records, maintenance obligations and only the authority actually granted at that time.

The planning model is:

1. Generation 1 — Founder and originating architecture.
2. Generation 2 — Continuity and institutionalization.
3. Generation 3 — Expansion and professional stewardship.
4. Generation 4 — Distributed leadership and ecosystem maturity.
5. Generation 5 — Long-horizon resilience and succession.
6. Generation 6 — Intergenerational modernization and preservation.
7. Generation 7 — Re-adjudication of mission, rights and stewardship under then-current law and evidence.

### Generational rules

- **Founder intent is evidence, not automatic authority.** It remains preserved as institutional/governance evidence and cannot be used by automation to bypass applicable law or current authority.
- **Generational lock.** Consequential changes must preserve or explicitly adjudicate canonical lineage, IP provenance, rights/licensing state, DAIL evidence lineage, CHLOM contracts, Pentafabric ownership boundaries, recovery capability, security boundaries, economic authority, human succession evidence and public/private classification.
- **No autonomous succession.** Agents may maintain records, detect gaps, prepare candidate handoff packets and request review. They may not appoint themselves, transfer ownership, rewrite founder lineage, appoint a legal successor, dissolve CrownThrive or create a new legal entity without separately authorized human/legal process.
- **Continuity tests.** Release and handoff gates should determine whether an authorized successor can reconstruct the architecture, understand rights state, locate protected evidence through authorized paths, restore required services, operate public-safe documentation and identify unresolved obligations.

The canonical charter is `standards/crownthrive-generational-continuity-charter.v1.md`. PentaGeneration operating material is maintained separately so the charter can remain stable while implementation evolves.

## Autonomous lifecycle and maintenance model

The Pentafabric lifecycle governs how material artifacts move through build, verification, authorization, release, observation, maintenance and retirement without collapsing state dimensions.

### Hybrid autonomy, fail closed

The operating model is hybrid:

- **Autonomous/bounded:** observation, reconciliation, documentation preparation, research, testing, candidate generation, non-consequential maintenance and bounded recovery.
- **Separately authorized/human-gated where required:** legal authority, ownership transfers, founder-reserved decisions, production economic activation, destructive operations, privileged credentials and other reserved consequential actions.

Agents must fail closed when required evidence is absent. No lifecycle stage may manufacture the authority required by a later stage.

### Lifecycle states

```text
PROPOSED → CANDIDATE → VERIFIED → AUTHORIZED → RELEASED → OBSERVED → MAINTENANCE → DEPRECATED → RETIRED
```

Failure/recovery path:

```text
HOLD → QUARANTINE → REPAIR → VERIFY → RELEASE
```

Retirement preserves historical evidence and replacement lineage. Silent deletion is not the default continuity action.

### Maintenance-controller boundary

The maintenance controller may observe dependency drift, documentation drift, schema drift, API/MCP contract drift, security findings, stale providers, failing checks, unreachable projections, vault-binding gaps, economic-state divergence and broken recovery routes.

| It may | It may not |
| --- | --- |
| Open repair candidates | Create legal authority |
| Regenerate derived documentation | Change ownership |
| Run tests and rebuild projections | Disclose secrets |
| Quarantine broken candidates | Activate unapproved commerce |
| Request verification | Bypass verification or self-certify |
| Prepare rollback packets | Self-merge protected changes |
| Mark stale artifacts for review | Destroy canonical evidence |

### Runtime truth rule

A repository file, workflow definition, API specification, MCP manifest, agent manifest, generated document, provider response or successful build is not by itself proof of live production. Runtime promotion requires applicable current readback and verification evidence.

The machine architecture is maintained in `chlom/architecture/pentafabric-autonomous-lifecycle.v1.md`.

## Continuous CHLOM runtime fabric

The CHLOM runtime fabric executes the governed portion of the lifecycle on repository-native recurrence and relevant source changes. The current runtime model uses three stages:

1. **Contract discovery.** Registered contracts/candidates are collected and validated. Invalid or unparseable contracts cause the cycle to fail closed to `HOLD`.
2. **Bounded agent lanes.** When discovery is `READY`, the runtime can fan out the contracted lanes: `rnd`, `documentation`, `rights_identity`, `compliance_oracle`, `commercial`, `mesh_reliability`, `continuity`, and `maintenance`.
3. **Assurance.** Reconciliation assembles a DAIL evidence packet and run summary with a longer-lived assurance record.

The runtime executes only the authority actually granted to each lane. It does not manufacture legal/economic authority, transfer ownership, disclose secrets or self-certify production state.

### Repository-native cron controllers

Two GitHub Actions controllers are part of the internal CHLOM recurrence fabric:

- **CHLOM Pentafabric Continuity** — hourly at `17 * * * *`. It validates Pentafabric manifests/contracts and the maintenance projection gate. Scheduled runs are validation/observation only; they do not release maintenance or activate external commerce.
- **CHLOM Runtime Fabric** — twice hourly at `7,37 * * * *`. It runs the governed runtime controller, fans out bounded agent lanes only when discovery reports `READY`, otherwise fail-closes to `HOLD`, and emits/uploads DAIL evidence for the cycle.

These are repository-native recurrence lanes, not additional external failure-domain clocks. They remain bounded by the same authority limits as the rest of CHLOM: no ownership transfer, no legal-authority manufacture, no unapproved economic activation, no secret export, and no self-certification.

The canonical scheduler topology continues to treat repository-native GitHub Actions, database-native recurrence, and PentaDocs recurrence as internal execution mechanisms rather than external failure-domain clocks.

## DAIL runtime evidence contract

Runtime cycles use the `dail.chlom.runtime-event.v1` evidence schema. The event binds cycle identity/state to an integrity hash and records the authority envelope. An illustrative shape is:

```json
{
  "schema": "dail.chlom.runtime-event.v1",
  "event_type": "RUNTIME_FABRIC_CYCLE",
  "run_id": "example-run-id",
  "timestamp_utc": "2026-08-26T00:00:00Z",
  "state": "READY",
  "agents": ["rnd", "documentation", "rights_identity", "compliance_oracle", "commercial", "mesh_reliability", "continuity", "maintenance"],
  "authority": {
    "mode": "hybrid_bounded",
    "economic_activation": "THRIVEEVERGREEN_ECAC_ONLY",
    "legal_ownership": "HUMAN_GATED",
    "destructive_operations": "HUMAN_GATED",
    "secrets": "VAULT_ONLY",
    "self_certification": "PROHIBITED"
  },
  "event_hash": "sha256-canonical-event"
}
```

The canonical schema is `schemas/dail/chlom-runtime-event.v1.json`; the orchestration definition is `.github/workflows/chlom-runtime-fabric.yml`. These machine contracts remain narrower and more authoritative for runtime validation than this public-safe narrative summary.

## Phase 3 interpretation

Phase 3 changes the institution-wide operating generation, not the truth requirements of this fabric. In Phase 3:

- continuity evidence is inherited, not reset;
- component semantic versions remain independent;
- runtime and provider certification remain subsystem-by-subsystem;
- a `HOLD` remains a `HOLD` until its specific evidence gate is satisfied;
- PentaDocs may project this state, but PentaDocs or its underlying provider cannot create CHLOM authority;
- PentaGeneration strengthens continuity/handoff coverage without becoming an ownership-transfer mechanism.
