## Purpose

A Dynamic Licensing Asset is CHLOM's canonical **machine-readable permission package**. It answers:

```text
WHO may do WHAT
with WHICH asset/right
WHERE
WHEN
through WHICH channels/uses
under WHICH conditions
with WHICH transfer/sublicense/renewal/remedy rules
under WHICH source authority
```

It is the operational bridge between source rights and downstream entitlement/commerce.

```text
SOURCE RIGHTS / AGREEMENT / AUTHORITY
                 |
                 v
           RIGHTS CLOSURE
                 |
        ISSUER STEWARDSHIP
                 |
                 v
         DLA CANDIDATE OBJECT
                 |
      POLICY / EVIDENCE / REVIEW
                 |
                 v
             ACTIVE DLA
        /         |          \
 entitlement    LEX       monitoring
        |         |          |
        +---------+----------+
                  |
        renew / transfer / hold /
        revoke / expire / correct
                  |
                 DAIL
```

## What a DLA is not

A DLA is not:

- source ownership itself;
- the historical Decentralized Licensing Authority;
- proof that an issuer owns more rights than its evidence supports;
- a marketplace listing;
- a payment;
- an entitlement automatically;
- a provider SKU/product ID;
- an NFT/token requirement;
- an irreversible license if source authority permits suspension/revocation;
- a legal conclusion beyond the source agreement/rights evidence.

## Rights-before-license invariant

The core constraint is:

```text
DLA_RIGHTS <= LICENSABLE_SOURCE_RIGHTS <= SOURCE_RIGHTS
```

No DLA can manufacture a right merely because a field is set to `true`.

## Stable identity and versions

The logical DLA can maintain a stable identity while terms evolve through explicit versions where permitted.

```text
DLA-123 v1
   -> renewal/amendment
DLA-123 v2
```

If a material change creates a legally/semantically distinct license rather than an amendment, a new DLA ID may be appropriate. That distinction belongs to the governing rights/agreement profile, not an arbitrary implementation rule.

## Source-rights linkage

Every DLA should resolve to source-rights evidence such as:

- ownership record;
- master rights agreement;
- assignment;
- licensor agreement;
- employment/work-for-hire evidence where relevant;
- copyright/trademark/license record;
- platform/provider terms where they actually govern use;
- founder/institutional rights registry where supported by source evidence.

The public article does not expose confidential agreements; it records safe references/status.

## Issuer stewardship

Current CHLOM separates the license object from the authority that can issue/manage it.

```text
DLA = Dynamic Licensing Asset
Licensing Stewardship / Issuer Authority = who may create/change/revoke within scope
```

Historical Decentralized Licensing Authority remains preserved separately.

## Issuer authority object

```yaml
issuer_authority_ref:
  issuer_ref: institutional identity
  source_authority_refs: []
  asset_or_catalog_scope: explicit
  permission_ceiling: explicit
  territory_scope: optional
  term: explicit
  allowed_actions: issue|renew|amend|suspend|revoke|transfer_approve|other
  status: active|held|expired|revoked
```

Issuer authority can never exceed source rights.

## Permission dimensions

A DLA can model permissions such as:

- reproduce;
- distribute;
- display;
- perform;
- stream/broadcast;
- adapt/derive;
- sublicense;
- manufacture;
- market/advertise;
- use name/mark/likeness;
- institutional/educational/commercial use;
- AI training/use where source rights support it;
- other domain-specific rights.

No list is universal. Rights must be explicit and source-backed.

## Restrictions

Examples:

- non-transferable;
- no sublicensing;
- territory limits;
- term limits;
- platform/channel limits;
- audience/use restrictions;
- attribution requirements;
- quality/brand controls;
- exclusivity;
- quantity/capacity limits;
- reporting/audit requirements;
- compliance/credential predicates.

## Territory

Territory should be machine-readable enough to evaluate intersections, but legal meanings can differ by agreement. The DLA references the adopted territory profile/source rather than guessing.

```text
requested territory ⊆ licensable territory
```

## Term

```text
current if starts_at <= now < ends_at
```

when an `ends_at` exists, subject to suspension/termination and agreement-specific rules.

A term calculation does not by itself decide grace periods, renewal rights or survival clauses.

## Exclusivity

Exclusive licenses require collision/capacity checks against overlapping rights.

```text
same asset
+ same permission scope
+ overlapping territory
+ overlapping term
+ incompatible exclusivity
= HOLD / conflict
```

## Transferability

Transfer is allowed only if:

- DLA/source rights allow it;
- transfer conditions are satisfied;
- new holder eligibility passes;
- required consent/issuer approval exists;
- economic/remedy conditions are handled;
- current policy/evidence is valid.

```text
payment for transfer != valid transfer automatically
```

## Sublicensing

A child DLA/sublicense must satisfy:

```text
child permissions ⊆ parent permissions
child territory ⊆ parent territory
child term ⊆ parent remaining term
child transferability <= parent transferability
child sublicense rights <= parent sublicense rights
```

The Rights Graph/ALG-004 performs closure/checking.

## Derivative rights

A DLA may authorize creation/use of derivative works while preserving source restrictions.

```text
source DLA permits derivative creation
     -> derivative object created
     -> derivative-rights record
     -> continuing source attribution/restrictions
```

Derivative ownership/rights cannot be inferred generically; the source terms control.

## Compliance predicates

A DLA can require current conditions before use/transfer:

- credential currentness;
- age/territory eligibility;
- sanctions/risk check;
- training/certification;
- rights evidence;
- usage/reporting obligations;
- ZK proof profile;
- human/professional approval.

The DLA references policy/proof profiles rather than embedding opaque private logic.

## Economic schedule

A DLA can reference pricing/royalty/fee schedules, but those schedules are separate objects.

```text
DLA grants permission
Economic Schedule defines money obligations
```

Changing payment provider or pricing alias does not change the DLA rights semantics unless the governing agreement says the economic term is constitutive.

## Agreement relationship

The signed/accepted agreement is an evidence/authority object tied to the DLA.

```text
agreement accepted
  + rights authority
  + DLA terms
  + policy currentness
  -> permission may become active
```

No click/payment event alone should generate a DLA if agreement/rights requirements remain unresolved.

## Entitlement relationship

```text
DLA active
  + holder/subject bound
  + required payment/conditions satisfied
  -> entitlement candidate
```

The entitlement is a downstream access/benefit state. It remains separately traceable.

## LEX relationship

LEX exposes/discovers/transacts eligible DLA-based offers.

```text
DLA != LEX listing
```

A DLA can exist privately without a marketplace listing, and a listing cannot create DLA authority.

## Lifecycle

```text
CANDIDATE
   |
RIGHTS / ISSUER / POLICY REVIEW
   |
   +--> HOLD / REJECT
   |
APPROVED / ISSUED
   |
ACTIVE
   |\
   | \ expiry -> EXPIRED
   | suspension -> HELD/SUSPENDED -> ACTIVE or REVOKED
   | renewal/amendment -> NEW VERSION
   | transfer -> new holder / transfer record
   | termination/revocation -> TERMINATED/REVOKED
```

## Activation predicate

A current-safe conceptual predicate:

```text
DLA_activatable =
  source_rights_valid
  AND issuer_authority_valid
  AND DLA_scope_within_rights
  AND mandatory_policy_passes
  AND mandatory_evidence_current
  AND agreement/assent_satisfied_if_required
  AND required_approvals_complete
```

A false prohibition can yield DENY; unresolved critical inputs yield HOLD.

## Suspension/HOLD

A DLA can be held/suspended because of:

- rights dispute;
- stale credential/compliance condition;
- provider mismatch;
- source agreement uncertainty;
- case/dispute;
- security incident;
- pending renewal/review;
- payment/economic dispute where terms authorize it.

HOLD is not the same as permanent revocation.

## Revocation/termination

Revocation requires valid source/remedy authority. The DLA record should preserve:

- reason class;
- authority;
- evidence;
- effective time;
- dependent entitlements/listings/children;
- appeal/remedy options;
- DAIL event.

## Descendant impact

Revoking/suspending a parent DLA can require reevaluation of child sublicenses/entitlements. The exact remedy depends on the source terms and policy.

## Renewal

Renewal must revalidate conditions that may have changed:

- source rights;
- issuer authority;
- holder eligibility;
- policy;
- economic terms;
- credentials;
- territory/term;
- outstanding disputes.

Renewal is not automatic merely because a provider subscription renews.

## Provider/token representation

Historical CHLOM often represents licenses as NFTs/SBTs/tokens. Current rule:

```text
DLA semantic object
   -> optional token/provider representation
```

The representation is an alias/adapter. The canonical CHLOM DLA meaning survives migration away from it.

## Failure modes

- source rights unresolved -> HOLD;
- issuer outside scope -> DENY/HOLD;
- DLA exceeds rights -> invalid/deny;
- exclusivity collision -> HOLD;
- holder eligibility stale -> HOLD;
- agreement missing -> HOLD;
- provider payment succeeded but DLA not activated -> no entitlement;
- provider token exists without canonical DLA evidence -> treat as provider evidence only;
- parent revoked -> descendant reevaluation;
- index says active but canonical state changed -> canonical state wins.

## Threat model

- fabricated ownership;
- unauthorized issuer;
- rights inflation;
- hidden sublicense;
- exclusive double grant;
- stale eligibility;
- provider/token alias takeover;
- payment treated as license authority;
- silent term/territory expansion;
- revoked parent with active child;
- public leakage of confidential terms.

## Test vectors

1. rights valid + issuer valid + terms subset -> candidate can proceed;
2. requested right absent upstream -> deny;
3. issuer authority expired -> no issuance;
4. exclusive overlap -> HOLD;
5. child sublicense exceeds parent term -> reject/trim not silently;
6. provider payment success before DLA activation -> no entitlement;
7. token/NFT representation removed -> canonical DLA remains;
8. renewal with expired holder credential -> HOLD;
9. parent revocation -> child reevaluation triggered;
10. correction -> version/DAIL lineage, no erasure.

## Restricted companion

Private custody includes full contracts/rights evidence, licensor/licensee identities where confidential, royalty/pricing terms, source chain-of-title, private disputes, provider aliases, security controls and unpublished asset details.
