## Source basis

Later CHLOM module/Help Center lineage uses **DAL** in distribution-related language described as **Distributions Authority / Layer**. This meaning is distinct from Genesis-era **Decentralized Attestation Ledger** and Grand Prospectus-era **Decentralized Adjudication Layer**.

The recovered source set does not justify forcing all distribution-era DAL references into one exact globally canonical long-form expansion. This record therefore preserves the source-supported **Distributions Authority / Layer family** and keeps exact wording source-scoped.

## Purpose

The distribution-related DAL concept belongs to CHLOM's historical architecture for connecting attribution, revenue/royalty obligations and downstream distribution.

```text
ATTRIBUTED USE / REVENUE EVENT
             |
             v
   DISTRIBUTION AUTHORITY / LAYER
      +------+-------+---------+
      |              |         |
  attribution      splits    eligibility
      |              |         |
      +------+-------+---------+
             |
       obligation routing
             |
             v
     payout / settlement rail
             |
        evidence / audit
```

## What this record does not claim

It does not establish that:

- DAL currently means distribution in modern CHLOM;
- a live autonomous distribution authority exists;
- historical payout/token rails are deployed;
- the layer can create royalty rights without source agreements;
- a provider payout proves institutional settlement;
- historical percentages/splits are current;
- ADE and DAL are the same object.

## Historical function family

Distribution-related source lineage can reasonably include:

- identifying attributable revenue/use events;
- resolving eligible beneficiaries;
- applying split/royalty schedules;
- routing obligations;
- interacting with treasury/payment rails;
- recording distribution status;
- corrections/reversals;
- audit/provenance.

The exact implementation remains source/version specific.

## Attribution boundary

A distribution engine requires evidence that revenue/use belongs to a particular asset/right/participant.

```text
provider metric / event
   -> attribution evidence
   -> governed attribution result
```

A provider's attribution claim is evidence, not automatically institutional truth.

## Rights-before-distribution

```text
source rights / agreement
   -> economic entitlement/schedule
   -> attribution event
   -> obligation
```

The distribution layer cannot manufacture royalty entitlement from traffic, plays, sales or other metrics alone.

## Relationship to ADE

Later CHLOM uses **ADE = Attribution & Distribution Engine**. That engine is the stronger current conceptual successor for automated attribution/distribution orchestration.

```text
historical DAL distribution lineage
          |
          v
ADE / Attribution & Distribution Engine
          |
   economic schedule / obligations
          |
   provider execution / reconciliation
```

DAL and ADE remain separate source identities.

## Relationship to Royalty & Splits Pallet

RSP-X defines versioned allocation/split rules. The distribution layer/orchestrator applies those schedules to eligible revenue/use events.

```text
schedule definition
  != attribution
  != obligation
  != distribution execution
```

## Relationship to Royalty Streaming

Historical Royalty Streaming can make obligations accrue/release over time or event cadence. Distribution DAL lineage can route/coordinate those obligations, but the streaming component remains separately documented.

## Treasury relationship

Treasury/fee routing may receive authorized portions of an economic schedule. Treasury state is not a fallback destination for unexplained remainders unless the adopted schedule says so.

## Payment/provider relationship

```text
distribution obligation
   -> provider payout instruction
   -> provider evidence
   -> institutional reconciliation
```

Provider `paid` does not equal settlement until the institutional records reconcile.

## Historical token relationship

Historical CHLOM tokenomics may use CHLOM Coin/crypto rails for distribution. Modern CHLOM is provider/currency neutral.

```text
historical token rail != current economic requirement
```

## Identity/Fingerprint relationship

Historical distribution concepts use Fingerprint IDs/DIDs to route economic benefits to stable participants.

Current-safe mapping:

```text
canonical economic party
   -> obligation
   -> replaceable payment destination alias
```

## Corrections and reversals

If attribution or a schedule is corrected after distribution:

```text
original obligation/distribution
   -> correction/reversal record
   -> compensating obligation
   -> reconciliation
```

Do not delete the original event.

## Modern mapping

```text
source event / revenue
 -> CrownLytics/provider evidence
 -> governed attribution
 -> ADE
 -> economic schedule
 -> obligation ledger
 -> execution adapter
 -> reconciliation

```

This preserves the useful architecture while eliminating the historical DAL acronym collision.

## Failure modes

- attribution unsupported -\> HOLD;
- rights/economic entitlement missing -\> no distribution obligation;
- schedule version unresolved -\> HOLD;
- beneficiary identity unresolved -\> HOLD;
- duplicate source event -\> idempotency prevents duplicate obligation;
- provider payout fails -\> obligation remains unsettled;
- provider reports paid but amount/currency differs -\> reconciliation case;
- historical token rate/split copied into current system -\> governance failure;
- DAL distribution wording mistaken for current DAIL.

## Threat model

- attribution fraud;
- duplicate payouts;
- beneficiary substitution;
- hidden split changes;
- provider payment destination compromise;
- manipulated revenue events;
- rounding/value leakage;
- stale schedule;
- source-rights dispute;
- token/provider data promoted as institutional truth.

## Test vectors for modernization

1. reconciled revenue \+ valid entitlement \+ current schedule -\> obligation candidate;
2. provider sale with no rights entitlement -\> no royalty obligation by inference;
3. same source event repeated -\> one obligation;
4. beneficiary provider account changes -\> canonical beneficiary stable;
5. provider payout succeeds but wrong amount -\> not reconciled;
6. schedule corrected -\> compensating/correction record;
7. historical crypto payout source -\> preserve historical rail, current mapping provider-neutral;
8. distribution DAL source phrase -\> resolves this historical record, not DAIL;
9. ADE current mapping -\> retain separate engine identity;
10. rights dispute -\> HOLD distribution/remedy according to authority.
