## Source basis

The recovered CHLOM component catalog explicitly names **CHLOM DID** as decentralized-identifier and verifiable-credential architecture. Historical Technical Blueprint, AI-driven whitepaper, Genesis and identity/Fingerprint materials describe DIDs as cryptographic identifiers associated with keys, credentials and service endpoints.

The current system preserves the identity semantics without requiring a public blockchain or one DID method to become CrownThrive's permanent source of truth.

## Purpose

CHLOM DID provides a portable identifier/credential boundary between an institutional identity and external identity/cryptographic systems.

```text
PERSON / ORGANIZATION / SERVICE / AGENT
                  |
                  v
       INSTITUTIONAL IDENTITY RECORD
                  |
          +-------+-------+
          |               |
        DID(s)        PROVIDER ALIASES
          |               |
          +-------+-------+
                  |
         CREDENTIAL / PROOF LAYER
                  |
                  v
        POLICY / DLA / GOVERNANCE
                  |
                 DAIL
```

## Identity versus identifier

The core invariant is:

```text
DID != person
DID != organization automatically
DID != verified identity automatically
```

A DID is an identifier and document/control mechanism. CHLOM's canonical institutional identity should remain stable even when the DID method, keys or provider change.

Historical/source-standard-compatible concepts can include:

```yaml

```

CHLOM does not require every field or one exact DID standard implementation. The current institutional schema records only what the selected DID method/profile actually supports and what CHLOM needs.

## Key separation

Keys associated with a DID are cryptographic controls, not the identity itself.

```text
identity stable
   |
DID stable or versioned
   |
key v1 -> rotate/revoke -> key v2
```

Key compromise should trigger key/DID control response without erasing the institutional identity record.

## Verification methods

A DID profile can define accepted verification methods such as:

- signing keys;
- authentication keys;
- key agreement keys;
- hardware-backed keys;
- organization/service credentials;
- future reviewed cryptographic methods.

The current allowed algorithms/key types belong to security policy, not to this article as hard-coded forever values.

## Service endpoints

Historical DID documents may contain service endpoints. CHLOM should treat those as **discoverable endpoint metadata**, not as authority to call or trust a service automatically.

```text
service endpoint exists
   != endpoint trusted
   != service action authorized
```

Provider/interface certification remains separate.

## Credential relationship

```text
DID / institutional identity
        |
        +--> credential issued by authorized issuer
        |
        +--> credential status/revocation
        |
        +--> proof / selective disclosure
```

A DID does not self-issue a trustworthy credential. The issuer, authority, evidence and current status must resolve independently.

## Fingerprint relationship

CHLOM Fingerprint ID and CHLOM DID are related but not identical:

```text
Fingerprint ID = privacy-preserving institutional identity anchor concept
DID = portable decentralized/cryptographic identifier representation
```

One Fingerprint identity may bind to one or more DIDs; a DID provider/method can change without changing the Fingerprint/institutional identity.

## CrownThrive ID relationship

Current CrownThrive ID/OIDC/SSO can operate as the main application identity surface while CHLOM DID provides portable cryptographic/credential interoperability.

```text
CrownThrive ID session/authentication
        |
canonical institutional identity
        |
optional DID/VC/ZK adapters
```

This avoids forcing users into a public-chain identity system merely to use current CrownThrive applications.

## DID lifecycle

```text
CANDIDATE
   |
proof / binding verification
   |
VERIFIED
   |
   +--> key rotation
   +--> service update
   +--> credential activity
   |
   +--> HOLD / SUSPENSION
   |
   +--> REVOCATION / RETIREMENT
```

The identity remains historically traceable across all transitions.

## DID creation/registration

Before registering a DID binding:

1. institutional identity exists;
2. requested DID method/profile is allowed;
3. actor has authority to bind the DID;
4. control of the DID/key is verified;
5. source proof/evidence is stored/referenced;
6. classification/purpose are recorded;
7. duplicate/conflicting bindings are checked.

## DID update

A DID document/key update must preserve:

- old document/version reference;
- new version;
- authority/signature evidence;
- effective time;
- reason/update class;
- downstream credential/proof compatibility;
- DAIL event.

## Revocation and retirement

A DID may be retired because of:

- key compromise;
- provider/method migration;
- organization/service retirement;
- identity correction;
- security incident;
- voluntary migration.

Retiring the DID does not erase credentials/events historically tied to it.

## Recovery

Recovery is a security-sensitive process and belongs to an explicit recovery profile.

```yaml
recovery_profile_ref:
  identity_ref: stable
  allowed_recovery_authorities: restricted
  factors_or_evidence: restricted
  waiting_or_review_period: optional
  emergency_path: optional
  audit_required: true
```

Exact recovery methods, backup material and secrets remain private/Vault-bound.

## Alias/correlation control

DIDs can create privacy risk if the same identifier is reused across contexts. CHLOM may support purpose-specific/pseudonymous identifiers and explicit alias binding rather than public universal correlation.

```text
same underlying identity
  -> DID A for domain A
  -> DID B for domain B
```

Cross-domain correlation requires purpose/authority.

## Zero-knowledge relationship

A DID can bind a credential/proof subject while ZK proves a predicate without disclosing raw identity data.

```text
identity / credential
       |
private witness
       |
ZK proof
       |
DID/pseudonymous subject binding
       |
verifier result
```

A valid proof still does not create action authority.

## Public projection

Public-safe DID information should be minimal. Depending on the use case it may include:

- safe DID identifier;
- method/profile;
- public verification key material as defined by the DID standard;
- service metadata intentionally public;
- current/retired state;
- public attestation references.

Do not publish:

- recovery secrets;
- private identity evidence;
- raw biometric/Fingerprint material;
- private credentials;
- hidden provider aliases;
- internal authorization graphs.

## Failure modes

### DID cannot resolve

HOLD the DID-dependent action and use alternative verified identity evidence if the workflow permits.

### Key mismatch

Do not accept the asserted DID control; route to verification/recovery.

### Duplicate conflicting DID binding

HOLD and reconcile identities rather than merging automatically.

### DID method/provider retired

Preserve historical identity/event links and migrate to an approved replacement adapter.

### Credential currentness unavailable

HOLD credential-dependent action even if the DID resolves.

### DID document update not authorized

Reject/hold the update and preserve the prior current version.

## Threat model

- key theft;
- DID takeover;
- resolver poisoning;
- fake DID method/provider;
- cross-domain correlation/privacy leakage;
- Sybil identities;
- credential issuer spoofing;
- service endpoint substitution;
- recovery abuse;
- tenant identity collision;
- binding a provider identity to the wrong institutional person/entity.

## Test vectors

1. verified identity \+ proof of DID control -\> binding active;
2. same DID submitted for two incompatible identities -\> HOLD;
3. key rotation -\> identity and DID history remain stable;
4. compromised key -\> revoke key, do not erase identity;
5. retired DID method -\> migration path, historical events remain resolvable;
6. valid DID \+ revoked credential -\> credential-dependent action fails currentness;
7. service endpoint changes -\> new version and authority evidence required;
8. public projection -\> no recovery/private credential material;
9. domain-specific DID cannot be silently correlated elsewhere;
10. provider/OIDC account changes -\> canonical identity remains stable.

## Invariants

```text
DID != institutional identity
DID control != credential authority
key != identity
resolver success != action authorization
provider DID method != CHLOM semantic identity
recovery != silent identity rewrite
private identity evidence != public DID projection
```

## Versioning

DID method/profile, resolver, key-policy and binding-schema changes are versioned. A new DID representation can supersede an old one while retaining the same institutional identity and source lineage.
