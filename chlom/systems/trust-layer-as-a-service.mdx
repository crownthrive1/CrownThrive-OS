## Source basis

Later CHLOM materials use **TLaaS** to mean **Trust Layer as a Service**, distinct from the earlier **Tokenized Licensing as a Service** meaning. This trust-layer concept packages CHLOM identity, evidence, attestation, verification, policy and provenance capabilities for reuse by platforms and partners.

The acronym collision is intentional historical lineage, not a reason to collapse both meanings.

## Purpose

Trust Layer as a Service provides reusable assurance components without requiring every platform to implement its own identity/evidence/policy stack.

```text
PLATFORM / PARTNER / WORKFLOW
            |
      TRUST LAYER SERVICE
            |
 +----------+-----------+----------+
 |                      |          |
identity/credential  evidence   policy/proof
 |                      |          |
 +----------+-----------+----------+
            |
         attestation
            |
      DAIL / audit receipt
```

## What trust means here

`Trust` is not a universal numeric score or claim that CHLOM guarantees an actor is trustworthy.

It means the system can provide **verifiable institutional evidence about specific claims and current state**.

Examples:

- identity/credential is current;
- source evidence exists;
- a policy evaluation returned PASS/HOLD/DENY;
- an attestation was issued by an authorized issuer;
- a DLA/license is active;
- an event/proof digest matches;
- a provider claim was reconciled or remains unresolved.

## Non-purpose

Trust Layer as a Service does not:

- create a universal trust score;
- replace legal/professional authority;
- make every source true;
- guarantee a counterparty's behavior;
- make provider verification sovereign truth;
- require blockchain;
- mean Tokenized Licensing as a Service.

## Service domains

A trust-layer implementation can expose independent service families:

```text
Identity Assurance
Credential Verification
Rights/License Verification
Evidence/Source Verification
Attestation Verification
Policy/Compliance Decision
ZK/Selective Disclosure Proof
Provider Reconciliation Status
DAIL Event/Proof Query
```

Each domain has its own source/authority/currentness requirements.

## Identity assurance

```text
identity resolved
 + credential/proof currentness
 + issuer/source assurance
 -> scoped identity result
```

Identity assurance does not create roles or rights automatically.

## Credential verification

A credential verification result should resolve:

- credential identity/version;
- subject binding;
- issuer identity/authority;
- signature/proof;
- effective/expiry time;
- revocation/status;
- requested claim/purpose.

## Rights/license verification

Trust-layer consumers can request a safe DLA/right status:

```text
DLA active for predicate/use at T?
```

The service returns a scoped result, not confidential contracts unless authorized.

## Evidence/source verification

Evidence verification can check:

- source identity;
- digest/integrity;
- custody/reference;
- observation time/freshness;
- attestation/reviewer state;
- conflict/correction state.

```text
digest matches != source claim is true automatically
```

## Attestation service

An authorized issuer/reviewer can create a minimal claim derived from protected evidence.

```text
private evidence
 -> authorized review
 -> scoped attestation
 -> partner verifies attestation
```

Attestation scope, issuer authority and revocation remain explicit.

## Policy/compliance service

A partner can submit a structured action/context for policy evaluation.

```text
request
 -> applicable Compliance Packs
 -> evidence/currentness
 -> ACE/Policy Engine
 -> PASS/HOLD/DENY
```

Partner API access does not grant permission to alter policy or bypass HOLDs.

## ZK/selective disclosure

Where supported, the trust layer can return a proof/verification result without exposing raw source attributes.

```text
proof valid != action authorized
```

The consuming service still applies its own authorized action policy.

## DAIL proof/query service

A partner can receive public-safe or role-authorized event/proof information:

- current status;
- event ID/type/time;
- safe source refs;
- correction/supersession links;
- digest/anchor proof.

DAIL access does not imply access to restricted evidence payloads.

## Currentness

Trust results are temporal.

```text
verified at T0
   != valid forever
```

Credentials, policies, rights, sanctions, provider state and source data can change. Results can include `valid_until` or require revalidation at execution time.

## Provider independence

External identity, KYC, signature, blockchain, payment, data and proof providers are replaceable evidence/execution adapters.

```text
provider result
 -> CHLOM normalization/reconciliation
 -> trust-layer result
```

## Multi-tenant/partner isolation

Partners should receive only the evidence/result authorized for their tenant, purpose and audience. A partner's ability to verify a subject does not provide unrestricted lookup capability.

## API/MCP/SDK surface

Possible operations:


## Failure modes

- source unavailable -\> HOLD/UNKNOWN;
- credential revocation unavailable -\> HOLD for freshness-sensitive use;
- provider result conflicts with institutional state -\> HOLD/reconcile;
- partner requests excessive evidence -\> deny/redact;
- stale trust result replay -\> revalidate;
- unknown issuer/source -\> HOLD/invalid;
- policy conflict -\> HOLD;
- proof valid for another subject/purpose -\> invalid.

## Threat model

- trust-score overreach;
- provider impersonation;
- stale verification;
- replay of old credential/license result;
- cross-tenant privacy leak;
- issuer-authority confusion;
- public proof surface exposing private evidence;
- partner using verification result beyond stated purpose;
- correlation/re-identification;
- agent/tool authority laundering.

## Test vectors

1. current authorized credential -\> verified result;
2. valid signature but issuer unauthorized -\> invalid/HOLD;
3. DLA active yesterday but revoked today -\> stale result not reusable;
4. partner asks for raw restricted evidence when safe proof suffices -\> deny/redact;
5. provider identity check succeeds but CHLOM evidence conflicts -\> HOLD;
6. ZK proof valid for different action -\> reject;
7. public DAIL query -\> safe projection only;
8. source correction -\> prior trust result superseded;
9. tenant A cannot use tenant B protected evidence;
10. Tokenized Licensing as a Service reference -\> route to separate TLaaS record.

## Restricted companion

Private custody may contain partner contracts, identity/KYC provider details, source/reliability profiles, private attestations, raw evidence, API/security configuration, proprietary scoring or conflict-resolution logic and incident data.

## Invariants

```text
Trust Layer as a Service != Tokenized Licensing as a Service
trust result != universal trust score
verification != action authority
provider result != institutional truth automatically
attestation != fact outside issuer scope
stale result != current result
public proof != restricted evidence body
```

## Versioning

Trust service types, result schemas, source profiles, privacy rules and partner APIs are versioned independently. Historical TLaaS source meaning remains preserved even if a current trust-service product uses a different public brand.

## Status

`historical_preserved + current_functional_mapping`. Individual production trust services require specific integration/security/readback evidence.
