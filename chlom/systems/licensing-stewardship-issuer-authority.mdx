## Why this authority has its own identity

Historical CHLOM used `DLA` for **Decentralized Licensing Authority**. Current CHLOM uses `DLA` for **Dynamic Licensing Asset**. The authority function did not disappear; it was separated into **Licensing Stewardship / Issuer Authority** so the license object and the authority controlling it cannot be confused.

```text
SOURCE RIGHTS
    |
    v
LICENSING STEWARDSHIP / ISSUER AUTHORITY
    |
    v
DYNAMIC LICENSING ASSET
    |
    v
ENTITLEMENT / LEX / USE
```

## Purpose

Licensing Stewardship answers:

```text
WHO is authorized
under WHICH source rights
for WHICH asset/catalog
within WHICH scope
for WHICH licensing action
for WHICH period
under WHICH policy/approval rules
```

It is a scoped authority object, not a generic admin role.

## Non-purpose

Licensing Stewardship does not:

- create source ownership;
- grant itself new rights;
- override a rights holder's restrictions;
- make every platform admin a licensor;
- let a payment provider issue a license;
- make a historical DLA validator/DAO current;
- equate signature control with institutional authority;
- eliminate professional/legal review where required.

## Source-rights dependency

The authority ceiling is constrained by rights evidence.

```text
ISSUER AUTHORITY <= LICENSABLE SOURCE RIGHTS <= SOURCE RIGHTS
```

If source rights are disputed or incomplete, the authority record is held or narrowed rather than expanded by assumption.

## Identity and authority separation

```text
verified identity != issuer authority
role title != issuer authority automatically
cryptographic key != issuer authority
```

The issuer identity, role/delegation and rights-backed authority all need independent evidence.

## Authority sources

Possible source-authority records include:

- direct ownership/control of rights;
- written licensing/agency agreement;
- publisher/administrator appointment;
- internal corporate delegation;
- work-for-hire/employment rights structure;
- rights-acquisition agreement;
- governance/founder assignment where the organization itself controls the rights;
- another valid source-specific delegation.

A source must be recorded and current; generic business role assumptions are insufficient.

## Catalog scope

Issuer authority can be scoped to:

```text
single asset
asset family
catalog
imprint
brand
platform-specific rights subset
territory
channel
license class
```

An issuer with authority over one catalog does not automatically gain rights over the full CrownThrive portfolio.

## Permission ceiling

The authority object should carry or reference the maximum permissions it may issue.

```text
issuer permission ceiling
  = intersection(source rights, delegation terms, policy constraints)
```

Every DLA candidate is checked against that ceiling.

## Action-specific authority

A source can authorize issuance but not revocation, or renewal but not sublicensing. Therefore action permissions are explicit.

```text
can_issue != can_revoke automatically
can_transfer_approve != can_amend terms automatically
```

## Delegation

```yaml
issuer_delegation:
  delegation_id: stable id
  principal_issuer_ref: authority holder

  valid_until: optional
  subdelegation_allowed: explicit

```

Delegation cannot expand beyond the principal authority.

## Stewardship versus ownership

A steward can administer licenses without owning the underlying IP if a valid administration/license agreement authorizes it.

```text
ownership != stewardship
stewardship != ownership
```

Public claims should use the correct role.

## Issuance flow

```text
DLA CANDIDATE
    |
resolve source rights
    |
resolve issuer authority
    |
check DLA <= authority ceiling
    |
policy/evidence/approval gates
    |
PASS -> issue/activate DLA
HOLD -> review
DENY -> no issuance
```

## Amendment

An amendment requires:

- current DLA/version;
- amendment authority;
- rights scope still valid;
- agreement/holder consent where required;
- policy/economic effects resolved;
- explicit version/supersession.

Silent mutation of active license terms is prohibited.

## Renewal

Renewal checks both the DLA and issuer authority currentness.

```text
DLA renewable
+ issuer authority current
+ source rights current
+ holder conditions current
 -> renewal candidate
```

A provider subscription auto-renew does not establish license renewal authority.

## Transfer/sublicense approval

The steward may approve transfer/sublicense only if source rights and DLA terms permit it and the authority object includes the action.

```text
requested child/transfer rights <= DLA rights <= issuer ceiling
```

## Suspension/HOLD

A steward can apply a temporary hold only when the source agreement/policy grants that remedy/action. HOLD should record:

- reason class;
- authority;
- evidence;
- effective time;
- review/expiry;
- restoration path.

## Revocation/termination

Revocation is high-impact and must be rights/remedy backed. It should not be triggered merely because:

- a provider account was disabled;
- a payment failed outside the contract's remedy terms;
- an AI score increased;
- an operator dislikes the holder.

## Conflict of authority

Two issuers/stewards can claim incompatible authority. The system should create a rights/authority conflict rather than choose one by recency alone.

```text
issuer A source X
issuer B source Y
   -> compare authority/rights/effective periods
   -> HOLD if unresolved
```

## Authority currentness

Authority can expire/revoke even while a DLA remains active under its terms. Current authority affects future changes, not necessarily the historical validity of prior issuance.

```text
valid issuance at T0
issuer authority expires at T1
DLA remains governed by its own term/remedy rules
```

## Separation from current DLA

```text
Licensing Stewardship / Issuer Authority = actor authority
Dynamic Licensing Asset = license/permission object
```

Each has its own ID, lifecycle, evidence and version.

## Separation from historical DLA

The historical Decentralized Licensing Authority is retained as architecture lineage. Current stewardship can be implemented in conventional services/databases/governance workflows and does not require decentralized validators or tokens.

## LEX relationship

A LEX listing requires both current DLA/right state and seller/licensor authority. Marketplace account ownership is not issuer authority.

## Failure modes

- source rights missing -\> HOLD;
- issuer identity unresolved -\> HOLD;
- requested license exceeds authority ceiling -\> DENY;
- delegation expired -\> no action authority;
- source agreement superseded -\> revalidate authority;
- two conflicting issuer sources -\> HOLD;
- provider role says admin but no licensing delegation -\> deny;
- cryptographic signature valid but signer authority absent -\> deny/hold;
- DLA issued outside authority -\> case/remedy/correction path.

## Threat model

- forged rights agreement;
- compromised issuer account/key;
- delegation creep;
- catalog-scope escalation;
- unauthorized sublicensing;
- admin-role confusion;
- hidden authority expiry;
- provider marketplace ownership treated as licensing authority;
- public disclosure of confidential rights agreements.

## Test vectors

1. source owner delegates one catalog -\> issuer can operate only that catalog;
2. issuer asks to issue rights not owned upstream -\> deny;
3. delegation expired -\> no new issuance;
4. historical DLA authority source -\> maps to historical record, not current automatic authority;
5. valid DLA exists but issuer authority later expires -\> existing license reviewed by its terms, future amendment blocked;
6. two licensors claim same exclusive rights -\> HOLD conflict;
7. payment provider admin attempts revoke -\> no issuer authority;
8. sublicensing action absent from authority -\> deny;
9. source agreement amended -\> new authority version;
10. authority correction -\> preserve original \+ supersession/DAIL lineage.

## Restricted companion

Private custody includes rights contracts, chain-of-title evidence, issuer/licensee identities where confidential, delegation instruments, legal opinions, source-rights analyses, private scope maps and disputes.

## Invariants

```text
issuer authority <= source rights
DLA rights <= issuer authority ceiling
identity != authority
admin role != licensor authority
signature != authority
stewardship != ownership
current DLA != historical Decentralized Licensing Authority
correction/revocation != erasure
```

## Versioning

Authority assignments and delegations are versioned independently from DLA objects. Source agreement changes create new authority states without rewriting prior valid events.

## Status

`current_canonical_authority_function`. Each live issuer/steward assignment requires explicit source-rights and authority evidence.
