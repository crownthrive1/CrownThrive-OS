## Source basis

Recovered CHLOM papers and the Help Center name **CHLOM Fingerprint ID** as a cryptographic identity anchor connecting people/entities with credentials, licenses, roles, transactions, governance, reputation and revenue routing. Historical materials include multi-signal, Sybil-resistance, device/behavior and identity-proof concepts.

Those source-era ideas are preserved, but **the current public article does not claim that any particular biometric, device, behavioral or scoring algorithm is deployed**. Exact derivation, weights, signals and anti-fraud logic are restricted IP/security material.

## Purpose

Fingerprint ID provides a stable CHLOM identity anchor that survives provider-account, wallet, credential and DID changes.

## Core identity principle

```text
Fingerprint ID = canonical identity anchor concept
provider account = alias
wallet = alias/destination
DID = portable identifier representation
credential = claim about identity
role = institutional authority assignment
```

None of those aliases should silently replace the stable institutional identity.

## What Fingerprint ID is not

Fingerprint ID is not automatically:

- a raw fingerprint image/template;
- a single biometric modality;
- a device fingerprint exposed publicly;
- a reputation score;
- a wallet address;
- a DID itself;
- proof of legal identity merely because an identifier exists;
- authority to act;
- a reason to correlate a person across every CrownThrive service without purpose/authority.

## Historical multi-signal lineage

Historical designs suggest combining multiple signals to reduce identity fraud/Sybil behavior. Candidate signal families mentioned or implied by sources can include:

- identity-document verification;
- credential evidence;
- device/account continuity;
- behavioral/account signals;
- cryptographic keys;
- provider attestations;
- biometrics or other proofing factors where lawful/appropriate.

The public-safe rule is:

```text
multi-signal identity confidence
   != public disclosure of signals
```

Exact signals, coefficients, thresholds, anti-fraud patterns and data retention remain restricted.

## Identity enrollment

```text
ENROLLMENT REQUEST
       |
resolve claimed person/entity
       |
collect authorized proofing evidence
       |
check duplicate/conflicting identity
       |
       v
candidate Fingerprint ID
       |
human/provider/cryptographic validation as required
       |
VERIFIED or HOLD
```

No stable identity should be created from a single weak matching signal if the adopted profile requires stronger proof.

## Duplicate/Sybil detection

Fingerprint ID can support duplicate-identity review, but a duplicate signal is not automatic proof that two records belong to the same person.

```text
candidate match
   -> evidence comparison
   -> HOLD / merge candidate / distinct identities
```

Merge operations require explicit evidence and authority and preserve alias/history lineage.

## DID binding

```text
Fingerprint ID
   +--> DID A
   +--> DID B
   +--> future portable identifier
```

DIDs may rotate/migrate while the Fingerprint identity remains stable.

## Credential binding

Credentials reference the identity anchor and remain independent objects with issuer, status and validity.

```text
Fingerprint identity
  -> credential A active
  -> credential B expired
  -> credential C revoked
```

The Fingerprint itself does not make credentials current.

## Role/authority boundary

```text
Fingerprint identity != role
Fingerprint identity != delegation
Fingerprint identity != approval
```

Identity is a prerequisite for accountable authority, not authority itself.

## Rights/licensing relationship

Assets, DLAs and agreements can reference stable identity subjects rather than fragile provider accounts.

```text
rights holder / issuer / licensee
      -> Fingerprint/institutional identity
      -> provider aliases only as execution metadata
```

This improves portability and correction behavior when external accounts change.

## Economic-party relationship

Historical CHLOM uses Fingerprint IDs for revenue routing. Current-safe mapping:

```text
stable economic party identity
   -> obligation/entitlement
   -> replaceable provider payment destination
```

Payment destinations must not become the canonical party identity.

## Privacy architecture

### Public-safe projection

Can expose only what the purpose requires, such as:

- opaque stable identifier;
- safe verification state;
- credential/proof status where authorized;
- public attestations.

### Restricted identity layer

May contain:

- proofing documents;
- private provider identifiers;
- biometric/device/behavioral data if actually used and authorized;
- duplicate-identity evidence;
- recovery methods;
- anti-fraud features;
- security incident data.

## Selective disclosure

Fingerprint identity can participate in credential/ZK flows so services verify a predicate without seeing raw proofing data.

```text
restricted identity evidence
       |
credential / proof witness
       |
ZK or selective disclosure
       |
service receives minimum predicate
```

## Recovery and continuity

If a user's device, provider account, wallet or DID is lost/changed:

```text
stable Fingerprint identity
    -> verify recovery authority/evidence
    -> bind replacement alias/key/DID
    -> revoke/retire compromised alias
```

Do not create a new identity merely because one provider credential changes.

## Corrections

Identity data can be corrected without rewriting historical events.

```text
identity record v1
   -> correction evidence
   -> v2 / corrected attribute
```

DAIL and dependent systems record correction/supersession references.

## Tenant and purpose boundaries

Stable identity does not imply unrestricted cross-tenant visibility. A system can use scoped/pseudonymous projections:

```text
canonical Fingerprint identity
 -> tenant-scoped identity reference
 -> public pseudonymous reference
```

Cross-context resolution is an authorized internal function, not a public universal lookup.

## Failure modes

- evidence insufficient -> HOLD;
- conflicting source identities -> HOLD;
- provider proof unavailable -> alternative proofing or HOLD;
- suspected duplicate -> review, never automatic destructive merge;
- compromised key/account -> revoke alias and preserve identity;
- restricted evidence requested publicly -> deny/redact;
- credential stale -> credential-dependent action not PASS;
- recovery evidence insufficient -> HOLD recovery.

## Threat model

- biometric/privacy leakage;
- device fingerprint overcollection;
- identity takeover;
- false merge;
- Sybil creation;
- provider account substitution;
- cross-tenant correlation abuse;
- anti-fraud threshold leakage;
- recovery fraud;
- identity-to-authority escalation;
- stable identifier used as universal public tracking ID.

## Test vectors

1. strong proofing evidence -> verified identity according to profile;
2. weak single signal when multi-factor proof required -> HOLD;
3. same provider account presented for two people -> conflict review;
4. wallet/DID changes -> stable Fingerprint identity remains;
5. compromised alias -> alias revoked, identity not deleted;
6. duplicate candidate later proven distinct -> keep separate;
7. duplicate candidate proven same -> governed merge with full lineage;
8. public projection -> no raw proofing/biometric/device data;
9. valid Fingerprint ID + no role/delegation -> no action authority;
10. economic provider destination changes -> obligations remain tied to canonical party.
