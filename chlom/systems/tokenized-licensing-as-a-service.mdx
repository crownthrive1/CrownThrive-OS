## Source basis

Historical CHLOM sources use **TLaaS** to mean **Tokenized Licensing as a Service**: a packaged service layer for creating, managing and transacting programmable/tokenized licenses through DLA, LEX, identity, compliance and settlement components.

Later CHLOM materials also use `TLaaS` for **Trust Layer as a Service**. The two expansions are separate concepts and are preserved in separate atomic records.

## Historical purpose

Tokenized Licensing as a Service aimed to make CHLOM's licensing infrastructure consumable by outside platforms without requiring each platform to build its own rights/identity/compliance/marketplace stack.

```text
EXTERNAL PLATFORM / PARTNER
            |
        TLaaS API/SDK
            |
 +----------+----------+---------+
 |                     |         |
rights/DLA          compliance   identity
 |                     |         |
 +----------+----------+---------+
            |
          LEX / entitlement
            |
     payment / settlement
            |
            v
       audit / ledger
```

## Historical capability family

Source-era TLaaS can include:

- asset/right registration;
- license-template/schema selection;
- tokenized license issuance;
- DLA authority checks;
- identity/Fingerprint/DID integration;
- compliance pre-checks;
- transfer/sublicensing controls;
- marketplace/LEX listing;
- royalty/split logic;
- escrow/settlement;
- revocation/renewal;
- developer API/SDK;
- audit/event history.

## What this article does not claim

It does not establish that:

- TLaaS is currently deployed as a tokenized public service;
- licenses are currently NFTs/tokens;
- a public blockchain is required;
- historic API endpoints are live;
- partner integrations are production-ready;
- token issuance creates legal rights;
- historical pricing or fees are current.

## Current semantic mapping

## Developer API model

Historical TLaaS is naturally exposed through API/SDK operations such as:

```text
register asset
validate rights
create license candidate
issue license
read license
verify license
transfer license
sublicense
renew

```

Each write must remain authority-gated.

## Tenant/partner isolation

A service offered to external partners requires explicit tenant/organization boundaries:

```text
partner A rights/templates/data
    != partner B visibility/authority
```

Cross-partner discovery/marketplace activity must be separately authorized.

## Rights-before-token invariant

```text
source rights
   -> valid licensable scope
   -> issuer authority
   -> license/DLA object
   -> optional token representation
```

Minting/creating a token first does not manufacture rights.

## Identity relationship

Historical TLaaS uses DID/Fingerprint/credentials to identify issuers/holders and apply eligibility conditions. Current implementation can use CrownThrive ID plus optional DID/VC/ZK adapters.

## Compliance relationship

TLaaS can call ACE/Compliance Packs/Policy Engine before issuance or transfer.

```text
service request
 -> rights check
 -> identity/currentness
 -> policy/compliance
 -> PASS/HOLD/DENY
```

The service cannot lower policy simply because a partner asks for a transaction.

## LEX relationship

LEX is an optional marketplace/discovery/transaction surface. A TLaaS-issued license need not be publicly listed.

```text
license service != marketplace automatically
```

## Economic relationship

Historical TLaaS can collect service fees, royalty obligations or marketplace payments. Current economic behavior must use adopted schedules/ThriveEvergreen/current P-11 authority rather than historical token assumptions.

## Escrow/settlement

If a transaction includes payment and rights transfer:

```text
payment hold
 + rights/DLA eligibility
 + agreement
 -> transfer/entitlement
 -> release/reconcile
```

Provider payment success never creates license authority.

## Revocation/renewal

The service must support lifecycle operations independent of token transfer:

- suspend;
- revoke/terminate;
- renew;
- amend;
- transfer;
- migrate representation/provider;
- correct evidence.

## Provider-neutrality

```text
CHLOM license semantics
    != blockchain/provider representation
```

A partner can migrate databases, payment providers or token rails without changing the canonical rights meaning if source terms remain the same.

## Historical smart-contract relationship

Source-era tokenized licensing often uses smart contracts to encode terms/royalties/transfer rules. Current CHLOM treats those contracts as optional execution adapters and validates semantic state independently.

```text
smart contract success != institutional rights truth automatically
```

## Security requirements

- strong tenant isolation;
- issuer/holder authentication;
- rights evidence integrity;
- key/provider security;
- idempotent writes;
- transfer authorization;
- privacy-preserving credentials;
- audit/event history;
- provider/chain exit plan;
- contract/API versioning;
- rate/request budgets.

## Failure modes

- partner requests license without source rights -> deny/hold;
- token mint succeeds but canonical DLA creation fails -> no institutional license;
- provider unavailable -> hold/retry, canonical state remains;
- duplicate issue request -> idempotent no duplicate license;
- transfer payment succeeds but rights transfer fails -> compensation/reconciliation;
- partner tenant mismatch -> reject;
- credential expires -> eligibility-dependent action holds;
- historical token representation unsupported -> license semantics can continue provider-neutral.

## Threat model

- forged issuer;
- partner privilege escalation;
- cross-tenant data leakage;
- unauthorized mint/transfer;
- token/rights divergence;
- bridge/provider exploit;
- API replay;
- metadata tampering;
- hidden sublicense;
- economic schedule manipulation;
- provider lock-in.

## Test vectors

1. rights valid + issuer authorized -> license service candidate PASS;
2. no rights evidence -> HOLD/DENY;
3. duplicate issuance request -> one canonical DLA;
4. provider token created twice -> only one canonical license binding;
5. provider token lost/migrated -> DLA remains;
6. partner A cannot read partner B restricted licenses;
7. payment success before transfer -> no entitlement yet;
8. revoked DLA -> provider representation marked/handled per adapter;
9. historical tokenized license imported -> source/right reconciliation before current DLA;
10. Trust Layer as a Service reference -> route to separate TLaaS meaning, not this one.
