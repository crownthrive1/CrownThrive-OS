## Source basis

The CHLOM Genesis Volume explicitly uses **DAL = Decentralized Attestation Ledger** for an evidence/proof/attestation memory layer. Later CHLOM documents reuse DAL for other functions. This article preserves the Genesis meaning as its own historical object rather than forcing later definitions onto it.

## Historical purpose

The Attestation Ledger concept provides a durable record of attestations, verification evidence and proof-linked events.

```text

          v

     +----+-----+------+------+

```

## What the historical ledger attempted to solve

Source-era CHLOM needed a memory layer for questions such as:

- Was a credential or identity claim verified?
- Was a license/compliance predicate attested?
- What evidence supported a prior decision?
- Which verifier/issuer signed the claim?
- Was a proof later revoked or superseded?
- Can another module verify the historical assertion without trusting one provider database?

## Attestation object

A conservative source-era abstraction is:

```yaml
attestation_id: stable id
```

Exact chain/runtime storage fields are not invented where the source does not provide them.

## Evidence relationship

```text
raw evidence
   != attestation
```

The attestation is a scoped assertion derived from evidence under an issuer/verifier authority profile.

## Issuer/verifier authority

A valid signature does not automatically make the claim institutionally valid.

```text
signature valid
 + issuer identity current
 + issuer authority covers claim
 + evidence sufficient/current
 -> usable attestation
```

## Proof relationship

Historical DAL could anchor proof references from identity, licensing, compliance or ZK workflows.

```text
proof valid
  -> attestation candidate/result
  -> ledger record
```

A proof remains scoped to its predicate and currentness.

## Revocation

Attestations can become invalid because:

- source credential revoked;
- evidence corrected;
- issuer authority ended;
- proof expired;
- underlying license revoked;
- source fact was superseded.

The ledger preserves the original assertion and adds revocation/supersession history.

## Historical decentralization concept

The source-era design may use replicated/on-chain storage so no single participant can silently rewrite attestation history. Current CHLOM does not require that architecture.

```text
historical decentralized ledger
   -> current append-only DAIL + evidence custody + optional anchors
```

## Relationship to current DAIL

Current CHLOM uses **DAIL = Decentralized Autonomous Information Ledger** as the broader event/evidence/correction lineage.

The Attestation Ledger meaning maps into DAIL as one event/evidence family:

```text
Historical DAL/Attestation
        |
        v
DAIL attestation/evidence events
```

The acronyms are not interchangeable in historical quotations.

## Relationship to Attestation & Audit Engine

The engine verifies evidence and creates/reviews attestation/audit outputs. DAIL stores current event lineage; the historical DAL concept is the source-era ledger analogue.

## Relationship to Evidence Vault

Evidence Vault/source custody contains the underlying private artifacts. The ledger stores references/digests/status rather than requiring all evidence to be public/on-chain.

## Privacy

Public attestation proof can expose only minimum necessary data:

```text
private evidence
 -> attestation/proof
 -> public-safe status
```

Historical decentralized storage must not be interpreted as a requirement to expose PII, contracts or biometric data publicly.

## Failure modes

- attestation has no source evidence;
- verifier lacks authority;
- proof/signature valid but claim scope differs;
- revoked source credential remains marked active;
- public ledger leaks restricted evidence;
- chain/ledger immutability prevents legitimate correction semantics;
- multiple contradictory attestations treated as one truth;
- historical DAL acronym mistaken for current DAIL.

## Threat model

- forged issuer;
- verifier collusion;
- evidence tampering;
- stale attestation;
- privacy leakage;
- revocation suppression;
- duplicate/conflicting attestations;
- public-chain permanence of sensitive data;
- ledger integrity confused with factual correctness.

## Test vectors for modernization

1. valid attestation \+ authorized issuer -\> current DAIL can preserve event/reference;
2. signature valid but issuer unauthorized -\> attestation unusable;
3. credential revoked -\> dependent attestation reevaluated/revoked;
4. two conflicting attestations -\> conflict set/HOLD;
5. private evidence -\> public projection contains only safe proof/status;
6. historical ledger record -\> preserve exact DAL meaning in source page;
7. current article says DAL without source era -\> terminology check required;
8. evidence corrected -\> new attestation/supersession, original retained.
