## Purpose

This screen is the LEX exchange/discovery surface for users who are authorized to discover, inspect and transact on licensable rights. The current implementation contract must place **rights and eligibility ahead of commerce**.

```text
DISCOVER
   |
INSPECT ASSET + RIGHTS + DLA
   |
VERIFY LISTING STATE
   |
ELIGIBILITY
   |
AGREEMENT / TERMS
   |
PAYMENT / ESCROW
   |
TRANSFER / ENTITLEMENT
   |
SETTLEMENT / RECEIPT
```

The recovered title uses `Decentralized License Exchange`. That historical wording is preserved. The current service does not imply a live decentralized chain marketplace.

## Primary roles

```text
visitor / public viewer
verified participant
license buyer / licensee
licensor / listing owner
reviewer / compliance operator
support / dispute operator
```

Admin/reviewer functions should not be embedded into ordinary participant controls without role gates.

## Entry conditions

Public discovery can be broader than transaction access. A material transaction can require:

- P-01 identity resolved;
- participant eligibility current;
- listing active;
- DLA current;
- licensor rights/authority current;
- agreement/offer version resolvable;
- applicable policy PASS;
- economic activation/current payment path available;
- no rights/case/guardian HOLD.

## Primary regions

### Header

- LEX identity;
- search;
- authenticated actor status;
- participant verification indicator;
- help/support;
- optional environment/status tag where relevant.

### Filter rail / drawer

Filters may include only dimensions that are actually indexed and semantically defined:

- asset/license class;
- territory;
- media/channel;
- duration;
- exclusivity;
- transferability;
- sublicensing availability;
- licensor verification state;
- DLA status;
- listing/offer type.

Do not offer a filter that implies a legal classification CHLOM does not have evidence to support.

### Listing results

Each listing card should use public-safe metadata and show enough rights state to prevent ordinary users from confusing a marketplace card with ownership proof.

Recommended fields:

```text
listing_id
asset public title
asset class
licensor public identity
DLA public status
offer/listing type
rights scope summary
territory
duration/effective period
transfer/sublicense flags
public verification/attestation state
listing status
```

Current price/offer fields appear only when a current authorized offer exists.

## Listing-card status vocabulary

```text
ACTIVE
HOLD
EXPIRED
WITHDRAWN
TRANSFER_PENDING
DISPUTED
```

A `HOLD` listing can remain discoverable only if policy permits and the reason can be presented safely; transaction controls remain disabled.

## Eligibility panel

Before a user initiates a transaction, the interface should show a safe current decision state:

```text
Eligibility: PASS
Policy version: reference
Identity: verified for this action
Restrictions: summarized
Valid until: time if decision expires
```

or

```text
Eligibility: HOLD
Reason class: additional verification required
Next step: complete verification / wait for review / resolve conflict
```

or

```text
Eligibility: DENY
Reason class: current license not transferable
Review/remedy path: where applicable
```

Protected rule details remain hidden.

## Transaction flow

```text
BEGIN
  |
select listing/offer
  |
resolve exact DLA/listing version
  |
eligibility
  |
agreement/terms
  |
confirm exact scope
  |
payment/escrow if required
  |
license/entitlement transfer
  |
provider + institutional readback
  |
receipt / DAIL
```

## Exact-scope confirmation

The transaction confirmation should summarize what the participant is actually acquiring:

- asset/reference;
- right/license type;
- territory;
- duration;
- channels/media;
- exclusivity;
- transfer/sublicense conditions;
- current offer/price version if applicable;
- agreement version;
- refunds/cancellation/dispute rules where applicable.

Generic `Buy license` language is insufficient when scope matters.

## Payment/escrow state

The interface should distinguish:

```text
PAYMENT NOT STARTED
PAYMENT PENDING
PAYMENT AUTHORIZED
ESCROW FUNDED
TRANSFER PENDING
TRANSFER COMPLETE
PAYMENT RELEASE PENDING
RECONCILIATION PENDING
SETTLED
COMPENSATION / REFUND PENDING
```

Do not collapse these into one green `Paid` badge.

## Current provider boundary

A payment or exchange provider can execute a step, but LEX state remains institutional.

```text
      |
      v

```

## Empty states

### No listings

Explain whether:

- no listings match filters;
- exchange is not currently open for the asset class;
- data is syncing;
- user lacks access to restricted listings.

### No transaction eligibility

Do not show an empty screen. Show current HOLD/DENY explanation and allowed next step.

## Loading/stale states

If rights/DLA state is refreshing:

```text
Rights status: Checking current state…
Transaction actions disabled until readback completes.
```

A stale cached ACTIVE DLA should not permit a new transfer.

## Error states

Distinguish:

- rights service unavailable;
- policy/eligibility unavailable;
- payment provider unavailable;
- transfer service unavailable;
- settlement pending;
- provider mismatch;
- public-index lag.

## Search/index boundary

LEX search results are an index/projection. The listing detail/transaction workflow should re-read canonical listing/DLA state before material action.

```text
index says ACTIVE
   |
canonical read says HOLD
   |
UI -> HOLD
```

## Security/privacy

Do not render:

- private agreements before authorized disclosure;
- source identity documents;
- private payout/account data;
- anti-fraud signals;
- private dispute evidence;
- secret/provider credentials.

## Accessibility

- filter controls keyboard operable;
- listing cards have semantic headings;
- status text not color-only;
- rights-scope tables accessible;
- confirmation dialogs announce exact scope/economic impact;
- asynchronous eligibility/transfer updates use live-region announcements;
- mobile filters use accessible modal/drawer focus management.

## Responsive behavior

Desktop can use filter rail \+ results. Mobile uses filter drawer and single-column cards. Transaction confirmation should not hide material rights scope behind hover-only UI.
