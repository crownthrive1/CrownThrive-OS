# Rights Graph, License Hierarchy and Derivative Rights

CHLOM's licensing architecture is not a flat list of permissions. Historical DLA and LEX sources explicitly contemplate ownership, transfer, leasing, sublicensing, child rights and fractional or scoped rights. Current CHLOM expresses that lineage as a **rights graph** with enforceable parent/child constraints.

The governing invariant is:

```text
CHILD RIGHTS <= PARENT RIGHTS <= SOURCE-CONTROLLED RIGHTS
```

A downstream license cannot create permission that the upstream rights controller never possessed or never granted.

## Core objects

The rights model separates at least these objects:

```text
SOURCE ASSET / WORK / BRAND / PROPERTY
                |
                v
        RIGHTS-CONTROL RECORD
                |
                v
       MASTER / PRIMARY GRANT
                |
       +--------+--------+
       |                 |
       v                 v
   CHILD LICENSE      CHILD LICENSE
       |                 |
       v                 v
   SUBLICENSE          USE RIGHT
```

Each node has its own scope, effective period, evidence and authority.

## Source rights

Source rights describe the maximum permission controlled by the recognized rights holder or authorized licensor.

Typical dimensions include:

- asset/work/brand/property identity;
- ownership or control basis;
- jurisdiction and territory;
- media/channel;
- field of use;
- exclusivity;
- duration;
- modification/adaptation rights;
- distribution rights;
- public-performance rights;
- reproduction rights;
- resale or transfer rights;
- sublicensing rights;
- derivative-work rights;
- economic obligations;
- moral-rights or attribution constraints where applicable;
- termination/reversion conditions.

The rights graph does not decide legal ownership merely because a user asserts it. Source claims must be evidence-backed and may require professional review depending on the domain.

## Parent license

A parent license is a grant whose permissions may become the ceiling for one or more downstream grants.

```yaml
license_id: DLA-123
parent_id: null
source_rights_ref: RIGHTS-001
holder_id: ORG-A
granted_rights:
  territory: [US, CA]
  media: [streaming, download]
  sublicensing: true
  modification: false
  exclusive: false
  valid_until: 2028-12-31
```

## Child license / sublicense

A child license must reference the parent from which its authority descends.

```yaml
license_id: DLA-456
parent_id: DLA-123
holder_id: PLATFORM-B
granted_rights:
  territory: [US]
  media: [streaming]
  sublicensing: false
  modification: false
  exclusive: false
  valid_until: 2027-12-31
```

The child is valid only if its effective rights fit inside the parent's rights and the parent explicitly permits sublicensing.

## Rights-conservation check

```text
for each rights dimension:

child.scope ⊆ parent.scope
child.term  <= parent.term
child.territory ⊆ parent.territory
child.media ⊆ parent.media
child.exclusivity must not exceed parent
child.sublicensing requires parent.sublicensing = true
child.modification requires parent.modification = true
```

If any dimension exceeds the parent:

```text
candidate child license
        |
        v
rights comparison
        |
   +----+----+
   |         |
 valid     exceeds
   |         |
   v         v
continue    DENY / require new upstream grant
```

## Derivative rights

Derivative rights are permissions to transform or build on an underlying work or asset.

Examples may include:

- remixing or adaptation;
- translation;
- excerpting;
- derivative visual design;
- franchise format adaptation;
- curriculum adaptation;
- software derivative/extension;
- branded merchandise;
- localized editions;
- synchronization into another media format.

A derivative asset should not be assumed to own the underlying source rights.

```text
SOURCE WORK
   |
   +--> adaptation permission
             |
             v
      DERIVATIVE WORK
             |
             +--> new rights in derivative elements
             |
             X  does not erase source obligations
             v
      source attribution / royalty / restrictions
```

## Rights graph topology

```text
                  [SOURCE ASSET]
                        |
                        v
                [RIGHTS CONTROL]
                        |
          +-------------+-------------+
          |                           |
          v                           v
   [PRIMARY LICENSE A]         [PRIMARY LICENSE B]
          |                           |
   +------+------+                    |
   |             |                    |
   v             v                    v
[SUB A1]      [SUB A2]            [USE B1]
   |
   v
[DERIVATIVE ASSET]
   |
   +--> derivative-specific rights
   +--> inherited source obligations
```

The graph may branch, but every edge must have an authority basis.

## Chain of title

Chain of title is the ordered evidence explaining how current licensing authority derives from prior rights control.

```text
source ownership/control evidence
        |
        v
primary grant / assignment
        |
        v
current rights controller
        |
        v
license / sublicense
        |
        v
entitlement / permitted use
```

A missing link should resolve to HOLD rather than be inferred.

## Rights state versus entitlement state

Rights and entitlement are different.

```text
RIGHTS: what may legally/institutionally be granted
DLA:    what permission was granted
ENTITLEMENT: what the specific actor/system can currently access/use
```

Therefore:

```text
rights cleared
   != license issued
   != entitlement active
```

## Transfer

A transfer may change the holder of a license or ownership/control record, depending on the instrument.

A transfer check should evaluate:

- transferability flag;
- current holder authority;
- transferee eligibility;
- territory/jurisdiction;
- required approvals;
- outstanding obligations;
- sanctions/holds;
- effective date;
- payment/settlement conditions;
- whether transfer terminates, supersedes or preserves prior holder rights.

## Assignment versus sublicense

```text
ASSIGNMENT
holder A ----> holder B
control moves according to instrument

SUBLICENSE
holder A retains parent rights
        |
        +----> holder B gets bounded child rights
```

The data model must not treat these as synonyms.

## Exclusivity conflicts

An exclusive grant creates collision constraints.

```text
exclusive territory/media/term reserved to A
             |
             +--> overlapping candidate B
                       |
                       v
                  conflict check
                       |
                     DENY/HOLD
```

An exclusive grant does not necessarily block non-overlapping rights in another territory, medium or term if the source instrument permits them.

## Fractionalization and partial rights

Historical CHLOM sources explore fractional ownership/licensing. Current treatment should distinguish:

- fractional economic participation;
- fractional ownership/control;
- fractional usage rights;
- revenue-share interests;
- membership or governance interests.

These are legally and economically different constructs and must not be collapsed into one token or percentage field.

## License versioning

A DLA should be versioned when material terms change.

```text
DLA v1 active
   |
 amendment approved
   |
   v
DLA v2 active
   |
DLA v1 preserved as historical
```

Current effect may supersede the prior version, but the prior rights history remains available in DAIL.

## Termination and reversion

Termination may cause rights to revert to the parent or source controller.

```text
child license terminated
        |
        +--> child entitlement ends
        +--> downstream children evaluated
        +--> outstanding obligations preserved
        +--> parent/source rights remain or revert
```

A terminated parent may invalidate descendants unless the governing instrument explicitly allows survival.

## Downstream invalidation

```text
PARENT REVOKED
     |
     v
find descendants
     |
     +--> child 1 HOLD/REVOKE
     +--> child 2 HOLD/REVOKE
     +--> derivative entitlement review
     +--> public listing withdrawal
     +--> DAIL correction events
```

This must be deterministic and auditable.

## LEX relationship

LEX may expose only rights packages that are eligible for transaction.

```text
source rights
   |
rights graph
   |
DLA candidate
   |
transfer/sublicense eligibility
   |
LEX listing
```

LEX cannot widen a license merely because a seller lists broader terms.

## Economic obligations

A rights edge may carry obligations such as:

- royalty rate or schedule reference;
- minimum guarantee;
- platform commission;
- recoupment;
- reserve;
- attribution/credit;
- reporting;
- audit rights;
- tax/withholding treatment;
- post-termination obligations.

The rights graph should reference the economic schedule rather than embed mutable provider pricing objects as authority.

## Compliance Pack interaction

A license may require ongoing policy compliance.

```text
DLA active
   |
   +--> Compliance Pack v7 required
   |
   +--> attestation every 90 days
   |
   +--> missing attestation => HOLD/SUSPEND
```

This links rights, rules, records and remedies.

## Public versus restricted projection

A public rights view may show:

- asset identifier;
- public license type;
- holder public identifier where appropriate;
- status;
- territory/media summary;
- effective period;
- verification reference.

Restricted terms, private contracts, personal data and confidential economics remain protected.

## Rights conflict states

| Condition | Disposition |
| --- | --- |
| source control verified | continue |
| source control disputed | HOLD |
| parent license missing | HOLD |
| child exceeds parent | DENY |
| exclusive overlap unresolved | HOLD/DENY |
| parent expired | DENY activation |
| sublicense not allowed | DENY |
| economic schedule missing | HOLD commercial activation |
| transfer prohibited | DENY |
| rights valid but entitlement not issued | no access yet |

## Graph integrity invariants

```text
no_cycles
one_stable_identity_per_node
all_child_edges_have_parent_authority
child_rights_never_exceed_parent
expired_parent_cannot_create_new_child
revoked_rights_cannot_activate_entitlement
public_projection_cannot_expose_restricted_terms
```

## Current implementation boundary

The rights graph, DLA hierarchy, chain-of-title and entitlement separation are immediately implementable in cloud/API infrastructure. Historical NFT/SBT/tokenized-license representations are optional adapters and do not define the institutional rights semantics.
