## CHLOM Portal, Dashboard and Widget Catalog

Legacy CHLOM, MM Suites, MVP and Help Center sources describe many dashboards, wireframes, scorecards and widgets. Phase 2.95 normalizes these into **role surfaces composed from reusable components**.

<Warning>
  **Recovered requirements, not a deployed component library.** A named portal, dashboard, widget, card, badge, panel, meter, or role composition does not prove that a route, package, API, data source, permission, embed, or production surface exists.
</Warning>

## Build a surface from this catalog

<Steps>
  <Step title="Resolve role and task">
    Identify one stable role class and the bounded read or action it needs. Keep identity, role, authority, and provider access distinct.
  </Step>
  <Step title="Select reusable primitives">
    Compose only the identity, rights, policy, evidence, case, revenue, or integration components needed for that task.
  </Step>
  <Step title="Bind exact contracts">
    Register the surface and widget IDs, backing API/event versions, scopes, data classes, freshness, side effects, and denial/failure behavior.
  </Step>
  <Step title="Implement accessible states">
    Support keyboard and assistive-technology use, narrow layouts, loading, empty, stale, held, denied, error, and recovery states without relying on color alone.
  </Step>
  <Step title="Test authority and evidence">
    Verify that the client cannot widen permissions, expose restricted evidence, bypass HOLD/DENY, or represent a provider/UI state as institutional truth.
  </Step>
</Steps>

## Role compositions

**Founder/Holdings** gets portfolio, risk, authority, capital, incident and system-health compositions.

**CHLOM Steward/Reviewer** gets rights, policy, evidence, approval, case and remedy compositions.

**Licensor/Rights Holder** gets asset, license, offer, royalty and dispute compositions.

**Licensee/Operator** gets permissions, conditions, evidence tasks, renewal, payment and support compositions.

**Developer** gets apps/clients/scopes, sandbox, API docs, events, logs, quotas and certification status.

**Suite Pro/MM Suites Operator** gets credentials, location/suite state, booking, compliance scorecard, local revenue, campaigns and training.

**Affiliate/Ambassador** gets approved offers, links, conversions, disclosure/training, commission and payout state.

**Publisher/Advertiser** gets property/inventory, creative rights, campaign status, delivery, billing and measurement.

## Registry fields

Each surface/widget receives `surface_id`, owner platform/pallet, roles, capabilities, required scopes, data classification, API dependencies, event subscriptions, version, implementation state, accessibility state and embed policy.

| Contract area | Required developer detail |
| --- | --- |
| Identity and ownership | Stable `surface_id`/component ID, owning platform or pallet, and source lineage |
| Roles and authority | Role classes, exact scopes, approval dependency, and explicit read/write separation |
| Data | Input/output schema version, classification, purpose, retention, redaction, and freshness |
| Integration | API/event dependency, environment, auth, side effects, errors, retries, and fallback |
| Presentation | Accessible label/state, responsive behavior, embedding/origin rules, and localization where applicable |
| Evidence and lifecycle | Implementation state, verification time, audit emission, correction, deprecation, and successor |

## Phase 3 engineering rule

Do not begin by coding hundreds of pages. Build a governed component library and compose surfaces by role. A single evidence timeline, rights card, approval panel or payout statement should be reusable across Virality Music, MM Suites, Locticians, AdLuxe, CrownThriveU and external CHLOM tenants when their policies allow it.

## Error, testing, and support boundary

This catalog publishes no component package, import path, UI framework version, API base URL, authentication flow, response schema, error code, or live route. Unknown role, authority, evidence, data classification, freshness, provider, or write outcome must render a fail-closed state and preserve a non-sensitive audit/support reference.

Use the [support request workflow](/workflows/support-request) for access or data-state conflicts and the [API endpoint discovery workflow](/developers/api-endpoint-discovery-and-adapter-registry) when a backing contract is missing.
