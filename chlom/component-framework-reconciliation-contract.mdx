# CHLOM Component & Framework Reconciliation Contract

Recovered CHLOM material uses several overlapping implementation vocabularies: modules, engines, services, frameworks, protocol layers, historical runtime pallets, modern capability pallets, APIs, registries, schemas, endpoints and integration surfaces. This contract defines how CrownThrive reconciles those terms into current component identities without treating a legacy title as proof that anything is deployed, enabled, certified, decentralized, on-chain, public, or economically active.

The source taxonomy remains preserved in the [CHLOM Module Catalog](/chlom/module-catalog) and [Full Component and Pallet Atlas](/chlom/full-component-pallet-atlas). Current implementation intent is decomposed through the [Component, Pallet and Service Implementation Map](/chlom/component-pallet-service-implementation-map). Those records are related but not interchangeable.

## Core invariant

A recovered component name establishes **institutional lineage**, not operational truth.

```text
recovered name
→ canonical component identity
→ source and alias lineage
→ current implementation class
→ interface contract
→ evidence-qualified state
→ test and certification state
→ optional deployment state
```

No step may be skipped merely because an old article uses terms such as `engine`, `protocol`, `API`, `registry`, `framework`, `pallet`, `integration`, or `service`.

## Component identity contract

A current component record should separate stable identity from implementation details. At minimum, a machine-addressable record should be able to carry:

```yaml
component_id:
canonical_name:
aliases: []
component_class:
source_refs: []
capability_pallets: []
current_state:
interfaces: []
dependencies: []
data_classes: []
authority_ceiling:
provider_bindings: []
acceptance_tests: []
evidence_refs: []
rollback_or_disable_path:
public_projection_state:
```

The stable `component_id` survives a provider swap, domain move, implementation rewrite, API-version change, or UI redesign. Provider identifiers are aliases or bindings, not the CrownThrive institutional identity.

## Vocabulary boundaries

The same word may describe materially different objects across the recovered estate. Reconciliation must preserve the distinction.

- A **historical runtime pallet** is a protocol or blockchain-era design concept unless independently evidenced otherwise.
- A **capability pallet** is a modern CrownThrive packaging boundary that can contain services, policies, workflows, interfaces and success criteria.
- A **module** is a logical capability unit and does not by itself imply a separately deployed service.
- A **service** is an implementation unit only when a current service contract and deployment evidence exist.
- A **framework** describes reusable structure, rules or composition and does not automatically grant execution authority.
- An **engine** may describe an algorithmic or orchestration capability; the name alone does not prove an executable runtime exists.
- An **API, MCP, webhook, SDK, schema, registry, endpoint or integration** is machine-facing only to the extent the current contract, authentication boundary, side effects and provider state are actually evidenced.

## Machine-interface reconciliation

For machine-facing component titles, a current successor must state more than a conceptual name. The minimum safe contract distinguishes:

1. **identity** — what institutional component the interface belongs to;
2. **surface** — API, MCP, webhook, SDK, schema, registry, event or endpoint;
3. **state** — planned, controlled-test, verified read, verified write, production, deprecated or another governed state;
4. **authority** — what the caller is allowed to do, independent of technical reachability;
5. **side effects** — whether a call is read-only, reversible, externally visible, economic, rights-affecting or destructive;
6. **evidence** — what proves the claimed current state;
7. **rollback** — how a failed or harmful integration is disabled or compensated.

The current machine-contract spine remains connected to the [CHLOM Registry Model](/chlom/registry-model), [CHLOM Ecosystem Integrations](/chlom/ecosystem-integrations), and [Phase 3 Service Contract](/chlom/phase-3-service-contract).

## Current-state labels

A component should use an evidence-qualified state rather than a binary “exists/does not exist” label. Typical states include:

- recovered;
- reconciled;
- specified;
- prototype;
- controlled-test;
- staged;
- production;
- maintained;
- deprecated;
- superseded;
- research;
- target-architecture;
- blocked.

Production is never inferred from a detailed design, repository file, historical Help Center article, provider marketing page, generated code, or successful unit test. Production requires the applicable deployment, authority, security, observability and rollback evidence.

## Authority and safety boundary

This reconciliation contract operates inside D2 documentation and architecture authority. It can classify, link, specify, test and prepare component contracts. It cannot create D3 authority, legal-policy effect, rights or license grants, investment authority, token or settlement authority, provider-write authority, secret publication, money movement, production activation or a Phase 3 entry decision.

When a component intersects identity, evidence, rights, economics, legal policy, restricted material or high-impact provider writes, the specialized control plane governs. Relevant public-safe boundaries include the [Identity & Trust Reconciliation Contract](/chlom/identity-trust-reconciliation-contract), [Evidence & Audit Reconciliation Contract](/chlom/evidence-audit-reconciliation-contract), and [Source Reconciliation and Authority](/chlom/source-reconciliation).

## Continuity and contradiction handling

If two sources describe the same component differently, the system must not silently collapse them. Record the aliases, dates, source authority, implementation assumptions and current decision. A newer current contract may supersede an older implementation assumption while the earlier source remains intact as historical evidence.

A component that lacks enough evidence remains unresolved or held. The documentation program may create a current public-safe successor that explains the institutional meaning, but it may not fabricate the lost historical body or claim a terminal disposition until the governed acceptance lane approves it.

## Phase 3 relationship

This contract improves the machine-addressable substrate required for Phase 3, but does not unlock Phase 3. Component identities, interface contracts and current-state labels still have to reconcile with the [Phase 3 Readiness Gate](/technology/phase-3-readiness-gate), stable schemas, authority records, evidence, tests and operational controls.

Phase 3 entry therefore remains `blocked_pending_phase_2_99_hard_exit` until the independent hard-exit gate passes.
