## Source boundary

No standalone historical Arweave paper/specification or verified current deployment has been located. This article preserves the research lane and defines the controls required before any permanent-storage adapter can be used.

## Purpose

Arweave-style permanent or very long-lived storage is conceptually useful for artifacts intended to remain publicly retrievable and historically verifiable across provider changes.

That durability also creates a major governance constraint:

```text
permanent publication is easy to preserve
and difficult or impossible to reliably retract
```

Therefore the default CHLOM use case must be public-safe, rights-cleared, privacy-reviewed material—not private evidence or secrets.

## Candidate safe use cases

Potential research/use cases include:

- final public whitepapers or public prospectus snapshots;
- public-safe provenance manifests;
- immutable public release/manifests;
- public-safe proof/attestation artifacts;
- finalized public creative/media assets whose rights support permanent publication;
- historical public governance or documentation snapshots;
- durable public archives of already-public institutional records.

Each publication still requires a classification and rights decision.

## Prohibited-by-default material

Do not use permanent public storage as a default home for:

- credentials or API secrets;
- private keys;
- private Fingerprint data;
- personal/sensitive evidence;
- confidential agreements;
- trade secrets/proprietary algorithms;
- unpublished masters;
- data subject to likely future deletion/correction restrictions;
- information whose licensing does not permit permanent public redistribution.

A hash/commitment to protected material can sometimes be public-safe when policy allows, but the protected source body remains private.

## Public derivative first

For any source with private/internal content:

```text
PRIVATE SOURCE
 -> public-safe derivative/redaction
 -> independent digest/version
 -> rights/privacy review
 -> publication approval
 -> permanent-storage adapter
```

Never upload the protected master and rely on a UI to hide it later.

## Versioning and correction

Permanent storage does not support normal mutable overwrite semantics. A corrected document becomes a new version/publication:

```text
Institutional Document ID
 -> v1 permanent object A
 -> v2 correction object B
 -> effective version registry points to v2
```

The old public object may remain retrievable. Therefore legal/privacy/publication review must assume historical versions persist.

## DAIL and current-state separation

DAIL/current institutional records determine which publication version is current, superseded, withdrawn from active linking or otherwise effective. The permanent storage network is an archival/publication substrate, not the mutable state engine for licenses, policies, cases or economic records.

## Rights clearance

Before publication, confirm the organization controls the right to distribute the content in a durable public manner. A source may be internally owned but contain third-party material with narrower rights.

## Privacy review

Permanent public storage should undergo a stronger pre-publication privacy check than ordinary revocable web hosting. The review should consider not only visible content but metadata, embedded file properties, document comments, EXIF/media metadata and accidentally included source layers.

## Cost/economic model

Any permanent-storage fee or token/network requirement is an external provider/network execution cost. It does not activate historical CHLOM tokenomics or become a CHLOM treasury rule without an adopted economic schedule.

## Gateway/provider neutrality

Retrieval can occur through different gateways/providers. The institutional publication record keeps the permanent object/transaction reference plus current gateway aliases; gateway changes do not alter the object identity.

## Availability versus permanence

A permanent-storage design can aim for long-lived persistence, but client/gateway/network access can still degrade. CHLOM should keep local/provider-independent provenance records and, for critical assets, additional copies according to continuity policy.

## Anchor relationship

A permanently stored public artifact can also be referenced in a Merkle/proof manifest. Conversely, a DAIL/provenance record can store the publication reference/digest. These are complementary integrity layers.

## Publication workflow

```text
CANDIDATE PUBLIC ARTIFACT
 -> RIGHTS REVIEW
 -> PRIVACY / CLASSIFICATION REVIEW
 -> FINAL PUBLIC DERIVATIVE
 -> DIGEST / VERSION
 -> APPROVAL
 -> PUBLISH

```

## Failure handling

Design for wrong version selected, hidden metadata, rights status unresolved, public/private mix-up, publication transaction/provider failure, readback mismatch, gateway outage and later correction that cannot retract the older object.

## Tests

Test public whitepaper, restricted source producing a safe derivative, correction/version supersession, rights-clearance HOLD, hidden metadata scan, publication readback, wrong object reference, gateway replacement and active-site unlinking of an older superseded publication.
