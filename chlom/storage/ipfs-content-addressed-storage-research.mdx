## Source boundary

The recovered CHLOM component atlas explicitly includes **IPFS research** in the storage architecture family. A standalone historical IPFS specification or current production deployment has not been located. This article therefore preserves the research concept and defines how an IPFS-style adapter could participate in CHLOM without becoming the canonical source of institutional truth.

## Purpose

IPFS-style content-addressed storage can identify content by a cryptographic content identifier rather than only by a provider path. This can support portable public artifacts, integrity checking, distributed retrieval and selected evidence/provenance use cases.

The core CHLOM boundary is:

```text
IPFS CID / content address
= storage/integrity reference
!= rights
!= policy
!= source authority
!= proof the content should be public
```

## Candidate CHLOM uses

Appropriate research/use cases can include:

- public whitepapers and public documentation snapshots;
- public-safe evidence/proof artifacts;
- public media/assets whose rights permit distributed storage;
- software/schema/release artifacts;
- public attestation or manifest files;
- content-addressed references inside provenance records;
- optional redundancy for non-secret immutable assets.

Restricted personal evidence, private contracts, trade secrets and credentials should not be placed on broadly retrievable decentralized storage simply because content addressing is technically available.

## Content addressing and digests

A CID/content address provides a strong link to particular content bytes according to the addressing scheme. If the file changes, the content address changes. CHLOM's provenance registry should record which source/version the CID represents.

## Canonical-state separation

Canonical DLA, rights, identity, policy, economic and case state remains in governed institutional records. IPFS is not the primary mutable state database for current operational workflows unless a future architecture explicitly adopts such a design.

## Mutable/current references

Because content addressing is immutable by content, CHLOM can represent a changing document through versioned objects:

```text
Institutional Document ID
 -> version 1 -> CID A
 -> version 2 -> CID B
 -> version 3 -> CID C
```

The institutional record determines which version is current/effective while retaining old content-address references.

## Pinning and availability

A content address does not guarantee continued availability. CHLOM must separately track pinning/hosting/provider availability and recovery strategy. Multiple pin providers or self-managed nodes are implementation options, not institutional requirements.

## Public/private classification

Before publication to a distributed storage system, verify that content classification and rights permit durable/public retrieval. Redaction should occur **before** publication, producing a separate public derivative and CID.

## Rights and takedown reality

Content-addressed/decentralized distribution can make later suppression difficult. CHLOM should not publish content whose licensing, privacy, legal or retention posture requires reliable future removal unless the storage strategy actually supports that requirement.

## Evidence and proof use

A DAIL/evidence record can reference a CID for a public-safe artifact. The evidence record still carries source, issuer, currentness, classification and authority metadata. The CID alone does not say whether the artifact is authoritative.

## Merkle/anchor relationship

IPFS content addressing and CHLOM Merkle/notary anchoring are separate integrity patterns. A CID can be included in a manifest or Merkle batch; an anchor can reference that manifest. Neither replaces the canonical institutional object/version registry.

## Adapter interface

A current optional adapter can expose:

```text
store_public_content
pin_content
verify_content_available
resolve_cid
verify_content_matches
retire_local_pin
migrate_pin_provider
```

These operations remain subject to classification/rights policy.

## Provider neutrality

Public gateways, pinning providers or node infrastructure are replaceable. Stable CHLOM object IDs and recorded CIDs survive provider changes.

## Operational status

Track pin/provider health, content availability, verification time, retrieval latency and provider aliases. A temporarily unavailable CID is a storage availability issue, not evidence that the institutional record disappeared.

## Tests

Test same content producing stable content reference under the selected implementation, changed content/version, public derivative of restricted source, unpinned/unavailable content, multiple pin providers, provider migration, wrong content for recorded reference and DAIL/provenance resolution.
