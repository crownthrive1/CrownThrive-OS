## Release scope

CHLOM is CrownThrive's Compliance Hybrid Licensing and Ownership Model for Rights, Rules, Roles, Revenue, Records and Remedies. CrownThrive operates within **Phase 3 — Execute**; component release versions and maturity are separate from that institutional phase.

**Implementation available; production readback pending.** The CHLOM 1.2 wallet and installation implementation is preserved in [source snapshot f101cb0](https://github.com/crownthrive1/chlom-protocol/commit/f101cb061ea41d7b2a20f38d9e2aedd96d55b270) on `release/chlom-1-2-wallet-installation-20260920`. This identifies the reviewed source snapshot, not a final release or deployment. The exact release receipt must bind the final source, installation artifacts, applied migrations, production verification and recovery evidence.

## Wallet integration

The available implementation adds injected EVM wallet discovery with EIP-6963/EIP-1193, connection and account/network change handling, and a server-verifiable signed-message observation. The initial snapshot explicitly limits that observation to the browser flow; it is not an application login or a durable rights binding. Production configuration and end-to-end readback remain pending in this record.

Wallet integration is a sequence of separately evidenced capabilities:

| Capability | What acceptance establishes |
|---|---|
| Browser provider discovery | The application can find and select an injected EVM provider using the supported discovery interface. |
| Account connection | The user permits the selected wallet to expose an address and network to the application. |
| Signature observation | A domain-bound, expiring challenge signature is verified for the stated address and scope. |
| Account authentication | A separate replay-safe identity/session contract binds the wallet to an authorized account. |
| Rights projection | Canonical CHLOM records establish licenses, entitlements, obligations, proofs and receipts for that account. |
| Economic execution | A separate authorized transaction produces verified provider receipts and reconciliation. |

A connected address does not grant asset ownership, copyright, a license, a governance vote or permission to spend funds. Signature observation must not be described as account authentication unless the complete session and replay controls are implemented and accepted. Contract-wallet verification, relay connections and embedded wallets must be declared separately when supported.

The complete CHLOM Wallet/Vault design covers ownership, licenses, credentials, entitlements, obligations, proofs, receipts, royalties and settlement status. Canonical rights and evidence must survive changes to wallet vendors, chains and hosting providers.

## Policy and proof boundaries

Adaptive compliance uses approved, versioned policy packs with source provenance, purpose, effective dates and explainable evaluation. AI can support classification, anomaly detection and review routing. It cannot silently enact a new policy or manufacture a legal determination.

The public audit projection should expose only authorized summaries and cryptographic commitments. Private evidence remains private by default. A message signature proves its stated signing claim; a hash commits to bytes; a Merkle proof establishes inclusion relative to a root. None of those should be labeled a zero-knowledge proof. ZK claims require the actual proof system, circuit/version, key custody and verifier acceptance.

## Token terminology and licensing

Historical papers describe CHLOM Coin as utility and CHM as governance; an experimental launch guide uses C-CHLOM and L-CHLOM. The current [source reconciliation](https://github.com/crownthrive1/chlom-protocol/blob/main/docs/architecture/SOURCE_RECONCILIATION.md) leaves final names and roles unresolved. Utility accounting, governance authority, transferable tokens and issuance remain distinct implementation choices.

The [repository license](https://github.com/crownthrive1/chlom-protocol/blob/main/LICENSE) is proprietary. Public source visibility does not grant an open-source or general commercial-use license. Separately licensed dependencies keep their own terms.

## Installation and acceptance

Use the installation and environment references in the exact CHLOM source snapshot. Do not use a moving branch as an immutable deployment identifier. Node/runtime support, package license, third-party notices and configuration requirements are part of the install contract.

Install from an identified release artifact or exact source revision. Use that release's documented runtime, dependency lock, configuration reference and migration instructions. Keep server credentials out of browser bundles and public documentation.

Acceptance should record:

1. Exact source version and artifact digest.
2. Reproducible build and relevant tests.
3. Installed runtime/configuration and applied migrations, if any.
4. Actual wallet selection, network/account changes, rejected signatures, expired challenges and disconnect behavior.
5. Exact deployment readback and recovery procedure.
6. Independent entitlement, payment or issuance acceptance for any commercial capability claimed.

A protocol installation is separate from native CHLOM LEX administrator setup. Published offers, price references or finite billing instructions do not establish customer authorization, an executed schedule, settled payment, delivery or payout.
