# CHLOM Concept, Algorithm, Model and IP Asset Registry

CHLOM's intellectual property is broader than paper files. A paper may contain dozens of independent concepts, algorithms, equations, diagrams, data schemas, workflow methods and system invariants. Those assets need **stable institutional identities** so they can be tracked, protected, implemented and superseded independently.

## Registry status

```yaml
article_state: reconstructed_source_grounded_plus_current_registry_design
current_role: technical_IP_asset_registry_contract
paper_is_asset_container: true
paper_equals_implementation: false
protected_IP_publication: metadata_and_public_safe_patterns_only
founder_adjudication: open_after_publication
```

```text
PAPER / SOURCE
    |
    +--> CONCEPT
    +--> ALGORITHM
    +--> FORMULA / MODEL
    +--> STATE MACHINE
    +--> SCHEMA
    +--> ASCII MODEL
    +--> POLICY PATTERN
    +--> INTERFACE CONTRACT
    +--> THREAT MODEL
    +--> TEST VECTOR
    +--> IMPLEMENTATION REQUIREMENT
```

## Core distinction

```text
paper_id != concept_id != algorithm_id != implementation_id
```

One concept may appear in many papers. One algorithm may implement multiple concepts. One implementation may replace another without changing the underlying institutional concept.

## Why this registry exists

Without asset-level records, CHLOM knowledge collapses into documents that are hard to compare, version or implement.

```text
DOCUMENT-CENTRIC ONLY
       |
       +--> same idea copied across papers
       +--> formulas buried in appendices
       +--> algorithms lose provenance
       +--> diagrams become screenshots
       +--> implementation status becomes ambiguous

ASSET REGISTRY
       |
       +--> stable concept ID
       +--> source provenance
       +--> current authority
       +--> version / status
       +--> implementation links
       +--> test / evidence links
       +--> confidentiality
```

## Asset class: Concept

An abstract institutional or technical idea such as Rights-before-Revenue, Dynamic Licensing Asset, DAIL, Compliance Packs, Fingerprint identity, Rights Graph, Oracle Lattice, Smart Treasury, LEX and founder adjudication/correction without erasure.

## Asset class: Algorithm

A repeatable decision or transformation procedure such as policy evaluation, rights closure, sublicensing validation, oracle aggregation, allocation/reconciliation, proof verification or DAIL correction propagation.

## Asset class: Mathematical model

A formula or quantitative relation such as net supply change, staking APY, basis-point allocation, quorum ratio, risk score, reserve ratio or SLA availability.

## Asset class: State machine

A controlled set of states and transitions for DLA, LEX, credentials, policies, cases, payments, reconstruction or release.

## Asset class: Schema

A versioned machine-readable object/event contract with explicit compatibility and confidentiality rules.

## Asset class: ASCII model

A portable explanatory architecture diagram. ASCII is explanation, not executable state.

## Asset class: Threat model

A record of protected assets, trust boundaries, actors, attack paths, mitigations, residual risk and monitoring.

## Asset class: Test vector

A deterministic or adversarial fixture connecting inputs to expected intermediate/output/disposition behavior.

## Formula change control

A formula version change must document mathematical expression, variable meanings, units, input sources, changed assumptions, old/new output comparisons, threshold implications, affected economic/policy contracts and migration behavior.

## Concept collision handling

```text
AIE: AI Intelligence Engine
AIE: Anomaly Intelligence Engine
```

Represent as two concept records with a documented relationship rather than one mutable definition.

## Asset status state machine

```text
discovered
 -> source_grounded
 -> decomposed
 -> classified
 -> specified
 -> prototyped
 -> tested
 -> controlled_test
 -> production_verified
 -> maintained
 -> superseded
```

Any asset may stop at historical/research state indefinitely.

## Vault / custody expectation

Restricted source files, detailed algorithm bodies, proprietary research and machine manifests should have protected canonical custody outside public documentation, with public Mintlify pages providing safe indexes and interpretations.

## Founder adjudication

A Founder decision may declare a concept canonical or retired, resolve duplicate algorithms, reclassify a formula, define color-paper semantics, set confidentiality, rename a component or approve a reconstructed model for implementation. The decision appends a new effective interpretation without destroying source lineage.

## Final institutional rule

If CHLOM creates an idea worth naming, a model worth calculating, an algorithm worth using, or a diagram worth preserving, it receives a durable record.

```text
IF IT MATTERS TO CHLOM
      |
      v
GIVE IT AN ID
      |
      v
GIVE IT PROVENANCE
      |
      v
GIVE IT A VERSION
      |
      v
GIVE IT A STATUS
      |
      v
GIVE IT TESTS / EVIDENCE WHEN IMPLEMENTED
```

That is how CHLOM technical IP stops being trapped inside documents and becomes governed institutional memory.
