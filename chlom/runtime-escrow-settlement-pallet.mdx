## Historical purpose

The Escrow & Settlement Pallet was designed to make license/payment exchange atomic inside the historical CHLOM runtime: funds or value were held until compliance/transfer conditions were satisfied, then released only when the transaction completed.

```text
BUYER VALUE / FUNDS
       |
       v
     ESCROW
       |
       +--> compliance / eligibility
       +--> license/asset transfer condition
       |
 conditions satisfied?
       |
   +---+---+
   |       |
  no      yes
   |       |
refund   release + settlement
```

## Escrow is a conditional state

Escrow does not mean ownership, entitlement or settlement.

```text
value held in escrow
     !=
transaction settled
```

## Historical atomicity

Inside one runtime, CHLOM could model asset/license transfer and value release as one atomic state transition.

```text
if all preconditions true:
    transfer license
    release escrow
else:
    no final transfer/release
```

## Current distributed-system mapping

Current provider-based payments and license services may not support true atomicity across systems.

```text
payment provider
   +
rights/license service
   +
commerce service
   +
settlement service
```

Therefore current CHLOM uses **sagas and compensating actions** where needed.

```text
STEP A succeeds
STEP B fails
   |
COMPENSATE A / HOLD / REVIEW
```

Never call a multi-provider flow atomic unless its implementation actually guarantees atomicity.

## Condition model

Conditions can include:

- payment/capture evidence;
- active DLA/license;
- transfer/sublicense eligibility;
- counterparty verification;
- agreement execution;
- policy/compliance PASS;
- timelock expiry;
- delivery/acceptance condition;
- dispute absence/resolution.

## Timeout

Escrow requires timeout/expiry semantics so funds/value are not stranded indefinitely.

```text
pending escrow
   |
expiry reached
   |
conditions still unresolved?
   |
refund / cancel / route governed review
```

## Dispute relationship

Disputed escrow remains held until an authorized disposition determines release/refund/other remedy.

## Settlement relationship

```text
escrow release
    !=
P-11 settlement automatically
```

P-11 reconciles expected obligation, provider/runtime receipts and final institutional status.

## Idempotency

Release/refund operations must be idempotent. Duplicate webhook/message processing cannot release/refund twice.

## Failure cases

### Payment captured, transfer fails

Refund/compensate/hold under current policy; do not call transaction completed.

### License transferred, provider payout fails

Hold/retry/compensate according to agreement and rights state; preserve transferred-state evidence.

### Conflicting dispute arrives during release

Use ordered/atomic local controls where available; otherwise HOLD if release not finalized and preserve exact event sequence.

### Provider says refunded, institutional order still active

Reconcile entitlement/order/economic state; provider receipt is evidence.

## Security threats

- double release;
- forged condition satisfaction;
- escrow drain;
- timeout manipulation;
- reentrancy/runtime exploits historically;
- race between dispute and release;
- provider callback spoofing;
- currency/value mismatch.
