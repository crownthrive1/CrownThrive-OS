## Historical purpose

The historical Attestations Pallet was CHLOM's generic runtime mechanism for writing standardized, verifiable assertions about proofs, decisions, settlements and other governed outcomes.

```text
EVENT / EVIDENCE / DECISION
          |
          v
ATTESTER AUTHORITY
          |
          v
STANDARD ATTESTATION
          |
          v
ON-CHAIN REFERENCE / STATE
          |
          +--> license checks
          +--> audit
          +--> settlement
          +--> cross-chain mirror
```

## Attestation meaning

An attestation is an assertion by an identified/authorized source about a defined subject and claim.

```text
observation
   !=
attestation
   !=
authority
   !=
factual correctness guaranteed
```

The pallet made attestations verifiable and immutable/referencable; it did not logically make every assertion true.

## Standardized schemas

The source explicitly states standardized schemas. Schema version is therefore part of the attestation's meaning.

```text
schema v1 claim
    !=
schema v2 claim automatically
```

Each verifier must resolve the schema/version that governed issuance.

## Issuer/attester authority

A valid signature is not sufficient if the signer was not authorized for the claim type.

```text
signature valid?
   |
  yes
   v
issuer registered/authorized for schema + scope?
   no -> HOLD/DENY
   |
  yes
   v
attestation current / not revoked?
   no -> HOLD/DENY
   |
  yes
   v
usable attestation
```

## Revocation

Historical attestations must support correction/revocation semantics even when the underlying event record is immutable.

```text
ATTESTATION A
   |
   +--> REVOKED by R
   +--> SUPERSEDED by B
```

The original remains part of provenance.

## Proof relationship

```text
RAW / PRIVATE EVIDENCE
       |
       v
PROOF / VERIFICATION
       |
       v
ATTESTATION
       |
       v
DEPENDENT POLICY / LICENSE / ACTION
```

An attestation can summarize successful verification without exposing the private evidence.

## Settlement relationship

A settlement attestation can state that a defined economic obligation was reconciled. It cannot create the obligation or underlying rights.

```text
rights/agreement -> obligation -> execution evidence -> reconciliation -> settlement attestation
```

## Decision relationship

Governance/case decisions can generate attestations suitable for downstream verification while the full decision/evidence remains protected.

## Privacy

Attestations should minimize data disclosure. Public verification can use digests/selective claims rather than raw evidence.

## Security threats

- unauthorized issuer;
- schema substitution;
- replay after revocation;
- stale verification cache;
- forged proof/signature;
- subject misbinding;
- privacy leakage through claim payload;
- misleading public presentation of scoped attestation as universal certification.

## Public / restricted split

Public-safe:

- attestation type/schema;
- public issuer identity;
- validity/revocation status;
- public proof/anchor reference;
- architecture.

Restricted:

- underlying evidence;
- private subject identity mapping;
- protected verification procedures;
- security findings;
- private settlement/case detail.

## Invariants

```text
attestation != truth by itself
signature valid != issuer authorized
attestation valid != action authorized
settlement attestation != rights
revoked != deleted
schema mismatch != PASS
anchor exists != factual correctness
historical on-chain attestation != current chain deployment
```
