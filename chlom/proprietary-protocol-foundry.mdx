# CHLOM Proprietary Protocol Foundry

## Institutional identity

```yaml
protocol_id: ct.protocol.metaprotocol-foundry
version: 1.0.0
private_body: vault_only
public_projection: contract_digest_only
candidate_default: controlled_test_hold
activation_default: false
monetization_candidate_default: true
```

The Protocol Foundry institutionalizes CrownThrive's repeated operating procedures as reusable proprietary protocol candidates. It does not publish the restricted protocol body or convert an observed workflow into active authority merely because it is useful.

## Candidate pipeline

```text
observe repeated procedure
→ classify novelty, ownership and risk
→ extract purpose, inputs, outputs and invariants
→ define authority ceiling and forbidden actions
→ compile restricted protocol body
→ create Vault-first protected custody
→ generate public-contract digest
→ assign owner and independent verifier
→ open controlled-test candidate
→ create pricing/licensing candidate
→ archive on material change
```

## Required protocol fields

Every protocol candidate must define:

- stable protocol ID and semantic version;
- canonical name and purpose;
- inputs, outputs and failure behavior;
- invariants and prohibited operations;
- evidence requirements;
- D0-D3 authority ceiling;
- owner and separate verifier;
- deterministic rollback or containment;
- public-safe contract;
- restricted implementation location;
- lifecycle and supersession policy;
- monetization candidate state;
- archive and continuity requirements.

## Authority model

| Class | Foundry authority |
| --- | --- |
| D0 | deduplicate, normalize metadata and compare public-contract digests |
| D1 | create a Vault-first candidate/HOLD record and deterministic custody receipt |
| D2 | independently verify implementation, safety, evidence and controlled-test eligibility |
| D3 | public activation, binding economics, exclusivity, constitutional authority, destructive change or production secret insertion |

Agents may not self-approve a protocol they compiled. A protocol body may not be publicly projected merely because a public contract exists.

## Vault-first custody

The private body is stored as a protected Vault asset. The institutional record exposes only:

- protocol identity and version;
- classification;
- public-contract digest;
- owner/verifier identities;
- lifecycle state;
- sanitized DAIL receipt;
- commercial-candidate state.

The body, private topology, calibration, credentials, private evidence and implementation-specific defensive controls remain restricted.

## Continuous agent operation

The non-voting Protocol Foundry Agent operates through a daily condition-watch subroute. It reuses existing institutional agents before proposing new identities and routes every material candidate through the proprietary asset classifier and independent proof verifier.

The foundry does not consume a new external scheduler slot. It runs as a governed subroute of the existing CrownThrive dispatcher, with stable-ID/version deduplication.

## Initial protocol family

The first governed protocol family includes:

- Credential Binding and Continuity;
- Protected Asset Custody and Archive Continuity;
- Metaprotocol Protocol Foundry;
- Protocol Commercialization and Licensing Continuity;
- Provider Adapter Certification.

All five private bodies are Vault-bound. Their public-safe records expose only contracts and digests. None is production-activated solely by registration.

## Continuity

Protocol versions are immutable. A new version supersedes but does not delete its predecessors. Material changes enter the encrypted archive path, and public documentation must identify the current version without erasing historical lineage.
