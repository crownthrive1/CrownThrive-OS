## Historical purpose

The Policy Pallet was designed to hold protocol-level policy state that other historical CHLOM pallets could consult before executing regulated or governed actions.

```text
GOVERNANCE / AUTHORIZED POLICY UPDATE
                |
                v
          POLICY PALLET
                |
        versioned rule state
                |
        +-------+-------+
        |               |
      DLA              LEX
        |               |
        +-------+-------+
                |
         compliance pre-check
```

## Policy versus code

A runtime policy representation is an implementation of an adopted rule—not the source of authority by itself.

```text
source authority
     |
adopted policy meaning
     |
machine representation
     |
runtime evaluation
```

A machine rule that diverges from the adopted source is defective even if the chain executes it consistently.

```text
POLICY v1
   |

   |

```

Historical transactions/decisions must retain a reference to the policy version that governed them.

## Compliance pre-check relationship

Historical CHLOM architecture describes in-runtime compliance hooks that could reject an operation before execution.

```text
PROPOSED EXTRINSIC
      |
POLICY LOOKUP
      |
IDENTITY / LICENSE / RISK INPUTS
      |
DECISION
ALLOW | REJECT | HOLD-like off-chain review path
```

The original runtime design was more binary than current CHLOM's explicit PASS/HOLD/DENY model. Current mapping adds HOLD for unresolved/stale/conflicting state.

## Governance relationship

Policy updates historically flowed through governance mechanisms. Current CHLOM preserves that principle without assuming token voting.

```text
authorized governance decision
       |
       v
new policy version
       |
       v
current services + DAIL
```

## Current Compliance Pack mapping

Current Compliance Packs package rules, evidence requirements, applicability and tests in a richer service model.

```text

```

## Policy precedence

Current mapping requires explicit precedence between overlapping policies. The historical title inventory does not prove a particular on-chain precedence algorithm, so none is invented.

## Policy compiler relationship

A Policy DSL/compiler can transform approved policy into executable representations.

```text
human/adopted source
    |
compiler
    |
candidate machine policy
    |
validation/test
    |
authorized executable version
```

Compilation never self-authorizes changes.

## Failure cases

### Unknown policy version

Current result: HOLD for actions requiring a resolved current policy.

### Source/machine divergence

Current result: HOLD/disable affected rule; open correction review.

### Stale policy cache

Canonical policy version controls; provider/service cache mismatch is evidence.

### Conflicting policies

Use explicit precedence where adopted; otherwise HOLD rather than selecting a convenient result.

## Security concerns

- unauthorized policy mutation;
- malicious policy broadening;
- version rollback;
- source/code divergence;
- hidden defaults;
- fail-open behavior;
- stale caches;
- rule injection/DSL parser abuse.

## Public / restricted split

Public-safe:

- policy architecture;
- public policy IDs/versions where appropriate;
- evaluation semantics;
- current mapping.

Restricted:

- anti-fraud rules;
- sensitive thresholds;
- confidential contract/jurisdiction mappings;
- exploit-sensitive compiler/evaluator details;
- private legal analyses.

## Invariants

```text
compiler output != adopted policy
historical binary allow/reject != current HOLD semantics automatically
policy update != historical erasure
runtime design != deployed runtime
```
