## Current and Target Architecture

<Info>
  **Current-state overlay:** CrownThrive is operating in **Phase 3 — Execute**. The retired decimal-phase label below identifies the historical origin of the cloud/API architecture, not the current institutional phase. Component deployment and certification remain evidence-specific. See [Current Operational State](/start-here/current-operational-state).
</Info>

CHLOM has two architectural layers that must not be confused.

## Current governed core — historical Phase 2.5 origin

The cloud-first, API-first, event-driven, multi-tenant, and human-governed core was established during the historical Phase 2.5 program and remains the current architectural baseline where supported capability by capability. This architecture description does not create blanket production or provider-write certification.

```text
Rights Registry
Rules / Policy Registry
Roles / Authority Registry
Revenue Registry
Records / Evidence Registry
Remedies / Case Registry
        ↓
Approval Service
        ↓
DAIL event and audit layer
        ↓
CrownThrive IO / MCP / platform integrations
```

This baseline is intended to support current CrownThrive platforms before irreversible decentralized infrastructure is introduced.

## Preserved target architecture

Historical CHLOM technical sources describe future capabilities including:

- programmable licenses and smart-license objects
- DLA lifecycle automation
- LEX licensing exchange
- decentralized identity and credentialing
- zero-knowledge proofs
- compliance and risk oracles
- smart treasury and automated split logic
- blockchain anchoring and settlement
- cross-chain or bridge infrastructure
- tokenized economic models
- DAO-style governance modules
- formal verification and theorem-driven protocol checks

These remain research, target architecture, or gated future modules until approved deployment evidence exists.

## Why the distinction matters

A system can preserve decentralization as a future design goal without claiming infrastructure exists before it is legally, economically, operationally, and technically validated.

This cloud-first baseline therefore preserves interfaces that can later support cryptographic anchoring or decentralized settlement while keeping business meaning stable.

## Gate before decentralization

Before a target module can move to production, it should have explicit evidence for:

1. legal and rights review
2. economic model validation
3. security review
4. privacy review
5. operational ownership
6. test coverage
7. rollback or recovery design
8. founder/governing approval
9. production deployment evidence

No historical white paper alone satisfies those gates.
