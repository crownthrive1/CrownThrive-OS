### Permanent creation rule

A future CHLOM paper should not wait for forensic recovery. At creation it should receive a stable paper ID, source custody/digest, version/date, confidentiality class, concept links, formula/algorithm/ASCII identifiers, current authority classification and implementation relationships.

```text
paper created
 -> paper ID + source custody
 -> concept / formula / algorithm / diagram extraction
 -> current/historical classification
 -> Mintlify + machine registry
 -> later implementation/test/runtime evidence
```

## IP record schema

Every recovered paper should receive:

- `paper_id`;
- paper family/color;
- exact title;
- original source file;
- source hash/reference;
- owner: CrownThrive, LLC unless evidence shows otherwise;
- author/contributor where known;
- original date/version;
- confidentiality class;
- current authority class;
- concepts covered;
- affected modules/pallets/platforms;
- patent/defensibility relevance;
- superseded-by/related-paper relationships;
- implementation references;
- public-release eligibility.

## Patent-status correction

Some historical CHLOM sources used **patent-pending** language. The Founder has clarified that the provisional/patent path was not pursued to filing. Current institutional and public records must therefore **not claim patent-pending status** unless a future verified filing creates that status.

Historical statements remain preserved as historical source content, with a correction note.

## Decomposition and recovery states

Each paper progresses independently:

`source_not_located → source_located → integrity_recorded → text_and_figures_extracted → terminology_mapped → claims_classified → requirements_and_invariants_decomposed → components_and_APIs_linked → ADR_reviewed → engineering_recovered → implemented_or_deferred`

A title in the Help Center proves that a knowledge object existed; it does not prove that the original body survived. Reconstructed summaries must be labeled as reconstruction rather than verbatim recovery.

The **Paper-to-Engineering Decomposition Pipeline** controls how papers become concepts, requirements, invariants, schemas, APIs, tests, components and implementation decisions while preserving the original source and confidentiality.

## Phase 3 use

Phase 3 engineering should mine this corpus for requirements, invariants, workflows, algorithms, schemas, threat models and interface/portal needs. A paper is an input to specification—not proof that code exists or that a legal/economic construct is approved.

Phase 3.0 should seed paper records and decomposition work queues. Trust/rights/evidence papers have priority. Dedicated-chain, token, bridge and advanced cryptographic papers remain 3E/Phase 5 candidates until core services and current legal/security/economic requirements are proven.
