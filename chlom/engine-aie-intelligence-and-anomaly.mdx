## Purpose

AIE is CHLOM's intelligence layer for turning observations into **risk, anomaly, pattern and recommendation evidence** that other governed systems can evaluate. Historical sources use AIE for the **AI Intelligence Engine**. Later architecture reuses AIE for the **Anomaly Intelligence Engine**. Both meanings are preserved; current machine records must include version/namespace rather than relying on the acronym alone.

## Historical AI Intelligence Engine

Genesis-era AIE was conceived broadly as the machine-intelligence engine feeding CHLOM's compliance and autonomous-decision architecture. Functions included:

- risk scoring;
- anomaly detection;
- predictive/compliance analysis;
- learning from transaction/behavior patterns;
- policy simulation;
- assisting ACE and historical ADE.

## Later Anomaly Intelligence Engine

Later architecture narrows the AIE label toward anomaly intelligence: identify deviations, suspicious patterns, drift, provider mismatches, inconsistent claims and unusual behavior for review or policy evaluation.

## AIE does not decide authority

```text
AIE score / anomaly
      !=
violation
      !=
license revocation
      !=
payment hold authority by itself
```

AIE outputs are evidence/recommendations consumed by ACE/P-02 or reserved human review.

## Feature/model boundary

Features are model inputs, not institutional facts unless separately supported.

```text
source evidence
   |
normalized observation
   |
derived feature
   |

```

Each transformation should be versioned/reproducible enough for the decision class.

## Risk model

A generic risk model is:

```text
risk_score = f(features, model_version)
```

Historical sources include example weighted formulas. Those formulas and later proprietary calibration receive source/model IDs; historical weights are not silently deployed as current thresholds.

## Anomaly model

A generic anomaly model may compare current observations to an expected baseline:

```text
anomaly = distance(x, expected_distribution_or_rules)
```

The distance function, baseline, thresholds and feature set are model-specific and can be protected IP.

## Rule-based anomalies

Not all anomalies require ML.

Examples:

```text
provider state != canonical state
payment amount != expected obligation
license active externally after local revocation
sudden role escalation
stale source presented as current
impossible event sequence
```

Deterministic anomalies should remain explainable.

## Statistical/ML anomalies

Possible methods include:

- z-score/deviation models;
- robust outlier methods;
- isolation/anomaly models;
- supervised fraud/risk classification;
- time-series drift/change detection;
- graph anomalies;
- ensemble scoring.

No specific method is declared production merely by listing the architecture family.

## Confidence and uncertainty

Confidence is not authority.

```text
high confidence model output
      !=
high authority decision
```

AIE should expose uncertainty where useful rather than hide it behind a single score.

## ACE relationship

```text
AIE
 produces intelligence evidence
   |
   v
ACE
 applies adopted policy + authority
   |
   v
PASS / HOLD / DENY / REVIEW
```

This separation is constitutional: intelligence can optimize understanding but cannot manufacture governance authority.

## Human review

AIE can trigger review when:

- risk/anomaly exceeds a governed threshold;
- uncertainty is high;
- model disagreement is material;
- protected decision class requires human judgment;
- evidence is contradictory;
- model drift/health is degraded.

## Feedback loop

```text
AIE output
  |
ACE/reviewer decision
  |
verified outcome / correction
  |
model evaluation data
  |
controlled retraining / calibration candidate
```

The model cannot silently retrain itself into production without governance/versioning.

## Drift

AIE should distinguish:

- data drift;
- concept drift;
- label/outcome drift;
- provider/schema drift;
- calibration drift;
- performance degradation.

```text
drift detected
   |
severity / scope
   |
continue | restrict | HOLD model
   |
review / retrain / rollback
```

## Failure modes

### Model unavailable

If a mandatory AIE check is required, ACE returns HOLD/fail-closed rather than bypassing it.

### Model stale

Recalculate or HOLD according to freshness policy.

### False positive

Human/policy review can correct the decision/evidence; correction feeds model evaluation without deleting original output.

### Provider schema changes

Hold/degrade affected model until feature normalization is validated.

### Model version changes during decision replay

Use the exact historical model version for reproducibility; current re-evaluation can be recorded separately.
