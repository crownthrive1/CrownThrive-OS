## Source basis

The recovered Help Center defines the **ZK Prover Cluster** as a scalable proving service for approved circuits with verifier compatibility, replay protection and attestations. Historical papers describe proof circuits for age, accreditation, solvency, credential validity and other compliance predicates.

## Purpose

The cluster converts private witness data into a proof for an approved predicate without exposing the underlying data to the verifier/public projection.

```text
PRIVATE WITNESS / CREDENTIAL / DATA
              |
              v
        APPROVED CIRCUIT
              |
       PROVING JOB ISOLATION
              |
              v
          ZK PROVER
              |
              v
 PROOF + PUBLIC INPUTS + METADATA
              |
              v
      ZK VERIFIER / ZKX
              |
       PASS / INVALID / HOLD
```

## Non-purpose

The cluster does not:

- establish the truth of witness data merely because a proof is valid;
- decide policy/authorization;
- make all proof schemes/circuits current CHLOM standards;
- store raw private witnesses indefinitely by default;
- expose proving keys/secrets or private credentials publicly;
- imply production proving infrastructure exists for every historical circuit.

## Witness handling

Witness material is highly sensitive. Requirements include:

- minimum necessary data;
- explicit purpose;
- memory/storage isolation;
- encryption in transit/at rest where applicable;
- retention/deletion profile;
- access logs;
- no public logs with raw witness;
- provider/model/tool data-use review;
- tenant isolation.

## Replay protection

A proof valid for one challenge/action should not automatically authorize another.

```text
proof
+ action/subject binding
+ nonce/challenge
+ validity window
```

The exact replay contract belongs to the circuit/workflow profile.

## Capacity model

Proving can be computationally expensive. The cluster should expose:

- queue depth;
- estimated/observed latency;
- job size/resource class;
- worker/prover health;
- failure/retry rate;
- proof cost/resource metrics;
- capacity limits and request budgets.

Capacity limits are operational, not proof semantics.

## Multi-prover architecture

```text
PROOF ROUTER
  |
  +--> Prover Worker A
  +--> Prover Worker B
  +--> Prover Worker C
        |
       isolated jobs
```

Worker/provider identities are replaceable. A proof remains tied to circuit/version and verification contract rather than one vendor brand.

## Verification compatibility

Before returning a proof as usable:

- verifier supports circuit/version;
- verifying key/version matches;
- public-input schema matches;
- proof scheme matches;
- challenge/nonce binding valid;
- proof not expired under workflow profile.

## Credential proofs

A proof may establish a predicate such as:

```text
credential is valid
age >= threshold
jurisdiction attribute satisfies allowed set
credential issuer belongs to approved issuer set
license status satisfies predicate
```

The verifier should learn only required public information.

## Financial/solvency lineage

Historical CHLOM contemplated solvency/compliance proofs. Any current financial use requires separately validated data, circuit correctness, audit/accounting basis and professional/legal authority. A cryptographic proof does not decide whether the predicate itself is the correct regulatory/accounting test.

## Failure modes

- circuit not approved -\> reject;
- witness unavailable -\> HOLD/fail;
- proving key mismatch -\> fail;
- insufficient capacity -\> queue/HOLD;
- proof generation fails -\> no proof;
- verifier incompatibility -\> HOLD/reprove/migrate;
- nonce replay -\> reject;
- proof expired -\> regenerate/revalidate;
- witness retention breach -\> security incident.

## Threat model

- witness exfiltration;
- malicious circuit;
- poisoned proving/verifying keys;
- compromised prover worker;
- replay;
- cross-tenant witness mixing;
- side-channel leakage;
- denial of service/capacity exhaustion;
- invalid proof accepted due verifier mismatch;
- trusted-setup compromise where relevant.

## Test vectors

1. approved circuit \+ valid witness -\> proof verifies;
2. wrong witness -\> proof generation/verification fails;
3. proof for subject A replayed for B -\> reject;
4. old circuit version after retirement -\> hold/reject according to migration profile;
5. verifying key mismatch -\> invalid;
6. cluster overloaded -\> queue/HOLD, not fake proof;
7. witness not retained beyond configured period -\> retention test;
8. public logs -\> no raw witness;
9. proof valid but credential revoked after proof -\> downstream currentness policy prevents stale authorization;
10. provider/worker changes -\> proof semantics remain circuit/version based.

## Invariants

```text
proof generation != proof verification
proof valid != witness source truth automatically
proof valid != action authority
witness != public record
provider worker != proof semantics
circuit version must match verifier version
replayable proof must not create duplicate authority
```
