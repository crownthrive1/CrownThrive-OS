# CHLOM Wallet Phase B evidence

**Evidence state:** `CONTROLLED_TEST`  
**Human institutional phase:** Phase 2.99  
**Phase 3 entry:** unchanged / blocked pending the Phase 2.99 hard exit

This packet advances wallet engineering without converting test evidence into production claims.

## Stripe webhook canary

A dedicated controlled-test webhook receiver now exists behind a database runtime gate. The receiver verifies a Stripe-format HMAC signature from the exact raw body, applies timestamp tolerance, rejects `livemode: true`, enforces an event allowlist, persists a provider receipt, prevents exact provider-event replay and appends CHLOM wallet evidence without inferring entitlement.

An end-to-end canary sent the same signed synthetic event twice through the deployed Edge Function:

```yaml
first_http_status: 200
first_state: RECORDED_TEST
second_http_status: 200
second_state: DUPLICATE
result: PASS_EDGE_WEBHOOK_REPLAY_CANARY
live_event: false
money_movement: false
rights_grant: false
```

The test signing secret is synthetic and restricted. It is not a Stripe live endpoint secret.

## Provider lifecycle and out-of-order canary

The same controlled-test adapter now covers the initial subscription/refund/dispute lifecycle instead of testing payment success alone. A deliberately out-of-order five-event sequence was delivered through the deployed webhook receiver:

```yaml
unique_provider_receipts: 5
unique_wallet_events: 5
delivery_states:
  - RECORDED_TEST
  - RECORDED_TEST
  - RECORDED_TEST
  - RECORDED_TEST
  - RECORDED_TEST
exact_replay_state: DUPLICATE
out_of_order_occurred_time_preserved: true
all_fulfillment_states: HOLD
money_movement: false
rights_grant: false
result: PASS_PROVIDER_LIFECYCLE_CANARY
```

The synthetic sequence covers `invoice.paid`, `customer.subscription.created`, `customer.subscription.updated`, `charge.dispute.created`, and `charge.refunded`. The invoice was delivered before an earlier-occurring subscription event to prove CHLOM preserves provider occurrence time separately from append order instead of rewriting history to make events appear ordered.

The controlled VCTR mapping also distinguishes asynchronous Checkout success/failure, invoice payment failure, and subscription create/update/delete events. None of these provider states independently creates entitlement.

## Passkey challenge-control canary

The restricted runtime now has a one-time passkey challenge service. It generates a random challenge, persists only the digest, binds the challenge to a relying-party ID and HTTPS origin, expires it, and prevents exact replay.

```yaml
wrong_origin_state: rp_or_origin_mismatch
valid_consume_state: CONSUMED_TEST
replay_state: challenge_already_consumed
raw_challenge_persisted: false
credential_verified: false
smart_account_deployed: false
money_movement: false
result: PASS_PASSKEY_CHALLENGE_CANARY
```

This validates challenge/origin/replay control only. It deliberately does **not** claim complete WebAuthn cryptographic assertion verification, production credential enrollment, smart-account deployment or account recovery readiness.

A candidate smart-account profile remains `specified_not_deployed` with an explicit CAIP-2 testnet target, WebAuthn/passkey commitment profile, modular ERC-4337/ERC-7579 direction, disabled paymaster/modules, `broadcast=false`, and `money_movement=false`.

## Wallet experience and public projection

The source-controlled wallet shell now models one consumer-facing surface with five separate lanes: **Money, Rights, Rewards, Impact and Proof**. Its reference tests passed with:

```yaml
unified_shell_sections: 5
provider_detail_leak: false
private_evidence_leak: false

```

The shell does not create a universal value balance. Active Rights require an entitlement reference, externally settled Impact requires evidence, Rewards are not inferred to be cash, and provider internals remain hidden from the ordinary customer projection.

This is a reference experience contract, not yet a deployed customer application.

## Contract hardening and stress evidence

The four no-value Solidity reference contracts compile under the exact `solc@0.8.36` workflow. Their source invariants were tightened so that:

- entitlement revocation requires an active entitlement and nonzero reason digest;
- split-policy supersession requires both source and replacement records and rejects self-replacement;
- ThriveFund obligation creation rejects zero amount;
- external-settlement and reversal transitions require evidence digests;
- repeat invalid ThriveFund/entitlement transitions fail closed;
- Anchor Registry keeps duplicate/zero/pause/authority guards;
- no controlled-test contract exposes transfer/send/value-call/delegatecall/selfdestruct primitives.

A deterministic source-aligned state-model fuzz suite also passed:

```yaml
result: PASS_CONTRACT_MODEL_FUZZ

anchors: 3163
entitlements: 2640
split_policies: 2294
thrivefund_obligations: 2284

evm_execution: false
audit_claimed: false
```

This is meaningful invariant testing, but it is still not EVM bytecode execution, an external audit, a testnet deployment or mainnet approval.
