## Purpose

The historical Allowlist/Registry Pallet was conceived as the runtime source for determining which actors, verifiers, providers or strategies were approved to participate in sensitive CHLOM operations.

```text
CANDIDATE ACTOR / PROVIDER / STRATEGY
               |
               v
REGISTRY ENTRY
               |
        +------+------+
        |             |
     APPROVED      PROBATION
        |             |
        +------+------+
               |
             ACTIVE
               |
       SUSPEND / REVOKE
```

## Registry is not endorsement

Allowlisting means an entity is approved for a defined scope under a defined version of policy. It does not mean CrownThrive guarantees quality, solvency, legal compliance or future suitability beyond that scope.

## Probation

Probation is a bounded state in which participation may be narrowed, monitored or subject to additional conditions.

```text
APPROVED
   |
trigger / review
   |
PROBATION
   |
   +--> RESTORED
   +--> SUSPENDED
   +--> REVOKED
```

Probation should not be modeled as a hidden flag with no documented effect.

## Revocation

Revocation must propagate to dependent operations.

If a verifier is revoked:

- new verification should be blocked;
- existing assertions may require review according to their own effective rules;
- dependent systems receive updated registry state;
- historical evidence remains preserved.

If a provider/strategy is revoked:

- no new activity should be routed through it;
- existing open activity is reconciled/closed/migrated under explicit procedures;
- provider exit evidence is retained.

## Provider independence

Provider IDs never become the stable institutional identity.

```text
registry subject ID
       |
       +--> provider account alias A
       +--> provider account alias B
```

This permits provider migration without rewriting the registry's semantic identity.

## Decision flow

```text
registry entry exists?
   no -> HOLD/DENY according to operation
   |
  yes
   v
status == approved?
   no -> HOLD/DENY
   |
  yes
   v
scope covers requested operation?
   no -> DENY
   |
  yes
   v
entry/current evidence not expired?
   no -> HOLD
   |
  yes
   v
PASS registry gate
```

Registry PASS is only one gate. Other policy/rights/authority checks still apply.

## Security concerns

- stale allowlist state;
- unauthorized approval;
- provider impersonation;
- scope escalation;
- registry bypass;
- fail-open behavior when registry is unavailable;
- revoked entity cached as active;
- mass approval without evidence;
- compromised privileged registry editor.

## Failure mode: stale cache

```text
canonical registry = REVOKED
cached integration = APPROVED
        |
        v
canonical state controls
block new sensitive action
record mismatch
```

## Evidence requirements

```text

```

## Public / restricted split

Public-safe may expose approved public providers/verifiers only where disclosure is intended.

Restricted companion can hold:

- private provider lists;
- eligibility evidence;
- probation reasons;
- security findings;
- private strategy definitions;
- exploit-sensitive revocation procedures.
