## Source basis

The lost Help Center describes the **Smart Staking Engine** as class-based minimums, reward curves and severity-scaled slashing with recurrence multipliers. Historical CHLOM papers use staking for validator security and as a possible compliance bond for issuers/oracle providers. Genesis includes example staking-yield and slashing ranges.

Those values are historical examples, not current parameters.

## Non-purpose

Smart Staking does not:

- make a token/staking product live;
- guarantee APY;
- allow automatic financial punishment without adopted authority/remedy;
- make stake equal expertise or regulatory authority;
- replace identity/credential verification;
- make historical CHM/CHLOM Coin mechanics current.

## Assurance mapping

The useful modern concept is **skin-in-the-game / assurance**, which may be implemented through mechanisms other than crypto staking:

- contractual bond;
- deposit/escrow;
- insurance;
- performance reserve;
- reputation/eligibility status;
- provider guarantees;
- access privilege subject to suspension.

The mechanism must fit legal/economic context.

## Identity relationship

```text
stable participant identity
  -> role/credential
  -> participation class
  -> optional assurance/bond alias
```

Bond/wallet identity is not the institutional participant identity.

## Eligibility/currentness

A participant may be financially bonded but no longer authorized if:

- credential expired;
- role revoked;
- security status held;
- policy changed;
- provider/validator certification expired.

Stake does not override these controls.

## Reward lifecycle

```text
eligible participation
 -> measure attributable activity/performance
 -> calculate candidate reward
 -> validate economic schedule
 -> obligation
 -> execution
 -> reconciliation
```

A reward calculation is not payment authority.

## Penalty lifecycle

```text
signal/allegation
 -> evidence/case
 -> finding
 -> authorized penalty/remedy
 -> execution
 -> appeal/correction if applicable
```

This preserves due-process/remedy architecture rather than direct algorithmic seizure.

## Failure modes

- eligibility lost -\> participation held;
- bond/provider evidence unavailable -\> HOLD;
- reward schedule missing -\> no reward obligation;
- duplicate performance event -\> idempotent calculation;
- penalty evidence disputed -\> case/review;
- financial execution fails -\> unresolved obligation/remedy;
- historical APY reused publicly as current -\> documentation/governance violation.

## Threat model

- stake concentration;
- bribery/collusion;
- slash abuse;
- Sybil participants;
- wallet/identity substitution;
- double rewards;
- manipulated performance metrics;
- economic insolvency;
- misleading yield marketing;
- staking authority replacing actual professional qualification.

## Test vectors

1. historical APY example -\> labeled historical, never public promise;
2. participant has stake but expired credential -\> cannot act;
3. duplicate reward trigger -\> no double obligation;
4. violation signal without finding -\> no financial penalty;
5. authorized penalty \+ appeal -\> preserve original and appeal lineage;
6. recurrence factor changes -\> new profile/version;
7. provider account changes -\> participant identity stable;
8. simulated reward curve -\> no real payment;
9. economic authority missing -\> HOLD;
10. assurance satisfied through non-token bond -\> semantics can still map.

## Current mapping

Current CHLOM retains Smart Staking as historical mechanism-design/assurance research. Any future staking, reward, slash or financial-bond implementation requires separate legal/economic/security adoption and production evidence.
