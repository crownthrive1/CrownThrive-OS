# CHLOM Construction Gates

CHLOM uses **evidence-backed construction gates** instead of broad project-status claims. A module, platform binding, agent, algorithm, oracle, paper or release advances only when the gates applicable to its scope and target stage are independently closed.

<Warning>
  A gate definition is not a PASS. A registry entry, paper, API route, smart-contract address, migration or UI control is never sufficient by itself to promote a capability. PASS requires the evidence identified by the gate and any specialist or reserved-human approval required by its risk class.
</Warning>

## Promotion model

```text
SOURCE / RECONCILIATION
        |
        v
    SPECIFIED
        |
        | applicable construction gates
        v
    PROTOTYPE
        |
        | implementation + authority + schema
        v
       TEST
        |
        | TEVV + security + recovery + evidence
        v
      STAGED
        |
        | chaos + capacity + integrations + canary
        v
    PRODUCTION
        |
        | D3 / legal / rights / money / mainnet gates
        v
    MAINTAINED
```

The machine contract is fail-closed:

```text
Target stage
    |
resolve applicable gates
    |
load latest non-superseded result
    |
+-------------------------------+
| PASS or justified N/A?        |
| required specialists approve? |
| D3 human approval present?    |
| originator separated?         |
+-------------------------------+
          |
       ALL YES
          |
          v
      PROMOTABLE
```

`WATCH`, `FAIL`, `BLOCKED`, `HOLD`, missing evidence, missing specialist review, or missing D3 approval prevents promotion.

## Risk and authority

- **D0** — observation/read-only evidence.
- **D1** — low-risk preparation/reconciliation.
- **D2** — consequential but reversible or policy-controlled construction; independent verification is required.
- **D3** — binding rights, production money, production keys, token/mainnet activation, legal commitments or comparable reserved actions. Agent quorum cannot substitute for authorized human approval.

For D2/D3 material certifications, the originating agent may not certify its own material change. The construction-gate RPC rejects an originator/self-certifier match when the evidence packet identifies the originator.

## Machine records

The private runtime now uses three construction-gate record families:

```text
construction_gate_definitions
        |
        +--> applicability / stage / risk / specialist requirements

construction_tracks
        |
        +--> scope + current stage + target stage + owner agent

construction_gate_results
        |
        +--> append-only evaluation result + evidence digest
             + evaluator + specialists + human approval reference
```

Latest results are projected through a current-result view; source results remain append-preserved.

## MCP calls

The controlled-test construction gate contract defines:

```text
chlom.gates.snapshot
chlom.gates.dashboard
chlom.gates.record
```

`chlom.gates.snapshot` resolves the applicable gates for one scope and target stage. `chlom.gates.dashboard` resolves active construction tracks. `chlom.gates.record` appends an evidence-backed result and is subject to D2/D3 controls.

The gate recorder fails closed when:

- a D3 PASS lacks explicit human approval;
- required specialist reviews are absent;
- an identified material originator attempts to self-certify;
- an invalid disposition or scope is supplied.

## Automated gate reconciliation

Construction tracks are automatically re-evaluated on a scheduled cadence. Re-evaluation does **not** manufacture PASS results. It determines whether all required latest evidence is closed and updates the track state accordingly.

```text
hourly reconciliation
       |
       v
load active tracks
       |
       v
resolve applicable gates
       |
       v
PASS only when every required gate is closed
```

## Assigned construction agents

Every gate now has a separate primary builder/reviewer and independent verifier assignment. Recovery-sensitive gates can also name a recovery agent. Primary and verifier identities are constrained to be different.

Additional specialist agents were registered specifically to close previously missing execution domains:

- Virality Music integration;
- KJV/Sermon Toolkit integration;
- third-party creator beta;
- legal/regulatory research;
- IP/licensing review;
- finance/tax/treasury review;
- accessibility/consumer protection;
- CIE cultural governance;
- blockchain/cryptographic protocol assurance;
- tokenomics/treasury simulation;
- recovery/custody;
- independent release certification.

These agents are **not additional sovereign governance votes**. They are scoped construction/specialist workers and verifiers under the existing CrownThrive governance constitution.

## Non-negotiable promotion rule

A subsystem cannot promote itself by changing its own label. The lifecycle field is downstream of gate evidence, not a substitute for it.

```text
BUILD -> TEST -> EVIDENCE -> INDEPENDENT REVIEW -> GATES -> PROMOTE
```

No `production`, `mainnet`, `live token`, `rights cleared`, `license active`, `checkout active`, `self-healed` or equivalent label may bypass this sequence.
