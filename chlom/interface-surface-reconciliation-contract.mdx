## CHLOM Interface & Surface Reconciliation Contract

The recovered CHLOM estate contains portals, dashboards, widgets, consoles, workspaces, scorecards and other operator-facing surfaces. Those names are useful institutional evidence, but a historical screen name does not prove that a current interface exists, that its underlying service is deployed, or that a user has authority to execute the actions shown on it.

This contract defines the current public-safe successor for interface-surface reconciliation. It is intentionally narrower than a product specification and narrower than an authorization policy. Its purpose is to preserve the lineage of recovered interface concepts while binding current surfaces to the same identity, component, evidence, machine-contract and lifecycle rules used elsewhere in CHLOM.

<Warning>
  **Reference contract, not a live UI specification.** No route, frontend package, API base URL, authentication flow, response schema, widget implementation, provider permission, or production availability is established by a recovered surface name or the illustrative record below.
</Warning>

## Reconcile a surface

<Steps>
  <Step title="Resolve stable surface identity">
    Preserve canonical name, type, aliases, historical lineage, owner components, and current implementation/projection state.
  </Step>
  <Step title="Define the role and data boundary">
    Pin role classes, required scopes, data classes, purpose, public/private/restricted projection, and identity/authority dependencies.
  </Step>
  <Step title="Separate every read and write">
    Classify display reads, bounded operator reads, reversible local edits, provider writes, institutional changes, legal/rights/economic actions, and production controls independently.
  </Step>
  <Step title="Bind machine contracts">
    Attach exact API/MCP/event versions, environment, authentication, side effects, failure behavior, provider dependencies, and audit/evidence contracts.
  </Step>
  <Step title="Implement state and freshness behavior">
    Render recovered, specified, test, held, stale, denied, production, maintained, and superseded states accurately without client-side authority shortcuts.
  </Step>
  <Step title="Test denial and recovery">
    Verify restricted-data exclusion, HOLD/DENY rendering, unknown mutation handling, accessibility, provider failure, correction, and support escalation.
  </Step>
</Steps>

## Core distinction

CHLOM treats these as different objects:

```text
surface identity
!= component implementation
!= service availability
!= authenticated session
!= role or authority
!= provider write permission
!= economic activation
!= production certification
```

A dashboard may accurately display a current record without being allowed to mutate that record. A widget may expose a status without proving the underlying provider is reachable. A portal may exist in documentation while its corresponding service remains planned, controlled-test, held, or unavailable.

<Tabs>
  <Tab title="Surface identity">
    The stable institutional concept and role-facing purpose can exist before an implementation or deployment.
  </Tab>
  <Tab title="Component and service">
    Reusable UI code and backing service availability require their own versions, contracts, environments, evidence, and lifecycle state.
  </Tab>
  <Tab title="Session and authority">
    Authentication, role/relationship, provider access, and institutional authority are separate decisions; a visible control cannot collapse them.
  </Tab>
  <Tab title="Production and economics">
    Production certification and economic activation remain separate from route reachability, provider writes, and interface documentation.
  </Tab>
</Tabs>

## Canonical surface record

A current interface should resolve through a stable machine-addressable record such as:

```yaml
surface_id: ct.chlom.surface.example
canonical_name: Example Operator Surface
surface_type: portal | dashboard | widget | console | workspace
owner_component_ids: []
role_classes: []
required_scopes: []
data_classes: []
read_capabilities: []
write_capabilities: []
provider_dependencies: []
event_subscriptions: []
implementation_state: specified
public_projection_state: documented
last_verified_at: null
```

The exact registry controls current values. The documentation layer explains meaning; it does not manufacture runtime state.

The record is illustrative: empty arrays and `last_verified_at: null` are explicit unresolved fields, not production defaults.

## Composition model

Recovered screens should be reconciled into reusable interface primitives rather than rebuilt as isolated historical pages. The normalized family already described in the [Portal, Dashboard & Widget Catalog](/chlom/portal-dashboard-widget-catalog) includes identity cards, rights summaries, evidence timelines, policy-result panels, case/remedy views, integration-health panels and other shared components.

A current interface can compose those primitives only when the backing components and data contracts are themselves governed. The [Component, Pallet & Service Implementation Map](/chlom/component-pallet-service-implementation-map) distinguishes recovered architecture from cloud-first services and later adapters. The [Component & Framework Reconciliation Contract](/chlom/component-framework-reconciliation-contract) prevents a named framework, pallet or engine from being treated as deployed merely because it appears in recovered documentation.

## Identity and authority boundary

A surface may display actor, role, eligibility or organization information, but identity is not authorization. Actor binding and trust semantics are governed through the [Identity & Trust Reconciliation Contract](/chlom/identity-trust-reconciliation-contract). A visible role badge, account name or credential indicator must not become a substitute for the machine-enforced authority decision that controls the actual operation.

The interface layer therefore consumes authority decisions; it does not mint them. Any action that requires higher authority must remain blocked until the governing service produces the required decision or approval.

## Evidence and audit boundary

Interfaces may display public-safe evidence state, receipts, correction history and audit summaries, but they must preserve the private/public boundary. The [Evidence & Audit Reconciliation Contract](/chlom/evidence-audit-reconciliation-contract) governs how evidence references, hashes, receipts and audit events relate to institutional truth.

The interface should prefer stable evidence references and status summaries over embedding restricted source material. Sensitive evidence, credentials, private keys, secrets, unrestricted provider tokens and private personal data are never made public merely because a recovered dashboard once referenced them.

## Machine-contract boundary

A surface is not a machine contract. Reads, writes, webhooks, API calls, MCP tools and provider operations remain governed by the underlying interface and integration contracts. The [CHLOM Ecosystem Integrations](/chlom/ecosystem-integrations) record defines the current integration spine, while the [Registry Model](/chlom/registry-model) supplies stable identities for machine-addressable objects.

A button labeled "approve", "publish", "pay", "issue", "revoke", "settle" or similar does not itself create permission. The interface must call an authorized service and render its result. If the service returns HOLD or DENY, the surface must preserve that result rather than bypass it with client-side state.

## Read and write separation

Each surface must explicitly distinguish:

- display-only reads;
- bounded operator reads;
- reversible local edits;
- provider writes;
- institutional state changes;
- legal, rights or economic actions;
- production-control actions.

A current interface can be production-visible while a particular write path remains disabled. Conversely, an authenticated provider write may exist in a controlled environment without making the entire interface production-certified.

## State and freshness

Interface documentation should use the same state discipline as the rest of CHLOM:

`recovered -> reconciled -> specified -> prototype -> test -> controlled_pilot -> production -> maintained -> superseded`

Each transition requires evidence. Screenshots, historical wireframes, code stubs and recovered titles are architecture evidence; they are not sufficient production proof on their own.

Current-vs-target interpretation should follow [Source Reconciliation and Authority](/chlom/source-reconciliation), and any Phase 3 implication remains subordinate to the [Phase 3 Readiness Gate](/technology/phase-3-readiness-gate).

## Public-safe interface rules

Public documentation may describe:

- the purpose of a surface;
- the canonical surface identity;
- supported role classes at a high level;
- public-safe read capabilities;
- implementation state when verified;
- related components and integrations;
- public-safe event or status semantics;
- known holds and unresolved dependencies.

Public documentation must not expose secrets, private evidence, unrestricted credentials, hidden provider identifiers, private customer data, or internal-only security material.

## No authority expansion

This contract does not activate any portal, provider write, payment, payout, settlement, license, rights determination, legal decision, credential, identity proof, production deployment or economic action. It provides a current successor for safe interface-surface lineage and machine qualification only.

Terminal disposition of recovered interface titles remains pending the governed parent-certification process. Phase 3 remains blocked until the independent Phase 2.99 hard-exit gate passes.

## Errors, testing, and support boundary

This page defines no shared UI error codes, API retries, cache policy, session lifetime, optimistic-update behavior, or compensation mechanism. An unknown role, authority, provider state, evidence state, data class, freshness timestamp, or mutation outcome must fail closed and preserve the last known safe record; the client must not manufacture success.

Use the [API endpoint discovery workflow](/developers/api-endpoint-discovery-and-adapter-registry) when the backing interface contract is missing and the [support request workflow](/workflows/support-request) for identity, permission, data, evidence, or current-state conflicts.
