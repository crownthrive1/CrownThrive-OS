## Pipeline objective

Continuously test new code, policy, model, validator/oracle configuration and recovered-state changes against known scenarios and invariants before those changes can influence governed licensing behavior.

## Pipeline topology

```text
CHANGE / TIMER / INCIDENT / NEW EVIDENCE
              |
          trigger run
              |
      freeze exact inputs
              |
      select scenario packs
              |
   replay + fault injection
              |
    invariant evaluation
              |
 policy/model/validator metrics
              |
    compare prior baseline
              |
   PASS | WARN | BLOCK/HOLD
              |
 evidence packet + release feedback
```

## Trigger classes

A simulation run may be triggered by:

- code/runtime change;
- policy pack update;
- model update;
- oracle/validator profile change;
- bridge configuration change;
- schema migration;
- incident/correction;
- scheduled drift assurance;
- newly recovered historical requirement entering current implementation review.

## Exact-input freeze

Every run needs exact refs for:

```yaml
run_inputs:
  code_commit: required
  configuration_version: required
  policy_versions: []
  model_versions: []
  scenario_pack_versions: []
  oracle_profiles: []
  validator_profiles: []
  schema_versions: []
  seed_or_randomness_ref: optional
```

Without reproducible inputs, a green simulation cannot be treated as durable evidence.

## Scenario selection

Run baseline happy paths, negative/authority tests, cross-layer failure injection, regression cases from prior incidents, edge cases and policy/model-specific test packs.

## Differential comparison

Compare the candidate against the last accepted baseline:

```text
which decisions changed?
which invariants changed?
which HOLD/DENY rates changed?
which rights/authority paths changed?
which evidence dependencies changed?
```

Any unexplained authority expansion is release-blocking.

## Drift assurance

Scheduled simulations can replay representative scenarios against current models/data providers to detect decision drift even when code has not changed.

## Validator/oracle degradation tests

Periodically simulate partial outage, stale observations, conflicting signers and compromised/ineligible members to verify quorum/HOLD behavior.

## Result states

```text
PASS  = required invariants and acceptance criteria satisfied
WARN  = non-blocking variance requiring evidence/review
BLOCK/HOLD = material invariant, authority, security or unexplained behavior failure
```

## DAIL/evidence integration

Material assurance runs should create or reference an institutional evidence record containing exact inputs, results, deviations and release linkage. Large raw test output may remain outside DAIL with integrity references.

## No automatic promotion

```text
continuous simulation PASS
        !=
automatic production deployment
```

Release authority remains a separate governed gate.
