## Purpose

The historical title establishes that TLaaS had a dedicated UI/wireframe artifact rather than existing only as backend service prose. This reconstruction preserves the workflow and information architecture supported by related CHLOM licensing sources without fabricating pixel-perfect lost screens.

- licensor/issuer;

- validator/assurance role in historical architecture;

Current roles must be assigned through institutional authority rather than inferred from wallet possession or provider login.

## Screen 5 — Review / Approval

The reviewer sees:

- requested action;
- source-rights evidence state;
- issuer-authority state;
- applicant/holder eligibility;
- applicable policy versions;
- conflicts/exclusivity;
- economic schedule version;
- evidence freshness;
- recommended or machine-derived signals clearly labeled as non-authoritative.

Actions:

```text
PASS / approve where role permits
HOLD / request evidence
DENY / reject within authority
ESCALATE / route to governed review
```

## Screen 6 — Evidence panel

Public-safe UI exposes references/status, not unrestricted private evidence.

```text
Evidence item

```

## Screen 7 — Lifecycle actions

Only authorized actions render as enabled:

- renew;
- amend;
- request transfer;
- approve transfer;
- request sublicense;
- suspend;
- revoke;
- terminate;
- restore/reactivate where policy permits;
- migrate provider representation.

Disabled controls should explain missing authority or prerequisite rather than silently disappear where feasible.

## Screen 8 — LEX handoff

A DLA can be proposed for LEX only after a rights/transferability check.

```text
DLA
 -> listing eligibility
 -> offer terms
 -> counterparty eligibility
 -> agreement/economic schedule
 -> settlement/entitlement
```

The UI must clearly distinguish:

```text
LICENSE STATE
MARKETPLACE LISTING STATE
PAYMENT STATE
ENTITLEMENT STATE
```

## Status language

Use explicit state labels:

```text
CANDIDATE
REVIEW
HOLD
ACTIVE
SUSPENDED
EXPIRED
REVOKED
TERMINATED
SUPERSEDED
```

Never use vague success language when an operation is merely queued or provider-side only.

## Token/provider representation panel

Historical TLaaS may show token/NFT/SBT representation. Current UI treats that as an adapter:

```text
Canonical DLA: DLA-123
Provider representation: chain/provider opaque ID
Representation state: active/migrated/retired/held
```

## Trust Layer separation

If a Trust Layer as a Service verification result appears in this UI, it should be labeled as evidence/verification input, not as the licensing service itself.

## Accessibility

The current reconstruction requires:

- semantic headings;
- keyboard operability;
- non-color-only status signaling;
- clear error text;
- focus management for dialogs;
- readable tables and timelines;
- evidence/privacy labels understandable without technical jargon.

## Security UX

- destructive actions require explicit confirmation;
- revocation/suspension shows scope and effect;
- issuer-authority changes show source basis;
- elevated operations expose audit consequences;
- secrets are redacted;
- session/tenant identity is visible;
- environment/sandbox is clearly differentiated from production.

## Failure-state UX

Examples:

```text
Rights unresolved -> HOLD banner + missing evidence list
Issuer unauthorized -> DENY + authority basis
Provider unavailable -> retry/queued, canonical state unchanged
Policy conflict -> HOLD + conflicting versions
Payment success but entitlement incomplete -> reconciliation state
Stale verification -> revalidation required
```
