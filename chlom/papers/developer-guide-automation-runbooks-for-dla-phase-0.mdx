## Operational principle

Automation may perform repetitive licensing work only inside explicit authority and deterministic safety gates.

```text
AUTOMATION MAY OPTIMIZE EXECUTION
AUTOMATION MAY NOT MANUFACTURE AUTHORITY
```

## Runbook family

This reconstruction preserves the operational domains implied by historical DLA source architecture:

- candidate intake;
- eligibility/evidence refresh;
- issuance/activation;
- renewal/expiry;
- transfer/sublicense validation;
- suspension/revocation;
- dependency/oracle failure;
- duplicate/idempotency recovery;
- correction/supersession;
- manual/governed review escalation.

## Runbook 1 — Candidate intake

```text
receive request
 -> validate request envelope
 -> resolve identity
 -> resolve source rights / issuer authority
 -> create candidate version
 -> resolve policies/evidence
 -> evaluate
 -> PASS | HOLD | DENY
```

Never activate on malformed or incomplete input.

## Runbook 2 — Evidence refresh

```text
scheduled/event trigger
 -> identify expiring/stale evidence
 -> refresh from authorized source
 -> compare prior/current state
 -> no material change: record refresh
 -> material conflict: HOLD affected action/object
 -> route review
```

## Runbook 3 — Renewal

Renewal requires current license state, current issuer authority, current source rights and current holder predicates. Payment auto-renewal alone is not licensing renewal.

## Runbook 4 — Expiry

When a hard expiry condition is reached, mark or project the DLA state according to the governing term profile and create a DAIL event. Do not delete the historical record.

## Runbook 5 — Transfer/sublicense

```text
requested rights
 <= active DLA transfer/sublicense ceiling
 <= issuer/source-rights ceiling
```

Then evaluate recipient eligibility, territory/term, approval requirements and settlement/entitlement dependencies.

## Runbook 6 — Suspension/revocation

Use `SAFE_HOLD`/suspension for unresolved or reversible conditions where the policy permits. Use revocation/termination only with appropriate authority/evidence.

## Runbook 7 — Dependency failure

```text
provider/oracle unavailable
      |
can decision be safely made from current authoritative evidence?
   /     \
 yes      no
 |        |
continue HOLD / retry / review
```

Never treat timeout as PASS.

## Runbook 8 — Retry/idempotency

Every externally retried state-changing action needs an idempotency key. A retry must not create a second license, payment obligation or revocation event.

## Runbook 9 — Correction/supersession

Incorrect institutional state is corrected by appending a superseding version/event with reason and evidence rather than deleting history.

## Runbook 10 — Human/governed escalation

Escalate when:

- rights are disputed;
- evidence conflicts;
- policy returns HOLD requiring judgment;
- override/remedy authority is needed;
- a high-impact correction is proposed;
- automation encounters an undefined state transition.

## Rollback/compensation

Where a write is reversible, automate rollback only if the compensation path is preauthorized and tested. Otherwise HOLD and escalate.
