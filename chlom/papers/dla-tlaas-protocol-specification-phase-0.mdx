## Source-supported service relationship

Related source bodies establish a general architecture in which external applications can access licensing/compliance capability through services/APIs rather than implementing the full protocol themselves.

Historical licensing-service responsibilities include:

- submit a license application/request;
- verify identity/credentials;
- evaluate license prerequisites;
- issue/manage tokenized or machine-readable license records;
- verify license state;
- renew/amend/revoke according to authority;
- expose application/API integration points;
- route exchange or downstream entitlement checks.

## Protocol preconditions

A service request must not bypass:

- identity resolution;
- source-rights/issuer authority;
- license scope;
- required policies;
- required evidence freshness;
- action-specific authority;
- downstream settlement/entitlement reconciliation.

## Tokenized Licensing lineage

The Technical Blueprint explicitly describes **Tokenized Licensing as a Service** as an approach for organizations/platforms to issue and manage licenses through CHLOM infrastructure, smart contracts and APIs.

Current record: [Tokenized Licensing as a Service](/chlom/systems/tokenized-licensing-as-a-service).

## Trust Layer lineage

The Grand Prospectus separately defines **Trust Layer as a Service** as an integration/service delivery layer that abstracts CHLOM capabilities through APIs/SDKs and supporting infrastructure.

Current historical/service record: [Trust Layer as a Service](/chlom/systems/trust-layer-as-a-service).

## Protocol response semantics

Current-safe service responses should distinguish:

```text
AUTHORIZED / PASS
HELD / NEEDS REVIEW OR EVIDENCE
DENIED
UNKNOWN / UNRESOLVED
```

Unknown cannot be silently coerced into PASS.
