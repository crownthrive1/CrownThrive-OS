## Issuance objective

```text
REQUEST
  |
resolve identity
  |
resolve source rights
  |
resolve issuer authority
  |
validate license profile / eligibility
  |
policy + evidence + approval
  |
PASS -> activate canonical DLA
  |
optional token/provider representation
  |
DAIL receipt
```

## Preconditions

A material issuance action should verify:

- actor identity;
- issuer authority for the exact asset/catalog;
- source-right evidence;
- license class/profile;
- holder/applicant identity where required;
- credential/eligibility predicates;
- territory and term validity;
- exclusivity/conflict constraints;
- policy versions;
- evidence freshness;
- agreement/consent requirements;
- economic schedule where applicable.

## Semantic issuance function

The historical function name is not recovered. A provider-neutral semantic contract can be represented as:

```text
issueLicense(request)
  -> validate request identity
  -> validate issuer authority
  -> validate source-right ceiling
  -> evaluate policy/evidence
  -> create/activate DLA version
  -> bind optional representation
  -> emit institutional events
```

This is pseudocode, not recovered Solidity.

## Rights ceiling validation

```text
requested permissions
  <= issuer authority ceiling
  <= licensable source rights
```

Violation is DENY, not a warning.

## Three-valued evaluation

```text
PASS -> may continue within authority
HOLD -> missing/conflicting/stale evidence; no issuance
DENY -> action prohibited
```

The historical code-oriented title does not justify fail-open behavior.

## Provider/token mint ordering

```text
canonical DLA activation
 -> optional provider representation
```

If business/profile rules require the provider representation to be part of the same externally visible activation, orchestration must compensate or HOLD when the provider step fails. Provider mint success alone never creates an institutional license.

## Renewal objective

Renewal is not a blind date extension. It revalidates the conditions that remain material at renewal time.

```text
current DLA
 + source rights current
 + issuer authority current
 + holder eligibility current where required
 + policy/evidence current
 + agreement/economic conditions satisfied
 -> renewal candidate
```

## Renewal types

A profile may model renewal as:

- new DLA version under stable DLA identity;
- distinct replacement DLA with explicit predecessor;
- term extension amendment;
- reissuance after expiry.

The governing profile/agreement decides; the implementation must not assume one universal pattern.

## Renewal validation

Reject or HOLD when:

- source rights expired;
- issuer delegation expired;
- license is non-renewable;
- holder no longer meets required credentials;
- conflicting exclusive right exists;
- required payment/agreement evidence unresolved;
- material policy changed and new requirements are unsatisfied.

## Idempotency

Repeated provider/API requests must not issue duplicate canonical licenses.

```text
same idempotency key + same governed request
 -> same canonical result
```

Conflicting reuse of an idempotency key is an error/HOLD.

## Payment interaction

Historical source examples discuss license fees and token payments. Current ordering remains:

```text
payment authorization/capture
   != license authority
```

If payment is required before activation, failure to activate after payment triggers reconciliation/refund/compensation rather than a fabricated license.

## Test vectors

1. valid issuance -> one canonical active DLA;
2. unauthorized issuer -> DENY;
3. stale credential -> HOLD;
4. requested right exceeds source -> DENY;
5. duplicate issuance retry -> same DLA/result;
6. provider mint succeeds but canonical activation fails -> no institutional license;
7. renewal after source-right expiry -> DENY/HOLD;
8. renewal with new policy unmet -> HOLD/DENY;
9. provider representation unavailable -> canonical/provider state reconciled per profile;
10. correction -> prior event retained, new state appended.
