## Developer objective

This guide reconstructs the architectural problem implied by the lost title: how a CHLOM licensing decision or governed rights object can be referenced across external networks without allowing a foreign chain, bridge, wrapped token or provider to manufacture rights.

## Source-grounded lineage

Recovered CHLOM technical sources discuss interoperability with Ethereum, Polkadot/XCM, Cosmos-style networks, mirrored/wrapped assets, cross-chain identity proofs and compliant transfers. Those are research/target architecture concepts unless current deployment evidence exists.

## Current interoperability invariant

```text
foreign representation
      !=
source rights
      !=
issuer authority
      !=
active Dynamic Licensing Asset
```

Cross-chain transport can carry evidence or a representation; it cannot expand the underlying grant.

## Export rule

Only export claims that the local authority is permitted to attest. A bridge service may attest to observed state; it does not become a licensor merely by operating the bridge.

## Import rule

Imported state is evidence. It must be evaluated against current CHLOM policy before becoming an entitlement or licensing state.

```text
verified foreign claim
      +
current policy
      +
current rights/authority mapping
      =
PASS | HOLD | DENY
```

## Identity portability

DID/credential proofs can be referenced across environments where verification methods and issuer trust are recognized. Identity portability does not imply license portability automatically.

## Asset wrapping/mirroring

A wrapped or mirrored token representing an asset must retain a link to the canonical source and cannot claim broader rights than the source object.

```text
wrapped_rights <= canonical_rights
```

## Replay/double-use controls

Cross-chain designs need controls for duplicate claims, replayed proofs, stale finality, reorgs, already-consumed entitlements and conflicting source updates.

## Revocation propagation

When canonical licensing/credential state becomes revoked, expired or corrected, dependent cross-chain projections should be re-evaluated and superseded/held according to policy.

## Failure modes

HOLD or reject when:

- source network cannot be verified;
- finality is insufficient;
- proof format is unsupported;
- source claim conflicts with institutional rights evidence;
- imported data is stale;
- bridge provider is unavailable and current state cannot be proven;
- canonical DLA has been superseded or revoked.
