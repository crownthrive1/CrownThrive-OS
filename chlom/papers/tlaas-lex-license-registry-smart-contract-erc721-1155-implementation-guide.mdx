## Core correction

```text
CANONICAL DLA
   != ERC-721 token
   != ERC-1155 token
```

ERC standards can represent selected license state, but they cannot establish source rights or issuer authority by themselves.

## When ERC-721 fits the historical design

A unique non-fungible representation may be appropriate where one token maps to one unique license instance or title-like object.

```text
DLA-123 <-> tokenId 987
```

The binding remains an adapter relationship.

## When ERC-1155 fits the historical design

A multi-token representation may be useful for license classes, seats, editions, bundles or multiple token types under one contract, subject to rights semantics.

```text
one token standard supports many ids
   != rights are fungible automatically
```

The legal/licensing meaning comes from the DLA and source agreement, not the token standard.

## Mint/issuance sequence

```text
source rights resolved
 -> issuer authority resolved
 -> policy/approval PASS
 -> canonical DLA active
 -> representation requested
 -> contract/provider mint
 -> binding readback
 -> DAIL receipt
```

A mint failure does not erase an already valid canonical DLA; the representation enters retry/HOLD according to profile.

A mint success without canonical DLA activation does not produce a valid institutional license.

## Transfer hooks

Historical LEX research expects smart contracts to prevent disallowed transfers. Current-safe enforcement checks canonical terms before permitting the provider transfer.

```text
transfer requested
 -> DLA active?
 -> transferable?
 -> actor authorized?
 -> recipient eligible?
 -> territory/term valid?
 -> required approval PASS?
 -> provider transfer
 -> canonical transfer reconciliation
```

## Non-transferable credentials

Historical SBT concepts can be represented through non-transferability rules or other credential adapters. The registry must not assume every credential is transferable merely because the underlying token standard supports transfer.

## Revocation and suspension

A provider representation may be frozen, burned or marked invalid depending on adapter capabilities, but canonical lifecycle state remains authoritative.

```text
DLA revoked
 -> provider adapter propagation
 -> readback
 -> discrepancy HOLD if propagation fails
```

## Upgrade/migration

A token contract can be replaced without changing the identity of the canonical DLA.

```text
old representation
 -> migrate / retire
 -> new representation
canonical DLA identity preserved
```

Provider migration must preserve chain-of-title and event evidence.

## Failure modes

- token minted before rights approval -> invalid representation / HOLD;
- provider holder differs from canonical holder -> reconciliation HOLD;
- transfer succeeds where DLA forbids transfer -> incident/correction path;
- metadata digest mismatch -> HOLD;
- provider contract inaccessible -> canonical DLA remains, adapter degraded;
- burn occurs without canonical revocation -> do not infer license revocation automatically.
