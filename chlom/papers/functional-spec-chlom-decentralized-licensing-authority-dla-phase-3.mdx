## Recovery boundary

## Historical functional objective

The historical DLA was intended to provide a governed license lifecycle capable of:

1. accepting a license/application request;
2. resolving participant identity and credentials;
3. evaluating eligibility and compliance conditions;
4. creating a license record/token when approved;
5. exposing license status for verification;
6. enforcing transfer/use restrictions;
7. supporting renewal, amendment, suspension and revocation;
8. recording evidence and lifecycle events;
9. interoperating with LEX, oracles, compliance logic and governance.

## Core functional requirements

### FR-01 — Stable license identity

Every governed license object needs a stable identifier and explicit version/state.

### FR-02 — Source authority resolution

A license cannot be issued solely because an applicant asks for one. The historical authority concept is normalized today to a source-rights-backed issuer authority.

### FR-03 — Identity resolution

The subject and issuer must resolve to governed identity records. Historical source material connects DLA to DID, SBT/credential and Fingerprint constructs.

### FR-04 — Eligibility evaluation

Required credentials, policy conditions and other prerequisites must be evaluable before issuance.

### FR-05 — Approval disposition

The decision surface should support at minimum:

```text
PASS / APPROVE
HOLD / REVIEW
DENY
```

Current CHLOM does not equate model confidence with authority.

### FR-06 — Issuance

Approved requests create an active license object with explicit scope, term and restrictions.

### FR-07 — Verification

A relying system must be able to determine whether a license is current and usable without trusting an unauthenticated screenshot or provider claim.

### FR-08 — Lifecycle transitions

```text
candidate -> review -> active
active -> amended/renewed
active -> held/suspended
active -> expired
active -> revoked/terminated
```

### FR-09 — Transfer/sublicense control

Transfer and sublicensing must be explicit, never assumed from possession of a token or record.

### FR-10 — Hierarchical licensing

Historical source material supports parent-child/sub-license relationships. Child rights cannot exceed parent/source rights.

### FR-11 — Revocation and suspension

The system must support reversible suspension where appropriate and irreversible/terminal revocation where the governing source permits it.

### FR-12 — Audit events

Each material lifecycle change needs attributable evidence/event history.

```text

child_rights <= parent_rights

```

## Required evidence gates

A current implementation should fail closed when material facts are unresolved:

- source rights unknown;
- issuer authority unknown;
- identity unresolved;
- mandatory policy result unresolved;
- license version/status ambiguous;
- required evidence stale or missing.

## Nonfunctional expectations inherited from source architecture

Related sources emphasize auditability, privacy-preserving verification, modularity, interoperability and automation. These are architectural goals, not proof of current production performance or SLA.
