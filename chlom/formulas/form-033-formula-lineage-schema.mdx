# FORM-033 — Formula Lineage Schema

## Formula identity

```yaml
formula_id: FORM-033
classification: metadata_schema
origin: CHLOM mathematical-model governance
adopted_as_documentation_contract: yes
```

Every CHLOM equation or quantitative model must be identifiable independently of the paper or article that contains it. FORM-033 defines the minimum provenance record.

## Example lineage pattern

```yaml
stable_id: ct.chlom.formula.supply.net-change.v1
name: Net Supply Change
origin: Genesis Volume
classification: historical_source_formula
adopted: false
```

This structure prevents a formula from losing its historical status when copied into a modern page.

## Classification semantics

**historical\_source\_formula** means explicitly recovered from source. **historical\_source\_example** is arithmetic/scenario material from source. **derived\_model** is a reconstruction/engineering abstraction added later. **adopted\_rule** requires explicit institutional authority. **production\_parameter** requires deployed/configuration evidence in addition to adoption.

## Visibility and vaulting

If a source marks the exact method proprietary or trade-secret, the public lineage record can still expose formula existence, purpose, safe inputs/outputs and vault binding while withholding the restricted expression or calibration.

## Supersession

A new formula version never rewrites the source history. `supersedes` and compatibility notes explain which model is effective for current use.

## Tests and implementation

A formula registry should distinguish a paper equation from implemented code. Test-vector and implementation refs remain empty until such assets actually exist and are verified.

## DAIL evidence

Adoption, retirement, supersession and production activation are separate events linked to the stable formula ID/version.

## Versioning

This schema itself is versioned. Older formula records remain parseable or migrate through explicit mapping.
