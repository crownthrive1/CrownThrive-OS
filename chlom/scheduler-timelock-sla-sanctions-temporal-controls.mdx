## Why time is a compliance input

A policy decision can be correct at one moment and invalid later. CHLOM therefore needs to model not only **what** is allowed, but **when** it is allowed, how long evidence remains valid, when a decision can execute, and what happens if a required external source becomes stale.

```text
AUTHORITY + EVIDENCE + POLICY + TIME
                |
                v
        EFFECTIVE DECISION
```

## Scheduler

A Scheduler is the mechanism that records **an authorized future action** and the conditions under which it may become eligible to run.

A schedule should identify:

- schedule ID;
- action type;
- target stable ID;
- originating decision/approval;
- earliest execution time;
- latest execution/expiry time where relevant;
- revalidation requirements;
- retry policy;
- cancellation authority;
- idempotency key;
- current state.

```text
AUTHORIZED
    |
    v
SCHEDULED
    |
    +--> CANCELED
    +--> EXPIRED
    |
    v
DUE
    |
    v
REVALIDATE
    |
 +--+----------+
 |             |
PASS        HOLD/DENY
 |             |
 v             v
EXECUTE      no side effect
```

Scheduling does not freeze reality. A future action must be revalidated if rights, credentials, sanctions state, policy, funding or authority could have changed.

## Timelock

Historical governance designs use delayed execution to give stakeholders time to observe or challenge consequential changes.

Modern timelock invariant:

```text
proposal / approved change
          |
          v
      TIMELOCKED
          |
    challenge window
          |
   +------+------+
   |             |
 no issue      hold/cancel
   |             |
   v             v
execute      review/remedy
```

A timelock is not only a delay; it is a **control window** between authorization and irreversible effect.

Potential uses include:

- major policy changes;
- governance/configuration changes;
- high-impact license revocations;
- treasury configuration changes;
- provider migrations;
- key/authority rotations;
- public-chain adapter upgrades.

Exact classes and durations require adopted policy.

## Sanctions Cache

A sanctions or restricted-party check is highly time-sensitive. The historical module name **Sanctions Cache** reflects the need to use external sanctions data efficiently without treating cached data as permanently valid.

```text
Authoritative sanctions source
          |
          v
fetch / verify / normalize
          |
          v
+---------+----------+
| Sanctions Cache    |
| version + fetched  |
| at + fresh_until   |
+---------+----------+
          |
          v
policy check
```

## Cache freshness rule

```text
cached result exists
       |
       v
current_time <= fresh_until ?
       |
   +---+---+
   |       |
  YES     NO
   |       |
   v       v
usable   refresh required
          |
          +--> unavailable -> HOLD / fail closed
```

A cached `not sanctioned` result cannot be used indefinitely.

## Time semantics that must not be conflated

```text
observed_at    = when external reality was observed
recorded_at    = when CHLOM recorded it
effective_from = when a rule/decision begins applying
expires_at     = when it stops being valid
execute_at     = when a scheduled side effect becomes due
fresh_until    = latest time evidence is acceptable
```

These timestamps answer different questions.

## Revalidation before execution

A scheduled or timelocked operation should re-check any dynamic prerequisite.

```text
approval at T0
     |
     +-- rights valid at T0
     +-- credential valid at T0
     +-- sanctions clear at T0
     |
wait
     |
execution at T1
     |
     +-- rights still valid?
     +-- credential still valid?
     +-- sanctions still clear?
     +-- policy version compatible?
     +-- authority still active?
```

If any required dynamic condition fails, execution does not proceed simply because an old approval exists.

## Failure conditions

Fail closed or HOLD when:

- the clock/effective period cannot be resolved reliably;
- a scheduled action lost its authority before execution;
- required evidence expired;
- sanctions data is stale and cannot be refreshed;
- the action already executed but idempotency cannot be proven;
- a timelock was bypassed;
- an SLA breach requires a remedy not yet adjudicated;
- retry behavior could duplicate an irreversible side effect.
