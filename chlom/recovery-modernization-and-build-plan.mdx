## CHLOM Recovery, Modernization and Build Plan

CHLOM is not being reduced to the currently easiest modules. The long-term directive is to recover the foundational architecture, preserve its IP lineage, modernize it against current technical capabilities, and implement it in controlled phases.

## Component rule

Every CHLOM component receives its own stable component ID, source lineage, current specification, version, implementation state, security classification, test state, deployment state and dependencies.

## Core recovery/build families

- Rights Registry and Evidence Model
- Rules / Policy Registry
- Roles / Authority
- Revenue / Allocation
- Records / DAIL
- Remedies / Case Service
- DLA lifecycle
- LEX licensing exchange
- DID / identity relationships
- ZK / privacy-preserving verification research and implementation where justified
- treasury/allocation logic
- oracle and external-evidence interfaces
- token/programmable-value research and any future implementation
- governance / approval / appeals
- audit and observability
- CrownThrive IO / MCP adapters

## State model

A component may be:

`historical-source → recovered → reconciled → specified → prototyped → tested → staged → production → maintained → superseded`

Research families such as ZK, token, decentralized settlement or oracle models may remain `recovered/research` until an ADR justifies implementation.

## Modernization rule

Historical implementation choices are not sacred. Preserve the underlying institutional function and IP, then choose current architecture based on security, cost, maintainability, portability, legal constraints and actual CrownThrive needs.

Examples:

- blockchain may be unnecessary for a current internal audit event that an append-only signed ledger can satisfy;
- decentralized identity research can inform a modern identity/credential architecture without requiring immediate on-chain DID deployment;
- token research may remain dormant until there is a lawful, economically justified use case.

## Build order

### Phase 3A — institutional core

DAIL/event model, Approval Service, Rights Registry, source/evidence IDs, authority and versioning.

### Phase 3B — licensing and rules

DLA, Rules Registry, Roles/Authority, policy evaluation, evidence-linked approvals.

### Phase 3C — economics and remedies

Revenue rules, allocations, cases, holds, appeals, correction/reinstatement.

### Phase 3D — exchange and identity expansion

LEX, richer identity/DID-compatible credentials, external evidence/oracle adapters.

### Phase 3E — advanced/privacy/decentralized research activation

ZK, programmable settlement, token or decentralized-governance components only where justified and approved.

## GitHub implementation principle

Executable CHLOM services should be built in version-controlled repositories with schemas, migrations, tests, fixtures, CI, ADRs, threat models and reproducible deployments. PentaDocs remains the institutional knowledge projection, not the runtime database. Mintlify is the current third-party rendering/hosting provider for that projection.

## Acceptance rule

No recovered module becomes `production` because a document describes it. Production requires executable implementation, tests, deployment evidence, monitoring, rollback/recovery capability and the required authority.
