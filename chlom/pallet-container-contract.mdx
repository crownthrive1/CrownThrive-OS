## Purpose

A **CHLOM pallet container** is the current cloud/API-era packaging boundary for a governed capability bundle. It is not merely a folder, UI group, microservice, pricing package, or historical Substrate runtime pallet.

The container exists so a deployable CHLOM capability can carry its complete institutional contract with it: identity, authority, policies, data, interfaces, operating procedures, economic rules, evidence, metrics, release state and rollback behavior.

```text
                     CHLOM PALLET CONTAINER

+------------------------------------------------------------------+
| Identity & Authority                                              |
| Who owns, operates, delegates, approves, reviews and supports it  |
+------------------------------------------------------------------+
| Capabilities                                                      |
| Modules, services, platforms, agents, workflows and user actions  |
+------------------------------------------------------------------+
| Policies & Rules                                                  |
| Institutional, corridor, tenant, privacy, asset, event and risk   |
+------------------------------------------------------------------+
| Data Contracts                                                    |
| IDs, schemas, events, retention, visibility and export rules      |
+------------------------------------------------------------------+
| Integrations                                                      |
| APIs, webhooks, MCP, batches, provider adapters and exit paths     |
+------------------------------------------------------------------+
| Commercial / Economic Model                                       |
| Offers, fees, splits, commissions, refunds, clawbacks, authority   |
+------------------------------------------------------------------+
| Operating Procedures                                              |
| Onboard, approve, dispute, incident, reconcile, offboard, restore  |
+------------------------------------------------------------------+
| Metrics & Evidence                                                 |
| Activation, conversion, compliance, revenue, health, DAIL receipts|
+------------------------------------------------------------------+
| Release / Security / Recovery                                      |
| Maturity, gates, rollback, compensation, provider exit, readback   |
+------------------------------------------------------------------+
```

## Canonical distinction

CHLOM has used **pallet** in two materially different eras.

| Namespace | Meaning | Current treatment |
| --- | --- | --- |
| `current_capability_pallet` | Cloud/API deployable bundle of institutional capabilities and integrations | Current product/architecture packaging model |
| `historical_runtime_pallet` | Substrate runtime module containing on-chain logic | Historical/target research unless separately implemented and evidenced |

The names may overlap. The namespace must not.

```text
P-03 Rights & Licensing
          !=
Historical DLA Runtime Pallet

P-11 Capital, Revenue & Settlement
          !=
Historical Treasury Pallet
```

A current capability pallet may **contain or map to** a historical runtime concept without inheriting its historical deployment assumptions.

## Container identity

Every pallet container must have a stable identifier.

```yaml
pallet_id: P-XX
canonical_name: string
semantic_version: semver
container_namespace: current_capability_pallet
owner: institutional owner
steward: operating steward
maturity: source-recovered|reconciled|specified|prototype|test|staged|production|maintained|superseded
priority: foundation|pilot|later-pilot|research|deferred
visibility: public|internal|restricted|vault-bound
```

Renaming a display label does not change the stable pallet ID.

## Authority model

A pallet container never manufactures authority.

```text
CAPABILITY EXISTS
      |
      v
AUTHORITY RESOLVED? ---- no ----> HOLD / DENY
      |
     yes
      v
POLICY APPLICABLE?
      |
      v
EVIDENCE SUFFICIENT?
      |
      v
ACTION WITHIN DELEGATION?
      |
      +---- no ----> HUMAN / GOVERNED ESCALATION
      |
     yes
      v
EXECUTE -> READBACK -> DAIL -> RECONCILE
```

Container authority must be derived from adopted institutional roles, delegated scopes, policy versions and exact action class. A provider credential, API success response, AI recommendation or historical paper does not grant authority by itself.

## Required container sections

Every pallet container must define the following sections. Missing required sections are explicit gaps, not implied defaults.

### Identity

Identity includes:

- tenant and organization scope;
- institutional owner;
- operational steward;
- human and agent roles;
- delegated authority ceilings;
- verification requirements;
- consent requirements;
- support and escalation owners;
- stable object and participant IDs.

### Capabilities

Capabilities enumerate what the pallet is allowed to provide.

Each capability requires:

```yaml
capability_id: stable ID
name: display name
side_effect_class: read|write|economic|rights|security|external
required_authority: authority class
inputs: schema references
outputs: schema references
failure_states: [PASS, HOLD, DENY, ERROR]
evidence_receipt: required|optional
```

### Policies

A pallet may be subject to multiple policy layers simultaneously.

```text
Institutional Policy
       |
Corridor / Ecosystem Policy
       |
Pallet Policy
       |
Tenant / Organization Policy
       |
Asset / Event Policy
       |
Jurisdiction / Professional Gate when applicable
```

Conflicts are resolved through explicit precedence and HOLD behavior, not silent last-write-wins logic.

### Data contracts

The container must identify:

- canonical IDs;
- required fields;
- schema versions;
- event names;
- DAIL envelope requirements;
- retention and deletion constraints;
- classification and visibility;
- public projection rules;
- export/import formats;
- provider mapping and alias rules;
- lineage and supersession.

### Integrations

Every external dependency is an adapter, not sovereign truth.

```yaml
integration_id: stable ID
provider: replaceable provider or internal service
authentication: reference only
capabilities: approved surface
health_check: required
readback: required for writes
idempotency: required where side effects exist
rollback_or_compensation: required
provider_exit: required
public_secret_exposure: prohibited
```

### Commercial and economic model

Economic activation is separately governed from capability existence.

The pallet records the applicable commercial objects and authority but must not invent prices, royalty percentages, tax rates, investment returns or entitlements.

Possible contract objects include:

- product/SKU;
- offer;
- price version;
- subscription;
- booking;
- fee schedule;
- commission schedule;
- royalty schedule;
- refund rule;
- clawback rule;
- settlement instruction;
- ThriveEvergreen ECAC where applicable.

### Operating procedures

At minimum, procedures should cover:

```text
onboarding
approval
normal operation
failure handling
incident response
disputes / appeals
reconciliation
provider outage
provider exit
offboarding
recovery / restoration
supersession
```

### Metrics

Metrics must have definitions, not just labels.

A metric record should state:

```yaml
metric_id: stable ID
definition: exact numerator/denominator or event rule
source: canonical event/data source
window: time period
classification: public|internal|restricted
quality_rule: completeness/freshness requirement
```

A count is not comparable to another count unless the metric definition is the same.

## Container-to-module relationship

A pallet is a container; a module is a contained capability or implementation unit.

```text
PALLET P-XX
   |
   +-- module A
   +-- module B
   +-- workflow C
   +-- agent/skill D
   +-- service E
   +-- UI surface F
   +-- provider adapter G
```

A module may be reused by more than one pallet when the reuse is explicit and authority remains scoped.

## Container-to-platform relationship

Platforms remain product identities. Pallets are cross-platform capability packaging.

A platform can consume multiple pallets; a pallet can support multiple platforms.

```text
                  +--> Platform A
Pallet P-XX ------+--> Platform B
                  +--> Platform C
```

This prevents platform-specific implementation from redefining pallet governance.

## Evidence and DAIL

Material pallet actions emit or reference a DAIL record.

A minimum pallet evidence envelope identifies:

```text
pallet_id
pallet_version
capability_id
actor / agent identity
authority / delegation reference
policy version
input evidence references
prior state
new state
decision: PASS | HOLD | DENY
time
correlation / idempotency reference
provider readback where applicable
correction / supersession link
```

DAIL records evidence and lineage; it does not itself create ownership, legal authority or professional certification.

## Public / restricted projection

The same pallet can have a public article and a restricted implementation companion.

### Public-safe

May include:

- purpose;
- architecture;
- named capabilities;
- lifecycle;
- public interfaces;
- public-safe schemas;
- high-level failure modes;
- status classification;
- approved ASCII diagrams;
- non-sensitive test examples.

### Restricted / Vault-bound

May contain:

- unpublished algorithms;
- proprietary scoring/calibration;
- fraud thresholds;
- detailed security topology;
- private evidence;
- provider credentials or secret references;
- unpublished financial schedules;
- protected evaluation corpora;
- exploit-sensitive runbooks;
- filing-sensitive inventions.

Secret values themselves remain in the approved secret store rather than ordinary documentation.

## Container invariants

```text
pallet name != authority
pallet exists != pallet deployed
provider connected != integration certified
API write succeeded != institutional state reconciled
price configured != economic activation authorized
paper described it != production implemented it
module reused != authority reused
public article != unrestricted implementation disclosure
```

## Release checklist

A pallet cannot be promoted merely because its documentation is complete.

```text
[ ] identity/authority complete
[ ] capabilities enumerated
[ ] policies bound
[ ] data schemas versioned
[ ] integrations evidenced
[ ] security review complete
[ ] side effects classified
[ ] tests pass
[ ] failure / rollback paths tested
[ ] DAIL emission/readback verified
[ ] documentation public/restricted split verified
[ ] provider-exit path verified where relevant
[ ] commercial activation separately authorized where relevant
```
