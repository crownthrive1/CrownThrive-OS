# CHLOM Continuous Build & Commercialization

CHLOM is maintained as a continuous institutional program, not a one-time code drop or documentation export.

## Lifecycle

```text
observe + recover
→ reconcile canon
→ research / identity / rights / compliance analysis
→ individual asset identification and articleization
→ agent-factory candidate intake
→ Execution Builder / PentaFactory
→ independent verification
→ canonical parent package
→ public child projection candidate
→ commercial package candidate
→ ThriveEvergreen / ECAC
→ DAIL evidence + outcomes + corrections
→ next cycle
```

## Continuous lanes

Standing CHLOM lanes include:

- source recovery and canon reconciliation;
- R&D and experimental lineage;
- stable IDs, DIDs, Fingerprints and provenance;
- ownership evidence, rights and DLA modeling;
- hybrid licensing design;
- compliance-oracle evaluation;
- DAIL records and evidence architecture;
- pallets, modules, containers and components;
- frameworks, plugins, skills, algorithms, formulas and scripts;
- APIs, MCPs, SDKs, webhooks and agent contracts;
- portals, dashboards, widgets, wireframes and scaffolds;
- documentation and individual articleization;
- repository parent/child projection;
- website-mesh observation and continuity;
- commercial packaging and ThriveEvergreen handoff.

## Individual asset rule

A materially designed CHLOM asset must be independently addressable and versionable even if it is also part of a larger framework or bundle.

The asset-class manifest explicitly includes pallets, modules, containers, components, services, frameworks, plugins, skills, algorithms, formulas, prompts, scripts, workflows, agents, oracles, contracts, schemas, registries, APIs, MCP surfaces, SDKs, webhooks, wireframes, scaffolds, portals, dashboards, widgets, DLAs, DID/Fingerprint profiles, DAIL record types, policy packs, commercial packages, research programs, papers, runbooks, evaluation packs and test suites.

A combination article may summarize a family, but it does not replace the institutional identity of a material individual asset.

## Source discipline

Automation must preserve the distinction among:

- current founder adjudication;
- current machine-verified institutional state;
- current canonical documentation;
- recovered primary sources;
- validated public registries/schemas;
- historical, superseded, experimental or research material.

Research can remain important IP without being current production truth.

## Build discipline

Candidate work must carry stable identity, version, source/authority reference, rights/public-private classification, dependencies, verification state, factory state, commercialization state and successor/supersession relationships.

Factory build completion is `BUILT_PENDING_INDEPENDENT_VERIFICATION`, not automatic PASS.

## Maintenance-aware automation

The continuous design includes scheduled validation and read-only mesh observation. Current targeted-maintenance governance blocks routine autonomous external mutation until the evidence-based maintenance release gate passes.

This avoids confusing “automated” with “uncontrolled.” Candidate generation and validation can continue while external mutation remains held.

## Commercial packaging

A verified capability can be transformed into a candidate package containing:

- exact capability/version;
- intended customer and use case;
- deliverables;
- license class;
- machine-access requirements;
- support and fulfillment definition;
- public/private boundary;
- dependencies and restrictions;
- CrownThrive SKU request candidate;
- pricing-input request;
- ThriveEvergreen / ECAC handoff.

The first package registry includes developer integration, rights/hybrid licensing, provenance/assurance, policy/compliance oracle, Pentafabric architecture, private/managed deployment, OEM/embedded, research/education and mesh-reliability candidate families.

## Economic activation

ThriveEvergreen is the exclusive CrownThrive SKU issuer. ECAC resolves economic activation. Candidate registration does not create a SKU, price, checkout, entitlement or revenue claim.

## Documentation continuity

The CHLOM Documentation & Projection Steward is assigned to detect terminology drift, stale repository relationships, missing asset articles, public/private leakage, unversioned correction, parent/child managed projection drift and historical claims presented as current.

That documentation loop is part of the build system, not an afterthought.
