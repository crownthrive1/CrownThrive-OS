## Purpose

The Drift Monitor detects when observed CHLOM behavior, dependencies, evidence or model outputs depart materially from an accepted baseline.

It answers:

```text
WHAT changed?
WHEN did it change?
WHICH subjects/actions may be affected?
WHICH baseline or version was expected?
IS the variance explainable and authorized?
DOES it require review, HOLD, rollback or revalidation?
```

It does not decide source rights, create licensing authority, legislate policy or promote changes to production by itself.

## Drift families

### Model drift

Changes in model output distribution, calibration, false-positive/false-negative behavior, feature relationships or domain performance.

### Policy drift

A rule or policy implementation behaves differently from the approved version, or applicable-version resolution changes unexpectedly.

### Evidence drift

Required evidence becomes stale, unavailable, contradictory or materially different from the evidence used for the prior decision.

### Provider drift

An external provider changes schema, API behavior, version, billing semantics, availability or returned state in a way that can affect institutional interpretation.

### Decision drift

The same governed scenario produces a materially different PASS/HOLD/DENY outcome without an explained and approved reason.

### Authority drift

Roles, scopes, delegations or effective permissions expand beyond the documented authority envelope.

Authority drift is release-blocking until resolved.

## Evaluation pattern

```text
CURRENT OBSERVATION
        |
resolve exact baseline
        |
normalize comparable inputs
        |
measure variance
        |
explain known authorized changes
        |
 +------+-------+
 |              |
explained      unexplained/material
 |              |
PASS/record    HOLD + review
```

## Continuous simulation relationship

The Drift Monitor can trigger or consume continuous simulation runs. A scheduled replay of frozen scenarios can detect decision drift even if no code commit occurred.

```text
simulation result
   -> baseline comparison
   -> drift observation
   -> evidence packet
   -> governed release/review decision
```

Simulation PASS remains evidence, not deployment authority.

## Model-lifecycle relationship

A new model version must have a documented evaluation and adoption path. Drift can cause:

- additional evaluation;
- reduced authority/scope;
- SAFE_HOLD for affected decisions where policy permits;
- rollback to a known-good version;
- re-evaluation of decisions made in an affected window.

## Provider drift

Provider success or schema change does not redefine CrownThrive institutional truth.

```text
provider state changed
      !=
canonical meaning changed automatically
```

Adapters should detect incompatible changes and fail closed or HOLD rather than silently reinterpret data.

## Evidence currentness

Evidence-sensitive decisions require an explicit observation time and freshness policy. Stale evidence can itself be a drift condition.

## Correction propagation

If drift is later confirmed to have contaminated prior material decisions:

```text
identify affected version/time window
 -> enumerate affected decisions
 -> re-evaluate under corrected state
 -> append corrections/supersessions
 -> preserve original history
 -> record DAIL evidence
```

## Security and abuse resistance

The engine must resist attempts to:

- choose a convenient baseline after seeing results;
- suppress material variance;
- relabel an authority expansion as ordinary model drift;
- train on contaminated outcomes without adjudicated correction;
- let a provider-controlled metric become the sole institutional baseline;
- auto-promote a new version merely because variance is low.
