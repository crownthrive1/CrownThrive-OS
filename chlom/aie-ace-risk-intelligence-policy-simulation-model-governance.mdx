# AIE and ACE — Risk Intelligence, Policy Simulation and Model Governance

The Genesis Volume explicitly defines **AIE = AI Intelligence Engine** and **ACE = Adaptive Compliance Engine**. In that source architecture, AIE supplies machine-learning intelligence and simulation while ACE applies policy, compliance checks and protective actions. Later CrownThrive material also reuses AIE for **Anomaly Intelligence Engine**, which remains preserved as acronym lineage rather than silently replacing the Genesis meaning.

Current CHLOM decomposes these functions into bounded, inspectable services rather than one unrestricted autonomous brain.

## AIE historical responsibilities

The Genesis source describes AIE capabilities including:

- transaction and identity risk scoring;
- fraud-pattern recognition;
- anomaly detection;
- predictive analysis;
- natural-language analysis of regulatory text or news;
- learning from confirmed outcomes and false positives;
- ingesting on-chain and oracle data;
- privacy-aware or federated-learning concepts;
- policy-impact simulation;
- model updates over time.

These functions should be modeled separately enough that one model failure cannot silently redefine the whole compliance system.

## ACE historical responsibilities

ACE is the active compliance guardian. Historical responsibilities include:

- pre-transaction policy checks;
- credential and license prerequisite checks;
- anomaly/risk consumption;
- quarantine or pause triggers;
- contract/static/dynamic analysis concepts;
- automated compliance reporting;
- policy-threshold adjustment after approved changes;
- enforcement coordination with DLA/LEX/ADE.

Current CHLOM keeps the deterministic policy layer authoritative over probabilistic AI confidence.

## Decision algebra

```text
hard DENY rule triggered
        -> DENY

required evidence missing
        -> HOLD

AI high-risk score
        -> HOLD / specialist routing unless policy defines bounded automatic response

AI low-risk score
        -> cannot override missing authority or hard rule

all rules/evidence/authority satisfied
        -> PASS candidate
```

The key invariant is:

```text
model confidence < institutional authority
```

## Risk scoring contract

A risk score should identify:

```yaml
score_id: stable-id
subject_id: subject
model_id: model/version
feature_set_version: version
input_window: period
score: numeric-or-categorical
risk_band: low|medium|high|critical
reason_codes:
  - controlled-code
explanation_ref: optional
observed_at: timestamp
expires_at: timestamp
source_refs:
  - evidence/oracle/event
limitations:
  - limitation
DAIL_event_ref: event-id
```

A number without model/version/time/context is not an institutional risk record.

## Risk versus finding

```text
risk score = probabilistic signal
finding    = evidence-backed conclusion under defined criteria
sanction   = authorized institutional action
```

These must remain separate.

## Anomaly detection

An anomaly engine can detect patterns such as:

- unusual transaction velocity;
- outlier license use;
- unexpected geography;
- duplicate identity patterns;
- suspicious graph relationships;
- abnormal payout routing;
- policy-bypass attempts;
- unexpected API/agent behavior;
- repeated failed verification.

An anomaly means **investigate**, not automatically **guilty**.

## False-positive handling

```text
ALERT
  |
  v
triage
  |
  +--> expected behavior -> close + learning label
  |
  +--> uncertain -> HOLD + specialist review
  |
  +--> violation evidence -> case / bounded action
```

Outcome labels should feed model evaluation only through governed datasets.

## Policy simulation

The Genesis and Grand Prospectus describe AI-assisted simulation of proposed policy changes.

Example questions include:

- What happens if a threshold changes?
- How many transactions would move from PASS to HOLD?
- Which user or platform classes are disproportionately affected?
- Does fraud detection improve while false positives rise?
- What operational workload would a new audit rule create?
- Which existing licenses become non-compliant under a proposed pack version?

Simulation is advisory.

```text
PROPOSED POLICY vNext
        |
        v
SIMULATION ENVIRONMENT
        |
 +------+----------------+
 |                       |
 v                       v
historic replay      synthetic scenarios
 |                       |
 +-----------+-----------+
             |
             v
 impact report
             |
             v
 human/governance review
             |
   +---------+---------+
   |                   |
approve              reject
   |
   v
controlled rollout
```

## Simulation dataset classes

Use only governed data appropriate for the purpose:

- anonymized or de-identified historical events;
- synthetic cases;
- public regulatory examples;
- approved test fixtures;
- redacted case outcomes;
- sandbox platform data.

Production secrets, personal data or protected evidence should not be copied into simulation without explicit authorization.

## Model registry

Every consequential model should have a registry record including:

- stable model ID;
- provider/architecture;
- version/hash;
- purpose;
- owner/steward;
- approved data classes;
- training/evaluation datasets;
- feature definitions;
- autonomy/decision ceiling;
- tools/access;
- known limitations;
- fairness/bias evaluation;
- security/privacy evaluation;
- drift status;
- rollback model;
- effective period;
- retirement state.

## Shadow mode

A strong rollout pattern is:

```text
live event
   |
   +--> current policy result
   |
   +--> candidate model result (no side effect)
                    |
                    v
               compare outcomes
```

Shadow mode reveals disagreements without allowing a candidate model to affect users.

## Drift monitoring

Model drift signals may include:

- score-distribution changes;
- rising false positives;
- rising false negatives;
- unexplained feature shifts;
- performance disparity across relevant groups;
- new fraud tactics;
- regulatory-domain changes;
- provider/model behavior changes.

Drift beyond threshold should reduce authority or trigger rollback rather than silently continue.

## Explainability

The Grand Prospectus emphasizes understandable reasons for consequential risk outcomes.

Current implementation should preserve:

```text
result
+ reason codes
+ input/evidence references
+ model/version
+ limitations
+ appeal/review path
```

A black-box score alone is insufficient for high-impact action.

## Fairness and protected characteristics

Historical material discusses fairness and avoiding discriminatory factors. Current implementation should test for unjustified disparate behavior and exclude protected/sensitive attributes unless their use is lawful, necessary and explicitly governed.

No article can certify legal fairness compliance merely from technical testing.

## AIE → ACE boundary

```text
AIE says: risk = 0.92
ACE asks:
  - which rule consumes this signal?
  - is the model current?
  - is the evidence fresh?
  - what action is permitted for this risk band?
  - is human approval required?
```

The policy must define the institutional consequence.

## ACE → execution boundary

ACE should produce a decision receipt, not unrestricted side effects.

```yaml
decision_id: stable-id
policy_pack: pack/version
inputs:
  - evidence/risk/credential refs
result: pass|hold|deny
reason_codes:
  - code
required_approvals:
  - authority-class
allowed_actions:
  - action-class
expires_at: timestamp
DAIL_event_ref: event-id
```

The execution layer consumes only allowed, unexpired decisions.

## Temporary protective actions

Historical sources contemplate rapid pauses. Current safety model may permit short-lived, reversible protective holds inside pre-authorized scope.

```text
critical anomaly
   |
   v
TEMPORARY HOLD
   |
   +--> evidence preserved
   +--> human/specialist review
   +--> automatic expiry
   |
   +--> release / extend by authorized decision
```

A temporary automated hold must not become indefinite punishment by inertia.

## Failure modes

| Failure | Response |
| --- | --- |
| model unavailable | deterministic fallback / HOLD |
| version unknown | HOLD |
| stale score | recompute / HOLD |
| unexplained critical result | HOLD \+ review |
| model contradicts hard rule | hard rule prevails |
| drift threshold exceeded | downgrade/rollback |
| provider changes model behavior | re-evaluate |
| simulation data unauthorized | stop simulation |
| AI recommends unsupported authority | reject recommendation |
| conflicting models | policy-defined resolution / HOLD |

## Adversarial tests

Required scenarios include:

1. prompt/instruction injection through external text;
2. poisoned oracle input;
3. adversarial transaction pattern;
4. stale model version;
5. missing reason codes;
6. model says PASS while required credential absent;
7. high-risk false positive with appeal;
8. fairness regression;
9. provider outage;
10. model rollback;
11. candidate model in shadow mode attempts side effect;
12. regulatory-text extraction hallucination;
13. duplicate risk events;
14. cross-tenant feature leakage.

## Core invariants

```text
AI recommendation != authority
risk score != violation
anomaly != guilt
simulation != adopted policy
model update != policy update
confidence cannot override DENY
missing evidence cannot become PASS
AI cannot self-escalate its autonomy ceiling
```

## Current implementation boundary

Risk scoring, anomaly detection, simulations, model registries and shadow evaluations can be implemented in the cloud-first CHLOM architecture now. Historical on-chain ML, federated network learning or autonomous ADE execution remain research/advanced adapters unless specifically evidenced and approved.
