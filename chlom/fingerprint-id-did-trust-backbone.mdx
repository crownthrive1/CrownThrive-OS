### Permanent signer rule

Before a future founder/executive override can be institutionalized, the human signer must be explicit. If the request does not identify the signer, the automation must HOLD and ask:

> **Who is signing their name to this override?**

A role name such as “Founder” or “CEO” is not a substitute for the person's name.

## Identity layers are deliberately separate

CHLOM must never collapse institutional identity, content integrity and cryptographic control into one identifier.

| Layer | Purpose | What it does **not** prove |
| --- | --- | --- |
| Stable institutional ID | Durable semantic identity such as `ct.platform.virality-music` | Current deployment, ownership or key control |
| Fingerprint ID | Deterministic digest of one exact versioned record | Human identity, legal title, rights clearance or DID control |
| DID | Standards-based identifier/controller relationship when adopted | Truth of every claim made about the subject |
| Verifiable Credential | Signed claim from an issuer to a subject/holder ecosystem | Underlying legal authority beyond the issuer's governed scope |
| DAIL event hash | Append-oriented evidence/correction lineage | That the event was lawful merely because it is hashed |
| External anchor | Optional notarization/oracle/chain receipt | CrownThrive authority by itself |

A Fingerprint ID is **not biometric fingerprint data**. CrownThrive does not authorize biological fingerprint templates for this registry.

For the broader object model, see [Institutional Record and Format Standard](/standards/record-and-format-standard), [CrownThrive ID](/technology/crownthrive-id), [Rights Ledger and Evidence](/chlom/rights-ledger-and-evidence), and [Data and Event Architecture](/technology/data-event-architecture).

## Fingerprint ID v1 contract

The initial format is:

```text
ctfp:v1:sha256:<64 lowercase hexadecimal characters>
```

The digest is computed over a versioned canonical representation.

Current bounded canonicalization profile:

```yaml
profile_id: ct-json-c14n-v1
encoding: UTF-8
object_keys: sorted
array_order: preserved
floating_point: rejected
hash: SHA-256
```

This deliberately avoids silently claiming RFC 8785 interoperability. RFC 8785/JCS is the target canonicalization standard for later conformance work. `ct-json-c14n-v1` remains frozen for every record already fingerprinted under v1. If the canonicalization profile changes, CrownThrive creates a new profile/version rather than regenerating old fingerprints invisibly.

## Restricted centralized registry

The Phase-2.99 operational registry is materialized in a restricted Supabase schema.

The public-safe logical model includes:

- subjects;
- Fingerprint IDs;
- DID bindings;
- credential records;
- attestations;
- subject relationships;
- optional future proof-anchor receipts.

Current controls:

```yaml
tables: 7
row_level_security: enabled_and_forced
anonymous_table_access: none
authenticated_user_table_access: none
service_role_access: bounded_server_side
raw_private_keys: prohibited
raw_biometrics: prohibited
did_bindings_seeded: 0
verifiable_credentials_issued: 0
external_proof_anchors: 0
```

The database currently stores stable IDs, controlled metadata and cryptographic digests. It is not a private-key vault and must not become one.

Sensitive key material belongs in an approved server-side key manager/Vault/HSM boundary. A public key or key reference may be recorded only where the governing cryptographic profile permits it.

Supabase is the initial operational registry, not the permanent identity of CHLOM. Exportability and stable IDs are required so the trust layer can move providers without breaking institutional identity.

## Standards and cryptographic-agility baseline

Current R&D uses authoritative standards as implementation inputs, not automatic CrownThrive deployment claims.

| Standard / ecosystem | Current use |
| --- | --- |
| W3C DID Core 1.0 | Stable DID architecture baseline |
| W3C DID Core 1.1 | Candidate Recommendation monitored; not adopted as production authority |
| W3C Verifiable Credentials Data Model 2.0 | Phase-3 credential model baseline |
| W3C Verifiable Credential Data Integrity 1.0 | Phase-3 proof/signature baseline candidate |
| RFC 8785 JCS | Canonicalization interoperability target |
| NIST FIPS 203 / 204 / 205 | Future PQC algorithm-registry candidates |
| NIST crypto-agility guidance | Algorithm inventory, replacement and migration discipline |
| Polkadot SDK / FRAME | Later Rust pallet research; not a chain-launch commitment |

The cryptographic design must be agile. SHA-256 is the current content-fingerprint algorithm for v1, not a promise that every future proof, signature, KEM or credential uses SHA-256.

CrownThrive should maintain an algorithm registry with:

```text
algorithm ID
purpose
standard/version
security status
allowed lifecycle state
implementation/library
key type
created/accepted dates
migration successor
reopen trigger
test vectors
```

## CHLOM integration model

Fingerprint IDs are intended to become cross-cutting CHLOM references.

```text
Stable subject ID
      ↓
Fingerprint ID(s)
      ↓
DAIL evidence / correction chain
      ↓
DID controller binding
      ↓
Verifiable Credential / attestation
      ↓
Rights / DLA / entitlement / policy relationship
      ↓
API / MCP / oracle projection
      ↓
Optional external anchor
```

This supports the current CHLOM cloud/API/evidence-first architecture while preserving advanced metaprotocol research for later phases.

The broader technical corpus is decomposed through the [Paper-to-Engineering Pipeline](/chlom/paper-to-engineering-decomposition-pipeline) and [Full Component & Pallet Atlas](/chlom/full-component-pallet-atlas).

### DAIL and corrections

A corrected institutional record does not delete the old fingerprint.

Instead:

```text
record v1 → fingerprint A
correction event → DAIL relationship
record v2 → fingerprint B
A remains historical
B becomes current if governance accepts it
```

That preserves evidence history and avoids pretending mutable records have one permanent content hash.

## Validation and rollback

The public manifest and deterministic validator prove:

- the founder override fingerprint;
- required signer name;
- 68 ordered S100 source fingerprints;
- the no-biometrics/no-private-key boundary;
- zero Phase-2.99 DID/VC/anchor activation;
- restricted migration receipts by hash only;
- Phase 3 remains blocked.

Runtime self-healing already corrected a mutable-function `search_path` security lint and added covering indexes for the new registry's foreign keys. The post-repair Supabase security advisor reports no security lints for the project.

Rollback is additive and explicit:

1. stop writes to the `chlom_identity` schema;
2. export the stable IDs/fingerprints/attestations;
3. revert the public documentation/manifest packet;
4. if governance authorizes database rollback, remove the additive schema only after preserving its evidence export.

Dropping the registry is never an automatic Agent-F action because it would destroy evidence history.
