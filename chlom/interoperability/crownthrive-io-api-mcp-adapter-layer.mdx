## Source boundary

The recovered CHLOM component atlas explicitly names a **CrownThrive IO / API / MCP adapter layer**. Existing CrownThrive IO and developer/integration documentation establish the broader provider-independent integration role, but a standalone historical adapter-layer body has not been located.

This article institutionalizes the adapter layer as a distinct CHLOM component without claiming one current codebase or endpoint set is already production-certified.

## Purpose

The adapter layer allows CrownThrive platforms, partner systems, MCP clients, internal services and external APIs to interact with CHLOM through stable institutional contracts rather than directly coupling every client to database tables or provider-native IDs.


## CrownThrive IO role

CrownThrive IO acts as an upstream/downstream integration and developer surface for ecosystem capabilities. The CHLOM adapter layer defines the governed interface contract that CrownThrive IO can expose or consume.

CrownThrive IO does not become the source of CHLOM rights, policy or institutional evidence merely because it is an integration gateway.

## API role

REST, GraphQL, event/webhook or internal APIs expose versioned CHLOM schemas and capability operations. Clients operate through stable tenant/object IDs and explicit scopes. Transport success remains separate from policy/authority result.

## MCP role

MCP tools/resources can project CHLOM capabilities to AI assistants/agents and other MCP clients. Every tool should declare:

```yaml
tool_id:
capability:
input_schema_ref:
output_schema_ref:
side_effect_class: read|candidate_write|consequential_write
required_scopes[]:
required_authority_refs[]:
idempotency_requirement:
DAIL_behavior:
privacy_class:
```

Possessing an MCP tool does not grant authority beyond the tool's governed action path.

## Client identity

Each API/MCP client has a stable application/client ID, tenant owner, environment, auth method, granted scopes, usage budget, current credential state and audit lineage. Client secrets remain in secret custody and are never written into public docs or DAIL.

## Action classification

The adapter layer classifies requests before routing:

```text
READ / QUERY
SAFE ANALYSIS / SIMULATION
WRITE CANDIDATE
CONSEQUENTIAL WRITE
PROVIDER EXECUTION
```

Consequential actions pass exact authority, policy, evidence, freshness and idempotency gates.

## Schema normalization

Clients and provider adapters use canonical schemas such as DAIL event, DLA record, policy pack, economic schedule, attestation, evidence reference, governed calculation and provenance binding. Provider-native payloads are translated at the edge.

## Stable ID resolution

External aliases—provider user IDs, payment IDs, listing IDs, chain addresses, CMS IDs or partner object IDs—resolve to canonical CHLOM identities/objects. Ambiguous alias mapping returns HOLD/CONFLICT rather than guessing.

## Scope and authority

API/MCP scopes determine which interface operations a client may request. They do not grant underlying business/legal authority.

```text
API scope allows request
+ institutional authority allows action
+ policy/evidence allow context
= executable candidate
```

## Provider adapters

The layer can route approved operations to payment, storage, analytics, messaging, media, identity, search, blockchain or other providers. Each adapter publishes normalized capability, version, health, auth class, rollback/reconciliation behavior and exit path.

## Readback and reconciliation

Consequential provider writes require readback or other execution evidence. CHLOM compares provider result to expected canonical state. A provider API success response is not final institutional truth by itself.

## DAIL and correlation

Every consequential request carries request/correlation IDs and creates or references DAIL events. Low-level telemetry can remain in operational logs while institutional decision/action receipts stay traceable.

## Error model

Normalized results distinguish authentication failure, scope restriction, authority HOLD, policy HOLD/DENY, stale version, validation error, alias conflict, rate limit, dependency outage, provider mismatch, privacy restriction and unsupported version.

## Rate and usage semantics

Where CrownThrive-local request ceilings apply:

```text
-1   = unlimited local ceiling
0    = zero requests permitted
N>0  = exactly N permitted in the defined window
null = unresolved/unknown -> fail closed
```

Provider-native limits are normalized separately.

## Security and privacy controls

Use least-privilege scopes, tenant/object authorization, secret references, schema/version validation, exact action snapshot binding, idempotency, audience-scoped projections, response redaction, audit logs, current credential/dependency checks and explicit disable/revocation paths.

## Agent/autonomy boundary

Agents may use API/MCP capabilities within delegated scope. They cannot self-escalate, create new authority, bypass reserved approvals or reveal restricted vault contents.

## Provider replacement and continuity

Stable CHLOM objects/client contracts survive provider replacement. Migration maps old/new aliases, reconciles outstanding events, tests replacement adapters and preserves historical readback/provenance.

## Tests

Test read client, candidate-write client, consequential action with missing authority, stale version, provider alias conflict, duplicate MCP invocation, provider outage, rate-limit semantics, cross-tenant request, secret redaction, provider replacement and agent request beyond delegated scope.

## Current status

This is the institutional adapter contract for CrownThrive IO/API/MCP convergence. Actual endpoints/tools/deployments require exact implementation evidence and release certification.

## Versioning

Client scopes, canonical schemas, API/MCP contracts and provider adapters are independently versioned. Breaking changes use migration/deprecation rather than silent replacement.
