## Source boundary

The recovered CHLOM component atlas explicitly lists **interoperability metabridge** as a distinct component. No complete standalone source body defining the original metabridge protocol has been located.

The term is institutionalized as a higher-order interoperability concept: rather than one bridge between one pair of systems, a metabridge normalizes claims, identities, proof types, trust assumptions and message semantics across multiple heterogeneous bridge/adapter families.

## Problem it addresses

A direct adapter matrix scales poorly:

```text
System A <-> System B
System A <-> System C
System B <-> System C
...
```

Every pair can develop different identity aliases, claim types, replay rules, finality semantics and error models. The metabridge creates a governed normalization layer:

```text
SOURCE SYSTEMS / CHAINS / PROVIDERS
 A   B   C   D   ...
  \  |  /  /
   ADAPTERS
      |
      v
INTEROPERABILITY METABRIDGE
- source registry
- identity / object alias normalization
- claim schemas
- proof / receipt classification
- replay / sequencing
- policy routing
- privacy projection
      |
      v
CHLOM CANONICAL SERVICES / DAIL
      |
      v
DESTINATION ADAPTERS / SYSTEMS
```

This is a current engineering reconstruction of the recovered concept, not recovered historical implementation text.

## Metabridge is not universal trust

A metabridge does not make all connected systems equally trusted. It preserves source-specific trust contracts:

```yaml
source_system_id:
claim_types_allowed[]:
auth_or_proof_method:
finality_or_receipt_semantics:
freshness_policy:
independence_group:
privacy_class:
local_interpretation_policy_ref:
status:
```

A payment provider can be a valid source for its own execution event while remaining non-authoritative for asset ownership.

## Identity and alias normalization

The metabridge resolves external identities/objects to stable CHLOM IDs through registered aliases. Ambiguous mappings HOLD. It must never select an identity because two external usernames merely look similar.

## Claim-type registry

Each interoperable claim type has a stable schema and semantics such as:

- credential/identity attestation;
- asset/provenance claim;
- license/DLA status claim;
- payment/settlement observation;
- governance result;
- evidence/proof receipt;
- revocation/correction;
- provider/service health;
- another explicitly registered type.

Unregistered generic payloads do not gain institutional meaning.

## Protocol adapters

Adapters can target:

- Web2 SaaS/API providers;
- CrownThrive platforms;
- partner APIs;
- blockchains/ledgers;
- decentralized identity networks;
- payment providers;
- content/media systems;
- government/regulatory sources;
- storage/attestation systems.

The metabridge contract is provider-neutral; adapters carry provider-specific authentication and schemas.

## Proof portability

When a source claim includes a proof/attestation, the metabridge identifies proof type, circuit/key/source registry and context. Local proof usability is still evaluated under CHLOM verifier/policy rules.

## Replay and sequencing

The metabridge prevents the same source event from creating repeated local consequences. It should preserve source sequence/nonce/finality information where supported and generate a canonical semantic idempotency identity.

## Local policy sovereignty

Every imported claim passes local interpretation:

```text
REMOTE CLAIM VALID UNDER SOURCE
            |
            v
LOCAL POLICY / RIGHTS / AUTHORITY
            |
      PASS | HOLD | DENY
```

A remote governance vote, token transfer, credential or license does not automatically override local CrownThrive/CHLOM authority.

## Privacy federation

The metabridge should support minimum disclosure and transformation from private source data to safe local claims/attestations/proofs where possible. Raw personal/contract evidence should not be replicated across every connected system.

## Error model

Typed errors include:

`SOURCE_UNREGISTERED`, `ADAPTER_AUTH_FAILURE`, `UNSUPPORTED_CLAIM`, `SCHEMA_MISMATCH`, `ALIAS_AMBIGUOUS`, `REPLAY`, `SEQUENCE_GAP`, `PROOF_INVALID`, `SOURCE_STALE`, `LOCAL_HOLD`, `LOCAL_DENY`, `DESTINATION_UNAVAILABLE`, `PRIVACY_VIOLATION`.

## Observability

Correlate source message, normalized claim, local evaluation, destination action and corrections. Operational dashboards can show adapter health, lag and error counts, while DAIL holds the canonical consequential event/evidence lineage.

## Governance

Adding a new source system, claim type, proof type or destination side effect is a governed change with source trust review, schema tests, privacy/security assessment, negative tests and rollback/disable procedure.

## Threat model

Confused-deputy trust expansion, alias poisoning, replay, adapter credential compromise, schema downgrade, forged finality/proof, source collusion, privacy leakage, destination double execution, bridge recursion/loops and a remote system treated as universal authority.

## Tests

Test one source/one destination, many source types, claim-type mismatch, alias ambiguity, replay, sequence gap, source revocation, provider replacement, blockchain reorg/finality reversal, private claim projection, destination outage and bridge-loop prevention.

Source adapters, claim schemas, proof methods, trust policies and destination adapters are independently versioned. Historical source semantics remain preserved.
