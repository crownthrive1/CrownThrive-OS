## Source boundary

The recovered CHLOM component atlas names **Web2/Web3/multi-chain messaging** as a distinct interoperability family. CHLOM also preserves conventional API/webhook architecture and historical blockchain/bridge research. This article institutionalizes the cross-environment messaging family without claiming one specific historical transport implementation or a live multi-chain network.

## Purpose

The component lets CHLOM express one institutional message/claim model across heterogeneous transports:

```text
WEB2
REST / webhooks / queues / SaaS APIs
       \
        \
         CHLOM CANONICAL MESSAGE / CLAIM
        /
       /
WEB3 / MULTI-CHAIN
chain messages / events / proofs / bridges
```

The transport changes; the institutional semantics should not.

## Web2 transport classes

Potential Web2 adapters include authenticated REST callbacks, webhooks, message queues, event buses, serverless jobs, partner APIs and other conventional networked services.

Each adapter defines authentication, delivery guarantees, ordering, retry, rate limits, payload limits and data-classification constraints.

## Web3 / chain transport classes

Historical/future adapters can observe or submit blockchain events/messages, proof receipts, bridge messages or chain finality information. Exact networks/protocols are not adopted by this article.

## Semantic equivalence

The same semantic event delivered through different rails should normalize to one institutional event when appropriate. Provider webhook plus provider API readback may describe the same payment event. Bridge relay plus source proof may describe the same remote claim. Semantic identity and reconciliation prevent duplicate institutional effects.

## Web2 trust model

Web2 messages rely on provider/API authentication, signed webhooks where supported, service identity, source registries and readback. Provider success remains external evidence.

## Web3 trust model

Web3 messages can rely on key/signature verification, contract/event identity, protocol finality evidence or bridge verification. A finalized source-chain event remains external evidence for local CHLOM policy.

## Multi-chain identity

Addresses, chain account IDs, contract IDs and token/NFT IDs are external aliases. CHLOM stable asset, DLA, identity and economic IDs remain canonical. One institutional object can have multiple chain/provider aliases.

## Ordering and finality differences

Web2 systems may provide eventual retries without consensus finality; chains may provide probabilistic or protocol-defined finality and possible later corrections. The adapter reports the source model explicitly so consuming policy can distinguish pending, accepted, corrected or uncertain evidence.

## Privacy

Restricted identity, agreement or evidence bodies should not be placed on broad/public transports merely for interoperability. Prefer commitments, hashes, attestations, public-safe proofs and opaque references when they satisfy the use case.

## Side-effect commands

A message requesting a side effect still passes the destination authority/policy gateway. A signed message from a remote system is not self-executing institutional authority.

## Duplicate and domain controls

A message processed for one destination/action should not be accidentally applied to another. Domain separation can include tenant, destination, action type and nonce or semantic event identity.

## Correction handling

Web2 refunds/reversals and chain/bridge corrections are appended as new evidence. Local effective state is recomputed according to policy; historical source messages remain preserved.

## Defensive controls

- authenticate registered sources;
- validate message schema and version;
- enforce tenant/object scope;
- deduplicate semantic events;
- record source timing and finality/receipt state;
- constrain payload classification;
- require local policy/authority for side effects;
- preserve correction/reversal lineage;
- support provider/transport replacement;
- observe adapter health and delivery lag.

## Conformance tests

Test one event through Web2 and Web3 adapters, duplicate source evidence, corrected chain/source event, webhook retry, provider readback, alias normalization, public-data minimization, cross-domain duplicate prevention and local DENY despite valid remote evidence.
