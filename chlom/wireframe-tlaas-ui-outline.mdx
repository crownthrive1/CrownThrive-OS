## Terminology boundary

Historical CHLOM uses **TLaaS** for more than one expansion. This UI article preserves the exact recovered title without silently choosing one meaning.

```text
TLaaS
 +--> historical Tokenized Licensing as a Service
 +--> historical Trust Layer as a Service
```

The current interface should identify the active service profile explicitly by stable service/profile ID. A user should never infer semantics from `TLaaS` alone.

## Purpose

The TLaaS UI is a service-oriented control surface for participants or operators who need to request, inspect, issue, verify, monitor or integrate CHLOM trust/licensing capabilities through governed APIs/services.

```text
IDENTITY
  |
SERVICE PROFILE
  |
REQUEST / ASSET / CREDENTIAL / LICENSE
  |
POLICY + RIGHTS + EVIDENCE
  |
PASS | HOLD | DENY
  |
SERVICE RESULT / DLA / ATTESTATION
  |
API / WEBHOOK / DAIL RECEIPT
```

## Primary roles

```text
service consumer
issuer / licensing steward
organization operator
developer / integrator
reviewer / compliance operator
support / audit operator
```

A role visible in the UI does not expand the actor's underlying P-01/P-02 authority.

Because TLaaS has historical semantic collisions, the selector should render explicit profile identity:

```text

```

Example safe display:

```text
Profile: Licensing Service
Lineage: historical TLaaS / Tokenized Licensing-as-a-Service

```

or

```text
Profile: Trust Layer Service
```

No UI should present one expansion as the canonical universal meaning until adjudicated/source-governed.

## Overview region

Recommended cards:

- service profile/status;
- current API/schema version;
- current Compliance Pack/policy set;
- connected provider/adapters;
- request volumes by decision state;
- current incidents/HOLDs;
- expiring credentials/licenses;
- integration health.

Metrics require exact definitions and as-of state.

## Request creation

The user begins with an explicit service request type.

```text
Create request
  |
select capability
  |
select subject/asset
  |
provide required evidence/parameters
  |
preflight validation
  |
policy/rights/authority evaluation
  |
PASS / HOLD / DENY
```

Material request types should not be hidden behind a generic `Run` button.

Possible public-safe capability groups:

```text
license candidate / DLA request
license verification
credential / attestation verification
rights/evidence preflight
eligibility check
service-integration test
public verification request
```

The exact production capability set depends on current implementation evidence.

## HOLD experience

A HOLD screen should identify:

- request ID;
- safe reason class;
- missing/stale/conflicting requirement;
- responsible next actor or automated step;
- expected review/expiry if known;
- current evidence/version snapshot;
- support/escalation route.

Do not expose exploit-sensitive policy thresholds.

## API / webhook console

Developer-facing section can expose:

- public endpoint documentation;
- schemas;
- webhook event types;
- test/sandbox fixtures;
- request/response examples;
- idempotency semantics;
- rate-limit/request-budget semantics;
- current version/deprecation.

It should not expose secret values. API keys are created/managed through secure flows with masked/one-time handling.

## Request-budget semantics

Any CrownThrive-local request ceiling displayed must follow the standing institutional semantics:

```text
-1   = unlimited CrownThrive-local monthly ceiling
0    = exactly zero requests permitted
N>0  = exactly N requests permitted per month
null = unresolved/unknown -> fail closed
```

Provider quotas/billing/contractual limits remain independently authoritative.

## Empty states

- no requests: explain how to create an authorized request;
- no licenses: distinguish truly empty from unavailable/filtered;
- no providers: show service cannot execute provider-bound operations;
- no policy: HOLD profile rather than show ready state.

## Error states

```text
service unavailable
policy resolver unavailable
rights service unavailable
provider adapter failed
webhook delivery failed
schema/version mismatch
readback conflict
request budget exhausted/zero
```

These are not all `DENY` states.

## Security/privacy

- no raw secret display;
- evidence minimized by role;
- tenant isolation;
- protected policy details restricted;
- webhook URLs/credentials access controlled;
- audit receipt visibility scoped;
- provider identifiers/public data separated from private account configuration.

## Accessibility

- explicit labels for profile/capability ambiguity;
- status not color-only;
- code examples accessible/copyable;
- request state updates announced;
- tables keyboard navigable;
- modals trap/restore focus;
- confirmation text identifies exact side effect.

## Responsive behavior

Mobile reduces left nav to drawer and shows task-oriented cards. Developer schema/code views can horizontally scroll with accessible labels rather than shrinking illegibly.
