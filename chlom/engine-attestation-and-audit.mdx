## Purpose

The Attestation & Audit Engine turns **evidence into scoped, reproducible assurance records**. It verifies sources/proofs, evaluates defined audit criteria, records findings, tracks remediation, issues bounded attestations/certification packages and maintains DAIL lineage without confusing an internal technical audit with legal or professional certification.

```text
AUDIT SUBJECT / CLAIM
        |
        v
SCOPE + CRITERIA VERSION
        |
        v
EVIDENCE COLLECTION
        |
        v
VERIFICATION / TESTS / REVIEW
        |
        +--> findings
        +--> exceptions
        +--> insufficient evidence
        |
        v
AUDIT OUTCOME
 PASS | PASS-WITH-FINDINGS | HOLD | FAIL
        |
        v
ATTESTATION / ASSURANCE PACKAGE
        |
REMEDIATION / RE-AUDIT / EXPIRY
        |
        v
DAIL
```

## Audit is scope-bound

```text
audit PASS
   !=
all systems safe forever
   !=
legal compliance opinion
```

Every outcome must identify what was tested, under which criteria/version, at what time and with what evidence coverage.

A scope should define:

- subject/system/version;
- environments;
- time period/as-of;
- criteria/control set;
- excluded areas;
- evidence sources;
- sampling if used;
- reviewer authority/competence;
- required independent verification if applicable.

## Assurance package

An assurance package can bundle:

- scope;
- criteria/version;
- outcome;
- public-safe finding summary;
- evidence/DAIL references;
- attestation IDs;
- expiration/review date;
- limitations;
- remediation status.

Private workpapers stay restricted.

## Continuous audit

Continuous audit is a repeated evaluation pattern, not a guarantee of continuous compliance.

```text
events / telemetry / changes
          |
          v
continuous monitors
          |
threshold / schedule / trigger
          |
          v
AUDIT CHECK / CASE / REVIEW
```

A monitor can create a finding/HOLD candidate when evidence changes.

Material changes that can trigger targeted review include:

- policy version change;
- identity/authority change;
- provider migration;
- security incident;
- new algorithm/model version;
- rights/license update;
- payment/settlement workflow change;
- public-claim change;
- deployment/release.

## Failure modes

### Evidence unavailable

Outcome can be HOLD/not-tested; do not convert missing evidence into PASS.

### Audit criteria changed mid-run

Freeze the audit's criteria snapshot or formally restart/version the affected tests.

### Provider attests itself compliant

Provider attestation is evidence, not independent audit.

### Findings fixed after report publication

Issue remediation/retest/superseding assurance; do not rewrite the prior report invisibly.

### New code commit after exact-head checks

Prior certification remains valid only for prior head; rerun checks for new head.

## Security/privacy

Audit workpapers may expose vulnerabilities, private data, contracts and security topology. Public assurance artifacts should minimize details that enable exploitation or violate confidentiality.

## Public / restricted twin

Public-safe:

- scope;
- criteria IDs/versions;
- outcome;
- safe limitations;
- attestation/verification status;
- high-level remediation state.

Restricted:

- test evidence;
- vulnerability details;
- private findings;
- contracts/legal workpapers;
- exploit reproduction;
- protected test algorithms;
- reviewer deliberation.

## Metrics

Potential definitions:

- retest success;
- recurring findings;
- evidence completeness;
- expired attestations;
- continuous-monitor HOLD triggers;
- audit/provider disagreement rate.

## Invariants

```text
audit PASS != legal certification
provider attestation != independent assurance
closed finding != fixed without evidence/retest
new version != old audit coverage automatically
attestation != factual truth beyond scope
missing evidence != PASS
public assurance != full workpapers
```
