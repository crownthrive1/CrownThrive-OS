## Source boundary

Recovered CHLOM/CrownThrive developer materials explicitly identify **Python** as an SDK/tooling target alongside JavaScript and historical Solidity/Web3 tooling. A definitive historical or production Python package has not been located in the current recovery corpus.

This article therefore institutionalizes the Python SDK target and its required semantics without inventing a package name, PyPI release or exact exported method catalog.

## Purpose

The Python SDK gives server processes, data workflows, compliance/audit tools, simulations, automation jobs, AI/ML services and partner integrations a typed client over CHLOM's institutional contracts.

Its central rule is the same as every interface:

```text
SDK capability != action authority
```

The SDK makes governed interfaces easier to consume; it cannot bypass them.

## Synchronous and asynchronous use

The SDK can support synchronous and asynchronous clients where implementation warrants it. Both must preserve identical institutional result semantics, version checks and idempotency behavior.

## Typed models

Use generated or hand-maintained typed models for canonical CHLOM schemas such as DLA records, DAIL events, evidence references, policy results, calculations and cases.

Type validation should reject unknown mandatory schema versions rather than silently dropping fields that may affect rights, policy or economics.

## Result states

The SDK exposes institutional result states directly:

```text
PASS_CANDIDATE
HOLD
DENY
PENDING
CONFLICT
STALE_VERSION
MATCH
HOLD_MISMATCH
```

A caller should not need to parse prose to know a DLA activation candidate is on HOLD.

## Exceptions versus domain outcomes

Transport, authentication, unsupported schema and client misuse can use exceptions according to Python conventions. A valid business/domain result such as `HOLD` should generally remain a typed result, not be disguised as an exception unless the specific SDK contract deliberately defines otherwise.

## Idempotency

Provide helpers or explicit parameters for semantic idempotency on side-effect candidates. Automatic retry logic must only retry operations classified safe/retryable and must preserve the original semantic key.

## Retry discipline

Reads can often use bounded retries for transient failures. Consequential writes require stricter behavior: retries must not duplicate effects and should use canonical readback/reconciliation when the first attempt's result is uncertain.

## Pagination / iteration

Typed iterators can simplify paginated reads while preserving cursor, query and tenant context. The SDK should expose page metadata when consumers need reproducible audits.

## Event/webhook support

Python server tooling can support safe parsing and verification helpers for registered event/webhook adapters, schema validation, canonical event identity, idempotency and correction handling.

## Dataframe / analytics boundary

The SDK can optionally provide transformations useful for analytics, but canonical institutional records must remain distinct from analytical DataFrames/notebooks. A derived table is not the source of DAIL, rights or settlement truth.

## AI/ML integration

Python is a natural implementation language for model/risk/simulation services. Model inference clients must preserve model/version, evidence refs, uncertainty and result classification. An SDK convenience wrapper cannot transform a model score into authority.

## Audit and batch workflows

Batch operations should preserve per-item result/evidence identity. A bulk call that processes 1,000 objects cannot hide which records were PASS, HOLD, DENY or failed technically.

## Protected evidence

The SDK returns public/role-scoped evidence projections and download handles only when the caller is authorized. It should not make private vault bytes automatically available because the Python environment is server-side.

## Logging

Default logs must avoid credentials and protected payloads. Safe correlation IDs, object IDs where permitted, operation names, result classes and timing can support observability.

## Compatibility matrix

Each SDK release declares supported server/schema versions and deprecations. Unknown incompatible server versions fail explicitly.

## Conformance tests

- typed schema round-trip;
- authentication/scope failure;
- tenant isolation;
- PASS/HOLD/DENY preservation;
- semantic idempotency retry;
- ambiguous write followed by readback;
- pagination iterator;
- event parsing;
- batch mixed results;
- protected evidence access;
- model-result/authority separation;
- unsupported schema version.
