## Purpose

The Parameter & Config Service is CHLOM's versioned source for non-secret operational parameters and references to protected configuration. It ensures that policy-governed values, service parameters, limits, feature states and integration configuration are typed, validated, effective-dated, reviewable and reproducible.

```text
SOURCE AUTHORITY / POLICY
          |
          v
PARAMETER DEFINITION
          |
          v
CANDIDATE VALUE / VERSION
          |
VALIDATE / APPROVE / TEST
          |
          v
ACTIVATE FOR ENVIRONMENT/SCOPE
          |
          v
READBACK / DAIL
```

## Scope

A parameter can be scoped. Global values are not assumed when a tenant/service-specific value exists.

```text
global
  -> environment
      -> tenant/org
          -> service/pallet
```

Precedence must be explicit in the definition; no implicit last-write-wins.

## Validation

Before activation:

- type/schema valid;
- units valid;
- allowed range/domain;
- dependencies resolve;
- policy/source authority valid;
- security classification respected;
- compatibility tests pass;
- required reviewer/approval complete;
- rollback path exists for material change.

## Effective periods

```text
v1 active until T1
v2 active from T1
```

Historical events reference the effective config version so decisions remain reproducible.

## Feature/capability state

A feature state can be modeled explicitly:

```text
DISABLED
CONTROLLED_TEST
STAGED
ACTIVE
HELD
RETIRED
```

A feature flag is not authority to use a capability outside current governance/policy.

## Request-budget semantics

For CrownThrive-local monthly request ceilings:

```text
-1   = unlimited CrownThrive-local ceiling
0    = exactly zero requests permitted
N>0  = exactly N requests permitted
null = unresolved/unknown -> fail closed
```

Provider quotas, contractual entitlements, throttles and billing remain independently authoritative.

## Rollout

Material changes can use staged rollout:

```text
CONTROLLED_TEST -> partial scope -> broader scope -> full target
```

At each stage, monitoring/evidence can HOLD promotion.

## Rollback

Rollback is a new governed state transition. It does not delete the failed/retired version.

```text
v5 active -> issue detected -> rollback to compatible v4 semantics
```

The service records why/when/how.

## Secret references

```yaml
secret_ref: vault://stable-reference
```

Public/internal docs can state that a secret exists and which logical purpose it serves without exposing value.

## Provider config

Provider settings are projected from canonical intent when possible. Provider state is read back and mismatch recorded.

```text
canonical intended config
      |
provider adapter write
      |
provider readback
      |
match / mismatch
```

## Failure modes

### `null` critical parameter

Fail closed/HOLD according to parameter definition; do not reinterpret as `0` or unlimited.

### Unit mismatch

Reject candidate and require correction.

### Provider refuses requested configuration

Keep canonical requested/authorized state distinct from provider-observed state; HOLD dependent capability where needed.

### Config changes after a decision

Historical decision remains tied to old effective version; new decisions use current version.

### Rollback target incompatible

HOLD and route migration/recovery rather than force a structurally invalid rollback.

## Security threats

- unauthorized config change;
- secret leakage;
- environment drift;
- hidden defaults;
- dangerous `null` handling;
- provider overwrite;
- rollback to vulnerable state;
- cross-tenant bleed;
- unreviewed feature activation.

## Restricted companion

Contains protected thresholds, anti-abuse limits, model calibration, provider configuration details, secret-reference mappings, rollout topology and failure-injection tests.

## Invariants

```text

feature enabled != action authorized
secret reference != secret value
null != unlimited
0 != unlimited
provider setting != canonical setting automatically
rollback != erasure

```
