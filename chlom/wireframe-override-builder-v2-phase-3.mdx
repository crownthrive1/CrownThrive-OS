## Purpose

V2 preserves every safeguard from the base Override Builder and adds a deeper **impact-analysis and staged-execution workspace** for overrides affecting multiple services, policies or dependent objects.

```text
TARGET / ORIGINAL DECISION
          |
          v
OVERRIDE CANDIDATE
          |
          +--> scope
          +--> authority
          +--> evidence
          +--> dependency graph
          +--> policy/state simulation
          +--> safeguards
          +--> compensation
          |
          v
STAGED APPROVAL / EXECUTION PLAN
          |
          v
READBACK / POST-OVERRIDE CERTIFICATION
```

## V1 versus V2

```text
V1
single bounded override construction + preview

V2
adds dependency graph, diff/simulation, multi-stage execution,
per-stage approvals/readback, and post-change certification
```

V2 is optional in the recovered title. Articleization does not make it a mandatory current release.

## Dependency graph

The builder resolves downstream objects/services likely to be affected.

```text
OVERRIDE TARGET
   |
   +--> direct dependent objects
   |      |
   |      +--> provider projections
   |      +--> entitlements
   |      +--> transactions
   |
   +--> policy/economic/security dependencies
```

The graph is an impact aid; completeness depends on registered dependencies and cannot be represented as perfect if unknown integrations exist.

## Impact classes

```text
NO SIDE EFFECT
REVERSIBLE WRITE
RIGHTS EFFECT
ECONOMIC EFFECT
SECURITY/ACCESS EFFECT
GOVERNANCE EFFECT
EXTERNAL PROVIDER EFFECT
IRREVERSIBLE / PROFESSIONAL RESERVED
```

Impact class drives safeguards/approvals.

## Policy/state simulation

V2 can replay the proposed override against synthetic/historical scenarios without enacting it.

```text
CURRENT POLICY / STATE SNAPSHOT
            +
OVERRIDE CANDIDATE
            |
            v
SIMULATION
            |
      scenario results
```

Simulation is advisory and cannot grant authority.

## Diff view

```text
BEFORE                          AFTER CANDIDATE
----------------------------------------------------------
Decision: HOLD                  Exception: PASS for scope X
Expiry: n/a                     1 hour
Affected object: DLA-123        DLA-123 only
Transfers allowed: none         transfer to ID-456 only
Provider action: none           Provider X call required
```

Unknown/uncertain impacts are shown explicitly.

## Execution plan

```yaml
stages:
  - id: S1
    action: create bounded institutional override
    rollback_or_compensation: revoke override
  - id: S2
    action: execute provider projection
    requires_readback: true
  - id: S3
    action: reconcile dependent state
    requires_readback: true
```

Each stage can have its own authority, idempotency and failure path.

## Stage gates

```text
S1 PASS
  |
S2 executes
  |
readback failed?
  yes -> HOLD / compensate / do not proceed S3 blindly
```

## Approval matrix

```text
Approval role       Required?       Status
------------------------------------------------
Override authority  yes             approved
Rights reviewer     conditional     pending
Economic reviewer   if value move   n/a
Security reviewer   if access       n/a
Founder/reserved    if required     pending
```

The matrix is generated from current policy—not hard-coded into the visual.

## Quorum/independence

If multiple approvals are required, the system must validate independence/eligible actors according to the governing rule. Multiple child agents do not count as independent human approvals by default.

## Compensation graph

```text
ACTION A -> ACTION B -> ACTION C
  ^          ^           ^
 comp A     comp B      comp C
```

V2 can show which steps have true rollback and which only support compensation.

## Post-override certification

After execution/readback:

```text
[ ] override active in institutional state
[ ] provider projections match
[ ] dependent rights/economic state reconciled
[ ] no unexpected policy conflicts
[ ] DAIL receipts complete
[ ] expiry/review scheduled
```

A provider `success` alone does not close certification.

## Monitoring panel

Active V2 overrides can expose:

- time remaining;
- affected objects;
- provider state;
- anomalies/HOLDs;
- linked cases;
- current monitoring evidence;
- manual/reviewer intervention state.

## Expiry preview

V2 simulates restoration at expiry to identify whether new dependent state will conflict with the baseline.

## Error/uncertainty states

- dependency graph incomplete;
- simulation service unavailable;
- policy conflict;
- approval matrix unresolved;
- compensation path missing;
- provider dry-run unsupported;
- target version drift;
- stage readback mismatch.

Any material unresolved dependency can HOLD the override rather than be hidden as a warning.

## Accessibility

Dependency graphs require a structured list/table alternative. Diff views use text markers in addition to color. Multi-step flow exposes progress and error summaries. Simulation results can be navigated by keyboard and screen reader.

## Security/private twin

Restricted companion can hold full dependency topology, security/economic blast-radius data, privileged approval matrices, protected override templates, red-team simulation cases and emergency controls.

## Invariants

```text
V2 optional != current production commitment
simulation != authorization
dependency graph != guaranteed completeness
approval matrix != approved action
stage success != final certification
rollback != compensation
multiple agents != independent quorum
original decision remains immutable in lineage
```
