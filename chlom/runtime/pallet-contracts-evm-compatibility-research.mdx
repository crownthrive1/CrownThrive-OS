## Substrate runtime lane

Historical CHLOM designs use native pallets for deterministic core state such as identity, DLA, policy, treasury, governance, attestations, escrow and other functions. Native runtime logic can enforce strong state-transition invariants but requires runtime governance and upgrade discipline.

## Pallet-contracts lane

Substrate's contracts-style runtime research can support sandboxed contract execution that interoperates with native runtime interfaces. A CHLOM design would need explicit boundaries between contract-owned state and canonical pallet/service state.

No specific pallet-contracts API or version is claimed by this recovered research record.

## EVM lane

EVM compatibility research can support Solidity/tooling ecosystems and external contract interoperability. A CHLOM EVM adapter should translate stable institutional objects into contract interfaces without making chain addresses, token IDs or contract storage the sole identity of a right/license.

## Cross-VM semantic equivalence

If the same DLA or entitlement is represented in different runtimes, its effective rights and lifecycle must remain consistent. Different VMs cannot independently expand scope or create conflicting canonical versions.

## Contract-call authorization

A contract call or chain transaction can prove execution under that runtime; it does not prove the caller has institutional authority unless the runtime contract is correctly bound to CHLOM identity/authority and current policy.

## External data

Both native runtime and contract VMs require explicit oracle/attestation interfaces for external facts. Contracts must not treat unregistered external data or relays as authoritative by default.

## Economic state

Historical token/fee/staking research is preserved separately. EVM or pallet-contracts compatibility does not activate CHLOM Coin, CHM, staking, DeFi or crypto payment products.

## Interoperability patterns

Safe patterns include:

- native runtime calling registered contract interfaces;
- contracts requesting canonical runtime state;
- event projection into DAIL/indexers;
- bridge/adapter normalization across VMs;
- proof/attestation verification through registered interfaces;
- provider-neutral client APIs above both runtimes.

## Safety properties

- one canonical institutional object per governed identity/version;
- no contract-created rights beyond source rights;
- explicit upgrade authority;
- deterministic/versioned interface schemas;
- replay/domain protection across networks;
- consistent precision/unit rules;
- protected secrets remain off-chain;
- no public PII/private evidence storage by default;
- current local policy remains authoritative for local actions.

## Conformance tests

Test one DLA represented in native and EVM-compatible layers, scope mismatch, version upgrade, event duplication, chain/network alias change, revocation propagation, precision mismatch, oracle evidence change and one runtime unavailable.
