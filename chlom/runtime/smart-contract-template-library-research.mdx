## Source boundary

The recovered CHLOM component atlas explicitly lists **smart-contract templates** within the runtime research family. Historical CHLOM papers include licensing, escrow, governance, treasury, proof and marketplace smart-contract concepts, but a standalone template-library body with exact code has not been located.

This article institutionalizes the template family as architecture/IP and defines how reusable templates must be governed before any future deployment. It does not publish or imply production smart-contract source code.

## Purpose

A template library standardizes recurring on-chain or smart-contract behaviors so every project does not reimplement sensitive rights/economic logic differently.

Candidate template families, grounded in recovered CHLOM domains, include:

- DLA/license representation and lifecycle adapters;
- rights/metadata registry adapters;
- escrow/conditional settlement;
- royalty/split allocation interfaces;
- attestation/proof verification hooks;
- governance/proposal/timelock modules;
- treasury routing;
- bridge/claim receipt handling;
- controlled transfer/sublicense checks;
- emergency pause/guardian interfaces.

These names are current engineering categories, not claims that each historical template body has been recovered.

## Template versus instance

```text
TEMPLATE
  != DEPLOYED INSTANCE
  != ACTIVE PRODUCTION CONTRACT
  != LEGAL AGREEMENT
```

A deployed instance must bind to an exact template version, configuration, parties, rights/economic policy, environment/network and release certification.

## Rights templates

Any rights or DLA template must preserve CHLOM's rights-conservation invariants. It cannot mint or transfer a right absent from the canonical source-right chain merely because contract state permits a token or transfer.

## Economic templates

Escrow, royalty or treasury templates use versioned economic schedules and deterministic arithmetic. Historical tokenomics percentages or research parameters are never embedded as current defaults without explicit adoption.

## Governance templates

Proposal, council, multisig or timelock templates are execution mechanisms only. They cannot create corporate/legal/founder authority beyond the governing institutional framework.

## Attestation / proof templates

Verification templates reference approved verifier/circuit/key registries. Cryptographic success remains separate from proof usability and action authority.

## Configuration discipline

## Security requirements

Before a template can be approved for deployment, require threat modeling, static/dynamic analysis as applicable, property/invariant tests, access-control review, arithmetic tests, reentrancy/state-order review where relevant, pause/recovery behavior, upgrade review and independent review proportional to consequence.

This article intentionally documents defensive controls, not exploit recipes.

## Determinism and external data

Smart contracts should not directly assume external API truth. Oracle/attestation inputs are typed external evidence with source/currentness policy. Where nondeterministic off-chain computation is required, results return through registered proof/attestation/oracle interfaces.

## Secret handling

Private keys, deployer credentials and administrator secrets are never embedded in source templates or docs. Deployments use approved key custody/signing controls.

## Upgrade boundary

Upgradeable templates reference a separate upgrade policy. Immutable deployment and proxy/upgradable deployment are distinct architectural decisions; neither is silently assumed.

## Event/DAIL mapping

On-chain events can be observed and projected into DAIL or other institutional records. Chain events remain external/protocol execution evidence; CHLOM preserves stable institutional IDs and local authority interpretation.

## Provider/network neutrality

A template can have Substrate, EVM or other implementations without making one VM/network the institutional object. Template intent/invariants remain stable while runtime adapters can differ.

## Failure states

Unresolved authority, missing source-right mapping, unsafe/default configuration, failed invariant tests, unsupported runtime, stale oracle/proof assumptions, missing rollback/pause path, upgrade authority ambiguity and unverified deployment bytecode/source mapping.

## Tests

Test template/instance identity, rights overscope rejection, deterministic split conservation, timelock/approval revalidation, attestation verifier retirement, emergency pause, configuration mismatch, upgrade compatibility and chain event-to-DAIL reconciliation.
