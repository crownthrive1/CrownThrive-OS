## Purpose

Formal State-Machine Verification applies mathematical or machine-checkable reasoning to CHLOM's most consequential lifecycle logic so that invalid state transitions are detected at the model/specification level rather than only through examples after implementation.

The recovered Gold Paper contains restricted formal-proof and TLA\+ starter material. Exact protected proof specifications remain vaulted; this article exposes the public-safe methodology, target state machines and verification requirements.

## What is being verified

CHLOM has multiple distinct state machines whose invariants matter independently:

- Dynamic Licensing Asset lifecycle;
- LEX listing lifecycle;
- LEX transaction lifecycle;
- agreement and entitlement lifecycle;
- credential/attestation lifecycle;
- proof/circuit/verifier lifecycle;
- governance proposal/timelock lifecycle;
- policy version/adoption lifecycle;
- payment/settlement/refund lifecycle;
- case/review/appeal/remedy lifecycle;
- audit/certification lifecycle;
- bridge/remote-claim lifecycle;
- provider adapter and execution lifecycle;
- upgrade/deployment lifecycle;
- DAIL correction/supersession lifecycle.

Each deserves a distinct formal target rather than one oversized universal state graph.

## Verification goals

Formal verification can target:

### Safety

A forbidden state can never be reached under modeled transitions.

Examples:

```text
revoked DLA cannot become usable without a valid restoration/renewal transition
child rights never exceed parent/source rights
settled economic event is not duplicated by replay
unauthorized actor cannot execute a reserved transition
```

### Liveness

A valid process eventually reaches an allowed terminal/progress state under stated fairness/system assumptions.

Example:

```text
approved non-blocked timelocked action eventually becomes executable or explicitly expires/holds
```

### Conservation

Economic or capacity state is conserved according to the model.

### Uniqueness / idempotency

A semantic event cannot create multiple consequential effects.

### Correction integrity

Corrections/supersessions change effective state without erasing the historical event chain.

## DLA verification targets

Properties include:

- no activation without source rights and issuer authority;
- requested/child scope stays within controlled scope;
- expiration/revocation blocks current use;
- suspension is not silently cleared;
- renewal/amendment produces valid version lineage;
- parent revocation propagates according to policy;
- explicit unlimited/cap semantics are preserved;
- duplicate activation request does not create duplicate license effects.

## LEX transaction verification targets

- rights and eligibility precede agreement/fulfillment;
- payment evidence cannot skip entitlement checks;
- one semantic payment/transaction creates at most one entitlement/economic effect;
- reversal/refund creates explicit compensating state;
- transaction cannot progress after source DLA becomes unusable without governed remediation.

## Credential/proof verification targets

- revoked/expired credential is not current;
- retired circuit/key prevents current proof usability according to policy;
- proof validity does not skip authority;
- recovery/key rotation preserves historical attribution while changing current control.

## Governance verification targets

- proposal mutation after approval invalidates prior exact-snapshot approval;
- quorum and eligibility use a defined snapshot;
- timelock cannot execute early;
- approval/authority is revalidated at execution;
- emergency or reserved-authority controls follow their explicit scope/TTL.

## Economic verification targets

- allocation conservation;
- deterministic rounding/residue;
- duplicate provider event cannot double settle;
- provider mismatch cannot silently rewrite expected obligation;
- refund/reversal preserves original history and corrects current effective state.

## Case/remedy verification targets

- case status does not itself execute remedy;
- reviewer conflict/eligibility gates are respected;
- appeal/supersession does not erase prior decision;
- a scoped hold cannot affect unrelated actions unless policy says so;
- remedy execution requires its own authority/idempotency state.

## DAIL verification targets

- events are append-only;
- correction references form valid acyclic lineage;
- unauthorized correction does not become effective merely because it is newer;
- projection can be rebuilt from canonical events and reducer version.

## Model checking versus theorem proving

Different formal tools can be used according to the property and implementation. This article does not canonize one language/tool. Recovered TLA\+ starter material is protected lineage, not a requirement that every CHLOM component use TLA\+.

## Abstraction discipline

A formal model proves properties of the **modeled system under stated assumptions**. It can still be wrong if the model omits a real implementation behavior. Every formal result therefore records abstraction assumptions and implementation mapping.

## Implementation conformance

Formal verification has three distinct layers:

```text
FORMAL MODEL properties hold
      !=
IMPLEMENTATION conforms to model
      !=
DEPLOYED VERSION is the verified implementation
```

Production claims require all relevant bindings.

## Counterexamples and failures

A model checker/theorem effort that finds a counterexample produces a first-class assurance artifact. The workflow should preserve the failing trace, affected invariant, model version, remediation and re-verification result rather than hiding the failed model run.

## Public/private boundary

Public docs can expose:

- state-machine name;
- property/theorem names;
- assumptions at a safe level;
- verification status;
- tool/model version;
- implementation mapping status;
- safe counterexample/remediation summaries.

Restricted proof scripts, trade-secret algorithms, private security assumptions or exploit-sensitive traces can remain vaulted.

## DAIL / provenance

Formal-model creation, approval, verification result, implementation mapping and supersession should receive stable IDs/provenance. A future deployment can point to the exact model/property version it claims to satisfy.

## Tests and validation

In addition to formal model checking, maintain executable conformance tests generated from state transitions/invariants where feasible. Compare formal traces with real service/API test fixtures and replay historical edge cases.

## Current status

CHLOM has recovered formal-methods and theorem lineage plus current state-machine models, but documentation alone does not certify current production components as formally verified. Each component needs an exact model-to-implementation evidence packet.

## Versioning

State machines, formal models, properties, tools and implementation mappings are independently versioned. A behavior-changing code update invalidates prior conformance until remapped/reverified.
