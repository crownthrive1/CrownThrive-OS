## Purpose

CI/CD and deployment scripts convert a versioned source tree into testable artifacts and governed deployments while preserving a verifiable chain from source commit to artifact, migration, environment, deployment and post-deployment readback.

```text
SOURCE HEAD
 -> BUILD / LINT / SCHEMA VALIDATION
 -> TESTS / CONFORMANCE
 -> SECURITY / PRIVACY CHECKS
 -> ARTIFACT MANIFEST
 -> MIGRATION / DEPLOYMENT PLAN
 -> APPROVAL / RELEASE GATE
 -> CANARY / STAGED DEPLOYMENT
 -> READBACK / RECONCILIATION
 -> RELEASE RECEIPT
```

Individual implementations can include:

- dependency/build scripts;
- code/schema generation;
- database migration validation;
- policy/schema compatibility checks;
- test fixture/simulator execution;
- unit/integration/e2e/property tests;
- security/secret scanning;
- artifact packaging/signing/digest generation;
- deployment manifest generation;
- canary/staged rollout;
- health/readback verification;
- rollback/compensation helpers;
- docs/API/schema publication;
- release provenance/DAIL registration.

These are current contract categories, not recovered historical filenames.

## Exact-head rule

All consequential release evidence binds to the exact commit or immutable source digest tested.

```text
approval for head A != approval for head B
```

A new commit invalidates prior exact-head certification for the changed release.

## Build reproducibility

Where feasible, pin dependencies/toolchains and record build inputs so an artifact can be reproduced or at least traced. Non-reproducible third-party/provider outputs are recorded as external dependencies rather than silently treated as deterministic build products.

## Database migration gate

Before applying migrations:

- validate forward schema;
- detect destructive changes;
- preserve stable IDs and DAIL/history;
- verify RLS/tenant boundaries where applicable;
- test rollback or forward-fix strategy;
- check downstream views/indexes;
- snapshot/backup according to policy;
- bind migration to exact release.

A migration must not delete institutional history simply because a table/schema was redesigned.

## Configuration and secrets

Environment configuration is versioned separately from code. Secret values are injected at runtime from approved custody. CI logs and generated artifacts must be scanned to prevent credential leakage.

## Approval gate

Green CI does not grant deployment authority. Release certification and required human/governance approvals are separate gates.

```text
all automated checks PASS
+ required authority/approval
= deployable candidate
```

## Canary rollout

For consequential changes, deploy to a bounded cohort/environment first. Monitor functional health, error rates, rights/policy results, provider reconciliation, DAIL events, privacy/access behavior and support signals before expanding.

## Post-deployment readback

Do not treat deployment API success as proof the desired version is active. Read back version/config/schema state from the target environment and compare to the release manifest.

## Rollback / compensation

Rollback depends on the change class:

- code rollback;
- configuration rollback;
- database forward-fix or restore;
- provider adapter disable/revert;
- economic compensation/reversal;
- policy rollback;
- DLA/entitlement correction;
- public projection rollback.

External side effects may require compensation rather than simple code rollback.

## Multi-environment behavior

Scripts must take explicit environment IDs and fail closed on unknown environment. Production deploys should not infer target from a default branch or local shell context.

## Audit evidence

Release/deployment receipts should include who/what initiated the deploy, authority/approval refs, exact source/artifact digests, environment, scripts/tool versions, migrations, start/end/result, canary/readback and rollback state.

## Failure states

Unpinned/mismatched source head, missing artifact digest, secret scan failure, failing invariant test, migration incompatibility, wrong environment, missing approval, canary degradation, post-deploy version mismatch, rollback untested and provider state unreconciled.

## Tests

Test wrong branch/head, dirty/uncommitted source, artifact mismatch, destructive migration detection, staging/production separation, missing secret reference, failed canary, deployment success with readback mismatch, rollback and external side-effect compensation.

## Current status

The delivery contract is current reconstruction architecture. Specific scripts/workflows must be separately registered with implementation paths and release evidence.

## Versioning

Pipeline contract, scripts, toolchains, manifests and environment configuration are independently versioned. Historical deployment receipts retain exact versions used.
