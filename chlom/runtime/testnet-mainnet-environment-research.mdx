## Historical environment intent

In a decentralized runtime design, **testnet** provides a non-production environment for protocol, validator, token, smart-contract, bridge and governance experimentation; **mainnet** represents the production network whose state/economic/rights effects are live.

The core environment-separation invariant survives even when the implementation is cloud-first:

```text
TEST / SANDBOX STATE != PRODUCTION STATE
```

## Identity separation

Test users, DIDs, clients, API keys and provider accounts should be clearly separated from production identities. A test credential must not be accepted as a production credential unless a specific migration/issuance process creates a valid production object.

## Asset and DLA separation

Synthetic/test assets, licenses and entitlements use test/sandbox identities or explicit non-production flags. The system must prevent a sandbox DLA from becoming a production license merely because IDs look similar.

## Economic separation

Sandbox/test payments, token balances, credits, royalties and settlements are non-production fixtures. Test provider modes/accounts should be isolated from live provider accounts. A test transaction cannot enter production revenue/settlement records.

## Policy separation

Staging/test can exercise candidate policies before adoption. Candidate policy versions must not become production active through test success alone. Production activation follows governed policy migration/approval.

## Data separation

Production personal/confidential evidence should not be copied into lower environments merely to make tests realistic. Prefer synthetic fixtures, redacted/anonymized data or explicitly governed secure test datasets.

## Secrets and providers

Use environment-specific secret namespaces and provider accounts where feasible. A deployment script must require explicit target environment and should not silently fall back to production credentials or endpoints.

## External side effects

Lower environments should block or safely sandbox irreversible side effects such as live payments, production emails/messages, public publishing, licensing state changes or external legal/economic actions unless a controlled test explicitly permits them.

## Testnet-specific future considerations

If a blockchain testnet is reactivated, define:

- network/genesis identity;
- chain spec/runtime version;
- validator/test authority set;
- test token semantics and disclaimers;
- faucet or distribution rules if any;
- bridge isolation;
- chain reset policy;
- explorer/indexer endpoints;
- upgrade policy;
- separation from mainnet addresses/keys where required.

These are future design requirements, not current deployment claims.

## Mainnet-specific future gates

A production decentralized network would require explicit adoption, legal/economic/security review, validator/governance design, key custody, incident controls, chain/runtime audit, bridge/oracle review, token/economic decision if applicable, genesis/finality evidence and production certification.

## Promotion

Code/config can be promoted; data/state/identities are not automatically promoted. Every artifact uses release provenance and explicit migration rules.

```text
staging PASS
!= production activation
```

## Observability

Every environment reports version/config, schema, policy set, provider adapters, dependencies and current health. Dashboards must display the active environment prominently to prevent operators from confusing test results with production state.

## Tests

Test environment ID required, production secret unavailable in sandbox, sandbox DLA rejected in production, test payment isolated, candidate policy remains non-production, provider test/live separation, production data redaction, deployment to wrong environment rejected and future testnet reset behavior simulation.
