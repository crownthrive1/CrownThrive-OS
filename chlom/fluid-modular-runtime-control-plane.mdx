# Fluid Modular Runtime Control Plane

CHLOM is implemented as a **fluid metaprotocol**, not as a single website, token, chain, database or smart contract. Business identities and rights objects must survive infrastructure replacement.

<Warning>
  This page reports a **controlled-test** implementation state. It does not claim production token issuance, autonomous mainnet governance, production DLA/LEX settlement, legal clearance of crypto economics, or a deployed Substrate mainnet.
</Warning>

## Controlled-test evidence added August 20–21, 2026

- capability discovery and version/state metadata;

## Public identity

CHLOM public identity uses an opaque identifier rather than encoding a government identifier, password, email address or secret.

Pattern:

```text
ctid_<opaque 128-bit identifier>
        |
        +--> did:chlom:ctid_<identifier>
        |
        +--> public verification key(s)
```

The public resolver may expose:

- public CHLOM ID;
- DID;
- public display metadata approved for publication;
- public verification keys;
- public DAIL lineage.

It must never expose:

- private keys;
- Vault secret names intended to reveal custody internals;
- passwords;
- government identifiers;
- restricted source records;
- sealed identity evidence.

A public CHLOM ID is a cryptographic/operational identifier, **not a Social Security number and not a substitute for a government identity document**.

## DAIL controlled-test implementation

DAIL currently uses an institutional append-only event table and chained SHA-256 event commitments.

```text
Event N-1 hash
      |
      v
canonical event payload --> payload SHA-256
      |                         |
      +-------------------------+
                    |
                    v
                event hash
                    |
                    v
                Event N
```

Corrections append new events. They do not rewrite historical events.

A scheduled integrity watchdog recomputes the chain and records health evidence. External Merkle/testnet anchoring remains a later chain-adapter capability and must be independently read back before being promoted.

## Two pallet namespaces

CHLOM intentionally keeps two distinct meanings of `pallet`:

1. **Capability pallets** — the 12 CrownThrive cloud/API packaging families used to group reusable capabilities across the ecosystem.
2. **Substrate runtime pallets** — future Rust/Polkadot SDK runtime modules.

The controlled-test registry marks these namespaces separately so documentation or agents cannot mistake a packaging pallet for a deployed blockchain runtime.

## Self-healing boundary

Self-healing is recovery, not authority expansion.

Allowed low-risk patterns include:

```text
Detect -> Diagnose -> Simulate -> Canary -> Verify -> Repair or Rollback -> DAIL
```

Agents may automatically repair approved deterministic or reversible failures within their registered authority. They may not silently modify ownership, binding rights, money destinations, legal terms, production-token issuance, privileged identity or public claims to make an error disappear.

## Oracle fabric

High-impact observations are designed for freshness checks, source authority and quorum/aggregation rather than blind single-provider trust.

The oracle registry is a controlled-test/specification surface. It does not mean every external oracle feed is connected.

## Recovery architecture

The current recovery model separates primary secrets from cross-provider ciphertext recovery:

```text
Supabase Vault
   | primary encrypted secret/key custody
   |
   +--> governed recovery process
             |
             v
       encrypted recovery capsule
             |
             v
         Google Drive
       ciphertext only
```

The recovery capsule has been independently read back and checksum-verified. Public documentation records the recovery state but never the password or private-key material.
