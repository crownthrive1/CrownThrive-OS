# WF-002 — Private Vault / Public Publish Workflow

## Workflow identity

```yaml
workflow_id: WF-002
name: Private Vault / Public Publish
classification: canonical_ip_protection_workflow
version: 1.0.0
```

## Purpose

WF-002 protects CHLOM's defensible IP, trade secrets, private evidence, credentials and exploit-sensitive implementation details while still institutionalizing the existence, purpose, interfaces and lineage of those assets in public-safe documentation.

The objective is **dual persistence**:

```text
protected master -> restricted vault custody
public-safe derivative -> Mintlify / public docs
binding metadata -> connects both without leaking protected content
```

## Classification gate

Every source asset is reviewed for:

- public-safe architecture and terminology;
- internal operational details;
- proprietary algorithms or heuristics;
- trade-secret calibration, weights or methods;
- confidential agreements/economic terms;
- personal/sensitive evidence;
- credentials, keys, tokens and secrets;
- exploit-sensitive security/override material;
- legal or professional materials requiring restricted handling.

If classification is unclear, default to HOLD/restricted review rather than public disclosure.

## Protected master custody

The restricted copy retains the complete source body and source provenance. Where available, preserve source filename/title, version/date, source location, digest/hash, confidentiality label, stable vault ID, access class, owner/custodian and related public article IDs.

Restricted material is stored in the governed private vault/Drive custody path rather than public docs. Credentials/secrets belong in runtime secret management and may be referenced by secret ID/class, never copied into documentation.

## Public-safe derivative

The public article can include:

- asset existence and stable ID;
- purpose and architectural role;
- safe inputs/outputs/interface contract;
- invariants and safety properties;
- source lineage and version;
- historical/current mapping;
- tests/verification targets;
- a statement that protected implementation details are separately vaulted.

It must omit the protected method, secret values, sensitive identities, exploit recipe or other restricted payload.

The binding proves the public-safe record represents a protected institutional asset without making the private body public.

## Change propagation

When the private source changes, compare material differences and update the public-safe article only where new information is safe and relevant. Preserve old public/private versions and record supersession.

## Special protected families

Examples include private Fingerprint/identity resolution, model weights/calibration, restricted Gold Paper proof bodies, splitter/override internals, ZK circuit/witness details, emergency kill-switch mechanics, credentials, private provider contracts and confidential economic schedules.

## Publication test

Before public push, confirm:

```text
no secret value
no private credential
no protected source body reproduced
no personal evidence over-disclosed
no exploit-sensitive mechanism leaked
no trade-secret implementation exposed
```

and confirm the public article still contains enough technical substance to institutionalize the asset rather than becoming a vague placeholder.

## Drive/vault durability

Restricted masters should have durable custody independent of the public docs branch. Where a private recovery vault exists, place protected artifacts there with stable names and version dates. Public Git/Mintlify should contain only safe derivatives and vault-binding metadata.

## DAIL/provenance

Where implemented, record custody, classification, publication and supersession events in DAIL or the institutional provenance registry. A hash/anchor proves integrity only; it does not make the asset's claims true.

## Tests

Run secret scanning, protected-keyword/content review, role-based access tests, public/private diff inspection, broken-binding detection, duplicate-vault detection and restore/readback tests.

## Versioning

Material classification-rule changes require a new WF-002 version and re-evaluation of affected public/private assets.
