# WF-003 — Versioned Correction / Adjudication Workflow

## Workflow identity

```yaml
workflow_id: WF-003
name: Versioned Correction / Adjudication
classification: canonical_continuity_workflow
version: 1.0.0
related_algorithm: ALG-031
```

## Purpose

WF-003 governs what happens when new evidence, implementation readback or an explicit founder ruling changes CHLOM's effective interpretation. The workflow corrects current knowledge **without erasing the earlier source, version, title, acronym, design or decision**.

## Trigger conditions

Use WF-003 for:

- founder adjudication of terminology or architecture;
- newly recovered source that changes an old article;
- production evidence contradicting planned/historical documentation;
- provider/deployment mapping corrections;
- deprecated or retired platform/component meaning;
- schema/API version corrections;
- public/private classification correction;
- historical article that needs a current mapping added;
- error discovered in a previously institutionalized article.

## Stage 1 — Freeze the existing record

Capture the current article/object version, source refs, effective interpretation and current Git/DAIL/provenance reference before editing. Do not overwrite history first and reconstruct it later.

## Stage 2 — Classify the correction

```yaml
correction_class:
  factual_source_correction
  founder_adjudication
  terminology_canonicalization
  implementation_readback
  provider_mapping_correction
  security_or_privacy_correction
  retirement_or_deprecation
  economic_or_policy_version_change
```

## Stage 3 — Determine scope

Resolve all affected dependencies: pages, pallet/module articles, formulas, algorithms, wireframes, schemas, navigation, API/MCP manifests, tests, code mappings, public claims and private vault bindings.

A canonical-name correction is not complete if old active navigation, workflow labels or machine manifests still conflict.

## Stage 4 — Preserve historical semantics

Historical source quotations and source-specific meanings remain intact. Add fields/sections such as:

```yaml
historical_source_meaning:
current_canonical_meaning:
superseded_interpretation:
effective_from:
adjudication_or_evidence_ref:
```

Example: historical `DAL` meanings remain preserved while current `DAIL` is **Decentralized Autonomous Information Ledger**.

## Stage 5 — Update effective articles and registries

Apply the corrected current interpretation to every dependent current-state article, registry, surface and build contract. Use compatibility aliases when changing an opaque identifier would break existing integrations.

## Stage 6 — Version and changelog

Increment the relevant article/schema/policy version, append a changelog entry, identify the prior version and state whether the change is documentation-only, build-affecting, migration-requiring or production-verified.

## Stage 7 — Public/private propagation

If protected material is involved, update the private master and public-safe derivative under WF-002. A public correction must never accidentally expose details that were previously restricted.

## Stage 8 — Validation

Search for contradictory active terms, stale mappings and unpropagated dependencies. Run body-integrity, continuity, security/privacy and machine-manifest checks. Unresolved propagation means HOLD.

## Core invariant

```text
correct_without_erasure
```

The current effective interpretation can change. The historical record of what CHLOM previously specified remains institutional memory.

## Tests

Test terminology correction, historical meaning retention, alias compatibility, implementation mismatch, partial propagation detection, private/public reclassification and competing corrections.

## Versioning

WF-003 changes are themselves versioned because correction policy is part of CHLOM's institutional continuity model.
