## Purpose

The SDK & API Gateway gives authorized applications, providers, agents and developers a stable way to consume CHLOM capabilities without coupling to internal databases or provider-specific implementations.

## Gateway is not authority

```text
valid API credential
   !=
permission for every endpoint/action
```

P-01/P-02/domain policy resolves actual capability.

## Authentication

Possible mechanisms:

- OAuth/OIDC;
- service credentials;
- signed requests;
- short-lived tokens;
- API keys for limited use;
- mTLS/specialized provider auth where required.

Raw credentials remain in secret storage.

## Idempotency

Material create/execute operations should accept or generate stable idempotency keys.

```text
same logical request + same idempotency key
   -> one material side effect
```

The exact key-retention period is endpoint/provider specific.

## Correlation / trace

Requests can carry a correlation ID so the resulting service/provider/DAIL events can be traced end to end.

## Versioning

```text
schema/API v1
  |
breaking semantic change
  |
v2
```

Deprecated versions get explicit retirement/migration windows where possible.

## Error model

Errors should distinguish:

```text
400 validation
401 authentication
403 authorization / explicit deny
409 version/idempotency/state conflict
423/defined HOLD representation
429 throttle/quota
5xx service/provider failure
```

Exact HTTP code conventions are implementation choices, but HOLD must not be confused with ordinary technical failure.

## PASS/HOLD/DENY response

Material policy-gated APIs can return structured decision state:

```yaml
decision:
  result: PASS|HOLD|DENY
  decision_id: stable ID
  reason_codes: []
  requirements: []
  valid_until: nullable
```

## Request-budget semantics

CrownThrive-local ceilings use:

```text
-1 = unlimited local monthly ceiling
0 = zero requests
N > 0 = exact N monthly requests
null = unresolved/unknown -> fail closed
```

Provider limits remain separate.

## Sandbox

Sandbox/test environment should:

- use synthetic/non-production data;
- clearly label simulated provider behavior;
- expose deterministic fixtures;
- support failure injection;
- prevent live economic/rights side effects;
- use separate credentials/keys.

## MCP / tool surface

MCP tools should declare:

- name/description;
- input schema;
- side-effect class;
- authority requirements;
- output schema;
- idempotency/readback behavior;
- human confirmation requirements if applicable.

Agent use of MCP does not expand the agent's delegation.

## SDK behavior

SDKs should wrap transport, schemas, retries and safe helpers—not hide material policy/decision states.

A helper that automatically retries a payment/license action must preserve idempotency.

## Failure modes

### Provider API returns 200 but readback differs

Return/record pending/mismatch, not institutional success.

### API schema version unknown

Reject or negotiate explicitly; do not guess fields.

### Client retries after timeout

Idempotency prevents duplicate side effect.

### Rate budget null

Fail closed rather than treat as unlimited.

### MCP tool visible to agent but delegation lacks action

DENY at authority gate.

## Security

- credential scoping/rotation;
- schema validation;
- tenant isolation;
- SSRF/injection defenses;
- replay/webhook protection;
- rate limiting;
- authorization on every object;
- secret redaction;
- audit of high-impact actions;
- provider exit/fallback.

## Restricted companion

Contains unreleased APIs/tools, provider mappings, auth topology, threat models, quotas/thresholds, security tests and private integration schemas. Secret values remain in secret storage.

## Invariants

```text
API key != unlimited authority
API success != institutional PASS
SDK helper != policy bypass
MCP tool visibility != delegation
provider API != canonical identity
retry != duplicate side effect
sandbox != production
schema-valid != semantically authorized
```

The SDK & API Gateway is a first-class CHLOM developer-service specification. Every production endpoint/tool/provider adapter must carry exact current implementation and security evidence.
