## Historical purpose

The Scheduler/Timelock Pallet provided protocol-native delayed and scheduled execution for actions that should not happen immediately after approval. Typical CHLOM use cases include governance enactment, license transitions, SLA deadlines, staged treasury activity and emergency review windows.

```text
ACTION APPROVED
      |
      v
SCHEDULE / TIMELOCK
      |
      +--> cancel / supersede if authorized
      |
      v
EXECUTION TIME REACHED
      |
      v
REVALIDATE AUTHORITY + POLICY + STATE
      |
 PASS | HOLD | DENY
      |
      v
EXECUTE + EVIDENCE
```

## Scheduled does not mean still authorized

A central current invariant is:

```text
scheduled != eligible at execution time
```

Conditions can change between scheduling and execution. Current CHLOM therefore revalidates material actions before execution.

## Timelock versus scheduler

```text
SCHEDULER
executes at/after a defined time or recurrence

TIMELOCK
enforces a minimum delay before execution can occur
```

One system can implement both semantics.

## Revalidation gate

At execution time, verify:

- action still pending/current;
- actor/delegation still valid;
- policy version/effective conditions;
- target object state;
- rights/eligibility;
- evidence freshness;
- budget/economic authority if relevant;
- no emergency hold/revocation;
- idempotency/not already executed.

## Failure modes

### Policy changed during delay

Revalidate current/effective policy; HOLD/DENY rather than executing stale authorization if the action is no longer permitted.

### Worker outage delays execution

Record actual execution time and missed/delayed state; do not falsify on-time execution.

### Duplicate worker claims same action

Use atomic/idempotent claim; only one material execution succeeds.

### Clock/timezone ambiguity

HOLD sensitive execution until the intended clock basis is resolved.

### Scheduled treasury action after budget revoked

DENY/HOLD under current economic authority even if original schedule was valid.
