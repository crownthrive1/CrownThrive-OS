## Required distinctions

Credential custody, runtime authentication and provider-write authority are three separate states:

```text
credential custody
      ↓ separate proof
bounded runtime authentication
      ↓ separate operation-specific proof
provider write authority
```

A credential existing in Vault does not prove that a provider accepts it. A successful read does not grant write authority. A successful bounded write canary does not create general provider-mutation authority.

## Dual-reference semantics

A primary reference and continuity-recovery reference may contain the same provider credential. When they do, the record is a **dual reference to one provider credential**.

It is not an independently issued secondary credential. Independent recovery exists only when the provider issues a distinct credential or CrownThrive certifies another recovery mechanism.

## Initial binding transaction

The governed binding operation performs one atomic server-side transaction:

1. validate the registered credential identity and lifecycle state;
2. require authenticated founder/service-role authority for initial secret insertion;
3. create the governed primary reference;
4. create the continuity-recovery reference when configured;
5. create an opaque immutable credential-version archive;
6. compute server-side HMAC continuity evidence without returning the credential;
7. register the immutable version and active binding;
8. append a credential-version event and restricted DAIL receipt;
9. refresh continuity state;
10. return only a sanitized receipt.

Permitted receipt fields include presence booleans, same-material verification, continuity state, opaque credential handle, version ID and receipt digest. The secret is never returned.

## Failure and rollback

The initial binding operation is transactional. A failed alias creation, fingerprint comparison, version registration or DAIL append rolls back the transaction.

After a successful bind, prior versions remain immutable. A later governed rotation preserves the previous active version and supports controlled rollback. History is appended or superseded; it is never silently deleted.

## Runtime certification after binding

Binding is followed by a separate read-first certification lane:

- exact endpoint and method;
- bounded request and response;
- correct tenant/account context;
- least-data projection;
- timeout and provider-rate behavior;
- sanitized request receipt;
- no raw provider body in MCP or public output.

Provider writes remain closed until an operation-specific authority, payload bound, idempotency contract, rollback, read-after-write and audit path pass.

## Agent and tool boundary

The non-voting credential-continuity agent may perform deterministic D0 refresh and approved D1 custody/alias repairs. It cannot self-authorize initial D3 secret insertion, provider rotation, general writes or destructive changes.

The controlled-test CHLOM Vault Broker exposes two founder/admin/service-role envelope tools:

- `chlom.credential.envelope.create` — creates a five-minute one-time public-key envelope and token;
- `chlom.credential.envelope.bind` — accepts only client-side encrypted ciphertext and returns a sanitized binding receipt.

The earlier MCP tool that accepted raw credential input is disabled. The active broker never offers generic secret retrieval, does not persist envelope ciphertext, consumes each session after binding, and never returns raw secret material.
