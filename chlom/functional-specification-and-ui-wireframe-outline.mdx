## Role matrix

| Role | Primary UI responsibilities |
| --- | --- |
| Participant | identity, applications, licenses, evidence, requests |
| Holder/licensee | DLA scope, renewal, transfer requests, proofs |
| Issuer/steward | issuance candidates, scope, approvals, renewals, revocation |
| Verifier/reviewer | evidence review, policy checks, attestations |
| Governance reviewer | proposals, decisions, overrides, timelocks |
| Operator/support | cases, provider mismatches, recovery, audit |
| Developer/integrator | APIs, webhooks, schemas, test fixtures |

Actual authority is resolved dynamically and is not inferred from route visibility.

## Form behavior

### Draft

Local/user-entered state can be saved without implying approval.

### Validation

Client validation improves usability; canonical server/domain validation remains authoritative.

### Policy preflight

For material actions, preflight can return PASS/HOLD/DENY before final submit.

### Confirmation

Confirm exact object/version/effect.

### Submission

Use idempotency/correlation IDs.

### Readback

Wait for institutional/provider confirmation where required.

## Version conflict behavior

When a user acts on stale state:

```text
loaded object version = 5
canonical object version = 6
       |
       v
409 / version conflict
       |
show current changes
       |
reload / reapply candidate
```

Do not last-write-win material governance/right state.

## Cross-screen handoffs

Examples:

```text
License Detail -> Open dispute -> Case intake
DLA application -> Evidence missing -> Evidence upload/reference flow
LEX transaction -> Payment captured/transfer failed -> Compensation case
Governance proposal -> Approved -> Timelock status
Fingerprint dashboard -> Credential revoked -> Affected DLA eligibility
```

A handoff carries stable IDs/correlation, not copied mutable state.

## Search and navigation

Global search must respect classification and role. Search indexes are projections; detail pages re-read canonical state before writes.

## Notifications

Notification payloads should carry stable subject/event references and safe summary text. The target page re-resolves current state.

## Auditability

Material screen actions should be reconstructable from:

```text
actor
session/context
action/object/version
input digest/reference
policy/decision
provider/service result
readback
DAIL receipt
```

## Analytics boundary

UX analytics can measure flows, but analytics must not expose private evidence or be confused with audit evidence.

## Acceptance criteria

A screen is not `done` because it renders. For a material action, acceptance includes:

```text
[ ] authorization enforced server-side
[ ] canonical version checked
[ ] PASS/HOLD/DENY rendered correctly
[ ] restricted fields protected at data layer
[ ] side effect idempotent
[ ] provider/service readback verified
[ ] failure/compensation path tested
[ ] DAIL/material event emitted
[ ] accessibility path passes
[ ] mobile/responsive state usable
[ ] support/remedy route works
```

## Responsive architecture

```text
Desktop: persistent nav + tables + split panes
Tablet: collapsible nav + drawers
Mobile: task-first single column + cards + staged forms
```

Material scope/terms cannot disappear on mobile.

## Accessibility requirements

- WCAG-aligned semantic controls;
- keyboard complete;
- no color-only decision states;
- accessible error summary;
- focus return after async dialogs;
- status announcements;
- logical reading order;
- accessible tables/charts/diagrams;
- confirmation text understandable without iconography.

## Security/privacy requirements

- secrets never rendered;
- protected evidence fetched only after authorization;
- no hidden restricted fields shipped to unauthorized clients;
- CSRF/session protections appropriate to stack;
- sensitive actions can require re-auth/step-up if policy defines;
- audit/log data minimized by role;
- downloads/exports classified.
