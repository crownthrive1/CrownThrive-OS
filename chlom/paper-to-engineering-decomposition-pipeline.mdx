# CHLOM Paper-to-Engineering Decomposition Pipeline

Recovering a paper is not the same as recovering the system it describes. Each paper must be decomposed into atomic, traceable engineering and governance records without erasing its original language or treating speculative architecture as deployed.

## Pipeline

```text
Original file + metadata
  → integrity hash and confidentiality class
  → text/figure/table extraction
  → terminology and alias map
  → claims and assumptions
  → concepts and use cases
  → actors/roles/authority
  → requirements
  → invariants and prohibited states
  → data entities and relationships
  → state machines and workflows
  → APIs/events/MCP tools
  → UI/portal/widget requirements
  → security/privacy/threat controls
  → legal/economic questions
  → test and evaluation cases
  → component/pallet/service mapping
  → ADR adoption/rejection/defer decision
  → implementation backlog
  → DAIL evidence and version graph
```

## Decomposition record types

### Concept

What the source proposes, its purpose, source wording, related concepts and current authority.

### Requirement

A testable capability or constraint using `MUST`, `SHOULD` or `MAY`, with source reference and acceptance criterion.

### Invariant

A state that must always hold, for example:

- accepted license terms are immutable; corrections create new records;
- one tenant cannot read another tenant's private evidence without explicit grant;
- revenue allocations reconcile to the distributable amount;
- an expired/revoked license cannot verify as active;
- public outputs cannot contain restricted evidence payloads;
- an agent cannot authorize a reserved legal decision.

### Decision candidate

A source proposal requiring ADR acceptance, modification, rejection or deferment.

### Research claim

A statement that needs validation, not implementation.

### Legal/economic hypothesis

Franchise, securities, token, tax, patent, ownership, transferability, inheritance, guaranteed return or other consequential structure requiring current review.

## Paper-family work queues

### Confirmed families

- White Papers;
- Blackpapers;
- Gold Papers, including Internal Goldpaper/MTD sources;
- Blue Papers;
- Red Papers;
- Green Papers;
- Genesis Volume;
- Grand Prospectus;
- Executive Implementation Brief and High-Level Technical Build Pack;
- Data/API/Security/Operations specifications;
- LEX/DLA/TLaaS/DAL studies;
- industry sovereign-licensing papers;
- module/pallet whitepapers;
- formal/TLA\+/Substrate/cryptography studies.

### Reserved recovery targets

Purple, Silver, Orange and Yellow paper families remain reserved `source_not_located` records until evidence is found. No agent may invent their contents based on color symbolism.

## Source-version comparison

Duplicate or revised papers require semantic comparison:

- added/removed sections;
- changed terminology;
- altered financial/legal claims;
- changed architecture;
- contradictions;
- later corrections;
- current concepts still useful;
- unique details at risk of loss.

Upload or modified dates are not sufficient to determine content authority.

## Protection

Restricted source text, algorithms, economic models and implementation details remain in private storage. Public Mintlify pages may publish summaries, taxonomy and current architecture but not confidential source content unless approved.

## Prioritization

Decompose first the sources that define Phase 3's trust core: Executive Brief, Data/API/Security/Operations, identity/rights/licensing/governance architecture, Goldpaper, DLA/DAIL/LEX, evidence, policy, roles, revenue/remedies and formal invariants. Advanced dedicated-chain/token papers remain preserved and enter 3E only after core services are proven.

## Acceptance

A paper is `engineering_recovered` only when its source is preserved and its actionable content is represented by linked structured records. A summary page alone is not sufficient.
