## CHLOM Paper-to-Engineering Decomposition Pipeline

Recovering a paper is not the same as recovering the system it describes. Each paper must be decomposed into atomic, traceable engineering and governance records without erasing its original language or treating speculative architecture as deployed.

<Warning>
  **Forensic workflow.** Decomposition creates candidate concepts, requirements, contracts, tests, and decisions. It does not adopt a proposal, clear rights, expose restricted IP, publish a production API, certify an implementation, or grant authority. Missing paper bodies and reserved paper families must not be reconstructed by inference.
</Warning>

## Workflow quickstart

<Steps>
  <Step title="Preserve and classify the source">
    Retain the original file and metadata, calculate its integrity hash, establish confidentiality/rights classification, and assign a stable paper/version identity.
  </Step>
  <Step title="Extract without rewriting meaning">
    Extract text, figures, tables, terminology, aliases, claims, assumptions, actors, roles, and use cases while preserving page/section references and source wording where permitted.
  </Step>
  <Step title="Create atomic records">
    Separate concepts, testable requirements, invariants, decision candidates, research claims, and legal/economic hypotheses. Do not turn a claim or hypothesis into an implementation requirement.
  </Step>
  <Step title="Derive engineering candidates">
    Model entities, relationships, state machines, workflows, API/event/MCP candidates, UI requirements, security/privacy controls, and test/evaluation cases with traceable source references.
  </Step>
  <Step title="Map components and decisions">
    Link candidate work to stable component/pallet/service identities, then route each consequential proposal through adopt, modify, reject, or defer review.
  </Step>
  <Step title="Package, protect, and accept">
    Produce the structured output package, implementation backlog, public-safe summary, DAIL/version evidence, and rights-appropriate private records. Mark `engineering_recovered` only when the source and actionable records are both preserved.
  </Step>
</Steps>

## Pipeline

```text
Original file + metadata
  → integrity hash and confidentiality class
  → text/figure/table extraction
  → terminology and alias map
  → claims and assumptions
  → concepts and use cases
  → actors/roles/authority
  → requirements
  → invariants and prohibited states
  → data entities and relationships
  → state machines and workflows
  → APIs/events/MCP tools
  → UI/portal/widget requirements
  → security/privacy/threat controls
  → legal/economic questions
  → test and evaluation cases
  → component/pallet/service mapping
  → ADR adoption/rejection/defer decision
  → implementation backlog
  → DAIL evidence and version graph
```

## Decomposition record types

<Tabs>
  <Tab title="Engineering records">
    **Concepts** explain purpose and relationships. **Requirements** are testable `MUST`, `SHOULD`, or `MAY` statements with acceptance criteria. **Invariants** define states that must always hold.
  </Tab>
  <Tab title="Decision records">
    A **decision candidate** preserves a proposal that requires an ADR or other governed accept/modify/reject/defer decision.
  </Tab>
  <Tab title="Research records">
    A **research claim** requires validation before implementation and must preserve its source, assumptions, uncertainty, and falsification/evidence path.
  </Tab>
  <Tab title="Legal and economic records">
    A **legal/economic hypothesis** remains non-operative until the applicable qualified review and governing decision address its jurisdiction, rights, tax, financial, ownership, or transfer implications.
  </Tab>
</Tabs>

### Concept

What the source proposes, its purpose, source wording, related concepts and current authority.

### Requirement

A testable capability or constraint using `MUST`, `SHOULD` or `MAY`, with source reference and acceptance criterion.

### Invariant

A state that must always hold, for example:

- accepted license terms are immutable; corrections create new records;
- one tenant cannot read another tenant's private evidence without explicit grant;
- revenue allocations reconcile to the distributable amount;
- an expired/revoked license cannot verify as active;
- public outputs cannot contain restricted evidence payloads;
- an agent cannot authorize a reserved legal decision.

### Decision candidate

A source proposal requiring ADR acceptance, modification, rejection or deferment.

### Research claim

A statement that needs validation, not implementation.

### Legal/economic hypothesis

Franchise, securities, token, tax, patent, ownership, transferability, inheritance, guaranteed return or other consequential structure requiring current review.

## Paper-family work queues

### Confirmed families

- White Papers;
- Blackpapers;
- Gold Papers, including Internal Goldpaper/MTD sources;
- Blue Papers;
- Red Papers;
- Green Papers;
- Genesis Volume;
- Grand Prospectus;
- Executive Implementation Brief and High-Level Technical Build Pack;
- Data/API/Security/Operations specifications;
- LEX/DLA/TLaaS/DAL studies;
- industry sovereign-licensing papers;
- module/pallet whitepapers;
- formal/TLA\+/Substrate/cryptography studies.

### Reserved recovery targets

Purple, Silver, Orange and Yellow paper families remain reserved `source_not_located` records until evidence is found. No agent may invent their contents based on color symbolism.

## Source-version comparison

Duplicate or revised papers require semantic comparison:

- added/removed sections;
- changed terminology;
- altered financial/legal claims;
- changed architecture;
- contradictions;
- later corrections;
- current concepts still useful;
- unique details at risk of loss.

Upload or modified dates are not sufficient to determine content authority.

## Protection

Restricted source text, algorithms, economic models and implementation details remain in private storage. Public PentaDocs pages may publish summaries, taxonomy and current architecture but not confidential source content unless approved.

## Prioritization

Decompose first the sources that define Phase 3's trust core: Executive Brief, Data/API/Security/Operations, identity/rights/licensing/governance architecture, Goldpaper, DLA/DAIL/LEX, evidence, policy, roles, revenue/remedies and formal invariants. Advanced dedicated-chain/token papers remain preserved and enter 3E only after core services are proven.

## Acceptance

A paper is `engineering_recovered` only when its source is preserved and its actionable content is represented by linked structured records. A summary page alone is not sufficient.

<Check>
  Acceptance requires traceability from each actionable record back to the preserved source version, plus explicit classification of contradictions, decision candidates, research claims, legal/economic hypotheses, restricted material, tests, and public-summary scope.
</Check>

## Failure, privacy, and support boundary

Stop the workflow when source integrity, version identity, rights/classification, provenance, or required private custody cannot be established. Preserve contradictions and missing sections as gaps; do not resolve them by color symbolism, title similarity, upload date, or adjacent papers.

No API request, credential, runtime environment, or production response is defined by this workflow. Derived interface candidates remain non-executable until the [component reconciliation contract](/chlom/component-framework-reconciliation-contract), [Phase 3 service contract](/chlom/phase-3-service-contract), and applicable security/rights review establish an exact contract. Use the [support request workflow](/workflows/support-request) for source, custody, rights, confidentiality, or review-blocking conflicts.
