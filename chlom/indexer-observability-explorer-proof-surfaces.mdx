# Indexer, Observability, Explorer and Proof Surfaces

The Grand Prospectus dedicates a major architecture area to **Observability & Indexing**. It describes network-health metrics, dashboards, public transparency tools, searchable indexes, historical archives, real-time alerts and privacy-aware views. This material is particularly useful for the modern cloud-first CHLOM build because observability and indexing are required whether the underlying execution layer is centralized, decentralized or hybrid.

## Why indexing and observability are different

```text
INDEXING      = make institutional records queryable
OBSERVABILITY = understand system behavior and health
EXPLORER      = expose selected records to users/public
AUDIT SURFACE = prove what happened and under which rule
```

They may share data pipelines but have different access, retention and truth requirements.

## Indexing scope

Historical sources describe indexing not only transactions but identity records, license text/metadata, policy packs, governance records and other protocol state.

Modern CHLOM indexes may support queries such as:

- active licenses of a given class/territory;
- current Compliance Packs by domain;
- actions affecting a specific stable ID;
- asset/license usage history;
- open disputes/holds;
- governance/decision status;
- source/evidence relationships;
- current versus historical platform state.

## Index versus canonical truth

An index is a **read model**, not the canonical authority.

```text
canonical records / DAIL
         |
         v
index projection
         |
         v
query result
```

If an index becomes stale or corrupt, the canonical record must still be recoverable and the index rebuildable.

## Index freshness

```text
canonical event N
      |
      v

      |
      v
read model at offset N?
   +--+--+
   |     |
 yes    no
   |     |
   v     v

```

Consequential decisions should not rely on a stale search index when the authoritative service can provide current state.

## Observability signals

Historical sources mention metrics such as transaction latency, validator uptime/responsiveness and compliance events. Modern CHLOM observability expands across:

- API latency/error rate;
- queue depth;
- policy decision rates;
- HOLD/DENY frequency;
- provider failures;
- evidence freshness;
- DAIL append/read lag;
- agent/tool failure rates;
- authorization denials;
- payment/webhook reconciliation lag;
- backup/recovery health;
- deployment/version drift;
- security signals;
- documentation freshness/validator state.

## Public Compliance Explorer

The Grand Prospectus proposes public transparency tooling similar to a blockchain explorer but with compliance context.

A modern public-safe explorer might expose selected data such as:

- public license status;
- public asset/provenance references;
- public policy versions;
- public-safe DAIL receipts/digests;
- public status/incident summaries;
- public governance decisions;
- cryptographic anchor references.

It must not expose restricted evidence, secrets, raw personal data or sealed disputes.


The same indexed object may have different projections for different roles.

## Search privacy

A record being searchable internally does not mean it is publicly discoverable.

```text
canonical record
    |
    +--> public index projection
    +--> subject-private projection
    +--> restricted review projection
```

Sensitive fields should be excluded before indexing into public/searchable surfaces rather than relying only on front-end hiding.

## Archives and historical retrieval

The Grand Prospectus emphasizes long-term archives so an organization can later reconstruct old compliance/license state.

```text
HOT INDEX
 recent / active records
       |
       v
WARM ARCHIVE
 historical searchable data
       |
       v
COLD / PROTECTED ARCHIVE
 long-term evidence
       |
       v
integrity verification against canonical digests
```

Retention must follow applicable legal, contractual and institutional rules; not every event should be retained identically forever.

## Audit surface

An audit query should be able to answer:

```text
WHAT happened?
WHO/WHAT initiated it?
UNDER WHICH authority?
USING WHICH evidence?
WHICH policy/version applied?
WHAT provider executed it?
WHAT was the result?
WAS it later corrected/reversed?
```

That is stronger than a conventional application log.

## Proof surfaces

A proof surface exposes evidence that a statement is true without necessarily exposing the evidence body.

Possible outputs include:

- signed receipts;
- DAIL event digests;
- Merkle proofs;
- provider attestations;
- ZK proofs;
- current-state certificates;
- exported audit packets.

The proof format must state exactly what it proves and what it does not.

## AI and analytics

Historical material expects observability data to feed risk/anomaly analysis and trend reporting. Current CHLOM can use AI for summaries, anomaly detection or advisory insights, but model output is not final institutional authority.

## Failure conditions

HOLD, degrade or flag when:

- index lag exceeds the allowed threshold;
- telemetry disappears unexpectedly;
- public/private classification cannot be resolved;
- a query result conflicts with canonical state;
- retention/archive integrity cannot be verified;
- a dashboard reports provider metrics without institutional reconciliation;
- alert routing fails for a consequential incident;
- a proof surface exposes more data than its authorization permits.
