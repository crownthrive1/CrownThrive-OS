## Source basis

Historical CHLOM sources explicitly name an **Identity & Credential Pallet** managing DIDs, SBTs and verification status. The Technical Blueprint describes DID registration, public keys/claims, trusted credential issuance, revocation/update functions and a unique Fingerprint ID serving as a unified identity anchor.

The separate DID Pallet article preserves DID-document mechanics. This article covers the broader **identity \+ credential** aggregate.

## Non-purpose

The pallet does not:

- make a biometric template public;
- equate a DID with a verified legal identity;
- equate a credential with a role or authority;
- make historical SBT/NFT tokenization mandatory today;
- allow credential issuers to grant rights beyond their issuer scope;
- claim a current public-chain identity deployment.

## Identity object

```yaml
identity_id: stable institutional ID
identity_type: person|organization|service|agent|other

account_aliases: provider/system aliases

```

Raw biometric or high-risk identity evidence remains restricted.

## DID relationship

```text
institutional identity
   +-- DID A
   +-- DID B
   +-- provider account C
```

A DID is an identifier/document system, not necessarily the institution's singular identity primary key.

## Issuer authority

Before credential issuance:

```text
issuer identity current?
issuer role current?
issuer authority includes credential type/scope?
source evidence sufficient?
required approvals complete?
```

A valid signature from an unauthorized issuer does not create a valid institutional credential.

## SBT lineage

Historical sources used non-transferable Soulbound Tokens as one credential representation. The current semantic model treats SBT as an optional representation/adapter.

```text
credential semantic object
   -> optional SBT/token representation
   -> optional VC representation
   -> provider alias
```

The credential meaning must survive provider/representation changes.

## Fingerprint ID

Historical Fingerprint ID unified identity, transactions, licenses and revenue routing. Current mapping requires a privacy-preserving stable reference and separates identity from provider destination data.

```text
Fingerprint reference
  -> identity
  -> credentials / rights / cases / economic party refs
```

Public projections must not expose private biometric/multi-signal derivation.

## Credential lifecycle

```text
CANDIDATE
   |
EVIDENCE / ISSUER REVIEW
   |
ACTIVE
   |\
   | \ expiry -> EXPIRED
   | suspension -> SUSPENDED -> ACTIVE/REVOKED
   | revocation ----------------> REVOKED
   | reissue/update ------------> SUPERSEDED -> new credential
```

Revocation/suspension must propagate to dependent permissions/DLAs according to policy.

## Key rotation and recovery

Keys are cryptographic controls, not identity itself.

```text
identity stable
  -> key v1
  -> rotate/revoke
  -> key v2
```

Recovery should require an adopted secure recovery profile. Exact recovery methods and credentials are restricted.

## Selective disclosure / ZK

Credentials can support privacy-preserving proofs:

```text
credential claims
   -> witness/proof generation
   -> ZK proof
   -> verifier confirms predicate
```

A proof of a predicate should reveal no more than required and still respect revocation/currentness.

## Role and delegation separation

```text
identity != credential != role != delegation != action approval
```

A professional credential may be one prerequisite for a role, but the role and current delegation are separately governed.

## Failure modes

- identity proof unresolved -\> HOLD;
- issuer authority missing -\> DENY;
- credential expired -\> not current;
- revocation state unavailable -\> HOLD for high-impact action;
- key compromised -\> suspend/rotate, do not delete identity;
- duplicate identities suspected -\> review/merge only with evidence;
- provider/DID unavailable -\> stable identity persists if alternative evidence exists;
- public request for restricted identity evidence -\> deny/redact.

## Threat model

- identity takeover;
- forged issuer;
- credential cloning;
- SBT/token transfer bypass;
- revocation failure;
- key compromise;
- biometric leakage;
- account alias collision;
- cross-tenant identity linking without purpose/authority;
- credential-to-authority escalation.

## Test vectors

1. authorized issuer \+ sufficient evidence -\> active credential;
2. unauthorized issuer signature -\> invalid;
3. expired credential -\> currentness check fails;
4. revoked credential -\> dependent action denied/held;
5. key rotation -\> identity/credential IDs remain stable;
6. proof verifies but credential revoked -\> action not PASS;
7. same display name -\> no identity merge;
8. provider account changes -\> stable identity remains;
9. historical SBT representation absent -\> semantic credential can still exist;
10. raw biometric data requested publicly -\> never projected.

## Current mapping

Modern CHLOM maps this pallet to P-01, the Identity Registry Service, credential lifecycle, signing/KMS, ZK proof services and DAIL. DID/SBT/token technologies remain optional representations rather than mandatory current runtime primitives.
