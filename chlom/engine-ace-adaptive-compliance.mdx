## Purpose

ACE is CHLOM's core **compliance-decision engine concept**: resolve the rules that apply to an action, gather the evidence needed to evaluate them, execute deterministic checks where possible, route unresolved/high-risk matters to appropriate review, and produce an explainable bounded decision.

```text
ACTION / REQUEST / EVENT
          |
          v
CONTEXT RESOLUTION
 actor / tenant / asset / jurisdiction / purpose / time
          |
          v
POLICY RESOLUTION
          |
          v
EVIDENCE RESOLUTION
          |
          v
RULE EVALUATION
          |
          +--> deterministic checks
          +--> external/oracle evidence
          +--> AI/risk recommendations
          +--> human-reserved review
          |
          v
PASS | HOLD | DENY
          |
          v
DECISION RECEIPT + DAIL + REMEDY PATH
```

## Historical position

Early CHLOM architecture positioned ACE as the enforcement brain sitting between identity/intelligence inputs and downstream licensing, exchange, governance and treasury modules. The concept remains valuable even when implemented as cloud services rather than an on-chain runtime.

## ACE is not legal authority

```text
ACE result
   !=
statutory legal opinion
   !=
professional license decision beyond delegated authority
```

ACE executes adopted institutional policy. It does not invent or expand the authority behind that policy.

## Policy resolution

ACE should identify the exact applicable policy set before evaluating rules.

```text
institutional rules
        |
corridor / cross-pallet rules
        |
pallet / service rules
        |
tenant / program rules
        |

        |
        v

```

Conflicts use explicit precedence or HOLD; no silent last-write-wins.

## Decision algebra

ACE's current public-safe decision vocabulary is:

```text
PASS
HOLD
DENY
```

### PASS

All mandatory conditions satisfied under current authority/evidence.

### HOLD

The system must not proceed yet because material state is unresolved, stale, conflicting, pending review or insufficient.

### DENY

An explicit current rule or authority state prohibits the requested action.

## Mandatory-gate composition

A safe base rule is:

```text
if exists mandatory DENY:
    DENY
else if exists mandatory HOLD:
    HOLD
else:
    PASS
```

Weighted/risk-derived inputs may inform HOLD/review but cannot override a mandatory DENY unless a separately authorized override rule exists.

## Deterministic versus advisory checks

```text
DETERMINISTIC
  exact rule evaluates from resolved inputs

ADVISORY
  AI/model/reviewer recommendation requiring policy interpretation
```

ACE should label the provenance of each check.

## AIE relationship

AIE provides intelligence/risk/anomaly evidence; ACE determines the policy consequence.

```text
AIE signal
   |
   v
ACE rule / threshold / human-review condition
   |
PASS | HOLD | DENY
```

AIE cannot self-enact an ACE decision outside delegated design.

## Policy Engine relationship

The Policy Engine executes machine rules; ACE orchestrates the broader decision context.

```text
ACE
  |
  +--> policy resolver
  +--> Policy Engine
  +--> evidence resolver
  +--> risk/AIE
  +--> reviewer workflow
  +--> decision receipt
```

## Compliance Packs

Compliance Packs provide versioned policy bundles.

- overrides/exceptions.

## Explainability

Every material ACE result should be explainable enough to answer:

```text
what was requested?
which policies applied?
which evidence was used?
which mandatory checks passed/held/denied?
which model/reviewer inputs influenced the outcome?
who/what had authority?
what remedy/review path exists?
```

Protected fraud/security logic can expose reason classes rather than exploitable internals.

## Decision freshness

A PASS can expire.

```text
PASS at T0
    |
credential expires / policy changes / asset revoked
    |
PASS no longer reusable at T1
```

Consumers should re-evaluate when applicable evidence/policy freshness requires it.

## Override

Overrides are explicit new decisions linked to the original outcome.

```text
ACE DENY/HOLD
   |
override request
   |
authority + scope + evidence + safeguards
   |
OVERRIDE DECISION
   |
DAIL
```

The original result remains intact.

## Simulation

```text
      |

```

Simulation results are inputs to governance—not adopted policy.

## Failure modes

### Missing policy source

HOLD rather than infer permission.

### Conflicting rules

Resolve adopted precedence; otherwise HOLD/adjudicate.

### Provider says eligible, local rights say revoked

P-03/current institutional rights controls; ACE denies/holds and records mismatch.

### Model recommends PASS, mandatory rule DENY

DENY.

### Rule evaluator unavailable

Fail closed for material action; do not silently bypass ACE.

### Stale PASS reused after revocation

Reject based on decision/evidence expiry and re-evaluate.

## Security threats

- policy injection;
- rule bypass;
- stale cache;
- model prompt/data poisoning;
- reason-code leakage enabling evasion;
- unauthorized override;
- cross-tenant context bleed;
- incomplete evidence treated as false/clear;
- decision replay outside scope.
