# Source Reconciliation and Authority

CHLOM has accumulated multiple generations of architecture, naming, implementation plans, and operating language. Phase 2 does not erase that history. It classifies it.

This page is the current public-safe source-authority successor for recovered reconciliation and audit material. It establishes how conflicting evidence is ordered and how corrections propagate without allowing a detailed historical artifact, provider screenshot, or runtime object to silently manufacture current institutional meaning.

## Authority order

Unless a newer founder-approved architecture decision states otherwise, use this order when sources conflict:

1. **Law, signed agreements, court or regulatory requirements, and binding obligations** where applicable.
2. **Founder-approved current architecture decisions and Phase 2/2.5 registries.**
3. **Verified production evidence, current release records, and operating runbooks.**
4. **Current dated CrownThrive/CHLOM public statements.**
5. **Historical technical papers, prospectuses, formal models, and compendia.**
6. **Experimental launch guides, vendor studies, and exploratory designs.**

This ordering works together with the [Documentation Source of Truth & Autonomous Governance](/standards/documentation-source-of-truth-and-autonomous-governance), which requires documentation changes to preserve the distinction between runtime/source evidence and approved institutional meaning.

## What this prevents

The source hierarchy prevents an older paper from silently overriding a current production state simply because the older paper is detailed.

Examples of historical conflicts that require explicit reconciliation include:

- DLA naming
- DAL / DAIL naming
- TLaaS expansions
- token names and dual-token models
- chain or mainnet assumptions
- DAO authority
- autonomous enforcement claims
- public LEX status
- decentralized identity implementation

The same rule applies to provider evidence. A provider control panel can prove the state of that provider account at a point in time, but it cannot alone establish CrownThrive-wide legal, rights, governance, economic, identity, or lifecycle authority.

## Evidence classes

Reconciliation should identify the evidence class before deciding what a source can prove. Useful classes include:

- signed or binding authority;
- founder or governed architecture decision;
- current runtime/provider evidence;
- current institutional registry state;
- current public projection;
- historical institutional source;
- exploratory or research source;
- restricted evidence reference.

The [Rights Ledger and Evidence Model](/chlom/rights-ledger-and-evidence) governs how evidence references, integrity markers, review state, and restricted exposure are represented. The [CHLOM Registry Model](/chlom/registry-model) supplies stable machine identities for the records being reconciled.

## Status labels

Source-derived capabilities should be labeled using language such as:

- current core
- active production
- controlled test
- planned
- research
- historical
- target architecture
- deprecated
- superseded
- blocked

A status label is meaningful only when tied to a source basis and an observation or effective time. "Active" without an evidence scope is not an institutional control.

## Contradiction handling

When two sources disagree, the expected result is a governed contradiction record rather than silent editing. The reconciliation should identify:

```text
claim A + source A
claim B + source B
→ authority comparison
→ current governing interpretation or HOLD
→ affected registry / article / workflow records
→ correction or adjudication event
→ downstream reconciliation
```

Where evidence is insufficient, `HOLD`, `unresolved`, or an equivalent explicit state is preferable to guessing. The institution should be able to distinguish "not yet verified" from "false", "historical", and "not applicable".

## Identity and actor evidence

Identity-related evidence follows the same model. A provider-native user ID, email address, CRM contact, community profile, or payment customer object can support identity reconciliation but does not by itself become the canonical institutional actor. See [CrownThrive ID](/technology/crownthrive-id) for the stable actor and assurance boundary.

## No silent correction

If an old source says one thing and the current registry says another, preserve the old source and record the newer governing decision.

The institution should be able to answer:

- what did we believe then?
- what evidence supported it?
- what changed?
- who approved the change?
- what is canonical now?

That is institutional memory, not duplication.

## Public and restricted projection

A reconciliation record may reference restricted evidence without publishing it. Public documentation should expose only the minimum approved facts needed to explain the current state, while restricted evidence remains subject to the [Restricted Source Register](/knowledge/restricted-source-register) and [Security & Privacy Continuity](/technology/security-privacy-continuity).

## Phase and automation boundary

Source reconciliation is a prerequisite for safe automation, not an automatic authorization to automate. The [Phase 3 Readiness Gate](/technology/phase-3-readiness-gate) separately tests whether stable schemas, actor identity, authority resolution, rollback, provider boundaries, evidence, and operating controls are ready for broader execution.

Until those gates pass, this page provides the substantive source-authority contract for controlled-test reconstruction and machine qualification while keeping provider writes, money movement, rights activation, high-risk legal/economic actions, and terminal documentation disposition fail-closed.
