## Core interface and integration

The root interface opens CHLOM core, with public aggregate status and a separate authenticated operator session. The optional LEX application is available at `/lex`. Core and LEX browser sessions use separate cookies.

The `/api/core` adapter connects genuine backend user identities to the existing `chlom_api_dispatch_v3` dispatcher. The backend retains operator assignments, scopes, authority ceilings, idempotency and DAIL receipts. Signing in does not grant operator authority. Public status returns allowlisted aggregates with explicit unavailable-source states; it does not expose private records or substitute zero counts for missing evidence.

The Node client and CLI provide the same bounded integration path. Read the exact [core API](https://github.com/crownthrive1/chlom-protocol/blob/a8b994eccfe767398a097d9c2ff24736f3863ebd/docs/CHLOM_CORE_API.md), [console](https://github.com/crownthrive1/chlom-protocol/blob/a8b994eccfe767398a097d9c2ff24736f3863ebd/docs/CHLOM_CORE_INTERFACE.md) and [client/CLI contract](https://github.com/crownthrive1/chlom-protocol/blob/a8b994eccfe767398a097d9c2ff24736f3863ebd/docs/CHLOM_CORE_SDK.md) before integrating. A domain receipt and its result determine what occurred; HTTP 200 alone does not establish a right, verified proof or payment.

## Component acceptance

| Component | Implemented scope | Acceptance still required |
|---|---|---|
| Core console and API | Independent root console, public projections, genuine user authentication and bounded canonical dispatch; public production readback recorded above. | An authorized private operator journey and its domain receipts. |
| Native FRAME candidate | Ten pallets: authority, identity, rights, licensing, settlement, tokenization, oracle, checkpoint, utility and policy; committed dependency lock and pinned toolchain. | Executable runtime/node, genesis, benchmarks, authority wiring, validator/recovery operations and security acceptance. |
| Utility and policy | Nontransferable resource allocations, reservations, consumption/releases and hash-chained receipts; approved policy versions and append-only revocations. | Governed configuration and runtime acceptance; transferable token issuance and external settlement are separate capabilities. |
| Oracle and checkpoint | Hardened oracle history, checkpoint and anchor integrity. | Actual runtime/network acceptance and provider evidence for any public anchor claimed. |
| Groth16 verifier | BN254 verification against a server-controlled circuit registry, key digests, ordered public signals, validity intervals and bounded workers. | Approved production circuit, trusted setup/key custody, application bindings and independent security review. |

Compiling the native candidate does not establish an operational network. Utility metering does not mint economic tokens or move funds. Historical token symbols remain unresolved in the source reconciliation. Regulatory signals route through defined policy authority; they cannot silently enact laws or become legal determinations.

## Privacy and zero-knowledge verification

Salted commitments and Groth16 verification are separate implementations. The verifier uses MIT-licensed `@noble/curves` for BN254 arithmetic and pairings; the CHLOM adapter has not been independently audited. Two original real proofs and altered-proof cases were compared with snarkjs. These test fixtures establish interoperability and regression evidence, not production rights proofs.

**No production circuit or proof-generation service is enabled by default.** Operators must establish the circuit, verification key, setup evidence, public-input bindings and approval before activation. Registry references are configured assertions whose underlying authority must be independently checked. The verifier receives public signals, not the private witness; public signals can still reveal information. See the exact [ZK verifier contract](https://github.com/crownthrive1/chlom-protocol/blob/a8b994eccfe767398a097d9c2ff24736f3863ebd/docs/CHLOM_ZK_VERIFIER.md).
