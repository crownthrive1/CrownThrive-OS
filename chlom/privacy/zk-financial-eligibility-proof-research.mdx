## Purpose

A ZK financial/economic proof can establish a bounded eligibility or state predicate without exposing the full account, balance, transaction history or confidential financial evidence.

Examples of **predicate families** include:

```text
balance_or_reserve >= threshold
net_required_amount_available >= obligation
financial_credential_valid = true
payment_or_settlement_condition_satisfied = true
approved_ratio_within_range = true
```

These are research/engineering patterns, not current product eligibility criteria.

## Financial proof is not payment truth

A proof of a financial predicate and a provider payment event answer different questions. A proof might establish a threshold condition; a payment provider might report an actual transaction. Neither automatically creates rights, an entitlement, an invoice, an earning or final settlement.

## Unit and currency discipline

Every financial predicate must define:

- currency or unit;
- precision;
- gross/net or balance basis;
- observation/reference time;
- whether conversion is involved;
- conversion-rate evidence if applicable;
- threshold source/policy version.

A USD threshold cannot be compared directly to a token or another currency without an explicit governed conversion model.

## Source evidence

Possible source classes can include approved financial attestations, provider/account statements, treasury records, settlement records or other policy-approved evidence. This documentation does not authorize access to any user's financial accounts by itself.

## Currentness

Financial state can change rapidly. The proof must carry a reference/observation time and policy freshness window. A proof that a threshold was satisfied at time T may not prove the condition remains true later.

## Solvency / reserve research

A threshold proof such as:

```text
verified_amount >= required_threshold
```

can support privacy-preserving reserve/eligibility research. The source and liabilities/basis definition matter: proving one asset balance is not equivalent to proving full solvency.

## Economic-schedule eligibility

A ZK proof can satisfy one prerequisite in a DLA/LEX/economic workflow—for example an approved deposit or capacity threshold—while the actual economic schedule, agreement, rights and authority remain separately governed.

## Provider/payment relationship

If the predicate depends on provider data, the source adapter must be registered, fresh and authenticated. Provider data remains evidence. The proof cannot upgrade provider semantics into institutional economic truth beyond the encoded and accepted predicate.

## Circuit governance

Each circuit defines the financial source schema, amount/basis semantics, unit/currency, threshold/range input, reference-time rule, public inputs, verification key, accepted source classes and retirement policy.

Exact circuit implementation, witness handling and any protected commercial thresholds remain restricted where classified.

## Privacy risks

Repeated threshold queries can leak a balance through binary search. Range choices, proof frequency, correlation identifiers and metadata can reveal economic information even when the witness is hidden. Verifier policy should limit unnecessary probing and use coarse predicates where possible.

## Regulatory/legal boundary

A financial ZK proof is a cryptographic/evidentiary technique, not a credit decision, investment recommendation, banking product, tax opinion, securities determination or underwriting authority. High-consequence use requires applicable legal/professional and institutional governance.

## DAIL evidence

Store only safe proof/circuit/version, predicate class, threshold/range reference, unit, source class, reference/evaluation time, verification result and later revocation/correction. Do not store private balances/statements in a public event.

## Failure states

Invalid/retired circuit, stale financial evidence, wrong unit/currency, unsupported source, threshold-version mismatch, context replay, source contradiction, conversion evidence stale, private balance leakage, proof valid but policy does not accept it.

## Tests

Test at/below/above threshold, wrong currency, stale source, changed balance after proof, conversion scenario, binary-search privacy abuse, revoked source credential, context replay, provider mismatch and public payload scan.
