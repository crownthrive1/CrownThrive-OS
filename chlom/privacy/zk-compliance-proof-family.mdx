## Purpose

CHLOM's recovered architecture repeatedly describes **zero-knowledge compliance proofs**: proofs that a required compliance predicate is satisfied while disclosing less underlying evidence than a conventional document/API response would expose.

This component family is broader than any one age, geography, identity, financial or license circuit. It defines how policy-specific ZK predicates are registered, verified, composed and governed.

## Core relation

The Gold Paper theorem lineage preserves the public-safe relationship:

```text
Verify(proof) = true
=> encoded_predicate = true
```

under the proof system's soundness assumptions.

CHLOM adds the institutional distinction:

```text
cryptographically_valid
!= policy_usable
!= authority_to_execute
```

## Predicate registry

Every compliance proof maps to a registered predicate/circuit. A predicate record must state:

- what fact is proven;
- what fact is **not** proven;
- accepted source credential/evidence types;
- public inputs;
- currentness/revocation requirements;
- context/domain separation;
- circuit/key version;
- security/audit status;
- activation/retirement state;
- applicable Compliance Pack references.

## Policy binding

A proof is useful only if the active policy accepts its predicate for the current action. A ZK proof cannot replace a different mandatory control merely because it is mathematically valid.

Example:

```text
proof_of_age_threshold
!= proof_of_professional_license
!= proof_of_rights_ownership
```

## Witness/source currentness

Where a proof depends on a revocable credential, current license, external status or time-sensitive economic fact, CHLOM checks currentness separately. Proof creation time alone does not freeze the underlying institutional state forever.

## Composition

Multiple ZK proofs can be composed institutionally as separate verified predicates. THM-009 preserves the historical compositionality lineage, while ALG-001/ALG-017 determine current policy combination.

```text
all required proof predicates valid/usable
+ all non-ZK mandatory controls passed
+ authority gate
= candidate action
```

## Selective disclosure

A ZK compliance proof should reveal only public inputs and predicate result required by the verifier/policy. Public proof receipts should avoid unique metadata combinations that unnecessarily correlate a subject across contexts.

## ZKX relationship

ZKX is the orchestration layer that can select the required proof type/circuit, ensure proof/key/currentness compatibility, verify results and hand public-safe proof evidence into policy evaluation. ZKX does not self-define the policy that makes a proof sufficient.

## Attestations relationship

A proof verification can generate an attestation/receipt stating that a particular circuit/predicate verified at a time under a context. That attestation remains subject to issuer/verifier authorization, schema/currentness and revocation rules.

## Verifier registry

Compliance proofs should use approved verifier/key/circuit registries. A verifier service or smart contract that is not approved for a proof type cannot make a proof institutionally usable merely because it returns `true`.

## Proof lifecycle

```text
CIRCUIT / PREDICATE DRAFT
 -> SECURITY / CONFORMANCE TEST
 -> APPROVED / ACTIVE
 -> PROOF CREATED
 -> PROOF VERIFIED
 -> POLICY USABILITY CHECK
 -> CONSUMED / RECORDED
 -> STALE / REVOKED / SUPERSEDED as applicable
```

## Failure states

Invalid proof, retired circuit, wrong verification key, unsupported predicate, wrong subject/context, stale/revoked witness source, missing policy applicability, replay, proof verifier unavailable, public-input mismatch, proof valid but action authority absent.

## DAIL evidence

Public-safe DAIL/proof receipts can include proof ID/digest, circuit/version, predicate class, public inputs, verifier registry ref, source class, verification result, policy context, evaluated time and subsequent revocation/correction references.

## Threat model

- bad policy encoded correctly;
- missing mandatory predicate;
- outdated circuit/key;
- verifier registry compromise;
- proof replay;
- correlation/privacy leakage;
- revoked credential reuse;
- public witness leakage;
- proof result treated as legal conclusion;
- proof result treated as execution authority.

## Tests

Test valid/invalid proofs, retired circuit, wrong key, wrong context, revoked witness, missing required second predicate, proof composition, verifier registry removal, replay and public receipt privacy.

## Current status

ZK compliance proofs are preserved as substantive CHLOM IP/research and current engineering targets. Individual production circuits and proof services require separate implementation/security evidence.

## Versioning

Predicate, circuit, verification key, proof schema and policy versions are independent. Every proof receipt records the exact versions used.
