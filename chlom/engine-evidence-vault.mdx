## Purpose

The Evidence Vault is CHLOM's conceptual and operational layer for **preserving the source objects that justify institutional records and decisions**. It provides chain of custody, classification, content identity, source lineage, access boundaries, retention, legal/security holds, recovery and public-safe projection references.

It must not be confused with a secrets manager.

```text
SOURCE FILE / RECEIPT / AGREEMENT / LOG / PROOF
                   |
                   v
             CLASSIFICATION
                   |
                   v
            EVIDENCE VAULT
          +--------+---------+
          |                  |
     private custody      digest / reference
          |                  |
          +--------+---------+
                   |
                  DAIL
                   |
        public/internal projections
```

## Custody domains

Current CrownThrive/CHLOM separates three protection domains:

```text
SECRET VALUES / PRIVATE KEYS
   -> approved secret store / Supabase Vault

RESTRICTED HUMAN-READABLE MASTERS / SOURCE EVIDENCE
   -> governed private Drive / private repositories

PUBLIC-SAFE DOCUMENTATION
   -> GitHub + Mintlify
```

The Evidence Vault engine records references/classification across those domains; it does not justify copying a password/token into a document.

## Content identity

A digest can identify exact bytes/content:

```text
d = H(content)
```

The algorithm/version must be named. A digest proves content equality/integrity under its assumptions—not factual truth.

```text
hash matches != statement is true
```

## Chain of custody

```text
SOURCE ORIGIN
   |
CAPTURE
   |
CLASSIFY
   |
STORE / HASH
   |
ACCESS / REVIEW
   |
DERIVED RECORD / DECISION
   |
CORRECTION / SUPERSESSION / HOLD
```

Each material custody transition can receive DAIL evidence.

## Source versus derived evidence

```text
SOURCE EVIDENCE
  original/provider/source artifact

DERIVED EVIDENCE
  normalized row, summary, transcription, calculation, model output, screenshot derivative
```

Derived artifacts must retain references to their inputs and transformation/version.

## Provider evidence

Provider evidence includes API readback, dashboard export, receipt, transaction record or service status. It proves only the provider-side fact represented within that provider's scope.

```text
provider receipt
     !=
institution-wide canonical truth
```

Reconciliation occurs in the relevant domain service.

## Classification

Evidence classification can control:

- who can access it;
- whether content may be indexed;
- whether it can appear in public docs;
- retention/hold requirements;
- whether a public digest/reference is permissible;
- whether legal/professional review is required.

## Public-safe projection

```text
RESTRICTED EVIDENCE E
        |
policy / minimization
        |
        v
PUBLIC PROJECTION P(E)
```

`P(E)` can include a stable evidence ID, digest, type, date and current status without exposing the original artifact.

## Evidence hold

A hold prevents deletion/alteration under defined governance/legal/incident conditions.

```yaml
hold_id: stable ID
evidence_refs: []
reason_ref: required
authority_ref: required
opened_at: timestamp
expires_or_review_at: nullable
status: active|released|superseded
```

The exact legal effect of a litigation/legal hold requires appropriate legal authority; this engine provides the custody mechanism.

## Recovery

Recovery quality is measured by round-trip/readback, not merely by backup existence.

```text
backup exists
   |
restore candidate
   |
content digest / metadata / link checks
   |
consumer readback
   |
RECOVERY VERIFIED
```

## Missing evidence

If a canonical record references evidence that cannot be located:

```text
evidence status = missing
related high-risk claim/action -> HOLD/review as policy requires
```

The system does not invent replacement evidence.

## DAIL relationship

DAIL stores the event/evidence lineage and references; the Evidence Vault stores or points to the protected source content.

```text
DAIL RECORD
  evidence_ref = EV-123
       |
       v
EVIDENCE VAULT INDEX
       |
       v
restricted source object
```

## Attestation relationship

An attestation can summarize verified evidence. The underlying evidence can remain restricted.

## Merkle/notarization relationship

Multiple evidence digests can be batched into a Merkle root or external notarization anchor. That provides integrity/time anchoring, not factual validation.

## Failure modes

### Source file renamed/moved in Drive

Canonical evidence ID remains stable; update custody locator after verified lookup/readback.

### Digest mismatch

Mark evidence integrity problem/HOLD; preserve both expected and observed digests and investigate.

### Public article links restricted file

Contain/fix projection and review permissions; do not solve by making restricted file public.

### Secret discovered in evidence doc

Move/rotate/revoke under security workflow; secrets belong in secret store, not document custody.

### Provider deletes historical dashboard record

Preserve previously captured evidence/digest where law/policy permits and mark current provider source unavailable.

## Security/privacy threats

- overbroad Drive sharing;
- secret leakage;
- tampering;
- malicious replacement with same filename;
- stale public projection;
- evidence deletion during dispute;
- cross-tenant evidence exposure;
- public indexing of restricted content.

## Restricted companion

The Evidence Vault by definition has a restricted operational estate. Public docs should document its contract, while private Drive/repository records hold source and indexes according to classification.

## Metrics

- public/restricted projection violations;

## Invariants

```text
Evidence Vault != secret store
evidence exists != claim true
hash match != legal/factual correctness
provider receipt != canonical truth
backup exists != recovery verified
public digest != permission to expose source
derived summary != source artifact
missing evidence != permission to fabricate
```
