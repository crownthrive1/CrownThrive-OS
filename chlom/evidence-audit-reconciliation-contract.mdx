## CHLOM Evidence & Audit Reconciliation Contract

This contract is the current public-safe substantive successor for recovered CHLOM evidence/audit material whose historical bodies are missing or no longer authoritative for current operating state. It does **not** recreate or quote missing historical bodies. It defines the current evidence, source, audit, and correction semantics machines and operators may rely on.

The governing distinction is: **a claim, the evidence supporting the claim, and the authority to act on the claim are separate objects**.

## Evidence classes

Evidence should be classified before it is used. Common classes include:

- signed agreements and binding authority;
- founder or governed architecture decisions;
- current runtime and provider observations;
- current registry state;
- release, deployment, test, and rollback evidence;
- public institutional statements;
- historical papers and compendia;
- exploratory or research material;
- restricted evidence references.

The [Source Reconciliation and Authority](/chlom/source-reconciliation) contract determines how those sources are ordered when they conflict. More detail does not automatically mean more authority, and newer metadata does not automatically mean fresher institutional meaning.

## Stable evidence references

Evidence relationships should use stable IDs or references so they survive repository moves, provider changes, filenames, and public-route changes. Where appropriate, an evidence record can include:

- stable evidence ID;
- source type and title;
- custodian;
- created, received, or observed time;
- integrity marker or checksum;
- classification and visibility;
- governing claim or object;
- review state;
- reviewer or governed decision reference;
- supersession/correction relationship;
- affected downstream records.

The [Rights Ledger and Evidence Model](/chlom/rights-ledger-and-evidence) provides the canonical evidence/provenance model. The [CHLOM Registry Model](/chlom/registry-model) supplies stable object relationships for evidence to bind against.

## Integrity is not truth

A checksum, signed receipt, immutable event ID, screenshot, provider log, or DAIL event can establish integrity or observed state within a defined scope. It does not independently prove every institutional conclusion drawn from that source.

Examples:

- provider delivery success ≠ institutional rights ownership;
- payment-provider success ≠ final economic settlement authority;
- a verified user account ≠ corporate or founder authority;
- a historical whitepaper ≠ current production state;
- a domain or repository existing ≠ production activation;
- a test passing ≠ permission to expand the test into D3 or provider-write authority.

The system should record both the evidence fact and the governing interpretation used to create institutional state.

## Audit questions

A sufficient audit trail should answer:

- what claim or state was evaluated;
- which evidence was available at the time;
- which source-authority rule applied;
- who or what performed the review;
- which authority basis governed the decision;
- what ALLOW, HOLD, DENY, correction, or no-change result followed;
- which downstream objects depended on that result;
- whether later evidence corrected or superseded it.

This is why documentation, registry rows, provider state, and audit events must be linked rather than collapsed into one mutable statement.

## Public and restricted projections

Evidence is private by default unless an approved exposure rule says otherwise. A public page may state that evidence exists, expose a stable evidence reference, summarize an approved result, or publish a checksum without exposing the underlying restricted artifact.

Sensitive identity records, credentials, secret material, security evidence, private agreements, personal data, restricted commercial evidence, and internal operating artifacts remain subject to the [Restricted Source Register](/knowledge/restricted-source-register) and [Security & Privacy Continuity](/technology/security-privacy-continuity).

## Correction and supersession

Corrections preserve lineage rather than overwriting history:

```text
original claim / record
→ new or contradictory evidence
→ authority comparison
→ correction or adjudication event
→ current governing record
→ affected downstream objects
→ remediation / reconciliation status
```

The previous state remains inspectable so CrownThrive can prove what was known, what changed, why it changed, and whether dependent systems were reconciled.

## Documentation as an audited projection

Documentation is a governed projection of approved institutional meaning. The [Documentation Source of Truth & Autonomous Governance](/standards/documentation-source-of-truth-and-autonomous-governance) requires material changes to resolve to `docs_updated`, `docs_no_change`, or `docs_delta_opened`. Evidence used by documentation must remain traceable to its source class and authority boundary.

A public documentation update therefore cannot turn restricted provider evidence into public operational detail merely to make a page appear complete.

## Machine-use boundary

Agents and services may use evidence to support bounded decisions only within their authority. They must not convert evidence into new legal, economic, rights, identity, or provider-write authority that is not present in the governing record.

A machine evaluation should be able to determine:

```text
claim / proposed state
→ stable institutional object
→ evidence references
→ source authority / freshness
→ policy and actor authority
→ phase / risk boundary
→ ALLOW | HOLD | DENY
→ audit / DAIL receipt
```

## Phase 3 boundary

This substantive evidence/audit contract improves machine-readiness without claiming broad production readiness. The [Phase 3 Readiness Gate](/technology/phase-3-readiness-gate) independently governs stable schemas, actor identity, authorization, rollback, provider boundaries, evidence, and operational controls.

Until the hard exit passes, evidence/audit reconciliation supports controlled-test qualification and parent review while D3 authority, provider writes, money movement, rights/license activation, production activation, and terminal article disposition remain fail-closed.
