# Oracle Lattice and Validator Assurance — External Evidence Without Blind Trust

Historical CHLOM uses an **Oracle Lattice** to connect protocol rules to off-chain reality and a validator network to maintain the proposed dedicated ledger. The core insight survives the cloud-first architecture: **consequential decisions must not blindly trust one external provider, one observation, or one execution surface**.

## Freshness is part of truth evaluation

```text
observation exists
      |
      v
is source authentic?
      |
      v
is observation fresh enough?
      |
  +---+---+
  |       |
 YES     NO
  |       |
  v       v
continue  HOLD / refresh
```

A historically valid sanctions check, credential or market value may be unusable for a current consequential decision if its freshness window has expired.

## Source authority versus source reliability

These are different concepts.

```text
AUTHORITY = is this source entitled to make this type of claim?
RELIABILITY = how consistently/accurately does it report?
FRESHNESS = how current is this observation?
CORROBORATION = do independent sources agree?
```

A highly reliable source cannot manufacture legal authority it does not possess. An authoritative source can still be stale or technically unavailable.

## Multi-source corroboration

Historical CHLOM proposes cross-validation and majority/median-style aggregation for some oracle classes.

```text
Source A ---- PASS ----+
Source B ---- PASS ----+----> threshold met ----> accepted observation
Source C ---- FAIL ----+
```

But not every domain should use majority vote. For example, an official court order may have a single legally authoritative source while market prices may appropriately use multiple feeds.

The aggregation strategy must therefore be policy-specific.

## Historical validators

The Grand Prospectus and Technical Blueprint describe validators maintaining a dedicated PoS/NPoS chain, checking transaction validity and potentially incorporating compliance pre-checks. Historical incentives include staking, rewards, slashing and governance oversight.

That is **target architecture**, not current production fact.

## Modern validator invariant

What survives today is the need for independent verification on consequential paths.

```text
proposed state change
       |
       v
primary evaluator
       |
       v
independent validator / verifier
       |
   +---+---+
   |       |
 agree   disagree
   |       |
   v       v
continue  HOLD / case
```

The verifier may be a separate service, agent, human reviewer, cryptographic validator or future decentralized node depending on the domain.

## Assurance bonds versus tokens

Historical papers use staked tokens and slashing to economically discipline validators/oracles. Modern CHLOM can preserve the **assurance bond** concept without requiring a live token.

Possible future representations may include:

- contractual deposits;
- reserve/holdbacks;
- provider SLAs;
- reputation score;
- insurance/bonding;
- token stake after legal/economic activation.

The invariant is accountability for false or malicious service—not the token format.

## Privacy

An oracle should transmit only the minimum necessary information. Historical sources explicitly contemplate ZK-assisted identity or sanctions proofs so a verifier can learn that a condition is satisfied without receiving the underlying personal data.

## Failure conditions

HOLD or deny consequential processing when:

- no authoritative source is available;
- freshness expires;
- critical sources conflict;
- provider authentication fails;
- observation signature/digest cannot be verified;
- source scope does not cover the claim;
- a validator/verifier is the same unseparated actor that generated the consequential result where independence is required;
- quorum/threshold is not satisfied;
- a fallback source would lower the required authority level.
