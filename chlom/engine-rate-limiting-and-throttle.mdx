## Purpose

This engine controls how much traffic, work or side-effect execution a CHLOM service is allowed to accept under **institutional budgets, provider limits, plan entitlements and safety controls**.

It exists to prevent cost overruns, provider lockouts, accidental floods, denial-of-service amplification and ambiguous `unlimited` semantics.

```text
REQUEST
  |
identity / tenant / service / capability
  |
resolve institutional budget
  + provider quota / contract / billing state
  + safety/rate controls
  |
  v
ALLOW | THROTTLE | HOLD | DENY
  |
meter / evidence / retry guidance
```

## Canonical CrownThrive-local monthly ceiling semantics

```text
-1   = unlimited CrownThrive-local monthly request ceiling
0    = exactly zero requests permitted
N>0  = exactly N requests permitted per month
null = unresolved/unknown and must fail closed
```

This supersedes prior local interpretations that treated `0` as unlimited.

## Provider limits remain authoritative

```text
CrownThrive local ceiling = -1
      !=
provider has infinite capacity
```

Provider throttles, contractual entitlements, quotas, spend caps, billing state and technical limits remain separate constraints.

The effective allowance is bounded by every applicable authority:

```text
effective_capacity = intersection(
  institutional budget,
  provider entitlement,
  safety limits,
  policy/authority,
  technical availability
)
```

This is a conceptual set intersection, not a provider billing formula.

## Rate policy

Rate limit and budget are distinct:

```text
budget = amount allowed over a larger accounting period
rate = allowed frequency in a short window
burst = temporarily tolerated peak
concurrency = simultaneous in-flight work
```

## Decision flow

```text
budget value resolved?
 no/null -> HOLD / fail closed
 yes
  |
 budget == 0?
 yes -> DENY
 no
  |
 local monthly remaining?
 no -> DENY/HOLD according to policy
 yes or -1
  |
 provider current entitlement available?
 no/unknown -> HOLD/DENY
 yes
  |
 short-window rate/concurrency okay?
 no -> THROTTLE / retry
 yes
  |
 action authority/policy still valid?
 no -> DENY/HOLD
 yes -> ALLOW
```

## Provider accounting mismatch

Provider usage and local usage can differ because of retries, provider-side counting rules or delayed reporting.

```text
local meter = 900
provider reports = 915
      |
      v
reconcile counting rules / retries / lag
```

Do not overwrite local records merely to match a provider dashboard without understanding the difference.

## Retry behavior

A throttled request can receive structured retry guidance:

```text
retry_after
reason_class
current limit scope
```

Automatic retries must use backoff/jitter/idempotency for side effects.

## Side-effect protection

Throttling/retries must not duplicate payments, licenses or governance actions.

```text
retry same idempotency key
   -> same logical operation
```

## Agent budgets

Agents receive budgets scoped to identity, skill/capability and delegation.

```text
agent budget != agent authority
```

An agent with remaining request budget cannot perform an un-delegated action.

## Spend-cap relationship

Some providers stop service or become read-only when spend caps/quotas are exhausted. The engine records provider-specific behavior and routes HOLD before assuming overage billing will occur.

## Failure modes

### Budget = null

Fail closed; do not interpret as zero or unlimited.

### Budget = 0

Deny all requests in that governed scope.

### Budget = -1 but provider quota exhausted

Provider constraint controls actual execution; HOLD/DENY accordingly.

### Provider dashboard stale

Do not infer available quota if current provider state is required; use certified local guardrails and HOLD if necessary.

### Retry storm

Apply circuit breaker/backoff and preserve idempotency.

## Security / abuse

- distributed abuse across identities;
- tenant evasion;
- rate-limit bypass through aliases;
- concurrency floods;
- provider quota exhaustion attacks;
- replay/retry duplication;
- unbounded `-1` misunderstood as provider unlimited.
