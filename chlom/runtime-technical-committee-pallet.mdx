## Source basis

Historical CHLOM sources explicitly identify **Democracy, Council, Technical Committee and Treasury** as governance modules adapted from Substrate patterns. The Technical Committee was a technical-expert lane intended to help evaluate upgrades, urgent defects and specialized runtime changes.

This article preserves that module separately from the Council/Multisig Pallet and the broader Governance/DAO Pallet.

## Non-purpose

The Technical Committee does not automatically possess:

- legal/commercial authority;
- unilateral protocol sovereignty;
- unrestricted emergency powers;
- the right to approve its own authority expansion;
- authority to change rights/economics merely because a change is technically possible.

## Review domains

A technical committee may evaluate:

- runtime/service upgrades;
- schema migrations;
- cryptographic/library changes;
- ZK circuit/verifier changes;
- model/runtime compatibility;
- performance/availability impacts;
- API breaking changes;
- security patches;
- emergency mitigations;
- rollback plans;
- provider-exit and recovery behavior.

## Authority handoff

A technical recommendation must route to the authority appropriate to the change.

```text
technical assessment
   !=
policy adoption
   !=
economic approval
   !=
legal/professional conclusion
```

For example, a technically safe royalty-calculation change still needs valid economic authority before altering active schedules.

## Emergency technical action

Historical governance frameworks allow fast-track technical response. Modern CHLOM requires:

- pre-defined emergency scope;
- evidence of incident/risk;
- minimum required technical approvals;
- bounded temporary action;
- no secret permanent policy change;
- follow-up governance review;
- rollback/restoration path;
- DAIL record.

## Compatibility

A review should identify:

- data/schema compatibility;
- API compatibility;
- event compatibility;
- stored-state migration;
- credential/DLA/policy semantics;
- observability changes;
- rollback compatibility;
- downstream consumer impact.

## Model/AI changes

Technical Committee expertise may participate in AI model deployment review, but model governance also requires risk/bias/evaluation evidence and current authority.

```text
model passes technical tests
   !=
model approved for high-impact decisions
```

## Failure modes

- committee member conflict -\> recusal/reassignment;
- missing test evidence -\> HOLD;
- no rollback for material change -\> HOLD unless separately authorized irreversible migration;
- security regression -\> reject/hold;
- breaking compatibility not migrated -\> HOLD;
- committee recommends change outside scope -\> route to appropriate authority;
- emergency mitigation expires -\> restore/reapprove according to policy.

## Threat model

- expert capture;
- concealed conflict;
- technical authority expansion;
- emergency shortcut abuse;
- insufficient test coverage;
- compromised artifacts;
- stale change evidence;
- approval of provider-specific design as institutional invariant;
- hidden breaking change;
- rollback path that cannot actually execute.

## Test vectors

1. low-risk compatible patch \+ full tests -\> recommendation/approval within scope;
2. missing security evidence -\> HOLD;
3. breaking schema change without migration -\> HOLD;
4. expert conflicted -\> vote/review excluded;
5. urgent exploit \+ preauthorized emergency profile -\> temporary mitigation \+ sunset;
6. economic semantic change -\> technical review cannot alone activate it;
7. rollback tested -\> release candidate eligible;
8. provider-specific change -\> provider-exit implications documented;
9. model upgrade -\> technical pass plus separate model-governance gate;
10. source-era Technical Committee concept -\> no claim of current live committee.

## Current mapping

Modern CHLOM maps this concept to governed technical review/change-control lanes involving release engineering, security, domain SMEs and appropriate approval authorities. It need not use Substrate's Technical Committee pallet.

## Restricted companion

May contain vulnerability details, private source diffs, security scans, exploit reproductions, production topology, rollback commands, private reviewer identities and restricted incident data.

## Invariants

```text
technical expertise != universal authority
technical approval != legal/economic approval
emergency mitigation != permanent policy
security test pass != production proof until deployment/readback
provider implementation != institutional invariant
committee cannot self-manufacture expanded authority
```
