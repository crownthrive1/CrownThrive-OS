Use this runbook to convert protected institutional knowledge into a public-safe, maintained, and fulfillable digital asset.

## Lifecycle

```text
concept → candidate → packaged → rights_cleared → pricing_authorized
→ fulfillment_certified → checkout_staged → live
```

A later state requires evidence from every earlier state. Never promote an asset because a downstream surface exists.

## 1. Resolve the repeatable method

Identify the operating pain, intended buyer, expected capability, assumptions, and authoritative sources. Separate the method from production identities, credentials, customer data, private incident evidence, and trade-secret calibration.

## 2. Build the package

Every commercial package should contain:

- a plain-language entry point;
- the operator or implementation runbook;
- reusable checklists, schemas, or manifests;
- positive and negative test expectations;
- version, dependency, and support assumptions;
- the customer license and update policy;
- an integrity hash for the exact compressed artifact.

Use immutable SKUs and semantic asset versions. Compress release artifacts with deterministic metadata where practical so equivalent content produces stable integrity evidence.

## 3. Prove the public-safe boundary

<Warning>
  Synthetic examples are allowed. Live credentials, raw provider secrets, account identifiers, customer payloads, private database rows, and internal incident records are not product content.
</Warning>

Review ownership, third-party licenses, data provenance, provider terms, and any embedded media before declaring `rights_cleared`.

## 4. Stage commerce

Create Stripe Products and Prices from the canonical SKU register. Use Stripe-hosted Checkout and dynamic payment methods. Keep amount selection server-side. Do not create a public Payment Link before fulfillment certification.

The exact Stripe product tax code and selling-entity registration posture require appropriate review. Do not substitute a generic tax code merely to remove a launch warning.

## 5. Certify fulfillment

The release passes only when evidence proves:

1. a valid payment event is authenticated;
2. invalid, stale, disallowed, and replayed events fail safely;
3. one paid order creates exactly one entitlement;
4. the correct buyer receives the intended private version;
5. another identity cannot obtain the asset;
6. refund, dispute, expiry, and migration transitions match visible terms;
7. retries do not duplicate entitlements or deliveries;
8. monitoring, rollback, and version integrity are recorded.

## 6. Publish and maintain

Publish the customer-facing offer only after terms, price, tax posture, entitlement, and delivery agree. Record Product and Price IDs in the private control plane, not the public asset.

Run narrow scheduled checks for provider drift, broken documentation links, stale assumptions, dependency advisories, and product gaps. Scheduled work may create evidence reports and candidate updates. It must not silently change provider secrets, legal terms, tax classifications, canonical documentation, or payment activation.

## Status contract

| Status | Meaning |
| --- | --- |
| `PASS` | Current evidence supports the exact claim |
| `WATCH` | Working, but freshness or drift needs attention |
| `BLOCKED` | A required permission, binding, policy, or dependency is absent |
| `DEFERRED` | Intentionally outside the present release boundary |

A high-quality asset is not only useful on day one. It tells the buyer when its assumptions have stopped being true.
