# Production deployment and rollback

Use this runbook for controlled production releases across CrownThrive websites, APIs, documentation, commerce, and supporting services.

## Preconditions

Before deployment, confirm:

- governed issue or release ID exists
- scope and acceptance criteria are clear
- branch and commit are identified
- required tests pass
- rights, privacy, security, commerce, or publishing approvals exist where applicable
- environment variables and secrets are present without exposing values
- migrations have rollback or reconciliation plans
- last known good release is recorded
- monitoring and smoke-test owners are assigned

## Release record

Record:

```yaml
release_id: rel_2026_001
platform: vm.crownthrive.com
environment: production
commit: git-sha-or-build-id
previous_release: rel_2026_000
operator: website-release-agent
approver: human-approver
started_at: UTC timestamp
rollback_target: rel_2026_000
```

## Deployment sequence

1. Freeze unrelated high-risk changes.
2. Confirm production health before deployment.
3. Apply configuration or migration prerequisites.
4. Deploy the approved build.
5. Confirm build and service startup.
6. Run route, API, authentication, commerce, and content smoke tests according to scope.
7. Compare public and registry states.
8. Monitor errors, latency, payment events, and customer impact.
9. Mark the release verified or initiate rollback.

## Minimum smoke tests

For a public site:

- homepage and primary navigation
- authentication and account entry
- search and sitemap
- critical forms
- mobile and desktop rendering
- legal and support routes
- error and 404 handling

For commerce:

- product page
- server-side price mapping
- checkout creation
- signed webhook
- entitlement
- protected delivery
- refund or dispute behavior if affected

For documentation:

- navigation tree
- page rendering
- internal links
- code blocks and diagrams
- public/private content scan
- search indexing intent

## CIE governed-internal production

Cultural Imprint Engine production is a headless governed-internal release, not a public website launch or commerce activation.

### Required source and runtime evidence

Before CIE activation, verify all of the following against the exact current snapshot:

- canonical Support `main` SHA
- canonical CIE `main` SHA
- current Support↔CIE technical-link receipt
- Guardian verification
- repository-family verification
- interoperability verification
- stable platform identity `ct.platform.cie`
- accepted public contract digest parity
- Framework Production Promotion Governance PASS
- Documentation Governance PASS
- Security Governance PASS
- Governed Merge Gate PASS
- rollback function `chlom_runtime.rollback_framework_production_v1`

### Production authority modes

CIE may enter production through one of three explicit modes:

1. `agent_d_certification` — normal independent parent-certification path.
2. `founder_override` — ask-first deadlock exception with a non-executable preflight and an exact separate Founder Continuity request.
3. `founder_direct` — explicit human Founder production instruction bound to an exact Founder Continuity request.

`founder_direct` is human-only. It requires D2/A2, `surrogate_state=ineligible`, tested rollback, exact version/content hashes, and request scope `CIE_GOVERNED_INTERNAL_PRODUCTION`. Agents may execute after the human decision is recorded; they may not manufacture or broaden the authority.

### CIE production state

A successful bounded activation sets:

```yaml
repository: linked_governed
package: maintained
operationally_enabled: true
algorithm: production_limited
production_agent: ct.framework-agent.cie
authority_ceiling: D2
vote_eligible: false
api_exposure: governed_internal_only
mcp_exposure: governed_internal_only
public_activation: false
commerce_activation: false
provider_write_effect: false
rights_effect: false
economic_effect: false
D3_auto: false
```

The protected production canary must return `PASS` and emit chain evidence without returning the private CIE policy body.

The CIE implementation repository may use the Framework Factory package hosted by its registered parent only when the latest exact technical-link receipt matches both heads and confirms Guardian, family, and interoperability proof with zero authority, activation, vote, or child-self-activation effects.

### Economic boundary

CIE production does not authorize pricing, checkout, Stripe, Crown Credits issuance, entitlements, rights grants, settlement, or money movement. Those remain under ThriveEvergreen and their own exact economic authority gates.

### CIE rollback triggers

Rollback CIE production when:

- exact Support↔CIE source linkage becomes stale or contradictory
- Founder or parent-production authority becomes invalid or is revoked
- the protected score canary fails
- private policy-bundle integrity fails
- chain evidence cannot be appended
- CIE algorithm authority exceeds the caller binding
- public or commerce authority appears without a separate governed grant

Rollback restores the recorded pre-production state and preserves all activation, rollback, chain, and DAIL receipts.

## Rollback triggers

Rollback or disable the affected feature when:

- authentication or authorization fails
- payment or entitlement integrity fails
- protected data is exposed
- critical routes return errors
- required migrations cannot reconcile
- customer-impact errors exceed the approved threshold
- public claims or product states become materially false
- monitoring is unavailable for a high-risk release

## Rollback sequence

1. Declare rollback and preserve incident evidence.
2. Stop additional unsafe traffic or automation where necessary.
3. Revert to the last known good build or disable the affected feature flag.
4. Reverse or reconcile migrations using the approved procedure.
5. Re-run critical smoke tests.
6. Confirm payment, entitlement, account, and public states.
7. Communicate customer impact where required.
8. Update the issue, release record, incident, and changelog.

## Database and state cautions

A code rollback does not automatically reverse:

- database writes
- Stripe objects
- entitlements
- credits ledger entries
- emails or notifications
- published files
- external API actions
- rights or license records

These require explicit reconciliation.

## Post-deployment monitoring

Monitor:

- HTTP and application errors
- authentication failures
- webhook failures
- payment and entitlement mismatches
- latency
- broken assets
- search and sitemap regressions
- support tickets
- conversion anomalies

## Closure

A deployment closes only when:

- production smoke tests pass
- registries and public states agree
- monitoring is stable
- required downstream systems are reconciled
- release notes and known issues are updated
- rollback readiness remains documented

<Warning>
  A successful build is not a successful release. Production behavior, records, and customer outcomes must also be verified.
</Warning>
