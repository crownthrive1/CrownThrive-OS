# Evidence reconciliation and gate audit

Use this runbook when a system must prove that source claims, machine state, documentation, and runtime evidence agree before a gate can pass.

## Operating principle

Evidence is stronger than inference. `PASS` remains drift-watched. A deferral is not a technical pass. Research growth is not automatically certification debt. Missing or inaccessible evidence remains `UNKNOWN` unless a governing rule supplies a different explicit state.

## Evidence ladder

Prefer, in order appropriate to the claim:

1. current canonical machine state;
2. first-party provider/runtime evidence;
3. authoritative repository or signed release evidence;
4. durable institutional records;
5. dated public observations;
6. historical sources;
7. research or planning material.

Do not use a weaker source to replace stronger current evidence merely because it is easier to retrieve.

## Reconciliation sequence

1. Identify the exact claim and its required proof class.
2. Resolve the canonical record and current state.
3. Enumerate expected source families.
4. Read available sources independently.
5. Record unavailable sources rather than guessing.
6. Compare values, dates, IDs, lifecycle states, and authority.
7. Classify each result as confirmed, drifted, contradicted, stale, or unknown.
8. Determine whether the claim may remain PASS, must reopen, or remains NOT-PASS/UNKNOWN.
9. Produce a sanitized evidence envelope.
10. Hand the packet to an independent gatekeeper where required.

## Evidence envelope

```yaml
claim_id: example.claim
required_proof: provider_and_machine
canonical_state: OPEN
sources:
  attempted: []
  read: []
  unavailable: []
findings:
  confirmed: []
  drift: []
  contradictions: []
unknowns: []
proposed_disposition: HOLD
originator_can_self_certify: false
```

## Drift rules

Reopen or hold a prior PASS when:

- authoritative evidence materially changes;
- a previously verified source becomes unavailable and continuity proof is required;
- implementation differs from the certified version or scope;
- a candidate branch changes after exact-head review;
- a provider/account/runtime fact conflicts with the registry;
- a classifier or refresh routine corrupts the proof denominator.

Do not reopen solely because unrelated R&D records were added unless those records were promoted into governed certification scope or materially touch the certified claim.

## Negative tests

A reliable reconciliation system must reject:

- `UNKNOWN -> PASS` without evidence;
- `DEFERRAL -> PASS` because a deadline exists;
- target version being treated as installed version;
- public page existence being treated as rights proof;
- planned repository name being treated as repository existence;
- synthetic webhook receipt being treated as provider delivery proof;
- mergeability being treated as governance acceptance.

## Verification checklist

- [ ] Exact claim and required proof class are defined.
- [ ] Canonical state was read first.
- [ ] Stronger evidence was not replaced by weaker evidence.
- [ ] Unavailable sources are recorded.
- [ ] Contradictions are explicit.
- [ ] R&D-only growth is separated from formal certification scope.
- [ ] PASS remains drift-watched.
- [ ] Independent gate review is preserved where required.

## Commercialization state

Public-safe pattern candidate. Private evidence bodies, customer/provider records, internal claim corpora, and restricted source content are excluded from commercial distribution.
