# Virality Daily Metrics, Public Surface QA and Placement Optimization

## Objective

Run one governed daily evidence cycle for Virality Music that keeps three independent planes coherent:

1. SoundCloud/public-provider evidence;
2. public website presentation and interaction quality; and
3. shadow-mode catalog/placement recommendations.

The cycle does not change a live catalog, Sites project, provider account, price, license or entitlement.

## Schedule and ownership

- **Cadence:** daily, once per America/New_York calendar day through existing agents
- **Measurement authority:** CrownLytics
- **Catalog authority:** Virality Music
- **Rights authority:** CHLOM
- **Commerce/license authority:** GSO
- **Public-surface authority:** Website Surface & Interaction Agent + `ct.subagent.virality-public-surface-visual-qa`
- **Automation owners:** existing scheduled Agents G, E, F, C, D, S and the Integration Heartbeat subagent
- **Human owner:** CrownThrive founder/operator

## Scheduled execution integration

The daily lane is embedded in the existing hourly institutional agents; it does not create another active automation. Each role applies a once-per-America/New_York-calendar-day guard for the Virality-specific work:

1. **Agent G — provider evidence:** creates one sanitized SoundCloud provider/public-evidence packet only when the current-day packet is absent.
2. **Agent E — API/MCP and registry:** reconciles the authenticated measurement lane into private Supabase with provider/date/attempt idempotency and evidence precedence; it preserves the public-embed/authenticated-read distinction.
3. **Agent F — public knowledge/content projection:** checks public wording, evidence dating, cognitive load and documentation effects; routine numeric noise does not become a commit.
4. **Agent C — build and documentation:** creates only material GitHub/Mintlify/site-remediation changes, preserves Drive custody and never self-merges.
5. **Agent S — security/privacy:** verifies third-party media/loading/privacy and protected-data boundaries.
6. **Agent D — gatekeeper:** requires current-head governance and visual/public-surface evidence before an eligible material public change is promoted.
7. **Integration Heartbeat — non-voting verification:** confirms current-day SoundCloud and public-surface evidence/blocker records exist, detects stale/partial/contradictory handoffs and raises `ACTION NEEDED` when required.

The evidence path is fail-closed. The heartbeat observes the chain but does not create a vote, certify evidence or enable a provider/site write.

## Preconditions

1. The private registry and RLS policies are healthy.
2. The latest verified metric and public-surface baselines are queryable.
3. Authenticated SoundCloud reads occur only when the credential/export gate is verified; public embed/playback inspection does not require that credential.
4. Provider writes, Sites writes and promotion execution remain disabled unless their separate adapter/authority gates pass.
5. The job has a request budget, timeout, retry cap and idempotency key where provider/API requests occur.
6. The public surface has a rollback/version reference before any future mutation is considered.

## SoundCloud public playback versus authenticated measurement

These are separate controls.

### Public playback

Virality may use SoundCloud's supported public embed stack without a CrownThrive SoundCloud API credential:

- oEmbed / standard iframe is the default for simple playback;
- the official HTML5 Widget API is used only when custom playback controls/events are needed;
- autoplay remains off by default;
- responsive, accessible, privacy-aware loading rules follow the [Public Surface Visual Quality & Media Embed Standard](/standards/public-surface-visual-quality-and-media-embed).

### Authenticated measurement

`soundcloud.sync.daily` remains blocked until a least-privilege credential or repeatable signed export is certified. A working iframe, public profile or public count can never substitute for authenticated Artist Studio/API evidence.

## Daily procedure

### A. Provider/metric lane

1. Create an idempotent sync-run row for the scheduled date.
2. Attempt the authenticated bounded SoundCloud read only when the credential gate is verified.
3. If authenticated evidence is unavailable, record `blocked` or `observed_unverified`; do not overwrite the latest verified snapshot.
4. Validate nonnegative values, identifier stability, pagination completeness, response freshness and field mapping.
5. Store one dated metric snapshot and its digest only at the evidence class actually proved.
6. Compare against the nearest verified snapshot using current metric definitions.

### B. Public-surface lane

7. Resolve the registered Virality production surface and current release/version baseline.
8. Verify homepage/primary listening CTA and explicit no-autoplay behavior with public read-only checks.
9. Instantiate `ct.subagent.virality-public-surface-visual-qa` when a visual capture/browser-capable runtime is available or when a material public change is proposed.
10. Check representative mobile/tablet/desktop layouts for navigation, typography, grids/cards, artwork crops, CTA hierarchy, persistent-player overlap, third-party embed fit, focus/keyboard behavior, reduced motion and layout stability.
11. Check SoundCloud presentation against `VIRALITY_SOUNDCLOUD_PUBLIC_EMBED_V1`: supported official embed, responsive width, autoplay off, no credentials, accessible title/controls, click-to-load/consent where required.
12. If a required visual state cannot actually be inspected, mark it `unknown` and open/maintain a D1 remediation/review item; do not infer PASS from HTTP or source markup.
13. Record material visual/public-state drift without changing the live Sites project.

### C. Recommendation lane

14. Evaluate catalog eligibility before calculating a score.
15. Generate expiring shadow recommendations with reasons and safeguards only from permitted evidence.
16. Do not execute the recommendation.
17. Report `SUCCESS`, `WATCH`, `ACTION NEEDED` or `FAILURE` with exact blockers and evidence dates.

## Public recommendation contract

Scoring runs only after binary eligibility passes. The public contract records the algorithm version, approved input families, output class, evidence window, reasons, expiry, safeguards and rollback state.

Exact coefficients, thresholds, normalization curves, fatigue and uncertainty calibration, minimum-sample rules and tuning history are restricted institutional runtime evidence. They are not published through GitHub or Mintlify. Missing or stale data increases uncertainty and may never receive a neutral or optimistic substitute.

Visual and accessibility QA remain separate inspectable controls. Every recommendation remains shadow-only until an independently governed execution gate authorizes a reversible target-specific action.

## Recommendation safeguards

- verified or explicitly labeled evidence only;
- no action on rights-pending, canon-pending, blocked, mature-audience-incompatible or fulfillment-incomplete assets;
- minimum sample size and stable measurement window;
- seven-day default cooldown after a placement change;
- per-world and per-format caps;
- no deletion or silent master replacement;
- no title, price, license, territory, exclusivity, audience or entitlement mutation;
- human/governed approval and reversible target-specific plan before any future execution;
- append-only event log.

## Visual/public-surface safeguards

- HTTP success is not visual PASS;
- desktop success is not mobile PASS;
- a working public embed is not authenticated provider evidence;
- a beautiful placement cannot override rights/canon/audience/commerce restrictions;
- dated evidence must stay visibly dated/scoped;
- primary user and business CTAs must remain distinguishable within deep archive pages;
- no first-visit autoplay;
- persistent media must not obscure controls/content or trap focus;
- generic visual polish cannot justify unsupported claims or fake social proof;
- a future autonomous Sites repair requires exact project identity, rollback checkpoint, read-before-write, read-after-write and the separately certified provider adapter.

## Documentation rule

Daily numbers and routine screenshots belong in the private evidence ledger and approved dynamic projections. GitHub and Mintlify receive a checkpoint only when the method, schema, evidence status, visual/public-surface standard, gate or operating decision materially changes. This avoids noisy commits and copied-forward stale statistics.

Every durable document, report, manifest, migration, source page or other file produced by this workflow must also be copied into the connected private Google Drive with the standardized `CrownThrive_[Platform-or-Workstream]_[Document-Type]_[Short-Title]_[YYYY-MM-DD]_v#` name, placed in the logical custody folder and verified by readback. A Drive outage or failed verification is `ACTION NEEDED`, not completion.

## Failure handling

| Failure | Required response |
| --- | --- |
| authenticated credential absent/rejected | mark metric lane `blocked`; preserve verified baseline; public embeds remain separately evaluated |
| public SoundCloud embed broken | open public-surface remediation; do not mislabel as credential failure |
| visual breakpoint unavailable to inspector | record `unknown`; do not synthesize visual PASS |
| mobile/desktop layout regression | open P1/P2 visual remediation according to impact; preserve rollback reference |
| third-party player creates overlay/focus/consent defect | hold material public promotion; route C/S/public-surface QA |
| partial pagination or provider rate limit | mark metric lane `partial`; store no verified replacement; retry within cap |
| value regression or schema drift | quarantine snapshot; open field-mapping review |
| rights/canon/commerce gate missing | suppress recommendation or public offer implication for that asset |
| storage/database write fails | fail the evidence run; do not publish new metrics |
| suspected credential exposure | disable authenticated tools/schedule path and open security incident; follow approved credential process |
| live target differs from approved plan | do not execute; require a new preflight |

## Rollback

For metric automation, disable the affected schedule/tool and preserve sync runs, snapshots, recommendations and decisions. For a future site mutation, restore the last governed Sites/release baseline through the certified provider path and re-run functional + visual + accessibility checks. Rollback may stop automation or restore presentation; it must not erase evidence.
