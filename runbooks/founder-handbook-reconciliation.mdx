# Founder Handbook Reconciliation Runbook

## Mission

Turn the recovered Founders Handbook/Playbook/Activation Package into durable institutional knowledge without rewriting history, promoting stale assumptions, or treating fluent reconstruction as evidence.

The handbook is a **founder-brain source family**. It contains doctrine, systems thinking, proposed structures, operating rhythms, technical concepts, economic models, cultural rules and future-state architecture. Every one of those claims must retain its effective era and evidence class.

## Non-negotiable rules

1. **Never silently destroy knowledge.** Material prior states survive in source history, correction records or explicit supersession lineage.
2. **Never silently overwrite a current claim.** Explain what changed, why, when and what evidence controls now.
3. **Never represent reconstructed current prose as recovered historical-original prose.**
4. **Never turn source intent into legal, financial, technical or production fact without the required evidence.**
5. **Never flatten conflicts.** Preserve both sides until authority/evidence resolves the disputed field.
6. **Never allow a historical page to govern current state merely because it ranks well in search.**
7. **Never auto-merge material D2/D3 changes.** Applicable specialists and independent governance are required.
8. **Never open Phase 3 while the founder documentation hard gate is materially incomplete.**

## Inputs

The reconciliation pass may use:

- restricted handbook source editions and checksums;
- current GitHub/Mintlify documentation and version history;
- THIVEBASE machine registries, tags, gates and deferrals;
- current public CrownThrive properties;
- connected Google Drive/Docs and Gmail evidence;
- provider/API documentation and current account/runtime evidence;
- founder decisions from accessible chats;
- founder recollections, clearly marked as recollection when not independently corroborated;
- digitized/indexed notebook/canon/doctrine artifacts;
- qualified legal, finance, rights, security, privacy, accessibility, regional/localization and other specialist evidence when applicable.

## Extraction procedure

For each material handbook proposition:

```text
locate source proposition
-> assign source section and effective era
-> classify proposition type
-> find current related institutional object/page
-> collect collateral evidence
-> research current best-use-case technology/standard if a current rebuild is needed
-> determine current disposition
-> update/rebuild the current artifact if supported
-> preserve historical proposition and source lineage
-> record conflict/supersession/correction relationship
-> run risk-derived specialist review
-> run independent sovereign acceptance where material
-> add compact page changelog/version note
-> propagate downstream phase effects
```

## Rebuilding a current artifact

When a handbook-derived asset is still valuable but its original implementation is obsolete or incomplete:

1. preserve the historical source;
2. identify the job the asset was supposed to perform;
3. collect collateral CrownThrive evidence and current requirements;
4. research the best current technology, standard, architecture and accessibility/security pattern appropriate to that asset class;
5. build a **new current artifact** with explicit version/effective date;
6. expose reusable public-safe templates, schemas, scaffolds or reference code where authorized and useful;
7. keep secrets, private routing, restricted evidence, customer data and protected proprietary internals out of public artifacts;
8. require the appropriate acceptance cell before the artifact becomes canonical.

## Governance and quorum

Material acceptance follows the current CrownThrive governance perimeter. CI, an agent tag or fluent prose is evidence, not quorum.

At minimum:

- D0/D1 deterministic corrections may use bounded automated review where policy permits;
- D2/D3 or otherwise material reconstructions require applicable specialist cells;
- independent sovereign review must be bound to the exact current head/change;
- the originating/materially implementing agent does not self-vote;
- current legal/rights/money/security/privacy/authority claims remain fail-closed until their specialist requirement is actually met.

## Historical-page reconciliation

Prior Phase 1–2.x pages must be rescanned after later evidence changes. A page may remain historical, but should receive a visible current-state overlay when its old conclusion could mislead a present reader.

A historical-page repair should contain:

```yaml
page_version:
change_date:
prior_state_preserved: true
current_disposition:
evidence_refs: []
conflicts_resolved: []
conflicts_remaining: []
downstream_phase_effects: []
review_cells: []
```

Do not rewrite the old event as if current evidence existed at the time.

## Handbook conflict classes requiring special care

The following require current evidence beyond handbook prose:

- legal entity / HoldCo structure;
- board, officer, founder-seat or delegated-authority claims;
- ownership percentages and equity rights;
- D&O coverage;
- franchise/regional-license obligations;
- ThriveFund money/clawback/treasury schedules;
- climate/provider partnerships;
- CHLOM token, DAO, chain, settlement and autonomous-compliance claims;
- production/provider deployment state;
- privacy/data-retention/security requirements;
- binding rights/licensing terms;
- current portfolio counts and metrics.

## Automation and self-healing

Safe automation should:

- detect stale roadmap/phase names;
- detect current pages still citing superseded aliases or providers;
- identify handbook propositions with no current disposition;
- find missing page-level changelog/version notes;
- detect contradictions between current machine registries and prose;
- open governed documentation PRs;
- repair deterministic D0/D1 links/metadata/cross-links;
- re-run validation after current-main movement.

Automation must **not** silently merge material reconstructed doctrine, authority, rights, security, money or current-provider claims.

## Phase 3 opening sequence

Once Phase 2.99 and the full documentation hard gate are accepted, the founder-approved Phase 3 opening order is:

```text
A. CHLOM + THIVEBASE Institutional Core
-> B. CrownThrive ID / identity + authority
-> C. one bounded platform-adapter pilot
```

This order is an execution sequence, not permission to bypass unresolved entry gates.

## Definition of done

The handbook deep pass is complete only when:

- every material source family has a current disposition or explicit unresolved record;
- high-risk current claims have stronger evidence and specialist acceptance;
- stale prior-phase pages have been reconciled or explicitly historicalized;
- current runbooks/canon/doctrine pages reflect accepted doctrine;
- all material changes preserve prior versions;
- no unreconciled current claim can silently enter Phase 3 through search, navigation or machine retrieval;
- the final Phase 3 snapshot cites the accepted handbook-reconciliation evidence.
