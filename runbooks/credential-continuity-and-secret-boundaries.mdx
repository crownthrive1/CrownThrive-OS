# Credential continuity and secret boundaries

Use this runbook when an integration depends on API credentials, signing material, OAuth tokens, service credentials, or secret-backed runtime configuration.

## Objective

Prove that an approved application can resolve and use the required secret through a supported secure path while preserving least privilege, auditability, recovery, and non-disclosure.

## Secret-handling rules

- Never place secret values in repositories, documentation, examples, generated artifacts, screenshots, chat transcripts, issue comments, or ordinary logs.
- Do not publish credential fingerprints when they materially aid correlation or attack planning.
- Store only a stable secret reference in machine manifests when a reference is needed.
- Keep server-side and client-side credentials separate.
- Do not use production credentials for documentation examples or synthetic tests.
- Secret access is not equivalent to permission to call every provider endpoint.

## Continuity sequence

1. Identify the integration and exact secret purpose.
2. Confirm the approved secret store/runtime binding mechanism.
3. Validate the application resolves the secret by reference, not embedded value.
4. Perform the minimum bounded authentication/read test.
5. Verify logs, error paths, traces, and audit records redact sensitive material.
6. Confirm rotation/revocation procedure exists.
7. Confirm a backup administrator/recovery path exists where required.
8. Record provider/account continuity evidence without storing the secret itself.
9. Keep write gates closed until the integration's separate write predicates pass.

## Machine record example

```yaml
credential_control_id: provider.example.runtime
secret_reference: provider_example_api_key
storage_class: approved_secret_store
client_exposed: false
runtime_resolved: true
auth_read_verified: true
write_authorized: false
rotation_procedure: documented
recovery_owner: role_ref
last_verified_at: timestamp
```

The example uses a synthetic reference. Commercial material must never contain CrownThrive production references when those references are restricted.

## Verification tests

Positive tests:

- runtime can authenticate with the expected least-privilege request;
- secret is not returned by the application;
- audit record identifies the action without the secret.

Negative tests:

- unauthenticated request fails;
- wrong role fails;
- secret value is absent from response/log output;
- disabled provider-write path remains disabled;
- stale/revoked secret produces a safe failure instead of silent fallback.

## Rotation and recovery

A credential continuity control should document:

- who can initiate rotation;
- how old material is revoked;
- how dependent services reload safely;
- how rollback works if a provider rotation partially fails;
- how emergency access is audited;
- how a lost vendor/account owner is recovered or escalated.

Do not rotate merely to satisfy a schedule if the adopted policy uses persistent server-side credentials and there is no compromise, expiry, or provider requirement. Rotation must follow the governing credential policy.

## Failure classes

- secret exists but runtime binding is unproved;
- provider accepts auth but secret is exposed in logs;
- multiple precedence sources create ambiguous credential selection;
- client-side code can retrieve a server credential;
- write scopes exceed the certified adapter need;
- rotation destroys recovery/rollback;
- secret store is the only recovery path with no continuity owner.

## Verification checklist

- [ ] Approved secret store is used.
- [ ] Only references, never secret values, appear in distributable artifacts.
- [ ] Runtime binding is proved with a bounded request.
- [ ] Logs/errors are redacted.
- [ ] Least privilege is explicit.
- [ ] Rotation/revocation/recovery are documented.
- [ ] Write capability remains separately gated.
- [ ] Customer/provider-specific evidence remains private.

## Commercialization state

Public-safe developer pattern candidate. Production secret references, fingerprints, Vault paths, provider account IDs, and private recovery identities are excluded from the commercial edition.
