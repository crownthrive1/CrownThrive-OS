# Documentation source reconciliation and articleization

Use this runbook when rebuilding or maintaining a large knowledge base from mixed current, historical, recovered, restricted, and research sources.

## Objective

Convert source material into durable institutional knowledge without flattening history, inventing missing content, exposing restricted material, or allowing stale documentation to outrank current machine/provider truth.

## Source states

Every source or recovered claim should be typed, for example:

- current canonical;
- current operational evidence;
- adopted policy;
- historical doctrine;
- superseded history preserved;
- research/target architecture;
- dormant/reconcile;
- restricted;
- needs owner validation;
- source not recovered.

## Articleization sequence

1. Inventory source titles/records with stable IDs.
2. Hash or otherwise integrity-record source masters where appropriate.
3. Classify source authority and lifecycle state.
4. Recover body text when lawfully and technically available.
5. Map duplicates, aliases, successors, and redirects.
6. Reconcile contradictory names, counts, dates, implementations, and authority.
7. Create substantive canonical articles only when evidence supports them.
8. Preserve unresolved titles as explicit unresolved-source records rather than placeholders pretending to be complete.
9. Apply public/private projection rules.
10. Generate navigation/redirect/article manifests.
11. Validate links, metadata, restricted-content boundaries, and stale-current-state claims.
12. Record changelog and source lineage.

## Terminal disposition model

Every title should eventually reach one of:

```text
canonical_substantive_article
merged_into_successor
redirect
restricted_record
superseded_history_preserved
explicit_unresolved_source
retired_with_reason
```

A title-only placeholder is not terminal completeness.

## Documentation-impact contract

A material platform change should produce one inspectable result:

- `docs_updated`
- `docs_no_change`
- `docs_delta_opened`

The result should link to the changed source, affected articles/registries, and validation evidence.

## Self-healing boundary

Documentation automation may safely perform bounded mechanical repairs such as:

- broken internal link repair;
- index/navigation regeneration;
- schema/manifest regeneration;
- stale derived count refresh;
- rerun of documentation validation;
- conflict-free rebase of a documentation-only branch.

It must not silently change signed terms, license grants, prices, legal obligations, private policy, security authority, canon, paid entitlement, or source history.

## Negative tests

Reject:

- historical text presented as current without classification;
- source-not-recovered records represented as complete;
- research architecture represented as deployed;
- private evidence copied into public docs;
- provider capability represented as account entitlement;
- generated summary treated as source authority;
- a merged manifest treated as body-recovery completion.

## Verification checklist

- [ ] Stable source/article IDs exist.
- [ ] Current, historical, research, restricted, and unresolved states are distinguishable.
- [ ] Duplicates/aliases/successors are mapped.
- [ ] Missing body evidence remains explicit.
- [ ] Public/private projection is validated.
- [ ] Navigation and redirects are machine-checkable.
- [ ] Material changes emit a docs-impact result.
- [ ] Historical evidence is preserved rather than destructively rewritten.
- [ ] Repository and secondary archive provide continuity.

## Commercialization state

Public-safe developer pattern candidate. The method may be sold as a recovery/articleization runbook and training module. Source bodies, restricted institutional archives, customer records, and third-party copyrighted material remain outside the product unless separately licensed.
