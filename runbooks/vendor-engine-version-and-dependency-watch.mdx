# Vendor, engine, version, and dependency watch

Use this runbook to keep a software/engine estate current without confusing vendor release information with the version actually installed in production.

## Core state model

Track these separately:

- `installed_version` - proved runtime/source version;
- `highest_known_vendor_version` - current authoritative vendor target when verified;
- `staged_target` - version selected for compatibility work;
- `support_state` - supported, security-only, EOL, unknown;
- `license_state` - current entitlement/rights state;
- `upgrade_state` - uninspected, evaluating, staged, validated, production;
- `rollback_state` - documented and tested status.

A newer vendor release should update the staged target when authoritative evidence is strong enough, but it must not silently rewrite installed state.

## Watch sequence

1. Read current installed-state evidence.
2. Check first-party vendor release/support sources.
3. Resolve version/date conflicts across official surfaces.
4. Record the highest-known target only when the source is reproducible.
5. Inspect security advisories and compatibility notes.
6. Check license/support entitlement and provider access.
7. Map application dependencies and breaking changes.
8. Create an upgrade candidate only when useful.
9. Require backup, staging, migration, customization, data, security, and rollback proof before production deployment.
10. Update the registry and documentation without auto-upgrading production.

## Dependency record

```yaml
component: example-engine
installed_version: unknown
highest_known_vendor_version: 5.4.0
vendor_evidence_date: 2026-01-10
support_state: supported
upgrade_state: evaluating
license_state: verified
breaking_change_review: open
rollback_state: required
```

## Upgrade gate

A production upgrade should prove:

- source/license entitlement;
- compatibility with runtime, database, extensions, and customizations;
- backup/restore readiness;
- migration path;
- staging deployment;
- security and data review;
- functional regression testing;
- provider/API compatibility;
- rollback criteria and target;
- documentation/changelog impact.

## Failure classes

- vendor target is represented as installed version;
- cached/partial vendor page creates a false latest-version claim;
- license entitlement is assumed from downloaded source;
- production upgrade occurs without rollback;
- customizations are overwritten;
- unsupported dependency remains hidden;
- provider/account feature access is inferred from public documentation.

## Verification checklist

- [ ] Installed and vendor-target versions are separate.
- [ ] First-party source is current and reproducible.
- [ ] Conflicting sources remain UNKNOWN until resolved.
- [ ] Support and license status are explicit.
- [ ] Upgrade requires staging and rollback.
- [ ] Production is not auto-upgraded by the watch task.
- [ ] Documentation and dependency registries receive the delta.
