# Stripe OS Monetization Operations

Operational runbook for `ct.binding.pentagreen-stripe-mesh.v3`.

## Healthy baseline

A healthy current readback should establish:

- `integration_control.stripe_os_mesh_status_v1()` -> `ACTIVE_MONETIZATION_READY`;
- both declared Stripe account roles provider-live;
- one deterministic credential fabric with HOT/WARM/COLD/EMERGENCY roles;
- one active PentaGreen commerce clock;
- no duplicate Stripe-specific scheduler;
- PentaGreen Commerce Binder active with provider-write permission and no self-approval;
- catalog mirrors available;
- webhook lanes active;
- no raw secret projection.

## Current institutional inventory

At the August 31 / September 1 production convergence point the canonical mirrors contained:

- 456 Stripe products;
- 478 Stripe prices;
- 48 Payment Links;
- 4 webhook lanes;
- 15 endpoint records;
- 18 Stripe capability families;

Treat these counts as observed production evidence, not eternal constants.

## New product monetization

1. Resolve canonical PentaSKU/offer/product identity.
2. Resolve existing PentaPrice evidence or an approved price rule.
3. Confirm rights, fulfillment, quality, route, custody and docs state.
4. Read the Stripe catalog bridge for an existing provider alias.
5. Submit one idempotent PentaGreen Stripe monetization request.
6. Commerce Binder executes the allowed provider operation.
7. Read the provider object back.
8. Reconcile Stripe IDs into provider mirrors as aliases.
9. Bind Checkout/Payment Link/subscription/invoice only as required.
10. Require signed provider event evidence before fulfillment/entitlement.
11. Append/read back terminal DAIL state.

## Existing product repricing

Stripe Price amount semantics are successor-object oriented. Do not mutate CrownThrive price history into a false single-object timeline.

1. Keep the prior provider Price as history.
2. PentaPrice approves or supplies the successor amount/evidence.
3. Create a successor provider Price.
4. Update the active provider alias/binding.
5. Reconcile links/subscriptions as required by the product contract.
6. Preserve the old Price alias and effective period.

## Subscription launch

1. Confirm recurring economic model and cadence.
2. Bind the recurring PentaPrice.
3. Create/read back the provider Price.
4. Configure subscription Checkout or Billing flow.
5. Bind required webhook events.
6. Verify subscription lifecycle from provider events.
7. Route failed-payment state to the customer-success/revenue-recovery lane.

## Invoice launch

Use invoicing when the sale is sales-led, contract-backed or operationally better suited to invoice collection.

- Preserve customer and contracting identity.
- Preserve invoice terms.
- Finalize/send only within the existing offer/contract authority.
- Reconcile payment from provider events/readback.

## Connect / marketplace launch

Before provider configuration, explicitly choose and document the economic model. Do not allow a factory to infer charge model from implementation convenience.

Required decisions include:

- who is merchant/seller;
- who owns customer relationship;
- fee model;
- direct vs destination vs separate-charge/transfer architecture;
- refund/dispute responsibility;
- connected-account capabilities;
- payout/money-routing authority.

PentaMarket and PentaGreen own those economic semantics. Stripe executes them.

## Webhook recovery

When a Stripe route is degraded:

1. Read `integration_control.stripe_webhook_status_v3()`.
2. Read the latest `stripe_webhook_provider_receipts_v3`.
3. Verify lane signing-secret alias and signed canary.
4. Verify provider endpoint URL/status.
5. Prefer repair/reuse of an existing endpoint over endpoint churn.
6. Never create/delete endpoints solely to escape a transient hold or provider capacity constraint.
7. Read provider state after mutation.
8. Verify a signed canary and/or natural provider event.
9. Reconcile PentaSELF problem state only from current evidence.

## Credential failure

Read `stripe_live_secret_lanes_v1`.

- HOT healthy -> remain HOT.
- HOT unavailable -> verify WARM independently before use.
- WARM unavailable -> verify COLD.
- EMERGENCY remains blocked until provider same-account verification.
- Same-material recovery aliases do not create redundancy.
- Never wildcard-select a Stripe-looking vault secret.

No automatic key deletion or rotation follows a provider failure.

## PentaGreen autowire

The existing commerce cycle invokes `pentagreen_stripe_autowire_v1`.

Expected behavior:

- unresolved products: zero Stripe jobs queued;
- newly reconciled eligible products: one idempotent PRODUCT_PRICE request each;
- repeated cycle: request returns REUSE instead of duplicate work;
- no independent Stripe cron appears.

Clock health:

`integration_control.pentagreen_stripe_clock_status_v1()`

Healthy state requires exactly one matching active job.

## Reserved effects

Do not route the following through generic factory monetization:

- refunds;
- transfers/payouts;
- bank/external-account changes;
- dispute accept/close decisions;
- arbitrary customer charges outside a governed order;
- final rights/legal commitments;
- material fee/liability model changes.

Use the corresponding PentaGreen specialized lane and existing authority contract.

## Evidence package

A production closeout should bind:

- exact CrownThrive SKU/offer/work identity;
- account role used;
- credential lane role used without raw material;
- provider request identity/idempotency key;
- provider object aliases;
- provider readback;
- webhook/event receipt when relevant;
- PentaGreen/PentaLedger result;
- GitHub source head/PR if code changed;
- PentaDocs and Drive custody refs when institutional topology changed;
- CHLOM/DAIL terminal event.

## Rollback

Provider configuration rollback should be compensating/forward when destructive rollback would erase economic history.

Examples:

- deactivate a wrong Price rather than rewriting transaction history;
- deactivate a Payment Link rather than deleting ledger evidence;
- restore prior webhook URL/binding using exact provider readback;
- mark an incorrect adapter generation superseded rather than deleting custody records;
- preserve all historical Stripe IDs as aliases/evidence.
