# Security sentinel and resilience watch

Use this runbook for recurring security and resilience oversight of repositories, integrations, agents, credentials, webhooks, infrastructure, and release candidates.

## Mission

Detect material exposure or unsafe drift without granting the sentinel unilateral product, release, legal, or sovereign authority. The sentinel can block, escalate, and preserve evidence; it does not silently rewrite business policy.

## Inspection domains

- secret leakage and unsafe credential references;
- authentication and authorization boundaries;
- enabled tool/capability risk level;
- dependency and runtime security advisories;
- RLS/data-access boundaries;
- request-body, response-size, timeout, and rate controls;
- webhook signatures and replay controls;
- public/private documentation projection;
- branch/release integrity;
- backup, recovery, and fail-closed behavior;
- suspicious privilege or scope expansion.

## Review sequence

1. Resolve the exact candidate/baseline.
2. Identify the assets and trust boundaries touched.
3. Scan public artifacts for credentials, restricted evidence, private identifiers, or protected implementation detail.
4. Verify role and authorization checks for privileged actions.
5. Inspect capability/tool enablement against the approved risk ceiling.
6. Review network/provider boundaries and request hardening.
7. Review database/data-access controls.
8. Review dependency/security findings using authoritative sources.
9. Confirm logging, evidence retention, and rollback path.
10. Classify findings by severity and whether they block promotion.

## Finding envelope

```yaml
finding_id: sec.example.001
severity: high
surface: webhook_receiver
claim: signature_verification_unproved
evidence_class: runtime_required
public_safe_summary: true
restricted_evidence_ref: private-only
promotion_effect: block
reopen_condition: verified_runtime_test
```

## Fail-closed conditions

Block promotion when:

- credential or restricted material is exposed;
- privileged action lacks authorization;
- production write capability exceeds approved scope;
- a security control is claimed but runtime proof is missing where required;
- destructive action has no recovery path;
- public documentation leaks trade-secret or private security details;
- serious dependency/provider exposure is unresolved and directly applicable.

## Verification checklist

- [ ] Exact candidate head/version was reviewed.
- [ ] Public artifacts contain no secret values or restricted evidence.
- [ ] Privileged actions have explicit authorization.
- [ ] Enabled capabilities stay within the approved risk ceiling.
- [ ] Database and data-access boundaries are checked.
- [ ] Webhook/API hardening is checked where applicable.
- [ ] Dependency findings are applicability-tested, not blindly copied.
- [ ] Backup/rollback/fail-closed behavior exists.
- [ ] Findings separate public-safe summary from restricted evidence.

## Commercialization state

Public-safe developer pattern candidate. Exploit details, production vulnerabilities, private security findings, credentials, secret topology, and proprietary adversarial corpora remain restricted or trade-secret controlled.
