## Repository Convergence, Failover, and Recovery Runbook

Use this runbook when a registered repository is stale, diverged, unreachable, missing required workflows, unable to consume the current family contract, or affected by a provider or continuity incident.

This public-safe runbook deliberately excludes private repository coordinates, credentials, protected recovery locations, and silent emergency-route details.

## 1. Detect and preserve

1. Record the stable repository/node ID, affected scope, observation time, observer, and evidence classification.
2. Preserve the last known good contract version, revision reference, release/tag inventory, workflow state, and public-safe evidence hashes.
3. Open or correlate the incident without overwriting a prior incident.
4. Send a sanitized signal through PentaNerves and preserve its event lineage through PentaSpine.
5. Mark stale, missing, contradictory, or inaccessible state `UNKNOWN`/`HOLD` rather than inferring health.

## 2. Classify the failure

| Failure class | Initial disposition |
| --- | --- |
| Contract/version drift | Prepare a scoped repository-native convergence candidate. |
| Missing or failed workflow | Hold promotion; diagnose the exact workflow and provider event. |
| Unauthorized or unverified cross-repository identity | Hold cross-repository execution; do not substitute another credential. |
| Repository/provider outage | Contain writes and evaluate the governed recovery tier. |
| Integrity or history mismatch | Quarantine the candidate and verify from the last known good evidence. |
| Documentation-only projection lag | Open a documentation delta; do not rewrite canonical OS state from the projection. |
| Restricted-route or security concern | Use the private incident path; do not publish operational details. |

PentaBrain may recommend a disposition, but the applicable owner, CHLOM authority, security boundary, and human gate still control execution.

## 3. Reconcile before failover

For a reachable node:

1. compare its scoped contract and schema versions with the canonical hub;
2. distinguish intentional repository-specific files from actual drift;
3. prepare a minimal candidate branch or pull request in the target repository;
4. run its required tests, security checks, documentation-impact check, and continuity gate;
5. obtain independent certification where required; and
6. read back the accepted node state before marking it converged.

Never bulk-copy the authority repository over a child, write directly to a protected `main`, erase child-specific history, or treat a green candidate branch as accepted provider state.

## 4. Select the recovery tier

### HOT_PRIMARY

Remain on the primary path when it is reachable, authoritative, and current. A live source path does not prove that cross-repository Actions credentials or every provider adapter are bound.

### COLD_RECOVERY

Use cold recovery only when the applicable package, custody reference, restoration order, authority, and verification plan are available. Restore into an isolated target first. Verify history, hashes, contracts, workflows, and restricted-data boundaries before any cutover.

### SILENT_EMERGENCY

The silent route is a restricted last-resort control. Follow its private authority and incident record. Do not expose, reconstruct, guess, or transmit its details through public documentation or ordinary logs.

## 5. Verify restored state

Before declaring recovery:

- verify stable IDs and required history;
- verify expected release/tag and artifact hashes;
- run contract, schema, documentation, security, and continuity validators;
- verify the exact authorized workflow identity;
- read back repository/provider state independently;
- confirm no restricted content entered public source;
- confirm no authority, rights, economic, or provider scope expanded;
- verify PentaSpine continuity and the sanitized PentaBody snapshot; and
- record remaining degraded dependencies and HOLDs.

The current implementation branch may prove deterministic and unit-failover behavior. Live cross-repository Actions binding, live Command Center deployment, and infrastructure failover remain `HOLD` until their provider readbacks and recovery drills pass.

## 6. Governed failback

1. Confirm the primary route's identity, integrity, and required controls.
2. Freeze conflicting writes during reconciliation.
3. determine the authoritative event/version sequence without discarding either side's evidence;
4. apply the approved reconciliation or correction;
5. run the same validation and readback used for recovery;
6. return traffic/work only after the failback gate passes; and
7. preserve the recovery and failback receipts, postmortem, and next test date.

## Required evidence packet

```yaml
incident_id:
node_id:
failure_class:
observed_at:
last_known_good_ref:
selected_tier:
authority_ref:
recovery_package_ref:
tests: []
provider_readbacks: []
command_center_readback: null
failback_receipt: null
docs_impact: docs_updated | docs_no_change | docs_delta_opened
remaining_holds: []
```

References in the public record must be sanitized. Secret values, private coordinates, and restricted-route details never belong in this packet's public projection.
