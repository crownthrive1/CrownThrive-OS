## Provider control-plane context

Viloud is the current cloud video/playout provider for this media mesh. The provider supports linear, on-demand, live, player embedding, HLS/M3U8 delivery, analytics, and advertising/FAST capabilities. CrownThrive retains network, brand, content, rights, and distribution-governance identity; Viloud is the transport/playout/provider layer.

The public Viloud Delivery API exposes channel metadata, schedule data, and XMLTV EPG endpoints. The provider documentation describes the management API as forthcoming, so automation must currently distinguish **delivery/read integration** from **dashboard-only management actions**.

Provider documentation also supports M3U8/HLS output for delivery to web players, mobile/TV apps and OTT platforms. Provider announcements captured by the founder further identify Castlify as the path for sending linear M3U8 channels to RTMP or SRT destinations.

## Delivery API integration contract

Current public provider documentation exposes read-side delivery endpoints using a Viloud channel ID:

```text
GET https://deliver.viloud.tv/channel/{channel_id}
GET https://deliver.viloud.tv/channel/{channel_id}/schedule
GET https://deliver.viloud.tv/channel/{channel_id}/epg?format=xmltv
```

The channel response can support standard JSON and Roku-oriented output where documented. The EPG endpoint supplies XMLTV. Integrations must tolerate additive response attributes because Viloud's API versioning guidance treats new attributes and endpoints as backward-compatible additions.

## Castlify distribution lane

The provider dashboard announcement identifies Castlify as a distribution path for taking a Viloud linear-channel M3U8 feed and sending it onward to RTMP or SRT destinations. Institutional meaning:

`CrownThrive content/rights → Viloud playout → HLS/M3U8 → Castlify distribution → RTMP/SRT destination`

This lane is **available capability**, not evidence that every CrownThrive channel has already been configured to an external RTMP/SRT destination.

## Secret handling

The RTMP stream key is a restricted runtime credential. It must **never** appear in Git, public documentation, logs, screenshots, client-side JavaScript, analytics payloads, issue bodies, or public configuration. ThriveBase stores only the logical secret reference `VILOUD_BLESS_THE_MIC_STREAM_KEY`; the raw credential belongs in the authorized runtime secret/vault layer.

The same rule applies to redeemed plan/license codes and any future API token, workspace token, webhook credential, or provider management credential.

## Intake contract for every channel supplied next

Every future channel/live-stream record supplied under this workflow should normalize into: canonical asset ID, network/brand owner, program title, provider, channel class, ingest protocol and endpoint, **secret reference only**, public playback URL, embed URL, destination set, asset roles, provider/account snapshot, view metrics, current status, provenance, and evidence timestamp.

Duplicate source text reconciles into one canonical asset record rather than creating duplicate assets. New destinations extend the destination set. Changed provider values create an auditable update event. Snapshot metrics append; they do not overwrite historical evidence.

## Governance boundary

“Listed in provider dashboard,” “registered asset,” “configured destination,” “verified playback,” “verified scheduled content,” “verified live carriage,” and “verified external distribution” are distinct evidence states. An empty channel or zero-view channel remains a valid registered distribution surface but must not be represented as actively programmed or viewed.
