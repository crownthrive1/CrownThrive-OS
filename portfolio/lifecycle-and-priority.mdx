# Portfolio Lifecycle and Priority

CrownThrive's institutional challenge is not lack of assets. It is converting a large accumulated portfolio into a controlled system with clear sequencing, ownership, cost, risk, and strategic purpose.

## Lifecycle classes

| Lifecycle | Typical priority | Operating meaning |
| --- | --- | --- |
| Core | P0 | Shared spine or primary near-term cash engine; must operate reliably now |
| Growth | P1 | Strategic asset funded after core controls; clear monetization and integration path |
| Incubate | P2 | Preserve and validate before committing full operating resources |
| Reserve | P3 / unassigned | Retain source, brand, domain, or optionality with low active burden |
| License / Sell | Case-by-case | Commercialize rights, brands, domains, templates, content, software use, or other assets where lawful |
| Sunset | Legacy | Stop active maintenance while preserving lineage, records, redirects, and required user/data transition |

## Current management snapshot

The August 2026 Holdings planning set records 68 portfolio assets, with 21 P0, 23 P1, 22 P2, and 2 P3 records. Those counts are a dated management snapshot, not a permanent truth. Stable asset IDs should survive priority changes.

Phase 2.99 Workstream 3A makes **priority**, **lifecycle**, **implementation state** and **institutional disposition** separate machine dimensions. A P0 label cannot prove production; an active public route cannot prove every capability; a sunset disposition does not erase domain, IP, contract or source history. The current crosswalk is recorded in [Relationship, Portfolio & Namespace Crosswalk](/knowledge/phase-2-99-workstream-3a-relationship-portfolio-crosswalk).

## Required asset record

Every active asset should eventually identify:

- stable ID and canonical name;
- aliases and historical names;
- corridor and asset class;
- lifecycle and priority;
- accountable owner/operator;
- canonical domain and deployment;
- target customer and problem;
- business/revenue model;
- current product/service state;
- rights and IP relationship;
- support path;
- canonical events and KPIs;
- dependencies and vendors;
- backup/export route;
- risk classification;
- last review and next decision date.

## Rule: card is not capability

A platform card, domain, purchased script, prototype, or public description does not establish a functioning product. An asset should be marked operational only when delivery, support, fulfillment, analytics, legal terms, security controls, and relevant transactions actually work.

## Rationalization without erasure

When assets merge or implementations change, preserve old domains, descriptions, IDs, content, customers, and dependencies in lineage records. Rationalization should reduce operating burden without destroying institutional history.
