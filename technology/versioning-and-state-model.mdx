# Institutional Versioning and State Model

Phase 3 requires every consequential CrownThrive object to have a stable identity and a separately versioned state. Names, vendors, phases, implementations and public claims may change without changing the underlying institutional identity.

## Required version fields

Every governed object should support:

- stable ID;
- canonical name;
- aliases and historical names;
- semantic/schema version;
- content/config version where relevant;
- effective date;
- previous version;
- successor version;
- lifecycle state;
- implementation state;
- legal state where relevant;
- evidence state;
- public-claim state;
- environment;
- owner/steward;
- source authority;
- last verified timestamp.

## Version namespaces

Use separate version namespaces rather than one generic number:

- `institutional_version` — identity/registry record;
- `schema_version` — machine contract;
- `policy_version` — adopted policy/rule;
- `content_version` — books, studies, pages, masters;
- `service_version` — API/service implementation;
- `deployment_version` — production release;
- `economic_schedule_version` — pricing/splits/fees;
- `rights_version` — rights/license terms;
- `public_claim_version` — approved public wording.

## Canonical lifecycle vocabulary

`concept → research → specified → build → prototype → test → pilot/beta → staged → production → maintenance → reserve → suspended → merged → retired → superseded`

Not every object uses every state.

## CHLOM component state

LEX, DID, ZK, treasury, token, oracle, DAIL, DLA and other CHLOM components must each carry their own state. `CHLOM active` is too broad to prove that every module is deployed.

Example:

- CHLOM governance model: `current-canonical`;
- DAIL service: `Phase 3 build`;
- historical LEX research: `research/recovery` until implementation evidence changes it;
- DID/ZK/token modules: version independently.

## Platform state

A platform record must distinguish:

- public site reachable;
- login/auth available;
- core workflow functional;
- payment path functional;
- entitlement/fulfillment functional;
- admin/ops path functional;
- support path functional;
- current build phase;
- last smoke test;
- known blockers.

A site being reachable does not automatically mean commerce or every feature is production-ready.

## Evidence rule

State transitions require evidence appropriate to the transition: test result, deployment record, signed approval, payment proof, domain/deployment evidence, registry update, legal record, or founder decision.

## Phase 3 requirement

Phase 3 services must reject ambiguous unversioned writes for consequential objects. Corrections append new versions rather than rewriting institutional history.
