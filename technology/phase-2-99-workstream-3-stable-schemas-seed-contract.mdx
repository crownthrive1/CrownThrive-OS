## Core invariant

Every machine record must answer five questions independently:

1. **What is it?** — stable identity and type.
2. **What state is it in?** — current/historical/planned/unverified/etc.
3. **Why do we believe that?** — source, evidence and authority.
4. **When was that true?** — effective/version interval.
5. **What may depend on it?** — policy, rights, economic, platform and automation relationships.

A complete-looking row with unknown evidence is worse than an explicit unresolved row.

- `not_connected`
- `blocked`
- `reserve`
- `sunset`

`not_connected` never means `nonexistent`; `historical` never means `current`; `specified` never means `deployed`.

## Macro-to-micro reconciliation relationship

Every schema family participates in the retroactive reconciliation lane:

```text
new source / revived site / provider evidence
  -> source record
  -> claim extraction
  -> conflict detection
  -> macro doctrine/portfolio/corridor impact
  -> platform/capability impact
  -> object/field impact
  -> article/changelog/docs-impact
  -> corrected seed/version
  -> validation
```

A micro-level fact may require a macro correction, and a macro decision must propagate to every affected micro record.

## Validation rules

Workstream 3 seed validation must fail when:

- the same stable ID resolves to incompatible current canonical identities;
- two economic schedules are simultaneously effective defaults without an explicit priority/supersession rule;
- a historical CHLOM target component resolves as production without E3\+ operational evidence;
- a provider capability resolves as CrownThrive deployment without authenticated evidence;
- an unresolved right, room, universe, platform, provider, price or authority is filled by similarity;
- a correction removes prior history;
- a restricted source payload is projected publicly;
- `not_connected` is converted to `nonexistent`;
- Phase 3 entry state becomes `go` before all hard Phase 2.99 exit criteria are evaluated.
