# Phase 3 Institutional Core Blueprint

Phase 3 converts CrownThrive's institutional doctrine and governed knowledge into executable services. It should begin with a small, auditable institutional core rather than attempting to rebuild every portfolio platform at once.

## Target architecture

```text
CrownThrive Operating System / Approved Knowledge
                    ↓
          Institutional Registry Core
                    ↓
     ┌──────────────┼──────────────┐
     ↓              ↓              ↓
   DAIL       Approval Service   CHLOM Core
     │              │         Rights · Rules · Roles
     │              │         Revenue · Records · Remedies
     │              │              │
     └──────────────┼──────────────┘
                    ↓
           Orchestrator / Agents
                    ↓
          CrownThrive IO / MCP
                    ↓
     Platform adapters + Codex + services
                    ↓
      Production systems / external vendors
                    ↓
          Events → DAIL → CrownLytics
```

## Service boundaries

### 1. Institutional Registry Core

Own stable IDs and schemas for organizations, actors, assets, platforms, corridors, domains, engines/vendors, products, knowledge sources, policies, risks, claims and relationships. It should not absorb every platform's transactional database.

### 2. DAIL — Decentralized Autonomous Information Ledger

Initial implementation is an append-oriented institutional event/audit service. Record event ID, type, actor, subject, source, time, correlation, environment, state transition, governing policy/approval, evidence references and correction lineage. The name preserves CHLOM doctrine; decentralization does not require public-chain deployment in this phase.

### 3. Approval Service

Evaluate whether an action is auto-allowed, denied, or requires one or more human approvals. Store request, risk class, policy/rights references, approvers, decisions, expiration, conditions and resulting event references.

### 4. Rights Registry

Record ownership/control, contributors, assignments/licenses, human authorship, AI provenance, permitted uses, restrictions, territories, windows, source assets, derivative relationships and evidence references.

### 5. DLA Service

Create and manage **Dynamic Licensing Assets** linked to rights. Lifecycle: draft → review → approved → active → amended/suspended/revoked/expired → corrected/reinstated where applicable. A DLA is a governed license object, not proof of a blockchain token.

### 6. Rules / Policy Registry

Version institutional, platform, product, cultural, compliance, security, privacy and workflow rules. Support effective dates, scope, precedence, test cases and human-review flags.

### 7. Roles and Authority Service

Resolve actor roles, delegated authority, program eligibility, organizational relationships and least-privilege permissions. Community titles, credentials and economic participation do not automatically grant institutional authority.

### 8. Revenue Registry

Version fees, royalties, splits, commissions, reserves, credits and payout logic. Initially calculate/reconcile; do not autonomously move material funds without approved rails and authorization.

### 9. Remedies / Case Service

Support holds, investigations, disputes, corrections, appeals, refunds-related governance, reinstatement and resolution evidence linked to the affected asset/license/event.

### 10. Orchestrator

Receive objectives/events, retrieve approved knowledge and registry state, select specialist workflows/agents, request approvals, invoke scoped tools, validate results and write DAIL events.

### 11. CrownThrive IO / MCP Gateway

Expose governed domain actions and platform adapters. Enforce authentication, authorization, rate limits, idempotency, validation, observability and data minimization. Never substitute raw database or shell access for a proper domain tool when a scoped action can be defined.

## Data ownership

- Transactional platforms remain authoritative for their own orders, subscriptions, content, bookings, tickets, courses and other operating state.
- Registry Core owns institutional identity/reference records and relationships.
- CHLOM owns governed rights/licensing records.
- Approval Service owns approval decisions.
- DAIL owns institutional audit/event history.
- CrownLytics consumes normalized events for analysis but is not the source of transactional truth.

## Sprint sequence

### Sprint 0 — Foundations

- stable ID conventions and schemas;
- source authority and status vocabularies;
- organization/actor/asset/platform seed records;
- privacy/risk classifications;
- environment/secrets/storage plan;
- synthetic fixtures;
- API/event conventions;
- AGENTS.md and repository controls.

### Sprint 1 — DAIL \+ Approval \+ Registry Core

Ship the audit/event backbone, approval state machine and base institutional registries. Prove append/correction behavior, idempotency, access control and evidence references.

### Sprint 2 — Rights \+ DLA \+ Rules \+ Roles

Implement CHLOM's executable rights/licensing authority with human approval gates and source-backed policy evaluation.

### Sprint 3 — Revenue \+ Remedies

Add versioned economics, reconciliation and case/remedy lifecycle.

### Sprint 4 — Orchestrator \+ IO/MCP

Connect specialist agents and P0 platform adapters only after governance services are stable and evaluated.

### Sprint 5 — P0 pilots

Run controlled use cases against Virality Music, CrownThrive Support, KJV Visualized/Sermon Toolkit, Locticians/Melanin Magic, AdLuxe or other P0 systems based on connector/deployment readiness.

## Initial acceptance criteria

Phase 3's institutional core is not complete because an API returns `200`. Before broad automation, prove:

- stable IDs survive edits and migrations;
- corrections append rather than erase audit history;
- restricted data cannot be retrieved by public roles;
- required approvals actually block execution;
- duplicate webhook/tool retries do not duplicate material actions;
- rights state and DLA state cannot silently diverge;
- policies and economic rules are versioned and traceable;
- every consequential mutation emits an attributable DAIL event;
- integration failures preserve recoverable state;
- tests and evals cover unauthorized, stale-source, conflicting-source and partial-failure cases;
- backup, restore and rollback procedures are exercised.

## Deferred target architecture

Do not launch tokens, DAO governance, public-chain settlement, bridges, autonomous legal/compliance authority, ZK infrastructure or production economic staking merely because historical CHLOM research describes them. Those remain separate gated architecture decisions after legal, security, privacy, economic and operational review.
