# Private Institutional Core and Storage Boundaries

The public **CrownThrive-Support** repository and Mintlify deployment are institutional knowledge projections. They are not appropriate stores for every operating record CrownThrive needs.

## Recommended storage model

```text
Public CrownThrive-Support / Mintlify
    Public-safe doctrine, architecture, support, policies, runbooks, source lineage

Private institutional registry repository / service
    Schemas, non-public registry definitions, controlled operating configuration,
    internal ADRs, private runbook metadata, automation configuration

Operational service databases
    Accounts, orders, licenses, cases, entitlements, campaigns, events and application state

Restricted evidence/object storage
    Contracts, assignments, source masters, protected evidence, private media,
    signed documents and other restricted artifacts

Secret manager / platform credential stores
    API keys, signing secrets, OAuth credentials, encryption keys, recovery material

Independent backup / archive
    Versioned exports needed for institutional continuity
```

## Repository roles

Phase 2.99 Workstream 1 now adopts a federated repository topology with a governed private core:

- `crownthrive1/CrownThrive-Support` remains the active connected public-safe institutional knowledge and Mintlify source.
- historical or separately evidenced CHLOM repositories remain preserved as lineage sources where verified; lack of current workflow connection is not evidence of deletion or nonexistence.
- `repo.crownthrive.os` is the logical identity for the required private institutional schemas/registries/machine-source boundary; its current state is `target_not_connected` until an exact private repository or equivalent service is provisioned and verified.
- `repo.chlom.services`, `repo.crownthrive.integrations`, `repo.crownthrive.infrastructure` and `repo.crownthrive.evals` are logical target boundaries for executable services, adapters/MCPs/SDKs, IaC and private evaluation fixtures. They are not claims that those repositories currently exist or are connected.
- restricted evidence and source masters remain in controlled object/document storage rather than ordinary Git history.

The full decision package is recorded in [Phase 2.99 Workstream 1 — Repository & Source Topology](/changelog/phase-2-99-workstream-1-repository-source-topology). Repository names may evolve through ADRs; the **authority, access and data-class separation** is the durable requirement.

## Never place in the public documentation repository

- production API keys or webhook signing secrets;
- wallet/private signing keys or recovery phrases;
- database credentials;
- full customer, contributor, employee or protected-person records;
- raw rights evidence or private contracts unless intentionally public;
- unreleased source masters and manuscripts;
- confidential Fingerprint implementation or private policy/risk logic;
- privileged legal communications;
- private partner economics or confidential financial data;
- security details that materially increase attack feasibility.

## Evidence references

DAIL and CHLOM should store durable references, hashes/checksums, classifications, source IDs and access metadata without requiring the audit ledger to contain the entire sensitive artifact.

## Backup rule

A vendor or SaaS integration may host a working copy, but critical institutional data must have an independent export and recovery plan. A future vendor outage or account loss must not be able to erase the institution's knowledge or rights history.

## Phase 3 gate

Before the first production service is deployed, CrownThrive should designate where each data class lives, which credentials it may access, how backups work, and which environments may process restricted records.
