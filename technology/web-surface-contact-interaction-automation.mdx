# Website Surface, Contact Interaction and Creative Asset Automation

## Governing decision

CrownThrive websites are operating surfaces, not independent sources of institutional truth. Sites-backed and other API-connected properties consume governed IDs, approved claims, Figma design contracts, Canva derivatives, contact/interaction requirements, analytics events, and recovery controls through explicit machine records.

```text
CHLOM / CIE / institutional records
→ Figma design contract
→ Canva approved derivatives
→ creative asset route registry
→ Sites / API-connected website
→ contact · CTA · form · link checks
→ DAIL / CrownLytics evidence
→ remediation queue
→ provider mutation only after certification
```

## Contact and interaction checks

Ordinary automated checks may verify:

- HTTPS status and response type;
- expected form presence;
- `mailto:` and `tel:` affordances;
- expected CTA text and destination routes;
- response checksum and latency;
- declared purpose and data class;
- consent/reuse boundaries;
- drift against registered expectations.

Ordinary health monitoring does **not** submit production customer contact forms and does not store form payloads.

The first machine run produced:

| Check | Result | Evidence |
| --- | --- | --- |
| CrownThrive home `Get In Touch` handoff | PASS | HTTP 200; expected text present |
| KJV `/contact` route | PASS | HTTP 200; mail interaction detected |
| CrownThrive primary contact page | D1 finding | HTTP 200; form + contact email text present; expected `mailto:` affordance not detected |

The CrownThrive contact finding created a D1 `site.interaction.remediation.plan`. It is autonomously plan-eligible but carries `external_mutation_allowed=false`.

## Contact-data and consent boundary

Operational contact is not marketing consent. Any later routing into ThrivePush, Collab Portal, CRM, analytics, email automation, or another system must preserve:

- source surface and form version;
- collection purpose;
- fields collected;
- consent basis;
- suppression/unsubscribe state where applicable;
- destination systems;
- retention profile;
- correlation/event identity;
- correction/delete path.

Synthetic/live submission testing requires a separate approved test identity, destination, anti-spam control, and run packet.

## Autonomous cadence

Two daily `pg_cron` jobs are active:

- `crownthrive_site_interaction_checks_daily` — due read-only interaction checks;
- `crownthrive_site_update_planner_daily` — internal remediation planning.

No external website mutation is performed by either job.

## Claim and namespace drift

Website differences in platform counts, phase labels, prices, metrics, or other public claims open evidence-controlled reconciliation. CrownThrive maintains multiple legitimate count universes and phase/maturity namespaces; an agent must resolve the intended scope before proposing a correction and cannot auto-rewrite by arithmetic convenience.

## Provider-write hard gate

A Sites or other website-provider adapter cannot mutate production until it proves:

1. exact provider/product/version;
2. exact site/project identity;
3. authentication and least-privilege scopes;
4. allowed page/field/asset mutations;
5. prohibited data classes and fields;
6. bounded test/dry-run path where supported;
7. read-before-write state;
8. rollback/version checkpoint;
9. read-after-write verification;
10. idempotency/concurrency behavior;
11. request/cost budgets;
12. rights/accessibility checks for asset changes;
13. DAIL/audit evidence;
14. provider export/exit path;
15. kill switch and degraded/read-only mode.

Before certification, every provider-side website mutation fails closed regardless of conceptual D0/D1 eligibility.

## Phase inheritance

- **Phase 2.99:** surface IDs, provider/project/version state, creative routes, contact/CTA checks, evidence, queues, direct MCP deployment, central-federation state, and provider-write gates.
- **Phase 3:** executable surface/interaction/claim/asset/event schemas and at least one bounded provider-adapter certification before provider-side autonomy.
- **Phase 4:** federated identity, entitlement, support, consent, analytics, and design patterns across website cohorts.
- **Phase 5:** contact/CTA conversion, form reliability, asset reuse, accessibility defects, and update latency become measured operational evidence.
- **Phase 6:** certified site/design templates and APIs may become governed developer/licensee assets.
- **Phase 7:** the interaction contract extends to kiosks, TapStations, MM Suites, and other phygital surfaces.
- **Phase 8:** provider custody, site/project inventory, creative ownership, export, and operational continuity become portfolio controls.
- **Phase 9:** advanced provenance/interoperability remains problem-driven.
- **Phase 10:** site/project mappings, interaction definitions, creative lineage, exports, agent instructions, and restore procedures become continuity artifacts.

A website is not integrated merely because it renders. Integration requires stable identity, governed content/design sources, interaction evidence, purpose controls, observable events, recovery, and a certified mutation boundary appropriate to its risk.
