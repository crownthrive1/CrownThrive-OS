# Website Surface, Contact Interaction and Creative Asset Automation

## Purpose

CrownThrive websites are operating surfaces, not isolated content silos. Every API-connected or Sites-backed property should consume governed institutional identity, claims, design contracts, creative assets, analytics and interaction rules through explicit records rather than copying state manually between websites.

This control plane extends the Design Control Plane and [IO / MCP](/technology/io-mcp) architecture into public web surfaces.

```text
CHLOM / CIE / institutional records
              ↓
     Figma design contracts
              ↓
   Canva approved derivatives
              ↓
 creative asset route registry
              ↓
   Sites / API-connected website
              ↓
 contact · CTA · forms · links · events
              ↓
 read-only autonomous checks
              ↓
 DAIL / CrownLytics / remediation queue
              ↓
 bounded update plan
              ↓
 provider write adapter only after certification
```

## Machine implementation — August 20, 2026

THIVEBASE/Supabase holds a private, service-role-only website-control registry for stable surface identities, creative routes, interaction definitions, append-only check evidence, update queues and provider certification state. Exact schema/table names, service identifiers, provider project identifiers, tool namespaces, scheduler identities, deployment versions and live findings remain restricted institutional evidence.

The authenticated website adapter provides bounded interface classes for:

- surface discovery;
- interaction checks;
- creative-route inspection;
- remediation-queue inspection;
- remediation planning.

External update execution and central dispatch remain disabled until separately certified. The existence of an adapter or registered interface is not proof that a provider write path is available.

## Current seeded surfaces

CrownThrive.com and KJV Visualized/Sermon Toolkit have stable internal surface records and public canonical hosts. Exact provider/project/version/rollback references are preserved in private custody. The provider/engine relationship remains evidence-classified; a rendering site does not prove editable-source custody or mutation authority.

## Creative asset routing

Website assets preserve source lineage through privately registered, versioned design-system and brand-kit references. Figma governs approved interface contracts; Canva is a downstream production source. These mappings do not authorize automatic site replacement. Routes carry rights, accessibility, publication and synchronization states separately, with `auto_sync_allowed=false` by default.

Future routes may add other CrownThrive platform assets only after the exact source, rights state, destination slot and provider relationship are established in private evidence.

## Contact and interaction checks

Bounded autonomous checks may verify public reachability, expected interaction types, required public markers, route integrity, declared purpose, consent boundaries, checksums, latency and remediation risk without retaining production form payloads or submitting real customer forms.

Detailed check URLs, response evidence, live findings and remediation records remain private. Public documentation reports only the doctrine and outcome class.

## Autonomous cadence

Daily read-only website checks and internal remediation planning run under private scheduler identities. The external update executor remains disabled. Once a provider write adapter passes authentication, field-scope, rollback and read-after-write tests, bounded mutations may be considered through the normal D0–D3 approval model.

## Contact-data boundary

A public contact form can collect personal data. The checker records structure and availability but does not retain form payloads.

Operational contact does not automatically authorize promotional reuse. Where a contact event is later routed into ThrivePush, Collab Portal, CrownLytics, CRM, email automation or other systems, the data flow must preserve:

- source surface and form version;
- purpose;
- fields collected;
- consent basis;
- suppression/unsubscribe state where promotional messaging is involved;
- destination systems;
- retention profile;
- event/correlation ID;
- correction/delete path.

## Claim and namespace drift

Website automation also watches for public statements that may no longer align with institutional records. A mismatch opens a reconciliation record; it does not automatically rewrite the website.

For example, current CrownThrive.com public pages expose multiple platform-count statements and public phase language. Because CrownThrive maintains separate count universes and phase/maturity namespaces, a scanner must first determine whether a difference is a genuine stale claim or a correctly scoped different namespace. Arithmetic convenience is not permission to auto-correct a public claim.

## Autonomous update classes

| Class | Website behavior |
| --- | --- |
| D0 | read/crawl/check/hash/compare; may run autonomously |
| D1 | deterministic repair plan or bounded reversible change after provider adapter certification |
| D2 | material content, public promise, campaign, design-contract or user-flow change; approval required |
| D3 | legal, rights, security, money, identity, destructive or reserved-authority mutation; explicit approval required |

Before the external write adapter is certified, **all provider-side website mutations fail closed regardless of conceptual class**.

## Required provider write certification

A Sites or other website-provider adapter cannot enable mutation until it proves:

1. exact provider/API identity and current version;
2. authentication and least-privilege scopes;
3. exact project/site ID;
4. allowed page/field/asset mutations;
5. prohibited fields and data classes;
6. dry-run or bounded test path;
7. read-before-write and read-after-write verification;
8. idempotency/concurrency behavior;
9. rollback/restore path;
10. asset rights/accessibility checks;
11. request/cost limits;
12. DAIL/audit evidence;
13. provider-exit/export path;
14. kill switch and degraded/read-only mode.

## Phase inheritance

**Phase 2.99:** register surfaces, provider/project references, contact/interaction checks, creative routes, MCP contracts, cron jobs and write-adapter gates.

**Phase 3:** make surface/interaction/claim/asset/event schemas part of the executable core and certify at least one bounded provider adapter.

**Phase 4:** federate websites through shared identity, entitlements, support, analytics, consent and design patterns while preserving platform-specific roles.

**Phase 5:** measure contact conversion, CTA performance, form reliability, update latency, asset reuse, accessibility defects and support/revenue outcomes.

**Phase 6:** expose certified website/design templates and APIs to approved developers/licensees.

**Phase 7:** extend the same interaction contracts to kiosks, TapStations, event screens and MM Suites phygital surfaces.

**Phase 8:** enforce portfolio-wide provider custody, asset ownership, export and operational continuity.

**Phase 9:** add advanced provenance/interoperability only when justified.

**Phase 10:** preserve site/project mappings, design/asset lineage, interaction definitions, provider exports, recovery and autonomous-agent instructions so websites can be rebuilt without undocumented operator memory.

## Permanent rule

A website is not considered integrated merely because it renders. CrownThrive integration means the surface has a stable identity, governed content/design sources, contact and interaction evidence, data-purpose controls, observable events, a recovery path, and a certified mutation boundary appropriate to its risk.
