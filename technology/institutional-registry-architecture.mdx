# Institutional Registry Architecture

Phase 3 should not begin from a handful of CHLOM tables. The broader CrownThrive institution needs a **federated registry architecture** that gives stable identity to the objects agents and platforms must reason about.

### Optimization and runtime evidence

ThriveBase maintains an optimization-specific institutional projection for the [ThriveBase Account Optimization Agent](/automation/thrivebase-account-optimizer):

- `thivebase_control.optimization_registry` — stable optimization IDs/keys, target/resource, baseline hashes/metrics, proposals, A/D authority, reversibility, rollback, expected/actual results, verification, independent review, DAIL receipt and lifecycle state;
- `thivebase_control.optimizer_runtime_state` — current observation baseline, regression-watch state and runtime status without multiplying historical rows for routine heartbeats;
- `chlom_runtime.agent_health` — real runtime heartbeat/readback state;
- `chlom_identity.agent_identity_records` — deterministic UUID/DID, fingerprint commitments and independently verified source/runtime bindings;
- DAIL — append-only material optimization, failure/correction and certification evidence.

<Note>
  `ThriveBase` is the canonical institutional name. The `thivebase_control.*` identifiers above are exact deployed legacy SQL identifiers and remain unchanged in documentation until a controlled schema migration proves a rename. Physical identifiers do not define public/canonical brand spelling.
</Note>

The optimization registry enforces `destructive_action = false`. A destructive request may be recorded as an analysis/recommendation/HOLD condition, but it cannot be promoted into an executable optimization state by the optimizer.

## Federated, not monolithic

A registry does not require one giant database. Operational systems can remain authoritative for their transactional state while the institutional layer maintains stable IDs, references, normalized events and governance relationships.

## Registry contract

Each registry needs schema version, stable ID, status vocabulary, source authority, ownership, audit timestamps, correction history, privacy class, export/backup behavior and API contract.

## Phase 3 gate

The first technical sprint should define these IDs and schemas before building agents that would otherwise create incompatible identifiers across different services.
