# ThriveBase Hosting Access & FTPS Control

## Purpose

This record governs the dedicated hosting-access path used for ThriveBase continuity work. It separates **credential custody**, **transport security**, **provider authentication**, **file-read capability**, **cPanel API read capability** and **write authority** so no successful layer is misrepresented as unrestricted deployment access.

The credentials remain restricted to the governed Vault/runtime path. Raw usernames, passwords, tokens, recovery aliases, private key material and provider-internal identifiers are not public documentation.

## Transport finding

The requested public FTP alias previously failed strict certificate-name validation. The institutional rule remains fail closed:

- never disable certificate verification to force credential-bearing access;
- never fall back to plaintext FTP;
- never treat `AUTH TLS` or a TCP connection as authenticated access;
- use only the certificate-valid provider endpoint established in restricted evidence.

A strict explicit-FTPS probe against the provider-canonical endpoint passed certificate validation, authenticated successfully, listed the restricted FTP root and completed a hash-only safe read canary. The one-shot FTPS probe was then disabled after success.

## Current cPanel and WHM control-plane state

The earlier cPanel API `403` observation is superseded. Current THRIVEBASE readback establishes a managed cPanel UAPI credential in Vault and an authenticated read through the JWT-protected `cpanel-account-api-control` adapter. The currently certified operation is the bounded `StatsBar/get_stats(diskusage)` read.

WHM is separately authenticated for allowlisted read-only observations. Its provider-write policy remains disabled.

These read certifications do **not** grant account, DNS, package, token, service, credential, filesystem or server mutation authority.

## Safe access rules

Read and recovery probes must continue to exclude `.env` files, private keys, credential files, database dumps, backup archives and other secret-bearing artifacts unless a separately governed incident/recovery packet explicitly requires them.

A provider-access capability is never equivalent to authority over THRIVEBASE data, GitHub source, DNS, certificates, billing, user accounts or production application state.

## Write gate

Hosting writes remain closed. A future hosting mutation requires a separately bound target and all of the following before provider dispatch:

1. exact resource/path identity;
2. pre-state hash or equivalent snapshot;
3. explicit non-destructive scope;
4. bounded payload/schema;
5. idempotency;
6. read-after-write verification;
7. rollback or compensation path;
8. post-rollback readback where rollback is exercised;
9. DAIL receipt;
10. independent verification where required by risk class.

<Warning>
  The Founder authorization for CrownThrive.io platform-API writes is **not** hosting/WHM/cPanel authority. Hosting writes remain closed and were not activated by that API authorization.
</Warning>

ThriveBase hosting access is read-certified across the established FTPS and cPanel/WHM read lanes, with credentials kept restricted. The FTPS one-shot probe is disabled after its successful canary. cPanel UAPI and WHM remain read-only. No provider-side hosting write is authorized or certified by this record.
