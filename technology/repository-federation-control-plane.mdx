# Repository Federation Control Plane

CrownThrive uses a **one institution / multiple governed repositories** model. `crownthrive1/CrownThrive-Support` is the canonical constitutional parent and institutional control-plane projection. Framework, service and research repositories remain separate repositories with their own bounded implementation concerns, but they do not become independent sovereign institutions.

## Parent-child invariant

A child repository moves through:

```text
pending_provisioning
→ provisioned_unlinked
→ linked_governed
→ suspended | retired
```

A child cannot move itself to `linked_governed`. The parent must verify the GitHub repository identity, required backlink contract, contract digests, inherited governance controls and applicable framework authority, then issue the parent certification.

A child in `pending_provisioning` or `provisioned_unlinked` may not publish governed work, invoke protected framework algorithms, create a sovereign vote, or claim CrownThrive production authority.

## Bidirectional linkage

Every governed child must maintain both directions:

- **parent → child:** `developers/manifests/repository-federation.v1.json` registers the child, parent, framework, state, authority and required contract;
- **child → parent:** `.crownthrive/federation.json` in the child identifies `crownthrive1/CrownThrive-Support`, the parent contract version/digest and the child's own immutable repository identity.

The private `institutional_federation.repository_references` registry records accepted API, MCP, doctrine, manifest, evidence, runtime-contract and backlink edges. Each accepted reference is associated with the append-only hash-chain evidence stream.

A stale or missing backlink is a federation defect. It does not disappear because the child repository otherwise runs successfully.

## Repository identity and API authentication

Repository-to-repository API calls use **GitHub Actions OIDC**, not a static shared GitHub/Supabase secret copied into every repository.

The federation bus validates the GitHub OIDC signature plus the expected issuer, audience, CrownThrive repository owner, repository name and immutable GitHub `repository_id`. The verified repository identity is then checked against the private federation registry before an operation is routed.

```yaml
issuer: https://token.actions.githubusercontent.com
audience: crownthrive-repository-federation
required_owner: crownthrive1
static_repo_shared_secret: prohibited
```

The controlled-test API is the `repository_federation_bus` service. Operations include repository state, bootstrap, heartbeat, publish, pull, reference registration, authority checks, parent child-certification and protected algorithm invocation.

## Constant communication and cross-chain evidence

Each governed repository must emit a heartbeat at least once per institutional relay period. The default liveness TTL is 3,900 seconds, leaving a small tolerance around an hourly cycle.

Agent communication uses structured repository messages:

```yaml
sender_repo_id:
receiver_repo_id:
sender_agent_id:
message_type:
severity:
payload:
requires_ack:
correlation_id:
chain_event_hash:
```

Message transport is available to governed CrownThrive agents but **message transport never creates a vote**. Sovereign votes remain bound to the active governance constitution and exact artifact/head evidence. Framework subagents likewise cannot manufacture additional votes.

Hash-chained repository events record heartbeats, messages, references, algorithm invocations and parent certification. The private event log keeps each repository's previous event hash, making ordered continuity tamper-evident without pretending that a database hash chain is a public blockchain.

## API and MCP relationship

The Edge Function is the authenticated runtime API. `integration_control.mcp_tools` provides the governed MCP registration layer for the same operations. MCP tool enablement never weakens API authorization: a tool call still inherits repository identity, parent certification, agent authority, risk class and D0-D3 limits.

Registered operations include:

- `repository_federation.heartbeat`
- `repository_federation.publish`
- `repository_federation.pull`
- `repository_federation.reference`
- `cie.score`

MCP registration is separate from production activation. A pending child remains blocked even if an operation exists in the MCP registry.

## Framework autonomy and override authority

A framework child is autonomous **inside its explicitly registered framework scope**. Its strongest ordinary override is a stricter result: deny, block, require correction, require evidence, or escalate.

For example, CIE may block an artifact because of a CIE hard block even when another domain approves it. CIE cannot use that framework authority to rewrite security policy, move money, transfer rights, change the sovereign constitution, remove Agent D, create D3 authority or certify its own repository.

Parent lock keys are non-negotiable for child repositories:

- constitutional governance;
- D3 human authority;
- security/privacy;
- rights/legal authority;
- money movement;
- repository federation;
- Vault/secret policy;
- phase hard gates.

The parent may suspend a child on material governance, security, continuity, custody or integrity failure.

## Framework algorithms and IP protection

Public repositories contain **contracts, dimensions, thresholds, hard-block ethics, schemas, digests and invocation clients**. Proprietary calibration, private evaluation corpora, confidence/recurrence calibration and other restricted implementation material do not belong in the public Support repository.

The machine registry is `developers/manifests/framework-algorithm-registry.v1.json`. CIE's protected policy bundle is resolved from Supabase Vault at runtime. The public CIE client calls the federation bus and receives only the permitted score/explanation output.

A Vault reference is not itself authority. Runtime invocation still requires an OIDC-verified governed repository and the calling agent/repository authority ceiling.

## Agent access

All registered CrownThrive agents may use eligible federation transport and callable framework tools from a governed repository. Access does not imply equal authority.

- ordinary agents can communicate, retrieve, reconcile and route within their registered scope;
- framework agents can exercise their explicit framework authority;
- framework subagents remain subordinate/non-voting unless a future constitution explicitly says otherwise;
- sovereign voting remains limited to the active voter manifest;
- D3 always remains human/reserved.

## Child repository bootstrap standard

A new framework repository must, before parent certification:

1. exist under CrownThrive custody;
2. be registered in the parent manifest before activation;
3. carry `.crownthrive/federation.json` backlinking to the parent;
4. use the current federation contract version;
5. inherit the governed merge/runtime/security baseline appropriate to its risk;
6. obtain GitHub OIDC identity through its own workflow;
7. call `bootstrap`, which leaves it non-operational;
8. pass parent inspection of its exact repository ID, backlink and contract digest;
9. receive parent `certify_child` authorization;
10. prove heartbeat and permitted message/reference traffic after certification.

Repository creation alone never satisfies these gates.

## CIE child status

`crownthrive1/CrownThrive-CIE` remains **pending provisioning**. The parent registry, private federation runtime and Vault-backed CIE algorithm are prepared, but the child GitHub repository does not yet exist, so no backlink or child OIDC proof can be certified.

The Convergent Ecosystem Framework Agent is therefore intentionally held until the CIE child completes provisioning, bidirectional linkage, OIDC bootstrap and parent certification.
