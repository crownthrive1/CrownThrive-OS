## Private Knowledge, RBAC and Automated Publication Architecture

CrownThrive needs one coherent knowledge control plane with multiple safe projections. “One knowledge base” does not mean every record belongs in one public repository or one search index.

## Knowledge classes

### Public

Approved support, public policies, platform explanations, public developer docs, current claims, public-safe frameworks, release notes and public status.

### Community/authenticated

Member, customer, creator, affiliate, partner, learner, church/team or developer guidance appropriate to the authenticated relationship.

### Internal

Operational procedures, non-sensitive platform records, drafts, task context, run packets, architecture working notes and staff knowledge.

### Restricted

Contracts, rights evidence, private source materials, unpublished assets, customer/identity/payment records, private economics, investigations, journals/reflections and sensitive partner/operator information.

### Strategic

Trade secrets, security architecture, confidential CHLOM algorithms/policies, incident details, negotiation strategy, unannounced portfolio decisions and sensitive capital/legal planning.

### Machine-only

Secret references, raw authorization state, policy-engine internals, private evaluation artifacts, service control records and event payload fields whose exposure creates risk.

## Recommended topology

```text
Private institutional source/control service
  ├── authoritative structured registries
  ├── restricted knowledge/source library
  ├── policy and role engine
  ├── search/retrieval indexes by classification
  └── publication pipelines
        ├── public CrownThrive-OS / PentaDocs
        ├── crownthrivesupport.com public help
        ├── authenticated role portals
        ├── operator/developer knowledge
        └── machine APIs/MCP resources
```

## CrownThrive-OS and crownthrivesupport.com

The current public repository/PentaDocs deployment should remain a public-safe institutional projection, with Mintlify retained as the current third-party provider layer. `crownthrivesupport.com` may become the branded knowledge entry point and can contain public plus authenticated areas only when the private areas are enforced through real application/data authorization.

Do not place private MDX in a public repository and rely on hidden navigation, obscure URLs, robots rules or frontend-only role checks.

## Authorization model

Use a combination of:

- RBAC for broad job functions;
- relationship-based access for organization/platform/asset ownership;
- attributes for data class, jurisdiction, purpose, environment and assurance;
- explicit grants for exceptional evidence access;
- policy-as-code for consequential actions;
- time-bound access and periodic recertification;
- break-glass access with incident review.

### Example decision context

```yaml
actor_id: ct.actor.01J...
role_ids: [ct.role.rights-reviewer]

  classification: restricted

  case_reviewer: true

```

## Search and retrieval isolation

Maintain separate indexes or enforce security filtering before semantic retrieval. A model must not retrieve restricted content and then redact after generation as the primary control. Caller identity, role, purpose, tenant/platform and data class are evaluated before results are returned.

Search logs and embeddings may themselves be sensitive. Do not send restricted corpora to external embedding/model providers unless approved data-use and retention terms permit it.

## Automated publication pipeline

```text
source or registry change
  → classify content and audience
  → scan secrets/PII/restricted terms
  → resolve source authority and current version
  → transform to audience-specific projection
  → legal/rights/cultural/claim review rules
  → build/lint/link/schema/accessibility/SEO tests
  → publish to approved destination
  → refresh public/private indexes and sitemaps
  → record DAIL event and source relationship
  → monitor rollback and drift
```

Public summaries of restricted sources must record the relationship and transformation version without exposing the source.

## Knowledge record

Every article/runbook/policy/source requires:

- stable knowledge/source ID;
- title and aliases;
- audience/data class;
- owner/reviewer;
- source authority;
- effective/current/superseded state;
- content version;
- related platforms/roles/policies;
- public/private projections;
- search/index state;
- review cadence;
- retention/hold;
- automation class.

## Private automation

Agents working with restricted knowledge require a registered agent identity, approved model/provider, private retrieval context, scoped tools, no public output destination by default, content-loss prevention checks and DAIL events.

## Document editing and collaboration

Use version control for public/system documentation and controlled document/evidence storage for restricted files. Collaborative editors must not become the only source of truth. Capture source exports, versions and authorship/decision records.

## Source-to-projection rule

One restricted source may produce:

- public summary;
- member guide;
- developer contract overview;
- operator runbook;
- founder dashboard;
- machine policy record.

Each projection has its own audience/version but references the same source and current authority.

## Automated lifecycle

- stale/unreviewed content enters a review queue;
- superseded content remains available according to role;
- public links redirect or archive appropriately;
- revoked access is removed from search and caches;
- deleted content follows retention/legal hold;
- index/document drift triggers repair;
- every publication can be rolled back to a verified version.

## Phase 2.99 decisions required

Workstream 2 now selects the core data architecture in [Private Institutional Data Architecture](/technology/phase-2-99-workstream-2-private-data-architecture): centralized institutional control, domain-partitioned operational stores, a restricted evidence vault, pre-retrieval search isolation, DAIL/event/workflow separation, RBAC \+ relationship \+ attribute authorization, purpose-limited cross-domain flows and provider-independent recovery.

Still to be finalized or implemented in later Phase 2.99 workstreams:

- identity provider/SSO integration;
- exact policy-engine implementation;
- secret manager/KMS and DLP tooling;
- exact database/object/search/queue/workflow providers and regions;
- publication workflow and CI implementation;
- crownthrivesupport.com public/authenticated deployment pattern;
- tested backup/restore and vendor-exit evidence.

## Target outcome

CrownThrive knowledge should update itself from governed records with minimal routine human work, while humans retain authority for legal, rights, cultural, security and other exceptional decisions.
