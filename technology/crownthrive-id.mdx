# CrownThrive ID

**CrownThrive ID** is the planned canonical identity and access layer for the CrownThrive ecosystem. It should broker authentication, roles, consent, eligibility, and portable profile references across heterogeneous CrownThrive platforms without forcing every platform onto one codebase.

This page is the current public-safe identity/trust successor for recovered identity-oriented Help Center material. It documents the institutional contract and boundaries; it does **not** claim that every platform is already federated, that every legacy account has been merged, or that an identity record by itself grants commercial, legal, rights, financial, or governance authority.

## Strategic purpose

The ecosystem spans independently deployed applications, hosted SaaS products, media systems, commerce properties, directories, community products, machine services, and future custom services. Identity therefore needs to be an institutional service, not an accidental byproduct of whichever community or SaaS platform happens to be active.

The identity layer must remain distinct from the [CHLOM Registry Model](/chlom/registry-model), which supplies stable machine-addressable institutional objects, and from the [Rights Ledger and Evidence Model](/chlom/rights-ledger-and-evidence), which records rights, evidence, provenance, and exposure rules. Identity says **who or what an actor is and what verified claims may be presented**. Other governed systems decide what that actor may do.

## Minimum responsibilities

CrownThrive ID should govern:

- canonical person, organization, creator, partner, staff, and service-account identifiers;
- authentication and standards-based federation where possible;
- role and capability assignments;
- consent and communication preferences;
- program and license eligibility references;
- account linking between legacy platforms;
- identity assurance and verification status;
- session and security events;
- portable profile references;
- suspension, recovery, merge, and account-deletion workflows.

## Identity is not authority

A stable actor ID is an input to authorization, not a substitute for authorization. A successful login must not independently create a license, payout entitlement, settlement authority, administrative privilege, provider-write permission, product entitlement, founder authority, or CHLOM approval.

Where a workflow needs institutional authority, it must resolve against the relevant governed record and evidence path. See [Source Reconciliation and Authority](/chlom/source-reconciliation) for source precedence and the [Phase 3 Readiness Gate](/technology/phase-3-readiness-gate) for the fail-closed requirements that apply before broad machine execution.

## Assurance and evidence boundary

Identity assurance can reference verification evidence, but sensitive evidence remains private by default. Public and downstream systems should receive only the minimum approved claims required for a bounded action. Raw identity documents, secret material, private keys, credentials, recovery factors, or restricted verification artifacts must not be projected into public documentation or ordinary platform payloads.

Identity evidence should be represented through stable evidence references, integrity markers, review state, and access policy rather than copied across systems. The [Restricted Source Register](/knowledge/restricted-source-register) and [Security & Privacy Continuity](/technology/security-privacy-continuity) define the surrounding exposure and least-privilege boundary.

## Architecture principle

Use standards such as OAuth 2.0 and OpenID Connect where platform compatibility permits. Integrations should use scoped adapters and least privilege. A social/community system may provide community features, but it should not become the permanent institutional identity source of truth solely because it contains user accounts.

Provider-native user IDs, email addresses, usernames, CRM contacts, community member IDs, payment customer IDs, and directory profile IDs are aliases or evidence inputs unless explicitly promoted through the governed identity model. They should not silently replace the stable CrownThrive actor identity.

## Lifecycle and correction

Identity state needs explicit lifecycle handling. Merge, suspension, recovery, deletion, alias changes, assurance changes, and role changes should preserve lineage so downstream systems can determine which actor record was valid at a given time.

Corrections are additive and auditable: preserve the original assertion, record the correction event, identify the governing evidence, update the current record, and reconcile dependent permissions or references. This follows the same correction doctrine used across CHLOM evidence and source reconciliation.

## Relationship to CHLOM

CHLOM records rights, licenses, authority, evidence, and eligibility. CrownThrive ID supplies the canonical actor identity used by those records. Identity evidence and sensitive verification artifacts remain private; public systems should receive only the minimum claims necessary for an approved action.

The intended machine path is:

```text
actor / provider identity
→ CrownThrive ID stable actor record
→ verification and evidence references
→ role / capability / consent context
→ CHLOM or service-specific authority check
→ bounded execution or fail-closed hold
→ audit / DAIL evidence
```

## Phase 3 requirement

Before broad automation, the institutional core needs stable actor IDs and a role/authority model that agents, APIs, entitlements, approvals, and audit events can reference consistently. The documentation and identity substrate may become machine-ready before production federation is complete; those two states must not be conflated.

Current documentation therefore treats CrownThrive ID as a substantive institutional identity/trust contract while keeping production activation, provider writes, high-risk authority, and unresolved platform-specific federation independently gated.
