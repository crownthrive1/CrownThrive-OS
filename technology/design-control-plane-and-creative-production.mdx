# Design Control Plane and Creative Production Governance

## Decision

CrownThrive adopts **Figma as the governed product-design, interaction-design and design-system control plane** and **Canva as a downstream high-volume creative-production layer**.

This is an architectural separation of duties, not a vendor lock-in decision. CrownThrive institutional identity, rights, policy and cultural authority remain governed by CHLOM, the Cultural Imprint Engine, adopted institutional standards and evidence. GitHub remains the implementation source for code. Mintlify remains the governed public-safe documentation projection. THIVEBASE/Supabase holds private machine registries, DAIL/evidence relationships and secret references where CrownThrive controls the credential. Google Drive is an archive/recovery and working-artifact mirror, not canonical executable authority.

```text
CIE / CHLOM / institutional authority
              ↓
       governed design contract
              ↓
            Figma
   tokens · components · patterns
              ↓
      design ↔ code evidence
              ↓
            GitHub
              ↓
       product implementations

Figma-approved brand/design contracts
              ↓
            Canva
              ↓
marketing · social · campaign · print · media production
```

## Canonical responsibilities

### Figma

Figma is the primary visual and interaction architecture layer for:

- foundations and design tokens;
- typography, spacing, color, elevation, radius, motion and accessibility contracts;
- shared CrownThrive components and variants;
- brand-family inheritance and controlled visual differentiation;
- responsive product patterns and page shells;
- application, dashboard, portal, kiosk and phygital interface design;
- prototyping and user-flow specification;
- component descriptions and implementation annotations;
- evidence-backed design-to-code and Code Connect mappings;
- design QA, accessibility and drift review.

### Canva

Canva is the downstream production layer for:

- social media graphics;
- campaign assets;
- flyers, posters and announcements;
- public-facing decks and media kits;
- thumbnails, quote cards and promotional art;
- reusable nontechnical templates;
- creator/community collateral;
- print and campaign production derived from governed brand/design contracts.

Canva must not silently redefine master tokens, component behavior, accessibility requirements, platform interaction patterns or CHLOM/CIE policy.

## Source-of-truth matrix

| Concern | Controlling layer |
| --- | --- |
| institutional meaning, cultural rules, rights and policy | CHLOM / CIE / accepted institutional records |
| visual and interaction design contracts | Figma |
| code implementation | GitHub and the applicable product repository |
| public-safe institutional documentation | governed Git \+ Mintlify projection |
| private machine registry, evidence references and secret references | THIVEBASE/Supabase |
| high-volume marketing/creative production | Canva |
| recoverable document/artifact mirror | Google Drive |

A downstream layer may implement or project an upstream contract. It does not acquire authority to redefine it by convenience.

## Token and brand provenance gate

No agent may invent a CrownThrive color, typography, spacing, icon, motion or brand token merely to populate a design-system file.

A token enters the canonical system only when its value and scope are supported by an authoritative current source such as an accepted brand specification, verified production implementation, governed brand kit, approved design record or explicit owner adjudication.

When sources disagree, the discrepancy becomes a governed design delta. Approximation is allowed only in clearly labeled research/prototype work and cannot silently promote into a canonical variable or production component.

## Design-to-code contract

Code Connect or an equivalent design-to-code mapping is evidence, not inference.

A mapping requires:

1. canonical Figma node/component identity;
2. exact repository;
3. exact source path;
4. exported component or implementation symbol;
5. supported variants/properties;
6. current implementation/version evidence;
7. owner and review state;
8. replacement/deprecation path.

A guessed source path, similarly named component or prototype is not sufficient. Unverified mappings fail closed.

Longer-term package targets may include shared token, component, icon, chart, commerce and media packages, but a target package name is not a claim that a package already exists.

## Agent team template

The automation control plane may instantiate the following bounded specialist roles when task requirements trigger them:

- **Design System Architect Agent** — foundations, components, design-system structure, inheritance and design contracts;
- **Design-to-Code / Code Connect Agent** — verified component↔source mappings, implementation drift and developer handoff;
- **Brand Content Production Agent** — downstream Canva/template/campaign production from approved design contracts;
- **Design Quality & Accessibility Auditor** — contrast, interaction states, responsiveness, consistency, accessibility and drift verification.

These are specialist subagents, not sovereign authorities. They inherit the CrownThrive autonomy classes, separation-of-duties rules, evidence requirements, tool budgets and approval matrix. The agent factory may create or retire task-scoped instances dynamically; it may not grant broader rights simply because the connector supports them.

## Tool-routing rules

The Tool/MCP Broker applies these defaults:

| Capability | Default class | Default state |
| --- | --: | --- |
| Figma inspect/read | D0 | permitted only through a certified connector path and request budget |
| Figma reversible design edit | D1 | task-scoped; source-provenance rules still apply |
| Figma Code Connect mapping | D2 | human/reviewer gated until exact source path is verified |
| Canva brand/read context | D0 | downstream context only |
| Canva design mutation/commit | D2 | preview \+ explicit commit approval |
| Mintlify read | D0 | bounded read |
| Mintlify branch edit | D1 | branch-scoped, reversible |
| Mintlify save/PR | D2 | repository/governance controlled |
| Google Drive read/archive | D0/D1 | archive/recovery use; never secret storage |
| GitHub repository read | D0 | repository scoped |
| GitHub PR/code mutation | D2 | explicit scope, validation and rollback |

The machine registry may be stricter than this table. A disabled tool remains disabled even if its conceptual autonomy class would otherwise permit the task.

## Current connector state — 2026-08-20

Current managed-connector evidence supports:

- Figma authenticated access and a governed canonical design-system file created;
- Canva authenticated brand-kit discovery;
- Mintlify authenticated branch-based documentation editing;
- GitHub authenticated repository inspection;
- Google Drive authenticated account access;
- THIVEBASE/Supabase private integration-control and Vault capability.

The central CrownThrive MCP/API dispatcher does **not** yet have certified unattended server-side adapters for those managed application connectors. Their machine tool contracts are therefore registered but dispatch-disabled until a real adapter, credential boundary, scopes, request budget, failure behavior and tests are certified.

Managed connector OAuth tokens are not copied into Supabase Vault. Where the provider owns the OAuth session, the credential-continuity record is `provider_managed_only`. Any future CrownThrive-controlled client secret, PAT, service account or refresh credential must be stored as a Vault-backed reference with rotation and least-privilege scope controls; raw values never enter Git, Mintlify, Figma, Canva, logs or generated public artifacts.

### Figma request budget

The currently verified Figma plan/seat supports a finite read-side MCP budget. The agent broker must meter reads, cache reusable context where safe and avoid repeated exploratory scans. Write-oriented capabilities that the provider exempts from read limits do not justify unnecessary mutation.

## Phase inheritance

### Phase 2.99

Record connector identities, credential boundaries, tool contracts, agent roles, canonical design-system identity, source-provenance rules, recovery paths and unresolved design inputs. Registration is not dispatch certification.

### Phase 3

Make approved design contracts executable: stable token schemas, component IDs, implementation relationships, accessibility/evaluation fixtures and evidence-backed Code Connect mappings. No approximate brand token may enter the production contract.

### Phase 4

Federate the design system across selected platform cohorts while preserving brand/corridor distinctions. New platforms inherit certified components/patterns instead of rebuilding common interaction primitives.

### Phase 5

Measure production design/content operations: conversion impact, production throughput, accessibility defects, implementation drift, support cost and reusable-component economics. Canva production becomes measurable downstream output, not an alternate design authority.

### Phase 6

Package mature design assets, templates, SDK/UI patterns and MM Suites deployment patterns for governed external developer/licensing use where chain of title, license terms and implementation support are ready.

### Phase 7

Extend certified patterns to kiosks, tap stations, location/device interfaces, accessibility, check-in, commerce, ticketing, rewards and other phygital/regional surfaces.

### Phase 8

Apply portfolio-level design inheritance, vendor portability, design-asset custody, export/backup and economic stewardship across Holdings-scale operations without double-counting brand/project variants as independent IP assets without an adopted rule.

### Phase 9

Add machine-readable design governance, verifiable provenance and advanced interoperability only where a validated problem requires it. Experimental cryptographic/decentralized methods do not inherit production authority.

### Phase 10

Preserve design tokens, component lineage, exports, source mappings, agent-role definitions, provider-exit procedures and restoration evidence so visual/product continuity survives vendor, model, repository and leadership transitions.

## Recovery and vendor-exit rule

The institution must be able to reconstruct the approved design contract without undocumented personal memory. At minimum retain versioned token definitions, component identities, implementation crosswalks, exported/recoverable assets, rights/provenance references, change records and provider-exit instructions in governed systems outside any single design vendor.

## Permanent rules

1. Figma is a design authority, not institutional/legal/cultural authority.
2. Canva is a production layer, not the master product design system.
3. GitHub code can diverge from design only through an explicit reconciled delta; neither side silently overwrites the other.
4. Design tokens and Code Connect mappings require evidence.
5. Managed connector credentials remain provider-managed unless a separately governed direct adapter is provisioned.
6. Tool capability does not imply permission.
7. Design automation inherits CHLOM, CIE, accessibility, rights, privacy, security, evidence and phase gates.
8. Every material design-system change produces documentation/repository impact and a recoverable next-state handoff.
