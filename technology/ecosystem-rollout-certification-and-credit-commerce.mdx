# Ecosystem Rollout, Certification and Credit Commerce

## Governing decision

CrownThrive uses one governed rollout-and-certification program to move platform cohorts from recovered/current evidence into tested operating state without collapsing identity, provider capability, implementation, rights, commerce, fulfillment, or phase authority.

The stable program is `ct.program.ecosystem-rollout-certification.v1`. The non-voting specialist/orchestration role is `ct.agent.ecosystem-rollout-certifier`.

The issue-backed execution projections are:

- GitHub issue `#178` — Ecosystem Rollout & Certification Program;
- GitHub issue `#179` — Unified Credit Commerce Migration & Monetization;
- GitHub issue `#100` — parent Phase 1–20 roadmap control board.

Issue/project state is execution coordination. It does not override accepted ADRs, hard gates, CHLOM/CIE authority, verified runtime evidence, or the current Phase 2.99 boundary.

## Sixteen-dimension certification contract

Every platform is evaluated independently across:

1. stable identity;
2. source/evidence;
3. provider/account/project mapping;
4. authentication and credential boundary;
5. read capability;
6. write capability;
7. design/brand provenance;
8. interaction/accessibility;
9. rights and chain of title;
10. credit-commerce eligibility;
11. fulfillment/delivery;
12. refund/dispute/reversal;
13. observability/DAIL;
14. recovery/provider exit;
15. public documentation/claim state;
16. lifecycle/release/deployment.

A `PASS` in one dimension never silently passes another. `UNKNOWN`, `HOLD`, `BLOCKED`, `DEFERRED`, `PACKAGED`, `CERTIFIED`, and `LIVE` retain their specific meanings.

## Unified Store Credits architecture

The target commerce flow is:

```text
payment provider
  → Store Credits funding
  → server-side provider readback
  → append-only THIVEBASE credit ledger
  → atomic credit purchase
  → CrownThrive order
  → CHLOM/THIVEBASE entitlement
  → CTL-* license grant
  → private delivery / membership access
  → refund or dispute reconciliation
  → append-only credit reversal when required
```

The credit program is `ct.credit.store.v1`.

Permanent economic boundaries:

- Store Credits are closed-loop purchasing value;
- they are not cash, interest-bearing balances, transferable instruments, cryptocurrency, or CrownRewards points;
- payment processors fund/reconcile credits but do not create CrownThrive licenses;
- CHLOM/THIVEBASE entitlement and license records control access rights;
- provider tax-code selection is evidence about provider configuration, not legal or tax sufficiency;
- a live payment rail cannot promote a package whose rights/license/fulfillment gates remain open.

## Current Store Credits gate

The technical rail has working server-side provider readback, append-only credit accounting, idempotent purchases, time-bounded memberships, `CTL-*` license issuance, private delivery, and synthetic refund reversal.

The program itself remains inactive because `legal_tax_state = specialist_review_required_before_live_activation` and the current packaged developer license requires further legal/terms review. The technical PASS evidence must be retained while the legal/terms gate remains HOLD.

## Asset-release certification

Asset release is intentionally separate from payment-rail maturity.

For each downloadable SKU, machine state records:

- package integrity;
- rights state;
- license-terms state;
- private-delivery canary;
- commerce-rail state;
- support-boundary state;
- overall release disposition.

Six current downloadable assets have passed private signed-delivery readback with HTTP 200, exact byte count and exact SHA-256 match. Signed URLs were not persisted. Their overall disposition remains `technical_pass_legal_hold` while rights/license terms remain pending.

A payment canary may block commerce activation. It must not erase independently valid package-integrity or delivery evidence.

## Canary model

Commerce canaries are append-only evidence and are classified by type and execution mode.

Current evidence includes:

- live-provider Stripe server readback without central webhook dependency;
- synthetic credit purchase;
- purchase idempotency replay;
- synthetic license issuance;
- time-bounded membership issuance;
- synthetic refund reversal with idempotent replay;
- per-SKU private-delivery signed-URL/readback canaries.

A synthetic canary proves the internal contract under test. It does not substitute for a live provider refund/dispute canary where provider behavior itself is the certification target.

- `ecosystem_rollout_certification`;
- `credit_commerce_migration`;
- `asset_release_certification`;
- `provider_legacy_rail_exit`;

The certifier may spawn task-scoped non-voting specialist children for source reconciliation, proof verification, design/Figma/Canva, website/contact/accessibility, API/MCP, security/privacy, IP/rights/licensing, finance/tax/treasury, operations/SRE, regional/localization, and commerce testing.

Children do not create sovereign votes or reviewer independence merely by being separate tasks. Same-family descendants cannot manufacture quorum.

## MCP and autonomous operations

A private Edge Function `ecosystem-rollout-control` implements a dedicated MCP `2026-07-28` read/plan surface. Direct tools include program snapshots, platform lists, certification matrix reads, commerce queue reads, asset-release state, canary history, and internal next-action planning.

The direct service is deployed with JWT enforcement. Central CrownThrive MCP tool records are registered `enabled=false` until authenticated end-to-end MCP client and central-dispatch certification are proven.

No current rollout tool can:

- mutate an external provider;
- certify a platform;
- activate Store Credits;
- publish a product;
- move money;
- grant a sovereign vote;
- enter Phase 3.

Make certification, entitlement, license, DAIL, reversal and bounded provider-adapter contracts executable. Pilot only from the accepted Phase 2.99 snapshot.

### Phase 6 — licensing, IP and developer economy

### Phase 7 — physical, phygital and regional expansion

### Phase 9 — advanced interoperability

Use cryptographic/provenance/interoperability methods only for validated needs. Machine-readable credits do not become token/crypto authority by implementation drift.

### Phase 10 — generational continuity

Prove reconstruction of platform certification state, credit ledgers, entitlements, licenses, assets, canaries, provider mappings and restore procedures.

## Absolute no-go rules

1. Do not disable a working production payment/webhook rail before replacement proof.
2. Do not call a product live because a price, ZIP, public page or provider product exists.
3. Do not grant a CrownThrive license from Stripe/provider metadata alone.
4. Do not convert Store Credits into transferable/cash/crypto value by drift.
5. Do not use customer PII as public ledger identity.
6. Do not delete failed/synthetic test history; append corrections/reversals instead.
7. Do not let a legacy certifier collapse asset integrity, rights, commerce and delivery into one status.
8. Do not infer an institutional stable ID from a platform name.
9. Do not treat direct MCP deployment as central federation or provider-write certification.
10. Do not advance Phase 3 from this rollout program while the Phase 2.99 hard exit remains blocked.
