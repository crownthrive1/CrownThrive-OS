## Status as of September 5, 2026

CrownThrive has two independently accessible Supabase projects: **ThriveBase** and **ThriveBase-Public**. Connected management and SQL observations verified both projects. The founder identified their compute tiers as Small and Micro respectively; the project metadata response did not independently return those compute labels.

A non-secret topology register has been installed and read back in both projects. ThriveBase holds the canonical topology metadata; ThriveBase-Public holds a documentation mirror. This register is not an executable route table.

**No Vault credentials were moved, no secret resolver was replaced, and no live API or MCP route was switched by this change.** A tool-level safety block interrupted a custody-dependency inspection. A topology record must not be represented as a successful migration, runtime adoption, provider authentication test, or CHLOM/DAIL certification.

## Ownership boundaries

| Project | Recorded role | Change boundary |
| --- | --- | --- |
| ThriveBase | Existing primary control plane | Preserve current credential custody and live service routes until an individually verified cutover. |
| ThriveBase-Public | Existing public-projection plane; candidate for reviewed offload | Keep credential access private. The word Public in its project name does not authorize secret disclosure. |

Exact project references, regions, inspection statistics, and operational evidence belong in the restricted CrownThrive MCP, API & Credential Control Registry and the PentaDocs Source & Publication Records folder. Do not copy credential values into documentation, repository commits, Sheets, Drive notes, or client-side configuration.

## Vault is not a shared global namespace

The inspected runtime-secret resolver reads the local ThriveBase Vault. Some credential-health and capability-lease functions also read that local Vault directly. Moving a named entry to another project does not automatically update those consumers.

A future split needs an explicitly authorized, project-qualified resolution contract and a complete dependency map. Keep root keys, signing keys, hot credentials, and active recovery paths in their current custody until their particular migration has passed validation. Treat cold or superseded credentials as candidates for review, not as disposable or automatically movable records.

Supabase documents Vault as database-managed encrypted secret storage with a controlled decrypted view. Its Edge Function limits are separate from Vault storage. Moving Vault rows is not proof of freed function deployment slots, lower compute consumption, or reduced billing. See the [Vault documentation](https://supabase.com/docs/guides/database/vault) and [Edge Function limits](https://supabase.com/docs/guides/functions/limits).

## Routing and certification responsibilities

PentaCredentials and PentaFlex retain custody and version continuity. PentaMCP and PentaWire must use verified bindings rather than inferred project names. PentaFabric and PentaMesh must distinguish documented destinations from deployed routes. PentaCertify must evaluate the actual operation and evidence before marking a cutover verified. PentaDocs publishes the resulting state, including incomplete work.

Adding project metadata does not demonstrate that any running consumer has adopted it. Preserve existing endpoints and bindings while preparing a successor route. Do not advertise automatic failover or cross-project secret resolution until those mechanisms are deployed and tested.

## Required evidence before a future cutover

1. Verify the candidate list, authority, source version, all direct and indirect consumers, and destination access controls. Preserve founder-supplied credential history.
2. Transfer through an approved confidential server-to-server mechanism; never export plaintext into documentation or client-visible logs.
3. Verify destination decryption and integrity without returning secret values. Test authorized access, denied unauthorized access, timeout behavior, and rollback.
4. Update the resolver and each affected direct consumer. Verify the actual API/MCP operation, not merely tool discovery or an inventory row.
5. Record the real change and available audit evidence. Retire a source copy only after the verified cutover and applicable preservation requirements allow it.

Until that evidence exists, the state remains **metadata registered; migration not executed**. Source credentials, existing routes, billing settings, and schedulers remain unchanged by this topology-documentation change.
