## Repository Family and Federation

CrownThrive uses a **federated repository family** with one canonical OS authority hub and independently governed component and execution repositories. Federation allows contracts, observations, evidence, and governed work to move across the family without turning the estate into an uncontrolled monorepo or a set of isolated source silos.

## Canonical roles

| Role | Public-safe responsibility |
| --- | --- |
| CrownThrive OS authority hub | Maintains canonical institutional state, public-safe governance, versioning, PentaDocs source, convergence contracts, and family-level evidence rules. |
| Public component repositories | Maintain approved public component doctrine, contracts, schemas, examples, and technical projections within their exact scope. |
| Restricted execution repositories | Maintain separately authorized implementation, service, integration, continuity, or control-plane scope without projecting private contents into public Git. |
| Evidence and custody systems | Preserve exact provider observations, restricted node identity, receipts, private heads, credentials references, recovery bindings, and other non-public evidence. |

The public authority hub is `crownthrive1/CrownThrive-Support`. Exact coordinates and heads for restricted repositories are intentionally excluded from this public projection.

## Stable repository-node record

Every governed node should resolve to a stable institutional identity and record:

- canonical role and accountable owner;
- visibility and permitted/prohibited data classes;
- default branch and repository-native review policy;
- source-of-truth scope and parent/peer relationships;
- accepted contract and schema versions;
- local node-manifest and attestation version;
- current observation time and freshness/expiry rule;
- convergence, workflow, certification, release, and documentation-impact state;
- backup/export, rollback, provider-exit, and incident route; and
- public projection policy.

Mutable repository names, provider IDs, URLs, branches, and heads remain external references. They do not replace the CrownThrive stable node identity.

## Federation contract

The family exchanges three public-safe record classes:

1. **contracts** — versioned schemas, invariants, compatibility rules, and required governance controls;
2. **attestations** — exact-node statements about the contract version and revision tested, without exposing restricted source; and
3. **receipts** — validation, provider readback, rollback, recovery, and documentation-impact evidence.

PentaFederation transports and relates those records. PentaInterOps validates compatibility. PentaNerves ingests sanitized changes. PentaBrain classifies drift. PentaSpine preserves ordered evidence. PentaFactory prepares bounded remediation candidates. PentaBody produces the operator projection.

## Independent state dimensions

A node's state must not be flattened into one green label. Record separately:

| Dimension | Example question |
| --- | --- |
| Discovery | Was the node observed through a current authorized provider surface? |
| Contract alignment | Does it consume the required family contract version? |
| Source convergence | Is its scoped candidate reconciled with the authority hub? |
| Workflow evidence | Did required checks execute on the exact revision? |
| Provider binding | Is the cross-repository execution identity authorized and verified? |
| Runtime/deployment | Is the relevant service actually deployed and read back? |
| Failover | Has the exact recovery tier passed restoration, cutover, and failback? |
| Projection | Is public documentation current, deployed, and safely redacted? |

## Current evidence posture

- Deterministic repository convergence and hot/cold/silent route selection are implemented and controlled-tested on the candidate revision; live provider binding and child readback remain `HOLD`.
- Live cross-repository GitHub Actions credential binding remains `HOLD` until exact provider execution and readback exist.
- Live Command Center deployment remains `HOLD` until the sanitized projection is deployed and read back.
- Infrastructure failover certification remains `HOLD`; documentation, route definitions, unit tests, or repository connectivity cannot substitute for a live recovery drill.
- The current public projection does not assert a total physical repository count because the exact private inventory is restricted and current-node observation must remain evidence-dated.

## Authority and privacy firewall

Repository presence, connectivity, a green workflow, compatible schemas, or an accepted peer attestation cannot create merge authority, D3 authority, rights, licenses, money movement, provider-wide mutation permission, or child self-activation.

Private node coordinates, private Git heads, silent-route details, secrets, raw signatures, and restricted implementation evidence remain outside PentaDocs. Public pages may disclose the applicable state and HOLD reason without disclosing the protected route or resource.
