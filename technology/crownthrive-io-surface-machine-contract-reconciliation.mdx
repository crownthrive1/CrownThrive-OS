# CrownThrive IO Surface & Machine-Contract Reconciliation

The recovered **CrownThrive IO BioLink Master Standard** is valuable institutional evidence about how CrownThrive intended identity-facing link surfaces to be structured. It is not, by itself, proof of the current deployment, provider configuration, API capability, provider-write permission, production status, or Phase 3 readiness of CrownThrive IO.

This page is the current public-safe successor for that recovered standard. It preserves the useful interface and machine-contract lineage while binding current claims to governed deployment, adapter, registry, and readiness evidence.

## Core separation

CrownThrive IO must keep these states distinct:

```text
surface identity
!= domain/deployment certification
!= machine contract
!= provider/API capability
!= authenticated provider write
!= production certification
!= institutional authority
```

A BioLink surface can have a stable CrownThrive identity even when a provider implementation changes. A public page can exist even when a specific API capability is unavailable. An API may authenticate successfully while a particular write permission remains closed. None of those facts alone authorizes a production mutation or changes institutional state.

## Canonical surface identity

A CrownThrive IO surface should resolve through stable institutional identity rather than through a vendor-specific page ID. The current record should preserve, where known:

```yaml
surface_id: ct.surface.crownthrive-io.example
platform_id: ct.platform.crownthrive-io
canonical_route: null
surface_class: biolink | short-link | qr | profile | static-page
implementation_provider: replaceable
provider_object_id: restricted_or_alias_only
read_state: unresolved
write_state: unresolved
production_state: unresolved
last_verified_at: null
```

The [Platform Registry](/ecosystem/platform-registry) governs canonical platform identity. Provider object IDs and deployment-specific aliases are implementation references, not the durable CrownThrive identity of the surface.

## Deployment evidence boundary

Domain and hosting observations are interpreted through [CrownThrive IO Domain & Deployment Certification](/technology/crownthrive-io-domain-deployment-certification). DNS resolution, TLS, HTTP reachability, application rendering, source-control state, and provider-admin evidence are separate checks. A successful public render does not certify every provider-side control path.

Current documentation should therefore state the narrowest verified result. If the domain is reachable but a provider API write has not been exercised with rollback, the public surface may be described as reachable while provider-write certification remains pending or held.

## Machine-contract boundary

The surface contract describes what a CrownThrive IO object means. The machine contract describes how software may read or change that object. Those contracts must not be collapsed.

The [Platform API Adapter Matrix](/developers/platform-api-adapter-matrix) governs provider-facing authentication, endpoint, scope, side-effect, webhook, retry, export, and rollback evidence. The [CHLOM Ecosystem Integrations](/chlom/ecosystem-integrations) record places that adapter inside the broader institutional integration topology.

A valid machine contract should identify at minimum:

- stable institutional object ID;
- provider alias or adapter binding;
- operation class such as read, create, update, delete, publish, rotate, or restore;
- required scopes and role/authority prerequisites;
- idempotency and replay behavior where applicable;
- expected provider response and normalized institutional event;
- rollback or compensation path for writes;
- evidence and correlation identifiers;
- public/private data classification.

## BioLink-standard continuity

The recovered BioLink standard can inform current composition rules such as profile hierarchy, link grouping, role-aware presentation, brand continuity, accessibility, metadata, and reusable surface patterns. Those design semantics remain useful even when the exact historical provider, page builder, or implementation has changed.

What does **not** carry forward automatically is any unsupported assertion that a historical field, button, automation, redirect, embedded widget, QR action, analytics hook, or provider integration is active today. Current capability must be established from present evidence.

## Read versus write

CrownThrive IO integrations must explicitly separate read certification from write certification.

```text
authenticated read
→ proves only the bounded read that was tested

bounded provider write
→ requires exact scope + side-effect test + readback + rollback/compensation

institutional state change
→ additionally requires governing authority and canonical event reconciliation
```

A provider may expose broad APIs, but CrownThrive does not infer permission or production safety from provider documentation alone. Provider reachability is execution evidence; it is not institutional truth.

## Registry and event continuity

Machine-visible CrownThrive IO objects should resolve through governed registry IDs and normalized events. The [CHLOM Registry Model](/chlom/registry-model) supplies the stable-object doctrine. Surface and adapter events should be able to answer what object changed, which actor or agent requested it, what authority basis applied, which provider executed it, what evidence proves the result, and how the action can be reconciled or corrected.

Where the provider changes, the institutional identity and lineage should survive. Where a provider object must be retired, its alias should remain historically traceable rather than silently reused for a different CrownThrive object.

## Phase 3 boundary

This reconciliation page does not unlock Phase 3. The independent [Phase 3 Readiness Gate](/technology/phase-3-readiness-gate) continues to govern entry. Documentation qualification proves only that the recovered CrownThrive IO BioLink standard now has a substantive, internally connected current successor suitable for parent review.

The current documentation source-of-truth rules in [Documentation Source of Truth & Autonomous Governance](/standards/documentation-source-of-truth-and-autonomous-governance) also remain binding: a current source may supersede a historical implementation claim without erasing the historical record that explains where the concept came from.

## No activation by documentation

This page does **not** activate a provider write, DNS change, page publication, redirect, credential, identity proof, payment, settlement, entitlement, production deployment, or Phase 3 service. It creates a current successor for surface and machine-contract meaning only.

Terminal disposition of the recovered BioLink title remains pending parent certification. Any operational or production claim must continue to be supported by current machine evidence, exact authority, readback, and rollback/compensation where the action has side effects.
