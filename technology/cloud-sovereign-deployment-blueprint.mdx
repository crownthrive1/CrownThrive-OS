## Cloud and Sovereign Deployment Blueprint

CrownThrive should move toward a governed cloud operating model that can survive vendor change and later support selectively sovereign or decentralized components. Cloud-first does not mean cloud-locked.

## Target reference stack

The current CHLOM high-level technical baseline supports a practical stack such as:

- TypeScript services using NestJS/Fastify or an equivalent supported framework;
- managed PostgreSQL with strong tenant isolation, point-in-time recovery and tested export;
- S3-compatible versioned object storage with legal-hold capability for evidence;
- Redis-compatible cache/queue coordination where appropriate;
- replayable event bus;
- durable workflow orchestration comparable to Temporal;
- OpenSearch-compatible search/indexing;
- OpenTelemetry-compatible tracing, metrics and logs;
- infrastructure-as-code such as Terraform/OpenTofu;
- CI/CD through GitHub Actions or an approved equivalent;
- managed secret store/KMS/HSM abstractions;
- provider adapters for payments, email, storage, identity and other replaceable vendors.

Equivalent technologies may be chosen through ADRs; institutional contracts and exportability matter more than brand loyalty.

## Environment standard

- `local` — developer machine/sandbox with synthetic data;
- `dev` — shared development environment;
- `test` — automated integration/evaluation;
- `staging` — production-like validation;
- `production` — live governed environment;
- `recovery` — isolated restore/continuity environment;
- `research` — advanced CHLOM laboratory isolated from production authority.

Never use production credentials or unrestricted production data in development/test.

## Workload separation

Partition services into domains such as:

- institutional registry/control plane;
- identity and authorization;
- CHLOM rights/policy/licensing;
- DAIL/events/evidence;
- commerce/entitlements;
- media/catalog;
- support/knowledge;
- advertising/affiliates;
- education/ministry;
- MM Suites/phygital operations;
- analytics/measurement;
- automation/control plane.

Domains communicate through versioned APIs/events and least-privilege service identities.

## Infrastructure ownership records

Every environment requires:

- account/subscription owner;
- billing owner;
- organization/project ID;
- region;
- deployment method;
- repository/branch/tag;
- domain/DNS/SSL;
- database/storage/search/queue/workflow dependencies;
- secret references;
- observability endpoints;
- backup and restore target;
- data residency/classification;
- incident owner;
- vendor exit/export method;
- current cost and capacity.

## Deployment contract

A production deployment must include immutable build artifact/image, source commit, dependency lock, migrations, configuration version, secrets references, test/evaluation results, approval, rollout strategy, health checks, rollback and DAIL release event.

## Progressive delivery

Use feature flags, canary or blue/green releases, shadow traffic, staged migrations and per-tenant activation where risk justifies them. Avoid irreversible all-at-once migrations.

## WordPress and hosted platform operations

For WordPress or vendor-hosted properties, maintain:

- core/theme/plugin inventory and versions;
- source/customization repository where possible;
- staging/backup;
- database/media export;
- update policy;
- vulnerability monitoring;
- least-privilege admin/service accounts;
- API/webhook inventory;
- caching/CDN/DNS records;
- rollback and vendor-exit path.

Custom plugins, snippets and bridges should be versioned in Git rather than living only in a dashboard editor.

## Centralized now, sovereign later

The first priority is an auditable, legally governable cloud system. Later sovereignty may include:

- portable/open data formats;
- self-hostable core services;
- multiple cloud regions/providers;
- independent key custody;
- DID/VC and proof portability;
- decentralized anchoring/attestations;
- external verifier/oracle participation;
- selective settlement/governance infrastructure.

Do not decentralize secrets, private evidence, personal data or legal authority merely to claim decentralization.

## Continuity

Recovery objectives must be explicit by service. Backups are verified only through restoration. Critical institutional registries, rights, policies, agreements and DAIL records require off-provider copies and documented recovery authority.

## Phase 3 deliverables

Phase 3.0 must produce the infrastructure repository structure, IaC baseline, environment registry, secret-management ADR, deployment standard, observability baseline, backup/restore tests and provider-abstraction contracts before services become critical dependencies.
