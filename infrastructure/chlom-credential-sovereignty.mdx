# CHLOM Credential Sovereignty

CHLOM treats credentials as protected capabilities, not as strings to circulate between agents, documents or client code.

## Core rule

A new governed credential follows this lifecycle:

`founder/provider creation -> one-time secure intake -> Vault custody -> opaque version binding -> capability lease -> server-side provider operation -> append-only custody receipt -> supersede or revoke`

The raw credential is never part of the public contract.

## Versioned custody

Each CHLOM-managed credential has:

- a stable server-side active alias for provider compatibility;
- an opaque immutable archived version in Vault;
- a configured recovery alias where applicable;
- an append-only version/event history;
- a random non-derived credential handle;
- a keyed internal fingerprint used only for custody consistency checks.

Rotating a credential does **not** delete the previous version. The new value becomes active while the prior version remains sealed for rollback, provenance and incident reconstruction.

Administrative/full-privilege credentials require explicit founder-supplied authority for rotation or rollback. An agent cannot manufacture that authority from a score or from possession of a lease.

## Capability leases

Agents should normally receive a `ctlease` capability handle rather than a provider credential.

A lease binds:

- one credential version;
- one caller;
- one allowed operation;
- one purpose;
- an authority class;
- a short expiration;
- a bounded use count.

The provider adapter consumes the lease server-side. Secret material is resolved only inside the trusted execution boundary and is not returned to the originating agent.

## Privacy and audit boundary

CHLOM is designed for **non-public correlation**, not absence of accountability.

Public and ordinary operational surfaces may expose only sanitized state such as capability purpose, lifecycle, version class and opaque receipts. They must not expose raw secrets, Vault names, private credential mappings, keyed fingerprints, provider account identifiers or recovery material.

Restricted custody records remain internally attributable so CrownThrive can prove who authorized a rotation, which version was active, whether a lease was consumed and whether rollback occurred. External providers may retain their own account, security and usage logs; CHLOM does not claim to erase or bypass provider-side records.

## Continuity and self-healing

Credential custody uses layered continuity:

1. active Vault alias;
2. immutable opaque Vault archive;
3. recovery alias where configured;
4. encrypted CHLOM continuity archive;
5. append-only DAIL/Git/Drive control history containing no secret value.

A custody watchdog checks alias/archive/recovery consistency using a Vault-held keyed fingerprint and returns only healthy/warning state. Missing recovery aliases may be repaired only from a fingerprint-verified archived version. No provider write is required for that internal repair.

Expired capability leases are automatically invalidated. Leases may also be explicitly revoked before expiration.

## Public/private contract

**Public-safe:** lifecycle model, opaque handle format, bounded lease semantics, authority invariants, rollback doctrine, continuity doctrine, sanitized health state.

**Restricted:** credential values, Vault locators, keyed fingerprints, provider mappings, recovery values, internal resolver topology, access-control internals and incident evidence.

## Governance invariants

- No silent deletion.
- No raw credential in GitHub, Mintlify, Drive plaintext, email, client code or public telemetry.
- No D3 authority from a lease or algorithmic score.
- No agent self-grant of a full-administrator credential.
- No public correlation between an opaque credential handle and a provider/account unless intentionally disclosed through a separate governed process.
- Provider-side traceability remains outside CHLOM's control and is not represented as anonymity.

This contract is currently **controlled test / governed HOLD** and does not by itself authorize new provider credentials, account changes, money movement, production promotion or Phase-3 advancement.
