# Automation Control Plane, Agent Factory and Work Queues

The automation control plane coordinates CrownThrive work without giving one model, connector, vendor or spawned child universal authority.

## Core services

1. **Objective intake** — founder directives, scheduled events, incidents, support cases, platform events and system health signals.
2. **Run-packet compiler** — converts the objective into scoped workstreams, sources, roles, tools, approvals, tests and rollback.
3. **Institutional retrieval** — resolves current records, source authority, audience, visibility and unresolved conflicts.
4. **Policy/authority evaluator** — CHLOM Rights, Rules, Roles, Risk and approval checks.
5. **Governed agent router/factory** — selects registered roles or instantiates bounded ephemeral children under a machine delegation contract.
6. **Work queues** — priority, dependency, retry, dead-letter, hold, research and scheduled queues.
7. **Tool/MCP broker** — issues scoped capabilities and routes approved services.
8. **Approval service** — machine and human approvals with expiration and conditions.
9. **Verification/evaluation** — tests outputs, claims, rights, security, accessibility and audience fit.
10. **Execution gateway** — performs changes through versioned APIs/MCPs/adapters.
11. **DAIL recorder** — append-only event, evidence, correction and decision trail.
12. **Knowledge updater** — updates registries, docs, search, runbooks and next-run baseline.
13. **Watchdog/recovery** — detects failure, retries safely, rolls back or escalates.

## Authority versus cognition

CrownThrive permits **fluid cognition with rigid authority**. An orchestrator may discover that a packet needs several specialties, and a specialist may fan out into bounded subchecks, but delegation never expands the sovereign voter pool or bypasses D3 authority.

```text
capability ≠ permission
child count ≠ quorum
confidence ≠ authority
research ≠ certification
successful build ≠ production approval
```

The fixed sovereign voter pool remains A/B/C/D/S. Children and specialists are non-voting unless a separately governed future change explicitly changes the constitution.

## Governed agent factory

The machine delegation contract is `developers/manifests/agent-factory-delegation-policy.v1.json`.

Every ephemeral child requires:

```yaml
child_run_id:
parent_agent_id:
root_agent_id:
delegation_path: []
independence_family:
role_class:
scope_key:
source_snapshot:
allowed_tools: []
allowed_data_classes: []
authority_ceiling:
budget:
ttl:
output_class:
promotion_route: []
termination_state:
```

Default child behavior is non-voting, no production write and a D1-or-lower authority ceiling unless a registered parent contract explicitly permits bounded D2 preparation. Material child output must remain reconstructable.

### Persistent versus ephemeral roles

**Persistent roles** require stable identity, owner, versioned contract, lifecycle, tools/data classes, eval suite, escalation path, lineage and governed activation.

**Ephemeral roles** exist only for a bounded run. They inherit an authority ceiling, budget and TTL and terminate as completed, expired, cancelled, failed or escalated.

A runtime cannot create permanent institutional authority merely by inventing a name.

### Spawn matrix

- **A** — strongest bounded dispatcher; may route research/retrieval/analysis/domain/coordination children to depth 2.
- **B** — read-only retrieval/audit children to depth 1; descendants cannot independently verify B-originated material.
- **C** — schema/validator/adapter/test/docs builder cells to depth 2; one implementation family, no self-approval.
- **D** — checks-only children to depth 1; no builder children and no delegated D vote.
- **S** — scanners/TEVV/dependency/threat-model children to depth 2; no security-vote multiplication.
- **E/F/G/H** — narrow specialist fan-out to depth 1.
- **I** — backup/export/restore collectors only.
- **J** — minimal snapshot collection only; late gate cannot be relaxed.
- **K** — dependency/impact analyzers; no phase advancement.
- **L** — scanner/parser helpers; tags create no authority.
- **M** — source-family fan-out to depth 2; retrieval is not verification.
- **N** — deterministic proof/expiry/contradiction subchecks only; no manufactured independence.
- **O** — branch/diff/collision/supersession helpers; no self-merge or history erasure.
- **operational probes** — no durable child-spawn role.
- **R&D specialists** — bounded ephemeral research children to depth 2, default `RESEARCH_CANDIDATE`.

## Same-family independence

Every delegated output retains `parent_agent_id`, `root_agent_id`, `delegation_path` and `independence_family`.

Descendants of one governed root do not become independent reviewers by using different prompts, models, tools or runtime IDs. Siblings of the same root do not satisfy separation-of-duties requirements against one another unless a higher governed policy explicitly recognizes distinct independence families. Children never count toward sovereign quorum.

## R&D specialist fabric

The R&D registry is `developers/manifests/agent-rnd-specialist-fabric.v1.json` and contains six permanent non-voting role identities:

- Legal / Regulatory
- IP / Rights / Licensing
- Finance / Tax / Treasury
- Blockchain / Cryptographic Protocol
- Accessibility / Consumer Protection
- Regional / Global Localization

Their default lifecycle state is `RESEARCH_CANDIDATE`. Their job is to research, model, challenge assumptions, discover requirements, propose architecture and create candidate work. They do not certify current institutional state.

### Research promotion

R&D growth is expected and is **not formal proof-coverage drift by count alone**. A research scope enters certification only after deliberate promotion or material contact with governed scope, including hard-exit impact, change to an existing governed disposition, canonical/production relevance or authoritative phase-entry evidence.

```text
RESEARCH_CANDIDATE
→ PROMOTION_PENDING
→ source reconciliation
→ independent proof
→ domain specialist
→ sovereign evidence/build/security/gate chain
→ CERTIFICATION_SCOPE
→ governed disposition
```

The reconciliation tags `CT:RND`, `CT:RESEARCH-CANDIDATE`, `CT:PROMOTION-PENDING` and `CT:CERTIFICATION-SCOPE` preserve this boundary.

## Tool credentials

Agents receive task-scoped capabilities, not standing universal credentials. Tool access is bound to actor/agent, role, run ID, platform/tenant, environment, scopes, expiration where supported, maximum actions/cost and approval state. Production secret values remain in approved secret management and are referenced rather than emitted.

## Work isolation

Parallel agents may work from the same source snapshot but must not concurrently mutate the same record/file without merge/lock strategy. Shared writes use optimistic concurrency, ETags/version preconditions or workflow locks.

## Quality gates

Every run selects applicable source authority, factual evidence, rights/provenance, legal-policy, privacy/security, cultural alignment, accessibility, SEO, API/schema, tests/build, commerce/entitlement, docs/changelog, provider/account/deployment separation, phase-gate, delegation/independence and rollback/continuity gates.

## Scheduler and probe discipline

Operational probes are cheap telemetry. Where possible, specialists consume recent sanitized probe outputs rather than duplicating the same provider read. Live schedules should avoid same-minute bursts where practical. A cadence change does not create a new agent identity or vote.

## Minimal-human-input target

Auto-approve only actions explicitly covered by policy. Humans receive concise exception packets stating decision, evidence, alternatives, risk, recommended action and consequence of delay.

## Observability

Track run success, latency, queue age, retries, cost, model/tool use, approval delay, failure class, rollback, correction rate, human intervention rate, child count/depth, child expiry, same-family independence violations, R&D promotion state and business outcome.

## Phase 3 implementation

Phase 3 can seed run, agent, child-lineage, role, tool, approval and event schemas only after the Phase 2.99 hard exit is genuinely satisfied. Phase 4 can activate federated work queues. Later phases can expand external builders and partners under CHLOM without changing the lower-level authority rules by implication.
