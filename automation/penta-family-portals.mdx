## Penta Family™ // Portals & System Guides

Penta Family uses one mandatory portal contract for every registered member. Portal existence and documentation are institutional requirements; **portal presence does not promote a member's maturity or grant execution authority.**

The canonical route pattern is:

```text
/penta/{machine_key_suffix}
```

Examples:

```text
penta.mail        → /penta/mail
penta.concierge   → /penta/concierge
penta.status      → /penta/status
penta.credentials → /penta/credentials
penta.compliance  → /penta/compliance
penta.identity    → /penta/identity
penta.procure     → /penta/procure
penta.quality     → /penta/quality
```

The dependency-free family runtime renders the machine portal payload:

```bash
python runtime/penta_family.py --root . --portal
python runtime/penta_family.py --root . --member penta.mail --portal
python runtime/penta_family.py --root . --member penta.compliance --portal
```

<Warning>
  A portal route is a contracted CrownThrive OS surface. `portal_state: contracted` is not proof that a public web frontend has been deployed at that URL. Production UI projection must preserve this backend contract and pass its own deployment/readback evidence.
</Warning>

## Mandatory portal sections

Every Penta member portal exposes the same institutional spine:

1. **Overview** — canonical identity, category and purpose.
2. **Status** — family state, member maturity, execution eligibility and portal state.
3. **Responsibilities** — human/operator surface and risk ceiling.
4. **Inputs & outputs** — dependencies and bounded output contract.
5. **Authority boundary** — what the system can and cannot authorize.
6. **Dependencies** — upstream/downstream registered systems and external authorities.
7. **SOPs & SLAs** — operating procedures, service obligations, TTLs and escalation rules.
8. **Runbooks** — normal operation, incident, rollback, recovery and continuity procedures.
9. **Guides** — operator, developer and governance usage guides aligned to current maturity.
10. **Evidence** — source catalog, maturity proof, receipts and readback requirements.
11. **API / MCP** — registered tools, adapters, APIs, MCPs and provider bindings only.
12. **Changelog** — material identity, maturity, provider, authority and behavior changes.
13. **Support** — accountable CrownThrive ownership and family escalation context.

The current production family composes **eight required catalogs**: core systems, PentaScribe/PentaMarketer, institutional services, operations/workforce, institutional controls, observability, readiness, and the bounded PentaImmune/PentaEVIBuilder maintenance-and-evidence extension. Members at `specified` or `implemented` maturity have portals and institutional identity but remain **non-executable through the family dispatch gate** until independently certified or promoted with evidence.

## Portal status semantics

Each portal displays **two separate states**:

- `family_status` — currently `production` for the Penta Family control plane;
- `member_maturity` — the individual system's evidence-backed state.

A portal for a `specified` system is therefore valid and useful while its execution gate remains closed. This separation is mandatory because institutional visibility must not be confused with execution authority.

## Provider, API and MCP rule

A system portal may list a provider, API, MCP, plugin, adapter, credential reference or tool only as one of these evidence-backed states:

```text
specified
implemented
certified
production
hold
retired
```

Provider capability never equals CrownThrive authority. Credential presence never equals permission. A successful historical call never equals current production eligibility.

## Guide lifecycle

Every Penta guide follows the same lifecycle:

**Discover** the current system/provider/evidence state → **Govern** authority, policy and audience → **Execute** only eligible capabilities → **Verify** via tests/readback → **Preserve** versions, receipts, decisions and institutional context.

When a member changes maturity, provider binding, API/MCP surface, SOP/SLA, authority boundary or responsibilities, its portal and guide are part of the required change impact.
