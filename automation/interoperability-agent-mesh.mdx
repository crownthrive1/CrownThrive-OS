# Interoperability Agent Mesh

The interoperability mesh is a non-sovereign execution layer beneath the existing CrownThrive governance constitution.

## Roles

### Interoperability Fabric Orchestrator

`ct.interop.agent-orchestrator`

Responsibilities:

- refresh the system and capability inventory;
- detect missing contracts, mappings and routes;
- prevent duplicate adapters;
- select collision-safe work;
- preserve exact provider/current/target distinctions;
- route work to bounded specialists;
- maintain append-only handoffs.

### Contract & Schema Steward

`ct.interop.agent-contract-steward`

Responsibilities:

- create stable public contracts;
- version schemas, events and identity envelopes;
- record input/output and data-class boundaries;
- generate public contract digests;
- classify protected implementation details;
- reconcile contract drift without overwriting prior versions.

### Adapter, Mapping & Route Builder

`ct.interop.agent-adapter-builder`

Responsibilities:

- propose schema and event mappings;
- create bounded adapter candidates;
- specify least-data policies;
- specify provider rate controls;
- specify idempotency and compensating rollback;
- prepare controlled-test route plans.

It does not inherit provider-write authority merely because a provider exposes a write endpoint.

### Independent Interoperability Certifier

`ct.interop.agent-certifier`

Responsibilities:

- verify exact contract versions;
- test schema and semantic compatibility;
- verify data minimization;
- test idempotency, replay and rollback behavior;
- verify authentication/capability boundaries;
- perform negative tests;
- issue or reject controlled-test certification receipts.

It cannot certify its own originating work and does not become a sovereign voter.

### Plugin Productization Steward

`ct.interop.agent-plugin-productizer`

Responsibilities:

- package certified capabilities into reusable plugin candidates;
- define support and license boundaries;
- route pricing research;
- maintain install/submission/readiness state;
- preserve protected-kernel separation;
- prepare future adapter-marketplace candidates.

It cannot activate checkout, create operative legal terms, submit a public listing or transfer protected source without separate authority.

## Lifecycle

The lifecycle is:

`inventory -> contract candidate -> mapping candidate -> route candidate -> controlled test -> independent certification -> read verified -> bounded write canary -> write verified -> product candidate`

A successful read does not prove write safety. A successful write canary does not grant generalized mutation authority. A plugin package does not prove installation, submission or customer entitlement.

## Scheduling

The internal schedule `ct.schedule.interoperability-fabric.hourly` runs at minute `:47` through the existing Vendor Engine Watch dispatcher. It creates no new external task slot.

Each cycle must:

1. refresh current systems and contracts;
2. identify missing or stale mappings;
3. select bounded collision-safe gaps;
4. require new evidence or an exact blocker;
5. route owner and different verifier;
6. update lifecycle state;
7. package reusable certified work;
8. suppress duplicate adapters and report no-op work separately.

## Authority boundaries

- A/B/C/D/S remain the sovereign voter pool.
- D3 remains human or qualified-professional reserved.
- Scores are evidence aids, not authority.
- Credentials remain in Vault and are consumed through opaque capabilities.
- Provider limits, billing and contractual restrictions remain authoritative.
- No agent may merge directly to main.
- No originator may self-certify.
- Nothing is silently deleted.
