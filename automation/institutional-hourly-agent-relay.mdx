# Institutional Hourly Agent Relay

## Purpose

The CrownThrive Phase 2.99 continuation program uses a **four-agent staggered hourly relay** so institutional work can progress every fifteen minutes without requiring any single scheduler to run more frequently than the platform-supported hourly cadence.

Each agent runs once per hour at a different minute offset and inherits the prior agent's repository-backed handoff. The agents do not communicate through hidden conversational memory. Their coordination substrate is the governed repository, PR/CI state, source/contradiction/validation registers, project-management comments, notifications and exact next-state records.

```text
:00  Agent A — Orchestrator & Integrator
  ↓
:15  Agent B — Evidence & Reconciliation Auditor
  ↓
:30  Agent C — Build & Documentation Executor
  ↓
:45  Agent D — Independent Gatekeeper & Handoff Steward
  ↓
next :00 → Agent A
```

## Stable roles

### Agent A — Orchestrator & Integrator

Responsibilities:

- inspect current `main`, open/recent PRs, CI and latest handoff;
- select the highest-priority safe packet;
- prevent duplicate ownership of an in-flight packet;
- execute or coordinate bounded work;
- propagate material changes into source/claim/conflict/registry/changelog/phase-gate records;
- leave an exact handoff for Agent B.

Agent A is the cycle lead, not an authority override. D2/D3 restrictions and hard gates still apply.

### Agent B — Evidence & Reconciliation Auditor

Responsibilities:

- independently audit Agent A's output;
- test source lineage and current/historical/research/proposed/unverified separation;
- detect hallucination, source promotion, count conflation, stale aliases, provider/deployment confusion and missing hard-gate evidence;
- repair deterministic low-risk defects or open governed deltas;
- advance a separate safe reconciliation slice when the prior packet is sound;
- hand an audited build packet to Agent C.

### Agent C — Build & Documentation Executor

Responsibilities:

- convert accepted evidence into articles, manifests, stable IDs, schemas, adapters, registries, validators and changelogs;
- work macro → corridor/platform → object/field → documentation/machine seed → tests;
- improve an existing owned PR rather than creating competing implementation work;
- validate/fix/revalidate and merge only within authority;
- hand the resulting packet to Agent D for independent verification.

### Agent D — Independent Gatekeeper & Handoff Steward

Responsibilities:

- independently inspect CI, branch/PR integrity, references, source-state controls, secret exposure, D0–D3 authority and downstream roadmap propagation;
- fix safe validation failures;
- block merges that violate source/gate/security rules;
- evaluate Phase 2.99 hard exit and Phase 3 hard entry every cycle without prematurely advancing;
- verify project-management comment/email obligations for material merged work;
- leave the authoritative closeout for the next Agent A cycle.

## Collision prevention

Before creating a branch or PR, every agent must inspect:

1. current `main` SHA;
2. open PRs;
3. branches associated with the same workstream/packet;
4. current CI state;
5. latest agent handoff/PM comment.

If another agent already owns the packet, the next agent audits, validates or assists that packet rather than opening a competing branch. Stale branches never define institutional truth.

## Source and phase rules

The relay inherits all institutional governance:

- Phase 2 / 2.99 remains current until its hard exit passes;
- Phase 3 cannot begin because time passed or an individual workstream succeeded;
- the ten-phase roadmap is fluid, but historical phase namespaces remain preserved;
- every material change re-evaluates dependent downstream phases;
- a source conflict opens a governed delta instead of being averaged into prose;
- unknown or inaccessible state remains explicit;
- `not_connected` never means `nonexistent`;
- provider capability never proves CrownThrive account entitlement/deployment;
- D2/D3 decisions never become self-approved through agent consensus.

## Notification contract

For each **material merged pass**:

- post one useful top-level GitHub PM comment on the relevant PR/tracking record;
- after final merge/validation, send Gmail `PASS SUCCESS` to `jones.usmc.kj@gmail.com` and `contact@crownthrive.com`;
- on a material blocker that genuinely requires human action, send `ACTION NEEDED` to both;
- do not generate success spam for no-op/audit-only cycles.

Until Collab Portal authentication/write certification passes, GitHub/Mintlify \+ Gmail remains the project-management fallback.

## Exact operating loop

```text
wake
→ inspect current truth
→ read previous agent handoff
→ reconcile
→ execute or audit one bounded packet
→ self-check
→ validate
→ fix/revalidate
→ merge if authorized
→ document/docs-impact
→ propagate future-phase consequences
→ notify when material
→ leave exact next state
→ next agent
```

The relay is designed to reduce human interaction, not eliminate human authority where evidence, law, rights, security or irreversible consequences require it.
