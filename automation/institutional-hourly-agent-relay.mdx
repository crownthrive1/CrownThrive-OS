# Institutional Hourly Agent Relay

## Purpose

The CrownThrive Phase 2.99 continuation program uses a **five-agent sovereign voter relay plus four scheduled non-voting specialist agents and embedded subagents**. The expanded execution chain increases coverage without increasing the sovereign voting denominator or creating authority from scheduler capacity.

Every scheduled role resolves current repository-backed state before acting. Agents and subagents do not rely on hidden conversational memory as institutional authority. Coordination uses governed repository state, PR/CI/security evidence, source/contradiction/validation registers, decision records, GitHub #98/#99/#100, Mintlify, live integration-control evidence and exact next-state handoffs.

```text
:00  Agent A — Orchestrator & Integrator                    [VOTER]
:05  Agent E — API/MCP Integration Specialist             [NON-VOTING]
:10  Agent F — Source & Articleization Specialist          [NON-VOTING]
:15  Agent B — Evidence & Reconciliation Auditor           [VOTER]
:20  Agent G — Domain, Engine & Vendor Certifier           [NON-VOTING]
:25  Agent H — Webhook & Provider-Delivery Certifier       [NON-VOTING]
:30  Agent C — Build & Documentation Executor              [VOTER]
:45  Agent D — Independent Gatekeeper & Handoff Steward    [VOTER]
:55  Agent S — Security & Resilience Sentinel              [VOTER]
next :00 → Agent A
```

The five-agent voter pool remains exactly `A/B/C/D/S` and establishes a **75% quorum** as `ceil(5 × 0.75) = 4` affirmative votes. E/F/G/H and every embedded subagent are advisory/execution specialists only. A missing voter vote or abstention is not an approval. Any registered `deny` or `block` prevents automatic merge. Agent D approval is independently mandatory for an automatic merge. D3 authority remains human/reserved and cannot be manufactured by quorum, specialist count or subagent count.

## Stable roles

### Agent A — Orchestrator & Integrator

Responsibilities:

- inspect current `main`, open/recent PRs, CI/security state and latest handoff;
- select the highest-priority safe packet;
- prevent duplicate ownership of an in-flight packet;
- execute or coordinate bounded work;
- propagate material changes into source/claim/conflict/registry/changelog/phase-gate records;
- score the packet using the governed risk model;
- leave an exact handoff for Agent B.

Agent A is the cycle lead, not an authority override.

### Agent B — Evidence & Reconciliation Auditor

Responsibilities:

- independently audit Agent A's output;
- test source lineage and current/historical/research/proposed/unverified separation;
- detect hallucination, source promotion, count conflation, stale aliases, provider/deployment confusion and missing hard-gate evidence;
- repair deterministic low-risk defects or open governed deltas;
- advance a separate safe reconciliation slice when the prior packet is sound;
- cast an evidence-backed vote and hand an audited build packet to Agent C.

### Agent C — Build & Documentation Executor

Responsibilities:

- convert accepted evidence into articles, manifests, stable IDs, schemas, adapters, registries, validators and changelogs;
- work macro → corridor/platform → object/field → documentation/machine seed → tests;
- improve an existing owned PR rather than creating competing implementation work;
- validate/fix/revalidate within authority;
- never self-approve a material originating D2/D3 change;
- cast a bounded implementation vote and hand the packet to Agent D.

### Agent D — Independent Gatekeeper & Handoff Steward

Responsibilities:

- independently inspect CI, branch/PR integrity, references, source-state controls, secret exposure, D0–D3 authority and downstream roadmap propagation;
- verify that quorum, risk score, applicable specialist endorsements and rollback/recovery evidence are complete;
- independently approve or block automatic merge;
- fix safe validation failures without weakening a control;
- evaluate Phase 2.99 hard exit and Phase 3 hard entry every cycle without prematurely advancing;
- verify project-management comment/Gmail obligations for material merged work;
- leave the authoritative closeout for Agent S and the next Agent A cycle.

Agent D is a required independent gate. Four approvals that omit Agent D do not authorize automatic merge.

### Agent S — Security & Resilience Sentinel

Responsibilities:

- inspect the changed attack surface, authentication/authorization, secrets, dependencies, workflows, APIs, cryptographic or blockchain surfaces, supply-chain exposure and rollback posture;
- ingest applicable GitHub CodeQL, dependency review and secret-scanning evidence without treating GitHub as the sovereign decision-maker;
- classify security findings and invoke only authority-appropriate self-healing;
- require critical/high findings to block automatic merge until repaired, revalidated or escalated;
- independently rerun or verify the original failed security control after a repair;
- activate legal/regulatory review for crypto/token, privacy, sanctions, KYC/AML, securities, rights or contract implications;
- prevent experimental CHLOM, AI/ML/LLM or blockchain research from inheriting production authority;
- cast the security/resilience vote and hand the cycle back to Agent A.

Agent S may autonomously repair only deterministic low-risk controls. Credential rotation, privileged access, destructive production changes, legal/security exceptions and other D3 actions remain reserved.

## Scheduled non-voting specialist agents

The specialist schedule is execution capacity, **not a second quorum**.

### Agent E — API/MCP Integration Specialist

- owns registered read-only API/MCP conformance, endpoint-path reconciliation, sanitized request-budget/credential-continuity evidence and THIVEBASE integration health;
- may prepare disabled future adapters and staging contracts;
- cannot enable provider writes, broaden scopes, rotate credentials, vote or promote an integration from `UNKNOWN`/`documented` to verified without runtime evidence.

### Agent F — Source & Articleization Specialist

- owns CT-P299-GATE-002 execution support and source/articleization portions of GATE-003;
- reconciles recovered titles/bodies, stable article IDs, disposition, exposure/risk/owner, canonical routes/navigation and P0/P1 body or explicit unresolved-source closure;
- cannot fabricate missing source bodies, publish restricted evidence or vote.

### Agent G — Domain, Engine & Vendor Certifier

- owns current-state evidence for CT-P299-GATE-001 and vendor/domain portions of GATE-003;
- verifies registrar/DNS/TLS/runtime, provider/account/license/support/API/export and installed-versus-target version evidence;
- cannot purchase/renew, accept vendor terms, perform production upgrades, overwrite historical purchase cost or vote.

### Agent H — Webhook & Provider-Delivery Certifier

- owns CT-P299-GATE-006 execution support and external-delivery portions of GATE-003;
- verifies sender authenticity, delivery/retry/replay/idempotency, bounded-body handling, fallback/readback and endpoint retirement across Collab Portal and other P0 webhook lanes;
- synthetic tests may validate receiver mechanics but cannot substitute for a real provider-delivery proof; H cannot vote.

## Embedded subagents

Scheduler capacity does not cap institutional specialization. Additional roles run **inside the scheduled agents as registered, non-voting subagents**:

- **Agent I — `ct.subagent.continuity-recovery`**: CT-P299-GATE-007 and continuity/recovery portions of GATE-003/GATE-008; verifies restricted-source boundaries, off-provider exports, backup/restore, credential-reference continuity, vendor/domain exit and reproducible recovery. It cannot retrieve/publish restricted bodies merely to prove existence or perform destructive recovery without authority.
- **Agent J — `ct.subagent.phase3-snapshot-packet`**: CT-P299-GATE-008 preparation; assembles the exact current commit/schema/infrastructure/source snapshot, unresolved/deferral state and Phase 3 entry packet. It is fail-closed whenever any inherited hard gate remains unmet and cannot itself open Phase 3.
- **Agent K — `ct.subagent.roadmap-transition`**: ten-phase dependency and downstream-impact reconciler; updates affected Phase 3–10 objectives, gates, tests, risks, rollback and handoffs after material changes. It cannot waive, rename away or mark a phase/gate passed.

The previously registered operational helpers remain available: `ct.subagent.integration-heartbeat`, `ct.subagent.credential-continuity` and `ct.subagent.vendor-engine-watch`. All embedded subagents are non-voting, receive task-scoped authority only and must return evidence to a scheduled agent for independent audit/gating.

## Sovereign merge authority

**GitHub is not the sovereign merge authority.** GitHub provides repository transport, CI execution, CodeQL/dependency/security evidence, audit history and post-merge defense-in-depth. CrownThrive's coded agent policy is the fail-closed institutional gate.

For an automatic D0–D2-eligible merge, all applicable requirements must pass:

1. current `main` and collision state reconciled;
2. institutional documentation validation passed;
3. Security Governance validation passed;
4. applicable provider security scans passed or are explicitly documented `not_applicable`;
5. no secret/restricted-data exposure;
6. risk score is at least `85/100`;
7. required specialist endorsements are present;
8. four of five eligible agents approve;
9. Agent D approves;
10. no agent casts `deny` or `block`;
11. authority class permits agent execution;
12. rollback/recovery exists;
13. documentation impact and downstream Phase 3–10 reconciliation are complete.

GitHub ruleset-based protection is now enabled and behaviorally verified as additional defense-in-depth. It remains non-sovereign: the provider perimeter cannot replace the CrownThrive agent/quorum/authority model, and the agent model cannot waive the required provider perimeter without an authorized D3 break-glass record.

## Collision prevention

Before creating a branch or PR, every agent must inspect current `main` SHA, open PRs, same-workstream branches, CI/security state and the latest handoff/PM comment. If another agent already owns the packet, the next agent audits, validates or assists rather than opening a competing branch. Stale branches never define institutional truth.

## Source and phase rules

The relay inherits all institutional governance:

- Phase 2 / 2.99 remains current until its hard exit passes;
- Phase 3 cannot begin because time passed or an individual workstream succeeded;
- the canonical roadmap is the Ten-Phase Institutional Program Charter;
- every material change re-evaluates dependent Phases 3–10;
- a source conflict opens a governed delta instead of being averaged into prose;
- unknown or inaccessible state remains explicit;
- `not_connected` never means `nonexistent`;
- provider capability never proves CrownThrive account entitlement/deployment;
- D2/D3 decisions never become self-approved through agent consensus;
- a crypto/token/blockchain concept remains research/target architecture until its phase, legal, security, tax, sanctions, custody and operational gates pass.

## THIVEBASE Monthly Heartbeat and delegated integration privileges

The hourly relay is complemented by a separate **THIVEBASE Monthly Heartbeat** on the first local calendar day of each month. The monthly cycle is ecosystem-wide rather than a replacement for justified higher-frequency availability probes. It must call `public.thivebase_health_snapshot()` first, verify the CrownThrive Supabase project remains `ACTIVE_HEALTHY`, then inspect cron failures, Security/Performance Advisor state, request-budget semantics, credential continuity, integration-control gates and registered P0 API/MCP/provider health through read-only certified paths.

The machine overlay is `developers/manifests/thivebase-operational-automation.v1.json`. It records the complete expanded execution topology without changing the A/B/C/D/S denominator:

- scheduled non-voting specialists: Agent E API/MCP, Agent F source/articleization, Agent G domain/engine/vendor and Agent H webhook/provider-delivery;
- existing embedded helpers: `ct.subagent.integration-heartbeat`, `ct.subagent.credential-continuity`, `ct.subagent.vendor-engine-watch`;
- additional embedded specialists created when scheduler capacity is constrained: Agent I `ct.subagent.continuity-recovery`, Agent J `ct.subagent.phase3-snapshot-packet` and Agent K `ct.subagent.roadmap-transition`.

Agent A dispatches/reconciles and invokes I/J/K when their gate scope is active; B audits evidence/version/phase state; C turns accepted specialist evidence into scripts/manifests/docs/tests; D independently prevents false pass or phase promotion; S owns security/resilience review. E/F/G/H and every embedded subagent remain non-voting. None of these privileges authorizes provider writes, credential rotation, production upgrades, purchases/terms acceptance, rights/money/legal decisions, hard-gate waiver or `UNKNOWN → PASS` without evidence.

The software-engine default is the latest provider-published release as the **target/reference version**, never as proof of the installed version. CodeCanyon/marketplace prices remain channel-specific current evidence and cannot overwrite historical CrownThrive purchase cost. Reward Loyalty remains `v4` in production and `v5.27.0` as the vendor target until staging and production evidence explicitly changes that state.

## Notification contract

For each **material merged pass**:

- post one useful top-level GitHub PM comment on the relevant PR/tracking record;
- send Gmail `PASS SUCCESS` after authoritative merge/validation;
- send `ACTION NEEDED` only for a material blocker requiring human action;
- do not generate success spam for no-op/audit-only cycles;
- never include secrets, private evidence bodies or restricted operational values.

Until Collab Portal is fully operationally certified, Gmail resolves three private runtime recipient references: founder tracking, institutional tracking and the **Collab Portal fallback tracking mailbox**. The public repository deliberately stores only those logical references—not the private routing address.

The Collab Portal fallback tracking mailbox is disabled only when all seven certification predicates pass simultaneously: exact credential match, authenticated project metadata, pinned institutional project UID, approved field mapping, authenticated project read, bounded write/read-back, and webhook sender/delivery integrity. Any later regression in those controls reactivates the fallback automatically. Founder and institutional Gmail tracking remain active after Collab fallback retirement.
