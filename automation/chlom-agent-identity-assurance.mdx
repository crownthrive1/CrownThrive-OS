# CHLOM agent identity assurance

CrownThrive agents, subagents and framework transport identities are bound to a machine identity record in THIVEBASE/Supabase. The control exists to prove **which governed identity acted from which repository revision and whether that identity is currently alive** without exposing private CHLOM Fingerprint material.

## Public/private rule

The recovered CHLOM identity doctrine is explicit:

- the public-facing DID may be public;
- the CHLOM Fingerprint ID remains private;
- keys, salts, private telemetry, credential material and private Fingerprint commitments are not documentation fields;
- public verification uses safe identifiers and cryptographic digests instead.

A public page, manifest or API that exposes the private Fingerprint ID fails governance review.

## Public verification record

The public-safe identity directory is machine-readable at:

`https://tzajnzshmtzjenqulehq.supabase.co/functions/v1/public-agent-identity-directory`

Each record may expose:

- agent UUID;
- stable `repo_id` and `agent_id`;
- framework ID when applicable;
- public DID and DID state;
- immutable GitHub repository ID after physical provisioning;
- repository full name;
- exact current authoritative Git SHA when available;
- latest authoritative heartbeat time and TTL;
- heartbeat freshness;
- SHA-256 public identity digest;
- assurance/governance state;
- public authority ceiling and non-voting/voting classification already allowed by governance.

The directory deliberately excludes private Fingerprint record UUIDs, salts, Fingerprint commitments, verification keys, credentials and secrets.

## Runtime auto-assignment

The identity layer is not manually maintained. Supabase now binds:

`repository_agent_bindings → CHLOM agent identity → DID binding → repository identity/SHA → heartbeat → SHA-256 public digest`

New governed agent bindings automatically receive an agent UUID, candidate CHLOM DID, private Fingerprint record and public digest. Repository registration and authoritative heartbeat changes automatically refresh repository ID, SHA, heartbeat and digest state.

The current `did:chlom:*` method is an **internal candidate method**, not a claim that an externally resolvable W3C DID method has already been deployed. External resolution must remain `UNKNOWN` until an accepted resolver/provider implementation is proved.

## Framework child behavior

A planned child repository receives identity records before physical provisioning, but its repository ID, child SHA and heartbeat remain empty. That state is `prospective_unprovisioned` and cannot be called operational.

After GitHub proves a physical repository through OIDC bootstrap, the immutable GitHub repository ID and observed SHA may populate. Operational heartbeat remains blocked until parent certification and the existing sequential framework gate are satisfied.

The ordered sequence remains:

Repository identity, DID assignment, CI, heartbeat and Fingerprint registration create **no sovereign vote**. Agent D remains the parent certifier and D3 remains human-reserved.

## Documentation hard gate

`Documentation Governance` must execute `scripts/chlom_identity_assurance.py`.

The review fails when any of these conditions occurs:

- public DID/UUID/digest fields are missing;
- an active parent agent lacks repository ID, exact SHA or heartbeat evidence;
- a planned child claims a physical repository or operational state without provider proof;
- a physical child repository ID conflicts with the Framework Factory manifest;
- a framework transport identity becomes vote-eligible by identity assignment;
- a Fingerprint identifier, Fingerprint commitment, key reference, credential or secret leaks into the public directory;
- the public/private identity contract is weakened.

On the default branch, the scheduled `CHLOM Agent Identity Assurance` workflow emits an OIDC-bound heartbeat at minute `:47` each hour and then requires fresh heartbeat evidence. Pull-request review validates identity completeness and privacy boundaries without fabricating a default-branch heartbeat.

## Cryptographic boundary

A SHA-256 public identity digest is an **integrity fingerprint of public-safe identity state**, not the private CHLOM Fingerprint ID and not a digital signature. Signature/verifiable-credential claims require separately proved key custody and verification evidence.

## Rollback and recovery

The database migration is additive. A code rollback can revert the workflow, validator and documentation packet without deleting identity evidence. Any destructive identity-data rollback requires separate governed authorization.

If heartbeat or repository state drifts, preserve the last known evidence, mark the identity stale or pending, and repair through OIDC/readback. Never manufacture a heartbeat, SHA, repository ID, DID resolution claim or Fingerprint proof.
