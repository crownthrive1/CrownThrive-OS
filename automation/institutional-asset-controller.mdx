# Institutional Asset Controller

**Controller:** `ct.asset.agent-controller`  
**Maximum authority:** A2 / D2  
**Sovereign-vote effect:** none  
**Schedule:** internal hourly subroute at minute `:23`  
**External scheduler slots added:** zero

The Institutional Asset Controller coordinates CrownThrive's reusable asset estate without becoming a sovereign voter, a generic secret broker or an unrestricted code-execution service.

## Controller mesh

| Agent | Primary responsibility |
| --- | --- |
| `ct.asset.agent-controller` | whole-estate inventory, priority, collision control, handoff and cycle governance |
| `ct.asset.agent-cataloger` | stable IDs, classification, fingerprints, metadata and version reconciliation |
| `ct.asset.agent-compiler` | deterministic blueprint, scaffold, manifest and package plans |
| `ct.asset.agent-dependency-resolver` | exact plugin, pallet, kernel, contract, data and evidence dependencies |
| `ct.asset.agent-execution-governor` | runtime class, allowlisted entrypoint, idempotency, rollback and readback plans |
| `ct.asset.agent-custody-provenance` | source lineage, Vault custody, public/private boundary and archives |
| `ct.asset.agent-security-verifier` | secret, authority, privacy, replay, dependency and negative testing |
| `ct.asset.agent-lifecycle-continuity` | version history, supersession, deprecation, archive and recovery |
| `ct.asset.agent-commercialization` | non-live product, license, pricing, support and marketplace candidates |
| `ct.asset.agent-independent-certifier` | independent asset, package, dependency, execution-plan and bundle certification |

Every material asset has an owner and a different verifier. Controller identities do not inherit the voting rights of their parent agents.

## Asset lifecycle

The enforced lifecycle is:

`inventory -> classification -> stable identity -> blueprint -> dependency resolution -> compile plan -> source materialization -> tests -> independent certification -> controlled package -> promotion or supersession`

A later stage cannot be inferred from an earlier one:

- a blueprint is not source code;
- source code is not a verified executable;
- a package is not installation;
- installation is not public submission;
- submission is not publication;
- technical certification is not rights, pricing, tax or D3 approval.

## Controller cycle

The database runtime `asset_fabric.run_controller_cycle` performs a bounded controller cycle. Each cycle:

1. freezes a cycle ID;
2. scans the curated asset estate;
3. detects secret, authority, dependency, test, version, execution, collision and commercialization gaps;
4. records append-only findings;
5. assigns bounded specialist work;
6. writes per-agent work receipts;
7. updates first-class health state;
8. appends a DAIL checkpoint;
9. returns counts and blockers without exposing protected material.

The cycle never executes generated scripts, installs plugins, submits apps, changes a provider, moves money or enables checkout.

## Scrutiny classes

### Secret and custody scrutiny

The custody agent and security verifier check for credential-shaped manifest content and public/private boundary violations. Findings report labels and references, never matched secret values.

### Authority scrutiny

The controller rejects:

- D3 automation;
- originator self-verification;
- provider-write inheritance;
- arbitrary native-binary execution;
- direct-main merge authority;
- sovereign-vote inheritance;
- hidden checkout or entitlement activation.

### Dependency scrutiny

Dependencies use stable asset IDs and exact versions. A dependency record can cover:

- runtime;
- public contract;
- kernel;
- pallet;
- plugin;
- data;
- identity;
- evidence;
- security;
- licensing.

An unresolved dependency keeps the asset on HOLD.

### Execution scrutiny

Executable-class assets require a signed execution plan with:

- source-controlled entrypoint;
- source digest;
- allowlisted runtime;
- bounded filesystem and network policy;
- timeout;
- idempotency;
- rollback;
- readback;
- owner/verifier separation.

Opaque executable binaries are not generated by the factory. A future native binary must pass reproducible-build, signing, malware, provenance and rollback gates.

### Lifecycle scrutiny

All records use append-or-supersede history. The lifecycle agent preserves:

- predecessor versions;
- failed tests;
- prior package manifests;
- old runtime and submission packets;
- custody and evidence receipts;
- explicit supersession relationships.

## Blueprint factory

The deterministic blueprint matrix currently combines:

- 40 CrownThrive domains;
- 20 asset archetypes;
- five deployment profiles.

This produces 4,000 candidate blueprints. The controller may generate or reconcile records through `assets.generation.run`. It does not materialize 4,000 files or represent them as certified production assets.

The script, workflow, skill, prompt, test and runbook records are controlled specifications until their referenced source is materialized and independently tested.

## Promotion rules

An asset may reach `verified` only when:

- exact identity and version are frozen;
- required dependencies are satisfied;
- the current version has append-only custody;
- required tests have independent PASS receipts;
- executable assets have a verified execution plan;
- Asset Readiness Score is at least the protected threshold;
- Asset Risk Score is within the protected maximum;
- no unexpected activation state exists.

Promotion to `live` remains separately governed and may require provider, rights, counsel, tax, fulfillment, payment, support and sovereign acceptance.

## Commercialization boundary

The commercialization agent may build candidate bundles, scopes and unit-economics models. It cannot:

- set a live price;
- invent MSRP or discounts;
- create Stripe objects;
- activate checkout;
- create an entitlement;
- grant redistribution rights;
- transfer protected kernels;
- authorize seller payouts.

## Continuity rule

The Controller exists to make CrownThrive assets reusable, inspectable, versioned and durable. It does not trade evidence quality for asset volume. Large candidate matrices are valuable only when every materialized asset remains traceable to an exact blueprint, source, dependency graph, test set, verifier and version record.
