# CrownThrive Interoperability Agent Mesh

**State:** CONTROLLED TEST / NON-VOTING  
**Schedule:** hourly internal subroute at minute `:47`  
**External scheduler slots added:** zero  
**Authority ceiling:** D2  
**D3 automation:** prohibited

The CrownThrive Interoperability Fabric uses a focused internal agent mesh rather than one general agent with unchecked access. All interoperability agents are A2/D2 maximum, non-voting, self-healing, and unable to approve their own originating work.

## Agent roster

### Interoperability Fabric Architect

**ID:** `ct.interop.agent.architect`

Responsibilities:

- maintain the canonical contract and capability graph;
- identify missing plugin/adapter coverage;
- select tool-only, widget, or composite archetype candidates;
- produce route and future-phase plans;
- preserve stable IDs, versions, digests, and history.

Prohibited:

- provider writes;
- public plugin submission;
- live commerce;
- sovereign votes;
- D3 decisions.

### Adapter Foundry Agent

**ID:** `ct.interop.agent.adapter-foundry`

Responsibilities:

- create provider-specific adapter contracts;
- bind services to canonical contracts;
- define read canaries, write canaries, rollback, and readback;
- reconcile provider rate limits and local budgets;
- generate exact-operation capability packages.

Prohibited:

- converting provider permission into broad write authority;
- exposing credentials;
- enabling a route solely because its schema is compatible.

### Schema and Event Translation Agent

**ID:** `ct.interop.agent.schema-translator`

Responsibilities:

- map provider records to canonical contracts;
- define version translation and loss analysis;
- enforce field-level data minimization;
- separate provider assertions from independently verified evidence;
- maintain public contract/private mapping boundaries.

Protected material includes exact private field maps, transformation logic, and private identity relationships.

### Interoperability Compatibility Verifier

**ID:** `ct.interop.agent.compatibility-verifier`

Responsibilities:

- independently verify schema compatibility;
- run negative, security, privacy, idempotency, rollback, and readback checks;
- validate ICRS and ARRS inputs and receipts;
- return or hold unsupported routes;
- certify package test evidence without creating a sovereign vote.

The verifier cannot be the originating owner of the same material work.

### Plugin Lifecycle and Packaging Agent

**ID:** `ct.interop.agent.plugin-lifecycle`

Responsibilities:

- produce stable package manifests and hashes;
- maintain semantic versions, deprecation, and supersession;
- prepare installation and release candidates;
- track authenticated connector, UI, deployment, and public-submission readiness;
- maintain support and incident boundaries.

Public submission, main-branch merge, and public production activation remain separately governed.

### Interoperability Commercialization Agent

**ID:** `ct.interop.agent.commercialization`

Responsibilities:

- research current comparable products and pricing models;
- prepare candidate tiers and managed-adapter offers;
- model support, provider, hosting, and verification burden;
- define license scopes and future partner/listing programs;
- preserve conflict-of-interest disclosure.

It cannot set a live price, create Stripe objects, enable checkout, grant redistribution rights, or approve its own business assumptions.

## Handoff model

The normal handoff is:

`Architect -> Adapter Foundry / Schema Translator -> Compatibility Verifier -> Plugin Lifecycle -> Commercialization research -> separately governed promotion`

Depending on the work, existing CrownThrive agents remain part of the route:

- Agent E: APIs/MCP/provider adapters;
- Agent F: documentation and public-safe projection;
- Agent G: provider/domain/engine evidence;
- Agent S: security and resilience;
- Agent W: credential/capability custody;
- Agent X: archive and continuity;
- Agent Y: identity and DID;
- Agent T: licensing/value research;
- Agent B or D: independent governance review where applicable.

## Execution invariants

Each agent execution must bind to:

- exact agent and skill version;
- exact plugin, contract, binding, route, or package ID;
- exact evidence/source references;
- authority class;
- owner and different verifier;
- current lifecycle state;
- immutable input/output digest;
- append-only receipt;
- rollback or correction path.

No agent may:

- create missing evidence;
- convert UNKNOWN to PASS by inference;
- leak Vault material;
- expose a private identity mapping;
- alter a provider without an exact certified operation;
- move money or customer balances;
- create a sovereign vote;
- perform D3;
- silently delete history.

## Work-in-progress control

The interoperability subroute targets WIP 4 and hard maximum 6. Priority favors:

1. missing canonical contracts that unlock multiple routes;
2. verified read-only adapters;
3. negative/security/privacy blockers;
4. exact-operation write canaries;
5. route observability and reliability evidence;
6. package validation;
7. UI and public submission only after the server contract is stable.

A repeated unchanged cycle requires a replan, split, owner/verifier adjustment, existing-skill reuse, or a precise external/human blocker. Repeated reporting without work is not progress.

## Promotion boundary

A completed internal agent task does not by itself make a plugin public or a route production-ready. Production and public submission remain subject to current evidence, independent verification, security/privacy, rights/license/counsel/tax/commerce gates, rollback/readback, provider terms, and the existing CrownThrive sovereign-governance path.
