# Agent version archive and continuity

CrownThrive preserves agent history as institutional evidence. A current definition is only the latest effective state; prior versions remain queryable, attributable and recoverable.

## Versioned objects

Each agent family may have independent versions for:

- institutional role definition;
- prompt/instruction implementation;
- machine manifest record;
- scheduler configuration;
- tool/adaptor bindings;
- evaluation suite;
- authority policy reference;
- run-packet/handoff schema;
- documentation projection.

Those versions should not be collapsed into one number when their change cadence differs.

## Archive rule

A version is archived when superseded, suspended or retired. Archive means **non-current, preserved and attributable**; it does not mean deleted.

Minimum archived record:

```yaml
agent_id: ct.specialist.example
version: 1.2.0
status: SUPERSEDED
effective_from: null
effective_to: null
superseded_by: 1.3.0
source_commit: null
prompt_source_ref: null
manifest_ref: null
evaluation_receipt_refs: []
change_reason: null
authority_changed: false
migration_required: false
rollback_supported: true
```

## Historical versus current truth

Historical instructions remain valid evidence of what the agent was permitted or expected to do at that time. They do not automatically authorize current execution.

```text
historical version
  ├─ remains immutable evidence
  ├─ may explain an old action or output
  └─ cannot override current effective policy

current version
  ├─ must resolve against current standards and phase state
  └─ governs new runs after its effective date
```

## Change classification

- **Patch:** wording, deterministic implementation repair, extra test or source reference with no authority/mission expansion.
- **Minor:** new bounded capability, new specialist/subagent, new evidence field or workflow integration within existing authority.
- **Major:** changed authority ceiling, sovereign-vote topology, phase-transition logic, protected-data scope, destructive/write capability or incompatible run-packet contract.

A version number never replaces the underlying D0–D3 classification.

## Schedule continuity

Scheduler records are implementation evidence. If scheduler capacity is unavailable, a registered role may move from scheduled to embedded execution without losing stable identity. That transition must record:

- prior schedule/cadence;
- new parent roles;
- reason for embedding;
- unchanged or reduced authority;
- handoff changes;
- affected tests and documentation.

This is the model used for Agents I, J and K: institutional roles are preserved as embedded subagents rather than dropped because scheduler slots are finite.

## Prompt and model continuity

Agent identity is provider-independent. Replacing a model/provider requires regression evaluation against the same role definition, stop conditions, authority ceiling and negative tests. A model upgrade cannot silently expand permissions.

## Recovery package

The minimum agent-continuity recovery package contains:

1. current topology manifest;
2. current and prior role definitions;
3. source templates and scaffold script;
4. prompt/instruction versions or governed references;
5. scheduler/export snapshot where available;
6. evaluation fixtures and latest pass/fail receipts;
7. associated standards and ADRs;
8. Git commit/release references;
9. current phase/gate dependencies;
10. off-provider export/restore evidence.

## Changelog consolidation

Agent-factory changes are summarized in the main Phase 2.99 changelog/control center and link to focused agent-factory patch notes when detail is material. Routine patch-level prompt or schedule updates are grouped under their parent agent/factory category rather than creating a new top-level changelog page for every small revision.

Major changes include:

- voter-pool changes;
- new authority class or production-write capability;
- new protected-data access;
- new externally licensable agent/pallet family;
- incompatible definition schema;
- phase-entry/exit logic change;
- provider/model migration with changed safety or tool semantics.

## Preservation standard

Never archive by deleting the only copy. Git history, accepted release references, exported manifests and Mintlify changelog/source lineage together form the recovery chain. Restricted prompts/fixtures remain outside public docs and are referenced by stable ID/checksum only.
