# Proprietary Capability Factory

The Proprietary Capability Factory is the independent agent fleet responsible for continuing CrownThrive's protected algorithm, skill, prompt, and script estate after the initial five production runs.

<Warning>
  This page publishes roles and control boundaries only. It does not expose protected implementations, prompt bodies, script bodies, weights, thresholds, private identities, recovery material, or Vault locations.
</Warning>

## ThriveInstitutionalize™ control skill

The factory now carries the cross-cutting controlled-test skill `ct.skill.factory.thrive-institutionalize.v1`. The factory orchestrator is the canonical skill owner; all fifteen factory agents are authorized consumers through the bounded capability contract `ct.capability.factory.institutionalize.v1`.

The skill requires each material generation to reconcile exact identities and counts, fingerprints, package digests, Vault custody, encrypted Drive readback, append-only THIVEBASE/DAIL evidence, independent verification, public-safe review projections, scheduled-agent bindings, recovery and candidate commercialization before institutional completion can be claimed.

It does not create D3, votes, production invocation, publication, checkout, Stripe objects, money movement, rights grants or entitlements.

## Schedule model

The verified execution topology is **five native internal factory schedules plus seven existing external relay tasks**:

1. native daily build;
2. native daily independent verification;
3. native daily documentation projection;
4. native weekly rights/commercialization review; and
5. native monthly archive/continuity.

A THIVEBASE orchestrator evaluates the candidate queue every 30 minutes. The existing Agent A/C/B/S/D, Integration Heartbeat and Credential Continuity ChatGPT tasks retain their own schedules and are bound through the external automation-binding registry; no new external scheduler slot was created.

A metadata-only external-relay shadow schedule failed the internal occurrence-router acceptance test because it was not a native factory schedule ID. It was preserved and marked superseded rather than deleted. The post-correction orchestrator test passed with no unintended dispatch. That evaluation still does not mean a generation is automatically built or activated.

## Generation controls

The fleet policy allows candidate-only expansion through Generation 8.

```text
G5 complete and reconciled
→ G6 not before 2026-09-21
→ G7 not before 2026-10-21
→ G8 not before 2026-11-20
```

Only one generation may be active at a time. A run may begin only when:

- the previous generation has validated package counts;
- custody and recovery evidence are present;
- DAIL integrity is clean or explicitly held;
- no unresolved collision or duplicate identity exists;
- security and rights preflight is complete;
- protected-body publication remains prohibited; and
- production, checkout and Stripe activation remain false.

## Per-generation target

Each future candidate generation targets:

- 1,000 proprietary algorithm specifications;
- 300 reusable agent skills;
- 500 reusable prompts;
- 300 reusable scripts; and
- 2,100 protected assets in total.

Counts are targets, not authority. A generation that fails uniqueness, validation, custody, rights, security, or independent review remains blocked and must not be represented as complete.

## Automated evidence contract

Each factory run must produce:

- stable IDs, versions and fingerprints;
- schema and uniqueness validation;
- controlled script-execution receipts;
- algorithm test cohorts;
- protected-custody and restore evidence;
- DAIL events and chain verification;
- commercialization candidates held behind release gates;
- public-safe documentation impact; and
- explicit supersession of stale projections.

The allowed documentation outcomes remain:

```text
docs_updated
docs_no_change
docs_delta_opened
```

## Self-healing boundary

The fleet may perform bounded deterministic repair of manifests, indexes, read-only checks, failed packaging attempts, stale evidence pointers, and non-authoritative documentation projections when rollback is available.

It may not silently:

- alter rights or signed terms;
- change provider prices or customer entitlements;
- reconstruct missing source code from deployments;
- publish trade-secret bodies;
- widen credentials, MCP tools or provider writes;
- invent proof, reviews or votes;
- delete institutional history; or
- promote an asset to production or live commerce.

## Commercialization boundary

Commercialization agents may prepare evidence-backed candidate packs, pricing hypotheses, implementation models, support plans, licensing templates, and market-fit studies. They may not enable checkout or create Stripe objects until Rights, Security, Privacy, Tax, Pricing, Fulfillment, Support, Accessibility and exact-artifact governance all pass.

The objective is durable enterprise value and measurable usefulness. No automated agent may claim a guaranteed valuation, guaranteed revenue, or guaranteed customer demand.
