# Proprietary Capability Factory

The Proprietary Capability Factory is CrownThrive's governed system for turning completed work into durable institutional capability. Its core contract is no longer simply “generate more assets.” The architecture is required to know how to:

**Create → Test → Identify → Secure → Preserve → Document → Reuse → Productize → Monitor → Continue**

and then repeat that loop for the next candidate generation without increasing its own authority.

<Warning>
  Perpetual means perpetual candidate/institutional continuation, not unlimited authority. D3 remains human-reserved. Production activation, protected-body publication, final rights/entitlements, checkout, Stripe, money/Crown Credits movement, and automatic canonical merge remain outside this lifecycle.
</Warning>

## Ten-stage institutional lifecycle

| Stage | Institutional purpose | Fail-closed requirement |
| --- | --- | --- |
| Create | Produce the exact governed candidate capability/package. | Exact scope, deterministic identity, rollback-aware build and public/private separation. |
| Test | Prove behavior and failure boundaries. | Deterministic, negative-authorization, runtime/syntax, failure-injection and independent testing. |
| Identify | Make the capability uniquely resolvable. | Canonical ID, version, SHA-256, fingerprint, provenance, package membership and DAIL/DID linkage. |
| Secure | Contain secrets, IP, privacy and authority. | Least privilege, Vault custody, no raw-key return, adversarial review, RLS/access controls and authority ceiling. |
| Preserve | Make the accepted state recoverable. | Encrypted custody, exact Drive cryptographic readback, append-only THIVEBASE, DAIL and rollback/recovery evidence. |
| Document | Make the safe contract understandable. | Public-safe interface/evidence only; protected bodies and secrets remain excluded. |
| Reuse | Convert one-off work into institutional capability. | Dependency, callable capability, agent, interoperability and reuse bindings. |
| Productize | Convert reusable capability into commercial candidates. | Candidate packages and pricing hypotheses only; rights/release/checkout gates stay closed. |
| Monitor | Detect drift and regressions continuously. | Cron, agents, bindings, DAIL, custody, security, health and no-production/no-commerce boundaries remain verified. |
| Continue | Route the next candidate generation. | All ten-stage evidence current; no authority expansion; one due/executing generation maximum. |

The closed loop is:

```text
CREATE
  ↓
TEST
  ↓
IDENTIFY
  ↓
SECURE
  ↓
PRESERVE
  ↓
DOCUMENT
  ↓
REUSE
  ↓
PRODUCTIZE
  ↓
MONITOR
  ↓
CONTINUE
  └────────────→ CREATE ...
```

## ThriveInstitutionalize™ v1.1.0

`ct.skill.factory.thrive-institutionalize.v1` is the cross-cutting lifecycle contract. Version 1.1.0 adds explicit ten-stage receipts and an evergreen continuation model.

The skill creates no sovereign authority. It records and verifies institutional state. Every independently verified stage must bind its generation/package, owner, verifier, evidence digest, candidate-only state and authority ceiling. Corrected evidence is appended or superseded; prior receipts are not silently deleted.

## Evergreen continuation

The factory uses a **rolling five-generation candidate horizon** rather than a permanent terminal generation.

The current G15 boundary is therefore a rolling window boundary, not a permanent end-state. At a horizon boundary, the orchestrator may extend the candidate planning ceiling by another five generations only when the completed generation's ten-stage lifecycle is `PASS`.

Horizon refill does **not** change:

- D2 maximum automated authority;
- D3 human reservation;
- non-voting factory-agent status;
- no-self-approval requirements;
- max one due/executing factory generation;
- rights, entitlement or provider-write authority;
- production activation state;
- checkout/Stripe state; or
- money/Crown Credits authority.

If a required stage is `HOLD`, `FAIL` or `UNKNOWN`, continuation stops rather than inventing evidence or authority.

## Agent lifecycle responsibility

The internal fleet and existing external relay mesh divide the lifecycle rather than allowing a single originator to build and certify itself.

- **Create:** orchestrator, domain architecture, algorithm/skill/prompt/script builders and productization; Agent C can perform bounded originator work.
- **Test:** TEVV, benchmarking, failure injection, runtime cohort and independent verification; Agent B verifies evidence.
- **Identify:** capability graph, lineage and continuity; Agent B verifies IDs/fingerprints/provenance.
- **Secure:** security red team, supply chain and rights/IP; Agent S performs independent security review.
- **Preserve:** archive custody, continuity and DAIL; Credential Continuity verifies Vault/ciphertext/readback boundaries.
- **Document:** documentation projection plus independent public/private review.
- **Reuse:** capability graph, productization, domain architecture and continuity register dependency/callability/interoperability relationships.
- **Productize:** commercialization, customer value, licensing economics, portfolio monetization, productization and rights/IP create candidate packages only.
- **Monitor:** continuity/control agents plus Integration Heartbeat verify drift, cron, DAIL, agent and scheduler state.
- **Continue:** orchestrator routes the next due candidate; Agent D remains the final independent candidate continuation gate where required.

## Scheduler topology

The system reuses the existing external task mesh rather than consuming additional ChatGPT scheduler slots:

- Agent A — orchestration and continuation;
- Agent C — bounded build/institutionalization;
- Agent B — independent evidence/identity/reuse verification;
- Agent S — independent security verification;
- Agent D — final candidate/continuation gate;
- Integration Heartbeat — monitoring and control-plane drift;
- Credential Continuity — secret/custody/preservation monitoring.

THIVEBASE/pg_cron performs frequent policy evaluation and queue routing. Future `planned` rows do not consume active WIP until their governed due time. Duplicate generation/package creation remains a no-op rather than parallel churn.

## Per-generation contract

A standard candidate generation targets:

- 1,000 proprietary algorithm specifications;
- 300 reusable skills;
- 500 reusable prompts;
- 300 reusable scripts; and
- 2,100 protected assets total.

Those counts are outputs, not proof. Institutionally complete means the generation can be identified, independently tested, secured, recovered, documented, reused, productized as a candidate, continuously monitored and safely continued.

## Self-healing boundary

The system may repair deterministic D0/D1 drift such as stale metadata, broken non-authoritative bindings, duplicate retry conditions and public-safe documentation pointers when the correct target is unambiguous and rollback/readback exist. D2 requires independent verification.

The lifecycle may never use self-healing to weaken a gate, create a vote, reconstruct or expose a secret, change final rights, move money, self-merge, promote a protected algorithm to production, or treat `UNKNOWN` as `PASS`.

## Why this matters

The institutional achievement is not merely the asset count. The architecture is designed to retain the **method of institutional survival** for what it creates: how to build it, prove it, name it, protect it, recover it, explain it, reuse it, package it, watch it and create the next governed generation.

That is what allows the factory to compound capability over time without allowing scale to outrun authority.
