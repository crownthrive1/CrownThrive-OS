# Agent Lineage & Version Archive

This archive preserves **how CrownThrive's agent system evolved**, not just its latest state. Current role definitions live in the [Agent Registry](/automation/agent-registry) and [Agent Templates & Pallets](/automation/agent-templates-pallets-and-commercialization). This page preserves prior generations, why they changed and what superseded them.

## Archive doctrine

Agent history is append-only. A new prompt, scheduler, authority rule, tool binding or subagent does not erase the prior generation. Every material revision should record:

```yaml
agent_or_pack_id:
version:
effective_at:
status: current | superseded | archived | suspended | retired
predecessor_version:
change_reason:
schedule_or_trigger:
vote_eligibility:
authority_change:
tool_scope_change:
source_template_version:
validation_evidence:
rollback_or_restore_target:
related_changelog:
```

Historical prompts may be preserved in restricted operational records when they contain implementation detail that should not be public. Public Mintlify records the stable role, material differences, version and evidence references rather than leaking private credentials or restricted instructions.

The machine-readable companion is `developers/manifests/agent-lineage-archive.v1.json`.

## Relay generation history

### Generation 0 — ad hoc conversational orchestration

**Historical state.** Agent-like work existed as individual chat/session instructions without a complete repository-backed role registry, deterministic quorum or stable handoff contract. Valuable as development lineage, but not acceptable as institutional authority.

### Generation 1 — four-role hourly relay

**Historical/superseded.** The first formal Phase 2.99 relay used A Orchestrator, B Evidence Auditor, C Builder and D Gatekeeper. This established staggered execution and separation of duties but did not yet include the independent Security Sentinel in the voting pool.

### Generation 2 — five-agent sovereign relay

**Current sovereign baseline.** Agent S joined A/B/C/D, establishing the five-voter pool and `4/5 + mandatory D` automatic D0–D2 merge threshold under `CT-ADR-GOV-011`. GitHub ruleset/required-check enforcement remains independent technical defense-in-depth.

### Generation 3 — scheduled specialist ring

**Current specialist layer.** Agent E API/MCP, Agent F Source & Articleization, Agent G Domain/Engine/Vendor and Agent H Webhook/Delivery were separated from the sovereign voter pool. They execute bounded specialist work but cannot manufacture votes or authority.

### Generation 4 — embedded subagent expansion

**Current embedded layer.** Scheduler limits and least-authority design led to Agent I, J and K being implemented as embedded non-voting subagents rather than independent scheduled jobs:

| Identity | Stable ID | Primary institutional function |
| --- | --- | --- |
| Agent I — Continuity & Recovery | `ct.subagent.continuity-recovery` | GATE-007 recovery, backups, exports, provider exit, restricted-source continuity |
| Agent J — Phase 3 Snapshot & Entry Packet | `ct.subagent.phase3-snapshot-packet` | GATE-008 exact source/schema/infrastructure/commit snapshot and entry packet |
| Agent K — Roadmap Transition | `ct.subagent.roadmap-transition` | downstream Phase 3–10 impact reconciliation after material changes |

This generation deliberately preserves A/B/C/D/S as the only voters.

## Operational-helper lineage

The THIVEBASE integration-hardening program introduced three reusable non-voting helpers:

- `ct.subagent.integration-heartbeat`;
- `ct.subagent.credential-continuity`;
- `ct.subagent.vendor-engine-watch`.

These became the seed pattern for the general `subagent-role-template.v1.yaml` contract. Their authority remains read-first and fail-closed.

## Source-template lineage

### Template generation 1.0.0 — 2026-08-19

Initial reusable source set:

- `agent-role-template.v1.yaml` — full scheduled/voting/specialist role contract;
- `subagent-role-template.v1.yaml` — embedded non-voting delegation contract;
- `agent-pack-manifest-template.v1.json` — packaging, license, release and Stripe placeholders;
- `chlom-capability-pallet-template.v1.yaml` — portable governed capability package;
- `third-party-attribution-template.v1.yaml` — open-source/external code license and notice gate.

The templates intentionally default to **no production writes, no phase advancement, no self-approval and no authorized price**.

### Template generation 1.0.1 — 2026-08-19

Generation 1.0.1 adds `chlom-runtime-adapter-template.v1.yaml` as a separately governed research template for future decentralized, cryptographic or protocol-runtime adapters. It does **not** replace the capability-pallet template and does not imply any runtime is deployed.

The runtime-adapter template defaults to `RESEARCH`, `production_deployed=false`, no required token/wallet/chain, public-ledger PII/restricted-evidence prohibition, Phase-9 earliest activation and explicit threat/legal/privacy/security/key-custody/recovery/rollback gates. This preserves the historical protocol/runtime research lineage while keeping current CHLOM cloud-first and institutionally operable.

## Version-preservation rules

1. Stable IDs survive prompt wording changes.
2. Scheduler/task IDs are runtime implementation references, not institutional identities.
3. A schedule change creates a version/update record when it materially changes operating cadence or responsibility.
4. Prompt improvements that alter authority, data scope, tools, phase gates, outputs or failure behavior are material and require changelog impact.
5. Prior accepted versions remain reconstructable from Git history and/or controlled archive.
6. A retired agent remains queryable as historical lineage and cannot silently reappear as current.
7. Commercial template versions and internal operational versions are related but separately versioned; public packages never expose CrownThrive-private secrets or evidence.
8. Capability-pallet and runtime-adapter template versions remain independent; neither silently supersedes the other.

## Changelog routing

- **Major topology/authority changes:** record in the [Institutional Changelog Index](/changelog/index) and a dedicated subject changelog.
- **Agent-specific material revisions:** update this archive plus the applicable agent/template page.
- **Mechanical D1 prompt wording or metadata fixes:** append to the subject changelog only when they affect reproducibility or machine behavior.
- **Runtime incidents:** remain in operational watch/incident logs and link back here only when they caused a durable agent-contract change.

## Machine ingestion

Machine consumers should prefer stable template/manifests and current registry records. This archive exists to answer lineage questions such as:

- Which version was active when a decision was made?
- When did an agent become non-voting or gain a specialist scope?
- Which template generated the current role contract?
- Which prior behavior was superseded and why?
- What rollback target exists if a new agent revision regresses?

The archive is therefore institutional evidence, not merely narrative history.
