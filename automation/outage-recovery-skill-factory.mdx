# Outage Recovery Skill Factory

CrownThrive converts repeated operational failures and recovery work into reusable institutional capability instead of allowing every incident to be rediscovered from scratch.

The current candidate skill identity is:

```text
ct.skill.thrive-outage-recovery.v1
```

Its public-safe purpose is to standardize incident detection, status tracking, provider/capacity evidence, native heartbeat recovery, credential gates, dependent canaries, reconciliation, lessons learned, and after-action packaging.

<Warning>
  Candidate status is not production certification or a public commercial release. Protected implementation bodies, credentials, private provider evidence, thresholds, exploit-enabling detail, and proprietary control logic remain in the governed private/Vault boundary.
</Warning>

## Factory state model

```text
observed pattern
→ extracted
→ sanitized
→ tested
→ independently verified
→ fingerprinted
→ registered
→ MCP/API packaging candidate
→ commercialization candidate
→ governed active only after applicable release gates
```

The originating incident remains the evidence source. The skill never replaces or rewrites incident history.

## Inputs

The skill consumes references, not unrestricted raw secrets:

- stable incident ID;
- service IDs and dependency graph;
- severity and lifecycle state;
- provider-state evidence references;
- native heartbeat references;
- capacity/usage state where relevant;
- mitigation and rollback record;
- dependent canary results;
- credential-intake/custody state;
- agent acknowledgement/impact dispositions;
- reconciliation results;
- documentation impact; and
- after-action lessons.

## Outputs

A successful controlled run can produce:

- incident/status record updates;
- missing-ack queue;
- recovery-readback packet;
- reconciliation checklist;
- canary/evaluation fixtures;
- runbook delta;
- alert/threshold candidate;
- provider-exit/recovery delta;
- documentation update or delta;
- sanitized factory candidate; and
- commercial-readiness gap list.

It may not create false PASS evidence to satisfy the output contract.

## Agent lanes

Recommended separation of duties:

| Lane | Responsibility |
| --- | --- |
| Incident orchestrator | creates/coordinates the governed incident run |
| Infrastructure/security | provider, capacity, access and security diagnosis |
| Recovery/rollback | restore, degraded mode, compensation and rollback evidence |
| Platform observers | impact/no-impact and platform-specific canaries |
| Evidence auditor | verifies source, timing, claims and missing evidence |
| Documentation sentinel/steward | status, changelog, runbook and article impact |
| Factory extractor | turns validated repeated work into a candidate capability |
| Independent verifier | tests that the candidate reproduces the intended safe behavior |
| Commercialization reviewer | determines whether a sanitized package has a legitimate customer use case |

No lane self-approves A3/A4 actions.

## Evaluation requirements

Before promotion beyond candidate state, test at minimum:

1. stale provider status with healthy native service;
2. healthy provider status with missing native heartbeat;
3. storage/capacity exhaustion with read-only degradation;
4. restart that returns before dependent jobs recover;
5. duplicate/out-of-order webhook events after recovery;
6. missing or rotated credential after restart;
7. public identifier supplied where a secret is required;
8. secret accidentally present in documentation payload;
9. one impacted platform and one `no_impact` platform;
10. recurrence during the monitoring window;
11. rollback/degraded-mode path; and
12. unresolved evidence that must remain HOLD.

Expected behavior is fail-closed when authority, secret custody, evidence, or recovery proof is missing.

## Vault and IP boundary

The factory keeps these items out of the public repository:

- secret values;
- raw credential fingerprints where restricted;
- private provider account/billing evidence;
- internal incident payloads containing sensitive data;
- security exploit paths;
- unreleased proprietary thresholds/algorithms; and
- private agent identity/recovery material.

Public documentation may expose stable IDs, role boundaries, state models, sanitized inputs/outputs, evaluation classes, and high-level control behavior.

## Monetization pathway

Validated public-safe capability may later support customer-facing offers such as:

- infrastructure continuity assessment;
- incident-readiness assessment;
- provider dependency and exit review;
- status-control-plane implementation;
- outage/recovery runbook package;
- synthetic recovery drill;
- managed reliability/continuity operations;
- API/MCP integration resilience review; or
- licensed templates and governed agent-skill packs.

These remain candidates until rights, security, privacy, legal, pricing, tax, fulfillment, support, customer-outcome, accessibility, refund/dispute, and release evidence pass the applicable gates.

No factory agent may automatically turn a lesson into a public product, Stripe object, customer entitlement, unrestricted MCP tool, rights grant, or production credential.

## Institutional learning rule

The capability factory exists to make the institution compound operational knowledge:

```text
incident
→ evidence
→ correction
→ lesson
→ test
→ runbook
→ skill
→ reusable package
→ independently verified release candidate
→ bounded commercialization when earned
```

This is the same institutional principle applied across CrownThrive: every governed run should strengthen the next run.
