# Machine Trigger Asset Fabric

CrownThrive machine-led triggers are institutional assets, not informal automation rules. The Trigger Asset Fabric gives each trigger a stable identity, authority ceiling, plugin binding, custody profile, factory intake state, deterministic derivative plan and fail-closed execution boundary.

## Current candidate package

The first fabric contains **32 trigger bundles** across Phase 2.99 hard exit, Phase 3 bootstrap, perpetual commerce and continuity. Each bundle deterministically materializes one candidate algorithm contract, one governed skill, one machine prompt and one automation script: **128 derivative candidate assets**.

These candidates do **not** increase the current 100,800 authoritative generation-asset count. They enter the Proprietary Capability Factory as `candidate_hold` and remain outside a completed generation until the governed lifecycle, independent verification, custody/readback and generation-orchestration gates pass.

The fabric is explicitly bound to the plugin-suite, Vault-binding and proprietary-factory-intake manifests so those relationships are no longer documentation-only cross references.

## Factory binding

The fabric binds to `ct.fleet.chlom-proprietary-asset-factory.100k-plus`, ThriveInstitutionalize v1.1.1, `ct.agent-suite.commercial-release-factory.v1`, `ct.contract.phase-gate.p299-hard-exit.v1`, `ct.platform.thriveevergreen`, CHLOM, DAIL, THIVEBASE and CHLOM Vault.

The dedicated factory-intake contract is `developers/manifests/machine-trigger-factory-intake.v1.json`. It records 32 trigger bundles and 128 deterministic derivative candidates while preserving an authoritative generation-asset delta of **zero**. The candidates do not enter a completed generation merely because they can be generated.

Continuation never creates authority. A scheduled run can discover, materialize, validate, hash, queue and hold candidate assets. It cannot create a sovereign vote, exercise D3, grant rights, activate Phase 3, enable commerce, publish automatically, move money/Crown Credits or widen provider credentials.

## Plugin suite

Five D2-ceiling, non-voting plugin contracts are part of the fabric and are separately registered in `developers/manifests/machine-trigger-plugin-suite.v1.json`:

1. `ct.plugin.machine-trigger-router`
2. `ct.plugin.p299-phase-gate`
3. `ct.plugin.phase3-bootstrap`
4. `ct.plugin.commerce-factory`
5. `ct.plugin.vault-dail-continuity`

Plugins route governed events and contract calls. They never inherit sovereign authority from the system they invoke.

## Vault binding

Every trigger asset is assigned a public-safe Vault profile. Public Git stores only the profile class and required behavior. Raw secrets, private Vault locators and recovery material are prohibited.

The binding contract is `developers/manifests/machine-trigger-vault-binding-contract.v1.json`. It requires exactly **32** opaque asset/SHA binding receipts, readback, and recovery proof. The live binding remains `PENDING_RUNTIME_BINDING` because the THIVEBASE SQL/control channel is currently timing out. The fabric does not fabricate those receipts. When the governed control path is writable, every binding must be exact asset/SHA bound, opaque-reference only, read back and recoverable.

## Commerce non-bypass

Every commerce trigger binds to ThriveEvergreen. No economic activation may occur without a valid, non-superseded ECAC and the applicable independent acceptance. Provider payment, delivery, API or fulfillment success remains evidence only and cannot directly manufacture invoice, payout, earning, entitlement, settlement or public performance truth.

The current Commercial Release Factory candidate branch is explicitly bound to the trigger fabric for candidate discovery, material-change reopening, package build, gate evaluation, ECAC decision, bounded publication, entitlement/fulfillment, drift monitoring, reconciliation, remedies, Vault custody, DAIL and supersession. This cross-branch binding remains candidate evidence until both governed paths are canonically accepted.

## Automation and exact binding

`.github/workflows/machine-trigger-asset-fabric.yml` runs on relevant PR/push changes, hourly reconciliation and explicit dispatch. It uses read-only repository permissions, materializes all 32 bundles, proves 128 derivative candidates, builds five plugin records and 32 Vault binding candidates, cross-validates the factory/plugin/Vault manifests and runs negative authority tests.

`CT-P299 Machine Hard Exit` independently validates the same fabric before it may evaluate Phase 3. The OIDC THIVEBASE snapshot service exact-pins the Phase-3 workflow, trigger manifest, trigger builder, plugin manifest, Vault binding contract, factory-intake contract and binding validator. A changed byte therefore requires an intentional rebind rather than silently inheriting authority.

The CT-P299 canonical source freeze also includes the trigger fabric, plugin suite, Vault binding contract, factory intake and binding validator. These assets therefore participate in the exact Phase 2.99 exit snapshot rather than remaining auxiliary automation.

Negative controls reject D3 expansion, default provider writes, ECAC bypass and public Vault locator disclosure. The workflow must retain an authoritative-generation count delta of zero until the Proprietary Capability Factory actually admits the candidates through its governed lifecycle.

## Current evidence

At the current candidate head, Machine Trigger Asset Fabric, CT-P299 Machine Hard Exit, Security Governance, Documentation Governance and Governed Merge Gate have completed successfully as technical validation on the preceding exact trigger-binding baseline. The trigger validator reports `PASS_MACHINE_TRIGGER_ASSET_FABRIC` and `PASS_MACHINE_TRIGGER_BINDINGS` with 32 bundles, 128 derivative candidates, five plugins, 32 Vault binding candidates and authoritative delta zero. Every material source update is re-run through the same checks before acceptance.

Those green checks do not change the Phase 3 verdict. Phase 3 remains `NO_GO` while hard-exit blockers, authority/recovery evidence, live `main` enforcement and required THIVEBASE aggregate reads remain incomplete.
