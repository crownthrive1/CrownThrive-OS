# THIVEBASE Capacity and Partner Monitoring

THIVEBASE monitoring converts infrastructure growth from an ad-hoc billing surprise into a governed capacity and commercial-intelligence loop.

## Monitoring objectives

Track, where provider evidence is available:

- database/storage consumption;
- egress and cached egress;
- MAU/third-party MAU;
- function invocations;
- realtime messages and peak connections;
- API/provider request budgets;
- log retention/recovery limitations;
- project inactivity/pause risk;
- cost and renewal changes;
- support/license expiry;
- provider incidents/outages;
- partner/referral-program status changes;
- referral commissions/revenue where approved;
- predicted exhaustion or upgrade date;
- CrownRewards/My CrownRewards production availability;
- Reward Loyalty v4→v5 migration state, supported-update-track changes, current v5 docs/changelog, API/Agent API changes and migration/security prerequisites.

## Provider identity boundary

Monitoring must not confuse interconnected provider relationships:

```text
Partnero → Crown Affiliates / Crown Ambassadors
Adserver.Online → AdLuxe Network delivery/reporting
Reward Loyalty → CrownRewards / My CrownRewards
```

Cross-platform events may be related, but a provider's availability, API state, pricing or failure belongs to the correct platform relationship.

## Standard alert states

```yaml
green: 0-49%
watch: 50-69%
plan: 70-79%
action_needed: 80-89%
scale_gate: 90%+
```

The percentage band is a default. A predicted exhaustion date, provider notice, security event, license expiry, outage, or loss of export/recovery capability may escalate the state early.

## Notification vocabulary

Operational alerts should use attention-first status labels consistently:

- `SUCCESS` — governed remediation or capacity action completed and revalidated;
- `FAILURE` — an expected control/monitor failed or a provider constraint has already impaired service;
- `ACTION NEEDED` — a threshold or deadline requires founder/operator action;
- `WATCH` — trend requires increased observation but no immediate action;
- `NO ACTION NEEDED` — reviewed state remains inside policy;
- `BLOCKED` — monitor cannot obtain authoritative data or a downstream gate is fail-closed.

The label describes the present operational state; it must not manufacture a successful provider or Phase gate.

## Monitoring cadence target

Until production load justifies tighter observation:

- automated/sanitized capacity snapshot: daily where provider metrics can be read safely;
- threshold and forecast evaluation: daily;
- partner/referral-program research queue: monthly or when a material vendor is added/renewed;
- provider terms/pricing/limits verification: monthly for high-priority infrastructure and before any scale decision;
- renewal/license checks: at least 60/30/14/7 days before a known expiry where data exists;
- CrownRewards public health and Reward Loyalty v5 support/API/changelog review: at least daily through the shared Engine & THIVEBASE watch while the v5 migration remains open;
- immediate recheck after an incident, pricing notice, provider-plan change or major platform activation.

No scheduled job may expose credentials or turn an unavailable metric into zero.

## CrownRewards migration monitoring

The current source-of-truth state is **v4 operational / v5 not yet deployed**. Vendor support confirms v4 may continue running while current updates/support move through v5.

Monitoring must:

- keep the public v4 site health separate from the v5 migration gate;
- check official Reward Loyalty 5.x changelog, upgrade/update instructions and Agent API docs;
- never report provider-documented v5 capability as deployed CrownRewards capability;
- preserve a backup/staging/rollback requirement before migration;
- track v5 commercial/update-track changes as provider snapshots rather than automatic purchase authority;
- keep Reward Loyalty API/MCP writes closed until production v5, least-privilege keys, read certification, rate/idempotency, audit and reconciliation gates pass.

## Self-healing boundary

Permitted automated remediation includes:

- rerunning read-only usage queries;
- regenerating sanitized snapshots;
- compacting or rotating non-authoritative transient data under approved retention rules;
- opening scaling/optimization work items;
- reducing optional telemetry frequency when a quota policy explicitly permits it;
- switching to approved backup/export paths;
- updating documentation when provider limits change.

Not permitted autonomously:

- upgrading a paid plan;
- purchasing the Reward Loyalty v5 upgrade;
- migrating CrownRewards production to v5;
- disabling security controls;
- deleting authoritative DAIL/rights/evidence records to recover space;
- rotating/exposing credentials without governed authority;
- changing customer prices;
- accepting vendor/referral terms;
- turning on provider writes that remain certification-blocked.

## Commercial intelligence loop

The Partner Registry should be checked alongside capacity because the same provider can be both a cost center and a potential referral/revenue partner.

```text
provider/tool
   ↓
usage + fit + reliability evidence
   ↓
capacity/cost profile
   ↓
verified referral/partner program?
   ├─ no → continue operational tracking
   └─ yes
       ↓
eligibility + terms + disclosure review
       ↓
approved CrownThrive recommendation/integration surface
       ↓
conversion/commission evidence
       ↓
CrownLytics + finance/CHLOM record
```

Referral revenue must never be used to conceal a provider's total cost, lock-in risk or poor fit.

## Phase gates

**Phase 2.99:** monitoring policy and machine fields may be formalized; current unknown usage must remain unknown. CrownRewards v4 remains the current production truth while v5 is prepared.

**Phase 3:** connect authoritative sanitized provider metrics, establish backup/restore tests and threshold automation; perform the governed CrownRewards v5 staging/cutover process only after the Phase 2.99 hard exit permits it.

**Phase 4:** aggregate provider/cost/capacity telemetry across P0/P1 adapters and route operational actions into OpsOasis/CrownLytics; federate certified Reward Loyalty v5 reward events across qualified ecosystem lanes.

**Phase 5+:** add customer-facing metering, usage billing, partner marketplace metrics and infrastructure margin analysis for external THIVEBASE offerings.
