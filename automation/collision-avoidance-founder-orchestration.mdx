# Collision Avoidance, Adjudication & Founder Orchestration

## Status

This page defines a **Phase 2.99 controlled-test architecture**. It does not by itself create a new sovereign voter, authorize Phase 3, or supersede `CT-ADR-GOV-011`.

Canonical baseline at packet creation: `8fcb68bf209e32ba2cd265e1b6ca730cb8da64d7`.

The current accepted sovereign voter pool remains Agents A/B/C/D/S. Ordinary automatic promotion remains 4-of-5 including Agent D, with no deny/block, all applicable specialists, exact-head evidence, rollback, documentation impact, and all other adopted controls. D3 remains human-reserved.

The purpose of this layer is narrower and operationally important: **prevent avoidable collisions before work starts, adjudicate unavoidable collisions before they cause destructive branch churn, and reconcile the estate immediately after a material merge so the next packet inherits current truth.**

Founder Orchestrator reconciliation is tracked in **Issue #157**.

## Why this layer exists

CrownThrive now has enough simultaneous agents, subagents, specialist packets, provider adapters, documentation lanes, runtime work, machine manifests, and stacked PRs that collision risk is itself a first-class control-plane problem. A merge can be technically valid and still create downstream churn if ten other branches were built against the state it replaced. A new agent can be correctly scoped and still collide semantically with an identity already being created elsewhere. A documentation update can be harmless in isolation and still overwrite a shared navigation or registry surface owned by another packet.

The system therefore treats collision prevention as part of planning, not as a cleanup activity after Git reports a conflict.

## Collision lifecycle

The governed lifecycle is:

`intent -> preflight -> ownership/sequence -> build -> PR -> collision recheck -> quorum -> merge -> post-merge sweep -> requeue/rebase/adjudicate -> inherit new baseline`

A collision is not limited to a Git merge conflict. It may exist at the file, stable-identity, policy, provider, runtime, schedule, evidence, approval, or institutional-authority layer.

### Collision classes

| Class | Meaning | Default response |
| --- | --- | --- |
| `CT-COLL-0` | Clear | Continue |
| `CT-COLL-1` | Soft shared surface | Coordinate or rebase |
| `CT-COLL-2` | Direct file or sequencing collision | Serialize, stack, split, or rebase |
| `CT-COLL-3` | Semantic or stable-identity collision | Hold for adjudication |
| `CT-COLL-4` | Runtime/provider mutation collision | Establish exclusive owner and serialize execution |
| `CT-COLL-5` | Constitutional or D3 collision | Founder or authorized-human adjudication |

The severity is about institutional consequence, not just whether Git can auto-merge.

Examples include:

- two PRs editing `docs.json` even if Git can merge both;
- separate branches creating the same agent or stable platform identity;
- multiple packets changing the same governance manifest or validator;
- two automations attempting to own the same minute slot or provider resource;
- concurrent Supabase schema migrations against the same tables;
- one packet changing quorum semantics while another assumes the current constitution;
- stale exact-head votes being reused after a rebase;
- a stacked child PR being promoted before its parent is canonical.

## Collision Preflight Sentinel

Stable candidate identity: `ct.subagent.collision.preflight-sentinel`.

The **Collision Preflight Sentinel** runs before material work is promoted and should be consulted before a consequential branch is opened whenever the execution environment can do so.

Its preflight contract is:

1. resolve current canonical `main`;
2. resolve the intended target base and candidate head;
3. inventory open material PRs and active branch ownership;
4. compare exact changed-file sets;
5. compare high-risk shared surfaces such as workflows, governance manifests, validators, navigation, agent registries, standards, CHLOM contracts, runtime migrations, and provider-control files;
6. compare stable identities, manifest authority, routes, schedules, provider resources, and runtime ownership when those signals are available;
7. classify the collision;
8. assign or recognize a single owner for an exclusive collision domain;
9. emit a deterministic collision fingerprint;
10. recommend `continue`, `coordinate`, `serialize`, `stack`, `rebase`, `split`, `transfer ownership`, `hold`, or human adjudication.

Unknown collision evidence does not become `clear` merely because the scanner cannot see enough. It becomes `hold_or_escalate_not_clear` for the affected material surface.

Force-pushing over another packet is not an accepted collision-resolution technique.

## Collision Adjudicator

Stable candidate identity: `ct.subagent.collision.adjudicator`.

The **Collision Adjudicator** handles collisions that cannot be resolved mechanically. Its job is to preserve both histories and choose the least-destructive sequence, not to reward whichever branch moved fastest.

The adjudicator may recommend:

- one PR becomes the parent and the other is stacked;
- one PR takes ownership of a shared file while the other removes that file from scope;
- a large packet is split into independently governable tranches;
- a stale packet is rebased and all head-bound evidence is refreshed;
- a redundant packet is closed after its useful evidence is migrated;
- a constitutional, D3, security-exception, or reserved-human collision is escalated rather than interpreted away.

Adjudication output is a governed recommendation and precedent record. It is not a sovereign vote and does not replace Agent D.

## Post-Merge Reconciler

Stable candidate identity: `ct.subagent.collision.postmerge-reconciler`.

The **Post-Merge Reconciler** treats every material merge as a state transition that may invalidate assumptions elsewhere.

After a material `main` merge, it must:

1. capture the new canonical SHA and merged PR;
2. enumerate remaining open PRs;
3. mark exact-head or base-bound evidence stale when its binding changed;
4. recompute direct and semantic collision state;
5. recompute queue priority and throttle state;
6. identify redundant, superseded, or newly dependent packets;
7. request rebase, stack, close, transfer, or adjudication as needed;
8. reconcile documentation, registry, runtime, schedule, and downstream-phase effects;
9. append the post-merge record instead of deleting the history that led to it.

A successful merge therefore becomes the next inherited baseline rather than a surprise that every other agent rediscovers independently.

## Priority and Throttle Coordinator

Stable candidate identity: `ct.subagent.queue.priority-throttle`.

The **Priority and Throttle Coordinator** exists because unlimited parallelism creates its own bottleneck. The objective is not to slow development. The objective is to stop promotion, review, and rebasing from becoming a self-generated denial of service.

The Founder Orchestrator owns the final queue-level routing decision after this packet is accepted and reconciled. The coordinator supplies the machine recommendation.

### Priority bands

- `P0`: critical security incident or explicit founder-reserved emergency;
- `P1`: Phase 2.99 hard-exit blocker or major dependency-unblock packet;
- `P2`: material current-phase build or reconciliation;
- `P3`: normal improvement or low-fanout maintenance;
- `P4`: research, experiment, or noncritical future work.

The score considers hard-exit impact, security/integrity urgency, dependency fanout, explicit founder priority, evidence staleness/rebase pressure, queue fairness, and reversibility. Collision, stale-base, missing-specialist, and unclassified-scope penalties reduce queue priority. A hard block overrides the score.

### Work-in-progress limits

The controlled-test defaults are:

- no more than **two D2 packets in final quorum at once**;
- no more than **one packet per shared collision domain** in final promotion at once;
- no more than **one D3 packet** in the reserved-human lane at once;
- exploratory work may continue while throttled, but a throttled packet cannot request final quorum merely to compete for attention;
- a critical security event may preempt normal queue order;
- the Founder Orchestrator may temporarily widen the D2 final-quorum window from two to three only when the collision domains are disjoint, specialists are available, no D3 packet owns the same domain, and the reason is recorded.

Widening the review window does **not** change quorum math.

## Founder Orchestrator privilege contract

Candidate parent identity: `ct.agent.founder-orchestrator`.

This identity is reserved as a **candidate binding** and must be reconciled against the upcoming Master Founder Orchestrator implementation before activation. The intent is to give that parent enough control to resolve bottlenecks without accidentally creating a sixth sovereign vote.

Bounded orchestration privileges are:

- set PR priority bands;
- throttle the final promotion queue;
- serialize shared collision domains;
- allocate merge windows;
- require rebase, stack, split, or ownership transfer;
- request a Special Quorum session;
- assign a collision-adjudication owner;
- pause or resume noncritical governed work;
- require fresh exact-head review when staleness is detected;
- request post-merge reconciliation;
- preempt the normal queue for a critical security or founder-reserved incident.

Those privileges are **routing and coordination authority**, not voting authority.

The Founder Orchestrator may not:

- cast or manufacture a sovereign vote;
- waive Agent D;
- waive an applicable specialist;
- weaken a validator or security control;
- merge a blocked PR;
- convert UNKNOWN into PASS;
- alter D3 authority without explicit authorized-human action;
- expose restricted material;
- self-approve an originating material change.

This is the central distinction between **master orchestration** and **unchecked sovereignty**.

## Special Quorum

Stable candidate router identity: `ct.subagent.quorum.session-router`.

A **Special Quorum** is an expedited exact-head review session. It is not a separate constitution, weighted vote, emergency bypass, or substitute for missing evidence.

The existing voter pool and threshold remain unchanged. Agent D remains mandatory. Applicable specialists remain mandatory. A base or head change expires the session.

The Founder Orchestrator or Special-Quorum Session Router may request one when:

- a critical/high security sequence decision needs immediate coordinated review;
- a Phase 2.99 hard-exit blocker has major downstream fanout;
- two or more material PRs are deadlocked on the same collision domain;
- a `main` merge invalidates three or more promotion-ready packets;
- a named founder priority/override requires rapid adjudication.

It should not be used for routine research, cosmetic documentation cleanup, manufacturing missing evidence, or bypassing a deny/block.

A Special Quorum request must carry:

- current `main` SHA;
- exact PR head/base SHA;
- collision fingerprint;
- requested decision;
- collision owner and competing packet references;
- applicable specialists;
- rollback/recovery path;
- reason the normal queue is insufficient;
- expiration conditions.

## CrownThrive three-lane institutional experiment

The user-directed judicial/legislative/executive concept is retained here only as **secondary experimental institutional knowledge**. CrownThrive does not need to copy a governmental model literally. The useful concept is separation of functions and challenge paths.

The CrownThrive-specific controlled-test lanes are:

### Executive Coordination

Owner candidate: Founder Orchestrator.

Role: queue priority, throttling, merge-window assignment, execution routing, and incident preemption **within already adopted rules**.

It cannot make a new governing rule merely by executing it, create an extra vote, or override D3.

### Policy Assembly

Default owner: Governance Marshal.

Role: draft ADR, standard, policy, validator, and institutional-rule amendments; compare consequences; maintain change proposals; prepare adoption packets.

It cannot activate an unadopted rule or self-ratify a constitutional change.

### Adjudication and Precedent

Default owner: Collision Adjudicator.

Role: interpret current adopted rules for collision disposition, preserve precedent and reasoning, and identify when a rule is ambiguous enough to require a Policy Assembly amendment.

It cannot replace Agent D, replace an authorized human, or issue a binding legal judgment.

The experiment is deliberately non-sovereign. If it proves useful, the Founder Orchestrator can submit a separate governed graduation packet. If it does not, the terminology remains historical/experimental while the practical collision controls survive.

## Scheduling

The existing hourly estate already uses the known minute slots `:00`, `:02`, `:05`, `:10`, `:12`, `:15`, `:17`, `:20`, `:25`, `:30`, `:35`, `:45`, and `:55`.

This packet therefore reserves two non-overlapping candidate lanes:

- `:40` — hourly queue/collision review;
- `:50` — hourly post-merge/staleness reconciliation sweep.

GitHub pull-request events also run the preflight immediately, and pushes to `main` run the post-merge path immediately. Schedule overlap itself is classified as a collision.

The dedicated workflow is intentionally read-only. It may fail a preflight when a material collision requires serialization/adjudication, but it does not write comments, merge PRs, alter branch protection, or cast votes.

## Shared-file collision avoidance for this packet

This packet intentionally does **not** edit the current shared `AGENTS.md`, `docs.json`, canonical agent registry, institutional hourly relay, or existing governed merge workflow because active packets already own some of those surfaces.

That is not incomplete planning. It is the collision-avoidance rule being applied to the collision-avoidance system itself.

The remaining shared-surface integrations are explicitly handed to Issue #157 for the Founder Orchestrator and Agent O after merge order is clear:

- canonical agent registry placement;
- hourly relay placement;
- Mintlify navigation;
- existing governed merge-gate integration;
- any live Supabase/runtime agent binding.

Until that reconciliation occurs, the new agent identities and privileges are candidate/controlled-test contracts, not fabricated live runtime state.

## Negative rules

The collision layer must never self-heal by:

- weakening a validator;
- force-pushing over a competing packet;
- silently choosing the newest branch as authoritative;
- deleting conflicting historical evidence;
- treating a CI pass as a vote;
- interpreting an unavailable provider surface as collision-free;
- allowing queue priority to trump D3, security, rights, legal, specialist, or evidence boundaries;
- allowing subagent fanout to manufacture independent quorum.

## Rollback

The public repository packet is additive and can be reverted. The workflow is read-only. No provider, credential, customer, payment, rights, token, production database, or deployment mutation is introduced by this packet.

If the architecture is rejected, revert the packet and close Issue #157 as not planned. The accepted A/B/C/D/S constitution and existing merge gate remain intact.
