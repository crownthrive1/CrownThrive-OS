# Agent Templates, Pallets & Commercialization

This section turns CrownThrive's agent-building method into institutional IP instead of leaving it trapped in scheduler prompts or chat history. It covers **internal agents**, **embedded subagents**, **commercially reusable templates**, **CHLOM capability pallets**, and **future runtime/decentralized adapters** while preserving the boundary between reusable architecture and CrownThrive-private authority, credentials, evidence, customer data and trade-secret implementation.

## Current topology

CrownThrive currently separates **sovereign voters**, **scheduled specialists**, and **embedded subagents**.

| Class | Current identities | Vote authority |
| --- | --- | --- |
| Sovereign relay | A Orchestrator, B Evidence Auditor, C Builder, D Gatekeeper, S Security Sentinel | A/B/C/D/S only; 4/5 plus D for eligible automated D0–D2 promotion |
| Scheduled specialists | E API/MCP, F Source & Articleization, G Domain/Engine/Vendor, H Webhook & Delivery | none |
| Embedded specialists | I Continuity & Recovery, J Phase 3 Snapshot & Entry Packet, K Roadmap Transition & Downstream Reconciliation | none |
| Reusable helpers | integration heartbeat, credential continuity, vendor-engine watch | none |

Agent titles do not create authority. The [Permissions & Approvals](/automation/permissions-and-approval-gates) and `CT-ADR-GOV-011` remain controlling.

## How an agent is built

Every agent starts from a reusable source contract rather than a free-form prompt. The current source templates are:

- `developers/templates/agent-role-template.v1.yaml`
- `developers/templates/subagent-role-template.v1.yaml`
- `developers/templates/agent-pack-manifest-template.v1.json`
- `developers/templates/chlom-capability-pallet-template.v1.yaml`
- `developers/templates/chlom-runtime-adapter-template.v1.yaml`
- `developers/templates/third-party-attribution-template.v1.yaml`

The build sequence is:

```text
institutional objective
→ canonical phase/gate ownership
→ authority class and vote eligibility
→ allowed/prohibited tool/data scope
→ evidence sources and UNKNOWN policy
→ output/handoff schema
→ validators + negative tests
→ rollback/recovery
→ documentation + changelog impact
→ versioned source template instance
→ controlled scheduler/agent deployment
→ observed runs/evals
→ promotion, correction, suspension or retirement
```

A prompt is therefore only one projection of the agent record. The durable identity is its stable ID, versioned role contract, permissions, tests, run history and archived predecessors.

## Embedded subagent pattern

Embedded subagents exist when a specialized function is needed but an independent scheduled task would waste scheduler capacity or falsely imply new sovereign authority.

### Agent I — Continuity & Recovery

Stable ID: `ct.subagent.continuity-recovery`.

Primary role: support `CT-P299-GATE-007` with backup, restore, export, provider-exit, registrar/domain continuity, restricted-source custody and reproducibility evidence. It may prepare deterministic D0/D1 recovery artifacts but may not perform destructive restoration, rotate credentials, delete evidence or mark recovery proven without an actual test.

### Agent J — Phase 3 Snapshot & Entry Packet

Stable ID: `ct.subagent.phase3-snapshot-packet`.

Primary role: support `CT-P299-GATE-008` by assembling the exact commit/schema/infrastructure/source snapshot and Phase 3 entry packet. It is deliberately **late-gated**: it must not create a false readiness packet while GATE-001/002/003/006/007 or another inherited requirement is unresolved.

### Agent K — Roadmap Transition & Downstream Reconciliation

Stable ID: `ct.subagent.roadmap-transition`.

Primary role: after every material change, identify affected assumptions and update dependent Phase 3–10 objectives, entry/exit gates, tests, artifacts, risk, rollback and handoff state. It cannot advance a phase or waive an earlier gate.

## CHLOM capability pallets

A **CHLOM capability pallet** is a portable governed capability package, not a claim that a blockchain/runtime pallet is already deployed. A pallet may contain:

- capability purpose and side-effect class;
- schemas and policy references;
- API/MCP/event contracts;
- validators and evaluation fixtures;
- documentation/runbooks;
- rights/security review state;
- rollback and continuity requirements;
- third-party notices;
- commercialization/license metadata.

This makes pallets useful in both the current cloud/software CHLOM architecture and later interoperable/decentralized architecture without conflating the two.

Candidate first pallets from the existing agent system include:

1. **Evidence Reconciliation Pallet** — source/current/historical/UNKNOWN classification and contradiction handling.
2. **Phase Gate Pallet** — hard entry/exit evaluation with downstream propagation.
3. **API/MCP Certification Pallet** — read-first adapter discovery, scopes, budgets, schemas and write gating.
4. **Credential Continuity Pallet** — secret-reference presence/rotation/recovery evidence without secret disclosure.
5. **Webhook Integrity Pallet** — authentication, bounded body, idempotency, replay and readback controls.
6. **Vendor Engine Watch Pallet** — latest target version, installed-version proof, support/license/pricing separation.
7. **Documentation Impact Pallet** — `docs_updated | docs_no_change | docs_delta_opened` and changelog synchronization.

Each pallet receives a stable ID and independent version; one agent pack may depend on multiple pallets.

## CHLOM runtime/decentralized adapter templates

The second CHLOM template family is `developers/templates/chlom-runtime-adapter-template.v1.yaml`. It exists for a **future optional protocol, blockchain, cryptographic or decentralized adapter behind a stable capability pallet**.

The runtime-adapter template is deliberately research-gated:

- lifecycle defaults to `RESEARCH` and `production_deployed=false`;
- earliest activation is Phase 9;
- no token, wallet, chain, smart contract or public network is required by default;
- private/restricted evidence and PII are prohibited from public immutable ledgers;
- threat model, legal/privacy/security review, key custody/recovery, rollback and off-chain reconstruction are mandatory before activation;
- token/securities/money-transmission/tax review becomes mandatory if the proposed adapter moves or represents economic value;
- a runtime adapter cannot replace the cloud/institutional core by implication and cannot inherit production authority from a paper, repository, prototype or naming similarity.

This gives CrownThrive both reusable **capability pallets** and separately governed **runtime adapters** without repeating the historical error of treating target decentralized architecture as current deployment.

## Open-source and third-party code rule

CrownThrive may learn from, integrate, fork or distribute open-source code **only when the exact upstream license permits the intended use**. Before code enters a public or paid package, record:

- upstream repository and version/commit;
- author/copyright holder;
- SPDX license identifier where available;
- required attribution/NOTICE text;
- source-offer or copyleft obligations;
- modification disclosure requirements;
- trademark restrictions;
- distribution/SaaS/network-copyleft triggers;
- compatibility with the CrownThrive package license.

`developers/templates/third-party-attribution-template.v1.yaml` is the required intake template. `THIRD_PARTY_NOTICES.md` is the public repository notice surface. Code with unclear or incompatible rights stays out of distributable/paid packages until resolved.

<Warning>
  CrownThrive must never remove required attribution, relabel third-party authorship as CrownThrive authorship, or assume that public source code means unrestricted commercial redistribution.
</Warning>

## Internal versus commercial package boundary

A commercial agent/template package is a **sanitized derivative** of the institutional source. It must exclude:

- API keys, secrets and credential fingerprints;
- private customer/partner data;
- restricted evidence and contracts;
- CrownThrive-specific production identifiers that are not necessary to the template;
- private economic calibration;
- unreleased rights/canon material;
- internal bypass/break-glass information;
- proprietary trade-secret implementation unless explicitly licensed.

The commercial package can include the framework, generic role schema, validators, example fixtures, public-safe runbooks and documented extension points.

## Stripe commercialization state

Stripe is the preferred direct-commerce rail for future agent/template/pallet packages, but **no live product or price is activated by this documentation patch** because an exact public price and package license have not yet been adopted. The machine package template therefore carries:

```json
{
  "stripe": {
    "product_id": null,
    "price_id": null,
    "checkout_enabled": false,
    "price_status": "not_authorized"
  }
}
```

The recommended first commercial shape is a **one-time digital license through Stripe Checkout**, with later optional bundles, update/support subscriptions, enterprise licensing and implementation services. Activation must follow the normal [Product Release Workflow](/workflows/product-release), [Payment & Fulfillment](/commerce/payment-and-fulfillment), license/rights review and protected-download entitlement controls.

## Audience projections

The same institutional record is projected differently by audience:

- **Founder/executive:** roadmap role, risks, economics, gates and portfolio opportunity.
- **Operator:** schedule, permissions, runbook, escalation and recovery.
- **Developer:** source templates, schemas, APIs/MCPs, validators, extension points and test fixtures.
- **Legal/rights reviewer:** ownership, third-party licenses, attribution, distribution obligations and commercial license state.
- **Customer/licensee:** sanitized capabilities, permitted use, support/update terms and license limits.
- **Machine/agent:** stable IDs, version, dependencies, allowed/prohibited actions, evidence state and exact handoff schema.

## Definition of done for a reusable agent pack

A reusable pack is release-ready only when its stable IDs, source templates, documentation, validators, negative tests, rights/license records, third-party notices, version/changelog, rollback, package checksum and fulfillment/license terms all agree. A Stripe Product/Price record alone never makes the pack release-ready.
