# Agent Templates, Pallets & Commercialization

This section turns CrownThrive's agent-building method into institutional IP instead of leaving it trapped in scheduler prompts or chat history. It covers **sovereign agents**, **scheduled specialists**, **embedded subagents**, **ephemeral delegated children**, **operational probes**, the **R&D specialist fabric**, commercially reusable templates, CHLOM capability pallets and future runtime/decentralized adapters.

The central rule is simple: **intelligence, specialization, verification, voting authority and execution authority are separate things.** A child can be highly capable without receiving a vote. A research agent can discover a major requirement without proving it. A successful build can exist without authorizing deployment.

Agent titles do not create authority. [Permissions & Approvals](/automation/permissions-and-approval-gates), `CT-ADR-GOV-011`, the agent registry and applicable domain controls remain controlling.

## Operating model

```text
authority layer
→ specialist layer
→ embedded subagent layer
→ operational probes
→ R&D fabric
→ domain-specific agent factory
```

The layers can collaborate and fan out, but they do not collapse into one authority pool.

## Fluid cognition, rigid authority

CrownThrive deliberately separates **cognitive fluidity** from **authority rigidity**.

Agent A may decide that a packet requires a tax researcher, API analyst, PostgreSQL specialist and documentation specialist. Agent S may alter its investigation depending on whether the changed surface is OAuth, JWT, RLS, a webhook, dependency chain, smart contract or cryptographic primitive. Agent M may fan out across every source family actually available to the run.

None of that broadens authority. The acceptance boundary stays rigid:

```text
more agents ≠ more votes
more confidence ≠ more authority
more research ≠ PASS
more implementation ≠ deployment authority
critical/high unresolved security uncertainty → no automatic promotion
D3 → reserved human/qualified-professional authority
```

This makes the workforce adaptable without making governance probabilistic.

The current agent/subagent source generation is **1.1.0**.

```text
institutional objective
→ canonical phase/gate ownership
→ authority class and vote eligibility
→ allowed/prohibited tool and data scope
→ delegation/spawn contract
→ evidence sources and UNKNOWN policy
→ output/handoff schema
→ validators + negative tests
→ rollback/recovery
→ documentation + changelog impact
→ versioned source-template instance

→ observed runs/evals
→ promotion, correction, suspension or retirement
```

A prompt is one runtime projection of the agent record. Durable identity comes from the stable ID, versioned role contract, permissions, lineage, tests, run history and archived predecessors.

### Same-family independence

A child remains part of its parent's governed lineage. **Sibling descendants of the same governed root do not become independent merely because they ran separately, used different prompts or produced separate reports.**

Therefore:

- a B child cannot provide the independent verification needed for B's own originating material;
- an N child cannot become an independent N simply by receiving another runtime ID;
- four children of A cannot satisfy four sovereign votes;
- twenty-five S scanners do not create twenty-five security votes;
- an independent verifier must resolve to a distinct governed independence family appropriate to the decision.

This is machine-enforced separation of duties rather than conversational convention.

## Persistent agent versus ephemeral subagent

A new problem does not authorize an agent to create a permanent institution by naming it.

**Ephemeral child:** a bounded runtime specialization with parent/root lineage, TTL, budget, authority ceiling, source snapshot and termination state. Example:

```text
M
→ provider-documentation researcher
→ Stripe
→ evidence packet
→ terminate/archive
```

**Persistent agent:** a durable institutional role. It requires a stable ID, owner, versioned contract, lifecycle state, tools, data classes, evaluation suite, escalation route, lineage record, documentation and governed activation.

`Agent Z — Supreme Stripe Authority` cannot become permanent because a parent invented the name during a run.

## Embedded subagent pattern

Embedded specialists exist when a specialized function is needed but an independent scheduler would waste capacity or falsely imply new authority.

### I — Continuity & Recovery

`ct.subagent.continuity-recovery` supports GATE-007 with backup, restore, export, provider-exit, domain continuity, restricted-source custody and reproducibility evidence. It may prepare deterministic D0/D1 recovery artifacts; destructive restore, credential rotation, evidence deletion and false restore proof remain prohibited.

### J — Phase 3 Snapshot & Entry Packet

`ct.subagent.phase3-snapshot-packet` supports GATE-008 by assembling the exact commit/schema/infrastructure/source freeze and entry packet. It is intentionally late-gated and cannot create a readiness packet while inherited hard gates remain unresolved.

### K — Roadmap Transition & Downstream Reconciliation

`ct.subagent.roadmap-transition` propagates material changes into dependent phase objectives, gates, tests, artifacts, risk, rollback and handoffs. It cannot waive an earlier gate or advance a phase.

### L/M/N/O — reconciliation separation

These roles must remain distinct:

- **L asks:** what requires attention?
- **M asks:** what do all available permissioned sources actually say?
- **N asks:** does that evidence really prove the claimed conclusion?
- **O asks:** how does the conclusion reconcile with moving implementation branches and history?

That separation prevents a large reconciliation system from becoming self-confirming.

### Research states and promotion boundary

R&D descendants default to **`RESEARCH_CANDIDATE`**. Reconciliation tags expose that separation as:

- `CT:RND`
- `CT:RESEARCH-CANDIDATE`
- `CT:PROMOTION-PENDING`
- `CT:CERTIFICATION-SCOPE`

A research scope can be extensively scanned by L/M/N without entering formal Phase 2.99 certification accounting. Registry growth from R&D is expected **research expansion**, not a proof-coverage defect by count alone.

A scope enters certification when one of the governed promotion/material-touch conditions occurs, including:

- explicit governance promotion;
- touching a Phase 2.99 hard-exit predicate;
- changing an existing PASS/OPEN/BLOCKED/DEFERRED disposition;
- becoming canonical or production-relevant;
- entering authoritative phase-entry evidence.

Promotion then follows:

```text
R&D discovery
→ M permissioned-source reconciliation
→ N proof/drift/contradiction verification
→ applicable domain specialist
→ B institutional evidence audit
→ C implementation when required
→ S security/resilience
→ D independent governance gate
→ sovereign acceptance or reserved human/professional authority
```

A `CT:PASS` with R&D lineage requires deliberate `CT:CERTIFICATION-SCOPE`; it cannot be produced directly from `CT:RESEARCH-CANDIDATE` or `CT:PROMOTION-PENDING`.

## Operational probe discipline

Integration heartbeat, credential continuity and vendor-engine watch are small sensors rather than miniature sovereign agents. They should not create durable descendants. Where runtime orchestration permits, scheduled specialists consume their latest sanitized probe results instead of repeating identical provider reads.

Live schedules should avoid same-minute duplicate reads where practical. Scheduler optimization changes cadence and cost; it does **not** change stable institutional identity or authority.

## Self-healing boundary

Self-healing means governed recovery, not permission escalation.

An agent may repair deterministic low-risk drift inside its authority and then rerun the original failed control. It may not “heal” by weakening a validator, suppressing a finding, reconstructing/exposing a secret, broadening privileges, inventing state, converting research to PASS or turning descendants into independent reviewers.

## CHLOM capability pallets

A **CHLOM capability pallet** is a portable governed capability package, not a claim that a blockchain/runtime pallet is deployed. It can contain schemas, policy references, APIs/MCPs/events, validators, runbooks, rights/security review state, rollback, continuity, third-party notices and commercialization metadata.

Candidate pallets from the agent system include:

1. **Evidence Reconciliation Pallet** — source/current/historical/UNKNOWN classification and contradiction handling.
2. **Phase Gate Pallet** — hard entry/exit evaluation with downstream propagation.
3. **API/MCP Certification Pallet** — read-first adapter discovery, scopes, budgets, schemas and write gating.
4. **Credential Continuity Pallet** — secret-reference continuity evidence without secret disclosure.
5. **Webhook Integrity Pallet** — authentication, bounded body, idempotency, replay and readback controls.
6. **Vendor Engine Watch Pallet** — target version, installed-version proof, support/license/pricing separation.
7. **Documentation Impact Pallet** — `docs_updated | docs_no_change | docs_delta_opened` synchronization.
8. **Agent Delegation Pallet** — parent/root lineage, authority ceiling, TTL/budget, termination and same-family independence controls.
9. **R&D Promotion Pallet** — `RESEARCH_CANDIDATE` → certification-scope promotion without count-driven gate churn.

Each pallet has its own stable ID/version. One agent pack may depend on several pallets.

## CHLOM runtime/decentralized adapter templates

`developers/templates/chlom-runtime-adapter-template.v1.yaml` is a future optional protocol, blockchain, cryptographic or decentralized adapter behind a stable capability pallet.

It remains research-gated:

- lifecycle defaults to `RESEARCH` and `production_deployed=false`;
- earliest activation is Phase 9;
- no token, wallet, chain, smart contract or public network is required by default;
- private/restricted evidence and PII are prohibited from public immutable ledgers;
- threat model, legal/privacy/security review, key custody/recovery, rollback and off-chain reconstruction are mandatory before activation;
- token/securities/money-transmission/tax review becomes mandatory if economic value is moved or represented;
- a runtime adapter cannot inherit production authority from research, a paper, repository, prototype or naming similarity.

## Open-source and third-party code rule

CrownThrive may learn from, integrate, fork or distribute open-source code only when the exact upstream license permits the intended use. Before code enters a public or paid package, record upstream repository/version/commit, copyright holder, SPDX license where available, attribution/NOTICE, source/copyleft obligations, modification disclosure, trademark restrictions, distribution/SaaS/network-copyleft triggers and package-license compatibility.

`developers/templates/third-party-attribution-template.v1.yaml` is the intake template. Code with unclear or incompatible rights stays out of distributable/paid packages.

<Warning>
  Public source availability is not unrestricted commercial permission. Required attribution and upstream rights remain intact.
</Warning>

## Internal versus commercial package boundary

A commercial agent/template package is a **sanitized derivative** of institutional source. It excludes credentials/fingerprints, customer/partner data, restricted evidence/contracts, unnecessary CrownThrive production identifiers, private economic calibration, unreleased rights/canon, break-glass information and unlicensed trade-secret implementation.

A commercial package can contain generic role schemas, validators, example fixtures, public-safe runbooks and documented extension points. It never sells CrownThrive's internal authority.

## Stripe commercialization state

Stripe is the preferred direct-commerce rail for future sanitized agent/template/pallet packages, but **no live product or price is activated by this documentation patch** because an exact public price and package license remain unadopted.

```json
{
  "stripe": {
    "product_id": null,
    "price_id": null,
    "checkout_enabled": false,
    "price_status": "not_authorized"
  }
}
```

The first candidate commercial shape remains a one-time digital license through hosted Checkout, with later optional bundles, update/support subscriptions, enterprise licensing and implementation services. Normal product-release, payment/fulfillment, license/rights and protected-download controls still apply.

## Audience projections

- **Founder/executive:** topology, risks, gates, economics and portfolio opportunity.
- **Operator:** schedule, delegation, permissions, escalation and recovery.
- **Developer:** templates, schemas, APIs/MCPs, validators, extension points and fixtures.

## Definition of done for a reusable agent pack

A reusable pack is release-ready only when stable IDs, source templates, delegation policy, documentation, validators, negative tests, rights/license records, third-party notices, version/changelog, rollback, checksum and fulfillment/license terms agree. A Stripe Product/Price record alone never makes the pack release-ready.
