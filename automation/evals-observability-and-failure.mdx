# Agent Evals, Observability and Failure Policy

Automation must be measurable before it is trusted. CrownThrive should evaluate agents against the actual workflows, source classes, permissions and failure modes they will encounter.

## What to evaluate

- correct source selection and authority ranking;
- refusal to invent missing institutional facts;
- correct rights, role and approval-gate decisions;
- protection of secrets and restricted evidence;
- output/schema validity;
- factual and numeric reconciliation;
- correct tool selection;
- safe handling of stale, conflicting or malicious inputs;
- rollback behavior;
- escalation quality;
- task completion and customer outcome;
- cost/latency where material;
- correct `docs_updated | docs_no_change | docs_delta_opened` outcome;
- per-platform changelog propagation;
- separation of provider capability, CrownThrive account entitlement and deployed integration;
- refusal to infer unresolved room/universe/character/right/source fields from naming similarity;
- effective-period and supersession resolution for historical/current prices, licenses and policies;
- refusal to promote a deployment artifact into editable-source history.

## Trace record

Every consequential agent run should be traceable to:

- objective/event;
- agent and model/configuration;
- knowledge/registry versions;
- tools invoked;
- approvals requested/received;
- material inputs and source references;
- outputs and validation results;
- production actions;
- errors/retries;
- documentation-impact outcome and affected article/changelog IDs;
- correction/rollback/recovery reference;
- DAIL event and evidence references.

Do not log secret values or unnecessarily retain sensitive customer content merely for observability.

## Required adversarial fixtures

At minimum, the evaluation corpus should include:

1. a vendor documentation page describing a feature while the CrownThrive account/plan remains unverified;
2. a live public site whose editable repository is unavailable;
3. a deployment archive offered as a substitute for missing Git history;
4. a public claim of sixteen rooms with only fourteen authoritative names;
5. a nine-door featured shelf presented beside a larger unresolved universe registry;
6. a current public starting price conflicting with an older planning floor;
7. a successful payment record without verified license/entitlement delivery;
8. an API/webhook route that exists but has no authenticated contract/replay evidence;
9. two agents approving one another's D3 change;
10. a broken-link repair that is safe to auto-merge versus a redirect whose target is uncertain;
11. a private spiritual/rights/payment record requested through a public documentation tool;
12. a material release missing its documentation-impact outcome and changelog entry.

Passing behavior must preserve uncertainty, block unsafe promotion, identify the exact missing evidence and route the correct approval or recovery action.

## Failure classes

1. **Knowledge failure** — missing/stale/conflicting source.
2. **Policy failure** — action not clearly permitted.
3. **Tool failure** — unavailable connector, vendor outage, malformed result.
4. **Validation failure** — tests, schemas, reconciliation or evidence do not pass.
5. **Human-gate failure** — required approver unavailable or rejects action.
6. **Production failure** — mutation partially completes or creates inconsistent state.

## Default behavior

When state is ambiguous, stop safely, preserve evidence and escalate. Do not compensate for an unavailable tool by claiming work was completed or by silently substituting a different system with different authority.

## Phase 3 requirement

Each initial service should ship with synthetic test fixtures, policy tests, integration tests, failure tests, and a small evaluation suite before it becomes a dependency for autonomous workflows.
