# Runbook productization and institutional knowledge commercialization

CrownThrive treats repeatable operational knowledge as an institutional asset. When an automated task, agent workflow, release procedure, evidence loop, recovery routine, or technical operating method becomes sufficiently repeatable, it should be evaluated for conversion into a **sanitized developer runbook, template, eBook chapter, training module, or licensed capability package**.

This is a productization contract. It does not turn private operations into public documentation and it does not authorize pricing or checkout by itself.

## Core rule

Every automated workflow must receive one of these productization dispositions:

- `PRODUCTIZE_PUBLIC_SAFE` - the pattern can be generalized without exposing CrownThrive-specific restricted material;
- `PRODUCTIZE_LICENSED` - useful implementation detail may be distributed only under an approved license;
- `PRODUCTIZE_TRAINING_ONLY` - suitable for education/examples but not as an implementation package;
- `PRIVATE_PATTERN_ONLY` - the workflow is too dependent on credentials, private evidence, customer data, security internals, personal information, or trade-secret know-how to distribute;
- `RIGHTS_REVIEW` - publication or commercialization waits for ownership, third-party, patent, trademark, privacy, or contractual review.

A source automation can remain private while a generalized runbook derived from its pattern is sellable.

## Non-negotiable isolation boundary

The following never enter a public or customer-facing runbook unless a separately governed disclosure explicitly permits the exact material:

- API keys, tokens, webhook secrets, signing secrets, recovery material, private keys, or Vault secret bodies;
- credential fingerprints or production secret-reference topology when it materially increases attackability;
- customer, partner, employee, family, legal, health, financial, school, or other personal case data;
- private DAIL/evidence bodies, provider payloads, account identifiers, private repository identifiers, internal incident details, or security findings;
- raw sovereign-voter instructions, unrestricted master-agent prompts, private authority mappings, or production identities;
- proprietary calibration, scoring weights, defensive detection logic, adversarial corpora, private evaluation sets, or trade-secret algorithms;
- patent-candidate technical mechanisms before invention/IP review;
- third-party copyrighted or licensed material beyond the rights granted for redistribution.

Encryption and restricted storage are not a publication license. Protected material remains protected even when a sanitized derivative is created.

## Productization pipeline

```text
automation / operating method
        ↓
pattern extraction
        ↓
IP + rights + privacy + security classification
        ↓
public-safe abstraction or licensed implementation boundary
        ↓
runbook + checklist + templates + machine manifest
        ↓
technical validation / negative tests
        ↓
Drive master + repository source + docs projection
        ↓
commercial offer lifecycle
        ↓
concept -> candidate -> packaged -> rights_cleared
        -> pricing_authorized -> fulfillment_certified
        -> checkout_staged -> live
```

## Required runbook anatomy

A commercializable developer runbook should contain:

1. Problem and intended operator.
2. Preconditions and authority boundary.
3. Inputs and expected outputs.
4. Step-by-step workflow.
5. Evidence/observability contract.
6. Failure classes and recovery path.
7. Security, privacy, IP, and rights cautions.
8. Rollback or fail-closed behavior.
9. Verification checklist.
10. Reusable templates or machine-readable schema where useful.
11. Version, changelog, support scope, and compatibility assumptions.
12. Commercialization state and explicit exclusions.

## Derivative-product rule

One automation may create several products without duplicating secrets or protected implementation detail:

- **Quick Runbook** - concise operator procedure.
- **Developer Edition** - schemas, examples, validators, and integration notes.
- **Team Pack** - checklist, incident worksheet, evidence packet, and role matrix.
- **eBook Chapter/Volume** - explanatory narrative, architecture, and worked generic examples.
- **Training Lab** - controlled exercises with synthetic fixtures.
- **Licensed Implementation Pack** - only after rights, security, license, support, and fulfillment certification.

## Repository and Google Drive custody

Repository source is the governed version-controlled implementation/documentation record. A durable master copy must also be placed in the approved Google Drive institutional-products library using the naming convention:

`CrownThrive_[Workstream]_[Artifact-Type]_[Short-Title]_[YYYY-MM-DD]_v#`

Repository history and Drive custody complement each other; neither silently replaces the other.

## Stripe boundary

Developer runbooks and eBooks are digital goods. The preferred simple payment surface, once commercial gates are satisfied, is a one-time hosted Stripe Checkout or Payment Link for individual products and bundles; recurring support may use a subscription later.

No agent may invent an exact price, create a live Price, enable checkout, or issue customer entitlement merely because a runbook exists. Product, price, license, tax/accounting, refund, fulfillment, support, and entitlement controls remain separate.

## Automation continuity

When a recurring CrownThrive automation is created or materially changed, Agent A should route a productization impact check. Agent C may build a sanitized derivative. Agent F controls public-safe source projection. Agent B independently audits evidence and rights. Agent S checks secret/security leakage. Agent D remains the independent gatekeeper for governed promotion. These activities create no new sovereign voter.

A routine run that produces no method change does not require a new product revision. A change to method, control boundary, schema, evidence class, recovery behavior, or reusable implementation pattern does.
