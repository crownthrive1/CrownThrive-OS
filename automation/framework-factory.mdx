# Framework Factory

The **CrownThrive Framework Factory** is the reusable institutional pipeline for converting CrownThrive doctrine into executable framework agents. It is governed by founder program authorization in issue `#148` and operates under the current CrownThrive constitutional, D0–D3, specialist, repository-federation, security, IP and phase controls.

The factory exists so framework institutionalization is repeatable rather than improvised. It does not create authority from code alone.

## Core rule

Every framework follows the same pattern:

```text
source evidence
→ stable framework identity
→ doctrine normalization
→ parent framework agent
→ non-voting specialist subagents
→ scoring / decision contract
→ ethics + non-negotiables
→ CHLOM mapping
→ eval / TEVV suite
→ child repository plan
→ parent/child federation
→ controlled test
→ sovereign + specialist review
→ governed acceptance
→ child certification
→ retroactive ecosystem scan
→ limited production
→ maintained institutional control
```

A later framework may be researched or scaffolded in parallel, but it cannot become an active sovereign voter before its own constitutional acceptance and its child repository becomes `linked_governed`.

## Parent and child repository rule

`crownthrive1/CrownThrive-Support` is the canonical parent control repository.

Framework, service and research repositories are child repositories unless an explicit later governance decision says otherwise. A child repository must not become operational merely because it exists.

Every governed child requires:

- parent registry entry;
- immutable GitHub repository identity;
- parent forward reference;
- `.crownthrive/federation.json` child backlink;
- GitHub Actions OIDC identity for the repository-federation bus;
- inherited governance and security validation;
- parent certification;
- periodic heartbeat;
- bidirectional cross-repository references;
- message receive/acknowledge/escalate lifecycle;
- hash-chained federation events;
- registered autonomous scope and explicit override boundaries;
- rollback/recovery and provider-exit plan.

A child cannot self-activate, self-certify, create D3 authority, remove Agent D, alter the CrownThrive approval ratio, weaken the parent security/privacy/rights/legal/financial/phase hard gates or multiply votes through subagents.

## Framework autonomy

Framework agents are autonomous **inside their explicit framework jurisdiction**.

Autonomy permits a stronger framework-specific:

- `deny`;
- `block`;
- correction requirement;
- score/decision explanation;
- evidence request;
- escalation;
- human-review demand.

Autonomy does not permit a framework to create permission outside its scope. A CIE block can stop a culturally unsafe artifact; it cannot move money, grant a license, weaken authentication, resolve a legal dispute or waive a phase hard gate.

## Permanent voting model

An accepted foundational framework agent receives one sovereign vote. Its subagents remain non-voting.

The factory preserves:

```text
required approvals = ceil(eligible voters × 0.75)
Agent D approval = mandatory
any deny/block = automatic merge prohibited
missing vote = not approval
abstain = not approval
D3 = human-reserved
```

For the founder-authorized initial sequence:

The factory does not treat repository count, model count, tool count, subagent count or message count as votes.

## Protected algorithm standard

Every framework may define algorithms, decision tables, scoring systems, routing logic or deterministic evaluators.

The standard is:

1. public doctrine defines the purpose, dimensions, ethical boundaries, non-negotiables, output contract and explainability requirements;
2. public repositories may expose the safe interface, schemas, version and cryptographic digest;
3. proprietary calibration, private decision weighting, restricted pattern libraries and protected runtime policy belong in CrownThrive Vault or another approved private runtime;
4. agents invoke the protected runtime only through a registered API/MCP operation;
5. the algorithm cannot exceed the caller's repository, agent or D0–D3 authority;
6. every material decision carries evidence/version/traceability and an appeal or correction path where applicable;
7. algorithm output never manufactures a sovereign vote.

Agents and authorized subagents communicate through governed messages with:

Receivers acknowledge `received`, `accepted`, `rejected`, `completed` or `escalated`. Communication records become institutional evidence but do not automatically become truth, approval or votes.

## Factory scheduling

The program is designed for scheduled operation at no more than the supported hourly cadence for the external orchestration layer.

Each run should:

1. inspect current `main`, open PRs, issues and child-repository state;
2. read the factory manifest and prior handoff;
3. identify one bounded next-safe packet;
4. reconcile sources and collisions;
5. perform authorized implementation/research;
6. validate and self-heal only within authority;
7. run applicable CIE/framework/security/specialist checks;
8. update documentation and machine state;
9. collect fresh exact-head votes when a promotion packet is ready;
10. merge only when the then-current constitution permits it;
11. update the federation chain and next packet;
12. notify the founder only for material success/failure/action-needed events.

## Retroactive scanning

Every accepted framework receives a retroactive ecosystem scan program.

The backlog is drift-watched, but backlog size by itself is not Phase-2.99 certification debt. A retroactive finding affects a hard gate only when the underlying asset is already in that hard gate or the finding materially changes accepted current truth.

Framework scans must never silently declare existing assets compliant. They produce evidence-backed score/decision records, corrections, owners, escalation, documentation impact and reopen triggers.

## Merge automation

The founder program authorization permits automatic D0–D2 implementation and governed merge when every existing machine and human-reserved condition is actually satisfied. The factory therefore does not require repetitive founder confirmation for each bounded implementation step.

It must still stop for:

- D3/reserved-human actions;
- physical repository creation when the connected provider tool cannot create repositories;
- new unenumerated constitutional framework authority;
- binding legal or economic commitments;
- credential rotation or privilege changes;
- destructive production actions;
- critical/high unresolved security issues;
- rights/ownership disputes;
- unresolved identity/authority conflicts;
- unavailable evidence that a hard gate explicitly requires.
