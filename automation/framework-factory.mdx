# Framework Factory

The **CrownThrive Framework Factory** is the reusable institutional pipeline for converting CrownThrive doctrine into executable framework controls. Founder program authorization is tracked in issue `#148`. The Factory remains subject to the accepted constitution, D0–D3 boundaries, specialist review, repository federation, security, IP classification, hard-exit and roadmap controls.

The Factory makes institutionalization repeatable. **Code, documentation, a repository, an OIDC identity, a framework identity, a successful CI run, `sync_agents`, or child certification does not create sovereign authority.**

## Current constitutional boundary

The accepted sovereign voter pool remains:

```text
A / B / C / D / S
current eligible voters = 5
required approvals = 4
Agent D = mandatory
any deny/block = automatic promotion prohibited
missing/abstain = not approval
D3 = human-reserved
```

Framework parents, framework subagents, child repositories and transport identities are **non-voting by default**. A framework may become a sovereign voter only through a separate accepted constitutional packet under the then-current constitution. Framework acceptance or child certification alone does not change `N`.

Every registered CrownThrive agent must honor the Factory contract when materially touching a framework.

## Parent and child repository rule

`crownthrive1/CrownThrive-Support` is the canonical parent control repository.

A child repository must not become operational merely because a name, registry row or repository exists. Every governed child requires:

- physical GitHub repository identity;
- parent registry entry and immutable repository ID;
- parent forward reference;
- `.crownthrive/federation.json` child backlink;
- GitHub Actions OIDC bootstrap for the federation audience;
- inherited governance and security validation;
- Agent-D parent certification under the current contract;
- heartbeat;
- bidirectional references;
- message receive/acknowledge/escalate lifecycle;
- hash-chained federation events;
- registered autonomous scope and override boundaries;
- rollback/recovery and provider-exit plan.

A child cannot self-activate, self-certify, create D3 authority, remove Agent D, alter the approval ratio, weaken parent hard gates or multiply votes through subagents.

## Protected algorithm standard

Public repositories may contain only public-safe doctrine, dimensions, thresholds, schemas, hard-block interfaces and digests. Proprietary calibration, weights, defensive rules, private eval corpora and restricted runtime policy remain in Vault or another approved private runtime and are invoked only through governed API/MCP/federation paths.

If the required private runtime or registered digest is unavailable, the correct state is **HOLD**. Do not duplicate protected logic into the public repository as a workaround.

Algorithm output never manufactures a sovereign vote and cannot exceed the caller's registered authority.

## IP and commercialization

The permanent `#131` IP gate applies before publication, licensing or customer packaging. PUBLIC_STANDARD/PUBLIC_DOCTRINE surfaces may use public-safe material. COPYRIGHT_LICENSED output requires explicit rights. TRADE_SECRET_CANDIDATE/CONTROLLED, PATENT_CANDIDATE, RESTRICTED_INSTITUTIONAL, private economic/policy calibration, proprietary eval corpora, credentials/fingerprints and private evidence remain excluded from public/customer outputs. Unresolved classification is HOLD.

Factory commercialization may prepare candidate manifests, validators, templates, training/service scopes and fulfillment designs. It does not invent or activate exact prices, Stripe Product/Price, checkout, certification status or customer entitlement.

## Retroactive scans

Accepted frameworks receive a retroactive ecosystem scan contract. Scans never silently declare existing assets compliant. They produce evidence-backed decisions, corrections, owners, escalation, documentation impact and reopen triggers.

Registry or research growth alone does not force a new hard-exit reconciliation sweep. A finding affects a hard gate only when the underlying asset is already in that gate or the finding materially changes accepted current truth.

## Scheduling and merge boundary

Each Factory run should resolve current `main`, open PR heads, hard-exit state, Factory/federation state, Mintlify and connected runtime state; select one bounded eligible packet; validate collisions and protected-IP boundaries; perform only authorized D0–D2 preparation/implementation; obtain independent verification and applicable specialist review; and merge only when the then-current governance permits it.

The Factory must HOLD for D3/reserved-human work, missing required evidence, unprovisioned child repositories, unresolved critical/high security issues, rights/ownership disputes, binding legal/economic commitments, privilege/credential changes outside accepted scope or any attempt to bypass the authorized sequence.
