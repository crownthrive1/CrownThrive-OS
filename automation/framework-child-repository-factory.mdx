# Framework child repository factory

The **Framework Child Repository Factory** is the repository-provisioning layer beneath the CrownThrive Framework Factory. It turns an accepted framework repository plan into a repeatable child-repository scaffold without allowing repository creation, CI, OIDC, automation or generated files to manufacture institutional authority.

Program authority remains issue `#148`. This packet is stacked on the active CIE parent packet, PR `#145`.

A child is never operational merely because files were copied or workflows passed.

Required pre-operational evidence includes:

- physical GitHub repository existence;

- exact child backlink contract;
- GitHub Actions OIDC identity;
- inherited security and governance checks;

## GitHub self-sustain layer

Each child receives two bounded workflows.

### Bootstrap workflow

The bootstrap workflow:

- validates the child contract;
- requests GitHub Actions OIDC with audience `crownthrive-repository-federation`;
- attempts only the narrow federation `bootstrap` action;
- has no child-certification, `sync_agents`, provider-write, customer-write or voting capability.

If the parent fleet manifest says `bootstrap_allowed=false`, bootstrap fails closed.

### Governance workflow

The child governance workflow runs on pull requests, pushes, manual dispatch and a framework-specific hourly minute.

It:

- compiles and validates child controls;
- verifies federation registration through OIDC on non-PR runs;
- emits a heartbeat only after the child contract is explicitly operational;
- checks whitespace/conflict markers;
- opens or updates one idempotent internal governance-drift issue when the validation job fails;
- closes that drift issue after deterministic recovery.

Drift issue routing is an operational repair surface, not a sovereign vote, framework certification or parent acceptance.

### Dependency upkeep

Each child receives Dependabot configuration for daily GitHub Actions update proposals. Update PRs remain subject to child and parent governance. There is no direct-to-`main` dependency repair and no automatic merge.

## Protected algorithms

Child repositories may contain safe schemas, interfaces, dimensions, thresholds, hard-block contracts and public digests where their IP classification allows it.

They must not copy protected calibration, weights, proprietary recurrence/confidence logic, private evaluation corpora, defensive detection rules, restricted evidence or credential material out of the governed private runtime merely to make the repository self-contained.

Unavailable private runtime/digest state means `HOLD`.

## Parent-side governance

The parent `Framework Child Fleet Governance` workflow runs on changes to the fleet controller/templates and, after acceptance to the default branch, hourly at minute `:42`.

It validates:

- exact eight-framework sequence;
- one-at-a-time bootstrap eligibility;
- predecessor linkage;
- non-voting and D3 locks;
- pinned Node-24-compatible Actions references;
- child workflow permission ceilings;
- CIE rendered bootstrap bundle;
- Convergent rendered scaffold-only bundle;
- current next-safe child action.

It does not create repositories, certify children, open provider accounts, create votes or merge its own work.

## Rollback / reopen

Rollback is a straight revert of this additive fleet packet. A rendered child scaffold can be removed by closing its unmerged bootstrap PR or reverting its bootstrap commit.

Reopen when:

- a planned child becomes physically visible;
- a GitHub repository ID changes or contradicts the registry;
- OIDC/bootstrap fails;
- parent certification changes;
- a workflow permission broadens;
- a protected-IP classification changes;
- predecessor acceptance/certification changes;
- the CrownThrive constitution changes.

Phase 2 / 2.99 remains current. This repository-factory work does not open Phase 3.
