# Framework repository governance standard

Every CrownThrive foundational framework repository is a **governed child** of `crownthrive1/CrownThrive-Support`.

A framework repository is separate for implementation custody, isolation, testing, private evidence and productization. It is not a separate constitutional authority. Its autonomy begins only after parent certification and exists only inside its registered framework authority.

## Required child contract

Every framework child must carry `.crownthrive/federation.json` with at least:

```json
{
  "contract_version": "1.0.0",
  "repo_id": "ct.repo.<framework>",
  "repo_role": "framework_child",
  "parent_repo_id": "ct.repo.crownthrive-support",
  "parent_repository": "crownthrive1/CrownThrive-Support",
  "framework_id": "ct.framework.<framework>",
  "governance_state": "provisioned_unlinked",
  "child_self_activation": false,
  "parent_certification_required": true
}
```

The exact child repository ID, GitHub repository ID, contract digest and parent contract digest are bound during bootstrap/certification.

## Inherited controls

A child must inherit or reference the current parent rules for:

- D0-D3 authority;
- sovereign voter eligibility and quorum;
- mandatory Agent D gatekeeping;
- applicable specialist activation;
- no self-approval of originating material changes;
- evidence/source hierarchy;
- documentation impact and changelog continuity;
- security, dependency and secret handling;
- Node-24-compatible/full-SHA GitHub Actions policy where Actions are used;
- rollback/recovery and incident handling;
- public/private/restricted projection boundaries;
- parent-child federation and Vault policy.

A child may use stricter rules. It may not silently weaken inherited parent minimums.

## Agent communication

Every registered CrownThrive agent is eligible to use federation transport from a governed repository when its task and data permissions allow. Repository communication uses the federation API/MCP/script interface rather than copying private credentials between repositories.

Framework subagents continuously exchange findings, work assignments, corrections, evidence references, escalation notices and liveness heartbeats through the parent-governed bus. Communications are audit records, not sovereign votes.

A framework agent's sovereign vote is accepted only when that framework agent is present in the active parent constitution and its child repository remains `linked_governed`.

## Framework autonomy

A framework may own a deterministic rule engine, evaluator, algorithms, subagents, schemas, tests and remediation workflow. It may independently return a stricter domain result inside its explicit authority, including:

- PASS/REVIEW/HOLD/FAIL under its own framework standard;
- deny/block;
- require correction;
- require evidence;
- assign registered remediation agents;
- escalate to Agent D or human authority.

A framework cannot reinterpret an explicit domain override as permission to exceed the framework's registered scope.

## Non-negotiable parent locks

Child repositories cannot override:

```text
constitutional_governance
d3_human_authority
security_privacy
rights_legal
money_movement
repository_federation
vault_secret_policy
phase_hard_gates
```

These keys remain parent-controlled even when a framework is a sovereign voter.

## Algorithms and Vault

Each protected framework algorithm uses two layers:

1. **public contract** — identity, version, dimensions/inputs, output schema, public thresholds/ethics, hard invariants, runtime action and public contract digest;
2. **restricted implementation** — proprietary calibration, private detection logic, model/eval assets and other protected IP stored only in approved private implementation/Vault surfaces.

The public Support repository must not contain the sealed algorithm bundle. Agents call protected algorithms through the federation runtime, which resolves the approved Vault bundle and returns only permitted output.

Algorithm invocation never grants more authority than the caller already has.

## Repository creation and activation

A new framework repository must be created under CrownThrive custody and remain inert until all of the following are true:

- parent forward registration exists;
- child backlink exists;
- GitHub immutable repository ID is captured;
- OIDC bootstrap succeeds;
- parent and child contract digests are recorded;
- required governance/security files exist;
- exact-head validators pass;
- applicable agents/specialists approve;
- parent certification changes state to `linked_governed`;
- post-certification heartbeat succeeds.

A missing step cannot be replaced with a chat assertion or a repository name.

## Framework voter expansion

A framework child does not gain a vote merely because it exists. The framework agent becomes vote-eligible only after:

1. explicit founder authorization;
2. governed constitutional adoption;
3. machine contract and evaluation suite;
4. child repository parent certification;
5. exact voter identity registration.

Subagents never increase the voter denominator.

For accepted foundational framework agents, the standing quorum formula remains `ceil(N × 0.75)` plus mandatory Agent D unless a later founder-approved constitutional decision changes it.

## Suspension

Parent governance may suspend a framework child on material security, rights, custody, integrity, evidence, federation, continuity or authority violation. Suspension disables operational federation authority without deleting institutional history.
