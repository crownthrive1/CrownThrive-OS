The **Perpetual Institutional Lifecycle** is CrownThrive's governed method for turning generated capability into durable institutional capability rather than one-off output.

```text
CREATE → TEST → IDENTIFY → SECURE → PRESERVE
      → DOCUMENT → REUSE → PRODUCTIZE → MONITOR → CONTINUE
```

<Warning>
  “Perpetual” means perpetual **candidate and institutional capability continuation**, not perpetual authority expansion. D3 remains human-reserved. Production activation, protected-body publication, final rights/entitlements, checkout, money movement, provider-write widening, sovereign votes and automatic canonical merge remain separately governed.
</Warning>

## Ten-stage contract

| Stage | Institutional purpose | Required boundary |
| --- | --- | --- |
| **Create** | Produce the exact governed candidate capability/package with deterministic identity and rollback-aware public/private separation. | Originator work is candidate-only. |
| **Test** | Run deterministic, negative-authorization, runtime/syntax, failure-injection and regression tests. | Originator cannot certify itself. |
| **Identify** | Assign stable IDs, semantic version, SHA-256, public fingerprints, package membership, provenance and DAIL/DID linkage. | Private identity mappings remain restricted. |
| **Secure** | Enforce least privilege, Vault/secret separation, privacy/IP containment, RLS/access boundaries and adversarial review. | Authority ceiling stays fixed. |
| **Preserve** | Create recovery custody, exact cryptographic readback, append-only ThriveBase/DAIL lineage and tested rollback/recovery. | Upload without readback is not preservation PASS. |
| **Document** | Project public-safe contracts, interfaces, lifecycle state, evidence digests and recovery rules. | No protected bodies, keys or credentials. |
| **Reuse** | Register dependency, callable capability, interoperability and agent bindings. | Reuse cannot expand original authority. |
| **Productize** | Package capability as candidate licenses, API/MCPs, managed agents, workflows, services and pricing hypotheses. | Candidate packaging does not activate commerce. |
| **Monitor** | Verify agents, schedules, bindings, DAIL, custody, drift, health, security and dependencies. | Monitoring is evidence, not self-certification. |
| **Continue** | Route the next due candidate and maintain the candidate horizon. | Current generation must independently satisfy the lifecycle before successor promotion. |

## Current generation starts unproven

The lifecycle runtime has ten stage definitions but **zero current lifecycle receipts** in the latest readback. That is intentional fail-closed behavior.

A live runtime does not imply a current generation has passed the lifecycle. Generation 48 must accumulate its own stage evidence. An older generation's PASS cannot be inherited.

```text
runtime exists ≠ current generation certified
policy active ≠ production authority
candidate horizon ≠ scheduled work due now
asset exists ≠ commercially activated product
```

## Estate-size agnostic design

The lifecycle contract does not define CrownThrive by one permanent asset total or terminal generation. Runtime state is resolved from ThriveBase at execution time.

Current public factory records may describe 48 completed generations and a 100K-plus protected asset estate, while the active continuation policy separately governs future candidate generations. These are related but different state dimensions.

## Independent agent mesh

The lifecycle uses originator/verifier separation. Current external relay roles remain cross-service verification and continuation lanes:

- Agent A — orchestration and continuation;
- Agent B — evidence and independent verification;
- Agent C — bounded build/document/reuse preparation;
- Agent D — independent final candidate gate;
- Agent S — security/resilience verification;
- Integration Heartbeat — monitoring and runtime drift;
- Credential Continuity — preservation/custody verification.

Internal factory agents remain non-voting unless a separate constitutional record explicitly says otherwise.

## Refill and continuation rule

The current active policy already preserves a candidate horizon through generation 60. No documentation or agent should shrink that governed ceiling merely because an older public contract described five-generation refill increments.

When a future refill is required, it may change candidate planning capacity only. It cannot change D2/D3 limits, provider-write authority, production state, rights/entitlements, checkout, money/Crown Credits, protected-body publication or canonical merge authority.

## Activation and continuation gates

Before a successor generation may advance, current evidence must establish, as applicable:

1. current active policy and predecessor history;
2. ten stage definitions;
3. append-only lifecycle receipts and mutation rejection;
4. exact current generation/package identity;
5. no inherited PASS from older generations;
6. owner/verifier separation;
7. no more than one due/executing generation;
8. future planned work does not count as active until due;
9. rollback/recovery state;
10. DAIL verification;
11. no production, checkout, money movement, final-rights or D3 authority leakage.

## Documentation continuity

Every material lifecycle change must pass the [Documentation Reconciliation & Continuity Framework](/standards/documentation-reconciliation-continuity-framework), update the [Framework and Engine Registry](/doctrine/framework-engine-registry) when framework identity/state changes, and preserve public/private boundaries under [Security, Privacy and Continuity](/technology/security-privacy-continuity).
