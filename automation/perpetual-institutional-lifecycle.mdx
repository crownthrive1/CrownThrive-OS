# ThriveInstitutionalize™ perpetual institutional lifecycle

The institutional achievement is not merely that the factory can generate more assets. The architecture is designed to know how to:

**Create → Test → Identify → Secure → Preserve → Document → Reuse → Productize → Monitor → Continue**

what it creates while remaining inside a fixed authority envelope.

<Warning>
  “Perpetual” means perpetual **candidate and institutional capability continuation**. It does not mean perpetual authority expansion. D3 remains human-reserved; production activation, protected-body publication, final rights/entitlements, checkout, Stripe, money/Crown Credits, provider-write widening, sovereign votes, and automatic canonical merge remain outside this lifecycle.
</Warning>

## The ten-stage loop

| Stage | What the architecture must know how to do | Required boundary |
| --- | --- | --- |
| **Create** | Produce the exact governed candidate capability/package with deterministic identity and rollback-aware public/private separation. | Originator work is candidate-only. |
| **Test** | Run deterministic, negative-authorization, runtime/syntax, failure-injection, and regression tests. | Originator cannot certify itself. |
| **Identify** | Assign stable IDs, semantic version, SHA-256, public fingerprints, package membership, provenance, and DAIL/DID linkage. | Private identity mappings stay restricted. |
| **Secure** | Enforce least privilege, Vault/secret separation, privacy/IP containment, RLS/access boundaries, and adversarial review. | Authority ceiling stays fixed. |
| **Preserve** | Create encrypted recovery custody, exact Drive cryptographic readback, append-only THIVEBASE/DAIL lineage, and tested recovery/rollback. | Upload without readback is not preservation PASS. |
| **Document** | Project public-safe contracts, interfaces, lifecycle state, evidence digests, and recovery rules. | No protected bodies, keys, or credentials. |
| **Reuse** | Register dependency, callable capability, interoperability, and agent bindings. | A completed artifact becomes composable institutional capability rather than a one-off. |
| **Productize** | Package reusable capability as candidate licenses, API/MCPs, managed agents, workflows, services, and pricing hypotheses. | Candidate packaging does not enable live commerce. |
| **Monitor** | Continuously verify cron, agents, bindings, DAIL, custody, drift, health, security, dependencies, and no-production/no-commerce invariants. | Monitoring evidence is independently verified. |
| **Continue** | Route the next due candidate and maintain the candidate horizon. | Current generation must independently pass the lifecycle; continuation creates no new authority. |

## Estate-size agnostic by design

ThriveInstitutionalize v1.1.1 deliberately does **not** hard-code a permanent generation count, asset total, internal fleet size, or terminal generation.

Live THIVEBASE is canonical for runtime state. Every material run resolves:

- the current active factory policy;
- current completed generation;
- current generation/package identity;
- current active factory fleet;
- current internal and external scheduler/binding topology;
- current custody/DAIL state; and
- current lifecycle receipts.

A newer public-safe projection may advance faster than an older implementation review packet. That is a **reconciliation signal**, not permission to manufacture PASS. If live THIVEBASE readback is unavailable, newer runtime facts remain HOLD/UNKNOWN until independently reconciled.

Most importantly, a current generation never inherits lifecycle PASS merely because an older generation passed.

## Evergreen continuation

The perpetual contract uses **five-generation refill increments** instead of a permanent terminal generation.

If an existing governed policy already authorizes a larger candidate range, that range is preserved rather than shrunk or deleted. At the next horizon boundary, another five candidate generations may be added only when the **live current generation** has current independent PASS evidence for all ten lifecycle stages.

Refill changes the candidate planning ceiling only. It never changes:

- D2 maximum automated authority;
- D3 human reservation;
- non-voting/no-self-approval factory status;
- provider-write authority;
- production activation;
- protected-body publication;
- rights or entitlement authority;
- checkout/Stripe state;
- money/Crown Credits authority; or
- canonical merge authority.

`HOLD`, `FAIL`, or `UNKNOWN` stops continuation rather than being coerced to PASS.

## Per-generation receipts

Each stage produces append-only institutional evidence tied to the exact generation/package, stage, originator/owner, independent verifier where required, evidence digest, authority envelope, and supersession lineage.

A newly activated lifecycle runtime starts the current generation at `UNKNOWN` unless **that current generation** already has valid lifecycle receipts. The migration does not bootstrap current PASS from the earlier G10/20K estate or from any other historical generation.

## Independent agent mesh

The live internal fleet is resolved dynamically by capability/class. The existing seven external scheduled roles remain the cross-service verification and continuation mesh without adding scheduler slots:

- **Agent A** — orchestration, activation recovery, and Continue;
- **Agent C** — bounded Create plus Document/Reuse/Productize evidence construction;
- **Agent B** — independent Create/Test/Identify/Document/Reuse verification;
- **Agent S** — independent Secure/Monitor verification;
- **Agent D** — independent Productize/Continue final candidate gate;
- **Integration Heartbeat** — Monitor evidence and runtime drift; and
- **Credential Continuity** — independent Preserve verification.

Originator and verifier must differ for stages requiring independent verification.

## Activation readback requirements

Before evergreen runtime can be called live, independent evidence must show:

1. an active evergreen successor policy with predecessor policy history preserved;
2. exactly ten lifecycle stage definitions;
3. append-only lifecycle receipts and mutation rejection;
4. current generation/package resolved from live THIVEBASE;
5. current-generation state `UNKNOWN` unless current-generation receipts exist;
6. no older-generation PASS inheritance;
7. exact owner/verifier separation and supersession validation;
8. max one due/executing generation;
9. future planned work does not count active until due;
10. predecessor/current-generation lifecycle PASS is required before successor enqueue;
11. any larger already-governed current ceiling is preserved;
12. future horizon refills add five only from current-generation 10/10 PASS;
13. internal lifecycle tables/functions remain inaccessible to public API roles;
14. orchestrator no-work calls remain idempotent;
15. DAIL verifies after activation; and
16. production, protected publication, checkout/Stripe, money/Crown Credits, final rights/entitlements, authority self-expansion, and D3 remain disabled.

## Why this is the real achievement

Generation creates inventory. Institutionalization creates **continuity**.

The factory becomes materially more valuable when it can preserve not just what was produced, but the knowledge of how to build it, prove it, identify it, protect it, recover it, explain it, compose it, package it, watch it, and safely create the next governed generation.

That is the mechanism that allows CrownThrive capability to compound without allowing scale to outrun institutional authority.
