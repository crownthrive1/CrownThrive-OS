# Documentation Source-of-Truth & Autonomous Governance Standard

## Status

- **Standard ID:** `ct.standard.docs-autonomy.v1`
- **Adopted during:** Phase 2.98
- **Applies to:** CrownThrive humans, agents, Codex tasks, LLM workflows, APIs, MCP servers, websites, services, platforms, projects, repositories, manifests and institutional publications
- **Change rule:** append, version, reconcile and preserve; never silently rewrite source history

## Institutional truth model

CrownThrive documentation is the **sole governed institutional source of truth for approved meaning**: canonical names, stable IDs, architecture, policy applicability, rights state definitions, operating standards, approved public claims, phase gates, product/capability state, version relationships and institutional decisions.

Operational systems remain authoritative evidence for transactions and runtime facts they originate. Stripe remains authoritative for processor objects; Git remains authoritative for commits; application databases remain authoritative for their live operational records; monitoring remains authoritative for observed health. Those systems feed evidence into the institutional record. They do not become competing doctrine.

```text
source / runtime evidence
        ↓
verification + authority classification
        ↓
institutional registry + version/correction graph
        ↓
approved documentation projection
        ↓
API / MCP / agent / human consumption
        ↓
implementation + telemetry
        ↓
drift detection and correction loop
```

If implementation and approved documentation disagree, the mismatch becomes a governed incident. An agent must not simply choose the more convenient state.

## Mandatory documentation impact contract

Every material code, configuration, product, price, license, route, API, model, prompt, domain, vendor, metric, policy, rights, content, universe, room, platform or operational change must produce one of three outcomes:

1. `docs_updated` — affected records/articles/changelog are updated in the same change set;
2. `docs_no_change` — a reviewed declaration explains why institutional meaning did not change;
3. `docs_delta_opened` — a governed documentation task is created and the release remains gated when the missing update could mislead users, operators, agents or developers.

A successful build with stale institutional documentation is not a complete release.

## Governance-as-code enforcement tiers

CrownThrive distinguishes **automated governance monitoring** from **automated governance enforcement**.

- `monitoring_only` — a validator can detect a violation and emit `FAIL`, but repository settings still allow a human or automation identity to place the change on `main` without that check being a mandatory merge condition.
- `merge_gate_enforced` — the repository's effective branch/ruleset policy requires the designated institutional validation check to succeed before a pull request can merge to `main`.
- `post_merge_revalidation` — the canonical branch is independently revalidated on push to `main` as defense-in-depth. This detects configuration bypass, provider drift or a merge-path defect after the fact; it does not substitute for a pre-merge required check.
- `policy_transition_enforced` — future machine registries validate permitted state transitions so unsupported promotion such as `unverified → production_verified`, `historical → current`, or `provider_capability → CrownThrive_deployed` is rejected by executable policy.

The institutional target is **fail-closed merge enforcement plus post-merge revalidation**, not validation logs alone.

## Article and page version standard

Every substantive article/page should converge on: stable content/article ID; canonical title and aliases; corridor/platform/category; article type and audience; recovery class; authority tier; source/evidence references; institutional content version; effective and last-verified dates; current/historical/superseded/archived/draft status; owner/steward; related platform/service versions; rights/legal/economic applicability; predecessor/successor relationships; correction/retraction history; public/gated/restricted projection; automation eligibility; and review interval.

Page-title changes do not destroy identity. Stable IDs survive renames and redirects.

## Recovered article program

The recovered legacy Help Center includes a 795-title inventory. Articleization does **not** wait for Phase 3.

- **Phase 2.98:** create and reconcile substantive P0/P1 institutional and support articles now while source recovery is active.
- **Phase 2.99:** complete the formal Help Center Articleization & Projection seed. Every recovered title receives a stable ID, disposition and source state. P0/P1 customer/operator/developer/legal categories receive substantive versioned bodies or an explicit `source_not_recovered` record. Navigation, redirects and article manifests become machine-readable.
- **Phase 3:** generate/synchronize API, MCP, schema and developer documentation from executable contracts and continue normal product/support article updates from governed change events.
- **Phases 4–10:** ecosystem activation, revenue/market proof, external licensing/developer economy, phygital/regional expansion, Holdings/capital scale, advanced interoperability and generational-continuity changes use the same article/update contract.

No missing body may be fabricated merely to achieve a numeric completion target.

## Highest-current-value rule

When multiple values exist, agents use the highest **current** value only when records share the same metric definition, population, unit, deduplication rule and period logic and stronger current evidence supports the larger value.

Do not use “highest number wins” across different scopes. Platform count, portfolio-asset count, software-engine count, domain count, registered profiles, verified profiles, active accounts, visitors and members are separate metrics. Older values remain versioned historical snapshots.

## Documentation change classes

### D0 — observational

No mutation. Search, compare, detect drift and generate an evidence packet.

### D1 — low-risk reversible documentation

Typo, deterministic broken link, metadata normalization, verified redirect, timestamp, formatting and source-reference changes may be auto-applied when required validators pass and rollback is trivial.

### D2 — bounded institutional update

Verified platform capability state, current vendor version, route inventory, non-legal product metadata, source-backed changelog and registry relationships may be approved by a delegated Documentation Steward when evidence meets the required tier, no high-risk domain changes and independent validation passes.

### D3 — consequential institutional change

Legal terms, rights ownership/grants, economic schedules, prices with customer effect, payout destinations, authentication/authorization, privacy/data sharing, material public claims, destructive migrations, security architecture, franchise/securities posture and irreversible actions require the applicable human/reserved/legal/security/finance/rights authority. Agents may prepare, test, recommend, block and reconcile; they may not self-authorize the consequential decision.

## Agent governance hierarchy

### Documentation Sentinel — A0/D0

Read-only drift detection across live properties, source repositories, docs, APIs and registries. Detects stale counts, routes, versions, links and contradictions; opens evidence-backed deltas; cannot merge or publish.

### Documentation Steward — A1/D1–bounded D2

Repairs low-risk docs, source-backed registry state, aliases, redirects and changelogs. May auto-merge D1 after required validators pass. D2 requires an independent verifier and policy eligibility.

### Platform Registry Agent — A1/D2

Maintains platform, domain, vendor, API, capability and lifecycle records. It cannot promote `unverified` to `production_verified` without evidence.

### Catalog & Rights Metadata Agent — A1/D1–D2

Validates product files, editions, metadata, rights references and entitlement manifests; may block release on inconsistency; cannot grant rights, invent chain of title or activate a human-review license.

### Release / Website Agent — A1/D1–D2

Reconciles site changes, routes, sitemaps, metadata, support articles and changelogs; can accept subordinate low-risk checks; escalates D3 changes.

### Legal & Rights Gate — verifier/blocker

Checks applicability, source authority, assent/version state and rights conflicts. It may deny or return required changes and does not replace qualified counsel where counsel review is required.

### Security & Privacy Gate — verifier/blocker

Checks secrets/data classification, least privilege, exposure, dependencies and rollback; may force fail-closed/read-only behavior; never auto-discloses restricted evidence.

### Economic & Commerce Gate — verifier/blocker

Checks price/split/order/payment/entitlement arithmetic and sources. It cannot redirect funds or alter customer-facing economic obligations without authorized D3 approval.

### Phase Gate Agent — institutional blocker

Evaluates Phase 2.99 and institutional Phases 3–10 entry/exit criteria after every material continuation; cannot mark a phase complete merely because code exists; writes new blockers into the inherited gate rather than resetting the roadmap; and propagates changed assumptions into every affected downstream phase.

## Subordinate approval and quorum rule

A parent agent may accept lower-risk subordinate approvals only when the subordinate is authorized for that check; the check is deterministic or independently reproducible; evidence/tool results are logged; no subordinate approves its own originating mutation; required human/reserved gates are not bypassed; failed checks return specific remediation; and the final decision records which checks passed.

Two agent approvals do not transform a D3 action into D2.

## Self-checking standard

Before publish, merge or deploy, applicable workflows verify source authority/freshness, stable IDs/references, schema/frontmatter, internal/external links, stale/superseded claims, terminology/aliases, rights/legal/economic overlays, route/canonical/sitemap/robots state, accessibility, API/schema/docs consistency, test/CI status, secrets/restricted-data leakage, backup/rollback target, changelog and docs-impact state.

## Self-healing standard

Self-healing means controlled recovery, not autonomous rewriting of truth. Permitted remediation includes restoring last known good state after validation failure, deterministic link/redirect/metadata repair, bounded idempotent retries, regeneration from an unchanged approved schema, reverting a failed low-risk docs-only change, opening an incident and degrading to read-only, quarantining stale/contradictory claims, and re-running health/source checks after provider recovery.

Agents must not self-heal by deleting historical evidence, rewriting accepted legal versions, inventing missing data, fabricating runtime success or suppressing unresolved rights/security conflicts.

## Cost-aware grassroots automation

Automation should be scrappy, cheap and powerful: webhook/event driven before frequent polling; changed-file/delta processing before full-fleet scans; caching stable metadata; batching low-priority audits; GitHub Actions and free/open tooling where compatible; portable standards over lock-in; synthetic/test data before paid production calls; token/request/cost budgets; backoff on provider limits; avoidance of duplicate services; and off-provider exports for critical registries/docs.

Cost savings never authorize weaker rights, security, privacy, legal or financial controls.

## Continuous phase reconciliation

Every material continuation evaluates whether it closes or creates a Phase 2.99 seed/private-core requirement and then performs a downstream roadmap-impact check against institutional Phases 3–10. The responsible run identifies which later objectives, dependencies, hard entry/exit gates, checkpoints, acceptance tests, artifacts, authority boundaries, risks, automation duties, rollback paths or handoffs changed. Relevant future-phase documents are updated in the same checkpoint when material, or an explicit governed delta is opened. A future phase is not allowed to remain stale merely because it predates the new evidence.

## Repository and source-code integration rule

Source-code-aware docs automation may use only repositories explicitly connected to the CrownThrive organization/deployment and registered with platform, owner, branch, environment and trust scope. Until a source repository is connected, website/code documentation uses verified public behavior, exported source artifacts and authorized evidence and records the repository as `not_connected`, never `does_not_exist`.

A target hostname is not a claim that the runtime service is already deployed.

## Definition of done

A change is institutionally done only when implementation, evidence, documentation, machine records, changelog, validation, approvals, production verification where applicable, and rollback/recovery state agree.
