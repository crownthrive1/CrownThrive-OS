# Documentation Reconciliation & Continuity Framework

The **Documentation Reconciliation & Continuity Framework** is CrownThrive's governed operating framework for keeping institutional documentation current, complete, internally connected, recoverable and machine-addressable while the ecosystem continues to grow.

## Why this exists

CrownThrive's documentation estate is no longer a static help center. It represents institutional doctrine, platform intelligence, rights, commerce, governance, technical architecture, recovery history, current state, future gates and machine-readable handoff context. That means a page can become stale even when its prose remains grammatically correct.

A sprint therefore cannot stop after correcting old wording. It must also ask what the page still **does not say**, what accepted evidence it fails to reference, which other records a future operator would need, and how the page affects article reconstruction and Phase 3 entry.

## Mandatory two-pass sprint contract

### Pass A — stale-state reconciliation

For every page in scope:

1. freeze the baseline commit and page list;
2. identify stale canonical names, aliases, statuses, provider/version claims, phase references, counts, architecture assumptions and public claims;
3. resolve against the [Source Authority Hierarchy](/knowledge/source-authority-hierarchy), [Evidence, Claims and Proof Standard](/standards/evidence-claims-and-proof-standard), current registries and adopted adjudications;
4. correct only what the evidence supports;
5. preserve historical statements, literal provider identifiers and deployed legacy physical names when they remain factually necessary;
6. version material corrections under the [Versioning & Correction Standard](/standards/versioning-change-control-and-correction);
7. emit one inspectable page outcome: `docs_updated`, `docs_no_change` or `docs_delta_opened`.

### Pass B — gap closure and continuity

For the same page set:

1. identify missing source qualifiers, relationships, API/provider boundaries, legal/rights/support state, runbook references, successor/predecessor lineage, phase impacts, machine-seed requirements and article-rebuild dependencies;
2. add facts only when supported by accepted evidence;
3. add continuity links to the records a future operator or agent needs to reconstruct meaning;
4. convert unsupported assumptions into explicit unresolved records instead of prose guesses;
5. update the 795-title article-rebuild mapping where the page closes, merges or creates a documentation responsibility;
6. record Phase 3 seed/gate contribution and remaining blockers;
7. propagate relevant future-phase implications.

## Internal-link continuity contract

A substantive current page should ordinarily carry at least two meaningful internal links. Preferred link classes are:

- source authority or evidence standard;
- canonical platform/framework/portfolio registry;
- applicable legal, rights, security or commerce standard;
- phase readiness or roadmap gate;
- alias/predecessor/successor/historical lineage;
- operational workflow or runbook.

Links are not decoration. They are continuity edges in the institutional knowledge graph.

A useful continuity edge answers at least one of these questions:

- **Where did this claim come from?**
- **Which record is canonical now?**
- **What governs this capability?**
- **What happens when it fails or changes?**
- **What does this block or enable next?**
- **What historical record explains the lineage?**

## 795-title Help Center rebuild

The recovered Help Center estate contains **795 titles** in the current forensic baseline. That number is a recovery universe, not the current Mintlify page count.

Every recovered title must reach exactly one governed terminal disposition:

| Disposition | Meaning |
| --- | --- |
| `canonical_article` | substantive current article exists |
| `merged_successor` | content is incorporated into a stronger canonical article |
| `permanent_redirect` | old route points to the current successor |
| `restricted_record` | content belongs in authenticated/private knowledge rather than public docs |
| `superseded_history` | preserved as historical institutional evidence |
| `unresolved_source` | source is not sufficient to reconstruct safely |

A title, placeholder or navigation label does not count as a rebuilt article. See the [795-Article Disposition Seed](/support/help-center-795-article-disposition-seed) and [Articleization Contract](/support/articleization-manifest-and-autopublication-contract).

## Phase 3 unlock contribution

This framework does not declare Phase 3 open. It reduces documentation bottlenecks by making Phase 2.99 outputs deterministic:

```text
source / current evidence
→ stale-state reconciliation
→ gap closure
→ continuity-link graph
→ article disposition
→ machine seed delta
→ validation
→ Phase 3 readiness evidence
```

The [Phase 3 Readiness Gate](/technology/phase-3-readiness-gate) remains fail-closed until its full hard-entry conditions pass.

## Twenty-phase impact horizon

The current evidence-backed named roadmap defines Phases 1–10. The founder has now required the documentation program to preserve downstream awareness through **Phase 20**.

Phases **11–20 are therefore represented as reserved impact slots** until authoritative definitions are recovered or adopted. This framework records whether a sprint may affect those future slots, but it does not invent their names, missions or gates. See [Twenty-Phase Horizon Reconciliation](/standards/twenty-phase-horizon-reconciliation).

A sprint succeeds when it leaves the scoped documentation **more current, more complete, more internally connected, more recoverable, more machine-readable and less dependent on conversational memory**, while preserving every unresolved state that the evidence cannot safely close.
