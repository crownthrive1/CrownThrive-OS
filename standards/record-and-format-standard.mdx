# Institutional Record and Format Standard

CrownThrive records should be human-readable and machine-addressable. Prose may explain a system, but consequential systems must also have structured records.

## Required common fields

Where applicable, every governed record should support: `id`, `record_type`, `canonical_name`, `aliases`, `owner`, `corridor`, `audience`, `authority_class`, `lifecycle_state`, `implementation_state`, `legal_state`, `evidence_state`, `visibility`, `institutional_version`, `schema_version`, `effective_at`, `supersedes`, `successor`, `source_refs`, `last_verified_at`, and `review_owner`.

## ID namespaces

Use stable semantic namespaces such as `ct.asset.*`, `ct.platform.*`, `ct.framework.*`, `ct.brand.*`, `ct.imprint.*`, `ct.paper.*`, `ct.policy.*`, `ct.sop.*`, `ct.api.*`, `ct.mcp.*`, `ct.actor.*`, `ct.role.*`, `ct.right.*`, `ct.license.*`, `ct.event.*`, `ct.claim.*`, and `ct.component.*`.

Names are display attributes. IDs are institutional identity.

## Version separation

Version these independently when applicable: institutional identity, schema, service, API, policy, legal terms, content, public claim, rights, economic schedule, deployment, data migration, and model/prompt configuration.

## Audience and role

Every operational artifact must identify its intended audience: public, member, customer, creator, affiliate, developer, partner, operator, moderator, reviewer, admin, super-admin, founder/governance, counsel, finance, security, or machine-only. Audience does not itself grant authority.

## Evidence and source precedence

Records should reference the source or decision that supports them. Current founder adjudications and verified production evidence may supersede older planning documents without deleting the older lineage.

## Time rules

Use ISO-8601 timestamps for machine records. Material claims must include the period they describe. Financial, member, traffic, product, and catalog metrics must not be reused without their measurement definition.

## Standardized API envelopes

Every institutional API should support a common error model, request/trace ID, version, timestamp, actor/service identity, environment, and applicable authorization context. Consequential mutations should return the resulting DAIL/event reference.

## Standardized documentation

Every platform record should ultimately include overview, ownership, current state, audiences, roles, dependencies, API/integration profile, data classification, commerce state, legal/policy dependencies, SEO/search profile, support model, operational dashboards, recovery path, and next milestone.
