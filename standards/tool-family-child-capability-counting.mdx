# Tool-Family and Child-Capability Counting Standard

## Rule

A source may name a parent tool family and one or more productized capabilities as adjacent brands or platforms. Current CrownThrive institutional counting must not automatically treat every source label as a top-level platform.

A child capability may receive its own stable identity when it requires independent operational state, while remaining subordinate to its parent for top-level portfolio counting.

```yaml
parent_type: platform_tool_family
child_type: child_capability
relationship: capability_of
child_has_independent_operational_state: true
child_increments_top_level_platform_count: false
historical_source_label_preserved: true
```

## Required child records

A productized child capability should be independently addressable when applicable for:

- canonical host/subdomain;
- provider/engine lineage;
- version and deployment;
- API/MCP contract;
- roles and permissions;
- data and retention;
- pricing/entitlements;
- legal/privacy coverage;
- rights/provenance;
- analytics/events;
- health/heartbeat;
- backup/rollback/vendor exit.

## Source-count preservation

Later or richer manifests may add subdomains, child hosts or capability records. They must not retroactively mutate an earlier source census. Preserve the old count and attach later detail through source-backed relationship edges.

## Reference implementation

The first explicit application of this standard is the [ThriveTools family](/platforms/thrivetools-institutional-registry):

- `ct.platform.thrivetools` — parent;
- `ct.capability.thrivetools.seo` — child;
- `ct.capability.thrivetools.opt` — child.
