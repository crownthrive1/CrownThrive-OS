# External Standards Alignment Register

CrownThrive standards must be internally owned and externally interoperable. This register identifies the current external baselines that CrownThrive adopts, profiles, or monitors. It does not delegate CrownThrive governance to an outside standard, and it does not make a vendor-specific implementation permanent.

## Version-control rule

Every external standard receives a stable record with publisher, identifier, adopted version/date, CrownThrive profile, affected systems, implementation evidence, exceptions, owner, review date, and successor. References such as “follow OAuth” or “WCAG compliant” are insufficient without the exact version and evidence.

```yaml
standard_id: ct.standard.external.mcp.2026-07-28
publisher: Model Context Protocol
identifier: MCP-2026-07-28
status: adopted_profile
applies_to: [mcp_servers, mcp_clients, tool_broker, developer_platform]
owner: ct.role.security-architecture
last_verified_at: "2026-08-17"
next_review_at: "2026-11-17"
exceptions: []
evidence_refs: []
```

## MCP-specific CrownThrive controls

A protected remote CrownThrive MCP server targeting `2026-07-28` must:

1. process each request as self-describing and avoid hidden dependence on protocol sessions;
2. validate `MCP-Protocol-Version` and route/authorize with the registered method/tool identity, including `Mcp-Method` and `Mcp-Name` where applicable;
3. use `server/discover` only as an optional capability-discovery path, not a prerequisite that creates undocumented authority;
4. publish or resolve protected-resource metadata;
5. validate token issuer, audience/resource, expiry and scopes, including authorization-server issuer checks;
6. bind client credentials to the issuer that created them and prohibit cross-issuer reuse;
7. bind authorization to the exact server/resource rather than accept broad bearer tokens;
8. prohibit token passthrough to downstream platforms;
9. use exact redirect matching and PKCE where authorization-code flows apply;
10. prefer Client ID Metadata Documents or another adopted current registration pattern; treat Dynamic Client Registration as a compatibility path under deprecation review;
11. keep credentials and sensitive payment/identity data out of URLs and ordinary elicitation/input forms;
12. treat tool descriptions, resources, prompts, extensions and annotations as untrusted metadata unless the server and source are trusted;
13. use Multi Round-Trip Requests only through registered request/confirmation schemas and preserve approval evidence for consequential continuations;
14. honor cache metadata without allowing stale tool/resource catalogs to bypass version, health, entitlement or authorization checks;
15. isolate extensions and experimental MCP features behind capability, version and policy gates;
16. avoid new dependencies on deprecated roots, sampling, logging and legacy HTTP\+SSE behavior unless a documented migration exception exists;
17. test confused-deputy, authorization-server mix-up, SSRF, prompt injection, data exfiltration, replay, stale-cache, scope escalation and header-routing manipulation cases.

## Search-specific CrownThrive controls

- A `robots.txt` rule never protects private content.
- A URL blocked from crawling cannot reliably communicate `noindex`; private routes require access control and public URLs that should disappear must remain crawlable long enough for the directive to be observed where applicable.
- Structured data must describe visible, current and supported page content.
- Canonical hints, redirects, internal links and sitemap entries must agree.
- Programmatic content requires governed data, substantive user value and quality gates.
- Public claim records, not copied prose, drive cross-platform numbers, status, ownership and offer metadata.

## AI and agent assurance

AI systems are governed as socio-technical systems, not isolated models. Each material use must register purpose, audience, provider/model, data/source classes, prompt/policy version, evaluation set, known limitations, human-review boundary, incident path, cost and retirement state. CrownThrive should monitor NIST AI RMF revisions and adopt changes through a versioned ADR rather than silently changing controls.

## Accessibility evidence

Conformance claims require page/component scope, WCAG version and level, automated results, manual keyboard/screen-reader review, known exceptions, remediation owner and test date. A passing scanner alone is not proof of conformance.

## Supply-chain evidence

Critical CrownThrive releases should resolve source commit, dependency lock, builder/workflow identity, artifact digest, provenance, tests, approval and deployment event. Public documentation builds may use a lower assurance profile than CHLOM rights, identity, finance or evidence services, but every profile is explicit.

## Review cadence

- security/authorization standards: quarterly and on material revision;
- MCP specification: at every supported protocol-version change;
- search-platform guidance: monthly automated watch plus deployment checks;
- accessibility: at design-system release and material interface change;
- AI standards: quarterly and on NIST/profile revision;
- supply chain: at CI/CD or builder change.

A newer external version is not automatically adopted. The standards steward opens a compatibility record, evaluates changes, updates tests and issues a CrownThrive patch or ADR.
