<Info>
  **Audience:** documentation operators, developers, auditors, product owners, and governance reviewers.

  **This standard:** defines when CrownThrive may say documentation is present, reconciled, published, current, or strong across all required surfaces.

  **Documentation state:** `reconciled`. This standard governs documentation evidence; it does not expand runtime, provider, legal, financial, rights, credential, publication, or D3 authority.

  **Review trigger:** any change to the canonical source hierarchy, required documentation surfaces, publication provider, documentation ledger, or public-readback contract.
</Info>

## Purpose

PentaDocs is CrownThrive's institutional documentation control plane. It turns governed source truth into human-readable, machine-readable, auditable, versioned, and publishable records across the Convergent Ecosystem.

A claim that something is "documented everywhere" is valid only when the required surfaces for that asset or architecture are known, updated, and read back. Presence in one Google Doc, one database table, one repository file, or one public page is not cross-surface parity.

## Core doctrine

```text
SOURCE PRESENT
≠ RECONCILED
≠ REVIEWED
≠ MERGED
≠ DEPLOYED
≠ PROVIDER READ BACK
≠ PUBLICLY CURRENT
≠ RUNTIME CERTIFIED
```

Documentation state must remain separate from runtime and authority state.

- A page may be editorially documented while the underlying system is not production-certified.
- A runtime may be healthy while public documentation is stale.
- A repository change may be complete while public deployment is still pending.
- A provider readback may prove publication while not proving legal, rights, payment, or product eligibility.

## Canonical source hierarchy

When sources disagree, resolve them in this order unless a system-specific contract explicitly states otherwise:

1. **Current provider/runtime readback** for mutable deployed state.
2. **Canonical DAIL event and terminal receipt** for material institutional actions and corrections.
3. **Governed database ledgers and registries** for current structured state, lineage, and reconciliation.
4. **Accepted repository source and exact commit** for versioned public-safe documentation and code-adjacent contracts.
5. **Governed Drive records** for institutional books, phase records, source packs, evidence workbooks, and human-readable continuity.
6. **Public PentaDocs/help-center projection** after deployment and provider readback.
7. **Historical documents** as lineage, not current-state authority unless explicitly reaffirmed.

No lower source silently overrides a higher current source. Conflicts are recorded and resolved; they are not erased.

## Required surface classes

The exact set depends on the asset, but a major CrownThrive architecture, product family, framework, phase, or institutional release should evaluate these classes:

| Surface class | Minimum record | Strong-state evidence |
| --- | --- | --- |
| Runtime | Current tables, functions, providers, schedulers, or deployed artifact | Exact current readback with observation time |
| DAIL | Material event, correction, release, or terminal receipt | Event ID, sequence/hash or equivalent canonical readback |
| Structured ledgers | PentaDocs change, delta, reconciliation, CHLOM, IP/asset, phase, or product ledger | Current row, stable identity, status, evidence hash |
| Repository | Public-safe MDX, schemas, manifests, changelog, or runbooks | Exact branch/commit and review/merge state |
| Drive | Canonical human-readable document, evidence workbook, phase book, or archive | File ID, version/revision, parent folder, accountable title |
| Public docs | PentaDocs/Mintlify or help-center route | Deployed route plus provider/public readback |
| Product/publication | Go Flipbooks, storefront, downloadable package, or customer guide where required | Exact asset/package and destination readback |
| Support | Help-center article, incident/runbook, owner/admin guide, or escalation path | Discoverable current route and accountable owner |

A private architecture may intentionally omit public or product surfaces. That omission must be explicit, not accidental.

## Documentation state vocabulary

Use these states consistently:

| State | Meaning |
| --- | --- |
| `DISCOVERED` | A relevant source or artifact was found but not yet reconciled. |
| `SOURCE_PRESENT` | The requested source exists and is identifiable. |
| `EXTRACTED` | Relevant content was read into a governed work packet. |
| `CONFLICT` | Sources materially disagree or authority is unclear. |
| `RECONCILED` | Conflicts and lineage are resolved against the current source hierarchy. |
| `DOCUMENTED` | The required human and machine records are written. |
| `REVIEWED` | Accountable review or governed automated validation completed. |
| `MERGED` | Repository change is accepted into the designated release branch. |
| `DEPLOYED` | The documentation provider accepted the intended release. |
| `PROVIDER_READBACK` | The deployed destination returned the expected version/content. |
| `PUBLIC_CURRENT` | Public-safe content matches the accepted current generation. |
| `SUPERSEDED` | A newer record replaces current use while preserving history. |
| `RETIRED` | The surface or artifact is intentionally inactive and non-restorable except by explicit governance. |
| `HOLD_*` | A named evidence, authority, provider, rights, security, or review prerequisite is missing. |

Do not convert a `HOLD` to `PASS` by weakening the requirement or hiding the missing evidence.

## PentaDocs evidence envelope

Every material documentation projection should carry or resolve:

```json
{
  "stable_id": "...",
  "title": "...",
  "subject_type": "architecture|platform|product|release|runbook|standard|asset",
  "source_refs": ["..."],
  "source_authority": "runtime|DAIL|ledger|repository|Drive|historical",
  "source_version": "...",
  "content_sha256": "...",
  "documentation_state": "RECONCILED",
  "runtime_state": "separate value or null",
  "authority_state": "separate value or null",
  "repository_ref": "owner/repo@commit or PR",
  "drive_file_ids": ["..."],
  "public_routes": ["..."],
  "provider_readback": "PASS|HOLD|NOT_APPLICABLE",
  "conflicts": [],
  "supersedes": ["..."],
  "accountable_owner": "...",
  "observed_at": "...",
  "next_review_trigger": "..."
}
```

Hashes must cover the intended source material, not volatile observation timestamps unless the timestamp is itself part of the claim.

## Cross-surface release sequence

A strong documentation release follows this order:

1. **Discover and bind sources.** Resolve the exact architecture, asset, release, or product identity.
2. **Read current state.** Retrieve runtime/provider evidence where the claim is mutable.
3. **Preserve history.** Archive prior source, file revision, or page version before material replacement.
4. **Reconcile contradictions.** Keep a contradiction or adjudication record when sources disagree.
5. **Draft human and machine projections.** Maintain equivalent meaning across prose, tables, schemas, and manifests.
6. **Validate documentation contracts.** Check frontmatter, links, navigation, private/public boundaries, stable IDs, and evidence references.
7. **Update governed ledgers.** PentaDocs change, delta, reconciliation, CHLOM phase/release, IP/asset, or product ledgers as applicable.
8. **Commit repository source.** Record branch, commit, and pull-request state.
9. **Deploy through the documentation provider.** Do not call a repository branch "public" before deployment.
10. **Read back the destination.** Verify route, title, version, content, links, and access behavior.
11. **Append release evidence.** Record DAIL or the applicable terminal evidence receipt.
12. **Update continuity records.** Document what changed, what remains, and the next review trigger.

A failure at steps 8–10 does not invalidate the source documents; it leaves public parity in an explicit hold state.

## PentaDocs operating responsibilities

PentaDocs should coordinate, not manufacture authority.

### PentaDocs owns

- source discovery and provenance;
- document architecture and audience framing;
- human/machine parity;
- version, supersession, and correction lineage;
- repository and Drive projection;
- documentation validation;
- publication-state and readback tracking;
- cross-surface reconciliation ledgers;
- continuity and next-review records.

### PentaDocs does not own

- legal approval or professional opinion;
- rights, ownership, or licensing grants;
- payment, settlement, treasury, or token decisions;
- credential creation or rotation;
- production deployment authority outside its explicit release contract;
- provider facts without provider readback;
- runtime certification by documentation confidence alone.

## Current PentaDocs control surfaces

The current institutional implementation includes:

- a governed Drive folder for PentaDocs source and publication records;
- a Mintlify-compatible repository source named **PentaDocs**;
- `integration_control.penta_docs_change_ledger_v1`;
- `integration_control.penta_docs_delta_registry_v1`;
- `integration_control.penta_docs_reconciliation_ledger_v1`;
- recurring delta projection, reconciliation, observation, configuration-watchdog, and site-enrichment jobs;
- DAIL-compatible change and release evidence;
- master phase, CHLOM, DAIL, and IP/asset ledgers.

These surfaces form one documentation fabric. They are not interchangeable copies: each has a distinct role and must preserve stable cross-references.

## Public and restricted information

Public PentaDocs may include architecture, operating contracts, public-safe schemas, user/developer guides, support procedures, release notes, and bounded evidence summaries.

Keep restricted:

- plaintext credentials, secrets, tokens, private keys, or signing material;
- private customer or member records;
- privileged exploit detail;
- proprietary scoring internals not approved for publication;
- restricted legal or rights evidence;
- private provider account identifiers where disclosure is not required;
- personal data and protected institutional evidence.

Public omission does not mean the evidence does not exist. Use stable restricted references and access-controlled records.

## Cross-surface parity checks

Before claiming "strong everywhere," verify:

- Drive source exists in the intended folder.
- Repository source contains the current generation.
- Navigation or a discoverable canonical entrypoint reaches the page.
- Links resolve.
- PentaDocs change/delta/reconciliation ledgers contain the release.
- CHLOM and DAIL phase/release records are updated where applicable.
- Master IP/asset registry includes newly created durable documentation IP.
- Public deployment is merged and provider-read back, or explicitly marked pending.
- Product guides, Go Flipbooks, support pages, or download packages are updated where the release requires them.
- Historical versions remain preserved and marked superseded rather than silently overwritten.

## Failure and recovery

| Failure | Required response |
| --- | --- |
| Source conflict | Preserve both sources; record conflict; route adjudication. |
| Repository update without deployment | Mark `MERGED` or `SOURCE_READY`; do not claim `PUBLIC_CURRENT`. |
| Deployment without exact readback | Mark `DEPLOYED_PENDING_READBACK`. |
| Public page stale | Preserve current source; open correction; avoid using public prose as runtime authority. |
| Broken links/navigation | Repair source; validate; redeploy; read back. |
| Restricted data exposed | Preserve incident evidence, remove public exposure, rotate affected credentials where authorized, and document the correction. |
| Historical document contradicts current state | Keep it as historical; add supersession and current-source references. |
| Missing product/support projection | Record an explicit destination hold and owner rather than calling parity complete. |

The DAIL Cursor-Controlled Capacity Mesh is a reference implementation of this contract. Its current documentation estate includes:

- runtime Cursor, continuity, MeshAssist, capacity-mesh, verification, and donor records;
- canonical DAIL releases and terminal readbacks;
- a Drive master ledger, complete compendium, evidence/publication workbook, phase books, diagrams, and recovery records;

## Acceptance checklist

- [ ] Stable subject identity is resolved.
- [ ] Current source authority is stated.
- [ ] Mutable claims have current readback.
- [ ] Historical sources are preserved.
- [ ] Contradictions are recorded and reconciled.
- [ ] Human and machine projections agree.
- [ ] Restricted information is excluded from public source.
- [ ] Drive and repository records are linked.
- [ ] Required master ledgers are updated.
- [ ] Documentation state is separate from runtime and authority state.
- [ ] Repository review/merge state is recorded.
- [ ] Deployment state is recorded.
- [ ] Public/provider readback is recorded.
- [ ] DAIL or terminal evidence is appended for material release.
- [ ] Remaining holds and next review triggers are explicit.
