# Versioning, Change Control and Correction Standard

CrownThrive uses versioning to preserve institutional truth, prove how decisions evolved, prevent silent overwrites, and allow humans and machines to resolve the correct state for a specific date, audience, platform, agreement, asset, or transaction.

The human patch label and four-part machine release identify the same governed change from different namespaces. Neither may be substituted for the other in machine records.

## CrownThrive four-part institutional release number

Use `EPOCH.PROGRAM.AUDIT.PATCH` for institutional-program releases.

| Segment | Meaning | Example in `2.7.9.1` |
| --- | --- | --- |
| `EPOCH` | broad institutional generation or recovery epoch | `2` = recovery and institutionalization era |
| `PROGRAM` | major workstream or operating program family | `7` = exhaustiveness/governance-preparation family |
| `AUDIT` | cumulative reconciliation, maturity or control pass | `9` = late pre–Phase 3 control baseline |
| `PATCH` | correction, expansion, re-audit or hotfix within that baseline | `1` = first patch |

This is **not** a replacement for service semantic versions. APIs, schemas, policies, economic schedules, documents, models, deployments, content and datasets keep their own version namespaces.

## Change classes

| Class | Use | Minimum control |
| --- | --- | --- |
| `editorial` | grammar, formatting, non-substantive clarity | author \+ diff |
| `factual_correction` | wrong date, name, metric, state, owner or description | evidence \+ reviewer \+ affected-claim list |
| `source_reconciliation` | competing sources resolved by authority rules | conflict record \+ decision \+ lineage |
| `founder_adjudication` | reserved institutional decision | founder record \+ effective date |
| `policy_amendment` | operating or legal-policy change | authority \+ acceptance/applicability analysis |
| `security_hotfix` | urgent risk reduction | incident ID \+ restricted details \+ post-review |
| `schema_migration` | record/data contract change | migration \+ compatibility \+ rollback |
| `economic_amendment` | pricing, commissions, royalties, splits or allocations | schedule version \+ effective window \+ approval |
| `rights_amendment` | ownership, permissions, restrictions or licenses | rights evidence \+ affected grants \+ remedy plan |
| `retraction` | content/claim withdrawn because it should not remain active | reason \+ replacement/notice \+ preserved history |
| `supersession` | a newer canonical record replaces an older one | predecessor/successor links |
| `rollback` | return execution to a verified earlier state | rollback reason \+ data reconciliation |
| `recovery_patch` | reconstructed content added after loss | recovery source \+ confidence \+ non-verbatim label |

## No-silent-overwrite rule

A material accepted record is append-only. Corrections create a new version and preserve:

1. prior value;
2. corrected value;
3. reason;
4. source/evidence;
5. actor and authority;
6. effective timestamp;
7. affected systems and audiences;
8. migration/rollback action;
9. public notice requirement;
10. DAIL event reference.

## Audit and re-audit rules

An audit may identify gaps without changing the canonical record. A re-audit patch may change records only when it documents the delta from the previous pass. Every audit release must publish:

- scope;
- source set and source-snapshot identifier;
- methods and tool/model versions where material;
- findings;
- records added, changed, corrected, withdrawn or deferred;
- contradictions and adjudications;
- risk accepted and accepting authority;
- validation evidence and failed checks;
- acceptance criteria;
- release status: `draft`, `candidate`, `accepted`, `superseded`, `withdrawn` or `void`;
- next inherited baseline.

A statement made during an audit is not canonical merely because it appears in a report. It becomes canonical only through the applicable accepted record, correction, adjudication or release decision.

## Audit-correction rule

Audits themselves are correctable institutional objects. When an audit finding, grade, source interpretation or standards reference is later shown to be wrong:

1. preserve the original finding and the evidence available at that time;
2. open an audit-correction record;
3. state the corrected finding and stronger source;
4. identify downstream pages, decisions and scores affected;
5. recalculate dependent conclusions where material;
6. publish the correction in the same or a more visible channel than the original claim when public reliance is plausible;
7. link both versions through the correction graph.

This rule applies to human and machine audits, including CrownThrive site reviews, legal-policy inventories, source-recovery assessments, model evaluations and automated compliance checks.

## Version-vector rule

A four-part institutional release number is only one coordinate. Consequential records must carry a **version vector** so a future agent can reconstruct exactly what governed an action without assuming that every subsystem changed together.

```yaml
release_context:
  program_phase: "2.97"
  institutional_release: "2.7.9.1"
  record_version: 4
  schema_version: "1.2.0"
  policy_version: "3.1"
  api_contract_version: "2026-08"
  mcp_contract_version: "2026-07-28"
  seo_profile_version: "2.0"
  deployment_ref: "git:sha-or-release-id"
  evidence_snapshot: "ct.snapshot.01J..."
```

No service may infer that two records share legal, technical, economic or content state merely because they were published in the same institutional release.

## Patch-number advancement

- Increment `PATCH` for a correction, re-audit, evidence refresh, hotfix or compatible expansion that preserves the same audit baseline.
- Increment `AUDIT` when the cumulative control/reconciliation baseline itself changes materially.
- Increment `PROGRAM` when the work enters a distinct institutional program family rather than merely extending the current one.
- Increment `EPOCH` only for a deliberately adopted institutional generation boundary with a migration plan.
- Never renumber an already accepted release to make history look cleaner.
- A skipped number remains skipped and may carry a reserved/void record explaining why.

The human-facing phase label and machine release number are separate fields. `Phase 2.97` may therefore produce `2.7.9.0`, `2.7.9.1`, `2.7.9.2`, and later patches without pretending the program phase itself changed.

## Effective-dated agreements and policies

Legal terms, licenses, economic schedules and accepted policies require immutable effective-dated snapshots in addition to version numbers. Store the exact rendered or signed artifact, hash, locale, applicability inputs and acceptance/grant evidence. A later policy version must not be retroactively substituted for the artifact that governed an earlier transaction unless the applicable law/agreement and recorded amendment permit it.

## Derivative and transformation lineage

When an agent, human or service transforms a source into a summary, dataset, public projection, API response, model input, derivative work or generated artifact, record the source IDs, transformation policy/tool/model version, resulting asset ID, reviewer/approval where required and visibility class. A derivative never silently becomes the authority for its own source.

## Public corrections

Public corrections require proportionate notice when the prior statement materially affected rights, money, legal status, eligibility, safety, privacy, public trust, purchasing decisions or institutional reputation. Minor editorial changes do not require a public correction banner, but remain visible in version history.

## Content-addressed and decentralized future

The canonical version graph should be capable of being independently verified without making decentralized infrastructure an MVP dependency. Phase 3 should therefore preserve deterministic hashes/content digests for consequential immutable artifacts and event envelopes where technically appropriate.

Later CHLOM implementations may add signed attestations, transparency logs, Merkle roots, verifiable credentials, DID-bound authority, replicated registries or external/decentralized anchors. Those proofs must reference the same CrownThrive stable IDs, predecessor/successor graph, policy context and effective dates. An anchor proves that a representation existed or was attested; it does **not** by itself prove ownership, legal validity, truth, consent, authorization or current applicability.

Decentralization strengthens verification and resilience; it does not replace correction, appeal, privacy, legal authority, access control or human-readable history.

## Gate

No Phase 3 service may implement mutable institutional records without this version graph, correction envelope and event trail.
