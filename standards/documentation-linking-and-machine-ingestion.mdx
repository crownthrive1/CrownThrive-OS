# Documentation Linking and Machine-Ingestion Standard

CrownThrive documentation is simultaneously institutional memory, human guidance, public-safe explanation, search infrastructure, and machine-ingestible knowledge. A page is not complete merely because its prose is accurate. It must be findable, related to the rest of the knowledge graph, appropriately structured for its audience, evidence-aware, accessible, and reusable by governed machines.

## Universal page contract

Every substantive CrownThrive page should make the following answerable without requiring a reader or model to infer them:

- what the object, concept, policy, platform, paper, or process is;
- who it is for;
- why it exists;
- whether it describes current, historical, proposed, target, deferred, or retired state;
- how it integrates with adjacent CrownThrive systems;
- what evidence or authority supports consequential claims;
- what the risks, dependencies, and limitations are;
- what a reader should do next;
- where related canonical pages live.

Pages serving different audiences may project different levels of detail, but they should resolve to the same stable institutional identities and state dimensions.

## Internal-linking rule

**Internal linking is mandatory for every substantive page unless a machine-declared leaf exception is justified.**

Each page should contain contextual links to at least:

1. one upstream or governing record when applicable;
2. one adjacent concept, platform, standard, or workflow;
3. one downstream implementation, runbook, registry, or next-step record when applicable.

Links must be semantically useful. Do not create repetitive keyword links merely to manipulate search ranking. Prefer descriptive anchor text that tells humans and retrieval systems why the target matters.

New pages must not become orphans. A new page should be linked **from at least one existing navigated or otherwise canonical page** before promotion, or carry an explicit pending-navigation dependency with an owner and integration target.

When a page is renamed, merged, superseded, or moved, update internal links and preserve redirects/canonical lineage under the existing search and migration standard.

## Long-form and table-of-contents rule

A visible table of contents is required when a page meets either of these conditions:

- five or more substantive H2 sections; or
- approximately 1,200 words or more of explanatory body content.

Short pages may omit a manual table of contents when headings remain obvious and navigation is not improved by one.

Long-form documents should use a predictable hierarchy:

```text
H1 — one page title
  H2 — major reader questions or system areas
    H3 — implementation details, variants, controls, examples
      H4 — only when truly necessary
```

Do not skip heading levels merely for visual styling.

## Standard page structure

Select the sections that apply, but preserve this semantic order where practical:

1. **Summary / Purpose**
2. **Who this is for**
3. **Current state and authority**
4. **Why it matters**
5. **Architecture / relationships / integration**
6. **Implementation or operating method**
7. **Risks and controls**
8. **Evidence / sources / claims**
9. **Approvals or decisions required**
10. **Metrics / validation / observability**
11. **Related pages**
12. **Next action or inherited baseline**

Research and paper pages additionally identify research question, methods/source set, alternatives, unresolved questions, current-vs-target boundary, and paper/research version.

Developer pages additionally identify interface version, authentication class without secret material, input/output contracts, side effects, errors, idempotency/concurrency behavior, tests, and rollback/compensation.

## SEO, AIO and documentation discovery

This standard extends the [Search, SEO, AIO, Metadata, Robots and Sitemap Standard](/standards/search-seo-metadata-robots).

Authoring guidance:

- use one unique intent-driven title per page;
- use a specific description that accurately describes the page instead of repeating the site name;
- write headings around reader questions and system concepts, not keyword stuffing;
- use canonical terminology and stable aliases naturally in the body;
- link related entities so the CrownThrive knowledge graph is traversable;
- include explicit current/historical/proposed labels so AI retrieval does not collapse time states;
- provide useful summaries near the top of long pages;
- avoid thin programmatic variants and duplicated pages;
- maintain language/locale metadata when localization is introduced;
- preserve canonical/redirect relationships through migrations.

Metadata length is a quality target, not an authority rule. When practical, public documentation titles should be concise enough to scan in search/navigation and descriptions should be specific enough to summarize the page without truncating its central meaning.

## Diagrams, graphs and code

Use diagrams or graphs when they reduce ambiguity in architecture, lifecycle, risk, data-flow, economic-flow, protocol, or dependency explanations. A visual must have an accompanying text explanation so the knowledge remains useful to screen readers and machine consumers.

Preferred diagram uses include:

- Mermaid for portable architecture, state, sequence, and relationship diagrams;
- generated charts backed by governed data for metrics/trends;
- explicit tables when exact comparison matters more than visual shape.

Code examples must:

- use language-tagged fenced blocks;
- distinguish example, pseudocode, prototype, test fixture, and production code;
- avoid credentials, secret fingerprints, private endpoints, or restricted evidence;
- state version/runtime assumptions when material;
- link to the canonical contract or implementation when one exists;
- avoid presenting historical CHLOM code concepts as deployed current state.

Solidity, smart-contract, cryptographic, blockchain, and token examples are research/prototype artifacts unless the relevant implementation and authority records say otherwise.

## Machine-ingestion contract

Pages intended for MCP, LLM, search, or agent reuse should expose predictable semantic fields through frontmatter, body structure, or a companion machine record:

```yaml
stable_id: ct.doc.example
record_type: documentation
state:
  lifecycle: maintained
  implementation: documented
  authority: adopted_standard
as_of: 2026-08-19
audiences: [human, operator, developer, machine]
source_refs: []
related_ids: []
current_claim_refs: []
```

Machine-facing companion records should prefer normalized fields over forcing downstream models to parse consequential state from prose. At minimum, machine output should preserve:

- stable ID and version;
- authority/current-state classification;
- as-of date;
- source/evidence references;
- affected entities/relationships;
- claims and confidence/evidence class;
- risks/blockers;
- recommendations separately from adopted decisions;
- approvals required;
- related canonical routes;
- correction/supersession lineage;
- reopen/refresh triggers.

Public machine-discovery output must never imply that crawlability grants training, licensing, rights, or implementation permission.

## Source and claim handling

A source supports only the claims it actually proves. Pages must not promote:

- a historical plan into current implementation;
- a title into a recovered article body;
- a provider feature into CrownThrive deployment;
- a research interpretation into legal/tax authority;
- a model output into a rights grant;
- a prototype into production state;
- an unavailable source into a negative fact.

Research pages should favor primary authorities and record the relevant date/jurisdiction. When current sources conflict, preserve the conflict until a higher-authority resolution exists.

Recovered CrownThrive source files remain valuable institutional evidence. Governed reconstruction may explain and modernize them, but reconstructed text must be labeled as reconstruction and link back to the source/provenance record.

## Accessibility and readability

Documentation must be usable beyond visual desktop reading. Authors should:

- use descriptive link text;
- provide alt text or equivalent explanation for meaningful visuals;
- preserve heading hierarchy;
- avoid conveying required meaning by color alone;
- label tables and code clearly;
- explain acronyms on first meaningful use where audience knowledge is uncertain;
- provide plain-language summaries for highly technical or regulated topics;
- keep technical depth available rather than deleting it for simplicity;
- structure long explanations into scannable sections.

The goal is layered readability: executive summary, practitioner detail, developer/protocol depth, and machine-readable structure can coexist on the same canonical knowledge object.

## Validation and drift control

Documentation governance should progressively automate checks for:

- broken internal links;
- orphan pages;
- missing/duplicate title or description metadata;
- heading hierarchy;
- long pages missing a TOC;
- code fences without language identifiers where language is knowable;
- missing related-page links;
- stale `as_of` or review triggers on dynamic claims;
- unsupported state words such as `production`, `approved`, `compliant`, or `certified` when evidence is absent;
- machine-record/schema validity;
- public/private data leakage;
- accessibility issues detectable automatically.

Automation may repair deterministic formatting/link defects when the correction is reversible and policy-defined. It may not rewrite consequential claims, legal language, rights, financial state, or technical authority merely to make a lint rule pass.
