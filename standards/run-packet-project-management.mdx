# Run Packet and Project-Management Standard

Every substantial CrownThrive run must be treated as a governed project increment, not an isolated chat instruction. The run packet is the machine-readable contract connecting founder intent, institutional records, agents, tools, approvals, deployment, evidence and the next run.

## Required run-packet fields

```yaml
run_id: ct.run.01J...
release_version: 2.7.9.1
program_phase: 2.97
run_type: audit_patch
objective: "Deepen governance, standards and protection baseline"
audience:
  - founder
  - institutional_operators
scope:
  included: []
  excluded: []
source_snapshot:
  source_ids: []
  website_snapshots: []
  repository_refs: []
assumptions: []
constraints: []
risks: []
roles:
  accountable: ct.role.founder
  orchestrator: ct.agent.program-orchestrator
  reviewers: []
workstreams: []
approval_rules: []
acceptance_tests: []
rollback: {}
outputs: []
dail_events: []
unresolved: []
next_run: {}
```

## Workstream design

Each workstream requires:

- objective;
- owner/agent;
- inputs;
- outputs;
- dependencies;
- autonomy class;
- data visibility;
- tools/MCPs;
- acceptance tests;
- failure behavior;
- cost/time budget;
- next handoff.

Parallel work is encouraged when dependencies allow it. Shared records and sequential writes require explicit coordination to prevent conflicting changes.

## Project roles

A run may assign specialized roles such as:

- program manager/orchestrator;
- forensic source analyst;
- institutional architect;
- CHLOM protocol architect;
- data/schema architect;
- security/privacy engineer;
- API/MCP architect;
- developer-experience lead;
- legal-policy analyst;
- IP/chain-of-title analyst;
- platform product manager;
- commerce/Stripe engineer;
- SEO/AIO engineer;
- media/canon archivist;
- ministry-content steward;
- MM Suites/phygital architect;
- QA/evaluation lead;
- release and continuity lead.

A title does not grant authority. Each role operates under the role registry and approval matrix.

## Definition of ready

Work does not begin until the run packet identifies authoritative sources, current branch/environment, intended audience, restricted data boundaries, known unresolved conflicts, required permissions and success criteria.

## Definition of done

A run is complete only when:

- requested artifacts are produced;
- records and versions are updated;
- tests/validation are recorded;
- material claims cite evidence;
- restricted content remains protected;
- failures and limitations are disclosed;
- rollback/migration notes exist;
- affected dependencies are listed;
- next-run state is explicit;
- changes are saved to the governed branch/PR or declared uncommitted.

## Handoff packet

The next run receives:

- current canonical release;
- exact branch/commit/deployment;
- completed and deferred work;
- known errors and risks;
- credentials/permissions required, by reference only;
- source and API inventory deltas;
- tests and evidence;
- next recommended sequence;
- no-repeat list so already-settled work is not rediscovered.

## Project-status projection and notification

The governed run packet remains authoritative. External project-management systems receive projections of accepted run state rather than becoming competing sources of truth.

### Collab Portal

The Collab Portal Secure API contract is verified under `S101`. Persistent Vault-managed server-side credential continuity and authenticated reads are verified, and bounded project update/read-after-write certification has passed. Broader mutation authority, effective secret-source precedence and provider webhook sender/delivery integrity remain separately gated.

After certification, each material run may project approved fields into the pinned Collab Portal project using the [Collab Portal Secure API Adapter](/developers/collab-portal-secure-api-adapter). The default PM surface is limited to project metadata/list/find and bounded project update. Project creation, task/comment/milestone/file/signature and webhook operations are not part of the verified Secure API contract and must not be fabricated.

If direct portal projection is unavailable or fails ambiguously, the run records `collab_portal_projection: blocked_or_pending`, preserves GitHub/Mintlify as the governed record, sends the required Gmail update, and continues safe parallel work.

### Project-manager communications

Every successful material pass should leave:

- an actionable GitHub PR/issue status comment where an appropriate thread exists;
- a final post-validation Gmail project update to the designated CrownThrive PM recipients;
- Collab Portal projection evidence or an explicit integration-gap/blocker state;
- the exact next packet and founder-review state.

Failures requiring attention use a separate action-needed communication rather than silently disappearing.

## Audit trail

The orchestrator must be able to answer: what was requested, what sources were used, what changed, who/what acted, what failed, what was approved, what was deployed, what project-management projections/notifications were emitted, and what remains.
