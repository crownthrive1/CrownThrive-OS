# Repository Parent-Child Technical Link Standard v1

## Purpose

A physical child repository may be technically connected to its registered parent without manufacturing governed activation. The technical link binds immutable repository identity, exact canonical parent/child Git heads, external provider observations, Guardian scope, family graph, interoperability contract and DAIL evidence.

## State separation

`TECHNICALLY_LINKED_PENDING_GOVERNANCE` means the current physical parent and child are mutually identified and exact-head evidence is recorded. It does **not** mean `linked_governed`, operational activation, sovereign voting, quorum effect, D3 authority, rights clearance, protected-runtime activation, checkout, entitlement or Phase advancement.

## Required gates

The link fails closed unless current repository observations exist for both sides and match the exact heads; the child repository ID matches the institutional registry; parent governance and child-self-activation prohibition remain enabled; the Repository Child Guardian binding is active and non-destructive; the family graph contains authority-safe Parent/Child and Guardian relationships; and the interoperability contract is registered.

## Guardian behavior

Before a verified technical link, the Guardian may emit `NURTURE_PARENT_LINK_REQUIRED`. After the exact technical link is verified, that action is resolved and the Guardian emits `NURTURE_GOVERNANCE_PENDING` until the separate governed certification/activation requirements are satisfied.

The Guardian may observe, nurture, reconcile metadata, refresh references, prepare patches and open handoffs. It may not merge, delete, archive, transfer, change visibility or self-activate the child.

## Family semantics

Within the Repository Child Guardian framework only, the parent may display as Father, the Guardian as Mother and CIE as Daughter. Those titles are presentation labels. They create no legal, biological, gender or authorization effect.

## Architecture and interoperability

Repository systems and the link contract are consumed by the interoperability agents and architecture self-model. New systems/contracts are macro architecture observations. Macro observation does not authorize autonomous application or activation.

## Founder Override ask-first rule

If the resulting exact-head source packet is technically green but governance-deadlocked, the system may prepare a deadlock preflight only. It must then ask the Founder before invoking any Founder Override. The preflight remains `AWAITING_FOUNDER_CONFIRMATION`, `override_executable=false`, and silence is not authority.
