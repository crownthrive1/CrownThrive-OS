# MCP, API and Integration Governance Standard

CrownThrive should expose a governed integration fabric rather than one uncontrolled super-API.

## Three-layer model

**Central institutional surface:** CrownThrive IO / API Gateway / MCP provides stable institutional capabilities, routing, discovery, common IDs, authorization context, events, and cross-platform workflows.

**Platform surfaces:** each platform may expose its own REST, GraphQL, webhook, vendor API, database adapter, feed, export, or MCP server according to what the underlying system supports.

**Private operational surface:** restricted internal tools, maintenance endpoints, evidence systems, admin actions, and sensitive data remain inaccessible to public/developer scopes unless an explicit role and policy allows them.

## API registry

For every platform collect: platform ID, product/vendor, base URLs by environment, documentation URL, authentication method, OAuth/OIDC support, scopes, rate limits, native endpoints, vendor endpoints, webhooks, event types, pagination, error model, SDKs, MCP tools/resources/prompts, data classifications, owner, credential owner, health check, version, last verification, and replacement/export path.

## MCP registry

Every MCP capability should identify server ID, platform, transport, deployment, authentication, tool/resource names, input/output classifications, side effects, autonomy class, approval requirements, audience, rate limits, audit requirements, and version.

Platform-specific MCPs may be hosted with the platform or in controlled engineering infrastructure. A central CrownThrive MCP may federate approved platform MCPs without exposing all internal capabilities to every caller.

## Security

Use least privilege, short-lived credentials where feasible, separate production and test access, secret-manager references rather than credentials in docs/code, request tracing, idempotency for mutations, signature verification for webhooks, and explicit private/public tool separation.

## API-first operating rule

When a platform offers a reliable supported API, prefer the API over brittle browser automation. When no API exists, create an adapter with a declared support level and migration path. Never silently scrape restricted/private surfaces as a substitute for authorization.

## Versioning

Breaking changes require explicit API/MCP versioning and migration records. A platform vendor upgrade must not silently alter the institutional contract.

## Automation

Phase 2.98 will collect available base URLs, API documentation, endpoints and integration methods platform by platform. Phase 3 converts the registry into executable adapters, health checks, credential scopes and generated developer documentation.
