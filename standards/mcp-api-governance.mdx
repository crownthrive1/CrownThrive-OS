# MCP, API and Integration Governance Standard

CrownThrive should operate a governed integration fabric: stable institutional contracts, platform-specific capabilities and replaceable vendor adapters. It should not expose one uncontrolled super-API or let each platform invent incompatible identity, event, error and authorization logic.

## Architecture layers

### Institutional API and MCP surface

CrownThrive IO/API Gateway/Institutional MCP provides:

- stable IDs and registry discovery;
- current platform/claim/policy state;
- identity/organization/role context;
- approval and DAIL references;
- cross-platform workflow routing;
- API/MCP capability discovery;
- common event and error contracts.

### CHLOM governance surface

Rights, Rules, Roles, Revenue, Records and Remedies services: evidence, approvals, DLA/licenses, entitlements, usage, cases, splits, settlements, corrections and audit.

### Platform surfaces

Each platform may expose native REST, GraphQL, webhooks, feeds, exports, database adapters, SDKs or MCP tools according to its engine and use cases.

### Private operations surface

Deployment, credentials, evidence, finance reconciliation, incident, security and administrative tools remain private and role-scoped.

### Vendor adapters

Provider-specific integrations sit behind CrownThrive contracts where practical. Stripe may be a default payment candidate; identity, storage, email, analytics, ad-server, media and other vendors remain replaceable.

## API registry minimum

For every API/interface capture:

- API ID, platform/owner and provider;
- interface class;
- environment base URLs;
- official docs/OpenAPI/GraphQL/package links;
- authentication and OIDC/OAuth issuer/audience;
- scopes/roles/relationship checks;
- endpoint/tool list;
- input/output/error/event schema versions;
- rate/usage/cost limits;
- pagination/filtering/sorting;
- idempotency/concurrency behavior;
- webhooks/events/retries/replay;
- data classification and retention;
- credential owner/secret reference;
- health/version endpoint;
- dependencies;
- support/SLA/incident path;
- export/vendor-exit/replacement path;
- last verification and test evidence;
- deprecation/migration status.

## API protocol baseline

- HTTPS/TLS for network interfaces;
- major URI/API versions for public contracts where adopted;
- backward-compatible minor changes where feasible;
- explicit deprecation and migration windows;
- OAuth/OIDC profiles based on current adopted RFCs rather than an undefined “OAuth 2.1” label alone;
- service identities for service-to-service access;
- centralized tenant, role, relationship, asset and policy authorization;
- idempotency keys for applicable mutation/financial operations;
- ETag/version preconditions for concurrency-sensitive updates;
- UTC timestamps;
- request/correlation IDs;
- standardized errors;
- audit/event references;
- no live secrets in URLs, docs or logs.

## MCP protocol profile

CrownThrive's target MCP profile is the final `2026-07-28` specification. New remote servers and federation components should be designed around:

- a stateless protocol core rather than hidden transport sessions;
- self-describing requests carrying the protocol version and caller/client context;
- `Mcp-Method` and `Mcp-Name` header-based routing and policy enforcement where applicable;
- optional `server/discover` for capability discovery;
- deterministic, cache-aware list responses without trusting stale catalogs for authority;
- Multi Round-Trip Requests for governed mid-call input or confirmation;
- formal extensions with separate registration, versions and approval rules;
- a minimum documented deprecation window and compatibility tests;
- migration away from deprecated roots, sampling, logging and legacy HTTP\+SSE behavior for new implementations.

Existing compatible MCP integrations may remain on an earlier protocol version during a recorded migration window. The registry must state the exact supported version; `MCP-compatible` without a version is not sufficient.

## Baseline service families

The CHLOM technical sources include high-level endpoint families such as:

- entitlement verification;
- provider webhook intake;
- dispute creation;
- dispute evidence submission;
- governance proposal submission;
- scoped audit-event queries;
- webhook endpoint registration.

These are source specifications to implement/test, not evidence that production routes already exist.

## MCP registry minimum

Every MCP server records:

- server ID, owner and platform;
- repository/deployment;
- transport and base URL;
- authentication/audience/scopes;
- visibility: public, partner, internal, restricted;
- tools/resources/prompts;
- input/output data class;
- side effects and autonomy class;
- approval/entitlement/policy rules;
- version and schema;
- rate/cost limits;
- health and observability;
- dependencies and fallback;
- incident/deprecation/retirement.

Every tool has a stable tool ID. Tool naming should use clear verb-object forms and must disclose side effects.

## Central federation

The central MCP/API fabric propagates:

- caller actor/service;
- tenant/organization;
- role and relationship;
- purpose and platform context;
- scopes;
- run/correlation ID;
- approval state;
- data classification;
- cost/rate budget;
- requested/compatible version.

A platform server re-evaluates authority; it does not blindly trust caller-supplied role text.

## Public, developer and private separation

### Public

Read-only approved platform/content/claim discovery.

### Authenticated customer/member

Own records, purchases, entitlements, saved content and support under purpose-limited access.

### Developer/partner

Sandbox/production APIs and MCP tools with explicit scopes, terms, quotas and certification.

### Operator/admin

Platform operations according to role and tenant.

### Restricted

Evidence, investigations, security, finance, private IP and reserved decisions through named privileged roles.

## Webhooks

Every webhook endpoint requires provider/account, environment, event list, signature algorithm/secret reference, payload version, idempotency, retry/dead-letter, replay, ordering assumptions, timeout, data class, owner, last delivery and rotation/deprecation record.

Webhook handlers must verify signatures, tolerate duplicate/out-of-order events where applicable, retrieve authoritative provider state when needed and reconcile partial failures.

## Adapter policy

Prefer supported APIs. If none exists, classify the adapter:

- supported native;
- supported vendor;
- controlled database/internal;
- feed/export;
- browser-assisted temporary;
- manual documented;
- blocked;
- deprecated.

Browser automation is never a substitute for authorization or a durable contract. Temporary adapters require an exit path.

## Developer experience

Generate reference docs and SDKs from authoritative schemas where possible. Provide sandbox identities, synthetic data, test webhooks, fixtures, rate-limit/error simulation and integration certification. Handwritten workflow guides must link to the current contract version.

## Data minimization

APIs and MCPs return only fields required for the purpose/role. Restricted evidence should usually be returned as a reference, status or signed proof—not raw content.

## Mutations and event trail

Consequential mutations return affected IDs, previous/new versions, approval, event ID and rollback/compensation reference. Accepted licenses, agreements and material decisions are immutable; amendments create linked records.

## Version/vendor drift

Automated health jobs compare live providers/interfaces to registered schemas, scopes and versions. Breaking drift creates a hold/incident and migration run packet. A vendor upgrade cannot silently change the institutional contract.
