# Executable Agent Contract & Version Convergence Standard v1.1

## Purpose

A CrownThrive agent is not executable merely because an agent row, skill name, schedule, prompt, heartbeat, or documentation page exists. Execution-eligible agents require a machine-checkable chain: registered identity, installed skill contract, explicit privilege profile, callable capability with a materialized handler, bounded authority, a real successful invocation receipt, and health/readback evidence grounded in execution.

Missing links fail closed. A descriptive-only, candidate, or disabled capability is not silently treated as runnable.

## Execution-state semantics

`test`, `controlled_test`, `active`, and exact `read_verified` skill states are execution-eligible for their governed contract and must have the executable chain. `disabled` means intentionally dormant and is not an executability failure. `candidate` remains non-execution-eligible until a governed canary and state promotion occur.

This distinction prevents the Master Suite and other registries from manufacturing authority merely to make dormant registrations look operational.

## Current whole-estate coverage

The current controlled-test census resolves **92 execution-eligible agents**, with **92 privilege-bound, 92 mapped to a materialized executable capability, and 92 carrying operational-presence evidence**. This is contract coverage, not production or economic activation.

## Authority

This convergence layer is D0-D2 only. D3 remains human-reserved. Provider writes, money movement, rights grants, checkout activation, direct-main writes, self-approval, self-certification, sovereign voting and secret/key-material return are prohibited unless a different exact governed contract independently authorizes them.

A capability can be executable while still being controlled-test and read-only, self-test-only, verify-only, or plan-only. Executability does not imply production activation.

## Archive Reverse Verification

The Archive Reverse Verifier is bound to `ct.capability.archive-reverse.verify.v1`. It remains verify-only by default and cannot run merely because the agent is registered. Execution requires the existing founder-granted standing authorization plus an exact-resource, sensitivity-bounded, short-lived lease. The v21 canary verified one algorithm member: ciphertext hash, plaintext hash, membership and canonical contract digest matched, while secret-body and key-material return remained false.

A successful reverse-verification receipt proves recoverability for that exact member only. It does not authorize bulk decryption, secret export, provider credential access or D3 action.

## Master Governed Agent Suite

The Master Suite is an umbrella registry with mixed lifecycle states. Current state is **32 test subroutes and 42 intentionally disabled dormant subroutes**. Only the 32 test subroutes receive `ct.capability.master-agent.control-self-test.v1`.

The shared self-test proves agent/skill/template/privilege/capability control-plane presence. It performs no domain action. It does not grant any provider, sales, pricing, security, identity, commerce, publication, remediation or project-management authority merely because an agent can self-test. Disabled subroutes remain disabled and are excluded from execution-coverage failure counts.

## Health rule

`healthy` in this layer means controlled-test operational presence for the exact capability that produced the receipt. It does not mean production readiness, economic approval, provider mutation authority, rights clearance or D3 authority.
