# Production Sites Bootstrap and Rollback

Production rendering is not publication authority. Each CrownThrive Sites surface must expose the registered governed-feed marker, exact surface identity, a read-only catalog proxy, a public site-consumer DID document and a deterministic public fingerprint certificate before it can consume a governed release projection.

## Acceptance cycle

A surface reaches `full_cycle_pass` only after one exact source state completes:

1. provider write and successful deployment;
2. independent public readback of the marker, exact surface and feed reference;
3. HTTP 200 readback of the proxy, DID document and certificate;
4. equality between the proxy response body SHA-256 and its digest header;
5. deliberate rollback;
6. public proof that the marker is absent and all three bootstrap endpoints are absent;
7. exact reapplication;
8. a second independent public readback.

Build success, preview success, a provider version, source history or a rendered home page cannot substitute for the cycle.

## Surface arming and release authority are separate

Bootstrap arming is evaluated per surface. A surface that completes the entire acceptance cycle may retain a bounded governed catalog-consumer lane. A surface that has not completed the cycle must remain unarmed and may not inherit another surface's proof.

This bounded runtime state is **not publication authority**. Every release still requires the active governed release policy, exact artifact/version binding, all applicable certifications, the current independent quorum including Agent D, and any human-reserved authority required by its risk class. Bootstrap PASS cannot waive a release HOLD, create a sovereign vote or turn technical evidence into commerce authority.

If a previously verified consumer loses its marker or registered feed binding, the runtime must disable that surface and quarantine queued publication work until verification returns.

## Founder authority and execution evidence are separate

A completed bounded provider task is execution evidence. It does not by itself institutionalize a continuing founder or executive override.

Under issue #150, a founder/executive override must identify the actual human signer by name and link the governed `typed_name_attestation` record before it becomes effective institutional authority. A role, account, prior message, successful provider write or bare boolean cannot substitute for the signer. Until that record exists, provider-mutation authority remains ineffective and the required question is: `Who is signing their name to this override?`

A typed name is an institutional digital-signature attestation, not cryptographic nonrepudiation. Key-backed proofs, DIDs and Verifiable Credentials remain separate phase-gated evidence.

## DID and fingerprint boundary

The public `did:web` document identifies a site consumer and its public service endpoints. The Fingerprint ID is a deterministic SHA-256 commitment under the versioned `ct-json-c14n-v1` profile.

These records are public digest evidence. They are not biometric data, a signed verifiable credential, proof of a controlled private key, sovereign agent acceptance or institutional certification. A cryptographic certification claim requires a versioned resolver profile, public verification key, protected signing key, signed credential/status record, proof anchor, rotation and independent verification.
